## The reader
- **Who:** a backend developer who runs SQLite as the database of a small web service — one server, a Python or Go app with a few worker processes.
- **Knows:** SQL and transactions (BEGIN, COMMIT, isolation in general terms); not SQLite's internals, its files on disk, or its locking.
- **Can do after the book:** decide whether WAL suits their deployment and turn it on correctly; choose a `synchronous` level knowing what each loses on an application crash and on a power loss; configure and control checkpoints; diagnose `SQLITE_BUSY` ("database is locked") errors, including the ones `busy_timeout` cannot prevent; find why a -wal file keeps growing and stop it; back the database up and handle its files without losing data.

## The brief
- **must-cover:** (MC1) how readers and the single writer interact in WAL mode (each reader's snapshot, one writer at a time); (MC2) what a checkpoint does, when it runs on its own, and what stops it from finishing; (MC3) why WAL needs shared memory (the -shm wal-index) and so does not work on a network filesystem; (MC4) how to turn WAL on and which `synchronous` setting to pair with it, with the durability each gives; (MC5) why the -wal file can grow without bound and how to stop it
- **leave-out:** the rollback journal's internals beyond one contrast; the WAL2 and BEGIN CONCURRENT branches; other databases' write-ahead logs; SQLite's C API beyond the PRAGMAs and the checkpoint call
- **trusted sources:** the SQLite documentation at sqlite.org (wal.html, pragma.html, fileformat2.html, lockingv3.html) — each still ranked per claim on the source ladder

## Chapter 1 — `how-wal-works`: "How SQLite's write-ahead log works"
- **key:** `how-wal-works` · **position:** 1 · **title:** "How SQLite's write-ahead log works" · **mode:** general
- **goal:** the reader understands how a WAL-mode database serves one writer and many readers: a commit appends frames to the -wal file and leaves the database file untouched; each reader keeps a snapshot fixed by its end mark and finds pages through the wal-index in shared memory (which is why WAL needs every process on one host); a checkpoint copies frames back and, once readers have moved on, lets the next writer reset the WAL; and a reader that stays on an old snapshot stops all of that.
- **reader tasks:**
  - T1 predict who waits for whom in a WAL database (readers, the writer, each checkpoint mode, recovery) → **deliverable:** a "who blocks whom" table, the RESTART/TRUNCATE-against-new-readers cell marked as disputed (D-01)
  - T2 decide whether a deployment can run WAL at all → **deliverable:** a checklist "Before you turn WAL on": one host, a local filesystem (not NFS or SMB), a writable directory for -wal and -shm beside the database, no need for atomic commits across ATTACHed databases, page size fixed, not on read-only media
  - T3 explain why a checkpoint is not finishing and why the -wal file does not shrink → **deliverable:** a checkpoint timeline diagram and a list "What stops a checkpoint" (a reader on an old snapshot; a write transaction in progress; another checkpointer) with "why the file keeps its size" (reset and overwrite, not truncate)
  - T4 read the three files on disk and know which one matters after a crash → **deliverable:** a table of the database, -wal and -shm files: what each holds, when it is created and deleted, whether recovery needs it

## Chapter 2 — `running-wal`: "Running SQLite in WAL mode in production"
- **key:** `running-wal` · **position:** 2 · **title:** "Running SQLite in WAL mode in production" · **mode:** general
- **goal:** the reader can turn WAL on and confirm it, pick a `synchronous` level knowing exactly what it gives up (nothing on an application crash; the latest commits on a power loss under NORMAL; and why macOS needs `fullfsync` for FULL to mean it), diagnose `SQLITE_BUSY` down to its cause — above all the deferred read-then-write transaction that `busy_timeout` never retries — keep the -wal file bounded with a checkpoint strategy they understand the cost of, and back up and move the database without losing committed data.
