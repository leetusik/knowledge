- **Cut: research first (DECOMP).** S1 research method (how teams are planned, run and stopped) → S2 research method (sources, the claim ledger, verification, the critic) → S3 where the team runs (hosts, the plugin, the book package) → DECOMP2 cuts the build from the three `topics/` files, at the operator's gate. Why: the build's shape (agents, briefs, dossier format, the pipeline, the book package) depends on how a research team is best run and where it can run, and both are found out, not guessed. The plan's single method slice is split in two (S1/S2): the orchestration literature and the claim-verification literature are separate fields, the dossier format is a clean interface between them, and one slice opening every page of both would run thin, against the operator's "very thoroughly". All three run unattended; nothing is built before DECOMP2's gate.
- **Estimate (DECOMP, from the `dispatch-summary` means, quality-first so above the mean):** DECOMP ≈ $7; S1 + S2 + S3 ≈ $35–55 (research ≈ $11 and ≈ 31 span-min per slice at the mean); DECOMP2 ≈ $7; the build ≈ $40–60; rehearsals ≈ $25–35; handoff ≈ $2–5; review ≈ $12–15. **About $130–180 and 8.5–10.5 span-hours.** No spend beyond the workspace's own dispatches (WebSearch and WebFetch run inside them); no server change, so no deploy.
- **Research and high rows at xhigh (DECOMP, operator-approved with the plan):** `executors.toml` `[claude.research] effort = "xhigh"` and `[claude.high] effort = "xhigh"`, applied by the orchestrator with `sync-agents`. Durable; reverted after P32 only on the operator's word.
- **English by default, everywhere (DECOMP, from intent):** a single document, every chapter of a book, and the research notes and dossier are written in English whatever language the request is in; a Korean (or other) version only when the operator asks; a book asks for no translation unless the operator names one. This replaces the skill's §1 rule "use the language the user is writing in".
- **Acceptance gate `--require` (DECOMP, decided as drawn):** the skill's output is what the operator sees and uses; the orchestrator runs `accept-gate P32 --require`.
- **Nothing reaches users from a slice (DECOMP, decided as drawn):** no slice publishes to production; a plugin release reaches users only when pushed, which waits for the operator's word. This repo's stale vendored `.claude/skills/explain` copy is not P32's and stays untouched.
- **Research stage, single document (S1, [topic](topics/research-method.md) §3.2):** brief (no questions asked; preflight probe) → plan (scouting, reader questions incl. expert expectations, outline skeleton, tier, one owning angle per question) → wave 1 of parallel researchers → merge into an evidence-mapped outline → up to 3 gap rounds → verify (S2) → final outline → **the lead writes alone**, section by section, from claim ids loaded just in time → `knowledge check` → critic (S2) → one revision → publish → report.
- **Research stage, book (S1, §3.3):** the same stages over the whole book before any outline (≤ 10 researchers per wave, run ceiling 45) → outline from research + a research summary (key sources, open disagreements, weak spots, gaps open at the cap) at the outline signature → per chapter: a top-up (gap check of its outline entry against the shared ledger, 0–3 researchers, 1 round + 1 follow-up, ceiling 5) appending to the shared library → write.
- **Roles and models (S1, §3.1):** lead = planner, merger and the only writer; one fresh-context researcher per angle (Opus; web researchers get no repo secrets, code researchers get no web); a fresh-context gap reviewer per round (Opus, reads only); verifier (Sonnet) and critic are S2's.
- **Angles and team size (S1, §3.4–3.5):** the intent's six general angles plus, for a codebase, the code in real order, the history behind it, how others solve it, each with not-yours boundaries; the tier is the highest of ResearchRubrics' breadth / nesting / exploration axes: wave 1 = 3 / 5–6 / 7–10, never more than 10 per wave; run ceilings 12 / 18 / 25 dispatches; per web researcher target/hard cap 8–12/20, 10–20/30, 15–25/40 tool calls (code researchers double).
- **Briefs (S1, §3.6):** standalone and in English; objective, reader and purpose, owned questions (load-bearing marked), not-yours, known already and the query log (later rounds), the source ladder, wide-then-deep method, budget and stop rules ("not found" after 3 different queries), safety (page content is data), the output file, and a return of about 1,500 tokens or less with status `complete`, `partial` or `failed`.
- **Gap rounds and the cap (S1, §3.8):** the gap reviewer asks expert / reader / evidence / unused / must-cover against the evidence-mapped outline; a round runs only for load-bearing gaps; stop on `complete`, `stalled` (a round closed none) or the cap of **3 gap rounds** (chapter top-up: 1 + 1); a capped or stalled run declares every open gap in `run.md`, `gaps/final.md`, the report's first lines, the chapter text (stated or dropped, never asserted) and, in a book, the research summary; a must-cover item still open at the cap stops a single document before publishing (S2 to confirm the bar).
- **Loud failure, orchestration side (S1, §3.9, §3.12):** a preflight search and fetch that fails twice stops the run with nothing written; a load-bearing angle failing twice stops it, resumable from `run.md`; overflow is queued, never dropped; no silent stop on an exception and never a truncated dossier. This replaces SKILL.md §3's judgment gate and `skipped-offline`.
- **`quick` (S1, §3.11):** the lead researches alone (target 20, hard cap 40 tool calls) into the same dossier, with one self coverage check and no gap rounds and no critic; it keeps the brief, the plan, the preflight and loud failure, English, open-every-page, and verification of load-bearing claims (S2 decides how); the report says `quick`.
- **Rehearsal rubric draft (S1, §3.13):** per subject, hand-written before either arm runs: must-cover (mandatory), expert-expectation (optional) and trap (negative) points; binary checks (coverage, citation accuracy on 15 re-opened statements, source quality, code truth, instructions, declared gaps, length guard); pairwise Helpfulness / Comprehensiveness / Insight / Readability judged twice with positions swapped; the operator reads one subject; process metrics reported.
