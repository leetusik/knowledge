### Book and chapter model — data contracts (P29.S1; evidence in `slices/P29.S1/result.md`)

- **Entities (P29.S1).** `Book 1─* Chapter 1─* Variant(lang) = one Document 1─* Version`.
  - The **document** stays today's unit: `rel_path`, slug, P23 version chain, search, MCP and graph are
    all unchanged.
  - A **chapter** is a thin entity that points at one document per language.
  - A **book** is an ordered list of chapters.
  - **Loose documents** (in no book) remain first-class. The library lists them under their project; the
    reader opens them with no book navigation.
- **Book (P29.S1).** Fields:
  - `slug` (`[a-z0-9-]`, unique per project);
  - `title`;
  - `kind`: `codebase` | `subject`;
  - `subject`: a display label, required for `subject`, optional for `codebase`;
  - `description?`;
  - `chapters[]`.

  Rules:
  - A book belongs to **exactly one project**, because P19 visibility is per project. Identity is
    `(tenant, project, book slug)`.
  - A project may hold 0..n books plus loose documents.
  - A **codebase** book lives in the repo's project (`project` = the repo's directory name).
  - A **subject** book lives in a project named for its subject: `project` = the subject slug, e.g.
    `finance`, `english`, `ai`. Visibility therefore toggles per subject shelf.
  - Library grouping keys: **by project** = `project` (codebase books plus loose documents); **by
    subject** = `book.subject`.
- **Chapter (P29.S1).** A manifest entry with these fields:
  - `key`: `[a-z0-9-]`, unique in its book, never reused.
  - `position`: a JSON number; ascending order, ties broken by `key`. A fractional value inserts
    without renumbering. For phase chapters, position = the phase number.
  - `title?`: an override. Absent means the shown variant's document title.
  - `variants`: `{<lang>: <rel_path>}`, where `lang` is a BCP-47 primary subtag (`en`, `ko`, …).
  - `source?`: e.g. `{"phase": "P8"}` or `{"phase": "P26", "slice": "P26.S2"}`.

  Each document is in **at most one** chapter. Chapter identity is `(tenant, project, book, key)`, which
  is durable across a reindex. The **format flag** is per document (it can differ per variant and per
  version): `html` (legacy, iframe path), `md` (plain Markdown, rendered natively today), or `native`
  (S2 defines it). It must be derivable from the file alone (extension or header), so a reindex
  re-derives it.
- **Versions × variants (P29.S1).** Each variant is its own document with its **own independent P23
  chain**; there is no joint version counter. A publish may record
  `translated_from: {lang, version}` in that variant's header, so the reader can flag a stale
  translation. For example, `p8` is EN v2 / KO v1 today.

  What the reader's switch needs per chapter: `variants[] = {lang, doc_id, rel_path, version, format,
  updated_at, translated_from?}`. Each variant's version list comes from the existing `/versions` routes.
- **Where each piece lives (P29.S1).**
  - **Book manifest, on disk:** `<root>/.books/<project>/<book>.json`. It owns the book fields plus
    chapter key, position, title, variants and source. Writes are server-only, under the write lock.
    Tenant #1 commits it together with its chapter, in the same scoped commit. Other tenants keep it
    under `tenants/<uuid>/`, uncommitted.
  - **Document:** `lang:` is added to the header. It is optional; absent means the manifest's variant
    key, else `en`.
  - **SQLite:** `books`, `chapters` and `chapter_variants` are rebuilt from the manifests by
    `server/reindex.py` (a third walk), so a DB wipe loses nothing.
  - **Postgres:** keeps only the org slug and project visibility (unchanged), plus S3's per-reader
    state.
  - Existing files are **never rewritten** to bind them into books; only manifests are written.
- **Images (P29.S1).**
  - **Storage:** `<root>/.assets/<project>/<date>-<slug>/<sha256>.<ext>`, per tenant root,
    content-addressed and immutable. Bytes are shared across versions and variants of the same document.
  - **Identity and reference:** the publish carries additive
    `assets: [{name, media_type, content_base64}]`. The server verifies magic bytes and stores each
    asset by hash. The version's header records `assets: {<name>: <sha256>.<ext>}`, and the body
    references the **name**; S2 designs the block syntax on top of that name. Each archived version
    keeps its own name map, so old versions render with their own images.
  - **Formats and limits:** `png`, `jpeg`, `webp` and `gif` only. **No SVG upload** (S2's sanitized
    inline SVG covers vector art). At most 2 MB per image, 20 per publish, and 12 MB per request.
    JPEG and WebP metadata (EXIF/GPS) are stripped server-side (a P30 dependency choice).
  - **Serving:** `GET /app/documents/{id}/assets/{sha256}.{ext}`, and the pretty
    `/@{org}/{project}/{slug}/assets/{file}`. Behind them is the same gate as `/raw`
    (`_resolve_readable_doc`: member, or a public project), and a hash not referenced by any version of
    that document is a 404. Every miss is the constant 404 (404-never-403). Responses carry the sniffed
    `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none';
    sandbox` and `Cache-Control: private` (unless the project is public). Raster bytes only, so nothing
    runs on the app origin.
  - **Deletion:** deleting a document removes its asset directory. Assets otherwise live as long as
    any version references them.
  - **Git (tenant #1):** see Operator Question 2. The default is "not committed".
- **Phase or slice → chapter (P29.S1).**
  - **Phase explain:** book `phases` in the repo's project (created on first use, title
    `"<project>, phase by phase"`). Key `p<N>` (a joint explain → `p<N>-p<M>`), position `N`, title
    `"P<N>: <phase name>"`, `source.phase`.
  - **One doc per slice:** book `p<N>` (title `"P<N>: <phase name>"`), key = the slice id lowercased
    (`s1`, `f1`), position = the slice's `order`, `source.slice`.
  - **General mode:** a subject book, as described under Book.
  - **What `/explain` sends** (all additive to `POST /api/documents`): `book: {slug, title?, kind,
    subject?}`, `chapter: {key, position?, title?, source?}`, `lang`, `translated_from?`, `assets?`.
  - **Server placement:** the server finds or creates the manifest. It resolves `(project, book, key,
    lang)`: if that variant exists, the publish is **its next version** (the same rel_path, which
    replaces the skill's list-and-match step for chapters); otherwise it creates the document and adds
    the variant. A new chapter with no `position` is appended at max+1.
  - **Without `book`/`chapter`:** today's behavior exactly (a loose document).
- **Legacy → native re-explain (P29.S1).** The first native publish onto an `html` variant is a
  **format-migration version**:
  - The html body is archived as `.versions/<project>/<date>-<slug>/vNNNN.html` (the archive directory
    is already keyed by stem).
  - The native body is written at `<date>-<slug>.<native ext>`, and the html file is removed.
  - The SQLite row keeps its `id` (its rel_path is updated in place), and the manifest variant is
    re-pointed.
  - The old rel_path stays resolvable as an **alias**: a by-path or MCP `rel_path` miss falls back to
    the stem.
  - The pretty URL is unaffected, because it is keyed by `(project, slug)`.
  - Only `html → native` is allowed; every other format change stays a 422.
  - P30 must make `parse_archive_rel_path` and the `document_versions` keying stem-based.
- **Compatibility (P29.S1).** Every change is **additive**:
  - `/documents/{id}` and `/@{org}/{project}/{slug}`: unchanged (P25 newest-wins).
  - **The reader's URLs (new):**
    - `/library` — the member's library;
    - `/@{org}` — the org's public library; the route is unused today;
    - `/@{org}/{project}/books/{book}` — a book. These are 4 segments, so they cannot collide with
      3-segment doc slugs;
    - `/@{org}/{project}/books/{book}/{key}[?lang=&v=]` — a chapter. A legacy chapter renders its
      document through the existing raw path.
  - `POST /api/documents`: new optional fields, `book`, `chapter`, `lang`, `translated_from` and
    `assets`. The `html → native` 422 is relaxed.
  - **New routes:**
    - `GET /api/books?project=`;
    - `GET`/`PUT /api/books/{project}/{book}` — the bearer write upserts the manifest and binds existing
      documents, which is how P30 migrates the 42;
    - `/app/books…`;
    - `/app/orgs/{org}/{project}/books/{book}`, public-gated by the project.
  - **Search:** FTS and embeddings over current documents, unchanged. Hits may gain
    `book`/`chapter_key`/`lang`.
  - **MCP v1:** `search`/`fetch_document` unchanged. Optional output fields `book`, `chapter_key` and
    `lang` are allowed by the contract.
  - **Graph:** nodes and edges unchanged (documents, `related`).
  - **Free:** no metering and no paid dependency.
  - **No breaking change.**
- **D13 (P29.S1).** **Not absorbed. It stays deferred.** General-learning citations are many in-body
  sources: S2's Sources block, which the research mode already writes as `#sources`. D13 is one
  public-origin URL per document. `_citation_url` stays `""`. A later refinement could return a
  chapter's public pretty URL, which is not login-gated, but that is D13's trigger to decide, not P30's.

## Operator Questions

_Questions only the operator can answer. Append only; every entry is routed at the review — folded into the acceptance walkthrough or filed with `defer-job`. An unrouted entry is a review finding._

1. **(P29.S1) Tenant #1's "private" content is public on GitHub — a live privacy fact.**
   - **The fact.** Every tenant #1 document is committed and pushed to `leetusik/knowledge`, which is a
     **PUBLIC** repo, whatever its project's P19 visibility. So "private" for tenant #1 means only
     "unreadable through the web app/API"; the text is world-readable on GitHub. That includes the
     `glide-ilab` and `base` onboarding material.
   - **Options:**
     - (a) Accept it and document that tenant #1 is publish-everything.
     - (b) Make the repo private. This breaks the public `install.sh` `git+` installer and the plugin
       marketplace.
     - (c) Stop committing tenant #1 content to this repo: back it up to a separate private remote, or
       treat it like the other tenants (box-only).
   - **Recommended default:** (c), with a separate private content remote, decided before P30 adds
     images and books to the content tree. Until you answer, nothing changes.
2. **(P29.S1) Are chapter images committed to git for tenant #1?**
   - **Recommended default:** **no.** `.assets/` is gitignored for every tenant: no new exposure on a
     public repo, and no repo bloat from binaries.
   - **Cost:** tenant #1's images then exist only on the box disk, with no off-box backup, until Q1's
     answer gives the content tree a private home. If Q1 lands on (c), commit the images there.
