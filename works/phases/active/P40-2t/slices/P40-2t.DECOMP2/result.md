## Why there is no join-rebuilt artifact (deviation 1)

`wave.md` defines a join-rebuilt artifact as a build output regenerated from **many slices'** sources. The plugin skill's companions are:
- `.agents/skills/explain/SKILL.md`, which has the same body;
- `web/public/SKILL.md`, a full copy;
- `plugin/agents/explain-critic.md`, regenerated by `--write-agents`.

They come from one source, `plugin/skills/explain/SKILL.md`. Only S1 and then S5 edit that source, and they never run side by side: S5 is declared on S1, and a shared set waits for its commit.

If the set were named as a join-rebuilt artifact, `wave.md` would apply its *At the join* rules:
- every round-1 commit (S2, S3, S4 included) waits until the wave drains, because S1 touches the artifact's source;
- S5 cannot start beside a still-running S2 or S3, because S1's commit waits for the drain;
- S1, as a wave executor, may never rebuild the artifact, so it could not prove `skills_parity.py` before returning;
- the orchestrator would need a rebuild command for the `.agents` copy, which has its own frontmatter, and no script does that.

None of this buys safety, because no two slices running together edit the source. So the companions are generated files inside S1's and S5's own sets, regenerated and parity-checked by each slice. P39-hk did the same with S10, and P39-hk's breakdown named no artifact. The intent behind the plan's wording still holds: the four files move as one unit, and two plugin slices never run together. If the orchestrator prefers the plan's wording, the switch is one edit to the breakdown's `## Join-rebuilt artifact`, and the wave then commits at the join.
