- **OQ1 (P30.S2):** Should a chapter variant name its document by `rel_path` or by a bare stem? (The plan said "stems"; P29 *Chapter* says `rel_path`.) — **decided:** `rel_path`, as in P29's contract. S5's html → native migration re-points the variant, as P29 says. Detail: `slices/P30.S2/result.md`.
- **OQ2 (P30.S2):** When a publish names a book or chapter that already exists, does it update that book's title, kind or subject, or that chapter's position, title or source? — **decided:** no. The manifest is authoritative, the request only seeds a NEW book or chapter, and `PUT /api/books/{project}/{book}` is the way to edit them. This is the most conservative option: a re-explain can never silently retitle or reorder a book.
- **OQ3 (P30.S2):** When a document bound into a chapter is deleted, should its manifest binding go too? — **decided:** the delete path is unchanged. Reads leave out a variant whose document is gone, a re-publish of that `(book, key, lang)` re-points it, and a `GET`→`PUT` round trip drops it. S8 (deleting a document purges readers' notes) may revisit this if it needs the binding removed.
- **OQ4 (P30.S3):** P29 says the svg block's "body is one `<svg>` element, plus `label`", but every typed body is YAML. What is the svg block's shape? **decided:** a YAML mapping, `{svg: <source>, label, caption?}`, the same shape as the figure row's svg item.
- **OQ5 (P30.S3):** Should ingest accept an unknown callout type, tone, shape, diagram kind or chart type and render it by the fallback (P29 says an unknown alert renders as NOTE, and `03-diagrams` calls this "P30's call"), or reject it? **decided:** reject it with a 422. This is the stricter option. The renderer keeps the fallbacks as defence in depth. An edge or step naming an unknown node is also a 422 (`diagram-ref`).
- **OQ6 (P30.S3):** Ids carried inside YAML conflict: P29 *Quiz* says item ids are required, while *Ids* mints `item-<n>`. What is the scope of a quiz option id? **decided:** quiz item, option and sources item ids are required, so `item-<n>` is never minted. Item and sources ids share the document namespace. Option ids are unique within their item (the signed quiz round's `answer: [b]`).
- **OQ7 (P30.S3):** What do h1, h5, h6 and headings or typed blocks nested in lists, quotes or callouts do? **decided:** every one is rejected. The title comes from the header, sections are h2–h4, and typed blocks and id'd code sit at the top level only, so every section boundary is a top-level block.
- **OQ8 (P30.S3):** What do annotation offsets measure? P29 *Anchors* points at the search projection; the signed `05-annotations` round defines a section's text as its passage containers. **decided:** the signed round. Sections are id'd top-level blocks, and the text is paragraphs, callout titles, table cells and code joined by "\n", with headings and typed-block text contributing nothing. There is no whitespace collapse (the plan's guess), and offsets count code points. Search uses a separate, wider `search_text`. Three related choices, also strict: GFM bare-email autolinks become `mailto:`, which is rejected; svg `class` is limited to `kb-fill-<tone>`/`kb-stroke-<tone>`; and an asset name is `[A-Za-z0-9][A-Za-z0-9._-]{0,127}` (S4 adopts it).
- **OQ9 (P30.S4):** P29 says JPEG and WebP metadata are stripped "(a P30 dependency choice)"; the plan says re-encoding must keep the pixels or the format is rejected. Re-encoding a JPEG or lossy WebP with Pillow is lossy. How are images stripped? — **decided:** at the container level, never by re-encoding, for all four formats (JPEG APPn/COM, PNG ancillary chunks, WebP EXIF/XMP, GIF comments and non-loop application extensions). The stripped bytes are decoded and compared with the original's pixels, and a mismatch is a 422. An EXIF orientation other than 1 is written back as an orientation-only block, so a phone photo still displays upright with its GPS, camera and time tags gone. No format is rejected. Pillow 13 is added for decoding, the size and the GIF still only.
- **OQ10 (P30.S4):** P29 draws a still frame only for an animated GIF. What happens to an animated PNG or WebP? — **decided:** rejected with `asset-animated` (the stricter option), so every animated image has the still the reduced-motion rule needs.
- **OQ11 (P30.S4):** P29 says `Cache-Control: private` unless the project is public, with no lifetime. — **decided:** `private, max-age=300`, or `public, max-age=300` only when the read came through the public path. The bytes are immutable, so the only staleness is a revoked right to read, and five minutes bounds it. The BFF relay re-asserts the same two values.
- **OQ12 (P30.S4):** Does a new version inherit the previous version's images, and may any document format carry assets? — **decided:** no inheritance: a version's map is exactly what its publish sent, and the archived version keeps its own map and files (P29). A re-explain re-sends its images, and S5's unknown-`asset:` 422 catches a missing one. An `html` document may not carry assets (`asset-format`: its sandbox could not load them); `md` may until S5 decides for `native`.
- **OQ13 (P30.S4):** Limits and deploy settings P29 does not state. — **decided:** a 40-megapixel cap per image (`asset-dimensions`, the decompression-bomb guard; an 8K screenshot fits); the 12 MB total counts decoded bytes; `deploy/knowledge.conf` raises `client_max_body_size` 5m → 20m (12 MB base64-encoded is about 16 MB) and adds the regex location that steers the asset relay to the web app. Both take effect at the next deploy, on the operator's word.

## P30.S9

- **OQ31 (P30.S9):** What does the re-anchoring write-back rewrite? The plan adds "the new offsets when found"; P29 says only that `anchor_status` and `anchored_version` are written back. — **decided:** only those two columns. The captured anchor (`block_id` and `quote`: exact, prefix, suffix, start, end) is never rewritten, and every read resolves from it against the version on screen. So a fuzzy match never compounds across versions, a `block` or `orphan` comes back by itself if a later version restores the text, and the signed "Made on {Language} v{n}" and "Read this section in v{n} →" stay true (the row's `lang`/`version` plus its original `block_id`). `updated_at` is not bumped: it stays the reader's own edit time. This is the option that can never lose or distort a reader's annotation.
- **OQ32 (P30.S9):** What does `anchored_version` mean once the ladder runs? — **decided:** the newest version on which the ladder found the text (exact, fuzzy or moved); it does not move on `block` or `orphan`. It is written only by a read of the document's current version, only for the caller's own rows, only when it or the status changes, and never over a result computed against a newer version (`anchored_version <= target` in the UPDATE). An old-version read (`?v=`) resolves for that version and writes nothing.
- **OQ33 (P30.S9):** The fuzzy method. P29 says only "similarity ≥ 0.8 over the quote with its context". — **decided:** similarity = 1 − Levenshtein distance / the longer length (bit-parallel Myers in pure Python, no new dependency). A hit needs ≥ 0.8 on both the quote alone and on prefix + quote + suffix against the candidate span widened by the prefix's and suffix's lengths: the quote-alone bar stops unchanged context from carrying a short, changed quote onto other words. Candidates rank by context similarity, then quote similarity, then nearness to the stored `start`, then position. A quote under 4 characters never matches fuzzily. "Moved" is an exact match only, ranked by how much stored context it repeats, then document order.
- **OQ34 (P30.S9):** Edge cases P29 leaves open. — **decided:** (a) a block note (no quote) on a retired id is `orphan` (P29 rung 5), never re-homed; (b) a section bookmark whose id is retired falls back to the nearest preceding id of the version it was made on (`place.exact: false`), else no section: bookmarks have no orphan state and are never dropped; (c) a version whose source is not native, whose archive row is missing, or which no longer parses is not resolved: the stored anchor is reported with `method: "stored"` and nothing is written, so a stricter future parser or a missing archive can never orphan a chapter; (d) another language's annotations are resolved in their own variant's current version (their status written back) and only their section is mapped onto the variant on screen; they are never painted; (e) `resume` maps the unit's latest position (any variant) onto the variant on screen by id, else its fraction; (f) the payload changes are additive except that the reads split orphans out of `annotations` into `unanchored` (no client consumed S8's shape yet).

## P30.S10

- **OQ35 (P30.S10):** In what unit does the server send an interval (08-review: "in days or minutes")? — **decided:** whole minutes, in every `previews.*.interval` and every write's `card.interval`; the page formats it (minutes, hours, days, months, years). A review interval is whole days, so it is an exact multiple of 1,440.
- **OQ36 (P30.S10):** What do `done_today` and the two daily limits count? — **decided:** `done_today` = distinct cards reviewed on the review surface today; the seeding review (a quiz answered in a chapter) is logged but never counted. A card back from Again today is not counted again and is served free of the reviews budget, but once `done_today` reaches `max_reviews_per_day` every card is held (08-review: the rating that reaches the limit ends the session). `new_highlights_per_day` counts highlight cards first reviewed today, and new highlights also draw on the reviews budget. Order: overdue relearning, then by due, then new highlights after the due cards (confirming the canvas's assumption).
- **OQ37 (P30.S10):** The day boundary. — **decided:** the review day is `[start, end)` from `day_starts_at_hour` in the profile's `time_zone` (UTC until the browser sets one); due = `due < end`, so a card due exactly at the next day's start belongs to the next day (P29's "due <= end of today", the end instant read as tomorrow's).
- **OQ38 (P30.S10):** FSRS fuzz is random, so a preview could differ from the rating's outcome. — **decided:** the fuzz draw is seeded by `(card id, review number)` (a subclass overrides py-fsrs's `_get_fuzzed_interval`, keeping the library's fuzz ranges), so a preview is exactly the interval the same rating then gets. `fsrs==6.3.2` is pinned exactly; an upgrade must re-check that private hook.
- **OQ39 (P30.S10):** Where does idempotence keep a review's result, with S8's tables fixed? — **decided:** `review_id` is the `review_logs` row id, and the log's `response` jsonb is `{answer, due, state}` (plus `seeded_by` on a seeding log), so a repeated id writes nothing and returns the stored outcome with current counts (`replayed: true`). A `review_id` already used for another card, or a rating on a suspended card, is a 409; another user's id, a retired card or an unreadable one is the 404. `state_before` 0 means never reviewed. No migration.
- **OQ40 (P30.S10):** How are drift and readability resolved with a `unit` that can lag? — **decided:** lazily, on every queue read and card write, through the gate: a `d:<doc>` card resolves through that document (also once it is bound into a book); a `c:<book>/<key>` card through the book's live variants of that chapter, so a chapter removed from its book hides its cards (kept, not deleted) until it is bound again. A card renders in the reader's last-used language (newest position), else its own, else `en`. A changed `type` resets the card (FSRS new, logs kept, `reset: true`); an id gone from EVERY readable variant's current version, each one parsed, retires it; an unparseable or non-native version decides nothing and the card is just not shown.
- **OQ41 (P30.S10):** Additions beyond P29's payloads. — **decided:** the queue adds `profile` and `limit_reached`; `where` adds `chapter_index`, `chapter_count`, `block_id`, `quiz_title`, `item_index`, `item_count` (08-review 11), and `block_title`, `annotation_id` for a highlight; a highlight's `front` adds `context` (80 characters each side, from the resolved section, else the stored prefix and suffix), `anchor` and `lang`; a card adds `status`, `reset`, `last_review`, `created_at`; the review reply adds `due_today`, `previews`, `next` (the queue head), `replayed` and `day`; every annotation carries `review`; `href` is `/@{org}/{project}/books/{book}/{key}?lang=…#{block}`, `/@{org}/{project}/{slug}#{block}`, or `/documents/{id}#{block}` for a slug-less tenant.
