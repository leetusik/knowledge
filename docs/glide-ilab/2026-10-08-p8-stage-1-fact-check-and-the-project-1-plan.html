The short answer

Stage 1 today is a weekly summarization pipeline and a read-only list page. Nothing else from the roadmap runs. A GitHub Actions job collects links from 9 investment houses every Sunday, summarizes each report with Codex, and writes eight summary columns into one table, research_documents (878 rows, 872 summarized, 72 consecutive weeks of history). A Next.js page owned by another team lists 347 of those rows. There is no theme, signal, stance or conflict anywhere on the page, and no weekly email exists in any repo, table or schedule. P8.S5 result §0; P8.S2 §0–§1; P8.S3 §1; P8.S4 §1–§2

Five findings change the plan more than any other (S5 §0):

  1. The roadmap's signal layer already exists as a dormant prototype. An unmerged July 2026 branch created five live tables and filled them once, on 2026-07-08: 201 signals from 3 documents, 120 themes, 644 aliases, 95 entities. Nothing has written to them since. “Stage 0” is therefore adopt or migrate populated tables, and signal extraction is a port-or-rebuild choice. S2 §9; S3 §2
  2. There is no email anywhere. No code, no dependency, no schedule, no recipient list. The only email table, mk_email_logs, holds 30 payment and cancellation mails, the last on 2026-04-07. Both email deliverables are greenfield. S2 §0; S3 DB-13; S4 §6
  3. The page lives in another team's repositories, and its tail is junk. dashboard-frontend and dashboard-backend are invisible to the operator's GitHub account. The last pages of the list show 12 Deutsche Bank disclaimer pages and 2023 J.P. Morgan articles as research, and 60.2 % of the summarized history cannot be listed at all. S2 §1.3; S4 §1.6–§1.8
  4. The “Hankyung ≥ 1 year” table covers six months. reports holds 2,270 rows from 2026-01-02 to 06-25, loaded once. S3 DB-6
  5. The operator cannot write anywhere. READ on the monorepo only, a read-only DB role with no staging copy, no GCP access, no CI on pull requests and no CODEOWNERS. Every code phase needs a merge path before it can finish. S2 §0; S3 DB-20/21

Out of these facts P8 proposes eight phases (PP-1 to PP-8), recommends porting the prototype selectively, drafts a scope-cut proposal for 대표, puts ten decisions to the operator (Q1–Q10), and hands Jake a 25-item Korean question block. 2. How P8 checked the facts

A fact-check is only as good as its evidence discipline, so it is worth seeing how the phase was cut. P8 was decomposed into five research slices that ran strictly in order, each on a different instrument, followed by a review. No slice wrote product code, no slice wrote to the database, and the GitHub Actions workflow was never dispatched. The whole phase ran between 10:26 and 13:45 KST on 2026-10-08. phase.json created_at / completed_at; phase.md ## Decisions, Breakdown

Claims before facts. S1 went first and turned the two Korean documents into a numbered register, each claim tagged with where it could be verified: repo, DB or page. Later slices then had a checklist rather than a vague mandate, and the review could count coverage mechanically: the 46 repo-verifiable, 48 DB-verifiable and 11 page-verifiable claims each got a row. phase.md ## Slices; P8.REVIEW result §1

Read-only by construction. The database was reached through a Postgres role named agent_readonly that holds only a SELECT grant, over Supabase's session pooler. Every public table has Row Level Security (RLS) turned on, which matters because Postgres applies a default-deny rule to such tables: “If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified” (PostgreSQL documentation, Row Security Policies — postgresql.org). The operator therefore added a for select … using (true) policy for that role on all 351 public tables, cleared with Jake first. A write attempt returned “permission denied”, and a table created later reads as zero rows until the policy is added to it too, which is one of the questions for Jake (F-4). intent.md Clarifications; S3 DB-20

One deliberate exception

The page is behind a login. The operator allowed the orchestrator to drive their own Chrome, already signed in with a Pro subscription, through the Claude in Chrome extension: navigate, read text, screenshot, nothing else. The workspace contract normally forbids driving the operator's profile; this was an explicit, P8-only, read-only override, and the review insists it is recorded as “how the operator views the Dashboard”, never as an agent verification runtime. Executors never touched a browser; they analysed the capture files. intent.md, Access and instruments; P8.REVIEW result §5

What the review checked. Beyond re-running each slice's own validation, the reviewer opened 36 evidence pointers at random: workflow lines, the publish SQL, the query log rows behind the headline counts, the capture files behind the page facts, and the extracted document lines behind the deliverable list. All 36 held. It also reconciled the numbers across slices and found no contradiction, listing the few early leads that later slices corrected: a news-table count of 4,985 in intent.md against 4,988 in S3 (different read times), a stale reltuples estimate of 0 candidates against the real 26, and a capture note's “32 undated” that S4 re-summed to 35. 3. Stage 1 as it actually runs

Here is the system as the four sources agree it exists. Dashed boxes are things that exist but do not run; orange borders mark components outside the monorepo.

3.1 The weekly job and its clock

The only scheduled Stage-1 work on main is the workflow .github/workflows/ib-research-report-pipeline.yml. Its trigger, quoted from the file:

schedule:
  - cron: "37 0 * * 0"

GitHub evaluates cron in UTC (“By default, scheduled workflows run in UTC” — GitHub Docs, Events that trigger workflows — docs.github.com), so 37 0 * * 0 is Sunday 00:37 UTC, which is Sunday 09:37 KST. The team's roadmap says collection happens on Sunday, and that much is true. But the last three scheduled runs were created at 14:21, 14:41 and 15:17 KST and then ran for hours. GitHub's documentation warns that “the schedule event can be delayed during periods of high loads of GitHub Actions workflow runs” and that high-load times include the start of every hour (same page). Whether load explains a gap of five hours is not established by the phase; what the plan does is treat the observed afternoon start as the fact to design around, which is why the weekly aggregation slot becomes a question for Jake (F-21) instead of an assumption. S2 §1.1 and §0 (gh run list); S5 B-25

Two more clock facts: a second workflow refreshes the Codex authentication token daily at 24 19 * * * UTC, which is 04:24 KST; and scheduled link collection has only existed since pull request #78 on 2026-09-28, so the first scheduled registration of new links was 2026-10-04. Each job is bounded by GitHub's limit that “each job in a workflow can run for up to 6 hours of execution time” (GitHub Docs, Actions limits — docs.github.com), and the workflow file itself records a single document taking 40m45s, which is why adding a signal-extraction step raises a budget question (PP-4 risk 6). S2 §1.1; P8.REVIEW spot-checks 1–4

3.2 What publish writes, and what it never writes

The “AI RESEARCH SUMMARY” users see is produced entirely by this pipeline. Its publish step runs one UPDATE, quoted from storage/supabase.py (lines 439–449):

update public.research_documents
   set title_ko = %(title_ko)s,
       summary_short_ko = %(summary_short_ko)s,
       summary_detailed_ko = %(summary_detailed_ko)s,
       summary_status = %(summary_status)s,
       summary_model = %(summary_model)s,
       summary_prompt_version = %(summary_prompt_version)s,
       summary_generated_at = now(),
       updated_at = now()

Eight columns, nothing more. In particular the pipeline never stores the report body: text_content, content_hash, storage_uri and friends were written by a crawler that was retired in pull request #102 and are untouched since. The body exists only on the Actions runner during the run. This single fact drives much of the plan: the roadmap's principle of 원문 비저장 (do not store the original text) is honoured by today's code, but 822 legacy rows still hold 6.6 million characters of body text from the old crawler, and any signal-extraction step must either run inside the weekly run, where the body still exists, or re-capture the pages. S2 §2; S3 DB-3, DB-4; S5 B-14

Three fields reach the page from this step. title_ko is the headline, the five bullets of summary_short_ko are the “AI RESEARCH SUMMARY” panel (bullet 1 doubles as the list card's teaser), and summary_detailed_ko is the paragraph section “리서치 본문 요약”. The prompt labels are inline-materials-v1+derive-v1 on 766 rows, while 106 rows still carry the retired crawler's labels (104 of them v7_reader_tone), and 6 rows have no summary at all. Deliverable R3, “no effect on the existing AI summary”, therefore has to freeze three fields, two prompt files, the labels and the models, and accept that the baseline is already mixed. 4. The dormant signal prototype

The most consequential discovery was not on main. S2 searched every branch and found origin/data-investment-research-crawling/feat/new-tasks, six commits from 2026-06-25 to 07-08, never merged into any main or develop, and dropped silently when its component was removed in pull request #102. What the 201 signals look like tells you what a port would inherit. Stance is bull 149, bear 39, neutral 13. Confidence runs from 0.62 to 0.98 with a mean of 0.847, so the roadmap's “below 0.6 goes to review” gate would filter nothing. And of the 39 documents the run marked success, 36 produced no signal rows at all: a silent failure nobody has explained. S3 §2.2, DB-9–DB-12

Why this changes the plan

The onboarding doc describes Stage 0 as “create the shared tables” and R2 as “build signal extraction and backfill six months”. Both premises are off. The tables exist and hold data, with foreign keys and ON DELETE CASCADE, so Stage 0 becomes a migration of populated tables (PP-2). The document backfill also already exists: 318 dated documents sit in the last 183 days and 72 consecutive ISO weeks of history are in the table, from the retired crawler's 2026-05-18 run. What does not exist is the signal backfill, so R2 becomes “extract signals over existing rows”, not “collect six months of reports”. S5 B-7, B-11, B-28; S3 Q2aa, Q2as

Port or rebuild

S5 lays out two options and a default. Option A, port selectively: keep the live tables after migration, keep the seeded dictionaries, keep the v3 prompt and its JSON schema as the starting prompt, and move the extraction call into the pipeline as a new stage running on the pipeline's Codex runtime over the captured text inside the run; re-implement the aggregation rules from R1's numbers rather than from the prototype's engine. Option B, rebuild: write extraction fresh inside the pipeline from the roadmap's steps and take only the seed data. Six facts decide between them: the prototype reads stored text_content that the pipeline never writes; its trend rules differ from the roadmap's (a 24-week slope with fixed thresholds 0.3 / −0.1 and no house minimum, against the roadmap's 4-week slope, two-house rule and a logarithmic disagreement formula); its schema lacks the Stage-0 ids; its rows carry no evidence sentence; the 36 empty successes; and the 2-of-430 entity linking. The recommended default is A, flipping to B if Jake says the prototype was rejected on purpose, if the empty successes are a model failure, if Codex cannot carry JSON-schema extraction at acceptable cost, or if PP-2 chooses fresh tables. S5 §D.2; S2 §9.4, DR-19–DR-22

8. Assessment

Assessment (the author's judgment, not a finding of the phase)

The fact-check is unusually well grounded. Four independent instruments agreeing house by house on the number 347 (page footer, API total, and a DB query) is the kind of triangulation most audits never reach, and the review's 36 spot-checks all held. A reader can trust the as-is map.

The plan is honest about time, which is its main virtue and its main warning. Every PP row carries a “realistic from 10/8” date that is later than the documents want, and the realistic dates themselves assume Jake answers the P1 questions inside week 1. If F-4 (migrations and staging), F-7 (the prototype's status) or F-29 (the email tool) slips past 10/16, the SC-2 and SC-3 variants are not pessimism but the plan.

Access, not engineering, is the critical path. Five of the five blocking rows are about access and ownership (a merge path, invisible repos, no staging DB, no email tool, no repo location). Sending the 25-item block before the Friday walkthrough is therefore the single highest-leverage action this week, and it is the one that needs no code.

Where I would weigh the evidence differently from the documents: the roadmap's “Sunday collection, Monday 07:00 email” is written as if the pipeline finished Sunday morning. The observed afternoon starts plus multi-hour runs make an early-Monday aggregation (S5's default for F-21) the safer design, and GitHub's own guidance that scheduled runs can be delayed under load supports not relying on the nominal minute.

Two things remain unverified and should stay labelled so: the detail API's 404 beyond the 183-day window is secondhand from issue #65, and the cause of the five-hour cron gap was not investigated. Neither changes the plan today.

Where sources conflicted, the later slice wins and the correction is on record: the news-table count (4,985 vs 4,988, different read times), the candidate count (0 from a stale planner estimate vs 26 counted), the undated count (32 mis-summed vs 35), and the “exactly five bullets” claim (S3) refined by S4 into five on pipeline rows and six on three legacy rows.
