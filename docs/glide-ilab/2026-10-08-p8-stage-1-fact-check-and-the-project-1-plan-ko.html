2. P8은 어떻게 사실을 확인했나

사실 확인은 근거 규율만큼만 좋다. 그래서 페이즈가 어떻게 잘렸는지 볼 가치가 있다. P8은 다섯 개의 리서치 슬라이스로 분해돼 엄격히 순서대로, 각기 다른 도구로 실행됐고, 마지막에 리뷰가 따랐다. 어떤 슬라이스도 제품 코드를 쓰지 않았고, DB에 쓰지 않았으며, GitHub Actions 워크플로는 한 번도 수동 실행되지 않았다. 페이즈 전체는 2026-10-08 10:26부터 13:45(KST) 사이에 끝났다. phase.json created_at / completed_at; phase.md ## Decisions, Breakdown

주장 먼저, 사실 다음. S1이 먼저 두 한국어 문서를 번호 매긴 등록부로 바꾸고, 각 주장에 어디서 확인할 수 있는지(저장소, DB, 페이지) 표시를 달았다. 뒤의 슬라이스들은 막연한 임무 대신 체크리스트를 받았고, 리뷰는 커버리지를 기계적으로 셀 수 있었다. 저장소로 확인 가능한 46개, DB로 48개, 페이지로 11개 주장이 각각 한 행씩 받았다. phase.md ## Slices; P8.REVIEW result §1

구조적으로 읽기 전용. 데이터베이스에는 SELECT 권한만 가진 agent_readonly라는 Postgres 역할로, Supabase의 세션 풀러를 거쳐 접근했다. 모든 public 테이블에 행 수준 보안(RLS)이 켜져 있는데, 이것이 중요한 이유는 Postgres가 그런 테이블에 기본 거부 규칙을 적용하기 때문이다. “If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified”(PostgreSQL 문서, Row Security Policies — postgresql.org). 그래서 운영자는 Jake와 먼저 확인한 뒤 public 테이블 351개 모두에 그 역할용 for select … using (true) 정책을 추가했다. 쓰기 시도는 “permission denied”를 돌려줬고, 나중에 만들어지는 테이블은 정책이 추가될 때까지 0행으로 읽히는데, 이것이 Jake에게 묻는 질문 중 하나다(F-4). intent.md Clarifications; S3 DB-20

3. 실제로 돌아가고 있는 1단계

네 출처가 일치하는 대로 그린 시스템이다. 점선 상자는 존재하지만 돌지 않는 것, 주황 테두리는 모노레포 밖의 구성 요소다.

3.1 주간 작업과 그 시계

main에 있는 유일한 예약된 1단계 작업은 워크플로 .github/workflows/ib-research-report-pipeline.yml이다. 파일에서 그대로 인용한 트리거:

schedule:
  - cron: "37 0 * * 0"

GitHub는 cron을 UTC로 평가하므로(“By default, scheduled workflows run in UTC” — GitHub Docs, Events that trigger workflows — docs.github.com) 37 0 * * 0은 일요일 00:37 UTC, 곧 일요일 09:37 KST다. 팀 로드맵은 수집이 일요일에 일어난다고 하고, 그 점은 사실이다. 그러나 최근 세 번의 예약 실행은 14:21, 14:41, 15:17 KST에 생성됐고 그 뒤 몇 시간을 돌았다. GitHub 문서는 “the schedule event can be delayed during periods of high loads of GitHub Actions workflow runs”라고 경고하며 매시 정각이 고부하 시간대에 포함된다고 말한다(같은 페이지). 부하가 다섯 시간의 간격을 설명하는지는 이 페이즈가 확정하지 않았다. 계획이 한 일은 관찰된 오후 시작을 설계의 전제로 삼는 것이고, 그래서 주간 집계 시각이 가정이 아니라 Jake에게 묻는 질문(F-21)이 됐다. S2 §1.1 and §0 (gh run list); S5 B-25

시계에 관한 사실 둘 더. 두 번째 워크플로가 Codex 인증 토큰을 매일 24 19 * * * UTC, 곧 04:24 KST에 갱신한다. 그리고 예약된 링크 수집은 2026-09-28의 풀 리퀘스트 #78 이후에야 존재하므로, 새 링크가 처음 예약 등록된 날은 2026-10-04다. 각 작업은 “each job in a workflow can run for up to 6 hours of execution time”이라는 GitHub 한도(GitHub Docs, Actions limits — docs.github.com)에 묶이고, 워크플로 파일 자체에 문서 한 건이 40분 45초 걸린 기록이 있다. 신호 추출 단계를 추가하는 일이 예산 질문을 낳는 이유다(PP-4 위험 6). S2 §1.1; P8.REVIEW spot-checks 1–4

3.2 publish가 쓰는 것, 절대 쓰지 않는 것

사용자가 보는 “AI RESEARCH SUMMARY”는 전부 이 파이프라인이 만든다. publish 단계는 UPDATE 하나를 실행하는데, storage/supabase.py(439–449행)에서 그대로 인용하면 다음과 같다.

update public.research_documents
   set title_ko = %(title_ko)s,
       summary_short_ko = %(summary_short_ko)s,
       summary_detailed_ko = %(summary_detailed_ko)s,
       summary_status = %(summary_status)s,
       summary_model = %(summary_model)s,
       summary_prompt_version = %(summary_prompt_version)s,
       summary_generated_at = now(),
       updated_at = now()

컬럼 여덟 개, 그 이상은 없다. 특히 파이프라인은 리포트 본문을 절대 저장하지 않는다. text_content, content_hash, storage_uri 등은 풀 리퀘스트 #102에서 퇴역한 크롤러가 쓰던 것이고 그 뒤로 손대지 않았다. 본문은 실행 중 Actions 러너에만 존재한다. 이 한 가지 사실이 계획의 상당 부분을 끌고 간다. 로드맵의 원문 비저장 원칙(원문을 저장하지 않는다)을 오늘의 코드는 지키고 있지만, 레거시 822행에는 옛 크롤러의 본문 660만 자가 아직 남아 있고, 어떤 신호 추출 단계든 본문이 아직 있는 주간 실행 안에서 돌거나 페이지를 다시 캡처해야 한다. S2 §2; S3 DB-3, DB-4; S5 B-14

이 단계에서 세 필드가 페이지에 닿는다. title_ko는 제목이고, summary_short_ko의 다섯 불릿이 “AI RESEARCH SUMMARY” 패널이며(첫 불릿은 목록 카드의 미리보기 문장을 겸한다), summary_detailed_ko는 문단 섹션 “리서치 본문 요약”이다. 프롬프트 라벨은 766행에서 inline-materials-v1+derive-v1이고, 106행은 아직 퇴역 크롤러의 라벨(그중 104행이 v7_reader_tone)을 달고 있으며, 6행은 요약이 아예 없다. 따라서 산출물 R3 “기존 AI 요약 무영향”은 필드 세 개, 프롬프트 파일 두 개, 라벨, 모델을 동결해야 하고, 기준선이 이미 섞여 있다는 사실을 받아들여야 한다. S2 §3; S3 DB-17; S4 DP-4; S5 B-26

3.3 페이지가 보여 주는 것

캡처 덕분에 페이지를 충실하게 그릴 수 있다. 목록은 섞인 피드 하나다. 각 카드에는 하우스 배지, 한국어 제목, 한 문장 미리보기, 날짜가 있다. 상세 페이지는 원문 링크와 요약 섹션 두 개를 더한다. 아래는 2026-10-08에 캡처한 1페이지의 첫 카드이고, 각 요소 뒤의 API 필드를 함께 표시했다.
