Background

Every team has two rulebooks. One is written down: a README, a pull-request template, an AGENTS.md. The other lives only in habit: how people name branches, whether they squash, who presses the merge button. A newcomer usually learns the second rulebook the slow way, by having a first PR corrected. P1 tried to shortcut that by reading the habit directly out of the history, and that is the story this page tells.

Beginner primer: the five terms this page leans on (skip if you know them)
  • Commit message convention. An agreed shape for the first line of a commit. This team uses Conventional Commits: type(scope): summary, e.g. fix(ai-chat): batch ETF summary reads. The type says what kind of change it is (feat, fix, refactor, test, chore, docs…); the scope says which part of the code it touches.
  • Pull request (PR). A request on GitHub to merge your branch into main. It has a title, a body (description) and a list of commits.
  • Squash merge. One of GitHub's three merge buttons. It folds all of a PR's commits into one new commit on main. The other two keep every commit (merge commit, rebase).
  • CI (continuous integration). A robot that runs the tests automatically on every push or PR and marks it green or red. This repo has none on PRs, which turns out to matter a lot.
  • Trailer. A Key: value line at the very end of a commit message, such as Co-Authored-By: Someone <email>. Git and GitHub read these to credit co-authors.

Two ideas carry the whole workflow. The first is about history, the second about safety.

Idea 1: the PR title becomes history, and branch commits become its bullets

Squash merging rewrites your branch into one commit. GitHub builds that commit's message from your PR, and that message is what everyone will see in git log forever. Here is a real one, PR #108, which had five branch commits:

Three rules fall straight out of this picture. Don't write (#N) in a title: GitHub adds it, and the team has already been bitten by doubles like (#62) (#66) in a6853fc. Write every branch commit conventionally, because each one is published as a bullet (427 of 502 branch commits already are). And the subtle one: on a single-commit PR, GitHub uses the commit's headline, not the PR title. On #49 the title was renamed 17 seconds before merge, yet 61e14e8 kept the old commit headline. If your PR has one commit, fix the commit, not the title.

Idea 2: nothing checks your PR, so your Verification section is the CI

Most teams have a robot standing between a PR and main. Here, there is none:

  • none of the three GitHub Actions workflows has a pull_request or push trigger; all three serve the IB pipeline on a schedule or by hand;
  • main is unprotected (the protection API answers 404), and no check is required;
  • 71 of 72 PRs have an empty check list;
  • no PR has ever had a formal GitHub review; the lead posts AI review reports as comments and merges his own PRs.

Yet merging to main has real effects. A change under ai-chat-backend/ redeploys DEV within minutes; a pipeline change runs for real at the next Sunday cron, writing to the KB and the database. So the guarantee that your change works comes from exactly one place: you ran the tests, and you wrote down what you ran, what you got, on which commit, and what you did not check, in the PR's ## Verification section. That last part comes straight from ai-chat-backend/AGENTS.md: "Report verified results, limitations, and checks that did not run separately."

2. The pull request

The template, .github/pull_request_template.md, verbatim:

## Summary
<!-- Describe what this pull request accomplishes. -->

## What is changed
<!-- List the concrete behavior or code changes. -->

## Why
<!-- Explain why this change is necessary. -->

## Related issue
<!-- Use `Closes #123`, `Refs #123`, or `None`. -->

It arrived in #82 together with the team skill .agents/skills/create-pull-request/SKILL.md, which adds: English; write only from the final diff, commits and issue (no conversation, no abandoned approaches); every section non-empty; pass the body with --body-file. The template has no Verification section, but 15 of the 26 PRs since #82 add one between What is changed and Why, and your rules make it mandatory.

Where the written skill and the real practice disagree. The skill says: if the branch name contains issue-<N>, write Closes #N. But issue #65 is an umbrella with many items, and PRs on task/issue-65-phase2 (#95), task/issue-65-tdf-search (#100), -16 (#109) and -25 (#110) all used Refs #65. Following the skill literally would close the umbrella by accident. Your CLAUDE.local.md overrides it: Closes #N only when the merge fully resolves the issue, otherwise Refs #N — <which part>, even on a task/issue-N branch. #107's body is the model: Refs #65 — item 23 only; this PR does not close the full issue.

Merging: 58 of 60 merges into main are squashes. The two merge commits, #1 and #14, are repository imports, which docs/repository-migration.md requires to use "Create a merge commit" so the imported history survives. Rebase merge is enabled but has never been used. Median time from open to merge is 1.1 hours: PRs are usually opened when the work is already done, often as drafts first.

3. CI and deploy wiring

The deploy diagram above comes from three small files. The DEV trigger:

# deploy/ai-chat-backend/dev.trigger.yaml (excerpt)
name: ai-chat-backend-monorepo-dev-app
github:
  push:
    branch: ^main$
includedFiles:
  - ai-chat-backend/**
ignoredFiles:
  - ai-chat-backend/**/*.md
  - ai-chat-backend/.env.example
substitutions:
  _BUILD_IMAGE: "true"
  _DEPLOY: "true"
  _SERVICE_FILE: deploy/ai-chat-backend/dev.service.yaml

Read it as a sentence: "on a push to main that touches ai-chat-backend/ other than Markdown and .env.example, build an image and deploy it with the DEV service file." Test-only changes count too, so they also redeploy DEV. The two PROD triggers differ only in the switches: prod.build.trigger.yaml fires on a tag ^ai-chat-backend-v[0-9]+\.[0-9]+\.[0-9]+$ with _DEPLOY: "false", and prod.deploy.trigger.yaml fires on a main push that touches prod.service.yaml, with _BUILD_IMAGE: "false" and _DEPLOY: "true". All three run the same cloudbuild.yaml, whose deploy step pins the image by its immutable @sha256 digest, runs gcloud run services replace, and then checks that the new revision is Ready, serves that digest and has 100% of traffic, failing the build otherwise.

After you merge, you can see the result on your squash commit:

gh api repos/glide-ilab/glide-ilab/commits/<squash-sha>/check-runs \
  --jq '.check_runs[] | [.name, .conclusion] | @tsv'

ai-chat-backend-monorepo-dev-app (etf-searcher) success means DEV serves your build. You may also see a red data-investment-research-crawling-app: that is a leftover Cloud Build trigger for the deleted crawler, nothing to do with you (it is hygiene finding 1 in D1). authenticate is the daily Codex-auth cron and is unrelated too.

Things a merge does not do: apply database migrations (a person runs python -m scripts.migrate), apply changes to dev.service.yaml, cloudbuild.yaml or trigger files (someone with GCP access applies those with gcloud), or update runtime secrets (update-runtime-secret.sh). If your change needs a DEV migration, agree with the lead before merging who runs it.

The IB pipeline is simpler and, in a way, sharper: .github/workflows/ib-research-report-pipeline.yml runs every Sunday (schedule: "37 0 * * 0", 09:37 KST nominally; GitHub's cron actually started these runs around 14:20–15:20 KST) from main with publication=kb-db, meaning real writes to the KB repo and the service DB. There is no build step, so merged means deployed.

One decision worth noticing: for pipeline runtime changes, you chose local tests only and to write "not run in Actions" in Verification, rather than dispatching the workflow on your branch.   1. Sort out access first (D1). Your gh account leetusik has READ on the repo: gh api repos/glide-ilab/glide-ilab --jq .permissions shows "push": false, so you cannot push a branch yet. Ask the lead for write access, and ask who reviews and merges your PRs (today the lead self-merges; nothing says what a new member should do). Ask whether you need GCP etf-searcher access; probably only for deploy/ work.
  2. Get an issue from the lead and read it (gh issue view <N>). Decide now: Closes or Refs … — which part.
  3. Branch from fresh main: git switch main && git pull --ff-only && git switch -c task/issue-<N>-<slug>.
  4. Read the folder's AGENTS.md and get a green baseline. A red baseline on fresh main is not yours to fix silently: tell the lead.
  5. Change, test, commit under the folder rules. Never stage .env, *.egg-info/, runs/, evals/ or any CLAUDE.local.md.
  6. Run the pre-merge checks for every folder you touched; note the SHA.
  7. Open a draft PR with the template and Verification (including what you did not verify).
  8. Merge as the team agrees, with Squash and merge. In the dialog, check the subject is your title + (#N) and trim Merge main into … bullets.
  9. After the merge, check the DEV check-run on your squash commit, then clean up with git branch -D <branch> (capital -D, because after a squash git doesn't see your branch as merged).

Best practices & next steps

How does this workflow compare with common practice outside the team? Mostly it is deliberate and sound; two gaps stand out.

Where it aligns

Conventional Commits with the folder as scope is the specification used as intended. The spec defines the scope as "a noun describing a section of the codebase", and lists among its benefits generated changelogs, semantic-version bumps and "a more structured commit history" (Conventional Commits 1.0.0 — conventionalcommits.org). In a monorepo, using the folder as the scope is what makes git log filterable by component. The spec also describes footers such as Refs: #123 in git-trailer format, which matches how the team's longer commit bodies end.

Squash merging for a readable main. GitHub describes squash as combining a PR's commits "into a single commit", and notes the default message "can include the pull request title, pull request description, or commit information, depending on repository settings and the number of commits" (GitHub Docs: About pull request merges — docs.github.com). That dependency on the number of commits is exactly the single-commit-headline gotcha the team hit on #49.

Where it diverges, and why that can be fine for now

No automated build on PRs or on main. Classic CI practice is that "every time the mainline receives a commit, the CI service checks out the head of the mainline into an integration environment and performs a full build", and that a failing build gets fixed first, often by reverting (Martin Fowler, Continuous Integration — martinfowler.com). This repo replaces the robot with author discipline and a written Verification section. With one active maintainer that is a reasonable trade: the person who merges is the person who ran the tests. With a second contributor it becomes riskier, because main deploys DEV automatically and the pipeline's production cron reads main.

No branch protection. GitHub can require approving reviews and require status checks to be "successful, skipped, or neutral" before merging into a protected branch (GitHub Docs: About protected branches — docs.github.com). This repo uses neither. P1 found the rulesets API refused with "Upgrade to GitHub Pro or make this repository public", so the plan the repo is on may limit what is available; whether classic protection is an option is a question for the lead, not something P1 could check with READ access.

Reusing a branch after its squash merge. The team has done this (task/issue-17 served #21, #53 and #55). GitHub warns that "if you keep working on the same head branch after a squash merge, later pull requests can include commits that were already squashed into the base branch", making conflicts more likely (GitHub Docs: About pull request merges — docs.github.com).

Concrete next steps

  1. Close D1 before anything else: write access, who merges, GCP need. No ticket can start until the first is solved.
  2. Start every PR from a fresh branch off main, never a branch that was already squash-merged, to avoid the replayed-commits problem above.
  3. Offer a small first ticket from the D1 hygiene list, if the lead likes the idea: for example, fix deploy/ib-research-report-pipeline/README.md, whose test command fails from the repo root and whose secret list omits the two Oxylabs secrets. It is low-risk and exercises the whole flow end to end.
  4. Later, propose a minimal PR check: one GitHub Actions workflow with a pull_request trigger that runs the two offline test suites. Both already run locally without network services (the pipeline suite stubs the DB, gh, Codex and Playwright), which makes them cheap CI candidates. This is a team decision; raise it, don't just open it.

Quiz

Click an answer to check it.

1. Your PR has exactly one commit, headlined wip etf fix. Just before merging, you rename the PR title to fix(ai-chat): handle missing ETF dates and squash-merge. What lands on main?

On a single-commit PR, GitHub's default squash subject is the commit headline, not the PR title, which is what happened on #49. Fix the commit itself (or edit the subject in the merge dialog).

2. You merge a PR that only changes ai-chat-backend/tests/test_schemas.py. What happens?

The DEV trigger includes ai-chat-backend/** and ignores only Markdown and .env.example, so test-only changes redeploy DEV too. No Actions workflow runs tests.

3. You're on branch task/issue-65-etf-chart, fixing one item of the umbrella issue #65. What goes in Related issue?

Closes would auto-close the whole umbrella. Team practice (#95, #100, #109, #110) and your CLAUDE.local.md override say Refs with a scope note, even on a task/issue-N branch.

4. How does a new version of ai-chat-backend reach PROD?

The tag trigger has _DEPLOY: "false", so it only builds. The PROD deploy trigger fires on a main push touching prod.service.yaml. Both need approval under the AGENTS.md and your deploy guards.

5. Why does your PR's ## Verification section matter more in this repo than in a typical one?

Nothing runs on PRs and main is unprotected, yet merging deploys DEV or feeds the production cron. The template doesn't even contain a Verification section; it's a team habit you've adopted as a rule.
