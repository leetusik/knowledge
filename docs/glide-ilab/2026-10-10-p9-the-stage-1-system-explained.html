1. The question and the short answer

The request, in the operator's words: "llm wiki kb access received. you may clone it and /create-phase for /explain the system. so that i can do well on project 1." "The system" is Stage 1 of the research agent (글로벌 IB 대시보드 + 주간 이메일): the pipeline that produces the Korean summaries on the global IB research page, together with the newly readable knowledge-base repository (the KB) where its results live.

The short answer. Stage 1 is one weekly GitHub Actions workflow in the monorepo folder ib-research-report-pipeline/. Every Sunday it collects new report links from nine investment houses (수집), renders each page in a headless browser (캡처), separates the article from the page's navigation (경계), gathers the PDFs, images and tables that belong to the article (자료), extracts the text of PDFs (추출), has an OpenAI Codex model write a Korean summary (요약), has a second model judge that summary against the source (판정), derives a Korean title and five bullets from the summary (파생), and publishes the result (발행) (AGENTS.md:17–40; yml:53–57). The result goes to two places: the KB, a git repository (glide-llm-wiki-kb) with one folder per document holding the summary, the verdict and the reports, and the research_documents table in the Supabase database, which the global-ib-research page reads.

Three facts organise everything else. First, which documents run is a pure function of what the DB and the KB already hold: the enumerate step gives each of the 878 DB rows one action (PROCESS, SYNC, SKIP or BLOCKED), and the Sunday run's new mode processes only rows that have no result anywhere (selection.py:102–155). Second, each document ends complete, partial or failed, decided only by "severe" findings from the judge and by gaps in the evidence; the judge's 0–5 scores are written down but never read by any code (stages/judge/status.py:17–45). Third, the KB holds results, not sources: no article body, PDF or image survives the Actions runner, and the KB keeps only the checksums that identify the evidence (AGENTS.md:169–175).

Publication is one commit on a fresh kb/batch/<UTC> branch of the KB, a push, six summary columns written into the DB, and then a pull request that a teammate merges by hand between 19 hours and 7 days later (storage/factory.py:57–225). The DB therefore runs ahead of the KB's main branch, and both partial and complete reach the DB as summary_status = success (stages/publish/promote.py:62). Today the KB holds 874 documents (338 complete, 474 partial, 62 failed) from 21 batch commits; only one batch, on 2026-10-04, came from the cron, and scheduled runs take minutes, not hours.

Three things to remember

  1. The KB holds results, not sources. No article body, PDF or image from a run survives the runner. The only stored bodies anywhere are the retired crawler's text_content rows in the DB, extracted differently and hashed differently (/.gitignore:11; AGENTS.md:169–175).
  2. Only severe findings gate a document; the 0–5 scores gate nothing. In today's KB every partial comes from the evidence stages and every failed failed before the judge ran (stages/judge/status.py:17–45).
  3. The weekly run is short, takes only missing documents, and writes the DB before anyone merges the KB. Retries and syncs happen only when someone dispatches the workflow by hand (selection.py:142–155; promote.py:62).

2. The shape of the system, and one Sunday run

Takeaway: five parts, one workflow. The pipeline code lives in the monorepo and runs on GitHub Actions; the KB repo stores results; the Supabase DB holds the rows the page reads; Codex CLI on the runner makes every model call. A Sunday run is two jobs that take about seventeen minutes.

2.1 The parts

  • The pipeline code: ib-research-report-pipeline/ in the glide-ilab monorepo, about 15,700 lines of Python under src/ib_research_report_pipeline/, with 18 prompt files under prompts/ and 73 test modules that act as its executable specification. The workflow file .github/workflows/ib-research-report-pipeline.yml (488 lines) runs it.
  • The KB: the repository glide-ilab/glide-llm-wiki-kb. It has no code and no README, only runs/<source_code>/<document_id8>/ folders, where id8 is the first eight characters of the document's UUID. The pipeline clones it fresh for every read and every publish (storage/git_storage.py:109–129).
  • The DB: three Supabase tables, research_sources (the houses), research_crawl_runs (one row per collection attempt) and research_documents (878 rows: URL, title, date, and six summary columns the pipeline fills).
  • The page: global-ib-research in the dashboard, which reads research_documents through an API and shows the Korean title, the five bullets and the summary paragraph.
  • Codex CLI: OpenAI's coding agent, which the README describes as "a coding agent from OpenAI that runs locally on your computer" (openai/codex README, github.com). The runner installs it, signs in with a CI account's saved credential, and the pipeline calls it as a subprocess for every summarize, judge and derive call (agents/runtime.py:82–127).

3. The evidence stages: from a URL to evidence (수집 → 캡처 → 경계 → 자료 → 추출)

Takeaway: the deterministic half of the pipeline turns a DB row (URL, title, date) into exactly two model inputs, fingerprinted together as evidence_sha256: a reference text (the article body the boundary selected) and a notes list (PDF extractions, article images, HTML tables). The fingerprint reaches the KB and binds every later model call, but the evidence itself never leaves the runner. A document becomes partial here when a selected input should have worked and did not; 470 of today's 474 partials are exactly that, mostly from code that no longer runs.

3.1 Collect (수집): the houses that work today

collect reads fixed listing pages, feeds or APIs for each registered house over plain HTTP, with Oxylabs and urllib fallbacks and no browser (collection/registry.py:17–29; collection/http.py:35–68). It keeps links dated inside the window (14 days on the cron) and, with --register-links, inserts URL, title, date and listing metadata into research_documents, filling only empty fields (storage/supabase.py:233–267). Everything downstream is driven by those rows, not by the registry: enumerate reads every research_documents row of every registered source code (storage/supabase.py:86–111).

"A source that works today" therefore means: registered in the code, collected weekly, and processed by new. That is exactly nine houses. Two more appear in the KB only because their legacy DB rows were handed to a backfill, and one DB source has no documents at all.

3.3 Capture (캡처) and boundary (경계)

  • Capture opens a fresh headless Chromium. The main document's raw bytes are held at the browser's route layer, so navigating to a PDF cannot turn into a download, a pitfall the docstring credits to the pipeline's reference-only predecessor (stages/capture/service.py:256–284). In PDF mode it checks for %PDF and stops. In HTML mode it waits for network idle, scrolls to the real bottom within 20 seconds, waits for the text to settle, snapshots the DOM, keeps the browser's own image responses and records PDF links (:332–452).
  • Fallback. When the browser captured no body, a plain httpx GET supplies the server's HTML instead. The code names Morgan Stanley's web application firewall as the reason (:456–468), which is the likely cause of its text-only evidence, although that is unconfirmed.
  • Fail fast. HTTP status 400 or above, or a body over 50 MiB, fails the capture before any Codex call, leaving only capture-failed.json (stages/capture/batch.py:59–103).
  • Capture identity. run_id is sha256 of the URL, the raw-bytes hash and the tool versions, cut to 16 characters (:83–85).
  • Boundary is a deterministic DOM heuristic, recomputed from the saved DOM on every run (stages/boundary/service.py:239–297). It tries site-specific fragments first, then an <h1> anchor against the largest landmark, then paragraph density. "Chrome" means nav, header, footer and aside plus observed publisher classes. Each PDF link gets a relation and a reason per occurrence: one_hop_cited and embedded are evidence; everything else is chrome (:434–503).

3.4 Components and materials (자료)

  • Supported: raster PNG, JPEG and WebP taken from the browser's response, never refetched (stages/components/materials.py:436–450); external SVG and AVIF, kept as originals with a bounded PNG representation; HTML tables, as JSON notes; single-slide Flourish embeds.
  • PDFs are re-fetched over HTTP, with one browser retry when the bytes are not a PDF (stages/components/service.py:247–326).
  • Unsupported inline <svg>, <canvas> and other iframes are recorded as unsupported. That is not a failure (materials.py:636–639).
  • Budgets: 8 images, 10 MiB each, 20 million pixels each. An image over budget is budget_exceeded, never downsampled (materials.py:21–34).

3.5 Extract (추출): PDF text only

On the weekly path, "understanding" a component means pdfplumber text and tables, on at most 60 pages and 400 blocks, with no model, no OCR and no rasterisation (stages/extract/service.py:121–157). pdfplumber's own README says it "works best on machine-generated, rather than scanned, PDFs" and lists optical character recognition among the things it does not provide (jsvine/pdfplumber README, github.com). A scanned PDF, or a chart inside a PDF, therefore yields no evidence.

  • One note per unique PDF bytes, carrying every occurrence (orchestration/runner.py:628–730). A direct PDF's text reaches the model twice, as the article and inside its note; that applies to 50 KB documents (BlackRock 30, HSBC 19, J.P. Morgan 1).
  • Images are never sent to a separate "understand" call. The runner calls understand_component only for PDF candidates (runner.py:619–625). Each available image becomes an article_image note with its path and sha256, and InlineEvidence attaches the image files to the summarize, judge, correction and arbiter calls themselves (inline_evidence.py:52–76). An image branch of the extractor exists but only a developer CLI reaches it (extract/service.py:228–277).

Two identity spaces for the same document. The KB stores these identities but not the evidence they name. Re-capturing reproduces an identity only if the page bytes and the DOM are unchanged. Separately, the only durable bodies are the retired crawler's research_documents.text_content (822 rows), extracted over plain HTTP with no rendered DOM, no boundary, and no images or tables, and hashed as content_hash. So text_content/content_hash and reference_sha256 describe the same document in different spaces, and no single reference can span both.

4. The judgment stages: from evidence to a judged summary (요약 → 판정 → 교정 → 상태 → 파생)

Takeaway: every model role crosses one boundary, codex exec on the CI account. The weekly chain is summarize → a single judge → a correction loop when a severe finding remains → the status rule → derive. The judge scores five axes from 0 to 5, but no code reads the scores: only severe findings decide, with accuracy and boundary fatal and the other axes degrading a document to partial. No published verdict keeps a severe finding, so every failed in the KB failed before judging and every partial came from the evidence stages.

4.1 The Codex runtime

One call is one subprocess: codex exec -m <model> --sandbox read-only --ephemeral … --cd <stable empty dir>. Images are passed as checksummed read-only snapshots with --image, and roles that must answer in JSON add --output-schema (agents/runtime.py:82–127; codex_exec.py:176–184). The fixed empty working directory keeps the server-side prompt-cache prefix stable (codex_runtime.py:3–20).

  • Retries depend on the failure class (codex_exec.py:268–402): infrastructure errors (capacity, connection, 5xx, timeouts) get up to three attempts, 5 s and then 15 s apart; a quota error gets exactly one more attempt on the fallback model gpt-reserve; a quality error is never retried.
  • The quota breaker: three consecutive document failures in a Codex stage abort the batch with exit 4. Infrastructure failures and no_article_content do not count (contracts.py:121; orchestration/runner.py:1287–1305).
  • The account guard runs only in the developer evaluation CLI. verify_account(), an e-mail allow-list check, is called only there, on a path the weekly chain never takes. On Actions the only check is codex login status (codex_auth.py:56–79; evals/cli.py:83).
  • Cost. A clean document costs three calls (summarize, judge, derive), a corrected one five, a repaired one up to eight, before retries; the KB mean is about 3.5. Token counts are parsed and discarded (agents/runtime.py:43). Judge plus derive take a median of 28 seconds (26 s with no correction, 68 s corrected, 109 s repaired).

4.2 Summarize (요약)

The summarizer receives the reference text in an <article> block, every note in a <material-components> block, the images, and the system prompt summarize_system.txt with its scope and multimodal sections (agents/summary.py:31–40). Its output schema is exactly {summary, content_found}. The six numbered rules of the prompt (prompts/summarize_system.txt:4–34):

#RuleGist, quoted

2정확성 (accuracy)"숫자·통화·날짜·등급·기간·단위·고유명사는 원문과 그대로 — 재계산·반올림·변환 금지."

  • The content gate. When the model answers content_found=false (an intro or player page, a promotion, navigation, or a video or webinar page without substance), the summarize CLI exits 7 with no_article_content and writes nothing (stages/summarize/service.py:88–96). In the KB, 33 of the 34 summarize failures are this.
  • summary-packet.json binds the summary to its inputs: reference_sha256, a self_check holding component_notes_sha256 and evidence_sha256 (identities, not a model self-assessment), the model, the prompt version and the run_id. Its own status is always "complete"; the graded status lives in chain-report.json (stages/summarize/service.py:101–119).
  • A style skill, $humanize-korean, is pinned at a fixed commit by the workflow and is used for style only.

4.3 Judge (판정): the rubric, and why the scores gate nothing

The weekly judge is the single judge: one gpt-5.6-terra call with single_judge_system.txt, producing a single-verdict/v1 (812 of 812 in the KB). A blind paired judge, which compares a baseline against the candidate in both orders, runs only when a local, gitignored golden set exists, so it is developer-only (orchestration/runner.py:874–899). The rubric scores integers from 0 to 5 on five axes, with anchors at 5, 3, 1 and 0 (prompts/single_judge_system.txt:12–42):

AxisQuestionWhat counts as severe (quoted)
completeness 완전성central claims, arguments, numbers and component conclusions, by salience"salience 상위 material 컴포넌트의 결론 누락 / 중심 논거 절반 이상 누락"
accuracy 정확성numbers, currency, dates, ratings, periods, units and proper nouns match the evidence"source fact와 불일치하는 숫자/날짜/등급/고유명사 1건이라도 존재"
boundary 경계·귀속fact kept apart from outlook; no chrome"chrome(related/nav/ad) 내용 유입 / 귀속 왜곡"
fluency 자연스러움natural Korean"severe 없음 (gate 전용 축)"
compression_salience 압축·salienceneither a full translation nor a title-level summary"원문 전체 번역 / title-level generic summary / salience 상위 정보 대량 유실"

A severe finding must quote the concrete number, date or wording behind it; [semantic] marks a meaning distortion and [numeric-only] a mechanical claim that a number string is absent (:56–74). The judge writes its rationale first, comparing "요약 표현 → 실제 원문 표현 → 대상/범위/조건/귀속의 일치 여부", and scores afterwards (:77–84).

The scores gate nothing. determine_status reads only the map of severe findings (stages/judge/status.py:17–45). A search for scores across publish, storage, selection, status and the runner finds only a console print (orchestration/runner.py:1088–1091). A completeness score of 1 with no severe finding is still complete. Even the derive docstring's phrase "the 5-axis gate already ran" (runner.py:1034) means the per-axis severe map, not a score threshold.

4.4 Program-side grounding and the non-negotiables

Code overrules exactly one kind of finding: a [numeric-only] item that quotes numbers (%, bp, $, 년) which are in fact present in the evidence, or present in the summary when the item claims they were omitted. Overruled items move to program_rejected (stages/judge/paired.py:80–109; stages/judge/single.py:124–133); that list is empty in all 812 final verdicts. Everything about omission, meaning and chrome stays with the models: "salience is never programmatic" (runner.py:937–940). Three rules bind production (AGENTS.md:229–233): severe findings describe only the candidate's defects; a checksum mismatch aborts; and program-side grounding runs first. A fourth, "the judge is blind", binds only the developer-only paired mode.

4.7 Derive (파생)

Derive runs after the status rule, only when the document is not failed (orchestration/runner.py:1024–1039). It sees only the finished summary and the original English title, never the source, and writes title_ko plus exactly five bullets beginning with - (prompts/derive_system.txt:7–34). Three gates guard it (stages/derive/service.py:79–130): the output schema (an extra key, a blank field or a Codex failure is exit 2), check_bullets (not exactly five non-empty - lines is exit 3), and ungrounded_numbers (a digit token in the bullets that is absent from the summary is exit 4). A derive failure is a promotion blocker, not a status change: the document keeps its status but has no DB projection (runner.py:1069–1071). Four KB documents are in that state because of usage limits before PR #39. The gates check presence only: a repeated number passes, and morgan_stanley/8d900e43 has bullets 2–5 repeating one sentence while passing every gate with a 5/5/5/5/5 verdict.

5. Selection and the knowledge base (선정 → 발행)

Takeaway: selection is a pure function. plan_action turns the DB state plus the KB state (read from every kb/* branch as well as main) into PROCESS with a reason (missing, stale, incomplete, retry), SYNC, SKIP or BLOCKED, and each selection mode takes only some of these, so the weekly new never re-processes, retries or syncs. Publication writes one result-only commit on a fresh branch and opens a PR that a teammate merges by hand; nothing auto-merges. The KB is a flat, linear corpus of 874 directories and 22 commits, most of it from the 09-08 → 09-11 backfill.

5.1 Four words that are easy to mix up

  • new is a selection mode: it takes only PROCESS missing.
  • retry is a PROCESS reason: a retryable failed attempt exists, and only the retry-failed mode takes it.
  • sync is both a mode and the SYNC action: copy a usable KB result to a destination that lacks it.
  • unchanged is a publish outcome: the document's files are byte-identical on every ref, so nothing is staged. It leaves no trace in the KB.

10. Quiz

Five questions. Click an answer to check it.

1. A document in today's KB has status partial. What does that most likely tell you?

Partial is set by component failures and limit hits (D2, D3). 470 of the 474 partials carry a component failure, no final verdict keeps a severe finding, and a derive failure leaves the status alone.

2. The Sunday cron runs in new mode with kb-db. Which documents does it process?

eligible lets new take only PROCESS missing; stale and incomplete belong to refresh, retry to retry-failed, and every SYNC to sync.

3. In a kb-db publish, in what order do the KB and the DB get written?

storage/factory.py pushes first (a storage failure stops before any DB write), promotes, applies SYNC writes, and only then opens the PR. The DB is ahead of KB main until the hand merge.

4. You need the article text a summary was written from. Where is it?

The publish allow-list excludes sources, runs/ is gitignored and never uploaded, and the only stored bodies are the retired crawler's text_content rows, a different extraction in a different hash space.

5. The judge gives a summary a completeness score of 1 but lists no severe finding. What happens?

determine_status reads only the severe map; the loop starts only on a severe finding that survives grounding; the scores appear in one console print and nowhere else.
