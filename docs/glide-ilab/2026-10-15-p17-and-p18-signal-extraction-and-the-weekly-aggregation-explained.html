1. Background

1.1 The pipeline, the dashboard and twelve empty tables

If you know the repo and the dashboard plan, skip to 1.2.

The ib-research-report-pipeline folder of the glide-ilab monorepo collects research reports published by global investment banks. The code, and this page, call each bank a house. Each collected report becomes one row of research_documents. The row says which house published the report (source_id), when (published_at), and, when the collector could read it, its body text (text_content). Until now the pipeline's job ended with a Korean summary of each report, published to a knowledge base. Its database is a Supabase PostgreSQL instance.

The research-agent roadmap asks for something no summary can give. Someone reading a hundred reports a month cannot easily see the patterns across them. The dashboard is meant to answer:

  • which investment themes houses discuss more this week than over the last few months;
  • where houses disagree with each other;
  • whether a particular house has changed its mind.

The screens are 이번 주 시그널 (this week's signals), the theme page and the house page.

The team agreed on twelve tables for that (decision DEC-004). The signal-tables pull request (#137) shipped them as migration 0002, merged into main as bac6f79 on 2026-10-14. That PR created the tables and carried over the theme dictionary, but no code wrote signals or aggregates yet. The tables themselves are explained in The signal-tables PR, explained, in this knowledge base (knowledge.hi2vi.com).

P17 and P18 are the two pipeline stages that fill those tables.

Definition: stage. A stage is one step of the pipeline. It has its own package under src/ib_research_report_pipeline/stages/, its own command and its own tables. The two stages here exchange data only through the database: P18 reads the rows P17 wrote. From P17's code, P18 borrows only two helpers, the database-target guard and P17's lock key.

1.2 What a signal is

A signal is a short, structured reading of one argument in one report. It says: this house is bullish on this theme over the medium term, and here is the sentence that says so. In the database it is one row of research_signals:

ColumnHolds
stancebull, bear or neutral: the house's view of the theme as named.
horizonshort (under 3 months), mid (3 to 12 months) or long (over 12 months).
confidenceA number from 0 to 1: the model's own estimate of how clearly the report states this view.
theme_idThe theme it is about, an id in the theme dictionary research_themes.
evidence_text, evidence_refOne sentence copied word for word from the report, and the paragraph it starts in (for example para12).
review_statusauto when the signal passed every automatic check; needs_review when a person should look first. approved and rejected are set only by people.

A toy row looks like this: House X · Theme A · bull · mid · 0.82 · para12 · auto. A 40-page report may give no signal at all, or a dozen. Most of a report is background, data or other people's views, and none of that is a signal.

2. Intuition

2.1 Reading is fuzzy; counting is exact

The two stages split the work along the line that matters most in a system like this: where the uncertainty lives.

Reading a long report and deciding which sentences carry a house's own directional view is a judgment call. Only a language model or a person can make it. It costs money, and it can be wrong. Counting what was read is arithmetic: it costs nothing, and a wrong number is a bug, not a matter of opinion.

So P17 does all the reading, once per report. It stores what it read together with its evidence and its doubts: a sentence that can be checked, and a review_status. P18 never sees report text. It reads P17's rows, applies the counting rules, and writes one set of numbers per week.

The counting rules come from R1, the team's written rules for checking extraction accuracy and for counting. 대표 approved them as starting values on 2026-10-14.

The split pays off whenever something changes:

  • If a counting rule changes, P18 can recompute every week for free.
  • If P17's reading of a report changes, only that report is read again.

Definition: 출발값 (starting value). Some values the specs and R1 do not fix, such as a tie-break order or the exact wording of a sentence template. In both phases each of those was chosen and labelled 출발값, so the team can see it is a choice and change it. A value the sources do fix is labelled 규칙 (rule).

2.2 P17: a strict form, then a check of the paperwork

Picture P17 handing the model a form with fixed boxes. Any answer that does not fit the boxes is refused, and the paperwork is checked before it is filed.

The form is a JSON schema, the shape of the answer written down in machine-checkable terms. The model must return a list of signals, and each signal has exactly these boxes:

  • a theme in its own words (theme_raw);
  • a short Korean label;
  • optionally, a theme id picked from the dictionary;
  • a stance, a horizon and a confidence;
  • the number of the paragraph it cites;
  • the evidence sentence;
  • the companies it names.

The provider's structured output mode enforces the schema, so the model cannot answer "very bullish": the stance box accepts only bull, bear or neutral.

To make citing possible, P17 first cuts the report into numbered units and shows them to the model as [P1] …, [P2] …. A unit is a line, and an overlong line is split into sentences. Lines that look like disclaimers, tables of contents or page furniture are marked as noise and not shown, but they keep their numbers.

The checks. A well-formed answer can still be wrong, so three checks follow, always in this order. The first failure names the reason.

The theme. The model names the theme in its own words and may pick a dictionary id. P17 then climbs a ladder and stops at the first rung that holds. Each rung records the method it used:

  1. The phrase is empty: unmapped, the only way to get that reason.
  2. The model picked the id of an active theme: llm.
  3. The phrase, normalized, equals an alias of an active theme: alias.
  4. The closest active theme by embedding similarity scores 0.75 or more: embedding. An embedding is a vector that places phrases of similar meaning near each other.
  5. The phrase equals an alias of a candidate theme: alias.
  6. The closest candidate scores 0.90 or more: embedding.
  7. Nothing fits, so P17 creates a new candidate theme, with an id derived from the phrase and an alias: alias.

Candidates are how the dictionary learns. P17 never throws a signal away for lacking a theme. Instead it parks the signal on a candidate that a person can later promote, merge or retire through a reviewed migration. Until then P18 ignores candidates, except to count how many might become new themes.

The bar for joining an existing candidate (0.90) is higher than for an active theme (0.75). It was raised from 0.85 after an accuracy pilot: two of seven merges at that level had joined opposite views.

The money. A model call's price is known only after it returns, so P17 reserves before it spends, the way a hotel puts a hold on a card. Each report's reservation is priced at the run's tier from two parts:

  • its measured input, at the cache-write rate;
  • a generous output allowance: 8,000 tokens, or the largest output seen so far if that is bigger.

A report starts only if what is spent plus everything reserved plus its own reservation stays within the cap given by --max-spend-usd.

2.3 P18: one house, one vote

P18 works one week at a time. A week runs Monday to Sunday in Korean time (KST), and a report belongs to the week of its published_at. A report published Sunday at 23:59:59 KST belongs to the earlier week; one at Monday 00:00 KST belongs to the next.

Take one toy week with four reports on Theme A:

ReportHouseStanceHorizon
rpt-1House Xbullmid
rpt-2House Xbearmid
rpt-3House Ybullshort
rpt-4House Ybullshort

P18 writes one research_theme_weekly row for Theme A that week:

signalsbullbearneutralreportshousesvotes

The last column is the one that matters. R1 defines the vote as one vote per house × theme × horizon × week. House X wrote twice on the same theme and horizon, and House Y did too. Each house gets one vote per horizon: (X, mid) and (Y, short).

A house that publishes daily notes therefore cannot outshout one that publishes a monthly outlook. Signal and report counts are kept beside the votes for the screens, but every trend judgment uses votes. A theme's share of voice is its votes divided by all votes that week. It is not stored; a reader computes it from the week's rows.

Not every signal counts. A signal is eligible only if all of these hold:

  • its report has a date;
  • it is auto or approved;
  • its confidence is at least 0.6;
  • its theme, after following any merges to the final theme, is active and not flagged excluded_from_aggregates.

Signals on candidate themes make no rows anywhere.

2.4 Rising and cooling, with toy numbers

Each run gives every theme with recent votes one row in research_theme_status, holding a trend_status. Four numbers drive it:

  • slope: the least-squares slope of the last 4 weeks of votes;
  • 4-week mean: the average of those 4 weeks;
  • 12-week mean: the average of the last 12 weeks, the last 4 included;
  • houses: how many houses voted on the theme in the last 4 weeks.

For 4 weeks, the least-squares slope simplifies to (−3·w₁ − w₂ + w₃ + 3·w₄) / 10, with w₁ the oldest week. The two tests are:

  • Rising: the slope is above 0, and at least 2 houses voted in those 4 weeks.
  • Cooling: the 12-week mean is at least 1 vote a week, and the 4-week mean is at most half of it.

When both hold, rising wins. A theme that is neither is stable.

Theme C is the case the precedence rule exists for. A theme coming back after a quiet month looks cold on averages, because the 4-week mean still carries three empty weeks. The latest weeks are the better guide, so rising takes precedence. The operator confirmed this starting value on 2026-10-15.

Two more guards keep thin data from producing confident labels:

  • The history gate. With fewer than 8 weeks of history before the run week, every theme is insufficient and gets no slope, means, change_pct or rank. With 8 to 11 weeks, the "12-week" mean averages over all the weeks available.
  • The cooling floor. The 12-week mean must be at least 1 vote a week, so a theme that fades from almost nothing to nothing is not reported as cooling.

Rising themes are ranked by slope, cooling themes by change_pct; stable and insufficient rows have no rank. The dashboard backend shows the top five of each list.

One more flag sits on these rows: is_new. It marks an active theme that was promoted from a candidate within the last 2 weeks and has at least 2 distinct reports in those weeks.

2.5 Conflicts, stances and the weekly sentence

Conflicts. Over an 8-week window, each house takes a side on each theme and horizon: the stance it expressed most often there. This is a plurality, not necessarily a majority. A tie at the top makes the house mixed, and mixed or neutral houses take no side.

A research_theme_conflicts row exists when at least one house is bull and at least one is bear on the same theme and horizon. Its strength follows R1:

R1's conflict strength, with b bull houses and r bear housesstrength = min(b, r) / (b + r) × ln(1 + b + r)

The first factor measures balance: it is ½ for an even split and shrinks as one side dominates. The second measures size, and grows slowly, logarithmically, with the number of houses involved:

bull : bear housesstrength
1 : 10.5493
2 : 10.4621
2 : 20.8047
3 : 10.4024
3 : 30.9730
2 : 60.5493 exactly ties 1 : 1 (both are ½·ln 3)

Conflicts are ranked by these keys, in order:

  1. strength;
  2. more houses;
  3. more reports;
  4. theme id;
  5. horizon.

Each row lists the houses on each side with their reports, newest first. The roadmap's quality filter also drops a conflict that rests on a single report. Under house sides that filter cannot bite at its default of 2: two houses never share a report, so any conflict involves at least two. The code keeps the filter and counts its drops anyway (zero so far).

Stances. research_house_theme_stances keeps one row per house × theme × horizon with eligible signals in the last 8 weeks:

  • stance: the house's plurality stance there, or mixed;
  • prev_stance: the same rule over the 8 weeks before that;
  • changed_week_start: set only when the two differ. It is the week of the earliest report in the current window that carries the new stance.

The dashboard uses that last column as its only sign that a house changed its mind.

The weekly sentence. research_weekly_narratives holds one Korean sentence per run, assembled from three fixed templates rather than written by a model (method = 'computed'). It names the week's most-voted theme with its house and report counts. It also names the top rising theme, and says so when the two are the same theme. The sentence costs nothing, never invents anything, and comes out identical on a re-run.

2.6 Re-running without forgetting

P18's output is a function of the database at the moment it runs. Re-running a week reads today's signals and today's dictionary. If a candidate was promoted or a signal approved since, the numbers change. That is intended, but it raises a question: what happens to the numbers the dashboard was showing?

The answer is that a re-run never deletes anything. Each run is a row in research_aggregation_runs carrying the week, the run's parameters and a flag, is_current, and every result row points at its run. A re-run inserts a new run with its rows, then moves the flag from the old run to the new one. The database itself guarantees that a week has at most one current run, and the move happens in one transaction: either all of it happens or none of it does.

3.2 One report's journey through P17

Selection. A full run selects reports in the window that meet three conditions:

  • published on or after --since;
  • a body that is not blank;
  • not yet done.

It takes them newest first. A report is done when it has a signal row, or when this stage marked it success or skipped. A report that yields no signal is still done, so it is not paid for twice. Markers left by an earlier prototype do not count. The pointer that records this is research_documents.signal_extraction_status. With its timestamp, it is the only part of that table P17 writes.

The model call. The schema is a Pydantic model. Note the comment at its top: the provider's structured outputs reject numeric and length bounds, so the ranges are checked in Python afterwards.

On the OpenAI path, llm.py asks LangChain for the strict JSON-schema mode:

There is one call per report and no fallback model, so every signal comes from one validated model. Some outcomes fail the report instead of producing signals, and each failure has a name:

  • refusal: the model declined;
  • max_tokens: a truncated answer;
  • parse_error: an answer that does not parse;
  • api_error:<Class>: an API error.

The prompt tells the model to:

  • extract only the house's own directional view, one signal per argument;
  • never give both bull and bear on one theme and horizon;
  • return an empty list when nothing qualifies;
  • copy the evidence sentence verbatim from the cited [P<n>] unit.

Its headings are "What a signal is", "Rules", "Input", "Output fields of each signal", "Theme dictionary" and "Self-check before you answer".

The dictionary grows during a run: a candidate created by one report can catch the same phrase in the next. An unverified sentence is never stored. evidence_text stays null, the reference keeps the cited unit, and the signal goes to review.

The write. store.write_document writes one report in one transaction, in this order:

  1. with --replace, delete the report's old signals;
  2. insert the new candidate themes;
  3. insert their aliases;
  4. insert the signals;
  5. insert the company mentions;
  6. set the report's status pointer.

If the database rejects any of it, the whole report rolls back, and the report's new candidates are also removed from the in-memory dictionary. A failure writes only the pointer failed, with a code, so a later run retries the report.

Model calls can run in parallel (--workers, default 4). Rows are built and written one report at a time, in selection order, so the dictionary grows in a predictable order.

Every subcommand takes --expect-db HOST:PORT/DBNAME, and backfill and recapture also take --report-dir. The README prescribes an order:

  1. --estimate counts tokens and prices the selection without calling the model.
  2. --dry-run calls the model and writes nothing to the database; the README's example limits it to 3 reports.
  3. The real run.

In backfill and recapture, every run except --estimate requires --max-spend-usd, the dry run included. In document the cap is optional.

The cap of Figure 3 is a small class. "Committed" means spent plus reserved:

stages/signals/service.py:190–209@property
def committed_usd(self) -> float:
    return self.spent_usd + sum(self.reserved.values())

def try_reserve(self, key: Any, input_tokens: int) -> bool:
    amount = self.reservation(input_tokens)
    if self.committed_usd + amount > self.cap_usd:
        self.refused = self.refused or (self.committed_usd, amount)
        return False
    self.reserved[key] = amount
    return True

def settle(self, key: Any, cost_usd: float, output_tokens: int) -> None:
    self.reserved.pop(key, None)
    self.spent_usd += cost_usd
    self.largest_output = max(self.largest_output, output_tokens)

Input tokens are counted with a local tokenizer when one is cached; otherwise the count is estimated at 4.5 characters per token. Real costs are settled from the usage the API reports, at the tier it reports, and a failed call still counts its billed tokens.

The flex tier is half price, with a 900-second timeout. When flex has no capacity it answers 429. The report is then marked capacity_refused and left for a later run.

The guard. Production must never be written by accident. So before anything touches the network, the database URL is parsed offline and compared with the target typed on the command line:

stages/signals/store.py:70–78def check_target(dsn: str, expected: str) -> None:
    if dsn_target(dsn) != parse_expected_target(expected):
        raise TargetMismatch("the database URL does not point at --expect-db; nothing was queried")


def open_checked(dsn: str, expected: str, connect_fn: Any) -> Any:
    """Check the target, then connect. A mismatch never reaches `connect_fn`."""
    check_target(dsn, expected)
    return connect_fn(dsn)

A writing run then takes a session-level advisory lock on a fixed key with pg_try_advisory_lock, and holds it until the run ends. A second writing run finds the lock taken and refuses. The lock has to be session-level: each report commits its own transaction, and a transaction-level lock would be released after the first one.

Exit codeMeaning (signal stage)
0Everything selected was processed.
2Database error: no URL, no connection, or a query failed.
3Nothing was selected.
4Refused before any call. Causes include a wrong target, the lock already held, a missing cap, a report that already has signals (without --replace), and missing keys or embeddings.
5Partial. Causes include a failed report, a stop at the cap, three database errors in a row, an unpriced call, and an interruption.

Runs write a report as JSON and Markdown, estimates included; document without a report folder prints the JSON instead. The report holds counts, mapping methods, similarity-score quantiles, review reasons, token usage, cost per tier and per report, and timings. It never holds text.

3.4 Recapture: reports whose text was never stored

Of the 324 reports in the window (published since 2026-04-11), 55 had no body in the database. recapture handles them one by one:

  1. It opens the report's canonical page in a headless browser.
  2. It extracts the article text, or the text blocks of a direct PDF.
  3. For two sources whose URLs are reused for newer reports, it checks that the page title matches the stored title. A mismatch marks the report skipped, without calling the model.
  4. It runs the same extraction as a backfill. The evidence is verified against the fetched text, marked evidence_space = 'pipeline_reference'.

All of this happens inside a fresh temporary directory (tempfile.TemporaryDirectory), which is removed on success and on failure alike. The fetched text is never stored: not in the database, the knowledge base or the repo. Only the signals, the run row and the pointer remain.

3.5 P18: three files and one rule

aggregates/core.py · ~800 lines
Pure computation: eligibility, merges, KST weeks, the five builders, the sentence, the recorded parameters. No database, no clock.
aggregates/store.py · ~250 lines
Four reads, one write transaction per week, two advisory locks.
aggregates/service.py · ~400 lines
The command line, the guards, the loop over weeks, the run report.

The rule is that every number is decided in core.py, from plain Python objects, so the logic can be tested without a database. An independent re-implementation in SQL could then check it. Such an oracle was written during the phase and agreed with every number (§3.10).

The SQL never groups by week: it reads rows in a time window, and Python assigns the weeks. The time-zone rule therefore lives in exactly one place:

3.6 From signals to six tables

Merges first. A signal keeps the theme id it was written with, even after that theme is merged into another. _resolve follows merged_into to the final theme and gives up on an unknown id or a cycle. Every row carries the final id.

The tally behind research_theme_weekly is four sets and a counter. The vote unit of §2.3 is the line self.votes.add((signal.source_id, signal.horizon)):

stages/aggregates/core.py:344–363 (abridged)class _Tally:

        self.houses.add(signal.source_id)
        self.votes.add((signal.source_id, signal.horizon))
        self.stances[signal.stance] += 1

Each run writes the 26 weeks ending at its week, because the theme page reads a 12- or 26-week series. It writes only the cells that have signals, and readers fill the gaps with zeros.

The trend. The slope uses exact fractions:

stages/aggregates/core.py:375–380def _ols_slope(ys: list[int]) -> Fraction:
    """Least-squares slope over x = 0..n-1; for 4 weeks (-3y0 - y1 + y2 + 3y3) / 10."""
    n = len(ys)
    x_mean = Fraction(n - 1, 2)
    sxx = sum((x - x_mean) ** 2 for x in range(n))
    return sum((x - x_mean) * y for x, y in enumerate(ys)) / sxx

The status rule is three lines:

stages/aggregates/core.py:583–587if judged:
    rising = slope > 0 and len(tally.houses) >= s.rising_min_houses
    cooling = mean_long >= cooling_floor and mean_short <= cooling_ratio * mean_long
    overlap += rising and cooling
    status = TREND_RISING if rising else TREND_COOLING if cooling else TREND_STABLE

overlap counts the theme-weeks where both tests held, so the run report can show how often the precedence rule decided. Three details keep the numbers exact and reproducible:

  • Comparisons use Fraction.
  • Stored values are rounded half away from zero, to match PostgreSQL's round: the slope and means to 4 places, change_pct to 1.
  • Ties between theme ids sort bytewise, like PostgreSQL's COLLATE "C".

change_pct is a percent: −72.0 means −72 %. The dashboard backend passes it through unchanged.

Conflicts. The house's side and the strength:

stages/aggregates/core.py:408–414 and 383–388def _plurality(counts: Counter[str]) -> str | None:
    """The single most frequent stance, `mixed` on a tie at the top, None with no signal."""
    top = max((counts[stance] for stance in SIGNAL_STANCES), default=0)
    if top == 0:
        return None
    leaders = [stance for stance in SIGNAL_STANCES if counts[stance] == top]
    return leaders[0] if len(leaders) == 1 else HOUSE_STANCE_MIXED

def conflict_strength(bull_houses: int, bear_houses: int) -> Decimal:
    """`min(b, r) / (b + r) × ln(1 + b + r)` at 40 significant digits, unrounded."""
    total = bull_houses + bear_houses
    with localcontext() as context:
        context.prec = _LN_PRECISION
        return Decimal(min(bull_houses, bear_houses)) / Decimal(total) * Decimal(1 + total).ln()

Ranking does not use those decimals. To compare two strengths, the code raises integers to integer powers. The table's 1 : 1 and 2 : 6 tie exactly and fall through to the next key, instead of being separated by the last digit of a logarithm:

stages/aggregates/core.py:391–401 (abridged)m1/n1·ln(a1) < m2/n2·ln(a2)  ⇔  a1^(m1·n2) < a2^(m2·n1),  with m = min, n = b + r and a = 1 + n

The parameters. Every run stores what it used in research_aggregation_runs.params (jsonb), with params_version 1:

  • the windows, thresholds and precedence;
  • the vote unit and the units of change_pct;
  • the eligibility rules, including houses: "all" and document_visibility: "not_applied";
  • the rounding, and the template version computed-v1;
  • how many signals were read.

A value can change without a schema change, and an old run still says what it was computed with.

3.7 The run switch and the locks

The guarantee of §2.6 is one index in the migration:

schema/0002_signal_tables.sql:267–273-- One current run per week, guaranteed by the DB (the only table that carries
-- both week_start and is_current). A recompute switches in ONE transaction:
-- first set that week's old current run to is_current = false, then insert the
-- new run with is_current = true and its result rows. The order matters: a
-- unique index cannot be deferred, so inserting first fails.
CREATE UNIQUE INDEX IF NOT EXISTS research_aggregation_runs_current_idx
    ON public.research_aggregation_runs (week_start) WHERE is_current;

store.write_week follows that comment to the letter:

stages/aggregates/store.py:224–247 (abridged)with conn.transaction(), conn.cursor() as cur:
    cur.execute(SELECT_CURRENT_SQL, (agg.week_start,))      # … for update
    found = cur.fetchone()
    flipped = found[0] if found else None
    if flipped is not None:
        cur.execute(UNSET_CURRENT_SQL, (flipped,))           # is_current = false
        if cur.rowcount != 1:
            raise LookupError("the current run to switch off was not found")
    cur.execute(INSERT_RUN_SQL, (agg.week_start, agg.week_end, agg.history_weeks, agg.n_reports,
                                 agg.n_houses, Jsonb(agg.params)))
    run_id = cur.fetchone()[0]
    # … executemany into theme_weekly, theme_status, conflicts and stances, then the sentence
return run_id, flipped

Two advisory locks keep P18 out of P17's way:

  • P18 takes its own lock exclusively, so two aggregations never overlap.
  • It also takes P17's lock in shared mode, with pg_try_advisory_lock_shared. While P17 writes, P18 refuses to start ("a signal extraction run is in progress on this database; nothing was read"). While P18 runs, P17's exclusive attempt fails, and P17 refuses.

Both locks are session-level and released at the end. A dry run takes no lock and reads in a read only transaction.

3.8 The aggregation command

From the README's ## 주간 집계 section (placeholders as written there)uv run python -m ib_research_report_pipeline.stages.aggregates run \
  --week 2026-10-05 --expect-db <host:port/dbname> --report-dir <dir> --dry-run
  • The week. --week takes a Monday, and --since/--through take a range of Mondays. With neither, the default is the Monday of (today in KST − 6 days). On a Sunday that is the current week; on any other day it is the week that ended last Sunday.
  • Refusals, all before any query: a week after the default; a date that is not a Monday; mixing the two forms; a wrong target.
  • Empty weeks. A week with no extracted report in it writes nothing.
  • Exit codes: 0 done, the dry run included; 2 a database error before any week committed; 3 every requested week empty; 4 refused; 5 stopped at a database error after at least one week committed. Earlier weeks stay committed.

The run report (JSON and Markdown) lists each week's outcome, run id, the run it replaced, and its rows per table. It also lists the trend counts, the rising/cooling overlap, the candidate themes that might be new, and the exclusions by reason. It closes with three standing caveats:

  • the history gate;
  • document visibility is not applied;
  • a re-run reads today's state.

4. Best practices & next steps

How do these choices compare with how others solve the same problems? Every claim below about outside practice links a page that was opened while writing this. The source's name and domain are kept in the text.

Where the implementation aligns with common practice

Schema-constrained answers, with the known gaps covered. OpenAI's guide says its structured outputs mode "ensures the model will always generate responses that adhere to your supplied JSON Schema". It also warns that "some features are unavailable either for performance or technical reasons", and that "a refusal does not necessarily follow the schema you have supplied" (OpenAI, Structured model outputs — developers.openai.com). P17 uses the strict mode, keeps numeric and length bounds out of the schema and checks them in Python, and turns a refusal into a named failure rather than a parse crash.

Grounding in verbatim quotes. Anthropic's guidance on reducing hallucinations recommends asking the model to "extract word-for-word quotes first". It also recommends verifying each claim "by finding a supporting quote", adding "If it can't find a quote, it must retract the claim" (Anthropic, Reduce hallucinations — platform.claude.com). P17's evidence check is the mechanical form of that rule: a sentence that is not in the report is never stored, and its signal waits for review.

A human queue for low confidence. Amazon's documentation describes the human-review pattern as getting "human review of low-confidence predictions or random prediction samples" (AWS, Using Amazon Augmented AI for Human Review — docs.aws.amazon.com; the service is now closed to new customers, but the page still describes the pattern). P17 sends low-confidence and unverifiable signals to needs_review, and P18 counts only auto and approved.

A discounted tier for bulk work. OpenAI's flex tier is priced at "Batch API rates" in exchange for slower responses, and may answer "429 Resource Unavailable", which is not charged. Its examples raise the client timeout to 15 minutes (OpenAI, Flex processing — developers.openai.com). The backfills ran on flex with a 900-second timeout, and treat a 429 as capacity_refused, to be retried later.

"Only one current row" as an index. PostgreSQL's manual shows a partial unique index that "enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not". Its example allows only one successful test per subject and target, but any number of failed ones (PostgreSQL, 11.8 Partial Indexes — postgresql.org). research_aggregation_runs_current_idx … WHERE is_current is the same pattern: old runs pile up freely, and only one per week can be current.

Session-level locks for multi-transaction jobs. PostgreSQL's manual explains that a session-level advisory lock is "held until explicitly released or the session ends". It does "not honor transaction semantics", while a transaction-level lock is "automatically released at the end of the transaction" (PostgreSQL, 13.3 Explicit Locking — postgresql.org). Both stages commit many transactions per run, which is why both hold session-level locks.

Where it deliberately diverges

Gating on the model's own confidence. Research on eliciting confidence from language models found that "LLMs, when verbalizing their confidence, tend to be overconfident". It also found that consistency across several responses helps mitigate this (Xiong et al., Can LLMs Express Their Uncertainty?, 2023 — arxiv.org). P17 still gates on the number the model writes, because R1 sets that 0.6 floor as its starting value.

Assessment. The copy fits the paper's warning: only 6 of 1,457 signals were held for low confidence. The gate rarely bites, so in practice the evidence check and the accuracy pilots do most of the protecting. The divergence is defensible as a cheap first filter. It should not be read as a measured error rate.

A gentler controversy score. Reddit's open-sourced ranking code scored controversy as magnitude ** balance, where magnitude is up-votes plus down-votes and balance is the smaller count over the larger. It returned 0 unless both were positive (reddit-archive/reddit, _sorts.pyx — raw.githubusercontent.com).

R1's strength has the same skeleton: both sides must be present, and balance and size both raise the score. But it grows only logarithmically with size, and it counts houses rather than votes:

splitReddit: magnitudebalanceR1: min/(b+r)·ln(1+b+r)

Assessment. The two orderings agree on these cases; both even tie 1 : 1 with 2 : 6. With 2 to 10 houses rather than thousands of voters, a logarithm keeps one more house from swamping the balance term. That is a reasonable fit for the data.

A computed sentence instead of a generated one. The weekly sentence uses templates where many products would ask a model to summarize. That trades expressiveness for zero cost, zero invention and identical re-runs. The sentence can only say what the numbers say. This is a design judgment, not an outside standard.

Next steps worth considering

  1. Measure the confidence gate instead of assuming it. The run reports already sort signals into bands (below 0.6, 0.6–0.8, 0.8 and up). Judged samples from the accuracy pilots could give a precision per band. If the bands do not separate right from wrong, the paper above suggests consistency across responses: ask twice and compare. Doing that only for borderline signals would keep the cost down (Xiong et al. — arxiv.org).
  2. Audit a random sample of auto signals, not just the queue. About 99.4 % of signals go straight to auto, so the queue says little about the error rate of what reaches the dashboard. A small random audit is the other half of the pattern Amazon describes, "random prediction samples", next to low-confidence ones (AWS A2I — docs.aws.amazon.com).
  3. Check that the quote supports the stance, not only that it exists. Anthropic's guidance asks for a quote that supports each claim (Anthropic — platform.claude.com). Today's check proves a sentence is real, and does not even require it to sit in the cited paragraph. A short second pass over just the sentence and the stance could catch a real sentence attached to the wrong view.

5. Quiz

Five questions. Click an answer to see whether it is right, and why.

1. A signal's evidence sentence is found in the report, its confidence is 0.55, and the model picked an active theme's id. What does P17 store?

The checks run in a fixed order (evidence, then confidence below 0.6, then mapping), and the first failure names the reason. A verified sentence is always stored. P18 will leave this signal out, because it counts only auto and approved signals.

2. A backfill runs with --max-spend-usd 2.00. So far $1.70 is spent, and $0.20 is reserved for two reports still being read. The next report's reservation is $0.15. What happens?

Before a report starts, the cap compares spent + reserved + the new reservation ($2.05) with the cap. Work already in flight is allowed to finish, and stopping at the cap is reported as a partial run.

3. In one KST week, House X publishes two reports on Theme A, both mid horizon, one bull and one bear. House Y publishes one report on Theme A, short horizon, bull. Every signal is eligible. What does research_theme_weekly hold for Theme A that week?

A vote is one house × theme × horizon × week: (X, mid) and (Y, short). The signal and report counts still count every row and every report. Contradicting stances do not remove anything.

4. A theme has 20 weeks of history. Its votes in the last four weeks are 0, 0, 0, 4, its 12-week mean is 2, and three houses voted on it in those four weeks. What is its trend_status?

The slope over 0, 0, 0, 4 is (0 − 0 + 0 + 12) / 10 = 1.2, and 3 houses is at least 2, so rising holds. Cooling holds too (1 ≤ 0.5 × 2), and precedence gives rising. insufficient depends only on the history gate (fewer than 8 weeks).

5. Why does write_week turn the week's old run off (is_current = false) before it inserts the new run?

The index (week_start) WHERE is_current is checked at each statement. Nothing is deleted: old runs and their rows are kept, just no longer current. The dashboard reads the current run.
