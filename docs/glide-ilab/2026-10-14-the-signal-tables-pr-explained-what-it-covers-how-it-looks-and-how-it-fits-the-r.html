1. Background

1.1 The repo, the pipeline and how PRs ship here

If you already know the monorepo and the research pipeline, skip to 1.2.

glide-ilab/glide-ilab is a private monorepo with three working folders: ai-chat-backend/ (the chat agent), ib-research-report-pipeline/ (this PR's folder) and deploy/. The pipeline collects research reports from global investment banks, writes Korean summaries grounded in each report's text, PDFs, images and tables, and publishes the checked result to a knowledge base. Its database is a Supabase PostgreSQL instance. Until now its whole shape lived in a single file, db_schema.sql, and the pipeline's README says it plainly: "런타임은 DDL을 실행하지 않는다": the running code never creates or alters tables. A person does.

In July a prototype added five tables for signals: short structured readings pulled from each report, such as "this bank is bullish on AI capital spending over the medium term". The design review called DEC-004 replaced that prototype with a cleaner family of twelve tables that the dashboard's screens can read. Three later decisions shape how the replacement ships:

  • DEC-010, the apply procedure. A migration and its table specs travel in one PR. The SQL is first applied to a local database restored from a production dump, and the commands and results go into the PR body. After cross-review and merge, the approved applier, Jake, applies it to production on request and records it in a ledger.
  • DEC-013, the placement (option A, "A안"). Numbered migrations go in schema/ and one spec per table in docs/tables/. 0001 is reserved for a later baseline that will replace db_schema.sql.
  • DEC-017. X4, the clean-up of the theme dictionary, is on hold, so this PR moves the dictionary as the prototype had it.

How code reaches main here is a matter of habit as much as of written rules. The team's own write-up of that habit ("How the glide-ilab team ships code") makes the central fact plain: since the monorepo began, one maintainer, Donggeon Lee (inspirit941), has opened every PR, and the write-up found he merged every one. PRs are squash-merged: GitHub folds a PR's commits into a single commit on main. A PR template has existed since 2026-09-30 (#82, "chore: add pull request skill and template"). No CI runs the tests for you; you run the folder's tests yourself.

Definition: migration. A numbered SQL file that changes the database's shape (tables, columns, constraints) from one known state to the next. Numbering gives an order, and a ledger records which files have run where. This PR introduces the repo's first numbered migrations: 0002, 0003 and a draft 0004.

2. Intuition

Think of the twelve tables as three shelves. The dictionary says what can be talked about: themes, the words that point to them, and the companies. Extraction records what each report said, one row per reading. The weekly aggregates condense a week of readings into what the dashboard draws. The existing report table, research_documents, stays where it is and is joined in. Here is a toy week flowing through the shelves. Four ideas carry the whole design, and each shows up in the diff:

  1. Dates and links are joined, never copied. No signal or aggregate table has a publish date or URL. If a report's date is corrected, nothing needs re-extracting; the join simply reads the new value.
  2. Every signal says where its evidence is. It records evidence_ref (a position), evidence_space (which body text the position indexes) and evidence_hash (a hash of that body). Since this morning the spec also says the evidence sentence is shown on screen. 대표 approved that as an exception to the rule that report text is not stored.
  3. One current aggregation run per week, guaranteed by the database. A recompute first switches the old run off, then inserts the new one, in one transaction.
  4. A person applies the SQL, one file at a time. Merging the PR changes no database. That is why the PR body has to carry the proof: what was run on a production copy, and what came out.

Why ship all of this as one PR rather than five? DEC-010 binds a migration to its specs: the reviewer should never see a table without its written meaning, or a spec without the SQL that makes it true. The CSV export rides along because it is the dictionary made readable without database access. And the one piece that can stand alone, moving db_schema.sql into a 0001 baseline, is deliberately left for the next PR.

A signal row, and the constraints that keep it honest

An excerpt from research_signals. The comments say what each evidence column means. The CHECK constraints make sure the database refuses a malformed row, whatever the code above it gets wrong:

CREATE TABLE IF NOT EXISTS public.research_signals (
    signal_id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id          uuid NOT NULL REFERENCES public.research_documents (id) ON DELETE RESTRICT,
    ...
    stance               text NOT NULL,
    horizon              text NOT NULL,
    confidence           numeric(4,3) NOT NULL,
    evidence_ref         text NOT NULL,         -- position inside the body named below
    evidence_space       text NOT NULL,         -- which body the ref indexes
    evidence_hash        text NOT NULL,         -- content_hash or reference_sha256 of that body
    evidence_text        text,                  -- one sentence, ≤ 400 chars; must appear in the body
                                                -- (whitespace-normalized), else review_reason = evidence_mismatch
    ...
    CONSTRAINT research_signals_stance_check
        CHECK (stance IN ('bull', 'bear', 'neutral')),
    CONSTRAINT research_signals_evidence_hash_check
        CHECK (evidence_hash ~ '^[0-9a-f]{64}$'),
    CONSTRAINT research_signals_evidence_text_check
        CHECK (evidence_text IS NULL OR length(evidence_text) <= 400),
    CONSTRAINT research_signals_review_reason_check

"One current run per week" is an index, not a promise

-- One current run per week, guaranteed by the DB ...
-- A recompute switches in ONE transaction: first set that week's old current run
-- to is_current = false, then insert the new run with is_current = true and its
-- result rows. The order matters: a unique index cannot be deferred, so inserting first fails.
CREATE UNIQUE INDEX IF NOT EXISTS research_aggregation_runs_current_idx
    ON public.research_aggregation_runs (week_start) WHERE is_current;
Definition: partial unique index. A uniqueness rule that applies only to rows matching a WHERE. Here, among rows with is_current true, no two can share a week_start. Old, switched-off runs can pile up as history without breaking the rule.

The taxonomy export

The CSVs are not edited by hand: the database is the source of truth, and the script re-exports it. The script refuses to run without its own connection variable and forces a read-only session:

export PGOPTIONS='-c default_transaction_read_only=on'
...
\copy (SELECT theme_id, theme_canonical, theme_group, status, merged_into, excluded_from_aggregates
       FROM public.research_themes ORDER BY theme_id COLLATE "C") TO 'taxonomy/theme_taxonomy.csv' WITH (FORMAT csv, HEADER)
What the PR does not cover: no runtime code, no tests, no GitHub Actions workflow, and no change to db_schema.sql. Nothing is applied to production. The extraction stage and the weekly aggregation that will fill these tables come in later PRs.

4. Best practices & next steps

Outside this repo, three bodies of practice speak to a PR like this one: how big a change should be, what its description should carry, and how squash merging and commit messages fit together.

Where the PR aligns

  • A standalone, imperative first line. Google's review guide asks that a change's first line be "a short, specific summary", written "as though it were an order", that stands alone in history (Google Engineering Practices: Writing good CL descriptions — google.github.io). Every commit subject and the PR title follow that form.
  • The why and the context in the body, not only links. The same guide warns that links can become inaccessible and asks for "enough context for reviewers and future readers" in the description itself (same source). The body restates each of Jake's answers it applies, rather than pointing at the sheet alone.
  • Re-read the description after review changes. The guide notes that changes evolve during review, so the description should be re-checked to confirm it "still reflects what the CL does" (same source). Each fix refreshed "Tested at" and the counts.
  • Scope as a section of the codebase. Conventional Commits defines scope as a noun naming a section of the codebase, and allows types beyond feat and fix, such as docs (Conventional Commits 1.0.0 — conventionalcommits.org). The folder scope and the docs type on the spec-only commits match.
  • Split by stacking. Google's small-changes guide suggests sending one change and building the next on it (Google Engineering Practices: Small CLs — google.github.io). The baseline that replaces db_schema.sql is held back as the next PR.

Where it deliberately diverges

  • Size. The same guide calls about 100 lines reasonable and 1,000 usually too large, and says file count matters too (Small CLs — google.github.io). This PR is +2,561 across 24 files. The divergence is defensible: DEC-010 binds a migration to its specs, a third of the lines are generated CSV, and the guide's own last resort for a change that cannot be split is to get the reviewer's consent in advance. DEC-010, in Jake's own words, asks for the migration and its specs in one PR.
  • The squash body. GitHub's default squash message for a multi-commit PR is "the pull request title and a list of commits" (GitHub Docs: Configuring commit squashing — docs.github.com). Trimming that list by hand departs from the default and from the maintainer's habit. Conventional Commits notes that in a squash workflow the merged message can be rewritten at merge time (Conventional Commits — conventionalcommits.org), which is what the trim does.

5. Quiz

1. The PR is merged on a Friday afternoon. What changes in the production database at that moment?

The runtime never runs DDL, and DEC-010 makes the apply a person's act, one approved file at a time. 0004 is a draft and is not applied in this round.

2. After the squash merge, what is the subject line of the new commit on main?

With two or more commits, GitHub's default squash message is the PR title and a list of commits; the plan trims the list to the three building commits. Only a single-commit PR takes its commit's headline as the subject.

3. Why does the body carry a separate ## Verification section that recent PRs in the repo do not?

The template has four sections; recent PRs put verification inside Why. Merging changes no database here, so the proof of what the SQL does has to travel in the body.

4. A report's publish date in research_documents is corrected from 10/03 to 10/06. What has to happen to its signals?

No signal or aggregate table has a date or URL column. week_start is an aggregation bucket recomputed each week from the joined published_at. And RESTRICT refuses a delete; it never cascades.

5. A weekly recompute must replace the current run for the week of 2026-10-05. Which order works?

The partial unique index on (week_start) WHERE is_current is checked row by row and cannot be deferred, so inserting first fails. Switching off first keeps the old run as history.
