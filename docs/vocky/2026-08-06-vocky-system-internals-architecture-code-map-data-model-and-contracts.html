Background

Part 1 established that vocky presents six doors — /auth, /app, /api, /api/project, /mcp, and Admin REST — over one canonical feedback store. This explainer opens the doors and walks the machinery behind them. The good news for a new maintainer: the machine is deliberately small. One Python application process, one worker process, Redis between them, PostgreSQL under them, and a Next.js app beside them.

Runtime shape

The server is a Starlette ASGI application (Python, managed with uv, package under src/vocky/) plus a separate worker process. The two communicate through a Redis-backed queue, and both read/write PostgreSQL through SQLAlchemy async sessions with Alembic-managed migrations. In production this becomes a five-container Compose project on one box: vocky-api, vocky-worker (the same image as the api, run under a different command — deliberately, so a partial rebuild can never leave the worker on stale persistence code), postgres, redis, and vocky-web (the Next.js app), all behind a shared edge nginx. Nothing publishes a host port; the edge vhost is the only ingress. /mcp is not a container — it is a Starlette Mount inside the api process.

Console entry points

pyproject.toml maps four scripts: vocky (the CLI), vocky-server (the ASGI host — renamed from vocky when the CLI took that name), vocky-worker, and vocky-smoke (the end-to-end smoke check).

Layering vocabulary

Vocky uses one layering pattern in both of its domain packages (src/vocky/feedback/ and src/vocky/accounts/), and it pays to learn it once:

  • types.py — transport-neutral dataclasses (kw_only, slots). No ORM object ever crosses this boundary, and records never carry secrets (no token_hash, ever).
  • repository.py — the sole ORM boundary. It flushes and refreshes but never commits.
  • service.py — owns the session lifecycle and the commit, and translates SQLAlchemy errors into domain errors (FeedbackPersistenceError, AccountsReadError, DuplicateEmailError, …).

Route modules sit above the services and do input normalization + error mapping; the worker reuses the same service/repository path as the API. That is the whole stack.

Intuition

The capture pipeline: accept fast, persist later

The heart of vocky is a write path that acknowledges before it persists:

A client gets 202 Accepted the moment the job is enqueued; the record becomes queryable only after the worker writes it. Three consequences shape the whole system:

  • Everything that must be true of a stored record must be true at enqueue time. The worker trusts the job blindly — it never re-derives the project. That is why resolve_capture_project(credential, project_name) → UUID (in capture.py, shared by REST and MCP) is typed to never return None.
  • Attachments must be uploaded first. The feedback row's UUID doesn't exist at capture time, so images go up synchronously (POST /api/feedback/attachments → attachment_id), the ids ride the queue, and the worker links them in the same transaction as the insert — guarded by a scope-match (claimed_user_id/claimed_source_product) and a feedback_id IS NULL condition that makes linking idempotent.
  • Post-persist work must be contained. The P13 email alert runs after the persistence try/except (whose failure branch returns), inside its own swallow-and-log except Exception. Anything escaping there would re-enqueue an already-committed job and create duplicate rows — placement, not politeness, is the correctness argument.

The two scope chokepoints

Multi-tenant safety in vocky is not sprinkled across handlers — it is concentrated in two request-scoped chokepoints, both established in middleware before any handler runs:

  1. Write scope: ProjectCredentialAuthMiddleware (auth.py) authenticates every /api/* and /mcp request by hashing the bearer and looking up a non-revoked credential, then stashes two things on the ASGI scope: the credential record and — the P10 innovation — resolve_credential_project_ids(credential), whose return type is tuple[UUID, ...], never None. The type is the enforcement: a handler cannot express an unscoped read because it has nothing to build one from. A project key resolves with zero DB calls; an org key costs one indexed SELECT.
  2. Read filtering: every scoped read funnels into FeedbackRepository._apply_query_filters, driven by FeedbackQueryFilters.project_ids (a set → SQL IN). The single-project project_id filter — whose None once meant "no filter" — was deleted outright. Convention everywhere: an empty scope short-circuits to an empty result in the handler; a scope is never collapsed to None.
Why so paranoid? There are ~ten credential-scoped call sites across four modules. A missed one is not an error — it is a silent cross-tenant read. Central resolution plus a non-nullable type turns that class of bug into something the type system refuses to compile, which is the cheapest kind of security review.

Search that speaks Korean

The free-text search on /app/feedback?q= is deliberately not PostgreSQL full-text search. to_tsvector('english', …) tokenizes and stems for one language; vocky's users write Korean with attached particles (조사), where 결제 must match 결제를 못 했습니다. So the predicate is a plain case-insensitive substring match over an immutable concatenation:

coalesce(message,'') || ' ' || coalesce(comment,'') || ' '
  || coalesce(target_text,'') || ' ' || coalesce(trigger_message,'')

…accelerated by a pg_trgm trigram GIN index (ix_feedback_events_search_trgm) over that same expression. The predicate expression (built in _feedback_search_target()) and the index expression are kept byte-for-byte in lock-step — only immutable operators (||, coalesce) are used, because a STABLE function like concat_ws cannot back an expression index. Editing one side without the other silently turns every search into a sequential scan while every test stays green.

One field, five places

The most instructive trap in the codebase: the Redis queue serializer (capture_queue.py) is a hand-written pair of explicit field allowlists. A capture field added to the payload type but not to both _serialize_payload and _deserialize_payload is dropped between the API and the worker with no error anywhere — capture still returns 202, the column just stays null. A new capture field must thread through five places:

  1. the raw input model (BaseCaptureFeedbackInput),
  2. _normalize_capture_payload (transport-neutral),
  3. CreateFeedbackEvent,
  4. both queue serializer halves — the only quiet failure,
  5. the repository's insert plus its _to_record read-back.

And for MCP a sixth: the tool's flat parameter list in tools/capture_feedback.py is hand-copied, so a field can exist everywhere else and simply never be advertised to agents. tests/test_capture_queue.py guards this in-process; vocky-smoke guards it against a deployed stack.

Provenance has exactly one transport-specific seam

The P14 recorded_by marker shows the codebase's seam discipline: _normalize_capture_payload stays transport-neutral, and the one place transport knowledge lives is normalize_mcp_payload, which stamps "agent" when the normalized value is None. REST's normalizer is byte-for-byte unchanged. The vocabulary, trim/blank rule, and the public error string (recorded_by must be one of: agent, human) live in exactly one module, src/vocky/recorded_by.py, mirroring trigger.py — and the read-side filter delegates to it rather than re-implementing membership.

App wiring order, and the MCP lifespan trap

create_app() registers routes in a deliberate order — /healthz, auth, app, app-feedback, usage, admin, api, project-feedback, attachments, and the Mount("/mcp", …) last so it can never shadow a core route. Two wiring facts bite anyone who touches this file:

  • The mounted FastMCP sub-app's own lifespan is not triggered by the host Mount, so the host lifespan nests async with mcp.session_manager.run(): around the app lifetime. Remove that and /mcp 500s at request time, not at startup.
  • /auth/* and /app/* match neither bearer middleware's path predicate — they are guarded per-handler by require_user (or deliberately unauthenticated, for signup/login, which instead lead with a handler-level per-IP rate limit).

The data model in one look

Nine tables: six accounts/tenancy + three feedback.

users ──< tenant_members >── tenants ──< projects ──< feedback_events
  │                                │              │            ├──< feedback_comments
  └──< auth_tokens                 └──< project_credentials    └──< feedback_attachments
                                        (project_id NULL = org key)   (feedback_id NULL until linked)
  • feedback_events — the canonical record: hybrid shape with first-class review columns (message, feedback_value, channel, target_type, trigger_type, recorded_by, …) plus JSONB context (messages, used_context, source_metadata, attributes). project_id is nullable — legacy rows stay NULL, invisible to every scoped read.
  • project_credentials — tenant_id NOT NULL always; project_id NULL is the org-key discriminator (no scope enum). Only token_hash (sha256) + a 12-char display prefix are stored.
  • Secrets convention: passwords are argon2id hashes; session tokens and vk_ keys are stored only as sha256 hex. No plaintext secret is ever persisted.
  • Closed vocabularies are app-validated, not DB-constrained — channel, trigger_type, recorded_by all nullable TEXT with no CHECK, so a new value costs one constant and no migration.

The migration chain runs 12 revisions, 20260423_2337 → 20260805_1200 (the current head, pinned by tests/test_persistence.py — every new migration must bump that pinned string). Two hard-won rules from its history: pin alembic downgrade targets by revision id, never "-1" (a relative step silently retargets when a later phase adds a head — this once produced 50 spurious test failures); and migrate before deploying code that reads a new column (old-code + new-schema is the only safe overlap — deploy/deploy.sh enforces it).

Three load-bearing subtleties

  • get_or_create_project's except nesting. Read-first → insert → catch IntegrityError → rollback → re-read, racing against UNIQUE (tenant_id, name). The race handler works only because it is nested inside the outer except SQLAlchemyError — IntegrityError is a SQLAlchemyError, so flattening them into siblings silently turns every duplicate-name race into a 500. A comment in the code says so; believe it.
  • Two duplicated normalize/serialize pairs, not one. admin_api.normalize_list_query is imported by the app- and project-feedback surfaces (one edit covers three), but api.py carries its own normalize_user_feedback_query and serialize_user_feedback_record. Missing that second pair is how a field lands on three read surfaces and silently not the fourth.
  • The owner-email query is the alert path's correctness hot spot. get_owner_email_for_project anchors its join on the project id and filters role == "owner", oldest-wins with .limit(1) (two owner rows are a legal state — .one() would raise). Re-anchor that join and one org's feedback gets mailed to another org's owner.

Best practices & next steps

Where vocky aligns with prevailing practice. Using pg_trgm's GIN operator class to index substring searches is the documented, standard mechanism: trigram indexes explicitly accelerate LIKE/ILIKE and regex matches, which is exactly the workload vocky's icontains predicate produces (PostgreSQL pg_trgm documentation — postgresql.org). Backing an expression index with only immutable operators is likewise required by PostgreSQL, and vocky's byte-for-byte lock-step rule between predicate and index is the correct discipline for keeping the planner on the index.

Where it deliberately diverges, and why that is legitimate here. The conventional choice for "search" is full-text search (to_tsvector), but FTS tokenizes per-language and would break Korean particle-attached matches — vocky's defining query. The trade-offs are real, though, and worth knowing as a maintainer:

  • The pg_trgm docs warn that a pattern with no extractable trigrams degenerates to a full index scan — very short queries (one or two characters) get little or no index help (PostgreSQL pg_trgm documentation — postgresql.org).
  • Whether trigrams are extracted from non-ASCII text at all depends on the build and locale: PGroonga's comparison page claims pg_trgm "disables non-ASCII characters support" by default via its KEEPONLYALNUM compile flag, working only when the database locale classifies those characters as alphanumeric — e.g. C.UTF-8 (PGroonga: pg_trgm comparison — pgroonga.github.io). Vocky's docs record that the Korean Bitmap Index Scan was verified with EXPLAIN on the target Postgres — that verification is load-bearing, not optional, because a locale change on a future database could silently demote Korean searches to sequential scans while every functional test stays green.

Concrete next steps for a maintainer:

  1. Add a CI or smoke assertion that EXPLAIN on a Korean search shows the trigram index in use, so the predicate/index lock-step and the locale dependency are machine-checked rather than remembered.
  2. Record the database locale requirement (non-ASCII trigram extraction) in operations.md beside the pg_trgm extension note, so a future managed-Postgres migration doesn't lose Korean search.
  3. Consider surfacing queue depth / dead-letter counts somewhere an operator looks — today a stuck worker is visible only as "feedback never appears" (the docs already flag the serial worker + SMTP timeout as the number to revisit as volume grows).
  4. Turn the "five places for a capture field" checklist into a PR-template item; it is the one silent-failure seam the test suite only partially guards.

Quiz

1. Why is resolve_capture_project() typed to never return None?

The queue round-trips project_id nullably and the worker trusts the job. Everything that must be true of a stored record must be true at enqueue time, so the resolver structurally cannot produce "no project".

2. You add a new capture field to BaseCaptureFeedbackInput, _normalize_capture_payload, CreateFeedbackEvent, and the repository insert + read-back — but forget the queue serializer pair. What happens?

_serialize_payload/_deserialize_payload are hand-written explicit allowlists — the one seam in the five-place threading that fails quietly. tests/test_capture_queue.py and vocky-smoke are the guards.

3. What makes an unscoped credential-authenticated read structurally inexpressible after P10?

Enforcement is by type: handlers scope off get_request_project_ids(), which cannot express "everything", and FeedbackQueryFilters.project_id (nullable) no longer exists. Empty scope short-circuits to an empty result, never to None.

4. Why must the search predicate expression and the trigram index expression stay byte-for-byte identical?

The planner matches the query expression against the index expression. Nothing errors on drift — performance just quietly collapses. (And only immutable operators like ||/coalesce may back the index; STABLE concat_ws cannot.)

5. The P13 email alert call sits after the worker's persistence try/except, wrapped in its own swallow-and-log except Exception. What bug does that placement prevent?

_handle_persistence_failure retries the whole job. An exception escaping the alert path would requeue an event that is already committed — duplicate rows. Containment is total and positional: the persistence except-branch returns, so alert code physically cannot run on a persistence failure. (The loop is protected separately, via asyncio.to_thread.)
