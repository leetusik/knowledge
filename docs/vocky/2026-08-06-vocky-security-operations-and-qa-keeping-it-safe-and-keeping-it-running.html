Background

Vocky went live at https://vocky.hi2vi.com on 2026-08-04 (phase P12). That date splits this whole subject in two: everything below used to be authored posture; it is now live posture serving real traffic. Two long-standing gaps were closed at exactly that boundary — admin auth now fails closed, and the public auth surface has a real rate limit — and both closures teach the house style: prefer fail-closed, versioned, tested controls over external or optional ones.

The only mitigation today is scope: mint a project-bound key for an agent runtime, never an org key. The docs say this publicly rather than letting readers assume the key is narrow.

What runs where

Production is a five-container Compose project co-tenanting an existing OCI box (opc@140.245.64.173, cloned at /home/opc/vocky — the path is load-bearing: the Compose project name, and therefore the data volume names, derive from it). A shared edge nginx (its vhost owned by the separate leetusik/edge repo) is the only ingress; every vocky service is expose:-only, addressed by container name on a shared Docker network. Cloudflare fronts it in Full (Strict) mode.

Intuition

The authorization stance in one sentence

Out-of-scope ids answer 404, never 403 — existence is never leaked. This one rule shows up everywhere: cross-tenant projects, other tenants' credentials, feedback outside a key's scope, even the org-credential surface refusing to acknowledge the caller's own project-bound key (it 404s there byte-identically to a foreign key, so the org surface cannot even probe the project surface's rows). The web app extends it by collapsing vocky's 400 and 404 into one not-found page — distinguishing "malformed" from "not yours" would leak the shape of what exists. Login's twin: unknown email and wrong password return an identical 401, so accounts cannot be enumerated.

Fail-closed vs best-effort — a deliberate asymmetry

Two neighbouring behaviors in the same middleware look inconsistent and are not:

  • Credential scope resolution fails closed — a DB error answers 500 credential scope unavailable and never falls through to a handler. Getting scope wrong is a cross-tenant read.
  • The last_used_at stamp is best-effort — a stamping failure is logged and swallowed. Failing an otherwise-valid ingest over bookkeeping would be backwards.

The same pattern at deploy time: every box secret interpolates as ${VAR:?message}, so a missing value aborts the deploy — because before P12 a blank admin token silently meant nine unauthenticated admin routes on the shared network, and a blank SESSION_SECRET passed the health gate entirely (the healthcheck fetches the static landing, which never reads it). Fail-closed is a lesson paid for, not a preference. And the admin middleware itself now answers 503 Admin API is not configured when tokenless — deliberately not a 401, because no credential could succeed.

The rate limiter and the invariant it stands on

/auth/signup and /auth/login — the only unauthenticated, guessable routes — carry an in-process fixed-window limiter (default 20 requests / 15 min per (client IP, route)), checked as the first statement in each handler, before any body parsing or password work. Four properties matter more than the numbers:

  • Client IP precedence is X-Real-IP → first X-Forwarded-For → socket peer. Behind Cloudflare + the shared edge, the socket peer is the edge container — a naive limiter would throttle the whole internet as one client. The flip side: those headers are client-controllable off the edge path, so this is an anti-abuse speed bump, never an authentication boundary.
  • Keyed on IP + route, never the email — so it leaks no account-existence signal and the generic 401 stays byte-identical.
  • Its state is per-process memory, which makes "vocky-api stays a single uvicorn worker" a real operational invariant — workers=N would silently divide the limit N ways.
  • Capture has no rate limit at all. POST /api/feedback and /mcp are unlimited, and the existing per-IP design is exactly wrong for server-to-server traffic (one third party = one IP). A per-credential bucket is deferred real design work, triggered by a second agent product or the first abuse incident.

The deploy lifecycle: image tags, not git reverts

Three rules fall out: migrate before serving (old-code + new-schema is the only safe overlap — additive, nullable, no-backfill migrations make this free); the worker reuses the api image with no build of its own (one build freshens both, so the worker can never run stale persistence code); and migrations live outside the images (an explicit, observable deploy step that can fail and roll back on its own).

How we know it works: the smoke ladder

QA is a ladder of increasingly real checks, each catching what the rung below cannot:

  1. The suites — 30 files / 238 tests (Python, against a real Postgres via the two-database contract; fakeredis stands in for Redis) and 10 files / 78 tests (web, vitest in Node, no jsdom — untestable things are extracted into pure helpers). Test files stay small and terse by house rule.
  2. vocky-smoke — walks the real spine (signup → project → key → capture → poll the read) against a running stack. Its reference payload is the deploy-time guard for the queue serializer's silent field-dropping; every new capture field extends it.
  3. CI — four proven-green jobs: skill byte-parity, installer bash -n, the web gate (lint/typecheck/test/format), and pytest against a Postgres service container. No Python lint or type-check exists anywhere — ruff and mypy are absent by fact, not oversight; ~34 pre-existing findings mean gating ruff needs its own sweep first.
  4. Manual-only territory — live MCP sessions (CI never opens one), email alert delivery (a clean worker log proves acceptance, not delivery), and the restore drill, which has never been rehearsed — the single largest remaining operational risk.

Code

Where the security machinery lives

  • src/vocky/auth.py — both middlewares, the path predicates, the scope resolver and ASGI-scope stash. src/vocky/accounts/security.py — argon2id hashing, secrets.token_urlsafe(32) token generation, sha256_hex. src/vocky/rate_limit.py — the fixed-window limiter (module-global dict, 20k-key prune cap that under-counts rather than over-counts).
  • web/src/lib/session.ts — the AES-256-GCM cookie seal (v1.<iv>.<ct>.<tag>, key = sha256 of SESSION_SECRET, fresh IV per seal; openSession returns null for every failure). web/src/lib/bff.ts — the one audited public pipeline: JSON-only 415 → same-origin 403 → per-IP 429 → parse/zod → vocky → seal cookie; upstream detail never echoed.
  • /mcp transport security — DNS-rebinding allowlist; a public host must be in VOCKY_MCP_ALLOWED_HOSTS or every call answers 421 Invalid Host header before the key is even examined (not 401 — retrying with another key cannot fix it). VOCKY_MCP_ALLOWED_ORIGINS stays unset on purpose: non-browser clients send no Origin. Known local-dev gap: the dev compose doesn't forward these vars.

And the proxy_set_header inheritance footgun: headers are hoisted to the server level and no location sets any — a single per-location header silently drops the whole inherited set for that route.

The app/edge header split

The app (web/next.config.ts) owns the generic headers and a production-gated, all-'self' CSP — with 'unsafe-inline' scripts/styles and no nonce, deliberately: a nonce needs middleware that forces dynamic rendering app-wide. No external origin is allowed at all; adding any third-party script/font/image means editing the CSP string. The app sets no HSTS — that belongs to the edge, whose short max-age reflects the shared-wildcard blast radius. nginx passes app headers through untouched.

Running the QA machinery

make test              # Python suite — needs DATABASE_URL + a DIFFERENT TEST_DATABASE_URL
make smoke             # vocky-smoke against the local stack
make verify            # smoke, then test
make external-smoke    # same smoke against VOCKY_EXTERNAL_BASE_URL (signs up a throwaway account!)
make check-skill-parity
cd web && pnpm typecheck && pnpm lint && pnpm test && pnpm format:check && pnpm build

Traps a new maintainer will hit, in likelihood order: the two-database contract (conftest.py raises if TEST_DATABASE_URL equals DATABASE_URL; the suite must run from the repo root because alembic.ini is relative); local e2e on pnpm dev, never pnpm start (the production build marks the cookie Secure, so plain-http clients silently bounce to login); origin-less curl POSTs to /api/auth/* get 403 by design (send Origin: https://vocky.hi2vi.com when probing); a stale local worker image makes captures accept but never appear (docker compose up --build -d worker); and env -u VAR proves nothing about the fail-loud secrets (Compose auto-reads the project .env — test with an explicit --env-file).

Two mirror-assertions that bite predictably

  • web/tests/skill-preview-ssr.test.ts pins SKILL.md's last section heading — any section added or renumbered in the skill must update that line.
  • tests/test_admin_api.py::test_admin_list_feedback_preserves_legacy_channel_filter compares one whole serialized record as an exact dict — every new response field lands on exactly that line. Editing it is not an additivity violation; the snapshot mirrors the serializer, not a client.

Best practices & next steps

Where vocky aligns with prevailing practice. Password storage is textbook: OWASP's first-choice algorithm is Argon2id — "the winner of the 2015 Password Hashing Competition", chosen for balanced resistance to side-channel and GPU attacks — and vocky hashes with argon2id via argon2-cffi (OWASP Password Storage Cheat Sheet — cheatsheetseries.owasp.org). Session handling also matches the recommendations: OWASP asks for ≥64 bits of CSPRNG entropy in session identifiers (vocky's secrets.token_urlsafe(32) is 256 bits), meaningless token values (opaque tokens, hashed at rest), and HttpOnly + SameSite=Strict + Secure cookies — exactly the sealed-cookie attributes the web app sets (OWASP Session Management Cheat Sheet — cheatsheetseries.owasp.org).

Where it deliberately diverges. OWASP recommends idle timeouts (15–30 min for low-risk apps) plus an absolute timeout of hours, enforced server-side (OWASP Session Management Cheat Sheet — cheatsheetseries.owasp.org); vocky issues a flat 30-day token with no idle timeout, no renewal, and no rotation. For a free product holding product-feedback data, the convenience trade is defensible — but it is a real divergence, worth revisiting if vocky ever holds higher-value data or adds team members with roles. The other honest divergences are documented in-repo: the no-nonce CSP (static generation over strict inline-script control), the per-IP-only rate limiting (wrong shape for server-to-server capture, knowingly deferred), and same-prefix org/project keys (incident-response legibility traded away, recorded with the counter-argument).

Concrete next steps for a maintainer:

  1. Rehearse the restore drill (deploy/restore.md) in a quiet window — it is documented, never run, and self-describes as a draft to be corrected by its first real execution. Also apply the P12.S5 backup cron + datastore log-cap --force-recreate on the box if not yet done.
  2. Per-credential rate limiting for capture before a second third-party agent product goes live — the per-IP module cannot serve server-to-server traffic.
  3. Off-box backup replication — today's backups die with the box.
  4. A ruff sweep, then gate it — the prettier precedent (sweep to zero first, then turn on the check) is the proven order; ~34 findings stand between here and a lint gate.

Quiz

1. A curl probe of /mcp on a fresh self-hosted deployment answers 421 Invalid Host header. What is wrong?

421 is the DNS-rebinding transport check on the Host header, before auth. A different key cannot fix it. (There is no MCP container — it's an in-process Mount — and _ORIGINS stays unset because non-browser clients send no Origin.)

2. Why must vocky-api stay a single uvicorn worker?

The limiter is a module-global dict. The invariant is documented in the module docstring and beside uvicorn.run(...); scaling out requires moving that state (e.g. to Redis) first.

3. A deploy's migration step fails. What does deploy.sh do, and what is the rollback unit?

Rollback is a tag flip — seconds, no rebuild, no data movement. rollback.sh never re-migrates (safe for additive migrations only); a schema-incompatible revert is a git-ref redeploy. Nothing ever runs down -v — the three data volumes must survive everything.

4. Which statement about vocky's test/QA setup is true?

The two-database contract is enforced loudly by conftest.py, and the suite exercises the real migration chain. There is no Python lint anywhere, and live MCP capture is manual-only territory.

5. Why do vocky's box secrets use ${VAR:?message} interpolation in compose.prod.yml?

Fail-loud interpolation is the single enforcement point (deploy.sh deliberately adds no second one). And note the testing trap: env -u VAR false-passes because Compose auto-reads the project .env — verify with an explicit --env-file.
