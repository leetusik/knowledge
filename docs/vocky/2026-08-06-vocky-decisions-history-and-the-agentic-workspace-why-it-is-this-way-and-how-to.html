Background

Vocky is not just a codebase — it is a codebase plus a memory of why. Two structures carry that memory: docs/current/decisions.md, a numbered record of operator-approved design decisions (D-P2-1 … D-P14-3) that "should not be re-litigated without a new decision superseding it", and works/phases/archived/, fourteen archived phases whose names alone tell the product's story. A new maintainer who absorbs these two structures can predict what the codebase will look like before reading it.

The phase arc, P1 → P14

  • P1 — relicense; retire the original agent-capture (MCP read tools gone for good).
  • P2 — accounts, tenancy, projects core: the pivot to a free multi-tenant SaaS; mandatory per-project vk_ auth replaces the static token.
  • P3 — Feedback API v2: project-scoped feedback, Korean-safe trigram search, usage monitoring.
  • P4 — the web app: tenant dashboard, project pages, BFF + sealed cookie; supersedes the packaged Admin Web UI.
  • P5 — the CLI: agent-first onboarding from the terminal; server entry renamed vocky-server.
  • P6 — landing page production edges + the complete (then-unexecuted) deploy kit; the old Admin UI physically deleted.
  • P7 — agent capture revived as the write-only /mcp surface.
  • P8 — the design gate: the deep-emerald brand, decided by the operator with Claude Design.
  • P9 — apply the design: the round-01 brand across app + landing.
  • P10 — accounts v2: user → org → project, org-level keys, the "default" project at signup — a real trust-boundary widening, landed enforcement-first.
  • P11 — frictionless onboarding: the curl | bash installer, the two-env-var agent contract, the published skill.
  • P12 — production launch (2026-08-04, vocky.hi2vi.com): the P6 kit executed green; admin auth fail-closed; auth rate limit; CI completed.
  • P13 — feedback email alerts over SMTP (worker-only, contained).
  • P14 — public agent-recorded feedback: the recorded_by marker, the field-mapping contract, the skill grown to 8 steps.

What is genuinely true today (2026-08-06)

  • Live: https://vocky.hi2vi.com serves; the installer and /SKILL.md are real; a signup round-trip was proven at bring-up.
  • Not on PyPI, on purpose: distribution is the site-served installer; uv publish remains unexercised.
  • Pre-MVP contracts: early-stage, not long-term-stable commitments.
  • Known stale docs: product.md and experience.md still carry pre-P12 "not live yet" passages beside the updated live-status text — the docs' own status headers are the tell; trust operations.md for liveness.

Intuition

Reading the decision record: five recurring values

The twenty-odd D-* entries are not random; the same values repeat, and knowing them lets you anticipate what a future decision will say:

  1. Additivity is the bar. P10's org keys landed enforcement-first and dark — every scope filter rewritten before any org key could be minted, proven by the whole suite passing byte-for-byte (D-P10-3). P14's marker changed no existing client's behavior. A change that would 400 existing callers (like server-enforcing comment) is rejected for exactly that reason (D-P14-3).
  2. Orthogonal dimensions get their own columns. recorded_by (who) was not folded into trigger_type (why) even though that needed zero migration — because an agent recording a survey could then never say both (D-P14-1).
  3. Boring, revocable auth. Opaque DB-backed tokens over JWT/OAuth (D-P2-1); mandatory per-project keys over any shared static token (D-P2-4); 404-never-403 everywhere (D-P2-5).
  4. Rename nothing that carries no behavior. tenants was never renamed to orgs (D-P10-1) — "org" is product-facing language only. Mechanical renames are their own slices, never folded into feature phases.
  5. Counter-arguments are recorded, not erased. D-P10-4 keeps one vk_ prefix for both key scopes and records honestly that a distinct prefix would have incident-response value. D-P10-5 accepts that optional --project can silently mint a broader key, and says so. When you disagree with a decision, the record usually already contains your argument — and the reason it lost.
Supersession chains matter: D-P8-1 supersedes D-P4-3 (the design gate moved and closed); D-P10-3 narrows D-P3-2 (a key's "both, full" authority now spans a chosen scope). P14 supersedes nothing but re-raises D-P3-2 sharply — unscoped keys now live in third-party runtimes. Read the Status header of decisions.md first; it maps these chains.

The workspace in one rule

Backlog routes. Slice folder explains. Result summarizes. Docs are versioned durable truth. Everything else in CLAUDE.md/AGENTS.md (the same file, two names) elaborates that sentence:

  • Work happens in phases (P1, P2, …), each decomposed into slices (P15.S1, P15.F1 for fixes). A phase starts with only DECOMP + REVIEW plus an intent.md capturing the operator's confirmed request verbatim; the DECOMP slice cuts the middle slices; the REVIEW slice validates everything together at the end.
  • An orchestrator/executor split. The main session (the orchestrator) plans each slice into its plan.md, commits, and owns all state transitions; the actual work is delegated to slice-executor subagent tiers picked by the slice's risk (low risk → mid tier; real code or cross-file work → high tier). The executor writes the slice's result.md and appends durable notes to phase.md (the phase notebook) — but never commits and never moves status. Tier models live in executors.toml, applied by sync-agents.
  • Durable docs are versioned, once per phase. Slices never edit docs/current/*.md (generated snapshots) and never run doc-new-version; they append one-line "Doc impact" notes to phase.md, and a passing review consolidates them into new files under docs/versions/<doc>/vNNNN_*.md. Old versions are immutable history — never patched. docs/index.json is the trail: eleven doc ids, each a chain of versions with a summary and source phase.
  • Deferred jobs park scope honestly. Nine are open today (D1–D10, D5 resolved), each with an explicit re-entry trigger — e.g. D9 "per-credential capture rate limiting: before a second third-party agent product goes live", D10 "capture-only key scopes: before recommending vocky keys in runtimes the operator does not control". They never affect slice selection until promoted. The deferred list is effectively the roadmap's risk register — read it.
  • Parallel mode is per-phase, opt-in — a phase can run on its own branch + git worktree (parallel-start), with merging gated on a quiet point and doc consolidation deferred to post-merge (versions come from one shared index). Slices within a phase always stay sequential.

How to change vocky, concretely

  1. Small/typo-level: the fast path — but never for behavior, contracts, or workflow.
  2. Standalone request: focused change + verification; if it alters durable truth, still cut a doc version.
  3. Real work: create a phase (/create-phase captures and confirms intent first — creating a phase never means executing it), then drive it with /do-next-slice or /do-whole-phase. Reviews record verdicts with review-phase; only pass closes the phase; archiving is a separate manual step.
  4. Contradicting a D-*: write a superseding decision in a phase — do not silently drift. The record is the contract with your past self.

Rules with teeth (the ones that bite)

  • Never hand-edit docs/current/*.md, the dashboards, or an old doc version — they are generated or immutable. The engine regenerates; you version.
  • A slice owns exactly two context files (plan.md, result.md) and never pre-fills another slice's plan. The phase notebook (phase.md) is the cross-slice memory — every slice reads it at start and appends durable findings at end.
  • Visual design is never the coding agent's call. The design-cowork skill governs: Claude Design + the operator decide; the agent writes a handoff, waits, lands the result as-is, and implements faithfully ("RESPECT THE DESIGN"). P8/P9 and the P11 landing sections all ran this way; P14 deliberately did not build a dashboard filter control because that would be design work.
  • Commit convention: type(scope): summary, imperative, one commit per completed slice, attributed to the model that did the work. No branches and no pushes unless asked (parallel mode being the documented exception).
  • Keep tests small — minimal high-value cases; a suite grows only on operator request or clear risk. (Part 3's counts — 238 + 78 — are a snapshot of what earned a test, not a coverage target.)
  • Operator co-work halts everything: a pending slice or phase stops selection until the operator clears it — that is how validation gates and design gates hand control back to the human.

Quiz

1. You want to change behavior that a D-* decision established. What is the correct move?

Decisions "should not be re-litigated without a new decision superseding it" — supersession is the mechanism (D-P8-1 over D-P4-3 is the worked example), and it lands via a new doc version, never a patch of the old one.

2. Why did P10 land its scope-enforcement rewrite before any org key could be minted?

D-P10-3: a NULL-project credential under the old code would have failed open to a global read, so enforcement had to come first — and running the untouched suite against the rewritten enforcement, before the feature existed, is what turned "existing keys are unaffected" from assertion into evidence.

3. A slice you are executing discovers that durable truth in architecture.md is now wrong. What does the slice do?

Doc versioning happens once per phase, at the review. docs/current/ is generated (never hand-edited), and implementation slices never run doc-new-version — the review does, so a phase's doc changes land as one coherent set.

4. What does an open deferred job (say D9, capture rate limiting) do to day-to-day slice selection?

Deferral is honest parking: the job records why it was deferred and the concrete trigger for revisiting (e.g. "before a second third-party agent product goes live"), but a human promotes it — nothing automatic, nothing blocking.

5. Why was recorded_by made its own column when adding an agent value to trigger_type would have needed no migration?

D-P14-1. The cheapest option was a real contender and was rejected on orthogonality; the record also lists the other rejected shapes (free-text convention, boolean, JSONB key) — a model example of how this repo reasons about schema changes.
