Background

Every product that people actually use generates feedback: someone clicks a thumbs-down, types "결제 단계에서 카드가 거절돼요" into a comment box, or tells an AI assistant that the export flow finally worked. In most systems this signal is scattered — some of it lands in application logs, some in support tickets, most of it nowhere at all. Teams that want to know what customers are asking for, praising, or struggling with end up grepping logs or guessing.

Vocky is a feedback layer that solves exactly this. A product's backend sends explicit, human-triggered feedback events to vocky over a single REST call; vocky structures them into one canonical, searchable store; and the team reads them back — in a web dashboard, from a terminal, or through their own admin panel. It is delivered as a free multi-tenant SaaS: no paid plans, no billing, no metering. It is live at https://vocky.hi2vi.com (deployed 2026-08-04, phase P12 of the project's history), though the contracts are still early-stage — the product calls itself pre-MVP.

Who it is for

  • Developers integrating capture — a backend engineer wiring a like/dislike button, a survey, or a feedback form to POST /api/feedback.
  • Teams reviewing customer voice — product and operations people searching and reading what came in.
  • Coding agents acting for a user — an explicit audience since P11. An AI agent can onboard a user, mint credentials, and capture feedback entirely from a terminal, and since P14 agent-recorded feedback (an agent deciding mid-conversation that something a user said is worth keeping) is a first-class, publicly documented flow.

What it deliberately is not

The MVP's restraint is as defining as its features. There is no automatic classification (no sentiment enum, no auto-tagging — the user's words are stored verbatim), no analytics suite (simple counts and trends only), no browser-direct ingestion (capture is a deliberate server-to-server action — a product's backend calls vocky, never the end user's browser), and no billing. Review and query surfaces exist but are always scoped and authenticated — there is no public cross-tenant query surface anywhere.

The accounts model: user → org → project

A user signs up with email + password. Signup lands a usable account in one step: it provisions the user, their org (auto-named "<email-local-part>'s workspace"), and a project named "default" — nobody starts at zero. An org owns projects; project names are unique per org, and creating a project by an existing name returns the existing one (so "make sure this project exists" is safe to script). The MVP flow is solo-owner: one org per account, no invites or roles yet.

Terminology trap for a maintainer: "org" is the product-facing word; the implementation still says tenant everywhere — the table is tenants, the API field is tenant_id. They mean the same thing. Nothing was renamed in the P10 accounts rework because the rename would have been a large mechanical change with zero behavior difference. Similarly, capture's user_id field identifies an integrating product's own end user, never a vocky account.

Intuition

Two credentials, two planes

The single most important mental model in vocky is the split between its two credentials. Everything else — which surface does what, what the web app may call, why the CLI has one odd command — falls out of this split.

Session tokenvk_ key
Minted byPOST /auth/signup / /auth/login /app/credentials (org scope) or /app/projects/{id}/credentials (project scope)
Held bya signed-in human (or the CLI's config store) a product backend or agent runtime, as a server-side secret
Unlocksthe control plane: /auth/* + /app/* — manage projects and keys, read/search feedback across all your projects, see usage the data plane: /api/* + /mcp — capture feedback, and read/manage feedback within the key's scope
Lifetime30 days, revoked on logout until revoked; plaintext shown exactly once at mint, only a hash stored

A vk_ key is itself a choice of scope: a project key works for exactly one project (the narrow default), while an org key (P10) works across every project in the org, including ones created later — when capturing with it, the caller names the destination project by name (get-or-created; omitted means "default"). Both look identical (vk_…); the way to tell them apart is credential.project_id — a UUID for a project key, null for an org key. The trade-off is stated, not hidden: an org key is more convenient and a bigger secret — revoking it cuts every project at once.

A vk_ key is not capture-only. Within its scope it can capture, read, PATCH, and DELETE feedback — there are no per-credential permission scopes yet. This is why the published guidance says: for an agent runtime, or any machine you don't control, mint a project-bound key, never an org key.

One store, six doors

Vocky keeps one canonical feedback store and one shared capture field set. What differs between surfaces is their role — who stands at each door and what job they came to do:

  • /auth/* — the public door: signup, login, logout, me.
  • /app/* — the session-authed control plane: manage projects and credentials at either scope, read/search feedback across all your projects (Korean-safe substring search), and view usage. Cross-tenant ids answer 404, never 403 — you cannot even probe what exists.
  • /api/* — server-to-server capture (POST /api/feedback, plus attachment upload) and a narrowly scoped end-user self-read, gated by a mandatory vk_ credential on every request.
  • /api/project/feedback ("Feedback API v2") — the external-admin-panel path: with the same vk_ key it captures with, a product reads and manages (PATCH review fields, DELETE, operator comments) its own scope's feedback.
  • /mcp — the agent-runtime door: a write-only MCP endpoint with exactly one tool, capture_feedback. Same vk_ bearer, same store, no read tools (reads stay REST-only).
  • Admin REST (/admin/api/*) — the self-hosted operator's review/management surface behind its own separate bearer. API-only: its packaged browser UI was deleted in P6, and the production edge 404s the whole /admin prefix.

A capture, end to end (toy data)

Say the checkout team's backend has a project key for project checkout-web, and a real user hits "결제 단계에서 카드가 거절돼요" into the feedback box. The backend POSTs:

POST /api/feedback
Authorization: Bearer vk_9f3c…

{
  "message": "결제 단계에서 카드가 거절돼요",
  "source": { "product": "checkout-web", "integration": "web-backend" },
  "feedback_value": 2,
  "trigger_type": "comment",
  "recorded_by": "human"
}

Vocky answers 202 Accepted with a request_id before anything is persisted: capture is asynchronous — accept fast, enqueue, and let a background worker write the record to PostgreSQL. The record becomes queryable moments later. Then any signed-in team member finds it with GET /app/feedback?q=결제 (or in the web app's Feedback page, or vocky feedback search 결제) — the search is a case-insensitive substring match that works for Korean, particles and all: 결제 matches 결제를 못 했습니다 too.

Who recorded this? The recorded_by marker

Since P14, vocky distinguishes agent-recorded feedback (an AI decided the user's words were worth keeping) from human-recorded feedback (a person clicked a button) as first-class provenance, not a naming convention. The rules are precise and worth memorizing:

  • The vocabulary is closed: "agent" or "human", nothing else — anything else is rejected, never coerced.
  • Omitting it stores null = unspecified — which is not "human". Everything captured before the feature also reads back as unspecified; vocky never backfills and never guesses.
  • /mcp is the one place it is inferred: that endpoint is the agent-runtime transport by construction, so an omitted marker is stamped "agent" there. REST and the CLI never infer (the CLI has no marker flag at all). An explicit value always wins on every transport.
  • Every read surface returns it, and every list surface filters on ?recorded_by=agent|human. There is deliberately no filter for the null rows.

The companion product decision: there is no sentiment enum. The user's own words — 답답함, 감사, a whole sentence — go in message verbatim; the agent's note about what happened goes in comment. Both are free text, both searchable. Operators hear the actual voice of the customer.

The field taxonomy, grouped by responsibility

Capture fields are grouped by the question they answer, not by transport:

GroupFieldsThe question they answer
Display & actionmessage (required), feedback_value (1 like / 2 dislike), commentWhat is the feedback?
Source identitysource.product (required), source.integrationWhich product/integration sent it?
Caller identityuser_id, session_idWhose feedback, which session?
Provenancerecorded_byWho recorded it — agent or human?
Triggertrigger_type, trigger_message, trigger_metadataWhy did capture happen — which button, survey, workflow?
Exact targettarget_type (message/conversation/surface), target_id, target_role, target_textWhat exactly was reviewed?
Review categorieschannel (web/mobile/support or null), tagsHow do operators slice it?
Contextconversation_id, messages, used_contextWhat surrounded it?
Metadataevent_at, source_metadata, attributesWhen, and product-specific extras

Note the deliberate orthogonality: recorded_by (who recorded) vs trigger_type (why captured) vs target_* (what was reviewed) are three different questions, so an agent relaying a survey response can answer all three. And message is the feedback's own display text — never an implicit pointer to "the latest message"; callers that know the exact reviewed item say so with the target fields.

Code

Everything above maps onto three user-facing client codebases in the repo (the server internals behind them are the next explainer's subject): the web app in web/, the CLI in src/vocky/cli/, and the published agent skill + installer in skills/vocky-feedback/ and web/public/.

The web app (web/) — the browser surface

A Next.js 16 / React 19 / TypeScript app (Tailwind v4, pnpm), and vocky's only browser surface (it superseded a packaged operator admin UI, deleted back in P6). Two things define its architecture:

  • It is a session-token client only. It talks to /auth/* and /app/* — never the vk_-keyed /api/*. It adds no capability the API doesn't have, and it deliberately carries no feedback management: the web app is where a human finds feedback; managing it belongs to a product's own admin panel over /api/project/feedback.
  • The browser never holds the vocky token. A server-side BFF ("backend-for-frontend") proxy seals the session token into an AES-256-GCM httpOnly cookie (web/src/lib/session.ts); browser JS can never read it, and every vocky call is made server-side (web/src/lib/vocky/).

The route groups tell the story (web/src/app/): (auth) is the unguarded login/signup pair; (app) is guarded once in its layout and holds the three signed-in pages — /dashboard (usage totals, daily trend chart, projects list, and the org-keys panel), /projects/[projectId] (per-project usage, credentials with last-used times, mint/revoke — the mint shows the plaintext vk_ key exactly once, with a warning, then only a 12-character prefix stub survives reload), and /feedback (cross-project list/search/detail; attachments download, never render inline). The root / is a public marketing landing that carries the real onboarding: a hero curl | bash install row, a #quickstart section walking the two-variable agent contract, and a #skill pane that renders the served SKILL.md read at request time.

The CLI (src/vocky/cli/) — the terminal surface

A Typer app, packaged lean (httpx + typer only; the whole server stack hides behind a pip install "vocky[server]" extra). The command groups mirror the API surfaces one-to-one:

vocky signup|login|logout|whoami      →  /auth/*        (session token)
vocky projects …                      →  /app/projects  (session token)
vocky keys mint|list|revoke           →  /app/…credentials  (session token; --project picks scope)
vocky usage                           →  /app/usage     (session token)
vocky feedback list|search|show       →  /app/feedback  (session token, read-only)
vocky capture "…" --product X         →  POST /api/feedback   (vk_ key from VOCKY_API_TOKEN)

That last line is the deliberate oddity: capture is the CLI's only vk_-keyed command (files capture.py vs the session-token auth.py/projects.py/feedback.py). The two credential planes are structurally prevented from crossing: capture reads its key from the VOCKY_API_TOKEN env var only (no --token flag — argv is world-readable), never sends the stored session token, and the vk_ key is never persisted to the config store — so vocky logout can't leave a key behind.

The CLI is built agent-first: --password-stdin keeps secrets off argv, --base-url / VOCKY_CONFIG_DIR allow headless, isolated sessions, errors go to stderr with non-zero exit, and keys mint prints the show-once plaintext key as the strict last line of output — a parsing contract, so a script can reliably grab it. The full reference is the hand-written docs/cli.md.

The agent skill and the installer — onboarding as product

Two environment variables are the whole agent contract:

export VOCKY_BASE_URL="https://vocky.hi2vi.com"
export VOCKY_API_TOKEN="vk_..."

(Recommended home: ~/.zshenv, never a repo .env — a repo file isn't auto-loaded by coding agents and is one commit away from a leak.) On top of that contract, vocky publishes an end-user agent skill, skills/vocky-feedback/SKILL.md, served byte-identically at /SKILL.md and shown on the landing. It is written to be executed verbatim by an agent: a zero-side-effect verify step (a bare authenticated GET /api/feedback — 400 means the token worked and only the missing filter was rejected; 401 means stop, never retry), the field-mapping table from the Intuition section above, three capture paths (CLI → raw REST → /mcp), and a branch-by-branch error table. A CI byte-parity gate (scripts/skill_parity.py) holds the served copy to the canonical file so they can never fork.

Distribution is a curl | bash installer (web/public/install.sh, served at /install.sh) rather than PyPI — nothing is published there. The script installs via uv tool install from GitHub main, needs no sudo, and its safety argument is structural: every executable statement lives inside main() and main "$@" is the file's last line, so a download truncated mid-transfer defines a function and hits EOF instead of half-executing.

Maintainer takeaway: all three clients are pure clients. The web app, the CLI, and the skill add zero backend capability — every one of them rides surfaces that exist independently. That is why the next explainer (system internals) can treat the server as one self-contained story: the six doors above are the complete public contract.

Quiz

1. A capture arrives over REST with no recorded_by field. What does vocky store, and what does it mean?

Omitting the marker stores null = unspecified; vocky never guesses. Only /mcp infers ("agent"), because that endpoint is the agent transport by construction.

2. You are handed a credential record and need to know whether its vk_ key is project-scoped or org-scoped. What do you look at?

Both kinds look identical as strings (vk_…, deliberately). The scope discriminator is credential.project_id: UUID = project-bound, null = org-wide. The dashboard and vocky keys list label it for you.

3. Which statement about the web app is true?

The web app never touches the vk_-keyed /api/* surface; the browser only talks to the Next.js origin, which seals the token in an httpOnly cookie. Finding feedback is the app's job; managing it belongs to /api/project/feedback.

4. What are the only required fields on POST /api/feedback?

message and source.product, both non-blank. And the nesting matters: source is the only nested object, and a top-level source_product on capture is rejected outright (that flat name exists only on the read path).

5. The "two-variable agent contract" means a coding agent can capture feedback with nothing but…

Two exports — the base URL and the vk_ key — are the whole contract: no plugin, no SDK, no config file. VOCKY_API_TOKEN carries the vk_ key and only that; it is never the session token, and the two cannot cross.
