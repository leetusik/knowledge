Background

The beginner's version: what is a "coding agent"?

If you already work with Claude Code or Codex daily, skip ahead to The problem this repo solves — this subsection is groundwork.

A coding agent is a large language model wired up to tools: it can read your files, edit them, run shell commands, and loop on the results. You describe what you want in English; it reads, writes, runs tests, reads the failures, and tries again. Claude Code and Codex — the two tools this repo targets — are command-line agents you point at a directory and talk to.

Every model has a context window: a hard limit on how much text it can hold in mind at once — your instructions, the files it read, the command output, its own reasoning. It is finite. On a long task you will hit the ceiling, and when you do the tool performs compaction: it summarizes the conversation so far and restarts from that summary. Anthropic's engineering write-up defines it exactly this way — "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary" (Effective context engineering for AI agents — anthropic.com).

Key concept — compaction is lossy

Summarizing is not free. Whatever the summary omits is gone. A decision you made forty minutes ago — "we settled on option B because option A breaks the migration" — can silently evaporate, and the agent will happily reintroduce option A an hour later, with total confidence. This single fact explains almost every design choice in this repo.

The problem this repo solves

Agents are extremely capable at the scale of one file and one hour. They degrade at the scale of one project and one week, in four recognizable ways:

  • They forget. Context compacts; earlier decisions vanish.
  • They redo work. Having forgotten, they solve the same problem twice — often differently the second time.
  • They sprawl. Mid-task they notice something interesting and chase it, and now the diff touches nine files instead of one.
  • They disagree with each other. Point three sessions — or two different tools — at one repo and you get three sets of conventions.

The instinctive fix is a better prompt. That does not scale, because a prompt lives inside the thing that keeps getting truncated. The fix that does scale is to move the important state out of the conversation and onto disk, in files with a fixed shape that any agent, in any session, in any tool, can read on the way in and append to on the way out.

That is what bootstrap_agentic_workspace.sh is: one dependency-light shell script that turns an empty directory into a structured home for agent-driven work. Its own README puts the goal plainly — make agents "decompose the work, remember what they learn, and prove it before moving on."

Who does what: the operator and the agent

One piece of vocabulary you will meet everywhere in this repo. You are the operator. You state intent, answer clarifying questions, review results, and decide when things are done. The agent types the commands. Every python3 scripts/workflow.py … invocation, every git commit, every validation run is the agent's job, not yours.

There is exactly one command you might ever type yourself — the one-time bootstrap. After that you drive the whole system in plain language and slash commands.

Intuition

The whole system collapses into one sentence, which the contract file states verbatim:

The contract, in one line

Backlog routes. Slice folder explains. Result summarizes. Docs are versioned durable truth.

Four clauses, four different jobs, four different places on disk. Let's unpack them with a concrete example.

Phases and slices

Work is organized into two levels, and only two.

  • A phase (P1, P2, …) is a unit of work with an objective. Think: one feature, one refactor, one investigation.
  • A slice (P1.S1, P1.S2, …) is one ordered step inside a phase. Think: one commit's worth of work.

Here is the part that surprises people. When you create a phase, you do not get a list of steps. You get exactly two slices:

Say you ask for "add refund support to the billing module." The agent captures your intent, creates phase P4, and stops. Later, when you tell it to execute, the DECOMP slice runs and cuts the middle slices — and only then does the shape of the work exist:

Why force planning to be its own step with its own artifact? Because a task you cannot slice is a task you do not yet understand. Making decomposition a first-class, recorded step means the agent has to demonstrate understanding before it is allowed to touch code.

Every slice owns exactly two files

A slice folder is deliberately spartan. Two markdown files, and neither has a template:

FileWritten byWhenContains
plan.mdthe orchestratorbefore any workwhat this slice will do and why
result.mdthe executorwhen the slice finisheswhat actually happened, including deviations

"Plan before, result after" is the proof-of-work mechanism. A slice that skipped its plan is visible; a slice whose result contradicts its plan is visible; both survive compaction, because they are files, not conversation.

The phase notebook: memory that flows forward

The single most important file for the "agents forget" problem is phase.md, the phase notebook. Every slice in the phase reads it on the way in and appends durable findings to it on the way out.

A real excerpt from this repo's own P12/phase.md shows the kind of thing that goes in — a decision, recorded once, that six later slices could then quote instead of re-deriving: 

The ordering follows the dependency chain: schema before lifecycle before merge before
visibility before CI before contract before README. Nothing downstream can name a field or a
command that S1/S2 have not defined yet, so the two design decisions that everything else quotes
(field names, command names) are settled first.

The orchestrator / executor split

Here is the second big idea. The agent you are talking to does not, itself, write the code.

The main session is the orchestrator. It plans, moves state, commits, and talks to you. For each slice it dispatches a subagent — a slice-executor — which runs in its own separate context window, does the slice's work, writes result.md, appends its notes to phase.md, and returns a short structured verdict.

Why bother splitting?

Context economy. Implementing a slice means reading a dozen files and running tests — thousands of tokens of noise the orchestrator will never need again. Doing that in a separate window and returning a paragraph keeps the orchestrator lean, so it can supervise a ten-slice phase without ever compacting.

The split is also a permissions boundary: the executor never commits and never changes slice or phase status. Only the orchestrator moves state. One writer, no races.

Two tiers, one cost lever

There are two executor tiers, and which one runs is decided by the slice's risk field — set deliberately during decomposition:

TierDefault modelGets
slice-executor-midsonnet @ high effortrisk: low only — a one-line or few-line edit, or docs
slice-executor-highopus @ high effortdecomposition, the review, and essentially all real code writing — every cross-file change without exception

Only an exact low routes down; anything unset or unrecognized lands on the thorough tier. And the routing is one-way-safe: if the mid tier discovers a slice is bigger than advertised, it returns escalate with its findings instead of guessing. The orchestrator appends those findings to plan.md and re-dispatches to the high tier. So a mis-rated slice costs you one wasted attempt, never a bad result.

The gates: nothing is done because you said so

Two statuses exist specifically to stop the machine, and they mean different things:

StatusShown asMeansCleared by
pending[~]waiting on you — validate something, or run something only you can runyou, explicitly
blocked[ ]a real impediment the agent cannot resolve itselfresolving the impediment

And a phase does not close on the agent's say-so. It closes on a phase review: the REVIEW slice runs in a fresh context that never edits source, checks the whole phase against its objective, and returns one of three verdicts — pass, changes_requested, or blocked. Only pass marks the phase done and lets the durable docs be versioned.

Docs: append-only, never edited

The fourth clause. Long-lived truth — architecture, decisions, API shape — lives in docs/, and it is versioned, not edited. You never patch an old version; you cut a new one, and it records which slice produced it. 

docs/versions/decisions/v0026_drop_the_low_executor_tier….md   ← immutable
docs/versions/decisions/v0027_opt-in_phase-level_parallelism….md ← immutable
docs/versions/decisions/v0028_flip_the_execution-mode_default….md ← immutable, latest
                       ↓ generated
docs/current/decisions.md                                        ← never hand-edit

So what we decided and why is always recoverable, and docs/current/*.md — the snapshot agents actually read first — is a build product, regenerated from the index.

Code

Now the real thing. Here is what is actually on disk in this repo and what each part does.

What the bootstrap script creates

bootstrap_agentic_workspace.sh is a single self-contained POSIX-sh file at the repo root (about 466 KB — it carries every skill, subagent, and template inline). You run it once against an empty directory: 

mkdir my-project && cd my-project
sh /path/to/bootstrap_agentic_workspace.sh . \
  --name "My Project" \
  --summary "What this project is, in one sentence."

Two other entry points matter once you have a project already:

  • --into-existing — non-destructive retrofit into a repo that already has code. It adds only what is missing and never clobbers your work.
  • --update (with --dry-run to preview) — pull newer machinery into an adopted workspace. It overwrites the engine, skills, and contract, but preserves all of works/ except templates and all of docs/.

The result is this layout:

A detail worth knowing early

.claude/settings.json pre-approves Bash(python3 scripts/workflow.py:*), so workflow commands run without a permission prompt every time — and explicitly denies git push --force and rm -rf. That is why the loop feels smooth without being unguarded.

scripts/workflow.py — the one manager

Roughly 1,900 lines of dependency-free Python. Every state change in the workspace goes through it — which is exactly why any agent, or CI, or you, can drive the workspace identically. It opens by declaring the entire state space as plain sets: 

DOC_TYPES = {"product", "experience", "architecture", "frontend", "backend", "data",
             "api", "operations", "security", "qa", "decisions"}
PHASE_STATUSES = {"planned", "in_progress", "in_review", "pending", "blocked", "done"}
SLICE_STATUSES = {"todo", "ready", "in_progress", "in_review", "changes_requested",
                  "pending", "blocked", "done"}
REVIEW_VERDICTS = {"pass", "changes_requested", "blocked"}

How "what runs next" is computed

This is the routing clause, and it is about fifteen lines. There is no scheduler and no dependency solver — just first phase that isn't done, first slice in it that isn't done: 

def resolve_current(phases: list) -> tuple:
    for phase in phases:
        if phase.get("status") == "done":
            continue
        current_phase = phase["id"]
        if phase.get("status") in ("blocked", "pending"):
            return current_phase, None, None
        open_slices = [s for s in phase["slices"] if s.get("status") != "done"]
        if open_slices:
            return current_phase, open_slices[0]["id"], open_slices[1]["id"] if len(open_slices) > 1 else None
        return current_phase, None, None
    return None, None, None

Note the second branch: a blocked or pending phase returns no slice. That is how the operator gate physically halts the machine — there is nothing for the loop to pick up. depends_on exists on slices but is advisory; validate only checks that the referenced ids exist. Ordering is the real mechanism, and --order accepts fractions (--order 4.5) so you can wedge a slice between two neighbors without renumbering anything.

Generated files are derived, never authored

rebuild_index_and_state() walks the phase folders and rewrites state.json, index.json, backlog.md, and deferred.md from scratch. Every state-changing command calls it. So the dashboards can never drift from reality — and they are declared as such in the engine: 

GENERATED_FILES = ("works/state.json", "works/index.json", "works/backlog.md",
                   "works/deferred.md", "docs/current/*.md")

What new-phase actually writes

The clearest demonstration that planning is deferred. The function writes phase.json, a skeleton phase.md, an intent.md from the template — and then creates precisely two slices: 

create_slice(phase_id, f"{phase_id}.DECOMP", "decompose phase",
             "decomposition", 0, "high", source={"type": "new_phase", "id": phase_id})
create_slice(phase_id, f"{phase_id}.REVIEW", "phase review",
             "review", 9999, "high", source={"type": "new_phase", "id": phase_id})

Note the orders: 0 and 9999. Middle slices get auto-assigned in steps of ten (_auto_order takes max + 10, ignoring the review slice), so REVIEW stays pinned at the end no matter how many slices get added.

Real state files

A slice is a folder with a slice.json and its two markdown files. Trimmed from this repo:

{
  "id": "P12.S4",
  "phase_id": "P12",
  "name": "Cross-stream status view",
  "kind": "implementation",
  "status": "done",
  "order": 40,
  "depends_on": [],
  "risk": "high",
  "paths": { "plan": "plan.md", "result": "result.md" },
  "archive": { "archived": false, "archived_at": null, "archive_path": null }
}

And the phase's review block, which is what a pass verdict writes:

"review": {
  "status": "pass",
  "reviewed_at": "2026-08-04T00:27:46+09:00",
  "reviewer": "slice-executor-high",
  "note": "Re-review after P12.F1: finding 1 closed at engine level … Docs consolidated:
           architecture v0003, operations v0021, decisions v0027 …"
}

That phase also shows the naming scheme for repair work: P12.F1 is a fix slice (kind: "fix", order 80) — created because the first review returned changes_requested. The phase reopened, the fix ran, the review ran again, and only then did it pass. That loop is the system working as designed.

The skills — how you actually drive it

Everything above is also packaged as Agent Skills: slash commands in Claude Code (/do-next-slice), $do-next-slice in Codex. Seventeen live in .claude/skills/; sixteen are mirrored in .agents/skills/ — do-whole-phase is Claude Code only, because it needs plan mode.

SkillWhat it does
/create-phasecapture intent, create the phase, stop — no decomposition, no code
/do-next-slicecomplete exactly one slice, then stop
/do-whole-phaserun the phase end-to-end including its review (Claude Code only)
/review-phasereview and record a verdict
/defer-jobpark an idea outside the backlog
/commitgroup pending changes into conventional commits
/parallel-phaserun a phase on its own branch + worktree, then integrate it back
/retrofit · /update-workspaceadopt into an existing repo · pull newer machinery

These are explicit-invocation only — the skill files carry disable-model-invocation: true, so an agent will not fire them on its own. They are your interface, not the agent's initiative. The one deliberate exception is design-cowork, a guide that is model-invocable and fires whenever work touches product visual design.

Execution modes

Both execution skills accept a mode word, and the default matters:

InvocationBehavior
/do-whole-phase (default: auto)plan inline → dispatch → repeat, with no plan-approval pauses. The safety halts still stop it.
/do-whole-phase gateyou approve each slice's readied plan before its executor runs
/do-whole-phase plan onlyproduce approved plans without executing; slices become ready ([r])

Even in auto, four things still stop the loop cold: a pending status, a needs_operator verdict, a blocked verdict, and a failed return from the top-tier executor. Speed is waived; safety is not.

executors.toml — the cost dial

This is the file to know if you care about spend. Two presets ship, selected by one top-level mode line, with per-tier overrides available: 

EXECUTOR_PRESETS = {
    "flex": {
        "mid":  {"model": "sonnet", "effort": "xhigh", …},
        "high": {"model": "opus",   "effort": "xhigh", …},
    },
    "economy": {                                   # the default
        "mid":  {"model": "sonnet", "effort": "high", …},
        "high": {"model": "opus",   "effort": "high", …},
    },
}

Edit the file, then have the agent run python3 scripts/workflow.py sync-agents, which writes the values into the four subagent definition files. The installer seeds this file once and updates never overwrite it — it is yours.

Two things you will meet later

Parallel phases. By default everything runs on one branch, one phase at a time. A planned phase can opt into parallel mode: its own branch, its own git worktree, its own agent session, while the default stream keeps working the phase in front of it. The unit of parallelism is the phase — slices inside one phase stay strictly sequential. Selection becomes stream-scoped, generated dashboards are regenerated rather than merged, and doc versioning is deferred to a serialized post-merge step (because version numbers come from one shared index). Ignore all of this until you have two genuinely independent phases.

The installer is a build product. In this upstream repo, bootstrap_agentic_workspace.sh is assembled by installer/build.py from the live repo files — the real workflow.py, the real skills, the real contract. Its own docstring states the payoff: "editing a live skill/agent/contract file + rebuilding is the whole workflow — no heredoc mirroring." A tracked pre-commit hook enforces installer/build.py --check, so the committed artifact can never drift from source. (This only applies here, in the upstream repo — a workspace you scaffold has no installer/.)

Your first fifteen minutes

  1. Scaffold or retrofit the workspace (the one command you type yourself).
  2. Open the directory in Claude Code or Codex.
  3. Say /create-phase <your first task> — or just "make a phase for X." Expect to be asked a clarifying question; answer it. The agent creates the phase and stops.
  4. Read the phase's intent.md. This is the confirmed record of what you asked; if it is wrong, fix it now, not later.
  5. Run /do-next-slice. That executes DECOMP — you get the slice breakdown, not code. Read it. This is your real review point.
  6. Continue with /do-next-slice per step, or /do-whole-phase to run to the review.
  7. When you feel the urge to expand scope mid-phase, don't — say "defer that." It lands in works/deferred/ and changes nothing until you promote it.

Ask "where are we?" at any point; the agent runs next and reads works/backlog.md, the generated dashboard whose status boxes are [x] done, [~] pending on you, [r] plan approved, and [ ] open.

This repo runs on itself

Every example in this document is real. The works/ and docs/ trees here are the project dogfooding its own system: twelve phases, the last of which (P12, opt-in parallel execution) went through seven implementation slices, a changes_requested review, a fix slice, and a passing re-review. Its README was itself written as a phase.

Best practices & next steps

How does this compare to how the wider ecosystem solves the same problems? Three places it lines up squarely with prevailing practice, two where it deliberately doesn't, and a few things worth doing next.

Where it aligns

Externalizing memory into files is the recommended technique, not a quirk. Anthropic's context-engineering guidance names three approaches for long-horizon agent work, and this workspace implements all three. It calls the second one "structured note-taking, or agentic memory … where the agent regularly writes notes persisted to memory outside of the context window" — which is precisely what phase.md is. It names the third as sub-agent architecture: "rather than one agent attempting to maintain state across an entire project, specialized sub-agents can handle focused tasks with clean context windows," with sub-agents returning condensed summaries while detailed contexts stay isolated (Effective context engineering for AI agents — anthropic.com). That is the orchestrator/executor split exactly, verdict-return and all.

The subagent mechanism this repo leans on is a first-class Claude Code feature with the same stated rationale: each subagent "runs in its own context window with a custom system prompt, specific tool access, and independent permissions," and the documented benefits include preserving context, enforcing constraints by limiting tools, and controlling costs "by routing tasks to faster, cheaper models" (Create custom subagents — code.claude.com). The mid/high tiering driven by risk is that cost-routing advice, made mechanical.

Phased artifacts before code is an established methodology. GitHub's Spec Kit formalizes spec-driven development as four sequential stages — Spec, Plan, Tasks, Implement — where "each phase produces a Markdown artifact that feeds into the next stage," giving agents "structured context instead of ad-hoc prompts" (Spec Kit documentation — github.github.com). Map it across and the correspondence is close: intent.md is the spec, DECOMP is plan-plus-tasks, the slices are implement, and the phase review is the validation checkpoint Spec Kit describes.

A root instruction file for agents is now a real convention. AGENTS.md is described as "a README for agents: a dedicated, predictable place to provide the context and instructions to help AI coding agents work on your project," is "used by over 60k open-source projects," is read by 30+ tools including Claude Code, Copilot, Cursor, and Codex, and is now maintained under the Linux Foundation's Agentic AI Foundation (AGENTS.md — agents.md). Shipping CLAUDE.md and AGENTS.md as byte-equal twins is the standard-compliant move.

Where it deliberately diverges

The contract is big — very big. The AGENTS.md guidance is for a file holding "the minimal, human-authored context" an agent needs: build commands, style, testing, boundaries (agents.md). This repo's contract is about 33 KB of dense prose covering orchestration modes, escalation ladders, parallel-stream rules, and design handoff protocol. That is a defensible trade — it is a routing contract, not a style guide, and it is read at the start of every session precisely so the rules survive compaction — but it is a real cost paid on every single session, and it cuts against the "keep it minimal" grain. Worth watching as it grows.

All state is git-tracked JSON and Markdown, not a database. No server, no daemon, no node_modules: python3 >= 3.8 and a POSIX shell. The benefit is enormous — state is diffable, reviewable in a PR, and survives any tool. The cost is that concurrent writers need explicit machinery, which is exactly why parallel mode needed a whole phase to build (branch + worktree per stream, regenerate-don't-merge for generated files, and serialized post-merge doc versioning because version numbers come from one shared index). For a single operator this is unambiguously the right call; for a large team writing simultaneously it is the first thing that would strain.

Next steps

  1. Run one small real phase end-to-end before judging any of it. Pick something genuinely small, use /do-next-slice rather than /do-whole-phase, and read plan.md and result.md at each step. The value of the artifacts is not obvious until you have watched them catch a drift.
  2. Set risk honestly during decomposition. It is the phase's main cost lever: only a one-line-or-few-line edit or a docs change belongs at low. Over-marking low just burns an escalation round-trip; under-marking costs opus tokens on a typo fix. If your bill matters more than latency, try mode = "economy" (already the default) and confirm with sync-agents.
  3. Adopt the deferred-job habit deliberately. It is the least flashy feature and the one that most changes outcomes, because scope creep is the dominant failure mode of agent sessions. Say "defer that" out loud the first ten times until it is reflex.
  4. Read docs/current/decisions.md before proposing changes to the machinery. Twenty-nine versions of recorded decisions mean most "obvious" improvements have already been argued — including several that were tried and reversed.

Quiz

Five questions. Click an option to check it.

1. You run /create-phase Add refund support to billing. Immediately afterwards, what exists?

Creating a phase and executing it are separate steps on purpose. new_phase writes phase.json, phase.md, and intent.md, then calls create_slice exactly twice — DECOMP at order 0 and REVIEW at order 9999. Deciding the middle slices is DECOMP's own job, later.

2. A slice's executor finishes and returns done. What does the orchestrator do next?

The orchestrator trusts a done verdict and runs only validate — state integrity, not the slice's tests. Behavioral validation is consolidated into the phase review, which checks every slice at once; doc versioning also waits for a passing review.

3. What is the practical difference between pending and blocked?

Both halt selection, but they mean different things and clear differently. pending ([~]) is "waiting on the operator" — you clear it back to in_progress. blocked is a genuine impediment. In resolve_current, a phase in either state returns no slice at all, which is how the halt is enforced mechanically.

4. A slice was rated risk: low, so it went to slice-executor-mid — but it turns out to need a change across four files. What happens?

The mid tier escalates rather than guessing. The orchestrator adds an ## Escalation section to the slice's plan.md and re-dispatches to the high tier — at most once per slice, and never downward. Note the executor cannot spawn anything or move status; only the orchestrator dispatches and transitions.

5. A slice changes something that belongs in the durable architecture doc. What is the correct handling?

Docs are versioned once per phase, at the review. Implementation and fix slices only record a "Doc impact" note in phase.md. docs/current/*.md is a generated snapshot (never hand-edited), and files under docs/versions/ are immutable — you cut a new version rather than patching an old one. A non-passing review stops before consolidation entirely.
