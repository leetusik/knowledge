Background

This repository, bootstrap_agentic_workspace.sh, is an installer that drops a complete agentic workspace into any project: a way of driving coding agents (Claude Code, Codex) through phases broken into slices, with versioned docs and a review at the end of each phase. One nicety of that review is the phase explainer — an interactive HTML write-up of what a phase changed and why — filed into a personal knowledge base (a small self-hosted document service, exactly like the one hosting the page you are reading).

New here? A knowledge base (KB) is just a service you POST documents to; it stores them, indexes them, and serves a browsable site. The bootstrap workspace talks to one over a tiny REST API. You can skip the rest of this paragraph if that is already obvious.

Three earlier decisions set the stage, and P9 only makes sense against them:

  • P7 — explain left the distribution. The /explain skill used to ride inside every workspace, hard-coded to one Mac. P7 deleted it and pointed users at a portable Claude Code plugin in a separate knowledge repo instead.
  • P8 — the review started invoking explain. A passing phase review began auto-producing the phase explainer by locating that installed skill and following it — best-effort, and gracefully skipped when no plugin or KB is present.
  • The gap P9 closes. Nothing operator-facing said how to reach a knowledge base without installing the plugin, and a freshly bootstrapped workspace received zero knowledge guidance — the seed documentation and the fresh-install console output never mentioned it. So "auto-explain on review" existed, but a new workspace had no obvious on-ramp to actually turn it on.

Intuition

The whole phase rests on one pre-existing fact about the external explain skill: its configuration resolver reads environment variables first, and its save path is plain REST — a single POST with a Bearer header. The plugin's config file is just one way to feed that resolver; environment variables are an equal, higher-precedence way. So the insight is: you do not need the plugin at all. Two exported variables and any agent can save.

P9's job was to take that already-true fact and make it the documented default — both in what a fresh workspace ships with, and in this repo's own operator docs.

Why ~/.zshenv, not a repo .env

The operator's first instinct was to put the exports in a repo .env. That fails for two concrete reasons, and the fix is to move them up into the home shell environment:

  • Neither agent auto-loads .env. Claude Code and Codex do not read a project .env into their process environment, so the resolver would never see the variables at all.
  • A secret in a repo file risks a commit. Even gitignored, it lives in the working tree. (This repo learned the same lesson once already, retiring its own executor-tier .env.)

~/.zshenv is sourced by every zsh invocation, so every Bash call Claude Code makes and every Codex exec inherits the variables, while the key stays out of all repositories. One org-level key then serves every repo, and each document's project defaults to the repo's directory name automatically.

Consume, don't build. The SaaS side — org-level keys, get-or-create projects, returned document URLs — is owned by the knowledge repo's sibling phases (P18/P19/P20). P9 only documents the contract this repo consumes; it implements no server-side behavior.

Best practices & next steps

Where P9 aligns with prevailing practice. Storing credentials in environment variables rather than in files checked into the repository is exactly the Twelve-Factor "store config in the environment" principle: config must be strictly separated from code, the practical test being that "the codebase could be made open source at any moment, without compromising any credentials," and environment variables are favored because they "pose minimal risk of accidental repository commits" (The Twelve-Factor App — Config — 12factor.net). P9's ~/.zshenv-not-a-repo-.env choice is a direct, and arguably stricter, application of that rule.

Stricter than the usual advice, on purpose. Most secret-handling guides stop at "add .env to .gitignore and commit a .sample.env template" so secrets never enter version control (GitGuardian — secure your secrets with .env — gitguardian.com). P9 goes one step further by keeping the token out of the repository tree entirely — not even a gitignored file — which sidesteps the whole class of "accidentally committed .env" incidents rather than merely guarding against them.

Where it deliberately diverges. The same sources recommend a dedicated secrets manager (Vault, AWS Secrets Manager, cloud KMS) for anything production-grade (gitguardian.com). P9 uses a plain exported variable. That is a proportional choice: the token is a low-scope knowledge-base ingest key for a single-operator developer tool, not a production database credential, and the explicit goal is one-command onboarding. A heavyweight secret manager would defeat the "low-friction by default" objective the phase exists to serve.

Concrete next steps.

  • Document key rotation / revocation for the KB token, so an accidental leak has a remedy that matches the manager-free posture.
  • Add a small workflow.py doctor check that verifies KB_API_BASE_URL/KB_API_TOKEN are set and the endpoint answers — turning today's silent "save skipped" into an actionable hint.
  • Once the knowledge repo's P18 org-level keys land, document the get-or-create-project flow end-to-end so the "one key, many repos" story is concrete.
  • Note the ~/.zshenv vs ~/.zprofile distinction for readers on non-zsh or non-interactive shells, so the "sourced everywhere" claim does not surprise bash users.

Quiz

1. Why did P9 recommend ~/.zshenv over a repository .env for the knowledge exports?

The resolver never sees a repo .env (the agents don't load it), and keeping the key in the home shell env keeps it out of every repository.

2. What makes the plugin unnecessary for saving a phase explainer?

Environment variables are the highest-precedence config source, and the save path is a single Bearer-headed POST — no plugin needed.

3. The phase concluded that the real obstacle for Codex was not Cloudflare. What was it, and what is the opt-in?

Cloudflare was verified a non-barrier (plain curl reaches the app). The sandbox is the blocker, and enabling network access is the documented — tradeoff-carrying — opt-in.

4. Why did slice S1 have to rebuild the artifact and bump the version in the same commit, while S2 did not?

The hard rule fires on any edit under installer/. README.en.md is a human-facing doc, not embedded machinery, so no rebuild was required — and the engine was never touched.

Middle slices only leave Doc-impact notes; the phase review consolidates them into new versions on a pass — which is why P9 produced operations v0017 and decisions v0023.
