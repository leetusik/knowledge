Filling the Idle Window: Pipelined Slice Planning and Copy-Based Plan Capture

Background

What this repository is

bootstrap_agentic_workspace.sh is a single shell script you run inside a project directory to install an agentic workspace: a small state machine plus a set of written rules that let an AI coding agent do multi-step engineering work without losing the plot between sessions. The state machine is one Python file (scripts/workflow.py). The rules are markdown — a contract (CLAUDE.md, mirrored byte-for-byte as AGENTS.md) and a folder of skills under .claude/skills/.

Vocabulary you need

Phase — a unit of operator-approved work (e.g. "P10"). Slice — one reviewable step inside a phase (P10.S1, P10.S2). Every phase starts with a DECOMP slice that breaks it into middle slices, and ends with a REVIEW slice that validates the whole thing. Orchestrator — the main agent session you talk to; it plans, commits, and moves state. Executor — a subagent the orchestrator dispatches to actually do a slice's work in its own separate context window.

The orchestrator/executor split exists for one reason: context economy. If the main session did all the implementation itself, its context window would fill with file contents and half-finished edits, and its judgment would degrade over a long phase. So the main session stays lean — it plans, hands the plan to a subagent, and reads back a short structured verdict.

Problem 1: the orchestrator sat idle for the entire executor run

The contract was explicit that the orchestrator must dispatch the executor as a background task and then wait for its completion notification "doing nothing else in the meantime". That sentence was added deliberately (commit d1767f9) to forbid a specific failure: an orchestrator that runs the executor inline, synchronously, in the main session — which defeats the whole point of delegating.

But "doing nothing else" is a blunt instrument. It also forbade useful, harmless work. The do-whole-phase loop — the skill that drives a phase end to end — was therefore strictly serial:

The costly part is research — reading the contract, the phase notebook, the relevant docs, and the code the next slice will touch, to figure out what the plan must say. And here is the observation the operator made that started this phase: research for slice N+1 does not depend on slice N finishing. Only the final reconciliation does — the part where you check what slice N actually changed. So the research was sitting on the critical path for no structural reason.

Problem 2: the approved plan was retyped instead of copied

The workflow uses Claude Code's plan mode: the agent researches read-only, presents a plan, and the operator approves it. The rule then said to write that approved plan "verbatim … not a paraphrase or summary" into the slice's plan.md, so the executor receives exactly what the operator agreed to.

The catch: the harness already has that plan on disk. When plan mode is entered, Claude Code writes the plan to a file (under ~/.claude/plans/) and names it. So the agent was re-emitting, through a Write tool call, a document that already existed byte-for-byte a few directories away. As the operator put it: "since we store a plan in two place, the later slice plan store can be done with cp."

Why the retype is a real risk, not just waste

An LLM regenerating a long document from its own context is not a byte-preserving operation. It can subtly reorder, compress, or drop a clause — and nobody notices, because the output still looks like the plan. That retype was the single point in the whole loop where what the operator approved and what the executor receives could silently diverge.

Intuition

The pipelining idea

This is the oldest trick in computer architecture, applied to an agent loop. A CPU does not wait for one instruction to retire before it starts fetching the next; it overlaps stages. Here, the "stall" is the executor's run — minutes of wall-clock time during which the orchestrator has nothing to do — and the work we want to overlap into it is the read-only research for the next slice.

The word doing the heavy lifting is reconcile. When executor N returns, the orchestrator does not throw away the brief and re-research. It starts from the brief and reads only the delta: what slice N actually changed (its reported files_changed), its result.md, and the new notes appended to the phase notebook. That is a small read, not a full pass.

What the gate is, and why it did not move

There is a single human checkpoint in this loop: the operator approves each slice's plan before its executor runs. A tempting "optimization" would have been to approve plan N+1 early, while N is still running — that would remove the pause entirely.

The design constraint that shaped everything

The operator's approval gate does not move. They still approve plan N+1 after seeing slice N's outcome — its result, its verdict, its notes. Only the research shifted off the critical path; the human's information at the moment of decision is exactly what it was before. This is what makes the change a pure latency optimization rather than a quiet weakening of oversight.

Making "read-only" structural instead of aspirational

A subagent researching a repo while another subagent is editing that same repo is obviously dangerous if it can write. You could write a rule — "the prefetch must not modify anything" — and hope. P10 did not do that. It gave the new agent a tool allowlist of exactly three tools:

tools: Read, Glob, Grep

Trace what that removes. No Write or Edit: it cannot touch a file. No Bash: it cannot run the workflow engine, cannot run git, cannot run a build. No Agent: it cannot dispatch a second executor. The guarantee is enforced by the harness at the tool layer, not by the model's willingness to follow prose.

Torn reads, and the blast-radius rule

The prefetch reads a working tree that another agent is mutating. A file might be read half-edited. There is no lock and no snapshot, so the mitigation is avoidance: the orchestrator tells the planner which paths slice N declared it would touch — its blast radius — and the planner researches around them, labelling anything it must read there as "possibly stale".

Honest about the limit

This is a mitigation, not a guarantee. It was recorded as an accepted trade-off rather than papered over. A related quirk: the phase notebook phase.md is inside every running slice's blast radius, because every executor appends notes to its tail — so it is permanently "readable but stale at the end".

Why copy beats retype

The second change is smaller and sharper. Instead of asking the model to reproduce the approved plan, take the file the harness already wrote and cp it. Byte-exact by construction — there is no room for a paraphrase because no text passes through the model at all.

But a copy needs a guard, and here is the subtlety that makes this more than a one-liner:

The harness reuses one plan file per session

Entering plan mode again overwrites the same file. So two rules are load-bearing: (1) confirm the file's opening lines match the plan you just approved — otherwise you may copy an earlier slice's plan, which is worse than a paraphrase; and (2) copy immediately, before the next EnterPlanMode clobbers it. The rule also forbids globbing ~/.claude/plans/ or picking by modification time — use the exact path the harness named for this session.

And a fallback, because not every environment has a plan file: Codex has no plan mode, and the workflow's unattended auto mode never enters plan mode either. In both cases there is nothing on disk to copy, so Write stays — stated explicitly rather than left as an unexplained exception.

Code

P10 changed no program logic at all. scripts/workflow.py — the state machine — is untouched by both slices. Everything here is machinery prose (the contract and the skills), one new agent definition, and installer plumbing. In a workspace whose behavior is defined by written rules, editing the rules is the code change.

1. The new agent: .claude/agents/slice-planner.md

A 59-line file. Its frontmatter is the security boundary:

---
name: slice-planner
description: Read-only research prefetch for an upcoming, not-yet-planned slice, run
  while another slice's executor is still working; returns a compact advisory brief -
  never a plan, never a file dump, never an implementation. Never writes, never runs
  commands, never commits.
tools: Read, Glob, Grep
model: sonnet
effort: xhigh
permissionMode: bypassPermissions
---

Two choices worth explaining. model: sonnet — a read-and-summarize job does not need the most expensive model, and for a hard next slice the orchestrator supplements with its own inline reading anyway. permissionMode: bypassPermissions — this looks alarming, but it grants nothing here: all three of its tools are already pre-approved in the project's settings. Its actual purpose is to stop a background prefetch from silently hanging on a permission prompt nobody is watching, which would violate the never-block rule.

The body then establishes what has to be stated in prose because no allowlist can express it: that inputs arrive by path (with no Bash, the planner cannot run python3 scripts/workflow.py next to discover anything — the dispatch prompt must hand it the slice id, the folder, the questions, and the exclusions), and that the output is a bounded brief — relevant files, patterns to reuse, constraints, open questions, and an explicit "not read / possibly stale" list. Never a plan. Never a file dump. Its own words:

- **No recommendation phrased as a decision.** "Two options, trade-off is X" is
  useful; "we should do X" is not yours to say.
- **Shallow beats exhaustive.** Answer the asked questions well, stop, and say what
  you left. A late brief is dropped.

2. The loop rewrite in do-whole-phase/SKILL.md

The existing dispatch bullet gained two scoped carve-outs. The first amends the "doing nothing else" sentence without dissolving it:

… and wait for its completion notification, doing nothing else in the meantime
**except the read-only `slice-planner` prefetch described in the next bullet** —
never run it synchronously inline in the main session, never write to the repo or
move workflow state while it runs, and one **executor** at a time: wait for it to
return before dispatching the next (the read-only planner is not an executor and
does not count against that limit).

Notice that the carve-out is narrower than it needed to be: the same sentence now also forbids repo writes and workflow-state moves during an executor run. Without that, "except the prefetch" could be misread as a licence for arbitrary concurrent work. The second carve-out is the parenthetical about "one executor at a time" — the prefetch is a genuinely concurrent dispatch, so the constraint had to be restated as one executor, not one agent.

Then a new bullet with six sub-bullets encodes the guardrails. Compressed, the five skip conditions are:

Skip when…Because
current slice is DECOMPthe middle slices do not exist yet — there is no "N+1" to research
next slice is REVIEWthe review is never pre-planned; its plan depends on the results
next slice is already readyan operator-approved plan.md already exists
phase or any slice is pendingthe loop stops for the operator there anyway
next slice's files sit inside N's blast radiuseverything worth reading is being rewritten as you read it

Plus: never block (the executor's return always wins; at most one prefetch in flight; never delay finish-slice/validate/commit), discard on any verdict other than done (the world the brief assumed did not happen), and scratchpad only, never a slice folder — because a slice owns exactly two context files and a stale draft sitting in a slice folder could later be misread as an approved plan.

3. Installer wiring — the three-edit trap

The distributable bootstrap_agentic_workspace.sh is a build product: an assembler (installer/build.py) embeds the live repo files into one self-contained script. Adding a new agent file needs three edits, and this is the phase's best transferable lesson:

  1. installer/build.py → add the path to FIXED_LIVE_FILES, which embeds it into the artifact's payload table. (Skills are globbed from disk; .claude/agents/ is enumerated explicitly.)
  2. installer/main.py → an explicit write_text(".claude/agents/slice-planner.md", …). The existing agent write is a loop over ("low", "mid", "high") — the three executor tiers — and would never emit a fourth file.
  3. installer/main.py → add the path to MANAGED_FILES, for the fresh-install conflict guard and bookkeeping.

Why a grep would not have caught the bug

With only edit #1, the agent file is embedded in the artifact — so grep slice-planner bootstrap_agentic_workspace.sh passes — but nothing ever writes it to a target directory. It ships as dead payload. The only check that catches this is a real install into a scratch directory, which is exactly why both slices and the review ran one.

4. The copy rule, at every site that persists a plan

The second slice's work was finding all the places, not rewriting one. The rule now reads, in do-next-slice step 2:

After approval, persist the plan: in Claude Code, **copy the harness plan file** —
the exact path the harness named for this planning session; never glob
`~/.claude/plans/` and never pick by modification time — to this slice's own
`plan.md` (e.g. `cp "<the named plan file>" works/phases/active/<P>/slices/<slice_id>/plan.md`),
after **confirming its opening lines match the plan just approved** (the harness
reuses one plan file per session, so a skipped step can leave an earlier slice's
plan sitting there); copy **immediately after approval, before the next
`EnterPlanMode`**, which overwrites the file. … any slice-local addition (an
`## Escalation` section, for example) is **appended after** the copy, never a
rewrite of the copied body.

The same rule landed in six places: both copies of do-next-slice (default branch and plan only branch — the two files must stay byte-identical below their frontmatter), do-whole-phase's default loop and plan only branch, and two clauses in the contract. do-whole-phase's auto branch got the opposite edit — an explicit note that it stays on Write, since plan mode is never entered there, so no file exists to copy.

One small supporting change: .claude/settings.json gained "Bash(cp:*)" in its allow list, so the copy does not raise a permission prompt immediately after every approval. The justification recorded for widening an allowlist is worth copying as a habit — it grants nothing beyond the already-allowed Write tool (overwrite a file, no deletion; rm -rf stays denied).

5. Shipping it as one release

Both slices are one release: slice 1 bumped WORKSPACE_VERSION 18 → 19 and opened a ## v19 changelog section; slice 2 appended to that same section without a second bump. Adopting workspaces run --update and get the new agent file (the update path classifies anything under .claude/agents/ as machinery, so a brand-new file arrives as an addition with no code change needed) plus the merged Bash(cp:*) entry.

Best practices & next steps

Where this aligns with prevailing practice

Idle-time speculative planning is an established technique, and P10 independently arrived at its standard guardrails. The research literature calls this exact pattern speculative planning during tool-execution stalls: drafting runs concurrently with tool execution and "halts immediately upon observation arrival, preventing staleness", with drafts treated as "optional guidance rather than mandatory constraints" so speculation cannot derail the real reasoning step (IdleSpec: Exploiting Idle Time via Speculative Planning for LLM Agents — arxiv.org). That is nearly a line-for-line match with P10's "never block on it — the executor's completion notification always wins" and "the brief is advisory input to your plan, never an approved plan". The same work accepts the same cost model P10 accepted: extra tokens are spent during otherwise-wasted time, and wall-clock latency is what improves.

Restricting speculative work to side-effect-free operations is the standard safety rule. Speculative execution frameworks classify tools as "fully speculatable, dry-run eligible, or speculation-prohibited", because "anything with side effects (database writes, API mutations, financial transactions) must be handled carefully"; and mispredictions are "simply discarded, and execution falls back to the standard sequential path", which is why speculation "can only help, never hurt accuracy" (Speculative Execution and Parallel Tool Calling, Zylos Research — zylos.ai). P10's Read, Glob, Grep allowlist is the strictest version of that rule: rather than classifying each action at runtime, it makes the speculative agent incapable of a side effect. Its "discard the draft on any verdict other than done" is the same fall-back-to-sequential guarantee.

Enforcing read-only via the tool allowlist, not via instructions, is the documented Claude Code posture. The harness itself distinguishes "tools that can't modify state, including file reads, text and file-pattern search, code navigation" from capabilities like "blanket shell access" and script interpreters, which are removed in lower-supervision modes; the underlying principle is that the system should "evaluate the real-world impact of an action, rather than just the surface text of the invocation" (How we built Claude Code auto mode, Anthropic Engineering — anthropic.com). Giving slice-planner exactly the three read-only tools — and no Bash, which is precisely the "script interpreter / blanket shell" category — is that principle applied directly. The decision record says so in the words that matter: the allowlist, not prose, is the enforcement mechanism.

Where it deliberately diverges

No runtime conflict detection — just a declared blast radius. Systems that speculate against mutable state usually add versioning, snapshots, or a validation step that re-checks the speculative read before committing to it. P10 has none: it asks the orchestrator to name the paths slice N declared it would touch and tells the planner to research around them. That is legitimate here because the consequence of a stale read is bounded — the worst case is a brief that is partly wrong, which the human-approved reconciliation step catches. There is no "commit" of speculative results to defend. The phase recorded this honestly as "a mitigation rather than a guarantee" instead of overclaiming.

Speculation depth of exactly one, with no adaptive policy. The literature tracks which speculation strategies are paying off and reallocates budget accordingly. P10 fixes one prefetch in flight, one slice ahead, with five hard-coded skip conditions and human judgment ("size it per slice") for the rest. For a loop that runs a handful of times per phase with a human in it, a Beta-posterior bandit would be more machinery than the problem deserves.

bypassPermissions on the speculative agent. Read literally this is the widest permission mode, which sounds like a divergence from least privilege. It is safe only because it composes with an allowlist of three read-only tools — the mode can only bypass prompts for tools the agent has, and it has nothing dangerous. It is worth flagging as the one place where the design depends on two settings agreeing, rather than on one setting alone.

Concrete next steps

  1. Reconsider effort: xhigh on slice-planner. Higher effort means longer latency, and this agent lives under a "a late brief is dropped" rule — the setting works directly against the goal. Its original justification ("matches the low tier's effort") went stale when the executor presets were re-cut in v18. Lowering it to medium or high is a one-line change plus a rebuild, and would raise the share of briefs that arrive in time.
  2. Decide whether the planner deserves an executors.toml knob. Because it sits outside EXECUTOR_TIERS, its model and effort are pinned in the agent file: operators cannot tune it, and /update-workspace silently resets a local change with no drift warning from validate. That is a known, deliberate deferral — it should be filed as a tracked follow-up rather than remembered.
  3. Measure the actual hit rate before extending the idea. Nobody yet knows what fraction of briefs arrive in time and survive to influence a plan. A few phases' worth of "brief used / dropped-late / discarded-on-verdict" tallies would tell you whether to tune the effort, widen the prefetch to slice N+2, or drop the whole mechanism for short slices.
  4. Keep the user-facing READMEs in step with the machinery. The review found README.en.md still enumerating only the three executor subagents now that a fourth agent file ships, and the Korean tier table still naming Opus for the mid tier after the v18 preset re-cut. Machinery correctness was validated by a real install probe; the prose describing it has no such check, which is a predictable gap worth one small follow-up.

Quiz

1. After P10, when does the operator approve the plan for slice N+1?

The gate deliberately did not move. Only the research shifted off the critical path; the human still decides with exactly the same information they had before, which is what keeps this a latency optimization rather than a reduction in oversight.

2. What actually prevents the slice-planner agent from writing to the repo or running a workflow command?

The prompt does state the rules, but only so the boundary is explicit rather than incidental. The enforcement is the allowlist: no Bash means no workflow commands, no git, no builds; no Agent means it cannot dispatch anyone; no Write/Edit means it cannot touch a slice folder.

3. Executor N returns escalate instead of done, and a prefetched brief for slice N+1 is sitting in the scratchpad. What happens to the brief?

Discard on any verdict other than done. On an escalation, slice N did not land as planned, so the brief's assumptions about the tree are unreliable — and writing it into a slice folder is forbidden anyway, since a stale draft could later be misread as an approved plan.

4. Why must the orchestrator confirm the harness plan file's opening lines before copying it into plan.md?

One plan file per session, overwritten on the next EnterPlanMode. Copying the wrong plan is worse than the paraphrase risk the change set out to remove — which is why the guard, and "copy immediately, before the next EnterPlanMode", are both load-bearing rather than decorative.

5. A new file .claude/agents/my-agent.md is added to FIXED_LIVE_FILES in installer/build.py, and grep my-agent bootstrap_agentic_workspace.sh returns hits. What is still broken?

This is the dead-payload trap the phase documented. The artifact contains the text — so every grep passes — but the installer's agent write loops over ("low","mid","high") and never emits a fourth file. Only a real install into a scratch directory catches it, which is why the probe is a required check rather than an optional one.
