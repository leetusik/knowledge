Background — the running shape

Everything you have read so far in this curriculum was about what the code does. This page is about where it runs, and the answer is: in seven containers on one shared 4-core Oracle Cloud VM, two of which you have never met. Those two are celery_worker and celery_beat, and almost every slow, flaky or long-running thing in changple5 happens inside them — scraping Naver, embedding a corpus, writing a 구성안, charging a subscription, sending a mail.

Seven services, and no web server among them

The production stack is one file: compose.prod.yml, 536 lines, seven services, every one of them restart: unless-stopped with its own healthcheck:

Three things about that table are worth stopping on.

The last three services build from the same directory. django_backend, celery_worker and celery_beat all say build: *backend_build — the same YAML anchor pointing at ./apps/backend. They are the same source, the same Dockerfile and the same env (they all splat the same &backend_env anchor); only the command differs:

# compose.prod.yml — the three commands that matter
django_backend:
  command: ["sh", "-c",
    "python manage.py migrate --noinput && exec gunicorn config.wsgi:application
     --bind 0.0.0.0:8000 --workers ${GUNICORN_WORKERS:-3} --timeout ${GUNICORN_TIMEOUT:-120}
     --access-logfile - --error-logfile -"]

celery_worker:
  command: ["celery", "-A", "config", "worker", "--loglevel=info", "--concurrency=2"]

celery_beat:
  command: ["celery", "-A", "config", "beat", "--loglevel=info"]

They are the same source but three separate images — and that is the single most expensive operational fact in this repo. A deploy that rebuilds only django_backend leaves the worker running last week's code, silently. Three of the eleven operator-configurable LLM roles (conversation_title, image_alt, text_enrichment) do not execute in django_backend at all — they run in celery_worker — so the operator console cheerfully reports a new model as saved while the worker keeps using the old one, with no error anywhere (docs/current/operations.md §“LLM Runtime Config” → “Deploy first, or the feature ships dead on the backend side”). Rebuild celery_worker and celery_beat alongside the web services, always. Explainer #17 owns the runtime-config store itself; here it is just “why the worker image is never optional”.

migrate-on-boot. django_backend runs manage.py migrate before exec gunicorn. What it buys: a deploy never needs a separate “now run the migration” step, so a new column and the code that uses it land together. What it risks: the migration runs while the old worker is still alive (compose starts the new backend before the old containers are all gone), so every migration must be backward-compatible for the length of a deploy — and if the migration fails, the container never reaches gunicorn and the health check keeps failing, which is the loud, correct behaviour.

The worker is not just “the backend with another command”. It also carries a browser. Only celery_worker gets LANG: ko_KR.UTF-8, TZ: Asia/Seoul and shm_size: 1gb, because the Naver login runs headful Chromium inside it and the scraper asserts that navigator.language starts with ko before it touches Naver. It mounts scraper_state (the persistent Chromium profile — that persistence is what makes the daily login look like a returning browser) and backend_media. celery_beat mounts only backend_media and gets none of the locale env: it schedules, it does not scrape.

Where the TLS is, and why it is not here

There is no nginx service in compose.prod.yml, and no service publishes a host port. Every app container is expose:-only. The front door is a separate compose project on the same host — edge-nginx, living in /home/opc/edge — which owns ports 80/443 for all three sites on that box and reaches changple5's containers by name over the external changple_shared_network. Cloudflare sits in front of that in Full (strict) mode. Explainer #1 established this; do not re-derive it from the compose file, because the compose file is precisely where it is not.

What Redis is doing here

Redis wears three hats, on three logical databases, and #1 recorded why they are split: Django's cache.clear() is a FLUSHDB, and it must not be able to wipe the Celery queue. db 0 is the Celery broker and result backend; db 1 is the Django cache; db 2 is the agent's retrieval cache. For Celery, “broker” means the queue a dispatcher pushes a task message onto and a worker pops it from; “result backend” means where a task's return value goes if anyone asks for it.

# apps/backend/config/settings.py:697
CELERY_BROKER_URL = env(
    "CELERY_BROKER_URL",
    default=f"redis://{REDIS_HOST}:{REDIS_PORT}/0",
)
CELERY_RESULT_BACKEND = env(
    "CELERY_RESULT_BACKEND",

Notice the code default carries no password, while the production Redis runs --requirepass. That is exactly why compose.prod.yml makes both required (${CELERY_BROKER_URL:?CELERY_BROKER_URL is required}) rather than defaulted: a soft default would connect to nothing and fail at the first dispatch instead of at docker compose up.

Intuition — the request thread is not where the work happens

Here is the whole idea of this page in one sentence, in the builder's terms:

Django's request thread does the smallest possible thing and hands everything slow, flaky or long-running to a Celery worker through Redis — and it does so only after its own transaction has committed.

The first half is ordinary: gunicorn runs three sync workers, each handling exactly one request at a time, so a 40-second scrape inside a request would block one third of the entire site's capacity for 40 seconds. Handing it off costs one Redis round-trip.

The second half — after the commit — is the part that bites everyone once. Consider a real toy case: an operator clicks 발행 on a content draft. In one HTTP request, Django opens a transaction, writes published_at on the row, and wants a worker to re-index that content into the vector store.

The worker usually wins that race, which is what makes the bug so nasty: the symptom is not a crash but a worker that reads a row in its pre-write state (or, worse, does not find the row at all and quietly exits). Django's answer is transaction.on_commit(callback): the callback is parked until the outermost transaction commits, and then runs; if the transaction rolls back, it is dropped entirely — which is the second thing you want, because you do not want to index a publish that did not happen.

Around that one pattern sit five supporting systems, and the rest of this page is those five:

  • Recovery — what if the worker was restarting when the job was queued? (§3.6)
  • Scheduling — who fires the daily 05:40 scrape? (§3.1)
  • Retries, at two layers — the Celery task retry above, and the LLM retry below. (§3.3, §3.7)
  • Alerting — what if the worker is the broken thing? (§3.8)
  • Observability — where does a builder look afterwards? (§3.9)

Code — the nine moving parts

3.1 The Celery app, and what namespace="CELERY" means

apps/backend/config/celery.py is 114 lines and it is the whole control surface. The first four lines do everything structural:

# apps/backend/config/celery.py:10-14
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")

app = Celery("config")
app.config_from_object("django.conf:settings", namespace="CELERY")
app.autodiscover_tasks()

config_from_object(..., namespace="CELERY") means: read Celery's configuration out of Django settings, taking every setting whose name starts with CELERY_ and lowercasing the rest. So CELERY_BROKER_URL becomes Celery's broker_url, and CELERY_WORKER_MAX_TASKS_PER_CHILD becomes worker_max_tasks_per_child. One settings file configures both Django and Celery, with no second config format. #2 owns settings resolution; this is the one line where it reaches Celery.

autodiscover_tasks() means: for every app in INSTALLED_APPS, import its tasks module. That import is what registers the task names — nothing else does.

The beat schedule: six entries, and one of them is the whole ingestion clock

Six entries, and the interesting one is the first. Beat does not know that the daily Naver scrape happens at 05:40 Asia/Seoul; it only knows to poke ingestion.evaluate_scheduled_incremental_schedule once a minute. That task reads an IngestionSchedule row from the database and decides whether it is time. Putting the schedule in a row instead of in crontab() is what lets the operator change the daily time from the console without a deploy — and it is why beat's own schedule can stay this short. (#8 owns the ingestion pipeline; #18 owns what the two billing sweeps actually do.)

The second thing beat is not doing is just as important: beat never executes a task. It publishes a message to Redis at the scheduled moment and nothing more. If the worker is down, beat keeps queueing; when the worker returns it drains the backlog.

Every single one of them is a thin wrapper. The pattern, verbatim from apps/backend/ingestion/tasks.py:

"""Celery task entrypoints for the ingestion app.

Thin ``@shared_task`` wrappers that bind the ``"ingestion.*"`` task names to the
pipeline callables in ``execution``, ``backfills``, ``reprocess``, the automatic /
manual-incremental run modules, and ``recovery``. Keep the task-name strings here
byte-stable: they are the Celery routing contract.
"""

@shared_task(name="ingestion.poll_provider_batches")
def poll_provider_batches(job_id: int) -> dict[str, object]:
    status = poll_provider_enrichment_job(job_id)
    return {"job_id": job_id, "status": status}

Two design rules hide in there, and both pay off constantly.

Why the logic lives in another module. poll_provider_enrichment_job is a plain function. You can call it from a test, from manage.py shell, or from another task, with no broker running and no Celery imported. The @shared_task wrapper adds exactly one thing — a name — and the name is the only part Celery needs.

Why the name is a string, everywhere. A dispatcher fires a task like this:

app.send_task("conversations.generate_session_title", kwargs={"session_id": session_id})

— not generate_session_title.delay(...). Dispatching by string means the dispatching module never imports the task module, which means content can queue a task that lives in content.tasks without an import cycle (tasks.py imports the pipeline modules; if those imported tasks.py back, Python would deadlock the import). The docstring's phrase for this is exactly right: the strings are the routing contract. Renaming a Python function is free; renaming the string in name= orphans every message already sitting in Redis under the old name.

3.3 A task that retries itself

When a task can fail transiently, the idiom is bind=True plus a retry budget. The cleanest worked example is the 컨설팅 report (#10 told the story; here is its Celery half):

# apps/backend/conversations/tasks.py:25-40
@shared_task(
    bind=True,
    name="conversations.generate_consulting_report",
    max_retries=CONSULTING_REPORT_GENERATION_MAX_ATTEMPTS - 1,   # 3 - 1 = 2
)
def generate_consulting_report(self, report_id: str) -> dict[str, object]:
    parsed_report_id = UUID(str(report_id))
    task_id = str(getattr(self.request, "id", "") or "")
    retry_count = int(getattr(self.request, "retries", 0) or 0)

    return run_consulting_report_generation_with_retry(
        report_id=parsed_report_id,
        task_id=task_id,
        retry_count=retry_count,
        retry=self.retry,
    )

bind=True makes Celery pass the task instance as self, which is how the function reaches self.request.retries (how many times this message has already been retried) and self.retry(...) (raise a special exception that re-queues the same message with a delay). max_retries = MAX_ATTEMPTS - 1 is the standard off-by-one: three attempts are two retries.

Then look at what the wrapper does with it — it hands self.retry to a plain function:

# apps/backend/conversations/tasks.py:43-69
def run_consulting_report_generation_with_retry(*, report_id, task_id="", retry_count=0, retry):
    try:
        return execute_consulting_report_generation(report_id=report_id, task_id=task_id)
    except AgentReportGenerationTransientError as exc:
        if retry_count < CONSULTING_REPORT_GENERATION_MAX_ATTEMPTS - 1:
            raise retry(exc=exc, countdown=CONSULTING_REPORT_GENERATION_RETRY_DELAY_SECONDS)  # 30s
        return terminally_fail_consulting_report_generation(report_id=report_id, error_detail=str(exc))
    except AgentReportGenerationPermanentError as exc:
        return terminally_fail_consulting_report_generation(report_id=report_id, error_detail=str(exc))

The pattern to steal: the policy (transient → retry with a countdown; permanent → record a terminal failure; budget exhausted → also terminal) is a normal function taking retry as a parameter. A unit test passes a fake retry and asserts the whole decision table without Celery, without Redis, and without waiting 30 seconds. The @shared_task above it is four lines of plumbing.

The other half of the pattern is the exception taxonomy. The code distinguishes TransientError from PermanentError at the dispatch boundary — and #15 recorded how that classification is produced: the agent answers 503 for any pipeline failure, and the backend's classifier treats {429, 500, 502, 503, 504} as transient and everything else (including a non-JSON body) as permanent. So “Gemini hiccuped” becomes a Celery retry 30 seconds later, while “the payload was malformed” fails the job immediately instead of burning three attempts on a bug.

3.4 Dispatch-after-commit, and its variants

Start with the smallest instance in the repository. This is apps/backend/conversations/dispatcher.py — all 31 lines of it, minus imports:

# apps/backend/conversations/dispatcher.py
def queue_session_title_generation_on_commit(session_id: int) -> None:
    def _dispatch() -> None:
        try:
            dispatch_session_title_generation(session_id)
        except Exception as exc:
            logger.warning(
                "Failed to dispatch conversation title generation for session %s: %s",
                session_id, exc,
            )

    transaction.on_commit(_dispatch)


def dispatch_session_title_generation(session_id: int) -> str:
    result = app.send_task(
        "conversations.generate_session_title",
        kwargs={"session_id": session_id},
    )
    return str(result.id)

Three decisions in those lines:

  1. The callback is registered, not called. transaction.on_commit(_dispatch) returns immediately. Django runs _dispatch after the outermost transaction.atomic() block commits. Two edge cases are worth knowing precisely: outside any transaction (Django's default autocommit mode, which is what this project runs — there is no ATOMIC_REQUESTS anywhere in settings.py) the callback runs immediately and synchronously; and inside nested atomic blocks it waits for the outermost one, because an inner block is a savepoint, not a commit.
  2. The dispatch cannot fail the request. A dead broker raises inside _dispatch, which logs a warning and returns. The user's message was already saved; they just get an untitled conversation.
  3. The dispatcher is a module, not a line in a view. Naming queue_…_on_commit makes the guarantee visible at every call site, which is why this codebase has twelve functions whose names end in _on_commit.

Now the hardened variant. Ingestion jobs are long, operator-visible and scheduled, so apps/backend/ingestion/dispatcher.py (77 lines) does three more things:

# apps/backend/ingestion/dispatcher.py:17-49
def queue_ingestion_job_on_commit(job_id, *, on_dispatch_error=None) -> None:
    def _dispatch() -> None:
        try:
            scheduled_at = IngestionJob.objects.values_list("scheduled_at", flat=True).get(pk=job_id)
            if scheduled_at is None:
                task_id = dispatch_ingestion_job(job_id)
            else:
                task_id = dispatch_ingestion_job(job_id, eta=scheduled_at)      # (1)
        except Exception as exc:
            logger.exception("Failed to dispatch ingestion job %s.", job_id)
            IngestionJob.objects.filter(pk=job_id).update(                      # (2)
                status=IngestionJob.Status.FAILED,
                finished_at=timezone.now(),
                error_message=f"Failed to dispatch ingestion job: {exc}",
            )
            if on_dispatch_error is not None:
                on_dispatch_error(exc)
            return

        IngestionJob.objects.filter(pk=job_id).update(                          # (3)
            status=IngestionJob.Status.QUEUED,
            celery_root_task_id=task_id,
            error_message="",
        )

    transaction.on_commit(_dispatch)
  1. It re-reads the row inside the callback to pick up scheduled_at and turn it into Celery's eta (“do not run this before that timestamp”). Re-reading, rather than closing over a value from before the commit, is deliberate: by the time the callback runs, the committed row is the truth.
  2. A failed dispatch is written down. The job goes FAILED with the error text, and an optional on_dispatch_error callback lets the caller react (the schedule evaluator uses it to raise an alert). Compare the title dispatcher, which only logs: here the row is the operator's view of the system, so “was this ever queued?” must be answerable from the database.
  3. A successful dispatch is written down too — status QUEUED plus celery_root_task_id, which is later what lets an operator cancel the job (app.control.revoke(task_id), three lines further down the same file).

Across those files there are exactly three dispatch idioms, and the differences are not stylistic.

Idiom 1 — app.send_task("name", …) inside on_commit (the default)

Everything above. Use it whenever a row you just wrote is the task's input.

Idiom 2 — app.send_task directly, no on_commit (two sites, both justified)

The first is celery.py's worker_ready handler (§3.6): it runs at process startup, where no transaction exists, so there is nothing to wait for. The second is the Notion mirror, and its docstring states the reasoning better than a summary could:

# apps/backend/content/notion_mirror.py:118-129 (called from draft_publish.py:170)
def queue_notion_mirror(job: ContentDraftJob) -> str:
    """The S4 seam entry point: called right after a Miracle publish
    succeeds (`execute_draft_publication`), OUTSIDE any transaction (the
    publish's own `transaction.atomic()` block already committed by then) —
    so this dispatches directly via `app.send_task`, NOT `on_commit`.
    ...
    """

The rule generalises: on_commit is not a ritual, it is an answer to “am I inside a transaction right now?” If the answer is no, on_commit runs the callback immediately anyway — harmless, but it hides the intent, and the comment above is better documentation than a no-op wrapper.

Idiom 3 — the task object, with a function-local import

Four sites use Celery's classic .delay() — accounts/views.py:117 and :132 (verification and password-reset mail), consultations/services.py:53 (the 상담신청 notification), and billing/views.py:381 (the Toss webhook) — and one uses .apply_async(): content/notion_export.py:198. All of them import the task inside the function:

# apps/backend/consultations/services.py:43-58
def _enqueue_notification(consultation_id: int) -> None:
    """Fire the async notification without ever blocking/failing the submit. ..."""
    try:
        from .tasks import send_consultation_notification     # deferred: tasks.py imports this module

        send_consultation_notification.delay(consultation_id)
    except Exception:   # noqa: BLE001 - enqueue failure must not fail the submit
        logger.exception("failed to enqueue consultation %s notification", consultation_id)

That function-local import is the import cycle idiom 1 avoids for free, worked around by hand. And none of the five wraps its dispatch in on_commit — correctly, because Django runs in autocommit and none of those views opens an atomic() block around the write, so the row is already committed when .delay() is called. The pattern is not “always use on_commit”; it is “know whether you are inside a transaction”.

3.6 Startup recovery: the worker_ready fan-out

Dispatch-after-commit protects you from a worker that is too fast. Startup recovery protects you from a worker that was not there at all. Celery emits a worker_ready signal when a worker has booted and is consuming the queue; celery.py:59-114 hangs eight re-dispatches off it:

# apps/backend/config/celery.py:59-114 (first two of eight, all identical in shape)
@worker_ready.connect
def dispatch_startup_recovery(**kwargs) -> None:
    del kwargs
    try:
        app.send_task("ingestion.recover_jobs")
    except Exception as error:
        logger.warning("Failed to dispatch ingestion startup recovery: %s", error)
    try:
        app.send_task("conversations.reclaim_stale_consulting_reports")
    except Exception as error:
        logger.warning("Failed to dispatch consulting report startup recovery: %s", error)
    ...

The eight, in order: ingestion.recover_jobs, conversations.reclaim_stale_consulting_reports, content.reclaim_stale_draft_generations, content.reclaim_stale_draft_publications, content.reclaim_stale_agent_chat_intakes, content.reclaim_stale_agent_author_briefs, billing.run_renewal_sweep, billing.run_reconciliation_sweep.

Every one is in its own try/except, which is the whole point of writing it out eight times instead of looping: one failing dispatch must never stop the other seven. Six of the eight are startup-only — they have no beat entry at all. The two billing sweeps are both startup and daily, so on a deploy day they run twice; that is safe by construction, because a renewal computes a deterministic orderId (and Toss Idempotency-Key) of the form sub-{id}-{period_end:%Y%m%d}-a{n+1} and skips without charging if a Payment row already exists for it (#18 has the full ladder).

Why does a worker restart matter so much? Because a deploy is a worker restart, and Celery's prefork children die with their task. A 12-minute embedding run that was 8 minutes in when the deploy landed leaves a row saying RUNNING and no process anywhere that intends to finish it. Recovery is what notices.

Follow the first one: ingestion.recover_jobs → recovery.recover_startup_state() in apps/backend/ingestion/recovery.py (296 lines). #8 owns what those jobs do; what matters here is the contract, and the module states it in a comment that deserves to be quoted in full:

# apps/backend/ingestion/recovery.py:32-38
#: Worker-boot recovery must never touch a paused run. Every queryset below is
#: a positive status allow-list that already leaves `paused` out, but the
#: exclusion is spelled out anyway (P53.S14 rule 3): a redeploy silently
#: un-pausing an operator-stopped run would be the worst failure this module
#: can have, and a future widening of one of those allow-lists must not be able
#: to cause it by accident.
_RECOVERY_EXCLUDED_RUN_STATUSES = {IngestionBackfillRun.Status.PAUSED}

The recovery contract, in three rules. (1) Allow-list, never deny-list — recovery acts only on explicitly named non-terminal statuses (RECOVERABLE_JOB_STATUSES = {QUEUED, RUNNING}), so a status invented next year is ignored by default rather than resurrected. (2) Redundant exclusions on purpose — PAUSED is already outside every allow-list, and is excluded again anyway, because the cost of getting it wrong (a deploy restarting a run the operator deliberately stopped) is far higher than a redundant .exclude(). The soft-재수집 run gets the same treatment for SUCCEEDED / CANCELLED / NEEDS_ATTENTION: “a finished run is history and a needs_attention one has already been judged.” (3) Re-dispatch, do not re-execute — recovery decides which message to send (poll vs start, based on the run's stored retry_state) and sends it; it never runs pipeline work in the boot path.

The reclaim tasks (the six others) share one invariant that #15 recorded from the other side, and it is the single easiest thing to get wrong:

The reclaim window MUST exceed the maximum attempt duration. If a draft generation can legitimately take 900 seconds (DRAFT_GENERATION_TIMEOUT_SECONDS = 900) and you reclaim anything “stuck” for more than 10 minutes, you will re-dispatch a live attempt and have two workers writing the same job. The real numbers keep a comfortable margin: CONTENT_DRAFT_RECLAIM_AFTER_MINUTES = 30 against a 15-minute attempt; CONSULTING_REPORT_RECLAIM_AFTER_DEFAULT_MINUTES = 15 against a 180-second attempt. The settings comment in settings.py:507-518 states the rule out loud so the next person who tunes a timeout knows to tune both.

3.7 Retries at two layers, and the two llm_resilience twins

You have now seen one retry mechanism (§3.3): Celery re-queues the whole task. There is a second one, strictly underneath it, inside a single LLM call. Keeping them straight is the difference between “one flaky Gemini response” and “three full pipeline attempts burned”.

There are two implementations of the inner layer, one per service: apps/backend/core/llm_resilience.py (330 lines) and apps/agent/app/llm_resilience.py (247 lines). They are deliberate twins — the same knob names on both sides, “so an operator configures one contract across both services” — and their differences are all forced by the environment they serve.

Both disable the vendor SDK's own retry so there is exactly one authority: native_resilience_kwargs() passes max_retries=1 (google-genai's “no retries” value) into the client constructor, and the module docstring names the consequence — call_with_retry is “the single 429 authority”.

The asymmetry is a decision, not an oversight

The backend twin's docstring records the reasoning verbatim:

# apps/backend/core/llm_resilience.py:42-48
**Scope (P77.S1 decision).** The widening is deliberately Gemini-wide at this
seam — every backend Gemini caller (content agent v2, ingestion enrichment,
conversation titles, brand verification) gets the same bounded transient
retry, because this module is already "the single retry authority" and a 503 is
transient for all of them. The agent-side twin
(``apps/agent/app/llm_resilience.py``) is deliberately NOT widened: it serves
interactive chat, where a multi-second backoff is worse than a fast failure.

Read that as a product decision wearing an infrastructure costume. A 구성안 generation running in a worker can afford to sleep 2 s, then 4 s, then 8 s before giving up — nobody is watching. A user waiting on a streaming chat turn cannot: an eight-second silent pause is worse than an honest “try again”. Same class of error, opposite right answer, and #15 recorded how the agent side then hands the problem upwards anyway — a 503 from the agent becomes a transient Celery retry on the backend, which is the slow-path budget re-entering by the correct door.

Both twins also encode one operator ruling that is easy to miss: a retry always re-invokes the identical client — same model, same thinking level. There is no fallback to a cheaper or different model, ever. The backend docstring: “because P77's operator ruling forbids any fallback to another model”.

Measuring it, instead of believing the docstring

You can execute these loops without a broker, without Django and without the Gemini SDK, by slicing the functions out of the source with Python's ast module and running them against stubs. Here is the backend loop, driven by a fake client that fails with two 429s, then two 503s, then a message-only "try again later", then succeeds — with time.sleep replaced by a list that records what it was asked to sleep:

seq = [APIError(429), APIError(429), APIError(503), APIError(503),
       RuntimeError("The model is overloaded. Please try again later."), None]

# result: ok | attempts: 6 | sleeps: [0.528, 1.212, 2.048, 4.976, 8.246]
# three 429s -> APIError 429 | attempts: 3
# 400 -> raised immediately, code 400
# deadline 25s, each attempt 20s -> stopped after one attempt, code 503

Four things fall out of those numbers, and none of them is obvious from reading:

  • Six attempts in one call. The two budgets are counted independently (used = {"429": 0, "transient server error": 0}), so a provider outage cannot eat the rate-limit budget. Total sleeping: about 17 seconds inside one “single” LLM call.
  • The jitter is real and applies to both classes. 0.5 → 0.528, 1.0 → 1.212, 2.0 → 2.048, 4.0 → 4.976: each delay is multiplied by 1 + random()*0.25 so a fleet of workers hitting the same outage does not re-converge on the same second.
  • The fifth failure had no status code at all. It matched _SERVER_ERROR_TOKENS ("try again later") — the narrow list of provider phrasings used only when LangChain's wrapper has swallowed the numeric status. An exception that does carry a status is judged by the status alone, so a 4xx can never match a token.
  • The wall-clock deadline works as advertised. With deadline_seconds=25 and 20-second attempts, the loop refuses the retry it cannot afford and re-raises immediately, so a caller inside a 120-second gunicorn worker can answer in its own words instead of being killed mid-request.

The agent twin, sliced the same way, behaves exactly as its docstring says — delays [0.5, 1.0] for base=0.5, max_retries=2, the original exception re-raised once the budget is spent, a wrapped 429 (a RuntimeError whose __cause__ is the APIError) still counted as retryable because the predicate walks the __cause__ chain, a 503 re-raised on the first failure, and max_retries=0 disabling the loop entirely.

Defaults are not what production runs. GEMINI_MAX_RETRIES defaults to 2 in code and in compose.prod.yml, but the env file sets it to 6. With the 3-retry 5xx budget on top, the backend's own docstring does the arithmetic: “up to ten retries and ~140 s of sleeping on top of every attempt's own request timeout — measured against a 120 s gunicorn worker”. That is precisely why deadline_seconds exists, and why a caller inside a web request should pass it while a Celery caller usually should not.

3.8 Alerts — when the worker is the broken thing

Everything so far assumes that when something breaks, something else still works well enough to record it. In July 2026 that assumption failed, and the module that came out of it, apps/backend/ingestion/alerts.py (101 lines), is the best-written piece of operational reasoning in this repository. Its docstring is the lesson:

# apps/backend/ingestion/alerts.py:1-21
"""Operator mail alerts for ingestion failures.

Born from the 2026-07 outage, where a leaked Playwright event loop poisoned a
Celery prefork child and EVERY ORM call in it raised SynchronousOnlyOperation
for days with zero external signal. The alert path therefore has hard rules:

- Zero ORM access: recipients are resolved WITHOUT the database ...
  A saved list wins once written — including a saved EMPTY list, which means
  "deliberately no recipients". A cache read failure is itself a miss, so a
  dead Redis degrades to env rather than to silence.
- Synchronous send, no .delay(): a queued task may never run when the worker
  is the thing that is broken.
- Never raises: an alert failure must not mask the original error.
- Throttle state is a module-level in-process dict, not the Redis cache (cache
  get/set raises when Redis is down). Worst case is one duplicate mail per
  prefork child plus a reset when a child recycles — acceptable for ops mail.
"""

Sit with what happened for a moment. A browser automation leak left one prefork child in a state where every database call raised. The child kept accepting tasks. The container kept passing its health check. The console kept rendering. Nothing said a word for days.

Celery replaces Django's logging configuration when it starts, which is why the setup_logging signal exists at all — connecting to it is how you say “no thanks, I will configure it myself”. And the service name is derived by looking at sys.argv: the same image, the same code, two identities, distinguished by the word beat on the command line. Crude, and exactly sufficient.

The handler itself has one subtlety, and it is the kind of bug you only find in production:

# apps/backend/operators/logging_handler.py:32-41
def emit(self, record: logging.LogRecord) -> None:
    if getattr(self._local, "_in_emit", False):
        return
    self._local._in_emit = True
    try:
        self._write_record(record)
    except Exception:
        self.handleError(record)
    finally:
        self._local._in_emit = False

Why _in_emit exists. This handler writes to the database. If that write fails, Django's database layer logs a warning. That warning goes to the root logger. The root logger calls this handler. Which writes to the database. Which fails. Without the guard, one database hiccup becomes infinite recursion inside the logging system. The flag is a threading.local() — per-thread, because gunicorn serves concurrent requests on separate threads and a shared flag would make one request's logging suppress another's.

The context column carries {"request_id": ...} only when ENABLE_CORRELATION_IDS is on, and outside a request (Celery, management commands) there is no bound id, so it stays None.

(b) Correlation ids — one id across two services

apps/backend/operators/middleware.py is 40 lines and is worth reading whole:

# apps/backend/operators/middleware.py:18-40
class CorrelationIdMiddleware:
    """Bind an ``X-Request-ID`` correlation id for the duration of each request.

    Generation is unconditional (never gated): every request honors an inbound
    ``X-Request-ID`` or mints a fresh UUID, binds it to a contextvar, and echoes
    it on the response. The ``reset(token)`` in ``finally`` is mandatory — Django
    serves requests on reused worker threads, so without it a contextvar could
    leak the previous request's id into the next request served by that thread.
    """

    def __call__(self, request):
        incoming = (request.headers.get(REQUEST_ID_HEADER) or "").strip()
        request_id = incoming or str(uuid.uuid4())
        token = _request_id_var.set(request_id)
        try:
            response = self.get_response(request)
        finally:
            _request_id_var.reset(token)
        response[REQUEST_ID_HEADER] = request_id
        return response

A ContextVar is the async-and-thread-safe replacement for a thread-local: set it at the top of a request and any code deeper in the stack can read it without passing it through twenty function signatures. set() returns a token, and reset(token) restores the previous value — the discipline that keeps a pooled worker thread from carrying one request's id into the next.

#2 taught the agent's half (app/correlation.py, a pure-ASGI middleware rather than BaseHTTPMiddleware, so the contextvar stays visible inside streaming generators) and the two gates. The join is what matters here: generation and the response echo are unconditional on both sides; ENABLE_CORRELATION_IDS (default True, and never set in compose.prod.yml) gates only FORWARD and PERSIST — whether the agent puts the id on its backend calls, and whether the backend stores it on a log row. So a browser that sends X-Request-ID: abc can find abc in the context column of rows written by two different services.

(c) Agent → backend error reporting

The agent has no operator console of its own, so it posts its errors into the backend's: apps/agent/app/error_reporting.py (137 lines).

# apps/agent/app/error_reporting.py:102-137 (abridged)

        return

Four things here are transferable to any async service. The report is fire-and-forget (a POST /api/admin/system-logs/report with the shared service token, 5-second timeout, every failure swallowed into a warning). It runs off the event loop via asyncio.to_thread, because the reporter uses a synchronous httpx.Client and blocking the loop of a streaming server is how you stall every other user's turn. It is a detached task, so tearing down the failed stream does not cancel the report of why it failed. And the module keeps a strong reference set — an asyncio task with no live reference can be garbage-collected before it ever runs, a genuinely surprising footgun.

Three call sites, each tagging its own context: chat.py:1495 (source: "chat_stream", plus the run id), content_drafts.py:151 (source: "content_draft", plus the job id — the one #15 showed), and consulting_reports.py:191 (report id + conversation nonce; it is the only one of the three that does not set a source key). Each adds request_id when one is bound.

3.10 Health checks and the boring parts

All seven services define a healthcheck, and the app ones are real HTTP probes:

  "import sys, urllib.request; response = urllib.request.urlopen('http://127.0.0.1:8000/api/health', timeout=5); sys.exit(0 if response.status == 200 else 1)"]

# compose.prod.yml — fastapi_agent (same shape, /agent-api/health on :8001)

# compose.prod.yml — celery_worker

  "from pathlib import Path; import sys; cmd = Path('/proc/1/cmdline').read_text(); sys.exit(0 if 'celery' in cmd and 'worker' in cmd else 1)"]

Look hard at that third one. The worker's health check reads PID 1's command line and asks whether the words celery and worker appear in it. That is liveness in the weakest possible sense: it proves a celery worker process was started. It cannot tell you whether the worker is consuming the queue, whether a prefork child is poisoned, or whether every ORM call has been raising for three days. The 2026-07 outage passed this check continuously. Written down plainly: the alert path in §3.8 exists because this health check structurally cannot do that job, and no amount of tuning the check would change that — only something that reports the work, not the process, can.

The depends_on: condition: service_healthy chains are a startup ordering tool, not a runtime guarantee:

django_backend  → postgres_db, redis
fastapi_agent   → postgres_db, redis, django_backend
celery_worker   → postgres_db, redis, django_backend
celery_beat     → postgres_db, redis, django_backend
nextjs_frontend → (nothing)

Both Celery services wait for django_backend to be healthy — which usually means the migration in its command has finished, so the worker never boots against a schema older than its code. Once everything is up, depends_on does nothing at all; a Redis that dies at noon is handled by restart: unless-stopped plus the code's own degradation, not by compose.

Finally the volumes, because two of them belong to the worker: backend_media (uploaded and derived media — mounted by backend, worker and beat) and scraper_state (mounted by backend and worker only). The second one holds the persistent Chromium profile for the Naver login, and the compose comment explains why it must survive a restart: cookies, cache and device state persisting is “what makes the daily login look like a returning browser”. pg_data and redis_data are the obvious two; Redis runs --appendonly yes, so a restart does not lose queued task messages.

The release procedure itself — deploy.sh, the GitHub Actions workflow, backup and rollback — is deliberately out of scope here; it lives in docs/current/operations.md §“Deploy: ./deploy.sh” and §“CI/CD: GitHub Actions”. This page is about the shape that runs, not the procedure that puts it there.

Quiz

1. A view opens transaction.atomic(), writes a row, and calls app.send_task("content.sync_content_chunk_index", kwargs={"content_id": 7}) directly inside the block. What is the most likely observable result?

The message is published immediately, and the worker is a separate process with its own connection, so it cannot see uncommitted rows. It usually wins the race, and the symptom is silently wrong data rather than an error. transaction.on_commit(...) parks the dispatch until after COMMIT — and drops it entirely on a rollback.

2. Why does ingestion/alerts.py refuse to use the ORM and refuse to use .delay()?

In the 2026-07 outage a leaked Playwright event loop poisoned a prefork child so that every ORM call raised SynchronousOnlyOperation for days. An alert that needed a database read, or that needed the worker to execute a queued task, would have been silent in exactly the situation it existed for. Hence: recipients from a Redis cache with an env fallback, a synchronous send, an in-process throttle dict, and a top-level except that never raises.

3. Gemini answers 503 UNAVAILABLE. What happens on the backend versus in the agent, and why do they differ?

P77.S1 widened only the backend twin, and the docstring says why: backend callers are batch/worker work where sleeping is free, while the agent serves streaming chat. Note also that no retry anywhere falls back to another model — the operator ruling is that a retry re-invokes the identical client. On the backend the 429 budget and the 5xx budget are counted independently, so an outage cannot consume the rate-limit allowance.

4. A reclaim task re-dispatches jobs that have been “running” too long. Its window is 10 minutes; the attempt it protects can legitimately take up to 15. What goes wrong?

The reclaim window must exceed the maximum attempt duration — the rule is written into the settings comment beside CONTENT_DRAFT_RECLAIM_AFTER_MINUTES (30 minutes against a 900-second attempt). Nothing deduplicates for you: the reclaim's whole premise is “no process is working on this any more”, and if that premise is wrong you get a double-dispatch.

5. DatabaseLogHandler.emit() sets a thread-local _in_emit flag and returns early if it is already set. What does that prevent?

The handler's output destination is the thing that can fail — and a failure inside the database layer is itself logged. Without the re-entrancy guard one hiccup becomes an unbounded recursion inside the logging system. It is thread-local rather than global so that one request's in-progress emit does not suppress another thread's logging.
