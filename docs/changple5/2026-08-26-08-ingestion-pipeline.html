Ingestion: how Naver cafe posts become an eligible corpus

Explainer #8 of the changple5 builder’s curriculum, Part B — the first of the two write-path pages. Explainer #7 walked the read path and took two things as given: a boolean column called reference_eligible that every retrieval statement filters on, and an array called keyword_terms that the entire lexical arm matches against. Neither falls from the sky. Both are produced by a machine that logs into a Naver cafe with a real browser, pages ~840 listing screens, fetches articles one at a time on a politeness timer, spends money on two different Gemini passes, and then — in exactly one function — decides whether the result may ever be quoted to a user.

Background

The corpus, and who owns it

미라클 — the product this codebase is — answers questions about starting and running a small food business in Korea. It does not answer them from the model’s memory. It answers them by quoting posts from 창플, a Naver cafe: a members-only community forum that the operator has run for years and that now holds roughly 42,000 articles written by its members. When 미라클 tells a user “a 치킨집 in that neighbourhood typically opens for around this much”, that sentence is supposed to be traceable to a specific post that a specific 창플 member actually wrote.

That makes the cafe the product’s supply side, and it creates an awkwardness worth naming up front: the corpus is ours, the platform is not. Naver Cafe offers no export, no bulk API for owners, no webhook when a post is written or moved or deleted. There is no “download my community” button. Everything this page describes exists because the only way to get the corpus out is to log in as a member and read it, post by post, the way a person would — and then keep doing that forever, because members keep writing.

Two more properties of the source shape everything downstream:

  • Not every post belongs in an answer. A 출석체크 (daily attendance check-in) board is 100% noise. A 가입인사 (introduce-yourself) board is 100% noise. A post by a brand-new member carries none of the authority a post by a 파트너회원 does. The cafe is a community, not a knowledge base, and something has to draw the line.
  • Posts are mostly pictures. A large share of 창플 posts are KakaoTalk screenshots, photos of a shop, or a menu board with the numbers on it. The text a language model can read is frequently not in the post at all — it is in the image.

So the write path has four jobs, and the rest of this page is those four jobs in order: collect the posts, persist them as rows, enrich them into something searchable (a summary, keywords, and alt text for every image), and judge whether each one is allowed to be quoted. Explainer #9 picks up where this one stops and turns the judged, enriched rows into pgvector chunks.

Skip if you know it This page assumes four things from earlier explainers, and re-derives none of them: the repo runs two Python apps over one Postgres (a Django backend owning schema backend, a FastAPI agent owning schema agent) with a one-way read grant so the agent can SELECT from Django’s tables but never write them (#1); background work runs on Celery over Redis db/0, dispatched after commit (#1, taught properly in #16); LLM model ids and thinking levels are live operator config read from a database table, not env vars (#2); and retrieval reads ds.reference_eligible = TRUE plus a live brand-policy join (#7).

Why the whole design collapses into one sentence

Before this subsystem was rebuilt, the question “may this post be quoted?” was answered independently at 13 different sites in two languages — six Django ORM Exists filters, five raw-SQL joins inside the agent, and two enrichment cost gates — with a minimum-length rule asserted at nine more. As docs/current/architecture.md puts it, those thirteen answers “agreed only by coincidence, and nothing re-asked the question when a rule changed.” The concrete symptom was a hole nobody could see: forty posts sat in the database waiting to be enriched that no trigger would ever fire for, because the rule that would have selected them had changed after they were stored.

The architectural ruling, stated once. There is now exactly one function that decides eligibility (evaluate_source in apps/backend/documents/eligibility_engine.py), its answer is materialized onto a column, and every other consumer — backend querysets, agent SQL, operator screens, cost gates — reads that column. A rule change is therefore a sweep (re-run the function over a scope of rows), never a re-scrape and never a re-derivation. Hold on to this: it explains at least half the code below.

The entities

All of them live in apps/backend/documents/models.py. Nine tables matter for this page; here they are with the one thing about each that is easy to get wrong.

Author
:35 A cafe member. Identity is member_key (Naver’s writer.memberKey), never the nickname — a rename keeps the key, and historical posts keep rendering the old nickname forever. Carries current_rank, is_banned, legacy_allowlisted, and a nickname_history list.
MemberRankPolicy

Two ideas that explain most of the design

“Collect everything, filter late”

The naive design filters at the scraper: don’t even store a 출석체크 post. This codebase does the opposite — it stores nearly everything it can read and decides afterwards. Two reasons, both practical:

  • A row is nearly free; a re-scrape is not. Storing a post costs a few kilobytes. Re-fetching 42,000 posts costs ~2.9 seconds each on the politeness timer, i.e. about 34 hours. If the filter lives in the scraper, every rule change is a 34-hour job. If it lives in a column, every rule change is a 3.5-second sweep.
  • A reason code is more useful than absence. When the operator asks “why is this post not showing up in search?”, eligibility_reasons = ["board_blocked", "rank_ineligible"] is an answer. A post that was never stored is not.

Reason codes are a set, not a scalar

This is the single most consequential small decision in the subsystem. A 출석체크 post written by a 참여회원 is genuinely both board-blocked and rank-ineligible. Collapsing that to one “primary reason” would make the diagnostic lie, and it would make the pipeline queues wrong. So evaluate_source never short-circuits: every gate runs, every failure is recorded, and the result is sorted(set(...)).

The payoff is that different consumers ask different questions of the same stamp:

Retrieval and the corpus counts ask for the boolean: reference_eligible = TRUE. Is this post quotable right now?
The enrichment pipeline asks about the codes: is eligibility_reasons a subset of {unenriched, enrichment_failed}? That means “the only thing wrong with this post is that nobody has enriched it yet” — i.e. spending money on it will actually help. Asking for reference_eligible here would be circular and would never converge: unenriched posts are by definition not eligible.
The operator’s diagnostic screen asks for the whole set, plus the timestamp of the last change.

Two gates, two mechanisms — and why they must not be merged

Almost everything the engine decides is a stored answer, which means it lags a rule change by one sweep, and the sweep runs on Celery, so it is asynchronous. Two gates deliberately break that pattern in opposite directions:

GateMechanismWhy
brand_filtered
(brand/branch toggle)		 Live SQL at read time. The stamped code is observational only — it is in RETRIEVAL_ONLY_REASON_CODES, so it never enters the blocking set and never flips reference_eligible. The real filter is a LEFT JOIN predicate on the toggle tables, spliced into every retrieval statement in the agent. A brand toggle must be instantly reversible with no sweep and no re-index. An un-swept row is therefore never wrongly filtered — only described stalely on the operator’s screen.
manual_excluded
(per-post kill switch)		 Synchronous write. A blocking code, written and re-judged in the same transaction as the operator’s click. It has no live-SQL twin, and “a kill switch that takes effect after the next Celery hop is not a kill switch.” One document is one SELECT plus at most one UPDATE — cheaper than the dispatch would have been.

Everything else — a board toggle, an author ban, a rank rule, the policy singleton, a post moving between boards — is the ordinary asynchronous path: change the rule, enqueue a scoped sweep, and the answer lands a moment later. Add up to 300 more seconds for the agent’s ranked retrieval cache (explainer #7) and you have the honest end-to-end latency of an operator toggle.

Where the money goes

Two Gemini passes run per post, and image alt is by far the more expensive one because a post can carry a hundred images. It also runs first, which is why the cost gate had to be installed at both stages rather than just at the text stage: on one measured run the missing image-alt gate paid for 5,890 posts that the very next stage would refuse — about ₩3,355 and 4.2 hours of wall clock, spent on 출석체크 posts and banned authors.

The cost gate is the eligibility engine wearing a different hat. enrichment_blocking_reasons(source) asks: “would this post be eligible once enriched?” — i.e. every blocking code except the enrichment codes themselves. Non-empty means “do not spend money here”. It is the same evaluate_source call with two codes filtered out, which is exactly the point: there is still only one definition.

Code

1. Collecting — the scraper

apps/backend/ingestion/scraper.py is 1,879 lines, and you should not read most of them. Its shape is what matters: a context manager that owns a Playwright browser, a persisted login session, two interchangeable transports, a politeness timer and a circuit breaker.

Three endpoints, and each has exactly one job. The article endpoint returns one post’s contentHtml plus its metadata. The board-list endpoint returns 50 article stubs per page — and crucially, each stub already carries menuId, memberKey, memberLevelName and writeDateTimestamp, so boards, authors and ranks can be resolved before a single article fetch is spent. The side-menu endpoint is the only authoritative source of board names; the listing envelope carries none. menu_id = 0 means “the whole cafe” and, importantly, includes boards whose collection is switched off.

Two transports

The scraper can read a post two ways, and the choice is a setting (SCRAPER_TRANSPORT, default "api"):

API_TRANSPORT (default)DOM_TRANSPORT
How A Playwright APIRequestContext issues one JSON GET, then the returned contentHtml is injected into a reused, network-blocked local page and walked by the unchanged extraction script. A real page load of the cafe article, then the same extraction script against the live DOM.
Cost0.22–0.32 s, one HTTP request. 2–4 s, a page load plus dozens of subresources.
Used whenAlways, first. Three cases: the operator pins SCRAPER_TRANSPORT=dom; the API answers with a malformed envelope or no contentHtml (measured at ~1.7% of one batch, concentrated in the pre-2019 id region); or API latest-post discovery throws.

The reason this swap was safe is worth internalising as a general lesson: only the transport changed, not the extraction. The same JavaScript walks the same .se-main-container markup either way — byte-identical extraction was proven on five posts before the change landed. The fallback is per-post, not per-run: extract_post (:742) tries the API, and on any exception that is not a circuit-breaker trip logs a warning, records a systemic failure, and falls through to _extract_post_dom.

The session, the timer and the breaker

Naver requires a logged-in member to read the cafe, so the scraper logs in with a real browser and persists the resulting cookie jar to SCRAPER_STORAGE_STATE_PATH — in the container, a mounted scraper_state volume. On the next run it restores that state instead of logging in again. Three failure behaviours around it are deliberate:

  • Pacing, not transport, sets the wall clock. _pace() (:803) sleeps before every live request: SCRAPER_REQUEST_DELAY_SECONDS (2.0) plus up to SCRAPER_REQUEST_JITTER_SECONDS (1.0) of jitter → ~2.9 s measured per post. The API made the fetch 10× faster and the run barely faster, on purpose.
  • Three consecutive 401s trigger exactly one re-login. UNAUTHORIZED_REAUTH_STREAK = 3. A single 401 is ordinary data (a rank-gated post the session may not read) and becomes the per-post outcome restricted. A streak that survives a fresh login is a soft-block signature and is counted as systemic.
  • A circuit breaker, counting only systemic failures. After SCRAPER_CONSECUTIVE_FAILURE_LIMIT (5) consecutive systemic failures — transport errors, malformed envelopes, extraction failures, a continued 401 streak — ScraperCircuitOpenError is raised, which fails the whole job with an alert rather than burning thousands of requests against a block. Per-post outcomes never count toward it.

One deliberate exception to a hard rule. The scraper’s contract is “outcomes cross this boundary as sentinel dicts (skip_reason), never as exceptions” — deleted_or_missing, restricted, parse_error are all just dictionaries. ScraperCircuitOpenError is the single exception, and its docstring says why: it must stop the job, not the post, so the untouched items stay recoverable by an ordinary retry.

Enumeration: what is the run even supposed to fetch?

enumerate_collectable_post_ids (enumeration.py:97) answers that for the full-collection preset by page-walking the listings of every collect_enabled board. The alternative — walking ids 1..latest — was measured and rejected: it would spend ~14,000 article fetches on ids that never existed and ~23,600 more on boards the operator excluded, while the listings hand back the same id set in ~370 requests. Page size is ENUMERATION_PAGE_SIZE = 50 (the cafe’s own default) and there is a MAX_PAGES_PER_BOARD = 2000 backstop that only ever trips on a non-terminating endpoint.

The side harvest is nearly free and turns out to be the whole point:

Every listing item carries the author’s member key and current rank, so the whole active membership lands on Author rows before the run fetches a single article. That is what turned 4,009 documents stamped author_unknown into decided ones. Per-author sweeps are suppressed during the walk (resolve_author_entity(record, enqueue_sweep=False)) and one full-corpus sweep is enqueued at the end — thousands of scoped sweeps would say the same thing far more expensively.

A partially enumerated set is corruption, not degradation. The enumerated id set is the run’s scope, so any board error aborts the entire pass. There is exactly one carve-out (and it is narrow by construction): if the caller passes the BoardSyncOutcome of the board sync that ran moments earlier, then a board whose listing fails and which that snapshot shows is gone from the live menu is a deleted board, not a failing one — it is switched off, alerted, and contributes zero ids. Absence is read from the snapshot only, never from the exception, and never by re-calling the endpoint.

Two more listing-only walks

Both exist because the cafe changes underneath us, and both cost zero article fetches and zero LLM calls:

  • sync_boards (board_sync.py:127) fetches the live side menu and diffs it against the Board table, applying three operator-confirmed postures: added → create with both switches ON and alert (so a noise board gets switched off quickly); removed → collect_enabled=False and alert, leaving posts and their retrievability untouched (only index_enabled feeds board_blocked, so no sweep is needed); surviving → refresh name/type/hidden, never the operator switches. Alerts here are sent unthrottled — a board appearing or disappearing is rare and consequential, and the default 6-hour window would swallow the second of two adds.
  • walk_membership (membership_walk.py:221) pages menuId=0 — the whole cafe, ~840 pages, ~40 minutes — to answer “which board does each post live in now?” A post the operator moves between boards changes nothing about its content, yet before this walk the only way to notice was a full re-scrape: 42k article fetches and an LLM bill. Three wire-format rules are pinned by a live probe and none is optional: pageSize stays 50 (100 is accepted and silently mis-served, returning 15 items); the menuId=0 envelope has no hasNext key, so the page budget comes from total_article_count with empty items as the real terminator; and an all-duplicate page is normal, not the end, because the listing is TIME-sorted and shifts under the walk as members post.

The walk repairs by intersection only — a post it observes with no DocumentSource row is simply not this machine’s business, and rows are never created here. A departure (a stored row nobody observed) is reported, never applied: nulling the FK would destroy the last record of where the post lived. And because a board change flips board_blocked, the moved posts get one scoped sweep — carefully guarded:

moved_post_ids = outcome.moved_post_ids
if moved_post_ids and not dry_run:
    # Guarded: `enqueue_eligibility_sweep(post_ids=[])` drops the scope
    # and sweeps the whole corpus.
    enqueue_eligibility_sweep(post_ids=moved_post_ids)

That comment is a real trap in this codebase, and it recurs: enqueue_eligibility_sweep builds its kwargs with if post_ids:, so an empty list is falsy, the scope key is never added, and the sweep silently widens to all 20,000+ rows.

Entity resolution

entity_resolution.py is small and holds the two identity rules the rest of the system depends on.

resolve_board (:44): identity is menu.id. An unseen board is created with both switches ON; an existing row only ever gets its display name refreshed, because operator switches are never overwritten by a scrape. A record with no menu id (the DOM fallback) leaves the FK exactly as it is rather than nulling it.

resolve_author_entity (:70) is a three-step ladder: a known member_key wins outright; an unknown key first tries to claim a key-less legacy row carrying the same nickname (that is how the backfilled rows acquire identity); only then is a new Author created. Nickname-only records (the DOM fallback again) resolve by nickname alone. A nickname change appends to nickname_history rather than overwriting. And the last few lines are the ones that matter for eligibility:

rank_changed = bool(rank) and author.current_rank != rank
...
if rank_changed and enqueue_sweep:
    # Rank renders as the member's *current* rank on every post they ever
    # wrote, so a rank change re-decides eligibility for their whole back
    # catalogue -- not just the post being scraped right now.
    enqueue_eligibility_sweep(author_ids=[author.pk])

This is the sweep trigger that fires from the middle of a scrape. A member promoted from 참여회원 to 파트너회원 makes hundreds of their old posts newly quotable, and the system learns that the moment it re-reads any one of their posts.

The rank-spelling trap. The two endpoints spell staff ranks differently: the article API says 카페매니저, the board listing says 매니저; the article API says 카페스탭, the listing says 카페 스탭. normalize_member_rank (documents/eligibility.py) removes whitespace outright and then maps the two listing-only aliases onto the canonical spellings, and build_entity_record_from_listing_item applies it before the resolver ever sees the record — writing a listing spelling straight into Author.current_rank would silently fail rank gating for the entire cafe staff. Unknown ranks pass through unchanged so a new cafe rank is visible in the data rather than silently rewritten.

2. Persisting — a job runs

All actual work is an IngestionJob with a list of IngestionJobItems, one per post. The job carries a type, a status, a JSON parameters blob, and an optional FK to whichever run owns it; the item carries a post id, a status, and a JSON payload that is the honest record of what happened to that one post.

IngestionJob.JobType  = scheduled_incremental | range_rescan
                      | image_alt_enrichment  | text_enrichment | index_handoff
IngestionJob.Status   = pending | queued | running
                      | succeeded | partial | failed | cancelled
IngestionJobItem.Status = pending | queued | running
                      | succeeded | skipped | failed | cancelled

Note partial. _finalize_job_status counts the terminal items: any FAILED item with at least one non-failed sibling makes the job partial; all failures make it failed; zero items counts as succeeded. That three-way split is what lets a run distinguish “retry these eleven posts” from “something is broken”.

The call chain for a scrape job is short and worth memorising:

1execute_ingestion_job(job_id) (execution.py:61) — marks the job RUNNING, branches on job_type, and wraps everything in a try/except that alerts first and marks the job failed second. The comment says why: everything below touches the ORM, which is exactly what is broken when a leaked Playwright event loop has poisoned this worker child.
2_execute_scrape_job(job_id) (:99) — opens one build_naver_cafe_scraper() context for the whole job (one browser, one login) and, for a scheduled incremental with no items yet, discovers the latest post id and materialises the items.
3_run_job_items(job_id, processor) (:154) — iterates item ids in (post_id, id) order, checking the cancel flag before each item so a cancel takes effect within one post.
4_process_scrape_job_item (:166) — skips already-terminal items, honours the force_update parameter, calls scraper.extract_post(post_id), then hands the record to the persist step.
5_apply_scrape_record (:528) — a two-line dispatcher: a record carrying skip_reason goes to _apply_skip_record, everything else to _apply_success_record (:539), which is where the writing happens.

        source.refresh_from_db()
    DocumentSourceStatus.objects.update_or_create(
        post_id=post_id,
        defaults={"status": DocumentSourceStatus.Status.SAVED, "error_message": ""},
    )

# Scrape-persist is the other natural per-document evaluation moment: board,
# author entity, rank, date and body all land here. Runs inside the same
# request but outside the transaction above so a sweep failure can never
# roll back a successfully scraped post.
evaluate_and_store(source)

Two protections are encoded there, and both are about not re-spending money.

(a) Entity resolution is deliberately outside the change comparison. resolve_author_entity and resolve_board run before the transaction and put their results into defaults, but _source_extraction_changed (:922) compares only content-bearing fields: title, author string, timestamps, url, raw_text, the alt-stripped replacement text, canonicalised image urls, and content_segments. The entity FKs, the rank and category are explicitly excluded. The inline comment spells out the stake: category is the board’s display name, “the cafe’s shelf label, not the post’s content”, so a board rename or a post moved between boards would otherwise blank every affected post’s enrichment and re-buy it. The field is still stored — only the change detector stops looking at it.

(b) Generated alt text survives a re-scrape. A fresh scrape returns bare [IMAGE_1] placeholders; the stored row may already have [IMAGE_1:주방 설비 견적서 사진], which cost a vision call. _merge_preserved_generated_alts re-attaches each generated_alt by URL and _apply_preserved_generated_alts rewrites the placeholders back into the fresh text. And for the change comparison, _strip_generated_alt_markup reduces both sides to bare [IMAGE_n] using that same _PLACEHOLDER_WITH_ALT_RE — so the alt text we just re-attached cannot itself register as “the content changed”. Three uses of one regex, all pulling in the same direction.

Date parsing is transport-shaped. _resolve_published_at prefers the API’s writeDate epoch-ms integer (so the API path never parses a string at all) and falls back to the DOM path’s %Y.%m.%d. %H:%M parser, whose format has been unchanged since 2018. Both land in Asia/Seoul. A post whose date resolves to None is not dropped — it is stored and stamped date_unparsed, per “collect everything, filter late”.

Cancelling

job_control.py holds the status vocabulary as named sets — CANCELLABLE_JOB_STATUSES (:21) through NON_TERMINAL_ITEM_STATUSES (:40) — and cancel_job_locally (:97) is two bulk .update() calls: the job to CANCELLED, and every non-terminal item to CANCELLED. Local, because the provider-side batch (below) has to be cancelled separately and asynchronously.

3. Enriching — two Gemini passes, two execution modes

Pass A: image alt text

ImageAltTextEnricher (image_alt.py:119) walks a post’s image_urls, asks Gemini to describe each picture in one factual Korean line, and rewrites [IMAGE_n] into [IMAGE_n:<description>] in text_with_image_replacement. Four details are load-bearing:

  • The per-post cap is a knob, not a rule. get_max_alt_images_per_post() (:36) reads IMAGE_ALT_MAX_IMAGES_PER_POST, default 100, where 0 means unlimited. It is a guard rail against a pathological post (the observed maximum is 202 images on one post), not a lever: exactly 1 of 6,942 stored posts exceeded it. Image URLs were never capped — this bounds alt-text spend only.
  • A per-job URL cache. The enricher holds self.cache: dict[str, str], seeded from any generated_alt already on the row, so the same image URL appearing in ten posts of one job costs one vision call.
  • The sentinel. When an image cannot be read, the alt becomes exactly 이미지 내용 식별 어려움 (“image content hard to identify”) — and the prompt instructs the model to answer with that same string when the picture is illegible, so the machine failure and the model’s own “I can’t tell” produce identical text.
  • The download-failure taxonomy is three-way, and the middle case is subtle. A definitive unavailability (404/410/empty/bad content type) applies the sentinel and caches it. A non-definitive URLError — a dead host, DNS gone, or a plain timeout, all indistinguishable at this layer — applies the same sentinel without caching, because the cache lives for a whole 500-post job and a transient blip must not permanently stamp every other post sharing that URL. An unknown exception still fails the image.

Alt text is also sanitised before it is ever written: sanitize_alt_text (:370) trims quotes, collapses whitespace and — the important bit — rewrites [ and ] into parentheses. A model that emitted a bracket would otherwise inject a fake placeholder into the body text and corrupt the very convention being written.

Pass B: summary and keywords

text_enrichment.py asks for a structured object:

class _GeminiTextEnrichmentSchema(BaseModel):        # :68
    summary:  str       = Field(description="한국어 본문 요약. 사실 중심, 지정된 길이 이내.")
    keywords: list[str] = Field(description="본문 핵심 키워드 목록. 최대 10개.")

One knob, TEXT_ENRICHMENT_SUMMARY_MAX_CHARS (default 500), does two jobs at once — it is the summary length cap and the short-post skip threshold, which gives the stage two paths:

  • Body ≤ 500 chars → the normalised body is the summary, verbatim, and the model call narrows to a keywords-only schema (_GeminiKeywordsSchema). Item payload records summary_mode: "body".
  • Body > 500 chars → a proportional target, stated in the prompt: resolve_summary_target_chars = clamp(round(0.25 × body), 150, 500). Longer post, longer summary. Payload records summary_mode: "generated".

Worked values for the generated path (computed by running the clamp): a 800-character body asks for 200, 2,000 asks for 500, and everything from ~2,000 characters upward also asks for 500 — so in practice the “proportional” band is only really proportional between about 600 and 2,000 characters, and the cap takes over above that.

And MAX_KEYWORDS = 10, enforced in Python by normalize_string_list(..., max_items=MAX_KEYWORDS) rather than trusted from the model.

This is where explainer #7’s lexical arm actually comes from. Retrieval’s “keyword” arm is not full-text search: no tsvector, no ILIKE, no trigram. It is exact set equality between the query’s tokens and the indexed keyword_terms array — which is this Gemini call’s keywords output, casefolded and whitespace-collapsed by normalize_keyword_terms. So lexical recall is entirely a function of the words this summariser happened to choose. If the model writes 비용, a user asking about 비용 can match lexically; if it writes 초기비용 instead, that query has only the vector arm left. (And since query planning does not strip Korean particles, a user typing 비용은 misses 비용 anyway — see #7.)

One invariant guards the whole thing, enforced in build_body_summary_result: summary and keywords must both be non-empty on success, or the function raises. An empty either would stamp unenriched and silently drop the post out of retrieval, so the short path refuses to pretend it succeeded.

Where the model ids come from — at run time, every time

Both enrichers resolve their model the same way, and it is not a constant:

model_name, thinking_level = resolve_role_config(
    ROLE_TEXT_ENRICHMENT,                        # or ROLE_IMAGE_ALT
    settings_attr="GEMINI_TEXT_ENRICHMENT_MODEL",
    default_model=DEFAULT_TEXT_ENRICHMENT_MODEL, # "gemini-3.1-flash-lite"
)

resolve_role_config (operators/llm_runtime.py) reads one row from the operator’s LLMRoleConfig table and falls back DB → Django setting → DEFAULT_* constant. Unlike the agent’s equivalent it keeps no cache and no TTL, deliberately: each builder is called once per Celery job, so a single ORM read already gives per-job liveness and a cache would only add staleness. A DatabaseError (including the unapplied-migration case) is logged once and treated as an absent row — a config read must never fail a Celery task. There is no per-role thinking-level env var, so an unset or out-of-vocabulary stored level means “send no thinking kwarg at all”.

Practical consequence for anyone deploying this: the operator can change the enrichment model from a web form with no redeploy — but the Celery workers must be running the current image, or those three roles silently keep whatever they were built with.

Direct vs batch, and the actual decision rule

Both enrichment stages have two implementations. Direct means one synchronous LLM call per post inside the job loop. Batch means the Gemini Batch API: you upload a JSONL file where each line is one request, the provider runs it asynchronously with no latency guarantee, and you download a JSONL of results later. It exists for exactly one reason — cost (batch inference is materially cheaper than synchronous inference) — and it is the right trade for a nightly job that nobody is waiting on.

resolve_enrichment_execution_mode (job_control.py:57) is the rule:

explicit_mode = parameters.get("enrichment_execution_mode")
if explicit_mode == DIRECT: return DIRECT
if explicit_mode == BATCH:  return BATCH
if parameters.get("trigger_mode") == AUTOMATIC_SCHEDULE_TRIGGER_MODE: return BATCH
return BATCH                                  # the fall-through default

Read against the callers, that resolves to a simple picture:

The batch path, end to end

Four functions in batch_execution.py, plus two tables:

1submit_provider_enrichment_job (:118) resolves the model once for the whole job, builds one PreparedProviderRequest per item (running all the same skip and cost gates the direct path runs), chunks them by MAX_BATCH_REQUESTS = 250 and MAX_BATCH_BYTES = 10 MiB, uploads each chunk as JSONL, creates the provider batch, and dispatches the first poll.
2poll_provider_enrichment_job (:173) re-asks the provider for each non-terminal batch, and re-dispatches itself with countdown=BATCH_POLL_INTERVAL_SECONDS (30) until every batch is terminal. Terminal means one of five states: SUCCEEDED, FAILED, CANCELLED, EXPIRED, PARTIALLY_SUCCEEDED.
3_capture_terminal_provider_batch (:886) downloads the output file and walks it line by line, matching each line back to a request by request_key. It is written defensively: invalid JSON lines are skipped, unknown or duplicate keys are ignored, a line carrying error stores an error, a line with no text output stores an error — and, crucially, any request key that never appeared in the output at all is explicitly stored as an error rather than left hanging.
4_finalize_ready_provider_items (:999) is the apply step, and its guard is the whole idempotency story: an item is finalised only when every one of its provider requests has a result or an error, and each request is stamped applied_at exactly once.

IngestionProviderBatch (models.py:842) is one uploaded file → one provider job, carrying external_batch_name, state, output_file_name and the model used. IngestionProviderRequest (:956) is the mapping row: one per (batch line ↔ job item), carrying request_key, the raw provider_result / provider_error snapshots and applied_at. Together they are why a worker can die mid-batch and the next poll picks up exactly where it left off.

The seam: the moment a post becomes enriched

Both paths converge on the same four lines — here in the direct path (execution.py:493-506), mirrored verbatim in the batch finaliser (batch_execution.py:1094):

DocumentSource.objects.filter(pk=source.pk).update(
    summary=enrichment.summary, keywords=enrichment.keywords,
)
# Enrichment is an eligibility input, and `.update()` above bypasses any
# model-level hook, so re-evaluate here: this is what turns a freshly
# enriched post into an index candidate.
source.refresh_from_db()
evaluate_and_store(source)
trigger_brand_match_for_post(source)

Three things happen in order and each depends on the one before. The write is a bulk .update() (fast, and it bypasses auto_now), which is precisely why the re-evaluation must be explicit. evaluate_and_store clears unenriched and, if nothing else was blocking, flips reference_eligible to TRUE — the post is now an index candidate. And trigger_brand_match_for_post can only run now, because a post with no summary is a candidate for no brand: the brand classifier reads title + summary.

The fingerprint

build_source_fingerprint(summary, keyword_terms) (fingerprints.py:36) is a sha256 over canonical JSON of exactly those two values — whitespace-collapsed summary, and keywords casefolded, collapsed and de-duplicated in order. It dedupes embedding work: if a re-enrichment produces the same summary and the same keyword set, the index layer knows there is nothing to re-embed. The agent keeps a byte-identical twin of this function in apps/agent/app/indexing/storage.py so both sides compute the same hash — explainer #9 picks that up.

4. Judging — the eligibility engine

707 lines in apps/backend/documents/eligibility_engine.py, and the centre of the whole subsystem. Its module docstring is unusually worth reading in full; the design in three parts is: a policy loaded once per sweep, a pure function per document, and an idempotent write-back.

The policy

@dataclass(frozen=True, slots=True)
class EligibilityPolicy:                       # :101
    published_on_or_after: datetime | None
    bot_min_content_length: int
    eligible_ranks: frozenset[str]

EligibilityPolicy.load() takes all three once, so every document in a sweep is judged against the same answer — a rank rule that changed halfway through a 20,000-row walk would otherwise produce an incoherent corpus. The rank set comes from rank_policy.load_eligible_ranks(), which reads the MemberRankPolicy table and falls back to the code constant ELIGIBLE_MEMBER_RANKS only when the table is entirely empty. That distinction is deliberate: turning every rank off must mean every rank is off, not “fall back to the defaults”.

evaluate_source, gate by gate

The function (:167) is one pass over nine gates, and its defining property is that it never short-circuits. Every gate runs, every failure joins a set.

1Manual override. source.manual_excluded → manual_excluded. Evaluated alongside the others rather than short-circuiting them, so a post that is both manually excluded and board-blocked keeps saying so.
2Board. board is not None and not board.index_enabled → board_blocked. A NULL board FK does not block: 301 legacy rows had drifted off the live board list and self-heal at re-scrape. Absence is not a decision.
3Author (_author_reasons). No author → author_unknown. Banned → author_banned (overrides everything). Rank in the eligible set → pass. Non-empty rank not in the set → rank_ineligible. Empty rank but legacy_allowlisted → pass (the transition rule for backfilled rows). Otherwise author_unknown.
4Brand / branch (_is_brand_filtered) → brand_filtered. Observational only — retrieval-only, never blocking. Brand-off overrides branch-on; a NULL brand never blocks.
5Source status. DELETED → deleted; anything else that is not SAVED (ERROR, or no status row at all) → restricted — the taxonomy’s name for “stored, but the source is not readable or confirmed”, which is exactly the shape of the scraper’s rank-gated 401.
6Publication date. published_at is None → date_unparsed; older than the policy date → date_before_policy. Two distinct codes because they are two distinct problems — and the live policy date is NULL, so the second never fires today.
7Length floor. Only when the floor is > 0: normalized_content_length(text_with_image_replacement) <= floor → below_length_floor. Note <=, not <. The live floor is 0, so this gate is currently off.
8Enrichment. No non-blank summary or no non-empty keyword list → unenriched.
9Nothing to enrich, ever. No summary and no body text in any of the three body fields and no images → no_body_text. Evaluated last because it is the answer to a post that would otherwise sit in unenriched forever.
blocking = {code for code in reasons if code not in RETRIEVAL_ONLY_REASON_CODES}
if not blocking:
    reasons.add(ELIGIBLE)
return EligibilityEvaluation(reference_eligible=not blocking,
                             reasons=tuple(sorted(reasons)))

no_body_text is the one code that exists to end a wait. An empty 영상 or 프리뷰 post has no text for the summariser and no image for the alt leg, so waiting can never change it. It is stamped in addition to unenriched (the codes are a set), and that is the whole mechanism: the pair {unenriched, no_body_text} is no longer a subset of {unenriched, enrichment_failed}, so the post silently drops out of the reprocess queue instead of being retried forever. It also self-heals in both directions — any body text, any summary or any image clears it at the next evaluation. And it needs no SQL twin, because it can never be a row’s only code.

The vocabulary itself lives in documents/eligibility.py — deliberately a constants-only module with no evaluation logic. Seventeen codes are defined; the engine stamps twelve; three (enrichment_failed, never_existed, blind) are reserved, because the pipeline genuinely cannot distinguish those states today and inventing them would be a lie. The operator’s aggregate screens therefore report null for those, never 0: a fake zero would read as “measured, none”, which is the one thing a coverage surface must never say.

The ₩ gate

def enrichment_blocking_reasons(source, *, policy=None) -> tuple[str, ...]:   # :270

“Would this post be eligible once enriched?” — every blocking code except unenriched and enrichment_failed. Non-empty means don’t spend. It is called at exactly the four places money is spent (direct image alt, direct text, batch image alt, batch text), and the resulting skip payload is honest about it: {"reason": "eligibility_blocked", "eligibility_reasons": [...]}.

The write-back, and why it is fingerprint-guarded

def store_evaluation(source, evaluation) -> bool:                    # :497

    unchanged = (

        and list(source.eligibility_reasons or []) == reasons

    ...
    return True

A no-op sweep writes nothing. That matters for two reasons. Mechanically, a sweep that touched 20,000 rows every time would churn updated_at across the corpus and make the operator’s “recently changed” views meaningless. Semantically — and this is the better reason — eligibility_evaluated_at means “when the answer last changed”, not “when we last looked”. The operator’s coverage tab renders it as 마지막 판정 (“last verdict”), and a verdict that has not changed has not been re-made. The third condition (eligibility_evaluated_at is not None) is what makes a never-stamped row always write once, even if its computed answer happens to match the column defaults.

The sweep

def sweep_eligibility(*, post_ids=None, author_ids=None, board_ids=None,
                      brand_ids=None, branch_ids=None, ranks=None) -> dict[str, int]:  # :545

Scopes are additive filters, not a union: passing several narrows, passing none sweeps the whole corpus. The body loads the policy once, builds a select_related("author_entity", "board", "brand", "branch") queryset, and walks it in batches of _SWEEP_BATCH_SIZE = 500 via .iterator(). Each batch pre-fetches the DocumentSourceStatus rows for its posts in one query — passing source_status= explicitly is what keeps the sweep from paying a status query per document — and applies its writes inside one transaction.atomic(). It returns {"evaluated": n, "changed": n, "eligible": n}.

Measured: a full sweep over 20,726 rows runs in 3.5 s; a rank-scoped sweep touched 1,319 documents in 0.6 s. That number is the reason the whole “materialize and sweep” design is affordable in the first place.

ranks deserves a note: a rank toggle affects every document whose author currently carries that rank, and there can be thousands. Naming the rank keeps the Celery payload one string instead of an author-id list.

Brand assignment, in one paragraph each

Automatic (documents/brand_verification.py, entry point verify_brand(brand, post_ids, ...) at :687): a per-brand Gemini prompt asking one narrow question — “이 게시글이 섬집에 관한 글인가? 그렇다면 어느 지점인가?” — over a closed world of exactly one brand plus its branches. 5. Orchestrating — runs, schedules, recovery

A job does one stage for one set of posts. A run is the campaign that strings the stages together, and there are five of them — deliberately five models rather than one with nullable columns, because their shapes genuinely differ.

Run modelWhat it is forStages
IngestionBackfillRun :11 The big one: collect the entire cafe (or the 2024+ slice). Freezes a sparse id set once and works it in batches with a checkpoint. Has a batch-boundary pause. scrape → image_alt → text_enrichment → indexing → (manual_index) → completed
IngestionAutomaticRun :173 The nightly catch-up. local_date is unique, so there is at most one per calendar day by construction. scrape → image_alt → text_enrichment → indexing → completed
IngestionManualIncrementalRun :261 The same pipeline, started by an operator on demand rather than by the clock. same five
IngestionReprocessRun :350 “Enrich whatever is still waiting” — its scope is build_enrichment_candidate_queryset(). No scrape stage at all. text_enrichment → indexing → completed
IngestionSoftResyncRun :447 Soft 재수집: board sync + membership walk + a chunk-index handoff. ~40 minutes, zero article fetches, zero LLM calls. no stage field — one pass, then handoff

Why soft resync is not a sixth backfill preset. Its own docstring answers this: the backfill model describes a staged pipeline with batch cursors, a frozen id scope and schedule-pause bookkeeping, and soft mode has none of it. Modelling it as a preset would mean carrying five nullable columns that must never be read. It also succeeds at handoff-accepted, not at chunk-run completion — a full reconciling chunk run measured 7 h 29 m against a 6-hour registry TTL, so it can never be polled to a terminal state, and holding the ingestion lock across it would wedge the cafe for hours over an idempotent agent-side pass.

The automatic-run stage machine

advance_automatic_run(run_id, triggering_job_id=None) (automatic_runs.py:122) is the whole driver, and it is a single transaction.atomic() around a select_for_update() on the run row. Every path out of it is a guard:

scrape→ job SUCCEEDED → freeze start_post_id/end_post_id from the job’s items, create the IMAGE_ALT job. Zero items → jump straight to SUCCEEDED.
image_alt→ job SUCCEEDED → create the TEXT_ENRICHMENT job over the same id range.
text_enrichment→ job SUCCEEDED → clear active_job/agent_run_id and enter indexing. From here there is no IngestionJob — the agent owns the work.
indexing→ start_automatic_run_indexing lists the pending candidates and POSTs them to the agent; poll_automatic_run_indexing re-dispatches itself every AGENT_INDEXING_POLL_INTERVAL_SECONDS = 30. No pending candidates → SUCCEEDED with no agent call at all.
completed status SUCCEEDED. Terminal, and every entry point returns immediately once the run is SUCCEEDED.
needs_attention reachable from any stage when the linked job ends non-successfully and the retry ladder is exhausted. Fires an alert on commit.

The retry ladder for the two enrichment stages (_queue_automatic_retry_locked) is the interesting part, because it is where batch mode earns its keep and then gives up:

  1. Only retryable failures qualify. If any failed item carries a non-retryable reason (source_missing, source_not_saved, no_images, content_too_short), no retry is queued at all — those are facts about the post, not transient errors.
  2. Retry the same mode over just the failed post ids, up to SAME_MODE_RETRY_LIMIT = 3 attempts.
  3. Then fall back once to direct_mode=True — if the Gemini Batch API is what is unhealthy, synchronous calls may still work.
  4. Otherwise: needs_attention + alert.

Indexing has its own smaller ladder: INDEXING_RETRY_LIMIT = 3 attempts, INDEXING_RETRY_DELAY_SECONDS = 300 apart.

The schedule

evaluate_scheduled_incremental_schedule() (schedules.py:83) is what Celery beat calls. It takes a select_for_update() on the singleton IngestionSchedule row and then walks a ladder of reasons not to run, each returning a named status the operator console renders:

disabled                          -> the schedule is switched off
already_processed                 -> last_processed_local_date == today (local)
not_due                           -> local_now < today's due time
skipped_automatic_run_active      -> a run is still going
skipped_automatic_run_needs_attention
skipped_soft_resync_run_active
... otherwise: create today's IngestionAutomaticRun and dispatch it

Everything is computed in the schedule’s own IANA timezone and converted to UTC at the edges, so “03:00 daily” means 03:00 in Seoul across DST boundaries elsewhere. compute_next_run_at (:55) is the read-only twin that answers “when next?” for the console.

Two self-healing paths run before the blocker checks, and both alert when they fire, because a recovery path firing means an earlier failure went silent:

  • Stale blockers. A scheduled_incremental job stuck non-terminal for more than STALE_SCHEDULED_SCRAPE_JOB_AFTER = 24 h is force-failed — otherwise one dead worker would block the daily schedule forever.
  • Terminal-failed automatic runs whose scrape job failed with zero items are cleared.

Worker-boot recovery

recover_startup_state() (recovery.py:85) runs when a worker starts, and re-dispatches whatever was in flight when the last one died: provider-batch polls for batch jobs that have live batches, initialization for INITIALIZING backfills, advances for runs whose active job has since gone terminal, and indexing starts/polls. It is the general “dispatch-after-commit means a lost task is possible, so re-derive from the database” pattern, which explainer #16 owns properly.

One rule in it is worth quoting because it is a design principle in miniature:

#: Worker-boot recovery must never touch a paused run. Every queryset below is
#: a positive status allow-list that already leaves `paused` out, but the
#: exclusion is spelled out anyway: a redeploy silently un-pausing an
#: operator-stopped run would be the worst failure this module can have, and a
#: future widening of one of those allow-lists must not be able to cause it by
#: accident.
_RECOVERY_EXCLUDED_RUN_STATUSES = {IngestionBackfillRun.Status.PAUSED}

A redundant guard, added on purpose, with the reason written next to it. The soft-resync set (_SOFT_RESYNC_RECOVERY_EXCLUDED_STATUSES) does the same thing for the same reason — re-touching a finished or judged run would mean re-firing a 40-minute cafe sweep behind the operator’s back.

Where this page stops

The last thing a run does with a post is hand it to the agent:

                              trigger="automatic_schedule",
                              manual_incremental_run_id=None):
    payload = {"post_ids": post_ids, "trigger": trigger,
               "bot_min_content_length": get_bot_min_content_length()}
    ...
    response = _request_agent_indexing(
        method="POST", path="/agent-api/indexing/runs", payload=payload)

That is ingestion/agent_indexing.py, a plain urllib client authenticating with the static X-Agent-Service-Token header (there is no user to impersonate here — see explainer #2 for the two shared secrets). start_automatic_run_indexing calls it; poll_automatic_run_indexing polls GET /agent-api/indexing/runs/<id> every 30 s. Its siblings are ingestion/index_handoff.py (the fingerprint-guarded ingested write-back) and ingestion/agent_chunk_indexing.py.

Everything on the other side of that POST — chunking, embeddings, agent.document_index_artifacts, agent.document_chunk_artifacts, the halfvec(3072) HNSW indexes, and how keyword_terms physically arrives in the table that explainer #7’s lexical arm queries — is explainer #9.

The one-sentence version of this page. A paced browser session turns a Naver cafe into DocumentSource rows; two Gemini passes turn those rows into a summary, keywords and described images; and one function — evaluate_source — turns all of that into a set of reason codes and a single boolean that the entire rest of the system, in both apps, simply reads.

Quiz

1. A post is currently reference_eligible = TRUE. The operator turns off the index_enabled switch on its board. Which single function decides that the post is now blocked, and what does every other consumer — the agent’s retrieval SQL, the operator counts, the enrichment cost gate — actually read?

One definition, materialized. The board toggle enqueues a scoped sweep_eligibility(board_ids=[...]); the sweep re-runs evaluate_source and stamps reference_eligible + eligibility_reasons. Everything else reads the stamp. The live-SQL treatment is the deliberate exception for brand/branch only.

2. Why does build_enrichment_candidate_queryset() select on the reason codes (eligibility_reasons ⊆ {unenriched, enrichment_failed}) instead of simply asking for reference_eligible = TRUE rows that lack a summary?

The engine’s own docstring makes both points. Circularity is the first; the second is the cost argument — a post carrying {board_blocked, rank_ineligible, unenriched} is not a candidate, because enriching it would change nothing.

3. The operator toggles a cafe rank (say 코어회원) from citable to not-citable in the authors tab. What happens, and roughly how long until search stops returning those members’ posts?

Rank is a stored gate, not a live one — and the sweep is deliberately asynchronous so the operator’s request returns immediately. Every operator count is “as of the last sweep”, plus up to 300 s of retrieval cache.

4. Explainer #7 established that the lexical retrieval arm is exact set equality against an indexed keyword_terms array. Which output of the ingestion pipeline is that array, and what follows for recall?

There is no tsvector, no stemming and no trigram anywhere in the path, so an indexed keyword either matches a query token exactly or contributes nothing. A word the summariser did not pick is invisible to the lexical arm, and only the vector arm can rescue it.

5. Under what circumstances does the scraper actually use the DOM_TRANSPORT Playwright page-load path?

extract_post tries _extract_post_api first and, on any exception that is not ScraperCircuitOpenError, logs a warning, records a systemic failure and falls through to _extract_post_dom for that one post. A 401 is the opposite case: it is per-post data and becomes the restricted skip outcome.
