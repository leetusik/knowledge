Background — what a “content” is in changple5

In this product, a content is one published 미라클 article. Concretely, it is a long HTML document with photographs — a real 창업 case study: what the shop was, what it cost, what went wrong — that a user reads on the site at /content/<id>. It usually carries a thumbnail, and it may carry a 총 비용 표 (a registered total-cost table, priced line by line, whose numbers are masked for non-paying readers).

A content is not just a page, though. It shows up in three different places in the product, and that is why it has so much machinery behind it:

  • You read it. The catalog lists it, the reader renders its body, its images are downscaled and re-encoded on the way out.
  • You attach it to a chat turn. The chat composer lets a user pick contents as 선택 콘텐츠 (“selected content”), and their plain text is injected into that turn’s prompt. That path was described from the agent side in #4 and #5; this page shows where the text comes from.
  • Retrieval can cite it. Published contents are the agent’s second corpus: chunked, embedded, and searched alongside the naver cafe posts. #7 covered the read side and #9 covered the chunk pipeline itself.
Jargon, defined once

Corpus — the body of documents a search system can retrieve from. changple5 has two: the scraped naver cafe posts, and the published contents. Chunk — a slice of a document (a few hundred to ~1,400 characters) that gets its own embedding, so retrieval can point at a passage rather than a whole article. Derivative — a re-encoded copy of an image (here: WebP, optionally downscaled) generated and cached beside the original. Seam — in this codebase, a single function every caller must route through so that one behaviour can be attached in one place.

Two populations, one table

Every content lives in one Postgres row of backend.content_notioncontent (Django model NotionContent), but the rows arrive by two very different roads:

  1. Legacy Notion exports. The original 미라클 articles were written in Notion and exported as ZIP files: one HTML document plus an image folder. An operator uploads the ZIP and the backend unpacks it into MEDIA_ROOT/html_content/<id>/. The model name NotionContent is a fossil of exactly this — the table has long since stopped being “content from Notion”.
  2. Agent-written drafts. Since P30 (v1) and P54 (v2), an operator can have the content agent write an article from KakaoTalk transcripts and corpus material, then publish it — which materializes the same kind of HTML tree under the same path and creates the same kind of row. Explainers #13 #14 #15 cover that agent; they are not published yet.

The reason this matters for this page: the library deliberately does not care which road a row came from. Publishing, delivery, chunk indexing, media derivatives and the cost table all work off “there is a row and there are files on disk”. This page stops exactly at the boundary the phase drew for it: a content row exists and is (un)published. How a draft gets written is the next three explainers’ job.

Intuition — a row, a folder, and one switch

If you keep three ideas in your head, the rest of this page is detail.

Idea 1: the row is the index card; the folder is the article

A content is stored in two places at once, and they have very different properties. Postgres holds the facts — title, description, publish state, and a set of materialized numbers about the document. The filesystem holds the document — one HTML file plus every image, under MEDIA_ROOT/html_content/<id>/.

Several of the columns on the left are materialized derivations of the document on the right: image_count, local_image_count, asset_bytes, has_body, has_canonical_header, and above all extracted_text — the whole article flattened to plain text. They are stored rather than computed on demand for two reasons. First, the reader needs to decide how to render before downloading the body. Second, and more fundamentally: the agent’s chunk index computes character offsets (char_start/char_end) into that text, and an offset is only meaningful if both sides agree, byte for byte, on which string it indexes. A derivation both sides recompute independently would drift; a stored string cannot.

Idea 2: visibility is one nullable timestamp, changed through one function

There is no is_published boolean. Visibility is published_at: NULL means draft, a timestamp means published (and says when). The timestamp form is not decoration — it reads naturally in the SQL the agent splices into its own queries: published_at IS NOT NULL.

Every transition goes through services.set_content_publish_state. That is not a style preference, it is load-bearing: an automatic index/de-index has to hang somewhere, and this codebase deliberately did not hang it on a Django signal. If you have one function, you can attach one behaviour and be sure it fires. If you have three call sites writing the column directly, you have three chances to forget — and forgetting was a real production incident (P53.F11: publishing extracted the text but nobody ever embedded it, so the article was live and unsearchable).

Idea 3: the index lags; the query does not

This is the single most useful thing to understand about the content corpus, and it is the reason the publish trigger is allowed to be best-effort.

When you publish, a background chain eventually adds the content’s chunks to agent.content_chunk_artifacts. That chain can be slow, retried, or (in the worst case) lost. But the retrieval SQL does not trust the index to be a gate. It re-states the visibility predicate in its own WHERE clause — html_path <> '' AND has_body AND published_at IS NOT NULL — joining back to the backend row over the one-way read bridge from #2.

The consequence, stated plainly

Unpublishing is instant. Publishing is eventual. The moment published_at goes NULL, no query can return that content, whether or not its chunks are still sitting in the index. The moment it becomes a timestamp, the content is readable on the site immediately — but it becomes citable only once the chunks land. That asymmetry is exactly the right one: the failure mode of a lagging index is “the AI has not learned about this article yet”, never “the AI is quoting something we took down”.

Because of that, the trigger module can be stateless: no backend run table, no reconciliation bookkeeping, just a pair of Celery tasks carrying their own attempt counters, plus a manual catch-up run that heals anything lost. Postgres stays the source of truth, and the recovery story is “re-run the catch-up”.

Code — walking the library

Five stops: the models, getting content in, the publish seam, reading content, and the two side domains (cost tables and the Notion mirror). Every path below is relative to the repository root; line numbers are as of 2026-08-26.

1. The models — apps/backend/content/models.py

The file is 1,120 lines and holds two domains. Lines 86–700 are the library (ours); lines 704–1120 are the v1 content agent’s draft models (ContentDraftSettings, ContentDraftJob, ContentDraftVersion, ContentDraftMessage, ContentDraftAttachment, ContentDraftDecision) — explainer #15’s subject. The v2 agent lives in its own package, content/agent_jobs/, and is only imported at the top of this file so Django registers its models under the same app label; that is explainers #13 and #14.

The queryset is the visibility policy (lines 115–200)

Read these four methods and you know every rule about who sees what:

class NotionContentQuerySet(models.QuerySet["NotionContent"]):
    def with_stored_html(self):     # the FILE predicate only
        return self.exclude(html_path="")

    def published(self):
        return self.filter(published_at__isnull=False)

    def drafts(self):
        return self.filter(published_at__isnull=True)

    def readable(self):             # the PUBLIC-VISIBILITY gate (P59.S1)
        return self.with_stored_html().published()

    def catalog(self):              # readable, minus the pinned rail
        return self.readable().filter(is_preferred=False)

    def preferred(self):            # the pinned rail itself
        return self.readable().filter(is_preferred=True)

The distinction between with_stored_html() and readable() is the one worth internalising. Maintenance jobs — weight backfill, media-derivative warming, remote-image localisation, the content agent’s reference-profile reader — use the file predicate, because a draft has real files and there is no reason to make a publish wait for a re-encode. Every public surface uses readable(). Operator surfaces deliberately use neither: an operator must be able to see a draft, which is why the operator lookup mixin does a plain filter(pk=…) (views.py:263–290).

There is no “unlisted” state

Two flags, not three states. published_at decides visible or not; is_preferred decides which rail a visible content appears on (the pinned /preferred list versus the paginated /catalog). A content is never “published but hidden from the catalog”: catalog() and preferred() partition readable() exactly, so every published content is in precisely one of them.

NotionContent.save() is a file pipeline, not a row write (lines 320–350)

This is the fact that explains a surprising amount of the rest of the codebase. Saving a content row does far more than write columns:

def save(self, *args, **kwargs):
    had_uploaded_zip = bool(self.zip_file)
    super().save(*args, **kwargs)
    field_updates = {}

    if self.zip_file:                       # 1. unpack the ZIP into html_content/<id>/
        process_uploaded_zip(self)
        self.zip_file.delete(save=False)
        ...
    relocated_thumbnail = relocate_thumbnail(self)   # 2. move the thumbnail into thumbnail_img/<id>/

    if self.pk is not None and self.html_path:      # 3. RESCAN the document
        field_updates.update(refresh_content_weight_fields(self).as_field_updates())

    if field_updates:
        type(self).objects.filter(pk=self.pk).update(**field_updates)

    if self.pk is not None and (had_uploaded_zip or relocated_thumbnail is not None):
        queue_content_media_derivative_warming_on_commit(self.pk)   # 4. re-encode images after commit

A .save() can therefore unpack an archive, move files, re-parse the whole HTML document, re-flatten it to text and queue an image re-encode. That is correct for an edit. It is wrong for anything that merely wants to touch one column — which is why publish state, cost tables and the draft publisher all write with a queryset .update() instead, each with a comment saying so. The weight rescan runs unconditionally (not just on the ZIP branch) on purpose: has_canonical_header compares the document against title, so a title-only edit that touches no file would otherwise leave the flag stale and the reader would print the title twice.

delete() is hooked at the model, not at the call sites (line 340)

def delete(self, *args, **kwargs):
    content_id = self.pk                  # captured BEFORE super() clears it
    cleanup_content_files(self)
    super().delete(*args, **kwargs)
    if content_id is not None:
        queue_content_chunk_sync_on_commit(content_id)

Hooking the model rather than the two call sites is what makes the Django admin’s per-object delete_queryset loop covered too (admin.py loops deliberately instead of issuing a bulk delete, for exactly this reason). The de-index needs no special “delete” message: a deleted row can no longer pass the agent’s chunkable gate, so the same scoped run that would index it now removes it.

2. Getting content in

An operator has a 500 MB Notion export ZIP and a browser. Between those two facts sits the most-engineered part of this app that nobody ever thinks about.

Why the upload is chunked at all

Not because the file is large in absolute terms — because of a hard ceiling nobody in the code controls. Production sits behind Cloudflare, whose request-body cap was measured at exactly 104,857,600 bytes (100 MiB) during P83. No amount of nginx or gunicorn tuning moves it. So the ZIP is cut client-side into 16 MiB pieces, each shipped as its own ordinary request, and reassembled server-side.

Three coupled limits, all now real settings (config/settings.py:471–480, :573):

KnobDefaultWhat binds it
CONTENT_ZIP_MAX_BYTES500 MiBThe ceiling the upload-session POST enforces (measured: 524,288,001 bytes → 400).
CONTENT_UPLOAD_CHUNK_SIZE_BYTES16 MiBMust stay under both Cloudflare’s 100 MiB and Django’s body cap.
DATA_UPLOAD_MAX_MEMORY_SIZE20 MiBDjango refuses a request.body read above this before the view runs. Django’s own default is 2.5 MiB — below the chunk size, so leaving it alone would kill every upload.

That last one is a genuine trap and the code treats it as one. The console sends each chunk as a raw application/octet-stream body, so request.body is read against the cap; if the cap is below the chunk size, Django raises RequestDataTooBig and the operator gets Django’s HTML error page instead of an API error. OperatorContentUploadChunkView._extract_chunk_body (views.py:491–514) catches it and translates it into an ordinary JSON refusal that names both numbers, so the console can print a sentence.

The three-call upload protocol

POST   /api/content/admin/uploads                       → 201 {id, total_chunks, chunk_size, expires_at}
PUT    /api/content/admin/uploads/<uuid>/chunks/<index>  → 200  (repeat N times, any order)
POST   /api/content/admin/uploads/<uuid>/complete        → 200  status=completed, assembled_path set

upload_sessions.py is 215 lines of unglamorous correctness:

  • calculate_total_chunks (:54) is ceil(expected_size / chunk_size), and expected_chunk_size (:62) computes the exact expected length of each index — the last one is the remainder. store_upload_chunk then rejects any chunk whose length is not exactly that, which is a cheap, complete guard against a truncated or duplicated body.
  • Chunks land at MEDIA_ROOT/.content_uploads/<uuid>/chunks/00000003.part (CONTENT_UPLOAD_ROOT_NAME = ".content_uploads"), and re-uploading an already-received index is a no-op past the size check — so a flaky network retry is free.
  • assemble_upload_session concatenates in index order into a .tmp sibling, verifies the assembled size equals expected_size, and only then does temporary_path.replace(assembled_path) — an atomic rename. There is no window in which a half-written ZIP is visible under the real name.
  • Sessions carry a 24-hour TTL (expires_at); cleanup_expired_upload_sessions is a periodic task that rmtrees the directory and marks the row expired.

From assembled ZIP to a row: the import job

The operator’s content write (POST /api/content/admin or PATCH admin/<id>) can carry a zip_upload_id. The serializer’s shared body (serializers.py:640–676) does four things inside one transaction, in this order:

upload_session = validated_data.pop("zip_upload_session", None)
requested_publish_state = validated_data.pop("is_published", None)

with transaction.atomic():
    if upload_session is not None:
        upload_session = self._get_zip_upload_session(upload_session.pk, lock=True)  # SELECT … FOR UPDATE
    content = content_factory()                                # create_ or update_operator_content
    if requested_publish_state is not None:
        self.publish_changed = set_content_publish_state(content, requested_publish_state)
    if upload_session is not None:
        self.import_job = queue_content_import_job(content=content, upload_session=upload_session)
    return content

Two details in there are easy to skim past. First, publish_changed and import_job are side channels: DRF’s save() returns only the instance, so the serializer stores each on itself and the view reads it back afterwards. publish_changed is None when the request never mentioned publishing, and otherwise carries the seam’s real verdict — which lets the console suppress its “published!” notice when nothing actually moved. Second, the upload session is locked with select_for_update() only at the moment it is consumed; the field-level validation that runs earlier, outside any transaction, does a plain read.

Then import_jobs.queue_content_import_job creates a QUEUED job, flips the session to queued, and dispatches on transaction.on_commit — the codebase-wide dispatch-after-commit pattern (explainer #16 owns it) with a failure branch that marks the job failed if even the dispatch raises.

execute_content_import_job (import_jobs.py:77) is the worker body, and it is idempotent by early return: a job already SUCCEEDED or FAILED returns its status without re-running. It locks the row, marks it RUNNING, resolves the assembled path (through resolve_assembled_upload_path, which refuses anything that resolves outside MEDIA_ROOT), and then does the whole import with one line:

update_operator_content(job.content, zip_file=upload_path)

— which is to say, it hands the file to NotionContent.save() and lets the post-save pipeline from stop 1 do the unpacking, the rewriting, the weight rescan and the derivative warming. And then, at the very end, the part that matters for this page:

if NotionContent.objects.filter(pk=job.content_id, published_at__isnull=False).exists():
    # S1's ordering edge (P59.S3): an operator can send `is_published: true`
    # together with a `zip_upload_id`, so the row is already published and no
    # publish *transition* happens here -- the files simply appear underneath
    # it. Without this trigger nothing would ever index that content.
    queue_content_chunk_sync_on_commit(job.content_id)
Why that branch exists

The seam fires on a transition. If the operator publishes and uploads in the same request, the transition happens while the row still has no files — and the seam itself notices this and returns early without queueing anything (there would be nothing to index). Minutes later the import job lands the files under an already-published row, and no transition occurs. This is the second of the three trigger sites, and it exists purely to close that ordering hole.

Unpacking: importers.py

import_uploaded_zip (:77) extracts into a staging directory, finds the primary HTML file, rewrites its relative asset references to the final MEDIA_URL paths, locates the asset directory, and only then swaps staging into place. Everything happens under a temporary root that a finally always removes, so a bad archive leaves nothing behind. Bad input is expressed as ValueError (“Uploaded file is not a valid zip archive”, “does not contain an HTML file”), which the service layer wraps into a ContentWriteError with field_name="zip_file" so DRF reports it against the right field.

Localising hot-linked images: remote_images.py

Legacy Notion exports are full of <img src="https://postfiles.pstatic.net/…"> — images that were never in the ZIP and still live on Naver’s CDN. Those are outside every optimisation this app can do: no WebP derivative, no width variant, no cache control, and a third-party host on the critical path of every page view.

localize_content_remote_images (:160) downloads them into the content’s own remote/ subdirectory, deduping by URL hash, and rewrites <img>, <source>, srcset and any wrapping <a> to point at the local copy. It is host-allowlisted, deliberately narrowly:

ALLOWED_REMOTE_IMAGE_HOSTS = frozenset({
    "blogfiles.pstatic.net",
    "postfiles.pstatic.net",
    "cafeptthumb-phinf.pstatic.net",     # added P83.S5 — 19 of 199 stragglers lived here
})
REMOTE_IMAGE_TIMEOUT_SECONDS = 20

This is a management command, not an automatic step, and it is genuinely load-bearing: running it on production in P83 localised 198 images and rewrote 396 references, taking one content’s first paint from 169 requests across 154 third-party hosts down to zero third-party hosts.

The weight scan: weights.py and extraction.py

refresh_content_weight_fields re-derives seven columns from the stored document (CONTENT_WEIGHT_FIELDS). Three of them are load metrics — image_count, local_image_count (whose difference is the un-reachable hot-linked remainder), asset_bytes. Two are reader gates ported from JavaScript the frontend used to run after downloading the whole body: has_body and has_canonical_header. And two are the RAG input: extracted_text plus extracted_text_version.

extraction.extract_document_text is a deliberately boring flattener: headings become #/##/### lines, block tags (p, li, blockquote, figcaption, td, th) become lines, every <img> becomes an [IMG] marker, and the output has no blank lines at all — which is why the agent’s content chunker splits on heading markers rather than paragraph breaks (#9).

The salt discipline

CONTENT_EXTRACTION_VERSION is currently "2" and is stored beside the text on every row. It is folded into the agent’s chunk-set fingerprint, so bumping it forces every chunk set derived from an old text to be rebuilt rather than silently mixed with new ones. Its docstring gives the rule and the exception: bump on any change to the emitted text; never bump for a pure refactor. Version 2 exists because P77.S3 changed one thing — an <img> inside a <figure> with no <figcaption> now contributes its alt text after the marker, since otherwise that caption would vanish from the RAG text entirely.

3. The publish seam — the centrepiece

Here is the entire function, services.set_content_publish_state (apps/backend/content/services.py:216), docstring elided. It is twenty lines and it is the most carefully reasoned twenty lines in the app.

def set_content_publish_state(content: NotionContent | int, published: bool) -> bool:
    content_pk = content if isinstance(content, int) else content.pk
    if content_pk is None:
        raise ContentWriteError("Content must exist before changing publish state.")

    published_at = timezone.now() if published else None
    changed = bool(
        NotionContent.objects.filter(pk=content_pk)
        .filter(published_at__isnull=published)        # <-- change detection, in SQL
        .update(published_at=published_at)             # <-- never .save()
    )
    if not changed:
        return False
    if not isinstance(content, int):
        content.published_at = published_at
        if published and not content.html_path:
            # Published before its files exist (the import-job ordering edge).
            return True
    queue_content_chunk_sync_on_commit(content_pk)
    return True

Five decisions, each with a consequence you would hit within a week of getting one wrong.

(a) QuerySet.update(), never content.save()

From stop 1: saving a NotionContent re-runs its post-save file pipeline. Flipping a visibility switch must not unpack an archive, move a thumbnail, re-parse the document and queue an image re-encode. An .update() emits one UPDATE statement and touches nothing else. As a bonus, updated_at is auto_now — and it is deliberately not bumped here, because the catalog orders by -updated_at and a visibility flip is not a content edit. Re-publishing an old article should not float it to the top of the list.

(b) Change detection happens in SQL, not in Python

.filter(published_at__isnull=published) is the whole trick, and it reads backwards until you see it. If you are publishing (published=True), the filter is published_at IS NULL — i.e. it matches only rows currently in the other state. .update() returns the number of rows matched, so changed is True exactly when a real transition occurred.

Doing it this way rather than “read the row, compare, write” buys two things at once. There is no read-modify-write race: two concurrent publishes cannot both see “it was a draft” and both fire the trigger, because the second UPDATE matches zero rows. And a republish is a genuine no-op that keeps the original publish timestamp — the article’s publication date does not quietly move every time someone clicks 발행 again.

(c) It returns a verdict, and the verdict is used

True means “the stored state actually moved”. That value is not decorative: the operator serializer stashes it as publish_changed and the console suppresses its result notice on False. Before P55.S17 the verdict was computed here and thrown away, so the write response could not tell the operator that nothing had happened.

(d) Signals were rejected on purpose — and that forces the seam

Why no post_save signal

A Django signal on NotionContent would fire on every write — including the file-pipeline .update() calls, the draft publisher’s .update(), the legacy importer’s .update(), and any admin edit — and it would not fire at all for the queryset .update() this function itself uses (Django emits no signals for bulk updates). So the natural “automatic” mechanism is both too loud and too quiet. The alternative is explicit: one function, and a rule that every caller uses it. That rule is enforced socially (docstrings and comments at every call site) rather than mechanically, which is the honest cost of this design.

3b. The trigger — chunk_indexing.py

484 lines whose whole job is: tell the agent that one content’s chunk set may be out of date. Note the word “may”. This module is scrupulously agnostic:

One call shape, both directions

Publish and unpublish and delete all send the exact same request: POST /agent-api/indexing/content-chunk-runs {"content_ids": [42]}. The agent re-reads its own eligibility gate at run time and either indexes the content or deletes its chunk set. So a flip that happens between enqueue and run always resolves to the database’s current truth — “the backend never decides index vs de-index”.

Fire-and-poll, with two separate budgets

Two Celery tasks, both stateless, both carrying their own attempt counters as task kwargs (SYNC_TASK_NAME = "content.sync_content_chunk_index", POLL_TASK_NAME = "content.poll_content_chunk_sync"):

SYNC_MAX_ATTEMPTS = 5
SYNC_RETRY_COUNTDOWN_SECONDS = (30, 60, 120, 300)   # transport/protocol failures: growing backoff
SYNC_CONFLICT_MAX_ATTEMPTS = 20
SYNC_CONFLICT_COUNTDOWN_SECONDS = 60                # HTTP 409: flat, patient, 20 minutes

POLL_START_COUNTDOWN_SECONDS = 5
POLL_INTERVAL_SECONDS = 20
POLL_MAX_ATTEMPTS = 90                              # 90 × 20 s = 30 minutes
POLL_ERROR_MAX_ATTEMPTS = 5                         # consecutive unreadable statuses give up sooner

The 409 deserves its own paragraph, because it is the interesting failure. From #9: the content chunk-index route holds a single-active-run guard — one Redis key agent:indexing:content-chunk-run:active set with SET nx ex — and answers 409 without registering a run. So when a second publish lands while a full corpus catch-up is grinding through thousands of chunks, there is no run id to poll and nothing to wait on. This module models that precisely:

class ContentChunkRunConflict(RuntimeError):
    """HTTP 409: another content chunk-index run holds the corpus (P59.S2).

    Deliberately **not** a subclass of `ContentChunkIndexingClientError`: a
    conflict is the expected outcome of two publishes in quick succession, is
    retriable by construction (no run was registered, so there is nothing to
    poll) and runs on its own budget. Keeping the hierarchies separate means an
    `except ContentChunkIndexingClientError` can never swallow it."""

Two exception types with no inheritance relationship, so a broad except on the transport error cannot accidentally consume a healthy conflict — and 20 flat one-minute retries, because “the thing failing” is a perfectly healthy run doing real work.

The three trigger sites, and why delete is one of them

  1. services.set_content_publish_state:262 — every real publish/unpublish transition.
  2. import_jobs.execute_content_import_job:168 — files landing under an already-published row.
  3. models.NotionContent.delete:358 — the row going away.

Delete is a trigger site for the same reason unpublish is: the chunk rows in agent.content_chunk_artifacts live in the agent’s schema, and Postgres foreign keys do not cross that boundary — the agent’s tables have no FK to content_notioncontent at all, and the read bridge is SELECT-only in one direction. So deleting the Django row does not cascade anything. Without this trigger, a deleted article’s chunks would sit in the index until the next full catch-up run, and the retrieval query’s join back to the (now absent) backend row is the only thing keeping them from being served.

Fail-soft dispatch, alert on give-up

queue_content_chunk_sync_on_commit wraps app.send_task in a bare try/except Exception that only logs. A broker hiccup must never break the publish that triggered it, and the cost of a dropped dispatch is a stale index until the next catch-up — exactly the recovery story the module is designed around. But nothing is silently lost: every give-up path emails the operator through send_ingestion_alert (explainer #16), under three content-scoped keys so a retry storm for one content collapses into one mail while a second content failing at the same time still gets through:

START_FAILED_ALERT_KEY_PREFIX = "content-chunk-sync-start-failed"
RUN_FAILED_ALERT_KEY_PREFIX   = "content-chunk-sync-run-failed"
POLL_TIMEOUT_ALERT_KEY_PREFIX = "content-chunk-sync-poll-timeout"

and every alert body ends with the same remedy sentence, spelled out as a runnable command:

CATCH_UP_REMEDY = (
    "Postgres stays the source of truth, so nothing is lost: re-run the "
    "content chunk catch-up to heal the index -- POST "
    "/agent-api/indexing/content-chunk-runs with {\"content_ids\": [<id>]} for "
    "this one content, or with {} for the whole corpus."
)

Transport-wise the client is plain urllib with a 30-second timeout and a bare X-Agent-Service-Token header — the shared-secret boundary from #2. There is no user to impersonate here, so no JWT is forwarded. And the response is validated field by field (_build_content_chunk_run_status): a payload missing run_id, trigger, status, progress or error_message, or with the wrong type, is a client error rather than an AttributeError three frames later.

Rendering the body: delivery.py

The stored HTML file is not what the browser gets. render_content_html parses it and rewrites every local asset reference (HTML_REFERENCE_ATTRIBUTES = (("img","src"), ("source","src"), ("a","href"))) from a raw MEDIA_URL path to a served api-content-asset URL — and for images, does a good deal more:

tag["src"]     = asset_url + "?w=2560"                       # CONTENT_MEDIA_BODY_WIDTH
tag["srcset"]  = "…?w=1024 1024w, …?w=2560 2560w"            # CONTENT_MEDIA_BODY_SRCSET_WIDTHS
tag["sizes"]   = "(max-width: 760px) 100vw, 680px"           # CONTENT_IMAGE_SIZES_ATTRIBUTE
tag["data-original-src"] = asset_url                         # uncapped — the lightbox's zoom source
tag["width"], tag["height"] = read_image_dimensions(source)  # so the box is reserved before bytes arrive

The ?w= values are a long-edge cap, not a width, and only three exist: CONTENT_MEDIA_WIDTH_VARIANTS = (512, 1024, 2560). Anything else — absent, malformed, unlisted — degrades to today’s behaviour rather than 400ing, so the contract can never break an existing URL. The sizes hint is derived from the real reader layout, not guessed: the article iframe spans a 720 CSS px column with clamp(1rem, 2.5vw, 1.75rem) of padding a side, giving a ~684 px image box; the <svg>-free arithmetic is written out in the comment at delivery.py:101–111. Note that only local images get any of this — a hot-linked postfiles.pstatic.net URL fails the storage-prefix test and is left exactly as it is, which is the whole motivation for remote_images.py.

?deferred=1 selects a second representation where each reserved local image’s source is parked in data-src/data-srcset, and its live src is replaced by a ~95-byte transparent SVG data URI with the image’s exact intrinsic dimensions. Nothing inside the document can un-defer it — the reader frames the article with a sandbox that has no allow-scripts, which is also why native loading="lazy" is inert there — so the swap is driven from the parent realm by an IntersectionObserver. Two measured details justify the odd shape: only images that came out of the width-variant pass with intrinsic width/height are deferred (an unreserved deferred image is 0 px tall, the article collapses into one viewport, and every image intersects at once), and the placeholder must be a real src rather than bare attributes because Chrome lays a srcless <img> out from the raw attributes instead of the attribute ratio — measured over-reserving one article by 2.3×. It is a variant rather than the default because the operator’s “미리보기 열기” links open this route in a bare tab, which has no parent realm to run the loader.

Caching: two fingerprints and one deliberate omission

CONTENT_HTML_RENDER_VERSION = "5"                 # BUMP when the rewrite or the URL shape changes
CONTENT_HTML_RENDER_CACHE_KEY_PREFIX = "content:html-render"
CONTENT_HTML_CACHE_CONTROL = "no-cache"           # store, but ALWAYS revalidate

fingerprint = sha256("5|eager|html_content/42/치킨집.html|184213|1755678901234567890")

The fingerprint mixes the render version, the eager/deferred flag, the file’s media-relative name, its size and its st_mtime_ns — nanoseconds, not seconds, so a same-second republish still flips it. That one string is both the ETag and the Redis render-memo key, which makes staleness structurally impossible: the key is the identity of the thing rendered, so the 300-second TTL only bounds Redis growth. Cache failures degrade to rendering; a Redis outage must never turn a content page into a 500.

The Last-Modified that was removed on purpose (P83.S5)

The HTML route sends an ETag and no Last-Modified, and calls request_cache_is_fresh(..., allow_if_modified_since=False). The reason is measured, not theoretical: Cloudflare strips ETag from every text/html response on production. With both headers present, a returning reader behind that CDN falls back to If-Modified-Since and gets a 304 for markup the previous render version produced — so a CONTENT_HTML_RENDER_VERSION bump silently never reaches them. With only the ETag, an intermediary that strips it costs one re-transfer of ~160 KB of markup (~30 KB compressed) on a page whose images are measured in megabytes, and can never serve stale markup. The file’s mtime is simply not a sufficient validator for a representation that also depends on a constant in the source code.

And the reason the content routes are allowed to set caching headers at all, on an /api/ path: the ApiNoStoreMiddleware from #2 stamps Cache-Control: no-store on every /api/ response that does not already carry one. Its docstring names these views explicitly as the load-bearing exception: API payloads are identity-scoped and must not be cached, but content HTML and media derivatives are public, non-identity-scoped bytes.

Images: media_derivatives.py

Every eligible image gets a WebP twin, generated lazily on first request and cached on disk. Four flavours per source — the uncapped encode plus one per ?w= variant — each in its own sibling root:

content_derivatives/webp/       html_content/42/치킨집/1H6A9367.jpg.webp   (+ .json sidecar)
content_derivatives/webp-w512/  …
content_derivatives/webp-w1024/ …
content_derivatives/webp-w2560/ …

WEBP_QUALITY = 85 · Pillow method=4 · ImageOps.exif_transpose · long-edge cap, never an upscale

Sibling roots rather than one root with a width key in the sidecar, because the freshness check is whole-dict equality on the sidecar — adding a "width": null key to the existing root’s metadata would have invalidated every derivative already on disk and forced a global re-encode. For the same reason _build_derivative_metadata adds the width key only for a capped variant. The sidecar holds {version, source_path, source_size, source_mtime_ns}: if any of them moves, the derivative is regenerated.

Writing is atomic in the usual way — encode to .name.tmp, then replace() — and every failure path (OSError, UnidentifiedImageError, ValueError) returns None and logs, so an unreadable source degrades to serving the original bytes rather than 500ing.

Warming is queued after commit by the same three write paths that touch files (queue_content_media_derivative_warming_on_commit), and covers all four widths including the 512 thumbnail variant — because the first uncached request pays a full Pillow decode and resize of the source, operators upload straight-from-the-shoot files (6 MB is real), and a list of cards is exactly where that latency would be visible.

The negotiation, and the CDN bug that changed it

select_content_media_representation (:178) decides what to serve:

Here is the story behind CONTENT_MEDIA_UNNEGOTIATED_CACHE_CONTROL = "private, max-age=3600", measured on production in P83.S5. Cloudflare caches /api/content/<id>/assets/… and ignores Vary: Accept (only the Enterprise “Vary for images” feature honours it). So whichever representation lands in the edge cache first is served to every later client for the whole TTL. One request without image/webp in its Accept header — a crawler, a link-preview bot, an uptime monitor, a stray curl — poisons that URL with the original bytes. The measurement: 7,996,055 bytes of JPEG returned as a cf-cache-status: HIT on …/1H6A9367.jpg?w=1024, against 131,300 bytes of WebP. A 61× regression, completely invisible at the origin.

The fix is one line and no negotiation change: mark the un-negotiated original private. It stays correct for the client that asked for it and is simply never stored at a shared cache, so it can no longer displace the WebP every browser wants. Browsers have all sent image/webp since 2020, so no reader response changes flavour or loses edge caching. Note the flag is keyed on what the client asked for, not on what was served — so a failed derivative (an SVG, an unreadable source) still caches publicly for the browsers that get it.

The ETag is built the same way as the HTML one, with the representation name in the mix ("webp-w1024" / "original"), so ?w=1024, ?w=2560 and the bare URL can never share a cache validator.

What a chat turn receives: build_selected_content_context

When a user attaches contents to a message, the agent calls back with their ids:

agent: fetch_selected_content_context()        # apps/agent/app/chat/backend.py:842
   →  POST {backend}/api/content/selection-context   {"content_ids": [42, 51]}
   ←  {"selected_content": [{id, title, description, text}, …]}

Server side that is ContentSelectionContextView → services.build_selected_content_context (:367), which for each content reads the stored HTML file, decomposes script/style/noscript, and flattens the rest to text with a block-tag-aware walker (_SELECTION_CONTEXT_BLOCK_TAGS, 25 tags), collapsing runs of blank lines. <img> tags contribute their alt text; <br> becomes a newline.

Three properties worth noting:

  • It is all-or-nothing. If any item’s HTML is missing, unreadable or empty, the whole call raises ContentSelectionContextUnavailableError and the route answers 503 with a single opaque detail — never a partial context, because a turn silently missing one of the three articles the user attached is worse than a turn that fails loudly.
  • It reads the file, not extracted_text. The two flatteners are genuinely different — this one preserves inline structure for a prompt, extraction.py emits offset-stable markdown-ish lines for the chunker. They are not interchangeable and the codebase does not pretend they are.
  • The agent verifies the answer. Per #4, fetch_selected_content_context fails if the returned ids are not exactly the requested ids in order — so a reordering or a dropped item cannot silently change what the model reads. The text then lands in the tail of the system prompt as [Current selected content], which is precisely why #5 insists nothing dynamic may be added earlier: the static Korean rulebook above it is the cached Gemini prefix.

Related, and much smaller: build_public_content_body_preview (:96) extracts a ≤180-char plain-text teaser for the catalog card, skipping any lead block that merely repeats the title or description — with a fuzzy prefix match (both ≥24 chars, either a prefix of the other) so a truncated description in the document still counts as a duplicate.

Recommendations, view history and analytics

NotionContentQuerySet.recommended_for (models.py:159) is popularity-then-recency: count ContentViewHistory rows in a 30-day window, excluding the current content and anything not readable, order by view count then -updated_at then -id; if fewer than 10 come back, backfill the remaining slots with the most recently updated readable contents. No personalisation, no embedding — and the fallback guarantees the rail is never short on a young corpus.

ContentViewHistoryListCreateView has an asymmetry that is easy to misread: get_permissions returns [AllowAny()] for POST and the authenticated default for GET. Anyone may record a view (the row’s user is then NULL); only the owner may list theirs. Recording still goes through ReadableContentLookupMixin, so you cannot record a view of a draft.

build_operator_content_analytics (services.py:270) is what the console’s per-content panel draws: lifetime and date-ranged view counts, unique users, and uses — where a “use” is a ConversationMessageSelectedContent row on a USER message, i.e. someone actually attached this article to a question. It counts on content_id_snapshot rather than a live FK, so analytics survive a content being deleted. The conversations import is deferred inside the function to avoid the content ↔ conversations cycle, and the daily series is built by walking every date in the range and filling zeros — a missing day is a real zero, not a gap in the chart.

5. Cost tables and the Notion mirror

The 총 비용 표 — two schema majors, one masking rule

A cost table is the paid-content payload of this product: the itemised construction and equipment cost of a real shop. It has its own written contract (docs/reference/content-standard/cost-table/contract.md) and cost_tables.py implements it in 1,252 lines. Three jobs: validate, project, attach.

Two majors are live at once, and neither migrates the other — a stored document keeps the schema string it was registered with:

The column keys (group · item · detail · min · max · note), the price section, the scalars and the masked projection are identical in both; 2.0 frees the printed labels, never the column set. Support is enumerated, never open-ended — SUPPORTED_SCHEMA_MAJORS = (1, 2) and a 3.x payload is an error, not a partial render.

Validation is non-raising by default: collect_cost_table_issues returns every violation in document order (validate_cost_table_document is the raising wrapper), because the operator’s upload preview must be able to show what is wrong before anything is attached. Each CostTableIssue carries three fields:

@dataclass(frozen=True, slots=True)
class CostTableIssue:
    path: str          # "groups[3].items[7].min"  — where
    message: str       # the developer-facing English clause, printed verbatim in mono
    message_ko: str    # the Korean clause for the same CONDITION

The Korean table (ISSUE_MESSAGES_KO) is keyed by the condition, not by the English sentence, so the same key yields the same Korean clause wherever the condition is checked and a wording change happens in one place. And it holds only conditions, never locations — the client composes “4. 간판 · 행 28 · 외부 간판의 min” from path against the document it is holding, because that is the only place that knows the document. An unknown code yields "", which the client renders as “fall back to the English clause”, never as a blank line.

Masking is an allow-list, and that is a security decision

build_cost_table_projection(document, entitled=…) returns either the entitled document or a masked one built by key omission from an explicit allow-list of the contract’s “safe to show as shape” fields. Never a deny-list — a deny-list leaks every field added after it was written. Where the contract grants a wildcard (unit.*, vat.*, columns.*), this module copies the known keys only, so a field added inside one of those objects later cannot ride the wildcard into a masked payload. A masked payload carrying a key the contract does not list as shape-safe is, by definition, a bug.

The public route mirrors that carefully. ContentCostTableView is auth-capable but never auth-required: authentication_classes = [JWTAuthentication] with permission_classes = [AllowAny]. Its neighbours run authentication_classes = [] and so literally cannot tell who is asking; IsAuthenticated would 401 a guest — but the masked table is a designed state a guest is meant to see, not an error. So a guest gets a 200 with the masked payload, exactly like a signed-in free user. Entitlement is read from the database (accounts.entitlements.get_entitlements → User.tier), never from the JWT tier claim, which as #3 established gates nothing server-side and can trail the DB by a refresh cycle. The response is private, no-store plus Vary: Authorization, because the body varies by entitlement. And an absent table is a 404, never a 200 with an empty object for the client to hide — “render nothing” is a server-side decision.

attach_cost_table takes the same posture as the publish seam and says so: it never touches the NotionContent row — no save(), so no file pipeline, and updated_at stays put, because a cost table is not a content edit. It locks any existing row with select_for_update() and refuses with CostTableAlreadyAttachedError unless the caller passed replace=True, so an operator re-upload is always deliberate rather than an accidental overwrite.

Workbook intake and the LLM normaliser

cost_table_workbook.py (1,681 lines) reads a filled 산출표 .xlsx — and does it with stdlib only, because no xlsx library exists anywhere in this stack. It opens the workbook as a zip of OOXML parts (xl/workbook.xml + the rels for sheet order, xl/worksheets/sheetN.xml, xl/sharedStrings.xml, xl/styles.xml). Four binding rules are worth remembering:

  • First sheet in workbook order, resolved through the rels — never by filename, because the delivered workbooks name the data sheet after the project.
  • Blocks are located by their labels (0. 체크사항, the column-header row, N. <name> 소계, 합계), never by absolute row number, because 창플 is told to insert rows inside a group.
  • unrecognized[] is a required output. Every label, column, row or trailing cell the parser cannot map is collected with its cell reference, its raw text and why. Nothing is silently dropped, and an unmapped row is never summed into a subtotal — the sheet’s own subtotals are transcribed as-is so a discrepancy surfaces as a reconciliation issue at preview instead of quietly changing the numbers.
  • Formulas are read, never evaluated. A 소계 cell contributes its cached value; a workbook saved by a tool that does not compute parses with placeholder totals, which is exactly what the reconciliation issues are for.

A workbook that does not match the template comes back as document=None plus issues — the module never raises, because the operator preview must be able to show the failure. That is where cost_table_normalize.py picks up (P82.S5): extract_workbook_grid() reads any workbook into a raw cell grid with no interpretation at all, and this module turns that grid into a 2.0 proposal:

grid → prompt → Gemini (structured output) → server-side assembly → the S1 validator → back to the console

Three properties are deliberate, and generalise well beyond cost tables:

  1. Nothing is persisted and nothing is auto-applied. The proposal goes back to the operator’s document editor and only their PUT writes anything. An invalid proposal is still a 200 — the whole point of a preview is that the operator sees the issues and fixes them.
  2. The model proposes text and numbers; the server decides structure. Group codes, the 1..n check-slot run, is_range, the schema string, the provenance block, and above all every contains_amount sensitivity flag are computed here by text_contains_amount(). A model is never trusted with a masking decision: a wrong flag leaks money to a free reader, and it is exactly the kind of judgement call a language model gets subtly wrong.
  3. Amounts cross the model as strings, not numbers. The house structured-output style makes every field non-nullable with a sentinel default — and a nullable number is the one thing that style cannot express, while 0 and “not quoted” are genuinely different facts in this contract. So the model writes "" for a blank cell and "1234.5" for a figure, and a string the parser cannot read becomes null plus an operator-visible warning — never a guess.

The model id is not hard-coded: it comes through the P44 operator LLM-runtime store under role ROLE_COST_TABLE_NORMALIZE (resolve_role_config, defaults gemini-3.7-flash / thinking high) — explainer #17’s subject. And because the operator is watching a spinner, the call is synchronous with a hard MAX_CALL_SECONDS = 90.0, chosen against the real stack: nginx proxy_read_timeout 300s → gunicorn --timeout 120 → this call. At 120 s gunicorn kills the worker and the operator gets a bare 502 with no detail; 90 s leaves room for the upload read, the grid extraction, the validator and both projections inside that budget.

The Notion mirror — notion_mirror.py

Last, and smallest: an archival side-effect. When the v1 content agent publishes a draft, the same scrubbed public copy is mirrored to a Notion database page (기록/보관). Be precise about the scope, because the name invites confusion in both directions: this has nothing to do with the legacy Notion exports that gave NotionContent its name, and it is triggered from exactly one place — draft_publish.py:170, right after publish_draft_job returns, outside the publish’s own transaction (which has already committed), which is why it dispatches directly via app.send_task rather than on_commit. The v2 agent’s publish path does not mirror.

The design rule is stated in the module docstring and enforced everywhere: a Notion failure or rate-limit never blocks, delays, or rolls back the 미라클 publish. Concretely:

  • queue_notion_mirror (:90) swallows every failure of its own — unconfigured is a quiet no-op, an already-mirrored job is a quiet no-op, and send_task raising is logged and swallowed.
  • The task never touches job.status, only the three mirror-state fields (notion_page_id, notion_mirror_error, notion_mirrored_at). A failed mirror must never look like a failed publish — fail_notion_mirror’s docstring says exactly that.
  • The double-dispatch guard exists twice: best-effort at queue time, authoritative inside execute_notion_mirror (:134), so a re-publish never re-mirrors.
  • The whole feature is dormant until configured: without NOTION_API_TOKEN and NOTION_MIRROR_DATABASE_ID every dispatch and every execution quietly no-ops. That is the house “unconfigured is the off switch” convention from #2 — no separate ENABLE_ flag.
  • Retries: NOTION_MIRROR_MAX_ATTEMPTS = 3, 30 s apart, with 429 and Notion’s 529 (“service overload”) in the retryable set alongside the usual 5xx.

One API detail is recorded in the docstring because it is a live trap: creating a page needs a two-call sequence — GET /v1/databases/{id} to read data_sources[0].id, then POST /v1/pages with a data_source_id parent — because the older database_id parent shape has been documented-deprecated since 2025-09-03.

And the body is re-derived, never stored: build_notion_mirror_markdown rebuilds (title, markdown) from the approved draft version the exact same way publish_draft_job derives the published HTML — same _extract_title, same _split_blocks, same scrub_public_text. One derivation, two outputs, so the 미라클 page and the Notion archive can never disagree.

Quiz

Five questions. Click an option to see whether it is right and why.

1. set_content_publish_state persists with a queryset .update(). What would break if it used content.save() instead?

NotionContent.save() is a file pipeline, not a column write (models.py:320–350): it unpacks any pending ZIP, relocates the thumbnail, re-parses the document to refresh seven weight fields, and queues media-derivative warming on commit. It also touches auto_now updated_at, and the catalog orders by -updated_at. The seam’s docstring names both consequences explicitly.

2. Which three sites queue the content chunk-index sync, and why is delete one of them?

services.py:262, import_jobs.py:168 and models.py:358. agent.content_chunk_artifacts lives in the agent’s schema, which the backend role can only read; there is no FK and no cascade. The import-job site exists for the ordering edge where an operator publishes and uploads in one request, so the files land under an already-published row with no transition to fire on.

3. An operator publishes a content while a full-corpus catch-up run is already in flight. The agent answers 409. What happens?

ContentChunkRunConflict is deliberately not a subclass of ContentChunkIndexingClientError, so a broad except cannot swallow it, and it runs on SYNC_CONFLICT_MAX_ATTEMPTS = 20 × SYNC_CONFLICT_COUNTDOWN_SECONDS = 60. The publish itself already returned 200 long before — the whole chain runs after transaction.on_commit.

4. Content HTML is served no-cache while an image derivative is served public, max-age=3600 — except for one case, which is private. Which case, and why?

CONTENT_MEDIA_UNNEGOTIATED_CACHE_CONTROL = "private, max-age=3600". Measured in P83.S5: 7,996,055 bytes of JPEG returned as a cf-cache-status: HIT against 131,300 bytes of WebP — a 61× regression invisible at the origin. The flag is keyed on what the client asked for, not on what was served. A source that is already WebP is one representation for everybody and stays public.

5. Suppose the chunk-sync task is lost entirely — a broker hiccup, and the dispatch never happens. A content was just unpublished. What can a user retrieve?

This is the asymmetry the page’s third idea names: unpublishing is instant, publishing is eventual. The chunk table carries no gates of its own, so the retrieval SQL repeats the readable-content predicate by joining back to the backend row over the read bridge (a test pins that the two copies have not drifted). A lost dispatch costs searchability of a new article until the catch-up run, never the exposure of a withdrawn one.
