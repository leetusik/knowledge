Background — what this curriculum is, and how to read it

changple5 was built by vibecoding: it works, it is in production, it makes money — and its builder had never sat down and read it. This curriculum is the sitting down. Nineteen pages, one per subsystem, written by walking the real code rather than the documentation, so that the person who owns this app can stop steering it by feel and start changing it deliberately. That is the whole ambition: not reference material, not an architecture deck, but a course you read once, front to back, after which nothing in the repository is a black box.

The order is deliberate and it is top-down. First the shape of the system: what the containers are, where the boundaries sit, who is allowed to write what. Then the chat product, which is the thing users actually touch and by far the most intricate machinery in the repository. Then the content side — where 미라클 articles come from and how they get published. Then running it: Celery, the operator console, billing, and the small subsystems that hang off the edge. Each part assumes the ones before it, because the code does.

Reading in order is not a suggestion

Every page after the first opens by linking its predecessor, and the pages were written to lean on each other rather than repeat each other. A handful of pages became anchors that later pages cite instead of re-teaching, and it is worth knowing which:

  • #2 owns configuration, schema pinning, the one-way read bridge and the two shared secrets. Nothing else re-teaches them.
  • #5 owns the chat loop — streaming, cancel, replay, the tool-call budget. #10 (컨설팅) explains only what differs from it.
  • #7 owns retrieval's read path. #5 names the three retrieval tools as surfaces and stops at the door; #8 and #9 own the write path that fills the index.
  • #12 owns the publish seam — the single function that makes an article public. #14 and #15 hand off to it rather than describing it.
  • #16 owns Celery, dispatch-after-commit and the mail path. Every earlier page that dispatches a background task points here instead of explaining it.

Read out of order and you will hit those pointers cold. Read in order and each page is roughly self-contained, because its prerequisites are three pages back.

What a page is, physically

Each page is one self-contained HTML document: between roughly 65 KB and 95 KB of markup, which the knowledge base extracts to somewhere around 37,000–63,000 characters of prose, code and tables. That is a long article, not a blog post. The honest pacing is one page per sitting; there is no prize for doing two. Part B is seven pages and is the long middle of the course — if you are going to lose momentum anywhere, it will be there, and the thing to do is stop after a page rather than skim three.

Three conventions hold on every page:

  • English prose, Korean product terms verbatim. 미라클, 컨설팅, 구성안, 창업가 MBTI, 상담신청, 발행 and friends appear exactly as the product and the code spell them — translating them would have made the pages harder to grep against the repository, not easier.
  • Real file paths, with line anchors. Claims are grounded in files, usually with a line number. Those anchors were verified on the day the page was published and code moves; if an anchor misses, the symbol name still finds it.
  • A five-question quiz at the end. Multiple choice, medium difficulty, answers revealed on click. They are there so you can find out whether you actually read the page.

The pages are dated snapshots. #1–#12 were published 2026-08-26, #13–#15 on 2026-08-28, #16–#19 and this guide on 2026-09-13. Where a page and the tree disagree, the code is the authority — that rule is what the curriculum was written under, and it is why the pages correct the documentation in a dozen places rather than repeating it. The corrections section collects every one of those, so a reader who only skims still learns where the folklore is wrong.

The curriculum, part by part

This section stands where every other page in the set has a Code section. There is no code to walk here: the code is on the nineteen pages, and this is the map to them. Part A — the shape of the system (#1–#4)

#1 · Big picture: three apps, one Postgres, one Redis, and how a request travels

After this page you will know why one product runs as three containers instead of one, and the answer is a concurrency model rather than fashion: Django runs under gunicorn with sync workers, one request each, while the agent is a single async process built to hold a streaming turn open for minutes. You will be able to draw the data layer from memory — one Postgres with two schemas and a deliberately one-way read bridge, one Redis split into three logical databases so that a Django cache.clear() (which is a FLUSHDB) cannot wipe the Celery queue or the agent's run registries — and you will be able to trace a request from the browser to a row and back.

Walks: compose.yaml, compose.prod.yml, infra/nginx/nginx.conf, infra/postgres/init/00-bootstrap.sh, apps/agent/app/main.py, apps/backend/config/{urls,asgi,wsgi}.py, apps/agent/app/api/routes/health.py.

Watch for: the production front door is not in this repository. compose.prod.yml defines no edge service at all — TLS and ports 80/443 belong to a separate edge-nginx project on the host. The nginx service you can read here is the dev front door. And config/asgi.py is referenced nowhere: production runs gunicorn config.wsgi.

#2 · Configuration and boundaries: settings, schema pinning, shared secrets, and live operator config

After this page you will know how a value actually reaches a running container — three rungs, .dev.env/.prod.env → the compose ${VAR:-default} → the code default — and, more usefully, why editing the dotenv file changes nothing for a container that is already up. You will know the three places search_path is pinned and why the agent pins none of them, and you will have learned the one pattern this codebase reuses for operator config read live across the read bridge: a module-level snapshot with a TTL, a failure path that keeps the last known good value, and throttled logging. That pattern appears three times with one skeleton; recognising it saves you reading the other two.

Walks: apps/backend/config/settings.py (all 781 lines, line-anchored), apps/agent/app/config.py, core/db.py, agent/app/db/connection.py, llm_config.py, chat/retrieval_config.py, retrieval/brand_policy.py, correlation.py.

Watch for: both shared secrets ship with committed dev defaults — in the code and in compose.yaml. A deploy that forgets to set them looks perfectly healthy and is fully compromised. (An empty configured service token, by contrast, fails closed on both sides.)

#3 · Identity and auth: Naver and Google login, JWTs, guests, and entitlements

After this page you will know the three caller shapes the backend recognises — a real User row, a GuestPrincipal, an AgentServicePrincipal — and why the authenticator order is forced rather than stylistic. You will have seen the same stateless-token trick used three times (the OAuth state, the email verification and reset tokens, the guest credential) in a codebase with no token table anywhere, including the fingerprint trick that makes every outstanding reset token die the moment a password changes. And you will know that entitlement decisions always re-read the database.

Walks: apps/backend/accounts/{social,naver,google,tokens,guest_tokens,entitlements,guest_limits,backends,models,views,usage,email_tokens}.py, apps/agent/app/api/dependencies.py.

Watch for: the tier claim inside the JWT gates nothing server-side. Its only live reader is the browser's badge; every enforcement point, including the agent's own per-turn read over the bridge, re-queries the row. That is why billing can change a subscription without invalidating a single token.

#4 · Conversations as the system of record: models, the API, and the agent write-back loop

After this page you will know why the Django table, not the agent, is the truth about a conversation, and what that costs: the user's message is written before the model runs, so a dead turn strands a lone trailing user row and there is a whole repair endpoint for it. You will understand the two invariants (strict user/assistant alternation, and append-only finalized messages) and the idempotency scheme underneath — uuid5 keys recomputed on both sides with a unique constraint as the floor, so a replay is a 200 and a different payload under the same key is a 409. And you will have met the authorization chokepoint that makes a foreign conversation id a clean 404 rather than a 403, by construction.

Walks: apps/backend/conversations/{models,views,serializers,querysets,snapshots,title_generation,guest_adoption,guest_retention}.py, apps/agent/app/chat/{backend,backend_errors}.py.

Watch for: the 409 your browser sees when you send a message too early is manufactured in the agent. Django answers 400; the agent string-matches the error text and re-raises it as 409. Rewording that message in models.py would silently turn every turn conflict into "the service is down" (tracked as Q3).

Self-check — Part A

A1. Which app may read which schema, and in which direction?

The agent's role has USAGE and SELECT on the backend schema — including on tables added by future Django migrations, thanks to ALTER DEFAULT PRIVILEGES. Django's role is granted nothing at all on the agent schema. The bridge is one-way by construction, not by convention (#1, #2).

A2. A container is running and you edit a value in .dev.env. What happens?

Nothing. The dotenv file is never copied into the image, so inside the container the resolver finds no file and does nothing; values arrive as real process environment variables from the compose environment: block. You have to recreate the service. The exception is operator-editable config, which is read live from Postgres with a ~30 s snapshot (#2).

A3. A user's subscription just lapsed, but their browser still holds a JWT with tier: "pro". Can they use Pro features?

No. The claim is a display hint. Every gate re-reads the database — get_entitlements on the backend, and the agent's own per-turn SELECT tier, chat_thinking_level over the read bridge. Only the badge is stale (#3).

A4. The browser receives a 409 when sending a message. Who produced it?

The agent. The model layer raised a plain ValueError, the serializer turned it into a DRF validation error, and Django answered 400; the agent's route sniffed the detail text for "alternate" / "awaiting a finalized assistant reply" and re-raised it as 409. Any other 400 from that write degrades to 503 (#4, Q3).

Part B — the chat product (#5–#11)

#5 · A chat turn end to end: the LangChain agent, streaming, cancel, and replay

After this page you will be able to narrate one turn in order: a thirteen-rung guard ladder, the user row written before the model starts, the SSE frame vocabulary the browser consumes, the agent loop with its four-call retrieval budget, and the assistant row written inside the generator. You will know how a turn survives a closed tab (the frames are buffered in-process and the run is durable), how cancel works with no task handle and no signal at all (two Redis fields, polled at named points), and why the search budget is reported inside tool results rather than in the system prompt — because the prompt is the cached Gemini prefix, and a per-turn number in it would cost the cache discount on every single turn.

Walks: apps/agent/app/api/routes/chat.py, apps/agent/app/chat/{agent,sse,durable_runs,run_registry,checkpointing,previews,fingerprints,user_thinking_level}.py, apps/agent/app/prompts.py.

Watch for: an answer is streamed live only when the turn is grounded. An ungrounded turn's deltas are buffered, so the three finalizer gates can replace the answer before the reader sees a word — with one honest exception, documented on the page, where a grounded turn's answer is replaced after it has already streamed.

#6 · Chat context: rolling windows, compaction, budgets, and recall

After this page you will stop thinking of a chat model as having memory, and start thinking of memory as a name for what the application chooses to re-send. You will know the rolling window's arithmetic — its watermark, its turn-boundary snapping, and what happens when a session falls behind — and the single most clarifying fact on the page: the conversation summary is not a message at all, it is a slot in the system prompt, rebuilt at every model step. You will also know why the recall tool is deliberately exempt from the search budget, and how it sees what the window has evicted.

Walks: apps/agent/app/chat/{rolling_window,rolling_compaction,compaction,budget,context,cited_ledger,citations,session_search_tool}.py, apps/backend/conversations/rolling_summary.py.

Watch for: the 200,000-token inline valve. Under the rolling window the common path makes no compaction call at all, but this second-line valve still can — and it logs nothing and persists nothing, so a session that keeps tripping it pays for the same merge on every turn (Q5).

#7 · Retrieval: the RAG read path from query plan to ranked citations

After this page you will know the full read path: a query plan, two candidate arms (lexical and vector) run over the read bridge, reciprocal-rank fusion with a recency boost, an LLM reranker, and only then body hydration — which is last for a cost reason and a security reason. You will know there are four corpora, not one, and you will understand the cache well enough to predict when it hits: thirteen key components, including a fingerprint of the operator's brand policy, so an operator toggle invalidates exactly what it should.

Walks: apps/agent/app/retrieval/{query_planning,candidates,ranking,cache,embeddings,brand_policy,content_search,cited_search,author_posts,document_bodies,operator_metadata,rate_limit}.py, apps/agent/app/api/routes/retrieval.py, apps/backend/documents/{eligibility,rank_policy}.py.

Watch for: the "lexical" arm is not full-text search. It is exact array overlap against the keyword list that ingestion's summariser chose — so lexical recall is a function of #8's enrichment, and a natural Korean question loses its particle-suffixed words entirely (Q7). And a single reranker failure burns the turn's whole four-search budget rather than falling back to the fused order (Q6).

#8 · Ingestion: how Naver cafe posts become an eligible corpus

After this page you will know how a 창플 cafe post becomes a corpus row: two transports (a fast JSON one and a slow DOM fallback, with the three real cases that force it), job/item bookkeeping that decides what survives a re-scrape, two Gemini enrichment passes (image alt text, then a text summary with keywords), and a nine-rung eligibility ladder that deliberately does not short-circuit, so every reason a post is excluded is stamped rather than just the first. That stamped reason list is what every downstream query reads.

Walks: apps/backend/ingestion/{scraper,execution,enumeration,board_sync,membership_walk,batch_execution,automatic_runs,schedules,recovery,job_control,monitoring,text_enrichment,image_alt,entity_resolution,models}.py, apps/backend/documents/{eligibility_engine,brand_curation,brand_verification,models}.py.

Watch for: enrichment_failed is defined, reserved and queried — and never written by anything. A post whose enrichment fails every time keeps the "never attempted" stamp, so it re-enters the paid enrichment queue on every reprocess run, and the operator console reports null rather than a count (Q8).

#9 · Indexing and embeddings: from documents to pgvector chunks

After this page you will know what an index is here — derived, lossy and rebuildable — and why that licences everything else about it. You will know the three artifact tables and why they do not share a column type (one dimension-less vector with no ANN index, two halfvec(3072) with HNSW), the three parallel pipelines that fill them (post summaries, post chunks, content chunks — the last two near-twins), the fingerprint with the chunker version baked in that makes a re-index cheap, and the one-embedding-per-request posture with the measurement that produced it.

Walks: apps/agent/app/indexing/** (both pipelines and their content_chunk_* twins), apps/agent/app/db/bootstrap.py, apps/agent/app/api/routes/{indexing,chunk_indexing,content_chunk_indexing}.py, apps/backend/ingestion/{index_handoff,index_candidates,agent_indexing,agent_chunk_indexing}.py.

Watch for: only the content-chunk route refuses a second concurrent run. Its naver twin registers every run it is asked for and says so in its own client's comment — "mutual exclusion is the caller's job" — while a full build takes longer than the registry's own TTL (Q10).

#10 · 컨설팅 mode: the planned multi-round consultation and its 구성안 report

After this page you will know exactly what a planned consultation adds to #5's turn: a LangGraph interrupt()/resume loop instead of a single pass, a round state machine with its own 409 vocabulary, and a 구성안 report generated by a Celery task rather than in the stream — because the report must survive a closed tab, a rate limit and a killed worker. You will also get a clean worked example of retiring a product mode without a migration, in the 무료 AI 진단 tombstone.

Walks: apps/agent/app/chat/consulting/{agent,planning,stream,grounding,tools,middleware,prompts,types}.py, apps/backend/conversations/{consulting_lifecycle,consulting_mutations,consulting_report_dispatch,consulting_report_finalization}.py, apps/agent/app/api/routes/consulting_reports.py.

Watch for: cancelling a probe writes no assistant reply at all — the card simply disappears and the round goes cancelled. That is deliberate (it keeps the alternation invariant intact), not a missing feature.

#11 · Safety and grounding: the injection guard, session lockdown, the citation gate, and trial caps

After this page you will have four concrete failure classes of an LLM product and the mechanism that answers each: prompt injection (a hard-reject after-model hook), ungrounded answers sold as sourced (the citation gates), abuse of a free anonymous surface (the double-guarded trial cap), and runaway spend (the limiters). More transferable than any single mechanism are the two house rules the page draws out — every rule is written twice, once in the agent as user experience and once in Django as the invariant; and fail-open versus fail-closed is decided per cap, with a stated reason, never by default.

Walks: apps/agent/app/chat/{security_guard,session_lock,guest_trial,guest_rate_limit,citations,missing_features}.py, apps/backend/conversations/guest_trial.py, apps/backend/accounts/guest_limits.py, apps/agent/app/retrieval/rate_limit.py.

Watch for: one documented open edge. A turn that searches, finds zero documents and then trips the injection guard refuses correctly but never carries the lockdown marker — so that conversation is not locked. It is rare by construction and has two backstops, and it is a one-line decision left open (Q13).

Self-check — Part B

B1. A user closes the tab three seconds into an answer. What happens to the turn?

It keeps running. With durable runs enabled the route hands the generator an always-connected shim, so the disconnect checks never fire: the turn completes, the assistant row is written, and re-opening the conversation replays it. The caveat is that the frame buffer lives in the agent's own process, which quietly requires exactly one agent container (#5, Q4).

B2. Where does the model learn how many searches it has left, and why not in the system prompt?

In the tool result. The system prompt is the stable, cached Gemini prefix; only the summary and selected-content slots are dynamic, at its tail. Putting a per-turn counter in the prompt would break prefix caching on every chat turn (#5).

B3. A user asks 치킨집 창업 비용은 얼마인가요? Which candidate arm carries that question, and why?

The vector arm. The lexical arm is exact equality against the indexed keyword array, and the tokenizer strips only surrounding punctuation — so 비용은 never matches the indexed 비용. Natural Korean carries particles on most content words, so the lexical arm routinely contributes less than it looks like it should (#7, Q7).

B4. On message ninety of a conversation, what does the model actually see?

The newest window of raw messages plus a [Conversation summary] slot rendered into the system prompt — not ninety messages. The user still sees all ninety in the browser, and the recall tool can search the evicted ones on demand, which is why the tool exists and why it is exempt from the search budget (#6).

Part C — the content side (#12–#15)

#12 · The content library: models, the single publish seam, media derivatives, and the Notion mirror

After this page you will know what a 미라클 content actually is as data, and why its extracted text is stored rather than derived on demand (the chunker's character offsets are only meaningful against one agreed string). #14 · Content agent II: architect, build, edit, publish

#15 · Content agent III: the agent-side drafting service and its live progress

After this page you will understand the generational split in one sentence — v1 makes an HTTP hop to the FastAPI agent and v2 does not — and you will know what that hop costs and what it buys. You will have seen a deliberately different agent design from #5's: a stateless hand-rolled loop with schema-only tools, where the model chooses a call and the application dispatches it by hand, which is a useful reminder that "tool calling" is two separable things. Self-check — Part C

C1. What single function makes a 미라클 article public, and why is it a function rather than a model signal?

set_content_publish_state in content/services.py. Signals were rejected deliberately — which is precisely what forces one auditable seam. It uses .update() rather than .save(), detects the change in SQL, and returns a verdict its five callers actually use (#12).

C2. A publish-triggered chunk-index dispatch is lost. What is the damage — and what if it had been an unpublish?

A lost publish trigger is survivable: the article is readable immediately but not yet retrievable, and a catch-up run repairs it. A lost unpublish trigger costs nothing at all, because retrieval filters on the live row — the index lags, the query does not. That asymmetry is what makes a stateless best-effort trigger an acceptable design (#12).

C3. What does 승인 on a 구성안 actually do?

It freezes the plan. It is the only guarded edge in the job state machine, and from that point every stage is stopped from altering the plan by machine checks: dropping, adding or retitling a marker each fails with its own code, while a pure reorder passes (#14).

C4. Which generation of the content agent calls the FastAPI agent over HTTP?

Only v1. The v2 package contains no reference to the agent API at all — its five progress producers are in-process Django/Celery call sites, and the shared HTTP progress route survives as a seam rather than a live path (#15, Q18).

#17 · The operator console backend and live LLM runtime config

#18 · Billing: the Toss subscription lifecycle from checkout to reconciliation

After this page you will know the whole money path — checkout, confirm, webhooks, renewal, the nightly reconciliation sweep — and the one property that makes it safe to replay: a renewal's order id is recomputable from columns that do not move, and the same string is sent as the payment provider's idempotency key. So a crash anywhere in a renewal is repaired by recomputing the id and asking again. You will also know how a subscription reaches the product, which is refreshingly boring: it writes User.tier, and every gate re-reads the database (#3).

Self-check — Part D

D1. You change a model id for a content-agent role in the operator console and nothing seems to happen. Why?

Those roles run on the backend inside Celery jobs, despite the console labelling them agent. The change is picked up on the next job via an uncached read, not within the agent's ~30 s snapshot — and a deploy carrying code for them must rebuild celery_worker / celery_beat, not fastapi_agent (#17, Q21).

D2. A background job is stuck after a deploy. What re-dispatches it, and when?

The worker_ready startup fan-out — eight tasks, not the three the operations doc lists (Q19). It fires when a worker starts, not on a schedule, so the reclaim windows are staleness thresholds evaluated at the next worker start. In practice deploys close the window (#16, Q12).

D3. Why does the ingestion alert path refuse to use the ORM?

Because it is the alert path for exactly the class of failure where the ORM and the queue may themselves be part of the problem. It resolves recipients without models and sends synchronously, and it never raises. Whether anyone is actually on the recipient list in production is a separate, open question (#16, Q20).

D4. Why can a renewal charge be safely retried when the first charge cannot?

The renewal's order id is derived from the subscription id, the period end and an attempt counter — all columns that survive a rollback — and is sent as the idempotency key, so recomputing it makes the provider replay rather than charge. The initial charge mints a random id inside the transaction, so a crash before commit loses it (#18, Q22).

Two mechanical facts about the curriculum itself

First, the knowledge base lists documents sorted by slug, and every page in this set is numbered 01- through 20-. The listing order is the reading order; you never have to reconstruct it.

Second, published pages are never edited. That is why no page links its successor — the forward direction did not exist when they were written, and this guide is what supplies it. It also means a correction discovered later does not appear on the page it belongs to: it lands here, in the phase record, or in a new page. If you read a page in six months and something smells stale, trust the code, and check this guide's corrections table before you trust the prose.

The one habit worth keeping. Every page in this set was written by reading the code and then checking the documentation against it, rather than the other way round. That is also the cheapest way to keep the set useful: when you change something these pages describe, the code becomes right and the page becomes a dated snapshot — which is fine, as long as you never again let a document be the thing you believe.

Quiz

Five questions across the whole curriculum — one per part, plus one that only makes sense if you have read all four. Click an answer to see whether it is right and why.

1. Which statement about the two Postgres schemas is true?

The bootstrap script grants the agent role USAGE + SELECT on the backend schema and then adds ALTER DEFAULT PRIVILEGES so future tables are visible too. There is no mirror grant in the other direction — the bridge is one-way in the database itself, not in code (#1, #2).

2. During a default chat turn, what decides whether the answer's text is streamed to the browser as it is produced, or buffered until the turn finishes?

The buffering predicate keys on grounding, not on the call count. Grounded turns stream live; ungrounded ones are held so the no-document, ungrounded-memory and filtered-citation gates can discard the draft before the reader sees it (#5, #11).

3. An operator unpublishes a 미라클 article. When does it stop being citable in chat?

This asymmetry — unpublish instant, publish eventual — is exactly what makes a stateless, best-effort index trigger acceptable: a lost dispatch can delay a publication becoming searchable, but it can never leave an unpublished article reachable (#12).

4. You change the model id for the content_architect role in the operator console. When does it take effect, and what must the next deploy rebuild?

The console labels it agent, but this role is called from the Django content agent inside Celery jobs, which read the store uncached per job. The label names the wrong service, which is why it is an open question (#17, Q21) — and why the "rebuild the worker" rule from #16 keeps catching people.

5. A chat answer cites a 미라클 article. Which chain of machinery had to run for that citation to be possible?

Contents are a second corpus with their own pipeline: set_content_publish_state (#12) → the content-chunk trigger → the agent's content-chunk pipeline (#9) → the content arm of the read path (#7) → the chat loop's citation enforcement (#5, #11). The first option describes the naver post corpus (#8), which is a different road entirely.
