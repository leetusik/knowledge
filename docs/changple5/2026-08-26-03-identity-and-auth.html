Background

The previous explainer, #2 Configuration and boundaries: settings, schema pinning, shared secrets, and live operator config, ended on the two shared secrets. It established who trusts whom with which string: JWT_SHARED_SECRET, minted-in-Django and verified-in-the-agent, and AGENT_BACKEND_SHARED_TOKEN, a static service token carried in both directions. It also showed the exact header builders the agent uses when it calls back into Django (apps/agent/app/chat/backend.py:516–540) and left one thing unexplained: where those credentials come from in the first place, and what each one actually says about the human at the other end.

That is this page. It is about identity — the mechanics by which a person sitting in front of a browser turns into something the code can name, check and refuse.

Two words that are constantly confused

Authentication asks who are you? and its answer is a name: user 4021, or guest b1f0…, or "the agent service". Authorization asks may you do this? and its answer is yes or no. They are separate steps, they fail with different HTTP status codes (401 versus 403), and in this codebase they are deliberately separated in a way worth naming up front: the token proves who, and the database row decides what. Never the other way round. Half of this page is about why.

Skip this box if you already know it

A credential is whatever a caller presents to prove an identity — a password, a cookie, a token in a header. A principal is the identity itself, as the server understands it after checking the credential. A claim is one statement inside a token: "user_id is 4021", "this expires at 10:31". Claims are asserted by whoever signed the token; they are only as trustworthy as that signature.

Skip this box if you already know it — JWT recap

Explainer #2 introduced the JWT (JSON Web Token): a small JSON payload plus a signature, written as three base64url chunks joined by dots. changple5 signs with HS256, an HMAC keyed by a shared secret — so anyone holding the secret can both create and verify a token. Two properties matter everywhere below. First, a JWT is signed, not encrypted: anybody can read the payload, they simply cannot change it without the secret. Second, verification is local and offline — you need the secret and a clock, not a database. That is exactly why the FastAPI agent can accept a caller Django authenticated, without ever asking Django.

Skip this box if you already know it — OAuth in one paragraph

OAuth 2.0 is the "log in with X" protocol. Rather than typing a Naver password into changple5 — which would then have it — the browser is sent to Naver, Naver authenticates the person and asks their permission, and Naver redirects back with a short single-use authorization code. The backend then swaps that code, server-to-server and using its own client secret, for an access token, which it uses once to read the person's profile. The whole point is that the code travels through the untrusted browser while the client secret and the resulting token never do. The state parameter is the protocol's slot for tying the trip back to the request that started it.

What is actually being protected

changple5 is a Korean startup-consulting product: a 미라클 chat agent grounded in a private Naver-cafe corpus, a 컨설팅 multi-round consultation that ends in a 구성안 report, a content library, a 창업가 MBTI quiz, and a Pro subscription. Almost none of that is public. A conversation belongs to exactly one account; a 구성안 report is a paid-tier artifact; the operator console must be reachable only by staff. So the identity layer is load-bearing product machinery, not paperwork.

Intuition

Three shapes of caller, only one of which is a row

Django's own mental model is that request.user is a row in the user table. changple5 widens that on purpose. After authentication, request.user is one of three things:

The two rowless principals are frozen dataclasses that simply declare is_authenticated = True and is_anonymous = False. That is the whole trick: Django REST Framework never asks whether request.user is a model instance, only whether it claims to be authenticated. So a guest can hold a real, scoped, refusable identity without costing a row, an index entry or a cleanup job.

The key idea of the whole page. A credential answers who, and nothing else. Every question of the form may this caller do X? is answered from the database, at the moment of the request. The tokens below carry a tier claim — and no rule anywhere is allowed to read it.

What is inside the token you are carrying right now

Log into changple5 and your browser is handed two tokens. Base64-decoded, the payloads look like this (real claim names, toy values):

ACCESS TOKEN                        REFRESH TOKEN
{                                   {
  "token_type": "access",             "token_type": "refresh",
  "exp": 1787051460,   // +30 min     "exp": 1789639860,   // +30 days
  "iat": 1787049660,                  "iat": 1787049660,
  "jti": "9f3c1e4a...",               "jti": "1c77b0d2...",
  "user_id": 4021,                    "user_id": 4021,
  "tier": "free"                      "tier": "free"
}                                   }

Six claims, and they divide cleanly by job. token_type separates the two so one can never be used where the other belongs. exp is the expiry, in seconds since 1970. jti ("JWT ID") is a unique id for this specific token, which is what makes revocation possible — you cannot un-sign a token, but you can write its jti onto a blacklist and refuse it later. user_id is the identity. And tier is the odd one out: a convenience copy of a database column, put there so a reader can colour a badge without a round trip.

The 30-day sliding session

Why two tokens? Because two properties are wanted at once and one token cannot have both. The access token is sent on every request, so it should be short-lived: if it leaks, the window is small. But nobody wants to log in every thirty minutes. So the long-lived refresh token is kept aside and used only against one endpoint, whose only job is to hand out a fresh pair.

changple5 turns on rotation: every use of a refresh token returns a brand-new refresh token and blacklists the old one. That has two consequences. A returning visitor stays logged in indefinitely, because the 30 days are counted from the most recent rotation, not from the original login. And a stolen refresh token has a self-destruct property: the moment either the thief or the real user rotates it, the other one's copy is on the blacklist and dead.

Why the tier claim must not be trusted

Look again at the third lane of the diagram. A user pays for Pro at minute 40. The database column flips immediately. The access token in their browser still says "tier": "free" and will keep saying so until it expires and a refresh rotates a new pair into place. If any server-side rule consulted the claim, that user would be told "Pro only" while holding a receipt.

The reverse case is worse. A user cancels, or a payment reverses; the database says free but their unexpired token still says pro. A rule reading the claim would hand out paid features to an unpaid account for the remainder of the token's life. So the rule in this codebase is absolute and mechanical:

The tier claim is a presentation hint, and only the browser reads it. Every enforcement point — the backend views, the agent's per-turn reader — re-reads tier from the database row. Below, we check that claim by grepping the whole repository for consumers, and find exactly one: the front end's badge.

An identity with no row

The anonymous trial is the most interesting design in this layer. A first-time visitor should be able to type a question and get a real answer before being asked to sign in. That means the server has to be able to say "this is the same anonymous person as a minute ago" — enough to scope their conversation to them, and to stop them from consuming the free trial a thousand times — without creating an account.

The obvious solutions are all bad. A shared anonymous account merges every stranger's chat into one history. A row per visitor fills the user table with garbage that then has to be swept. A cookie of random bytes has to be looked up somewhere, which is a table again. changple5's answer is to notice that a signed token is a storage mechanism: mint a JWT whose payload is a fresh random guest_id and an expiry, and the token itself becomes the identity record. The server stores nothing; it re-derives everything from the signature on each request.

The cost of a stateless identity is that it cannot be revoked one at a time — there is nothing to delete. The mitigations are visible in the design: a short 12-hour life, and a quota that is counted from the conversation rows carrying that guest_id rather than from a cache, so it survives a Redis flush. We will see both below.

Code

Everything below lives in two places: apps/backend/accounts/ (about 5,300 lines excluding tests — small for what it does) and one file on the agent side, apps/agent/app/api/dependencies.py. 1. The principal model

apps/backend/accounts/models.py:11 defines the user. It subclasses Django's AbstractUser — inheriting password, is_staff, is_superuser, last_login and the permissions plumbing — and then changes the identity field:

# apps/backend/accounts/models.py
class User(TimeStampedModel, AbstractUser):
    username = models.CharField(max_length=150, unique=True,
        help_text="Internal field used for authentication only.", editable=False)
    email = models.EmailField("email address", unique=True)

Django insists on a unique username; changple5 does not want one, so it keeps the column, marks it editable=False, and synthesises a value in save() (models.py:118): a social account becomes naver_<social_id>, anything else falls back to id_<pk> after the first save. The same method lowercases the email on every write, which is what makes Bob@X.com and bob@x.com the same login. The real identity is email, unique and case-folded.

The second model in the file, OperatorUserAuditLog (models.py:156), records what staff did to accounts — create an admin, update a user, reset a password — with the operator, the target, and a changed_fields list, and explicitly no values. It is a small, deliberate piece of governance: you can tell that a password was reset without the log containing anything sensitive.

The authenticator chain

Django REST Framework runs a list of authenticator classes in order until one returns a principal. The project-wide default (config/settings.py:551) is a single entry:

REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": (
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ),
    ...
}

Views that must also accept anonymous callers opt into a longer chain, and its ordering is a real constraint, spelled out at apps/backend/conversations/views.py:139:

# JWT is tried first so first-party callers are unaffected. Order matters:
# GuestTokenAuthentication returns None when its header is absent (so the chain
# continues), while AgentServiceTokenAuthentication RAISES on a missing header
# and must therefore stay last.
GUEST_CAPABLE_AUTHENTICATION_CLASSES = [
    JWTAuthentication,
    GuestTokenAuthentication,
    AgentServiceTokenAuthentication,
]

A subtle DRF rule that shapes two designs. An authenticator returning None means "not my credential, keep going"; raising AuthenticationFailed ends the chain with a 401. AgentServiceTokenAuthentication (ingestion/authentication.py:30) raises when its header is missing, so it can only ever be last. And this is precisely why the guest credential travels in its own X-Guest-Token header rather than in Authorization: SimpleJWT's JWTAuthentication raises on a bearer token that is not an access token, which would kill the chain before the guest authenticator ever ran. The header choice is not cosmetic — it is what lets the two credential families coexist on one view.

The service principal itself is four lines (apps/backend/ingestion/authentication.py:16) and the comparison is constant-time:

@dataclass(frozen=True, slots=True)
class AgentServicePrincipal:
    service_name: str = "agent-indexing"
    is_authenticated: bool = True
    is_anonymous: bool = False

# ... and in authenticate():
if not hmac.compare_digest(provided_token, configured_token):
    raise AuthenticationFailed("Invalid authentication credentials.")

compare_digest instead of == takes the same time whether the strings differ in the first byte or the last, so an attacker cannot learn the secret one character at a time by measuring response latency. You will see the identical call on the agent side. That token is explainer #2's subject; this page only notes it as the third shape of caller.

2. Way in #1 — social OAuth (Naver and Google)

This is how most real users arrive. The implementation is a small class hierarchy: accounts/social.py holds a provider-agnostic core, and naver.py / google.py subclass it. Its module docstring states the split exactly:

"""Provider-agnostic social OAuth core.
...
The shared core owns the signed-state make/verify, the JSON request helper (GET, plus
POST form-encoded for token exchanges like Google's), and the upsert/link
policy. Provider-specific concerns -- token exchange, profile fetch, and the
raw-profile -> user-field mapping -- stay as subclass hooks so each provider's
behavior is explicit and independently testable."""

The round trip, with toy data:

The signed state

Step 2's opaque string is built by build_login_url (social.py:104) and it is not random noise — it is a signed payload:

state = signing.dumps(
    {"provider": self.provider, "nonce": secrets.token_urlsafe(24)},
    salt=self.state_salt,
)

django.core.signing.dumps serialises that dict, stamps it with a timestamp, and appends an HMAC keyed by Django's SECRET_KEY mixed with the given salt (a per-purpose string; here "accounts.naver-oauth-state" from naver.py:22 versus "accounts.google-oauth-state" in google.py:20). The verification side, _validate_state (social.py:173), is the mirror image:

payload = signing.loads(state, salt=self.state_salt, max_age=self.state_max_age)
...
if not isinstance(payload, dict) or payload.get("provider") != self.provider:
    raise self.error_state(f"Invalid {self.display_name} state.")

So a callback's state must be a string this backend signed, under this provider's salt, less than state_max_age = 600 seconds ago, and naming this provider. Two of those checks are belt-and-braces against the same mistake: a Naver state replayed at the Google callback fails on the salt and on the provider field. Note what is not involved: no session, no cookie, no server-side table of outstanding states. Freshness comes from the embedded timestamp, uniqueness from the nonce — a stateless design that costs nothing to scale and that the login flow otherwise had no reason to keep state for.

Steps 7–8 are the subclass hooks. NaverOAuthService._exchange_code_for_token (naver.py:96) does a GET with a query string, because that is what Naver's endpoint wants; GoogleOAuthService._exchange_code_for_token (google.py:80) does a form-encoded POST that must also repeat redirect_uri, because that is what the OAuth spec and Google want. _upsert_user (social.py:263) is wrapped in @transaction.atomic and reaches for rows with select_for_update(), which takes a row lock so two simultaneous callbacks for the same person cannot both decide to create the account. Its logic is a small decision tree:

user = User.objects.select_for_update().filter(
    provider=self.provider, social_id=social_id).first()

if user is None:                                  # unknown (provider, social_id)
    user = User.objects.select_for_update().filter(email=email).first()
    if user is None:
        user = User.objects.create_user(...)      # brand new account
        created = True
    else:
        self._guard_link_conflict(user=user, social_id=social_id)
elif User.objects.select_for_update().filter(email=email)
        .exclude(pk=user.pk).exists():            # known identity, email now
    raise self.error_conflict(...)                # belongs to someone else

The interesting branch is the middle one: the provider identity is new, but that email address already has an account. changple5's answer is a hard refusal, never a silent merge. _guard_link_conflict (social.py:324) refuses three ways, each with a machine-readable conflict_provider so the web UI can say which door to use:

if user.provider and user.provider != self.provider:
    raise self.error_conflict("이미 다른 소셜 계정에 연결된 이메일입니다.",
                              conflict_provider=user.provider)
...
# A blank-provider, non-admin account with a usable password is an
# email/password signup (P24.S2). Adopting it as a social identity would
# clobber its password via set_unusable_password() below -- reject with a
# hard conflict instead.
if (not user.provider and user.user_type != "admin"
        and user.has_usable_password()):
    raise self.error_conflict("이미 이메일과 비밀번호로 가입된 이메일입니다.",
                              conflict_provider="email")

One email = at most one account, enforced as a 409. Auto-linking on a matching email is a classic account-takeover route: if a provider ever hands out an unverified address, the attacker inherits an existing account. Here the third guard exists for a different and equally real reason, and the comment says it plainly — the upsert ends with user.set_unusable_password(), so adopting a password account as a social identity would silently destroy its password.

The views are thin by comparison, and their job is mapping exceptions to status codes. NaverCallbackView (views.py:383) catches five error types and returns 503 for "not configured", 400 for a bad state, 409 plus the conflict_provider for a link conflict, 400 for a provider rejection and 502 for a provider outage — each with Korean copy built from the service's display_name_ko (네이버 / 구글). GoogleCallbackView (views.py:453) is the same block with the other class names. Both end identically:

return Response(build_refresh_token_pair(user))

which is where the three ways in converge. Routes are registered in accounts/urls.py:48–63 under the /api/auth/ prefix.

Why the Naver token is kept

Notice that the provider access token, once obtained, is used exactly once during login — to fetch the profile — and that Naver's is then stored while Google's is thrown away. The reason is account deletion. AuthWithdrawView (views.py:155) must not merely delete the local row; for Naver it also has to tell Naver that this app's grant is finished:

if user.provider == NaverOAuthService.provider and user.social_id:
    disconnect_outcome = "failed"
    access_token = (user.naver_access_token or "").strip()
    if access_token:
        try:
            service.disconnect(access_token=access_token)   # grant_type=delete
        except (...):
            disconnect_outcome = "failed"
        else:
            disconnect_outcome = "revoked"
user.delete()

NaverOAuthService.disconnect (naver.py:74) calls the token endpoint with grant_type=delete. Two design choices are visible: the deletion happens regardless of whether the disconnect worked — a user asking to leave always leaves — and the outcome is reported honestly to the client as revoked / not_linked / failed rather than being swallowed. Google needs none of this (google.py:59): "No Google token is persisted; withdraw deletes the row and the app grant stays user-revocable in Google account settings."

3. Way in #2 — email and password

The second door is a conventional signup, and its interesting parts are all about what happens between the account existing and the account being usable.

EmailRegisterView (views.py:503) validates with EmailRegisterSerializer — which lowercases the email, runs Django's password validators and translates their failures into Korean by error code (serializers.py:41), and normalises the phone number to bare digits matching 01\d{8,9} — then checks for an existing account and refuses with the same 409 + conflict_provider vocabulary the OAuth path uses. The account is created with provider="email" and the mail is queued:

def _enqueue_verification_email(user_id: int) -> None:
    """Fire the verification mail without ever blocking/failing the response.

    A broker outage (or any enqueue error) is logged and swallowed: the mail is
    best-effort and the resend endpoint is the recovery path, so an enqueue
    problem must never fail signup or resend."""
    try:
        from .tasks import send_verification_email
        send_verification_email.delay(user_id)
    except Exception:
        logger.exception("failed to enqueue verification email for user %s", user_id)

.delay() hands the job to Celery, a background worker system, and returns immediately; the HTTP response does not wait for SMTP. Celery, the queue and the dispatch pattern are explainer #16's subject. Note the two layers of "never fail the request": the enqueue is wrapped here, and the task itself (accounts/tasks.py) returns {"status": "error"} rather than raising, so no mail problem can crash a worker either.

Stateless email tokens, and the trick that makes a reset link single-use

There is no token table. accounts/email_tokens.py signs a payload, exactly like the OAuth state, with a distinct salt, purpose tag and lifetime per flow:

VerificationPassword reset
saltaccounts.email-verificationaccounts.password-reset
purposeemail-verificationpassword-reset
max age3 days1 hour
extra claim—fp: a password-hash fingerprint

Separate salts mean a verification token can never be replayed at the reset endpoint even before the purpose check runs. But statelessness has an obvious problem: if the server remembers nothing, what stops a reset link from being used twice, or from still working a week after the password changed? The answer is 11 lines:

def password_hash_fingerprint(password_hash: str) -> str:
    """Short, non-reversible fingerprint of a user's stored password hash.

    Embedding this in a reset token and re-checking it at confirm makes the
    token effectively single-use: once ``set_password`` rewrites the hash (on a
    successful reset, or any other password change) the fingerprint no longer
    matches and every outstanding token is rejected. This is the stateless
    equivalent of Django's PasswordResetTokenGenerator state-binding -- no table."""
    return hashlib.sha256((password_hash or "").encode("utf-8")).hexdigest()[:16]

Bind the token to state that the action itself changes. The token carries a digest of the current password hash. Completing the reset rewrites that hash, so the digest in every outstanding token — including the one just used — stops matching. One-time use, invalidation of all older links, and invalidation on any unrelated password change, all as a side effect of the operation itself. It costs one sha256 and no storage.

The check lives in _resolve_reset_token_user (views.py:642), which is shared by the preflight and the confirm endpoint so they can never disagree:

user = User.objects.filter(pk=payload.get("user_id"), provider="email").first()
if (user is None
        or user.email != payload.get("email")
        or payload.get("fp") != password_hash_fingerprint(user.password)):
    return None, Response({"detail": _RESET_TOKEN_INVALID_DETAIL,
                           "code": "token_invalid"}, status=400)

Three independent kill switches: the account is gone, the email changed since the token was minted, or the password moved. The same email re-check appears in EmailVerifyView (views.py:581) — "A later email change invalidates outstanding tokens".

The four password-reset endpoints, and why one of them is read-only

urls.py registers three reset routes plus the resend: request-password-reset, validate-reset-token, confirm-password-reset. The middle one (views.py:679) exists purely for user experience: it lets the reset page render a dead-link state on load, before showing a form the user would fill in for nothing. Its docstring is explicit that it "never sets a password or consumes the token" — which is only safe because consumption is a side effect of the hash changing rather than a flag the server flips.

Two anti-enumeration behaviours run through the whole family. RequestPasswordResetView and ResendVerificationView return the same cheerful 200 whether or not the address exists, so the endpoint cannot be used to test whether someone is a member. And EmailTokenObtainPairSerializer (serializers.py:183) overrides SimpleJWT's failure copy with one message for both wrong-password and no-such-account:

default_error_messages = {
    "no_active_account": "이메일 또는 비밀번호가 올바르지 않습니다.",
}

That same serializer holds the verification gate, and its placement is deliberate:

# Gate applies ONLY to provider="email" accounts (social/admin leave
# email_verified_at null by design). Runs after the password check
# succeeds, so it never reveals whether an unverified email exists to a
# wrong-password attempt -- those still get the generic failure upstream.
if self.user.provider == "email" and self.user.email_verified_at is None:
    raise AuthenticationFailed(
        "이메일 인증이 필요합니다. 가입 시 받은 인증 메일을 확인해 주세요.",
        "email_not_verified")

Checking verification after the password is what keeps the distinct email_not_verified code — which the front end needs, to offer a "resend" button — from becoming an oracle. You only learn that an unverified account exists if you already proved you know its password.

The dead-end that is deliberately avoided. ConfirmPasswordResetView (views.py:699) also stamps email_verified_at if it was null, with the reasoning in a comment: completing a reset via the emailed link already proves inbox ownership, and without this a user could successfully reset their password and still be refused at login as unverified.

Finally, password login itself. Django resolves credentials through a list of authentication backends; settings.py:546 puts a custom one first:

AUTHENTICATION_BACKENDS = [
    "accounts.backends.EmailAuthBackend",
    "django.contrib.auth.backends.ModelBackend",
]

EmailAuthBackend (backends.py:9) looks the account up by email — or by username when the identifier has no @ and the account is an admin — and then refuses anything that is neither an admin nor provider == "email". Social accounts fail here for a structural reason rather than a policy one: the OAuth upsert calls set_unusable_password(), which stores a hash that no input can ever match. A Naver user has no password to guess.

4. The token pair every door opens onto

Three ways in, one exit. build_refresh_token_pair (serializers.py:348) is six lines and is called by the Naver callback, the Google callback, email verification and password-reset confirm alike:

def build_refresh_token_pair(user) -> dict[str, str]:
    refresh = stamp_tier_claim(RefreshToken.for_user(user), user)
    return {"access": str(refresh.access_token), "refresh": str(refresh)}

}

Every line is load-bearing. SIGNING_KEY is not Django's SECRET_KEY — it is the separate JWT_SHARED_SECRET from explainer #2, the one value both apps are given, which is the entire reason the agent can verify these tokens. ROTATE_REFRESH_TOKENS plus BLACKLIST_AFTER_ROTATION require the rest_framework_simplejwt.token_blacklist app (installed at settings.py:78): rotation writes the old token's jti to a table, which is why revocation works at all in an otherwise stateless scheme. Three views expose the lifecycle, each a two-line subclass over a SimpleJWT base (views.py:137–153):

RouteViewWhat it does
POST /api/auth/tokenAuthTokenViewEmail + password → a fresh pair.
POST /api/auth/refreshAuthRefreshViewRefresh token → rotated pair; the old one is blacklisted.
POST /api/auth/logoutAuthLogoutViewBlacklists the submitted refresh token. The access token lives out its 30 minutes.

Logout does not instantly kill an access token, and nothing in this design could make it. A stateless signature has no revocation channel; the blacklist only covers the refresh token, and the ability to continue the session is what actually ends. The 30-minute access lifetime is the size of that window, and choosing it is exactly the trade this architecture makes: short enough to bound the damage, long enough that most requests need no round trip.

The tier claim and the one place it is re-read

accounts/tokens.py is 61 lines and mostly docstring — the docstring is the design document:

"""Shared JWT `tier` claim helpers (P27 D1).

`tier` is a DB-authoritative hint claim: every user-issued token pair carries
it so the agent (and any other JWT consumer) can read it without a round trip,
but nothing gates on it in P27 -- see `entitlements.py` for the actual
resolution seam. The claim is stamped on the refresh token; SimpleJWT's
`RefreshToken.access_token` copies all claims outside `no_copy_claims` onto
the derived access token, so stamping the refresh before deriving `access`
covers both token types from a single call site.

Refresh **rotation** must never simply carry the incoming token's `tier`
forward -- it has to re-read `user.tier` from the database so a tier change
takes effect on the user's very next refresh."""

Two mechanisms in one file. stamp_tier_claim is a one-liner (token["tier"] = user.tier) that is called on the refresh token only, and rides onto the access token for free because SimpleJWT copies claims when deriving one from the other. And restamp_tier_on_refresh handles rotation:

access = AccessToken(data["access"])
user_id = access.payload.get(api_settings.USER_ID_CLAIM)
user = get_user_model().objects.get(**{api_settings.USER_ID_FIELD: user_id})

stamp_tier_claim(access, user)
data["access"] = str(access)

if "refresh" in data:
    refresh = RefreshToken(data["refresh"])
    stamp_tier_claim(refresh, user)
    data["refresh"] = str(refresh)

Read that carefully: it takes the user id out of the freshly issued access token and hits the database for the current tier, rather than copying the value forward from the token that was presented. Doing it via the outgoing access token also avoids re-decoding — and therefore re-blacklist-checking — the incoming refresh token, which the caller (RefreshTokenRotationSerializer, serializers.py:316) has already processed. The practical consequence for the product: a subscription change reaches every JWT consumer on the user's next refresh, and not before — up to 30 minutes.

Which raises the obvious question: who suffers from that lag? Grep the repository for consumers of the claim and the answer is nobody on the server. Every "tier" string in Python is either the model, the stamping helper, the /auth/me serializer field or billing writing the column. The one live reader is the browser, and its own comment is candid (apps/web/src/lib/auth-client.ts:44):

// Paid tier (P27). Re-stamped from DB on `/auth/refresh` rotation only, so it
// can trail the DB by up to a rotation cycle -- consumers treat `tier === "pro"`
// as a hint ...

A badge that is briefly stale is a cosmetic bug. A gate that is briefly stale is a security or revenue bug. The architecture puts the claim firmly in the first category — and §7 shows where the real decisions are made instead.

5. Way in #3 — the anonymous trial

accounts/guest_tokens.py is 170 lines, a third of it explaining why the design is what it is. Its opening states the constraint that forced a new credential into existence:

"""The P68 anonymous trial needs a credential a *browser* may hold. The only
anonymous credential that existed before was the agent service token
(`X-Agent-Service-Token` == ``AGENT_BACKEND_SHARED_TOKEN``), which is the
internal API's shared secret and can therefore never be shipped to a client."""

The mint endpoint (views.py:322) is as small as it sounds — no authentication, no row:

class GuestTrialTokenView(APIView):
    authentication_classes: list[type] = []
    permission_classes = [AllowAny]
    throttle_classes = [GuestMintScopedRateThrottle]
    throttle_scope = "guest-token-mint"

    def post(self, request: Request) -> Response:
        del request
        token, guest_id, expires_at = issue_guest_token()
        return Response({"guest_token": token, "guest_id": str(guest_id),
                         "expires_at": expires_at.isoformat(),
                         "expires_in": int(guest_token_ttl().total_seconds())}, status=201)

and issue_guest_token (guest_tokens.py:85) builds the payload by hand with PyJWT rather than through SimpleJWT, because it is deliberately not a SimpleJWT token:

payload = {
    "token_type": GUEST_TOKEN_TYPE,          # "guest"
    "guest_id": str(resolved_guest_id),      # uuid4
    "iat": int(resolved_issued_at.timestamp()),
    "exp": int(expires_at.timestamp()),      # +12h by default
    # Not checked anywhere yet: the seam P68.S3/P68.S4 need to revoke a
    # single guest credential (adoption burn / abuse) without a new claim.
    "jti": uuid.uuid4().hex,
}
token = jwt.encode(payload, str(settings.JWT_SHARED_SECRET),
                   algorithm=GUEST_TOKEN_ALGORITHM)   # HS256

Same secret, disjoint claim set. A guest token is signed with the very same JWT_SHARED_SECRET as an access token — but it carries token_type: "guest" and a guest_id, and never a user_id. Since SimpleJWT's access verification requires token_type == "access" and the agent's user verification requires user_id, neither credential can ever be mistaken for the other. Reusing the key while making the payloads structurally incompatible is how one secret safely serves two credential families.

Verification (decode_guest_token, guest_tokens.py:111) checks the signature with a required-claims list, then adds two checks a library cannot make for you:

if claims.get("token_type") != GUEST_TOKEN_TYPE:
    raise GuestTokenError("Token is not a guest token.")

# Defense in depth: a guest credential must never resolve to a user
# principal, so a token carrying a user_id is refused outright rather than
# silently treated as anonymous.
if "user_id" in claims:
    raise GuestTokenError("Guest tokens must not carry a user_id claim.")

and returns the principal, a frozen dataclass carrying the only thing that scopes it (guest_tokens.py:63):

@dataclass(frozen=True, slots=True)
class GuestPrincipal:
    guest_id: uuid.UUID
    expires_at: datetime
    is_authenticated: bool = True
    is_anonymous: bool = False

GuestTokenAuthentication (guest_tokens.py:147) wraps that for DRF, and — per §1 — returns None when the header is absent so the chain continues. From there, guest_id is the identity everything is scoped by: conversations.querysets.guest_trial_conversation_session_queryset filters every lookup to it, so one guest can never read another's session.

What bounds a free trial

An identity anyone can mint for free is an identity anyone can mint a million of. accounts/guest_limits.py is the answer, and it is precise about which control is load-bearing:

The docstring explains why the middle one carries the weight:

"""**Why the per-guest quota is the load-bearing control.** The operator ruled
(2026-08-11) that the two-assistant-turn cap is per *conversation*; a guest may
start fresh trials. So the only thing bounding what one browser gets for free is
this quota -- and the mint throttle is what bounds how many `guest_id`s that
browser can hold.

**The quota counts rows, not cache entries.** ``ConversationSession.guest_id`` is
indexed, and a guest credential lives at most ``GUEST_TRIAL_TOKEN_TTL_SECONDS``
(12h), so "sessions carrying this guest_id" *is* the per-credential lifetime
count. That makes the primary control immune to a cache flush or a Redis outage,
and needs no new state."""

The per-IP caps use a fixed-window counter on the shared Django cache, which explainer #1 established is Redis logical database 1 (Celery's broker lives in db/0 and the agent's retrieval cache in db/2, precisely so that a Django cache.clear() — a FLUSHDB — cannot wipe either):

def incr_fixed_window(key: str, *, ttl_seconds: int) -> int:
    """Fixed-window counter on the shared Django cache (Redis db/1).

    ``incr`` never extends the TTL, so the window really is fixed. Raises
    whatever the cache backend raises -- each caller decides whether its cap is
    primary (fail closed) or best-effort (log and skip)."""
    try:
        cache.add(key, 0, ttl_seconds)
        return int(cache.incr(key))
    except ValueError:
        cache.set(key, 1, ttl_seconds)   # key expired between add() and incr()
        return 1

That one function is used with two opposite failure postures, and the choice is argued in each place. The mint throttle fails closed — "minting is the doorway to the whole trial surface", so an unreachable counter yields 503 guest_limits_unavailable rather than unlimited credentials (GuestMintScopedRateThrottle, guest_limits.py:212). The per-IP creation cap fails open — it is a secondary dimension over a forgeable value, and the row-counted quota behind it is unaffected, so an outage is logged and skipped (enforce_guest_trial_creation_limits, guest_limits.py:169, called from conversations/views.py:255).

IP handling deserves its own note, because the file is unusually honest about it:

"""**IP is best-effort, deliberately.** Prod is Cloudflare -> a standalone edge nginx
(out of this repo) -> app, so whether ``X-Forwarded-For`` holds the real client
address is an ops/edge decision, and a direct caller can forge it. IP therefore
only ever backs up an identity-keyed control, is sha256-scoped before it becomes
a cache key, and an unresolvable IP **skips** the per-IP cap instead of
collapsing every such caller into one shared bucket."""

Hashing the address before it becomes a cache key (guest_scope, guest_limits.py:114) means the counters and the refusal logs correlate one abuser's requests without ever storing a visitor's address. The refusals themselves speak a small vocabulary the client keys on — never on prose:

codestatusmeaning
guest_trial_quota_exhausted429this browser has started its allowance of trial conversations
guest_rate_limited429a rate cap tripped (mint per IP, create per IP)
guest_limits_unavailable503fail closed: the counter behind a primary control is unreachable

The numbers are settings, all with defaults that read as policy (settings.py:504–542): GUEST_TRIAL_TOKEN_TTL_SECONDS 12 hours, GUEST_TRIAL_SESSIONS_PER_GUEST 3, GUEST_TRIAL_SESSIONS_PER_IP_HOURLY 20, GUEST_TOKEN_MINT_THROTTLE_RATE "20/hour", and GUEST_TRIAL_SESSION_RETENTION_DAYS 7 for unadopted trial sessions. The 12-hour TTL has a stated reason worth repeating, because it shows the trial and the OAuth flow were designed together: "long enough for a real trial plus the OAuth round trip … short enough that it never becomes a durable anonymous identity".

Two neighbouring subjects belong to other explainers. The cap on how many assistant turns a trial conversation may have lives on the agent side (apps/agent/app/chat/guest_trial.py) with the rest of the safety machinery — explainer #11. And what happens when a guest signs in and their trial conversation follows them into the account — conversations/guest_adoption.py — is explainer #4.

6. How the agent recognises the same principal

Everything so far was Django. Now the same browser opens a chat stream at POST /agent-api/chat/stream, which is FastAPI — a different framework, a different process, a different database role. It gets the identical Authorization header, and it resolves it in apps/agent/app/api/dependencies.py without asking Django anything.

The core is _build_user_context (dependencies.py:124):

claims = jwt.decode(
    credentials.credentials,
    request.app.state.settings.jwt_shared_secret,
    algorithms=["HS256"],
    options={"require": REQUIRED_ACCESS_TOKEN_CLAIMS},   # ("exp", "token_type", "user_id")
)
if claims.get("token_type") != "access":
    raise unauthorized("Invalid authentication credentials.")

return AgentUserContext(
    user_id=_parse_user_id(claims, unauthorized=unauthorized),
    access_token=credentials.credentials,
    claims=dict(claims),
)

Three details repay attention. algorithms=["HS256"] is pinned rather than read from the token's own header — accepting the token's stated algorithm is the classic JWT vulnerability, in which an attacker submits alg: none or downgrades an RS256 token to HS256 and signs it with the public key. Requiring exp is likewise explicit, because a JWT library that is handed a token with no expiry claim will happily accept one that never expires. And _parse_user_id (dependencies.py:102) refuses a boolean before accepting an int, because in Python isinstance(True, int) is True and user_id: true would otherwise become user 1.

Note also what is kept: access_token=credentials.credentials. The agent holds on to the caller's raw token — the next section is why.

Chat has three possible credentials and demands exactly one (require_chat_caller_context, dependencies.py:347):

presented = [c for c in (credentials, service_token, guest_token) if c is not None]
if len(presented) > 1:
    raise _bearer_unauthorized("Provide exactly one authentication mechanism.")

Refusing ambiguity outright, rather than picking a winner by precedence, removes a whole class of confusion bugs where a caller presents two credentials and the server's choice is a surprise. The guest branch, _build_guest_trial_context (dependencies.py:306), mirrors the backend's verification — different framework, same three checks, and its docstring names the invariant:

"""Deliberately NOT `_build_user_context`: that one requires a `user_id` claim
and would resolve a user principal. A guest token resolves to an identity
(`guest_id`) and nothing else -- it can never become a user."""

A fourth entry point exists for the retrieval API: require_retrieval_caller_context (dependencies.py:188) accepts either a user bearer JWT or an X-Agent-Api-Key matched against a configured key map with compare_digest — the seam for external integrations reading the corpus without being a person.

The point of the whole arrangement

The agent authenticates locally, so a chat turn costs zero identity round trips. But it does need to write the conversation back into Django's tables, and at that moment it faces a choice: use its own service token, or carry the caller's credential. Explainer #2 established the answer at apps/agent/app/chat/backend.py:516–540, where three header builders sit side by side and _conversation_request_headers picks one:

"""Pick the caller credential for a conversation detail/message call.

* first-party turn -> the user access token (bearer);
* P68 anonymous trial turn -> the caller's own guest token, FORWARDED as-is.
  The agent does not substitute the service token here on purpose: the
  backend then scopes the lookup to that token's `guest_id`, so cross-guest
  isolation is enforced at the backend chokepoint rather than trusted to the
  agent;
* dormant changple_web BFF guest turn -> the service token."""

Authorization stays at the service that owns the data. The agent could open any conversation with its service token; instead it re-presents the caller's own credential, so Django's ownership rules run exactly as they would for a direct request. The route's own comment in chat.py puts it best: "the backend — not this route — decides which sessions it may reach." Verifying a token locally is a performance decision; forwarding it is a security decision, and the two are independent.

7. Entitlements — what the name is allowed to do

We arrive at authorization. accounts/entitlements.py is 132 lines and its core is almost anticlimactic:

@dataclass(frozen=True, slots=True)
class Entitlements:
    tier: str
    is_paid: bool


def get_entitlements(user: Any) -> Entitlements:
    """Resolve a user's current entitlements from their DB-authoritative tier.

    No caching, no JWT claim involved -- always reads `user.tier` fresh."""
    tier = getattr(user, "tier", User.Tier.FREE)
    return Entitlements(tier=tier, is_paid=tier == User.Tier.PRO)

That is the seam. Not because the mapping is complex today — it is one comparison — but because having one named function that every paid-feature check calls means the day a second paid tier or a one-off purchase arrives, there is a single place to change and a single grep target. The module says so: "Grep target for later phases: get_entitlements." It is also where the "no caching, no JWT claim" rule is stated in code rather than in a comment somewhere else.

The read-side gate

The one substantial policy in the file is the chat thinking-level gate, and it is a good example of a general problem. A Pro user picks the high effort level, which is stored in User.chat_thinking_level. Later they cancel. What should happen to the stored value?

Clearing it on downgrade sounds right and is a trap: subscriptions end in many ways — explicit cancel, expiry, a failed renewal, a refund, an operator edit — and every one of those paths would have to remember to clear the column. Miss one and a free user keeps a paid feature, silently. So changple5 inverts it: the column is never cleared, and the gate lives on every read.

PRO_ONLY_THINKING_LEVELS: tuple[str, ...] = ("high",)

def resolve_effective_chat_thinking_level(user: Any) -> str | None:
    """THE ONLY READER of `User.chat_thinking_level`. The stored value is never
    cleared on a tier downgrade (there are more downgrade sites than a hook can
    cover), so the gate lives here on the read side instead: a Pro-only level
    held by a non-paid user resolves to `None` -- i.e. unset, fall through to
    the operator/env ladder -- while the stored value survives for a later
    re-subscribe."""
    level = getattr(user, "chat_thinking_level", None) or None
    if level is None:
        return None
    if level in PRO_ONLY_THINKING_LEVELS and not get_entitlements(user).is_paid:
        return None
    return level

Gate on read, not on write. One chokepoint that every reader must pass beats n cleanup hooks that every future downgrade path must remember. It fails safe by default, and it preserves the user's preference so that resubscribing restores their setting instead of silently resetting it. The declaration "THE ONLY READER" is enforceable by grep, which is what makes the claim maintainable.

The resolved value is the top rung of a ladder; resolve_service_default_chat_thinking_level (entitlements.py:86) supplies the rest:

Its docstring notes the same never-fail posture used by every config read in the codebase: a DatabaseError is logged and treated as an absent row, and the function never returns None because the UI would have nothing to show.

Where a decision is actually made, on both sides of the bridge

ChatPreferencesView (views.py:208) is get_entitlements's first production caller, and its docstring is a small lesson in HTTP semantics:

"""The gate is in the view body on purpose, not in a permission class: it is
**value-dependent** (a free user setting ``medium`` is legitimate; only a
``PRO_ONLY_THINKING_LEVELS`` member is refused), and a permission class runs
before the payload is known. Order is validate -> authorize, so an unknown
value is a **400** and a locked level on a non-paid tier is a **403** -- an
authorization refusal is not a validation error.

``request.user`` is the DB row loaded by JWT authentication, so the tier read
here is DB-authoritative; the JWT ``tier`` claim is a presentation hint only
and is never consulted."""

And the same rule holds on the agent side, where there is no request.user at all. When a chat turn needs the user's effort level, apps/agent/app/chat/user_thinking_level.py does a per-turn point read across the read bridge:

SELECT tier, chat_thinking_level FROM "backend"."accounts_user" WHERE id = %s
...
if level in PRO_ONLY_THINKING_LEVELS and tier not in PAID_TIERS:
    ...  # -> None

It holds the bearer token that already contains a tier claim, and it queries the database anyway. Its docstring explains both halves: the gate is re-applied here as "defense in depth", with the backend named as the source of truth; and there is emphatically no cache, because llm_config.py's snapshot is process-wide and keyed by role, so a per-user value placed in it would leak one user's setting to every user that worker serves.

Quiz

Five questions. Click an option to see whether it is right and why.

1. A user pays for Pro at 10:00. Their access token was issued at 09:45 and still carries "tier": "free" until it expires at 10:15. Why does no paid feature refuse them in the meantime?

The claim is a presentation hint for the browser's badge and nothing else — tokens.py says so, and grepping the repository finds no server-side consumer. get_entitlements reads user.tier fresh, and the agent's user_thinking_level.py does its own SELECT tier, chat_thinking_level per turn rather than trusting the token it is holding. restamp_tier_on_refresh exists to keep the hint honest, not to make anything correct.

2. There is no table of password-reset tokens anywhere. What actually stops a reset link from working a second time?

password_hash_fingerprint (email_tokens.py:105) is a truncated sha256 of user.password, carried in the token as fp and re-checked in _resolve_reset_token_user. Binding the token to state that the action itself mutates gives single use, invalidation of every older link, and invalidation on any unrelated password change — with no storage at all.

3. A guest token is signed with the very same JWT_SHARED_SECRET as a user access token. Why can it never be used as one?

Access verification requires token_type == "access" and a user_id; guest verification requires token_type == "guest", a guest_id, and explicitly refuses any token carrying a user_id. The separate header solves a different problem — SimpleJWT raises on a non-access bearer token, which would end the authenticator chain before the guest authenticator could run.

4. A first-party chat turn hits POST /agent-api/chat/stream and the agent then needs to persist the messages into Django's tables. Which credential does it use for that write-back, and why?

_conversation_request_headers picks the caller's own credential — the bearer JWT for a first-party turn, the guest token forwarded as-is for a trial turn — and keeps the service token for calls with no human caller, such as the indexing hand-off. Verifying locally is a performance decision; forwarding is a security one. The bridge is also SELECT-only, so option two is impossible.

5. Redis becomes unreachable. What happens to POST /api/auth/guest-token and to an existing guest starting a new trial conversation?

The two caps have deliberately opposite postures. GuestMintScopedRateThrottle fails closed — minting is the doorway to the whole trial surface, so unlimited credentials are worse than a refusal. The per-IP creation cap is a secondary dimension over a forgeable value, so an outage there is logged and skipped; the load-bearing control is the per-guest_id quota, which reads rows rather than cache entries and is therefore immune to the outage.
