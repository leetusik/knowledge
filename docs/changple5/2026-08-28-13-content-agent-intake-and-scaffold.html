Background

Two job tables, one screen

Open /operator/miracle-agent in the changple5 operator console and you are looking at the content agent: the machine that turns the operator's raw material into a published article on 창플. There are two generations of it in the repository, and telling them apart is the first thing to get straight, because both still exist and both still have tables.

  • v1 — ContentDraftJob (built in P30/P52). It lives in apps/backend/content/models.py with a handful of draft_*.py modules (draft_dispatch.py, draft_publish.py, draft_views.py) and an agent-side service in apps/agent/app/content_drafts/. It is superseded but still routed: draft_views.py still calls queue_draft_generation_on_commit/requeue_draft_generation_on_commit, which still send the Celery task named content.generate_draft. Explainer #15 covers it. This page names it once and moves on.
  • v2/v3 — ContentAgentJob (built in P54, then reworked across P72–P82). It lives in its own package, apps/backend/content/agent_jobs/ — 57 modules and about 40,000 lines, by a wide margin the largest subsystem in this repository. This is what the console actually runs today, and it is the subject of this page and the next one.

A fact about the deployment, not about the code

The 미라클 에이전트 console ships to production but is unexercised there: there is no operator account on the production instance yet, so every job that has ever run has run on the development stack. Nothing below is speculative — it is all real, tested, deployed code — but if you go looking for production job rows you will not find many.

The product story

창플 publishes long-form articles about the real, unglamorous business of running a franchise outlet: what a founder actually decided, what it cost, what went wrong. The raw material for such an article is not an interview transcript and not a blog draft. It is two things the operator already has:

  1. Published Naver cafe posts — the corpus explainer #8 built by scraping, and explainer #9 turned into vector chunks. Here they are read as project records: partial, out of order, written by several people over months.
  2. KakaoTalk conversation exports — the operator's own chat rooms with the founder, exported from the phone as a .zip containing a .txt transcript and whatever photos KakaoTalk still had. This is where the 고민 and the 의사결정 live, the material that never made it into a public post.

The agent reads both, and then — and this is the design decision that shapes the whole subsystem — it does not write the article. It produces a 구성안: a composition proposal listing the core message, the sections with their headings and target lengths, the evidence each section rests on, and (since P74) which photos and conversation excerpts go where. The operator reads that proposal, edits it, and approves it. Only then does anything write prose.

Vocabulary you will need

  • 구성안 — the composition proposal. A JSON document with a core message and an ordered list of sections. Produced by the "architect"; approved by the operator.
  • 절 (unit) — one section of the 구성안.
  • 가이드 — the content standard, a versioned Korean markdown document that tells the agent what a 창플 article is allowed to be. It rides inside the prompts.
  • 제안 turn — one run of the proposal pipeline: analysis workers, then the architect call, then the recorded proposal.
  • 승인 (approve) — the operator's one gate. This page ends the moment before it.

Intuition

The big idea: the state machine is data, and the data is checked before the app can boot

A subsystem of 40,000 lines needs a spine, and here the spine is 606 lines long: apps/backend/content/agent_jobs/states.py. It contains no logic about photos, prompts, zip files or Gemini. It contains a list of legal moves:

Transition(
    JobState.PROPOSING,
    "proposal_ready",
    JobState.NEEDS_REVIEW,
    Actor.SYSTEM,
    Kind.ADVANCE,
)

Twenty-nine of these, over fourteen states. Nothing else in the codebase is allowed to write job.state — one function, services.transition(), looks the move up in that table and refuses if it is not there.

The part worth internalising is what happens at import time. The last statement in the module is:

TRANSITION_INDEX: dict[tuple[StateName, str], Transition] = _validate_table()

_validate_table() walks the table and asserts three design invariants. If any of them fails, importing the module raises AssertionError — which means Django cannot start, the worker cannot start, and the test suite cannot even collect. An illegal edge is a startup error, not a runtime bug. You cannot ship a state machine that contradicts its own design and discover it in production three weeks later, because the process will not boot.

That is a pattern worth stealing. Configuration-as-data is common; configuration-as-data with its invariants asserted at import is what makes it trustworthy. Everything else in this subsystem — nine LLM passes, a zip parser, a media matcher — is allowed to be messy precisely because the thing that decides what may happen next is small, declarative and mechanically checked.

A toy job to carry through

Take one imaginary job and follow it to the end of the page.

ContentAgentJob
  id          7f3a1c9e-…            (uuid pk)
  label       "행복한 김밥 강남점 3월"
  brand       행복한 김밥            (FK, exactly one brand per job)
  scope_mode  "branch"              (지점 선택 / 지점 미지정 / 브랜드 전체)

The operator picks four Naver cafe posts from that brand's corpus, uploads one KakaoTalk export, and presses 구성안 만들기. The KakaoTalk .txt inside the zip looks like this (four records — the real export from the operator's own phone had 389):

2024. 3. 12. 오후 2:10, 김세연 : 사장님, 지난주 매출은 어떠셨어요?
2024. 3. 12. 오후 2:12, 박정우 : 주말에만 30% 올랐어요. 점심 세트를 바꾼 게 컸습니다.
2024. 3. 12. 오후 2:13, 박정우 : 사진 2장
2024. 3. 12. 오후 2:15, 박정우 : 파일: 3월_원가표.xlsx

Beside it in the zip: 20240312_141305_001.jpg and 20240312_141305_002.jpg. There is no 3월_원가표.xlsx — KakaoTalk's export drops file attachments entirely, and drops older photos too. In the operator's real sample, 125 photos were referenced and 53 were present (~42%), and every one of the 19 파일: attachments was missing.

By the end of this page that raw material has become four normalized message rows with stable ids, a conversation boundary seg:5:1-4, two matched photos and one missing file reference, an immutable snapshot of every input, and a 구성안 document sitting in needs_review waiting for a human.

Snapshot, not lock

The second idea to hold on to is subtle and it changed once, in P79. Pressing 구성안 만들기 takes a snapshot of the inputs — a canonical JSON payload, hashed with SHA-256, stored in an immutable ContentAgentInputRevision row. Every downstream stage reads its inputs from that row rather than from the live tables.

But it does not lock anything. The operator can keep editing the selection while the proposal is being generated. The button's own served helper sentence says so:

SCAFFOLD_HELPER_SENTENCE = (
    "구성안을 만드는 동안에도 입력은 계속 고칠 수 있습니다 — 잠기는 것은 없습니다."
)

Which raises an obvious question: if the inputs kept moving, how does the screen know that the proposal you are looking at is out of date? Answer: it hashes the inputs again and compares. That one comparison — inputs_fingerprint(job) != frozen.content_hash — is the entire mechanism behind the sentence «구성안은 2024-03-12의 입력으로 만들어졌습니다.» No change-tracking table, no dirty flags, no write hooks. Two hashes.

Code

Everything below is real code in apps/backend/content/agent_jobs/ unless another path is given. Line numbers were verified on 2026-08-28.

1. The spine: a state machine that is data

Two files, 1,074 lines together, and they are the ones worth reading whole: states.py (606) holds the vocabulary and the table; services.py (468) holds the only writer and the retry semantics.

Provenance, stated in the file

states.py's module docstring is unusual and instructive: it says where every state came from. This subsystem was built through a design co-work process in which each "round" produced a signed implementation contract, and the docstring names the round and section for each edge — round 12 (proposing → needs_review → writing → integrating → draft_ready, the capped-retry failure question, and «There is no cancelled»), round 13 (publishing → published, and «Failures never advance state»), round 19 (the shrink). Then one honest exception:

**P81.S8 — a fourteenth token, and the only one not from a round.** 조정
(``adjusting``) is the operator's optional placement step between 초안 and 발행 …
Round 19's "five rows, always" reads **six** from here on — a deliberate,
recorded departure, not a silent edit.

A state machine that records which of its states are not from the design record is a state machine you can trust when it says the other thirteen are.

The ladder

JobState (states.py:77) is a Django TextChoices enum with fourteen members. Executing the module and counting gives exactly:

intake · processing · ready · needs_answer · proposing · needs_review ·
writing · integrating · draft_ready · approved_unpublished · adjusting ·
publishing · published · failed          → 14 states, 29 transitions

Two of those tokens are dead but kept

processing and ready are produced by nothing. They were the verdicts of 사전 점검 — a preflight run that P79 deleted. They survive because round 19 still prints a rail word for each and because legacy rows in the database still hold them. A new job simply stays in intake until 구성안 만들기. This matters when you read the table: they appear only as sources of request_scaffold, never as targets.

The shape of an edge

A Transition (states.py:245) is a frozen dataclass with seven fields: source, trigger, target, actor, kind, an optional guard, and a human note. The two enum-ish helper classes beside it are the interesting part:

  • Actor (:228) — OPERATOR or SYSTEM. Eighteen edges are operator-triggered, eleven are system-triggered. An operator edge attempted without an operator raises ActorRequired.
  • Kind (:233) — ADVANCE (14 edges), RECOVER (2), FAILURE (7), GATE (5), CANCEL (1). kind is not decoration: _validate_table uses it to enforce an invariant, and the append-only history log records it.

Exactly one guard survives in the whole machine:

GUARD_SCAFFOLD_REVISION_APPROVED = "scaffold_revision_approved"   # states.py:261

It hangs off needs_review --approve_scaffold--> writing, the one human gate left, and its implementation (services.py:115) refuses on two named blockers: scaffold_revision_not_approved (no approved revision row) and change_list_not_seen (there is one, but the operator never saw the list of what changed). P79 retired the other three guards along with the surfaces they gated.

The three invariants, enforced at import

_validate_table (states.py:520) is the heart of the design. Quoting the docstring's own numbering:

1. **No stop, no cancel outside ``proposing``.** There is no ``cancelled``
   state, and ``cancel`` is legal from exactly one state (round 12 §5.3:
   "Cancel exists only in ``proposing``"). Its target is now ``intake``: with
   the freeze retired there is nothing to fall back *to* but the inputs, which
   were editable the whole time anyway.
2. **Failures never advance state.** A ``failure``-kind edge may never raise the
   lifecycle order of the job and may never reach ``published``.
3. **``approved_unpublished`` and ``published`` are both arrivals** — 초안 저장 is
   a destination (「미발행 초안」), not a half-finished publish.

And the checks themselves, in code:

if transition.kind == Kind.FAILURE:
    if transition.target == JobState.PUBLISHED:
        raise AssertionError(f"failure transition {key} reaches `published` — "
                             "failures never advance state")
    source_order = LIFECYCLE_ORDER.get(transition.source)
    target_order = LIFECYCLE_ORDER.get(transition.target)
    if (source_order is not None and target_order is not None
            and target_order > source_order):
        raise AssertionError(f"failure transition {key} advances the lifecycle …")

cancel_sources = {t.source for t in TRANSITIONS if t.kind == Kind.CANCEL}
if cancel_sources != {JobState.PROPOSING}:
    raise AssertionError("cancel exists only in `proposing` (round 12 §5.3) …")
if "cancelled" in states:
    raise AssertionError("there is no `cancelled` state (round 12 §4)")

Plus three structural checks: no duplicate (source, trigger) key, no unknown state, and — added by P79 — no stranded state: every token must be both reachable and leavable, with published the single permitted terminal. That last check is why the request_scaffold edge has four sources rather than one: processing and ready are dead, but a legacy row sitting in one of them still needs a way out, and the assertion refuses to let you forget.

Two more assertions insist that STATE_PILL and STATE_LABELS — the pill colour family and the Korean word each state prints — cover exactly the vocabulary. Add a state, forget its label, and the app does not start.

The design lesson: states are a liability

P79.S3 shrank this machine from 21 states and 56 edges to 13 and 23 (P81.S8 later added 조정, making it 14 and 29). What was deleted: 사전 점검 (the preflight run and its blocked verdict), the 작업 시작 · 입력 고정 Start gate and its frozen state, the whole audit-and-auto-repair family (audit_running · audit_failed · repairing · awaiting_operator), and the 수정지시 / 구성안 재개방 paths (revising · reopened). The trigger was one operator sentence: «the process is overcomplicated».

Note the direction of travel. The machine got smaller as the product got clearer. Every state is a promise that some screen can render it, some transition can leave it, and some human knows what it means; the honest move when a surface dies is to delete its tokens too.

services.transition() — the only writer

services.py:137. Every state change in the subsystem goes through this one function, and its shape is worth copying:

with transaction.atomic():
    locked = ContentAgentJob.objects.select_for_update().get(pk=job.pk)
    edge = find_transition(locked.state, trigger)
    if edge is None:
        raise IllegalTransition(f"`{trigger}` is not legal from `{locked.state}` …")
    if edge.actor == Actor.OPERATOR and actor is None:
        raise ActorRequired(…)
    for guard in _edge_guards(edge):
        blockers = guard_blockers(guard, locked, context)
        if blockers:
            raise TransitionBlocked(guard, blockers)

    from_state = locked.state
    locked.state = edge.target
    …
    locked.save(update_fields=[…])
    ContentAgentJobTransition.objects.create(
        job=locked, from_state=from_state, to_state=edge.target,
        trigger=trigger, kind=edge.kind, actor_kind=edge.actor,
        actor=actor, note=note[:255], context=context,
    )

Four things happen here that are each deliberate. The row is re-read under select_for_update(), so the state the guard checks is the state on disk and two concurrent callers cannot race the same job. The refusals are typed — IllegalTransition, ActorRequired, TransitionBlocked (which carries a machine-readable blockers list) — so the HTTP layer maps them to distinct responses instead of a generic 400. The history row is written inside the same transaction, so a state change without its audit entry is not representable. And the guard registry fails closed:

def guard_blockers(name, job, context=None) -> list[str]:
    fn = _GUARDS.get(name)
    if fn is None:
        return [f"guard_not_implemented:{name}"]     # deny, with a name
    return list(fn(job, context or {}))

An unregistered guard denies its edge rather than silently allowing it — which is what let earlier slices declare a gate before the slice that computed it had landed.

Stage attempts: the retry budget (D56)

LLM stages fail. The design's answer, recorded as deferred job D56 and absorbed into the machine, is that a failed stage re-runs in place, on the same job, over the same input snapshot — never by creating a second job — and after a capped number of attempts it stops and asks a human.

MAX_STAGE_ATTEMPTS = 2        # services.py:49

The cap counts attempts, not extra retries, because the console literally prints «시도 n / 최대 2» and the printed string is the contract. Four functions implement it:

FunctionWhat it does
start_stage_attempt (:349) Opens attempt N of a stage over job.frozen_input_revision. Raises ValueError if there is no snapshot yet, and StageAttemptsExhausted (:76) at the cap.
finish_stage_attempt (:384) Stamps the attempt succeeded or failed with an error code, and stores its payload.
attempts_remaining (:344) MAX_STAGE_ATTEMPTS - count(attempts for this stage+unit), floored at 0.
fail_stage (:424) The whole of D56 in one call: finish the attempt, then take stage_retry (budget remains) or stage_capped (exhausted).

fail_stage looks the pair of triggers up in a small map so no stage invents its own vocabulary:

STAGE_FAILURE_TRIGGERS: dict[str, tuple[str, str]] = {
    str(JobState.PROPOSING):   ("stage_retry", "stage_capped"),
    str(JobState.WRITING):     ("unit_retry",  "unit_capped"),
    str(JobState.INTEGRATING): ("stage_retry", "stage_capped"),
}

stage_retry is a self-loop: proposing → proposing. The job does not move, the frozen inputs do not move, the id does not change — the failing unit simply runs again. And crucially, work already done is not thrown away: a worker that already succeeded is reused from its stored attempt payload (architect._reuse_analysis, architect.py:691). At the cap, stage_capped moves the job to needs_answer and a human is asked.

Why the operator's 다시 시도 gets a fresh budget

If attempts were counted per stage forever, the operator's «다시 시도» button would be a lie the second time it was pressed — the counter would already be at 2. So attempts are scoped to the turn:

def proposal_turn(job) -> int:                       # architect.py:658
    return max(job.transitions.filter(
        trigger__in=("request_scaffold", "propose_scaffold", "resume_scaffold")
    ).count(), 1)

def _unit_key(base: str, turn: int) -> str:          # architect.py:679
    if turn <= 1:
        return base
    return f"{base}@{turn}" if base else f"turn{turn}"

The turn number is derived from the append-only transition log — no counter column. Every entry into proposing (a fresh 구성안 만들기, a 다시 만들기, or a resume_scaffold out of needs_answer) increments it, and the unit key becomes post@2, conversation@2, and so on. Fresh key, fresh budget. And nothing is ever deleted — every ContentAgentStageAttempt row from every turn stays as the audit trail.

The snapshot, and its hash

freeze_input_revision (services.py:220) writes the immutable input revision. Its docstring records the P79 change of meaning in as many words:

**P79.S3 re-homed this act.** It used to be the Start gate's freeze, and it
locked the intake; the gate is gone and nothing locks … What survives is the
snapshot itself, because every downstream stage reads its inputs from
``job.frozen_input_revision.payload`` (the architect packet, the build brief,
``start_stage_attempt``'s D56 anchor).

Immutability is enforced rather than trusted: re-freezing an already-frozen row raises ValueError("an input snapshot is immutable — write the next one"). The identity of a revision is canonical_hash (services.py:209):

def canonical_hash(payload) -> str:
    encoded = json.dumps(payload, sort_keys=True, ensure_ascii=False, default=str)
    return hashlib.sha256(encoded.encode("utf-8")).hexdigest()

Sorted keys, no ASCII escaping (the payload is full of Korean), default=str so datetimes and UUIDs do not explode. The same function hashes scaffold revisions and chat revisions, so "is this the same thing?" has exactly one answer everywhere in the subsystem.

models.py (612 lines) holds seven tables. Their arrangement around our toy job:

Two details are worth pausing on.

The FK to the published article points from the job at the content, not the other way round. ContentAgentJob.published_content (:181) is a nullable ForeignKey("content.NotionContent", on_delete=SET_NULL, related_name="source_agent_jobs"). Explainer #12 established this direction: v1 has the mirror field ContentDraftJob.published_content with related_name="source_draft_jobs", and a hand-uploaded article has nothing to be null about. The KakaoTalk tables live next door, on purpose. chat_models.py (590) holds six more: ContentAgentChatArchive (the uploaded .zip and its named validation steps), ContentAgentChatRevision (the immutable normalized conversation, hashed with the same canonical_hash), ContentAgentChatMessage (one record, with a stable 1-based contiguous message_id that is never renumbered), ContentAgentChatMedia (one extracted image), ContentAgentChatMediaRef (the materialized reference↔file join), and ContentAgentChatSegment (one conversation boundary). models.py's own docstring reserves those tables for that module and says «do not widen these models to hold their data» — a stated seam, kept.

And a third file you should recognise but never read: legacy_models.py (198 lines), which its docstring calls history, with no reader. It holds the two tables round 19's deletion left behind (content_contentagentpreflight, content_contentagentauditrun). They stay registered with Django not out of tidiness but because a table Django does not know about while it still carries a FK to content_contentagentjob breaks TRUNCATE-based operations — including Django's own test teardown, which fails with «cannot truncate a table referenced in a foreign key constraint».

3. Intake I — the raw material: posts

Two modules, and one architectural fact that surprises people.

v2 never calls /agent-api

Grep-verified: apps/backend/content/agent_jobs/ contains zero references to agent-api, AGENT_BASE_URL or X-Agent-Service-Token. Post selection is plain Django querysets straight over DocumentSource — explainer #8's corpus — not explainer #7's retrieval chokepoint. And the LLM calls in this subsystem are made from Django itself, with langchain_google_genai, not by asking the FastAPI agent. The agent service owns the chat read path; the content agent is a backend-side pipeline that happens to call the same provider.

scope.py (605) answers "which posts belong to this job?". All three scope modes are a call into documents.brand_lookup.brand_documents() — membership is never re-derived here:

def scope_queryset(job, *, include_suspect=False):              # scope.py:84
    if job.scope_mode == ContentAgentJob.ScopeMode.BRANCH:
        return brand_documents(job.brand_id, branch=job.branch_id, …)
    if job.scope_mode == ContentAgentJob.ScopeMode.UNASSIGNED:
        return brand_documents(job.brand_id, branch_unassigned=True, …)
    return brand_documents(job.brand_id, …)

Note the third mode: 지점 미지정 is its own mode (branch_unassigned=True), not branch=None — which means 브랜드 전체. Conflating them would silently widen a pre-opening job's scope to the whole brand.

brand_universe_queryset (:110) is everything linked to the brand, 자동 · 의심 rows included: "the outer bound of what an operator may accept". Between the two sits the 범위 밖 제안 panel (out_of_scope_suggestions, :537, SUGGESTION_LIMIT = 20 at :78) — posts the operator can see but that are not members, each labelled with why:

REASON_OTHER_BRANCH      = "other_branch"        # scope.py:66-68
REASON_BRANCH_UNASSIGNED = "branch_unassigned"
REASON_AUTO_SUSPECT      = "auto_suspect"

OUT_OF_SCOPE_REASONS = {
    REASON_OTHER_BRANCH:      "다른 지점",
    REASON_BRANCH_UNASSIGNED: "지점 미지정",
    REASON_AUTO_SUSPECT:      "자동 · 의심",
}

The module docstring is emphatic about what this is not: «There is no corpus-wide lexical pass, and nothing here selects anything: acceptance is an explicit operator act.» The agent proposes; it never absorbs. When the operator does accept one, the row is written with Source.OUT_OF_SCOPE plus the reason it was outside, who accepted it and when.

selection.py (549) is the write side, and it is where the editability rule lives:

SELECTION_MIN = 1        # selection.py:46
SELECTION_MAX = 20       # 1–20 posts per job

EDITABLE_STATES: frozenset[str] = frozenset(…)                  # :80

paused_in_proposal is the P79 rule in one predicate: a job sitting in proposing is still editable, because the freeze is a snapshot and not a lock. Refusals are machine codes — selection_cap_exceeded, post_out_of_scope, unknown_post_id, selection_below_minimum, selection_not_editable — never prose the client has to parse.

4. Intake II — the KakaoTalk chain

This is the part of the subsystem with the most surface area and the most interesting engineering: roughly ten modules turning an untrusted .zip from someone's phone into selectable, citable conversation units. Follow our four toy messages through it.

4.1 The zip is untrusted input

chat_archive.py states two rules and both are load-bearing:

1. **Inspect before extracting.** Every check below reads the archive's central
   directory (and at most a 12-byte header per member) — nothing is written to
   disk until the archive has passed.
2. **Rejected files are not stored** (round 11 §4.3). Every rejection path in
   ``chat_intake.py`` deletes the quarantine, so a refused upload leaves a row
   carrying its machine reason and no bytes anywhere.

Five machine rejection reasons (:53-57): unsupported_format, encrypted_member, path_unsafe, ratio_exceeded, type_not_allowed. The budgets behind them (:117-125):

DEFAULT_MAX_MEMBERS           = 5_000
DEFAULT_MAX_EXPANDED_BYTES    = 2 * 1024 * 1024 * 1024      # 2 GiB
DEFAULT_MAX_COMPRESSION_RATIO = 120
DEFAULT_MAX_ARCHIVE_BYTES     = 100 * 1024 * 1024           # 100 MiB

TEXT_EXTENSIONS  = frozenset({".txt"})
IMAGE_EXTENSIONS = frozenset({".jpg", ".jpeg", ".png", ".gif", ".webp"})

The compression-ratio budget is the zip-bomb guard, and there is a pointed note about what is not reused: content/importers.py's _extract_archive recursively expands every nested .zip it finds with no depth or size budget. Here a nested archive is rejected instead.

Two refinements that only show up when real people use a thing. First, a non-allow-listed member is skipped, not fatal (an operator ruling from 2026-08-23): real KakaoTalk exports carry .mp4 videos, audio, PDFs, .vcf contacts, and refusing the whole export over one of them made ordinary archives unusable. Those members are never extracted, and the inspect step reports them as skipped_files / skipped_extensions so the operator can see what was left out. type_not_allowed survives for the two real attack shapes: a nested archive, and image-named bytes that are not an allowed image (checked by sniffing a 12-byte header, not by trusting the extension).

Second, and my favourite bug-that-was-anticipated:

Korean member names are handled explicitly. ``zipfile`` decodes a member name as
UTF-8 only when general-purpose flag bit ``0x800`` is set and otherwise falls
back to **CP437**, so a Windows-client export with CP949 names arrives as
mojibake unless the bytes are recovered. ``decoded_member_name`` does that
recovery (CP437 round-trip is lossless — the codec maps all 256 byte values).

4.2 Parsing the transcript: measured, not guessed

kakao_txt.py is 319 lines of pure functions with no Django import, and its docstring opens with a claim it then backs up: «The contract implemented here is measured, not guessed» — an earlier slice read the operator's own export byte for byte and wrote the format down.

The load-bearing discovery is about line endings:

**The record separator is CRLF; user line breaks are bare LF.** … the *last*
physical line of every record ends ``\r\n`` while a line break the sender typed
inside a message ends ``\n``. So records split deterministically and 114 of 389
records in the real file are multiline. A parser that instead asked "does this
line start with a timestamp?" would be wrong by design — a user can type a
date-shaped line, and one did not have to for the guess to be unsound.

Everything else follows: UTF-8 with a BOM; line 1 is the filename, line 2 is 저장한 날짜 : …; date separators (2023년 9월 1일 금요일) sit on their own record; a message record is 2023. 9. 1. 오후 4:24, 김세연 : <text>; a system record has the same timestamp followed by a colon and no sender. Timestamps are Korean 오전/오후 12-hour, resolved in KST = ZoneInfo("Asia/Seoul"), and they are minute-granular — remember that, it matters in a moment.

4.3 Storing it: five named steps, and a 30-minute reclaim

chat_intake.py orchestrates. 4.5 Matching photos to references — a scored join, not a lookup

Here is the mismatch chat_matching.py exists to bridge: the archive's image filenames carry send time to the second (YYYYMMDD_HHMMSS_<seq>.<ext>) while the transcript's timestamps are minute-granular. And the export is systematically incomplete.

4.6 LLM pass 1 — cutting the room into conversations

Until P73, conversation units were derived by a pure rule: cut at a gap of one day or more, recomputed on every read. P73 replaced it with an LLM that reads the messages and draws topic boundaries, so a same-day stream may split and a multi-day thread may stay whole. The old rule was deleted, not kept as a fallback — «a hidden day-gap fallback would resurrect it invisibly while the panel's label says 맥락 기준».

That single change forces the module's four decisions:

  1. Boundaries are persisted. An LLM is not a pure function, so a recomputed boundary could drift between two reads and silently drop the operator's selection. ContentAgentChatSegment stores them and chat_conversations.units() serves nothing else.
  2. Its own packet builder, windowed with carry-over. SEGMENTATION_WINDOW_CHARS = 80_000 per window, MAX_WINDOWS = 12 (~960k characters), and every window after the first restarts at the first message of the previous window's last boundary, so a conversation straddling a window edge is re-read whole. A progress guard closes a trailing segment at the edge when it alone would exceed half a window, so the loop always advances. It is pointedly not the architect's analysis.CHAT_PACKET_CHARS, which describes a different stage over a different revision and simply drops the overflow.
  3. Contiguous and total, always. The writer keeps only the cut points the model returned, snaps them to real message ids, and rebuilds the spans from them — so overlaps, holes and reversed ranges cannot survive into the table.
  4. All-or-nothing, failing open. Any window that fails drops the whole segmentation to a single whole-room boundary. Coverage is never partial, and the panel is never empty while messages exist.

Each segment records where it came from: source ∈ {initial, agent, fallback} — initial being the whole-room substrate written at parse time, which is rewritable precisely because nothing has been picked on top of it yet (can_write_boundaries, :213, refuses a rewrite once any seg: selection exists).

And one hard cap that is a lovely piece of product engineering:

#: **P81.S6 — how long an automatically drawn conversation may be, in SPOKEN
#: messages** (``kind != system``…)
#: … the fix is a **deterministic cap at segmentation** rather than a prompt
#: line an LLM may ignore on a bad day.
#: Measured on dev before the change: 103 agent segments, median 9 spoken, max
#: 35, and the *placed* captures ran {3,10,10,11,12,13,13,15,19,22,22,28,33,35}
#: — the 19–35 tail is what the operator is complaining about.
SEGMENT_MAX_SPOKEN = 15

The complaint was "published conversations are too long to read in one glance". The response was not a sentence added to a prompt; it was a measurement of the actual distribution, a number that trims the tail without touching the median, and a server-side cut applied after the model answers. Note also that the cap counts spoken messages: join/leave/invite system lines are not part of a reader's burden.

4.7 LLM pass 2 — which conversations are worth using

chat_pick.py reads each context unit against the job's own 콘텐츠 가이드 and pre-selects the ones worth writing about, with a Korean prose reason for the units it picked and the units it did not. Five decisions, and three of them generalise well beyond this codebase:

  • It is a post-ready follow-on, never a sixth parse step. It runs on its own record (an agent_pass row) instead of inside ContentAgentChatArchive.steps. That keeps the panel live while the pass runs, and it keeps an LLM failure from ever reading as a failed .zip.
  • One guide read, recorded. The version is resolved once at pass start and the label is stored on the record, so the UI prints what was actually read rather than a fresh resolve that could have drifted. What rides in the packet is that version's 선별 기준 chapter (SELECTION_CHAPTER = "14"), falling back to the whole body for versions that predate the chapter. No guide row ⇒ the pass does not run at all.
  • It writes through the existing whole-selection write — chat_conversations.set_selection(..., picked_by="agent"). There is one selection state, not a proposal state beside it.
  • No-clobber: the write is proposal ∪ operator_touched_selected \ operator_touched_unselected, computed by agent_pass.merge_no_clobber from durable provenance stamps. A pass landing on top of the operator's own picks changes none of them.
  • Fail open, everywhere. Missing key, unreachable provider, malformed return, fallen-back segmentation — all land on state = "failed" with no selection write at all, and the panel keeps every control it had.

Packet budgets: PICK_UNIT_CHARS = 2_500, PICK_MESSAGE_CHARS = 300, PICK_PACKET_CHARS = 60_000.

Provenance is durable, not a wall clock

The no-clobber algebra only works because every selection write stamps picked_by (operator or agent) on the rows it actually changes. A row that was already selected keeps whoever picked it — which is what lets the UI say «직접 고름» about a row the agent's later write merely left standing. Provenance in a column survives a worker restart and needs no session state; provenance in memory does not.

4.8 One selection write

chat_conversations.py serves the units and owns the write. A unit id carries its own range — seg:<chat_rev>:<from>-<to> for an agent-drawn one, range:<chat_rev>:<from>-<to> for one the operator made by hand — so an id is self-describing and verifiable, and the freeze can read the range straight out of it. Our toy job's single conversation is seg:5:1-4.

SEGMENT_LABEL   = "맥락 기준"        # what the panel calls the boundary rule
PREVIEW_MESSAGES = 4                 # the card shows 4 messages…
PREVIEW_CHARS    = 60                # …clipped to 60 chars each

set_selection (:714) replaces the whole selection atomically. Every id is checked against the units the server derives, so a stale screen cannot select a conversation that no longer exists — it is refused by name (unknown_conversation) instead. And the module maintains exactly one candidacy rule: two denormalized columns on the asset row (chat_message_id, conversation_selected) that assets.evaluate_candidacy reads, so "which chat photos may be used?" stays a pure function of the asset row rather than a second derivation.

One counting rule worth stating plainly: photo counts are present bytes only. A reference whose bytes are absent from the export contributes nothing to any count and appears in no payload. Our toy conversation reports two photos, not three.

5. Intake III — the rules the draft must obey

Material is not enough. The agent also needs to know what a 창플 article is, how long its sections run, and how ambitious this particular job is allowed to be. Four small modules answer those, and a fifth measures whether the whole intake is ready.

5.1 The 가이드: versioned, packaged, pinned per job

The content standard is a Korean markdown document, and it is treated exactly the way this workspace treats its own docs — versioned, never edited:

1. ``ContentAgentJob.guide_instruction`` — a job-scoped instruction, frozen into
   the input revision, which **cannot override the guide**;
2. editing the guide document itself, which creates a **new version** applying
   to later jobs only — a job that already froze v1.1 keeps v1.1 forever.

Rule 2 is why this is a versioned table and never an ``UPDATE``.

Where does the text live? Docker images ship apps/backend but not docs/, so each version is copied verbatim into agent_jobs/guide_source/ and seeded by a data migration. Eight files sit there today:

guide_v1_1.md  guide_v1_2_ko.md  guide_v1_3_ko.md  guide_v1_4_ko.md
guide_v1_5_ko.md  guide_v1_6_ko.md  guide_v1_7_ko.md  guide_v1_8_ko.md

LATEST_SEED_VERSION = SEED_V18_VERSION      # guide.py:219  →  "v1.8"

The current head version is v1.8, seeded by migration 0060. Its history is a nice illustration of the versioning discipline: v1.8 is not a diff of v1.7 but the operator's own rewrite, authored outside the repository and landed verbatim — the 31,544-character document compressed to 4,734 characters, every chapter restated in the operator's words, and §8 (총 비용 표) deliberately removed, so the standard now has 14 chapters, not 15.

What makes that drop-in rather than breaking is that the original chapter numbers are preserved and §8 is simply absent: 1–7, then 9–15. Every number-keyed reader still resolves — image_pick.PHOTO_CHAPTER §7, chat_pick.SELECTION_CHAPTER §14, allocation_pick.ALLOCATION_CHAPTER §15 — and build.guide_rules() skips the missing chapter cleanly, reporting missing == ["8"] and fallback == False. The fallback flag fires only when no requested chapter is found, which is why the chapter list keeps its "8": removing it would change nothing for v1.8 and would stop v1.1–v1.7 — still frozen on 20 jobs — from cutting the chapter they do carry.

guide_choice.py (279) makes the version a per-job pick, defaulted to the latest at job creation — «the choice is sticky, not a live pointer», which is why a "not latest" warning pill can exist at all. It is writable before the freeze only (guide_choice_not_editable), and the frozen note the console prints is a constant:

FROZEN_NOTE = "나중에 나온 가이드 버전은 이 작업을 바꾸지 않습니다."

A small detail with a large principle behind it: the picker's v<n> (한국어|영문) label is measured, not stored — there is no language column; detect_language counts Hangul against Latin characters in the body. The design rule is «nothing printed that the system did not measure», and it recurs throughout this subsystem.

5.2 참고 콘텐츠: an already-published article as the house style

reference_choice.py (300) lets a job pick one published NotionContent as its tone-and-rhythm exemplar. Three rules:

  1. Published only — the candidate read is NotionContent.objects.readable(), which explainer #12 defined as with_stored_html().published(). A draft cannot be a style standard.
  2. One per job, before the freeze only; the freeze unit is the published row's profile hash.
  3. Tone and rhythm only, never evidence. The exemplar's text reaches exactly one consumer — the 참고 콘텐츠 말투 분석 analysis worker — and «is never a fact source, never cited in a draft and never in the evidence overlay».

Note also that this supersedes the old global singleton ContentDraftSettings.reference_content_id for v2 and does not read it at all: «An unpicked job has no reference — that is the design's own empty state, and falling back to the singleton would leave the singleton driving v2.»

reference_shape.py (263) then does something I find genuinely elegant. Instead of inventing a target section length, it measures the published references:

SCALE_MAX  = 1200      # the length meter's full-scale value
OVER_RATIO = 1.5       # past this, a unit reads as over-long
MIN_HEADINGS = 2       # fewer than two headings → not segmentable, skipped

It flattens the reference through content.extraction (explainer #12's one-line-per-block form) and splits it at one heading level — «the level carrying the most heading lines, shallowest wins a tie». Why not just hard-code ##? Because the two dev references disagree: one numbers its sections ## under an # title, the other uses ###. Hard-coding would measure one of them as a single 15,000-character unit.

And when there is nothing to measure, it says so rather than guessing: available: False with null medians, the UI drops the tick mark and keeps the target bar. «Nothing is invented to fill the hole.»

5.3 깊이: how ambitious may this job be?

depth.py (481) classifies the job's material into one of two bands the guide promises:

That is the right call, and the comment is why it is not confusing three years later.

5.4 intake_state.py: what the intake is, measured on read

737 lines, and the module's opening sentence is the design in one line: «Nothing here moves a job. There is no transition, no queue and no LLM call in this module by design: reading what the intake is must never be a write.»

Six deterministic checks, in fixed order (:63-68):

CheckLabelAsks
CHECK_SCOPE범위 확인Is there a brand and a scope? This is the only one that can block.

Then the manifest builders (:147-296) — one per input kind, assembling into:

The fingerprint, and why it answers a question nothing else can

Two lines of code sit on top of that payload:

def inputs_fingerprint(job, payload=None):
    if payload is None:
        payload = current_inputs_payload(job)
    return canonical_hash(payload)

def inputs_changed(job, *, against: str, payload=None) -> bool:
    return inputs_fingerprint(job, payload) != against

Because current_inputs_payload has one function and two callers — the snapshot itself and the fingerprint the screen compares against — «what a 구성안 was built from and what the screen compares against can never be two different things». That is the whole answer to «your inputs changed since this proposal».

And note the constraint it buys you: the shape is frozen history. Already-stored revisions carry these exact keys — including answers, which nothing has ever filled — and the fingerprint hashes the whole dict, so adding or dropping a key would make every existing job report a phantom change. A hash over a payload is a schema commitment. Design it once.

Finally, scaffold_action(job) (:628) decides what the button at the foot of the 입력 요약 says and may do. Three readings, all served from the server so the console «prints, it never composes»:

  • blocked — brand or scope missing: enabled: false plus the one sentence «브랜드와 범위를 정해야 시작합니다 — 게시글·사진·대화는 없어도 됩니다.» This is the only disabled control in the whole flow. Enablement is computed from the inputs, never from the state column, so a job that never moved and one that came back from a cancel read identically.
  • building — the job is in proposing: a strip replaces the button, reading «방금 시작 · 보통 40초». The «보통 40초» is a stated habit, deliberately a constant and never a countdown («no number the system did not measure»), and the «방금» is time_ago of the request_scaffold edge read out of the append-only transition log — the fact is already recorded, so no new column.
  • stale — a 구성안 exists, 승인 has not happened, and inputs_changed(job, against=frozen.content_hash) is true: the label becomes 다시 만들기 under the dated sentence «구성안은 {날짜}의 입력으로 만들어졌습니다…».

6. The 제안 turn — how a 구성안 gets made

One button press. One Celery task. Six or seven model calls. One document. Here is the whole sequence.

6.1 The act: scaffold.request_scaffold

scaffold.py:7150, and it is short enough to quote entire:

6.2 The four analysis workers

analysis.py (909) holds four read-only workers that run over the frozen revision through bounded packets. Each maps to one of the guide's 자료 활용 원칙:

Three rules shape all four. And the frozen revision is the universe: bodies are fetched by identity and checked against the frozen body_sha256; a mismatch is recorded as a drift note rather than crashed on.

Why sequential rather than a four-way fan-out? The tuple that orders them says so:

A comment that records the option not taken, the reason, and where to change it. Copy this habit.

6.3 GeminiStructuredWorker: two recovery layers below D56

analysis.py:310 is the shared client for every structured call in the subsystem — architect, build, the passes — so «the five v2 LLM stages cannot drift apart in their resilience posture». Its run() carries two recovery layers below D56's operator-visible attempts: a malformed parsed is first repair-parsed from the raw message, and only if that fails is the call re-invoked once with a strict-JSON nudge:

MALFORMED_OUTPUT_REINVOKES = 1     # analysis.py:120
#: Bounded and constant on purpose: this retry lives **below** D56's
#: operator-visible stage attempts (``services.MAX_STAGE_ATTEMPTS``), so it must
#: never grow into a second attempt counter — and it is deliberately not a
#: settings knob.

Note the repair-parse detail: it reads the raw content through _normalize_content, «i.e. the Gemini list-content rule is honoured by never string-assuming, not by never reading». (Gemini's .content can be a list rather than a string; a bare .strip() silently falls through.)

Model resolution never hard-codes an id:

LLMRoleConfig row → settings attr → literal default        # analysis.build_client, :413

operators.llm_runtime.resolve_role_config cannot raise — the chain is total and even a DatabaseError is treated as an absent row — «which is why no content-agent call, pass or stage can stop on a missing model any more». Explainer #17 owns that store; here it is enough to know that the operator changes the model and the thinking effort for any of these roles at /operator/settings, with no redeploy.

6.4 The architect call

architect.py (1042) runs the turn. After the workers, one structured call derives the core message with its derivation record and lays out the sections. What rides in the packet: the four worker returns, the frozen guide (GUIDE_PACKET_CHARS = 40000), the job note (NOTE_PACKET_CHARS = 2000), the depth classification and its band, and the measured reference shape. Two constants are quoted straight into the prompt:

CORE_VALUES = ("성공보다 생존 · 결과보다 과정 · 고객 중심 · 브랜드 중심 · "
               "현실적인 고민과 해결 과정 · 무엇보다 왜")
HEADING_RULE = "한 문장, 판단이나 교훈을 담고, 25–45자"

What the stage may not do is stated as plainly as what it may: «write prose for the final content (that is the build stage), assign asset_id (photos are chosen after the writing), or invent a fact (an unverifiable beat becomes a risk, never prose)».

The deterministic fix worth stealing: keep the heuristic and the prompt in agreement

Sections come back with a target_len. Sometimes the model omits one, and the fallback used to be the midpoint of the band — which, for a 10,000–16,000자 document over 12–18 sections, is about 1,000자 per section, while the actual published references run to roughly two thirds of that. The article read padded.

P72.S14's fix (architect._fill_target_lens, :405) anchors an omitted target_len on reference_shape's measured per-unit median, clamped so the document's total still lands in the band. The band is a total-volume bound, not a per-section length.

And the second half is the part people forget: the same measurement rides in the prompt as one line, so the model's own targets and the deterministic fallback answer to the same number. A fallback that disagrees with the instruction you gave the model is a fallback that makes your output worse in a way nobody can see.

6.5 Failure, and cancel

D56 drives every failure here — each worker and the architect run inside a ContentAgentStageAttempt, and a failure calls services.fail_stage, which takes the proposing → proposing self-loop while budget remains and stage_capped → needs_answer at the cap. Nothing new to learn; it is the machinery from §1.

Cancel tolerance is the part unique to this stage. The operator may press cancel while the Celery task is running, and cancel is a real transition (proposing → intake). So every write re-checks the job's state first:

def _still_proposing(job) -> bool:                      # architect.py:711
    return _job_state(job) == JobState.PROPOSING

…
if not _still_proposing(job):
    logger.info("content agent job %s cancelled before recording", job.pk)
    return {"job_id": str(job.pk), "status": "cancelled"}

A cancelled-out run drops its results with a log line and writes nothing. No new state, no partial document. This is what «Cancel exists only in proposing» means operationally: the one place a cancel is legal is the one place a long-running task can be interrupted, and every write in that task is guarded.

6.6 Landing the proposal

_progress(job, stage="scaffold_proposal", step="proposal",
          note="구성안 제안을 기록하고 있습니다.")
with transaction.atomic():

Three details in six lines. The last progress ping goes out before the state moves, because past proposal_ready the job is needs_review, which is deliberately not in PROGRESS_ACCEPTING_STATES — a later ping would be a silent no-op. The proposal row and the state move are in one transaction. And the allocation pass is scheduled here, at the turn's end, as its one trigger — dispatched on_commit inside the scheduler so the worker reads the revision this block just wrote, with a broker outage logged and swallowed «because a proposal must never fail because a pass could not be queued».

The job is now in needs_review. This is where explainer #13 ends.

6.7 The 구성안 document itself

scaffold.py is 7,434 lines and about 215 function definitions — a module to sample, not to enumerate. Two things in it matter for understanding the rest:

ContentAgentScaffoldWorkingCopy (:683) is the 구성안 document in its mutable form. The rule around it is the module's first:

1. **Immutable history, one mutable copy.** ``record_scaffold_proposal`` writes
   the proposal; ``approve_scaffold_revision`` writes ``rev N``. Neither is ever
   mutated. The only mutable row is ``ContentAgentScaffoldWorkingCopy`` —
   nullable by design (no copy means "no edits since the last immutable row"),
   created lazily on the first edit and deleted the moment an approval freezes
   a revision.
2. **Nothing computed is stored.** Candidacy, coverage, the usage matrix, the
   unused pool, ``dirty`` and the change list are computed at read time.
3. **References, never copies.** A chat range is
   ``{chat_rev, from_id, to_id, count}`` pointing at the stable ``message_id``;
   message text is never copied into the scaffold, and a range carrying a stale
   ``chat_rev`` is refused rather than silently re-pointed.

normalize_document (:1446) is the one shape everything is forced through — the proposal row, every approved revision, and the working copy all carry the identical JSON — and its first act is to refuse unknown keys (_reject_unknown). A model that invents a field gets a ScaffoldError("invalid_document", …), and because scaffold.validate_document runs before the proposal is recorded, an invalid document fails the attempt and is never stored.

Two neighbours get a paragraph each. scaffold_pool.py (572) answers the drawer's one question — «what may I drag into this unit, and where is each of those things already used?» — for both allocatable kinds, keying used_in on scaffold.media_key (asset:<id> / capture:<rev>:<a>-<b>) so there is never a second spelling of the same identity. scaffold_note.py (1055) is the section editor that survived: round 15 deleted every structured field and all five structure ops, leaving one free-form note an LLM applies, run inside the request rather than queued (budget 8–20 s), with structural intent («delete this section») diverted to a dry-run that returns the six delete consequences plus a django.core.signing-signed confirm_token carrying the note, the unit and the document hash — so a confirm arriving after the document moved is refused rather than applied to a different 구성안 than the operator saw.

Comment drift #2 (code wins)

scaffold_note.py's decision 1 says «there is no new job state — states.py's 21 stand». There are 14 today; the sentence predates P79's shrink. The claim is still true (the note stage adds no state, and locks only section.note_pending); the number is stale.

6.8 P74's allocation pass — the 구성안 arrives already allocated

allocation_pick.py (890). Before P74, a 구성안 arrived with empty photo rows and a drawer for the operator to fill. Now, right after the proposal is recorded, one more pass reads the whole proposal and the whole pool at once and decides which 재료 belongs in which 절 — with one Korean sentence of reasoning per unit, «uneven by design, leftovers normal».

Six decisions, of which three generalise:

  • Chained, not folded into the architect's call. It runs on its own ContentAgentPass row (Panel.ALLOCATION), «which buys the whole tested lifecycle — atomic claim, land/fail-open, one operator retry, no-clobber merge — instead of re-implementing it inside the largest prompt in the pipeline».
  • It reads text only, never pixels. Every allocatable photo already carries the image pass's durable inspection_caption and agent_reason, and the media worker's inventory describes it in prose. A caption-less photo is non-allocatable anyway — «the pixels a second multimodal pass could newly learn from belong to items this stage may not place».
  • The model answers in pool keys, never raw ids (asset:<pk> / capture:<rev>:<a>-<b>). The keys ride in the packet, «so a hallucinated range cannot be spelled at all»; an unknown key is dropped and reported rather than fatal. This is a small, very transferable trick: constrain the output alphabet to identifiers you put in the prompt.

It reads the guide's §15 배치 기준 chapter (ALLOCATION_CHAPTER = "15", GUIDE_EXCERPT_CHARS = 6_000), lands as a new kind=PROPOSAL revision — so the allocated document becomes the base automatically and an untouched job still reads "not dirty" — and fails open, leaving the empty-media proposal and the entire manual path working.

Quiz

Five questions. Click an option to see whether it is right and why.

1. states.py ends with TRANSITION_INDEX = _validate_table() — a module-level call, so the checks run at import time. What does that buy, concretely?

The indexing is a side benefit; the point is the assertions. _validate_table raises AssertionError on a duplicate key, an unknown state, a failure edge that advances the lifecycle or reaches published, a cancel outside proposing, a stranded state, or a missing pill/label — and because it runs at import, Django, the Celery worker and even test collection all refuse to start. The machine's rules are checked before the app can boot.

2. cancel is legal from exactly one state, proposing, and its target is intake. Why that target rather than a dedicated cancelled state or the previous state?

The docstring says it directly: "with the freeze retired there is nothing to fall back *to* but the inputs, which were editable the whole time anyway". The third option is also wrong on a fact — request_scaffold has four sources, not one. And cancel is its own Kind.CANCEL, the only such edge in the table.

3. An analysis worker fails twice, the job hits stage_capped and lands in needs_answer. The operator presses 다시 시도. What happens to the attempt budget and to the work already done?

proposal_turn() counts request_scaffold / propose_scaffold / resume_scaffold edges in the append-only transition log, and _unit_key(base, turn) appends @turn for turns past the first — so the budget is scoped to the turn, "otherwise the three options round 12 §3.7 prints would be a lie the second time". _reuse_analysis reuses succeeded workers, and every attempt row stays as D56's audit trail.

4. The intake screen can say «구성안은 2024-03-12의 입력으로 만들어졌습니다 — 다시 만들어야 합니다». What makes that answerable, and what constraint does it impose on the codebase?

inputs_fingerprint() is canonical_hash(current_inputs_payload(job)), and inputs_changed(job, against=frozen.content_hash) is the whole comparison — computed on read, with no side effects and no write hooks (P78's write-time version was deleted). Because the hash covers the whole dict, the shape is a schema commitment: the payload still carries an answers key that nothing has ever filled, precisely because removing it would change every stored job's fingerprint.

5. Which statement about the content agent's intake pipeline is true?

Grep-verified: agent_jobs/ contains zero references to agent-api — scope and selection are brand_documents() querysets, and the LLM calls are made from Django directly. Segmentation deleted the day-gap rule outright ("a hidden day-gap fallback would resurrect it invisibly while the panel says 맥락 기준") and stores boundaries in ContentAgentChatSegment, because a recomputed boundary could drift between two reads and silently drop the operator's selection. And a missing media reference is carried as a row with state="missing", not dropped — it is only the photo counts that are present-bytes-only.
