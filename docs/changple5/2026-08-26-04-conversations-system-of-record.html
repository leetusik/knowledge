Conversations as the system of record: models, the API, and the agent write-back loop

Background

Part A of this curriculum built up the shape of the system. Explainer #1 showed three applications — the Next.js front end, the Django backend behind /api/, the FastAPI agent behind /agent-api/ — sharing one Postgres database split into two schemas with a deliberate one-way read bridge, and one Redis split into three logical databases. #2 taught how configuration resolves and where the two trust boundaries sit. The previous explainer, #3 Identity and auth: Naver and Google login, JWTs, guests, and entitlements, finished the job: it followed a human from a browser to a principal the code can name — a User row, a GuestPrincipal, or the agent service itself — and ended on the observation that when the agent calls back into Django on a first-party turn, it forwards the caller's own bearer token rather than its service token.

This page picks that sentence up and asks the obvious follow-on question: calls back into Django to do what?

The answer is the subject of Part B, and it starts here. When you type a message into the 미라클 chat and an answer streams back, something has to remember it. Reload the page and the conversation is still there; open it tomorrow and it is still there, with its citations, its generated title, and its position in your history rail. That memory is not in the agent. It is in a Django app called conversations, and this page is about that app and the loop that writes into it.

The one idea on this page

The Django conversations app is the system of record for chat: the single authoritative place a conversation exists. The FastAPI agent holds no durable chat state. Before a turn it reads the conversation from Django over HTTP; after a turn it writes the finalized user and assistant messages back over HTTP. Everything the agent keeps in between is scratch that can be thrown away.

"System of record" is worth defining, because it is a claim about authority and not about storage. Plenty of components hold a copy of a conversation: your browser renders one, the agent assembles one in memory to feed the model, LangGraph keeps a checkpoint of one. Exactly one of them is allowed to be right when they disagree, and that one is the Postgres rows behind conversations. Every other copy is a cache, a projection, or a draft.

Why the agent owns no chat state

This is a design decision, not an accident, and three separate pressures push the same way.

Streams die. A chat turn is a long-lived HTTP response — the model produces text for ten, thirty, sometimes ninety seconds. The user closes the tab, the phone drops off wifi, the container gets redeployed mid-answer. If the conversation lived in the agent's memory, every one of those events would be data loss. Because the agent's only durable act is an HTTP write to Django, a dead stream costs at most an unfinished answer — and even that has a documented repair path (§4.3 below). Explainer #5 covers the streaming machinery itself; the point here is that the persistence design is what makes it possible to be casual about a dying stream.

Authorization belongs next to the data. Explainer #3 ended on a comment in the agent's own chat route: "the backend — not this route — decides which sessions it may reach." If the agent held sessions itself, it would also have to decide who may read them, and that decision would then exist in two codebases that could drift apart. Instead the agent forwards the caller's credential and lets Django's queryset scoping answer the question exactly once, in one place. You will see that chokepoint in §3.2.

Invariants need a single writer. A conversation is not a bag of rows; it obeys rules. It starts with a user message. Roles alternate. A citation's [3] marker must point at something. A retried request must not duplicate a message. Rules like these survive only if there is exactly one piece of code that can violate them — and in changple5 that is a single Django model method, append_finalized_message, which every path funnels through.

Skip this box if you know Django's ORM

A Django model is a Python class that maps to one SQL table; each class attribute is a column. A ForeignKey is a link to another table's row, with an on_delete policy saying what happens when the target disappears (CASCADE deletes the dependent rows, SET_NULL keeps them and nulls the link). A QuerySet (Model.objects.filter(...)) is a lazy description of a query — nothing runs until you iterate it — which is why this codebase passes querysets around as reusable security scopes. queryset.update(...) issues one SQL UPDATE without loading or saving the object; obj.save() writes the whole row and fires Django's automatic timestamp fields. That difference turns out to matter (§1.3). A migration is a versioned file describing a schema change. Finally, with transaction.atomic(): opens a database transaction — everything inside commits together or not at all — and .select_for_update() takes a row lock (SQL SELECT … FOR UPDATE) so a concurrent request must wait rather than interleave.

Skip this box if you know what idempotency means

An operation is idempotent when doing it twice has the same effect as doing it once. "Set the title to X" is idempotent; "append a message" is emphatically not. The usual fix is an idempotency key: the client invents a unique id for the intent, sends it with the request, and the server records it. If the same key arrives again, the server returns the result it already produced instead of doing the work twice. This matters on any unreliable network, because a client that never saw a response cannot tell "the write failed" from "the write succeeded and the response was lost". changple5 uses this pattern in three places on this page, and the keys are derived rather than random, which is a small trick worth watching for.

Skip this box if you know the HTTP status codes

Five statuses do most of the talking below. 200 OK — here, sometimes meaning "this exact write already existed". 201 Created — a new row was written. 400 Bad Request — the payload was malformed or broke a validation rule. 403 Forbidden — you are authenticated but this is refused as policy. 404 Not Found — used here also to mean "not yours", deliberately, so that probing for someone else's conversation tells you nothing. 409 Conflict — the request is fine but the current state of the resource cannot accept it. The 409 is the one this app is famous for, and §2.1 explains exactly what produces it.

Intuition

Before any code, here is the whole idea in three pictures: what a conversation is as rows, the one rule those rows must obey, and the loop that puts them there.

2. The one rule: a conversation alternates

A chat transcript is not an arbitrary list of rows. It must start with a user message, and after that the roles must strictly alternate. That is the invariant, and almost every conflict this app reports is that invariant refusing something.

The subtlety is which message counts as "the current state". It is the last message ordered by (created_at DESC, id DESC) — not a counter, not the last row inserted, not a flag on the session. §2.1 shows why that ordering is chosen with care, and §3.5 shows what happens when a turn dies and leaves a lone user message as the tail: the conversation is stuck in the "may append: assistant" state, and something has to get it out.

3. The write-back loop

Now the loop itself — the thing this page's title promises. One default chat turn, drawn honestly, with the credential riding each arrow named.

Three things in that picture deserve to be said out loud, because each one is a decision.

The user's message is persisted before the model runs (step 3, before step 4). That is what makes the transcript survive a crash during generation — but it is also why a crashed turn leaves a dangling user message with no reply, which the alternation rule then refuses to build on. The failure-closure endpoint exists precisely to clean that up.

The agent forwards the caller's own credential on steps 2, 3 and 6, and only uses its service token on the internal failure-closure endpoint. So a bug in the agent's session-picking logic cannot leak someone else's conversation: Django scopes every lookup to whatever the presented credential owns. Contrast the failure closure, which must use the service token (there is no live request to borrow a credential from) — and therefore has to name its target's owner in the request body, which Django then re-verifies. Identity as payload, never as authority.

Every write carries an idempotency key, and only the user message's key comes from the client. The assistant message's key is derived from it — uuid5(namespace, "<nonce>:<client key>:assistant") — so the same turn retried, replayed, or resumed always computes the same key and can only ever produce one assistant row. That is a nice trick: you get idempotency without either side storing a table of keys.

Where the famous 409 comes from. Two different places produce "Conversation is awaiting a finalized assistant reply." — and only one of them is a 409 on the wire. (a) The agent checks before streaming: if the fetched transcript's last message is already a user message, it refuses with 409 (routes/chat.py:2007). (b) If that check is raced past, Django's alternation guard rejects the write — as a 400, because it is a DRF validation error. The agent then sniffs the returned detail text for the word "alternate" (_payload_indicates_turn_conflict, routes/chat.py:448) and re-maps that specific 400 into a 409 for the browser; any other 400 degrades to a 503. So the status code the browser sees is a translation, not the backend's own. §2.1 and §6.4 walk both halves.

Ownership, precisely

A session belongs to at most one of two things. A first-party session has user set and guest_id null. A P68 anonymous trial has user null and guest_id set. (The dormant diagnosis rows have neither.) There is no constraint expressing this — it is upheld by the create serializer, and every read path is written as a queryset that filters on the shape it expects rather than trusting the row.

Two ordinary-looking lines in Meta shape the whole product:

class Meta:
    ordering = ("-updated_at", "-id")
    indexes = [models.Index(fields=("user", "updated_at"), name="convsess_user_updated_idx")]

Default ordering is most-recently-touched first — that is the history rail — and the composite index is exactly the query the rail runs ("this user's sessions, newest first"). Keep updated_at in mind; it is about to become load-bearing.

1.3 The mutators, and one very deliberate .update()

The session's state changes go through small named methods rather than ad-hoc field assignment: lock() (:247), soft_delete() (:292), enable_pinning / disable_pinning, enable_sharing / disable_sharing, record_rolling_summary, and the read helper has_finalized_assistant_reply() (:289). They share a shape worth copying:

def lock(self) -> None:
    if self.locked_at is not None:
        return

    locked_at = timezone.now()
    type(self).objects.filter(pk=self.pk, locked_at__isnull=True).update(
        locked_at=locked_at,
    )
    self.locked_at = locked_at

Idempotent (a second call returns early) and race-safe without a lock: the condition locked_at__isnull=True lives inside the SQL WHERE, so two concurrent lockers cannot both win. Then the in-memory object is updated to match, so the caller sees a consistent object. soft_delete is the same shape.

But look at why record_rolling_summary uses .update() rather than .save() — the comment is one of the more instructive in the codebase:

"""Persist the rolling summary + its watermark (P61.S1).

`QuerySet.update()` rather than `.save()` is deliberate: `updated_at` is
`auto_now` and the owner's history rail orders by `-updated_at`, so a
`.save()` here would float the session to the top of the rail for a
background compaction job the user never triggered.
"""

Django's auto_now timestamp fires on save() and not on update(). Because the rail is sorted by updated_at, "touching" a row is a user-visible act — an old conversation would jump to the top of your list because a background job summarised it. A one-word choice of ORM method is a product decision.

1.4 ConversationMessage (:508) — and the constraint that makes retries safe

Fields: session (FK, CASCADE), role (user/assistant, indexed), content (text), public_id (unique UUID — the id the API exposes, never the primary key), idempotency_key (UUID), and metadata (JSON). The JSON blob is small but important: metadata.message_type is how a message announces that it is something other than a plain answer — security_lockdown, diagnosis_report, a consulting beat — and several rules downstream key on its mere presence.

class Meta:
    ordering = ("created_at", "id")
    indexes = [
        models.Index(fields=("session", "created_at"), name="convmsg_session_created_idx"),
    ]
    constraints = [
        models.UniqueConstraint(
            fields=("session", "idempotency_key"),
            name="convmsg_session_idem_unique",
        ),
    ]

That UniqueConstraint is the floor under the entire idempotency story: even if every application check were bypassed, Postgres itself would refuse a second message with the same key in the same session. Note also the ordering — (created_at, id), with id as the tiebreaker. Two rows written inside the same transaction can share a timestamp to the microsecond; without the tiebreaker their order would be undefined, and "the last message" would be a coin flip. The alternation check reads this ordering in reverse.

1.5 The three reference tables, and one shared numbering space

All three (:565, :614, :668) have the same skeleton: a CASCADE FK to the message, a nullable SET_NULL FK to the live row, a position, and *_snapshot columns frozen at write time, with unique constraints on (message, position) and (message, <the id>_snapshot). They differ in what they mean:

  • ConversationMessageSelectedContent — content the user attached to their question. User messages only.
  • ConversationMessageCitedDocument — a 네이버 카페 post the answer cited. Assistant messages only; carries an external source_url.
  • ConversationMessageCitedContent — a published 미라클 content the answer cited. Assistant messages only; has no URL because it links internally to /content/<id>.

The last two are siblings rather than one widened table, and the docstring says why: they validate against different corpora (DocumentSource versus NotionContent) and describe different destinations. But the reader sees a single numbered list — [1], [2], [3] — so their position values are drawn from one merged numbering space. No database constraint can enforce disjointness across two tables, so a single function does:

def normalize_cited_content_references(cited_content, *, cited_document_count):
    """Validate the merged citation layout (P41.S9).

    Returns ``(content_references, document_positions)``: the ``(content_id,
    position)`` pairs in position order, and the positions the cited DOCUMENTS
    take -- the complement slots, in the order the documents were given.
    """

Only the content half carries explicit positions over the wire; the documents silently take whatever slots are left, in order. When nothing but 네이버 documents is cited — the common case — the complement is just 1..n, i.e. byte-identical to how it behaved before content citations existed. Extending a format without changing its old shape is the whole art of the thing.

Finally, models.py:736–908 holds three more models — ConsultingReport, ConsultingRound, ConsultingFollowUpRequest — hanging off the same session. They are 컨설팅 mode's state machine and belong entirely to explainer #10; nothing on this page touches them.

§2 — The two invariants, from source

2.1 validate_next_message_role (models.py:336)

def validate_next_message_role(self, *, role: str) -> None:
    if role not in ConversationMessage.Role.values:
        raise ValueError(f"Unsupported conversation message role: {role}")

    last_message = self.messages.order_by("-created_at", "-id").only("role").first()
    if last_message is None:
        if role != ConversationMessage.Role.USER:
            raise ValueError(
                "Conversation sessions must start with a user message."
            )
        return

    if last_message.role == role:
        raise ValueError(
            "Conversation messages must alternate between user and assistant roles."
        )

Eleven lines. Three things about them.

The judgement is made on the last row, not on a counter or a flag. There is no last_role column that could drift out of sync with the messages; the state is derived from the data every time. The cost is one indexed query per write; the benefit is that the state can never be wrong.

The ordering is (-created_at, -id) — the exact reverse of the message Meta.ordering. Same tiebreaker, same result: even for rows written in the same transaction with identical timestamps, "the last message" is a single well-defined row.

It raises ValueError, not an HTTP exception. The model layer knows nothing about HTTP. Callers translate: the write serializer turns it into a DRF ValidationError (a 400), which the agent then translates again into the 409 the browser sees (§6.4). Three layers, three vocabularies, and the confusion this can cause is real — a debugging session that greps for "409" in Django will find nothing.

A note for the debugger. Because the check is "last message by (created_at, id)", a conversation whose tail is a lone user message can accept exactly one thing: an assistant message. That is the state a crashed generation leaves behind, and it is why this app has an entire endpoint (§3.4) whose only job is to write an honest apology so the transcript can move forward.

2.2 append_finalized_message (models.py:353) — the single writer

Every message in the database arrives through this method. It is worth reading as five phases.

Phase 1 — content and role rules. Empty (or whitespace-only) content is refused. validate_next_message_role is called. Then three symmetric checks: selected content is user-only; cited documents are assistant-only; cited content is assistant-only. A message may carry neither, either, or — across a conversation — both kinds of citation.

Phase 2 — the layout. Duplicate ids are refused (_require_distinct_ids), then normalize_cited_content_references computes the merged positions and the documents' complement slots.

Phase 3 — existence. Every referenced content and document is loaded with in_bulk, and anything missing is a hard ValueError:

# P41.S9: mirror the document check above -- an unknown content id is a
# hard error, never a silently dropped citation, because the marker the
# user already saw would then point at nothing.

That is the rule behind the rule. The answer text already contains [2]; a citation list that quietly dropped entry 2 would render a marker pointing at nothing. Better to fail the whole write.

Phase 4 — one transaction. The message row and all three kinds of reference row are created inside a single transaction.atomic() block, the side tables via bulk_create. A message with half its citations cannot exist, not even briefly.

Phase 5 — touch the parent.

updated_at = timezone.now()
type(self).objects.filter(pk=self.pk).update(updated_at=updated_at)
self.updated_at = updated_at

Explicit, inside the same transaction — because this is exactly the case where floating the session to the top of the history rail is correct: a human just said something.

What "finalized" means

The word appears in the method name, in the model's help_text, and in the serializers. A finalized message is a settled, durable fact: this is what was said. Streaming deltas, in-flight tool calls, the LangGraph checkpoint of a half-finished turn — none of that is finalized and none of it is in these tables. The agent accumulates the answer in memory, and only when the model has produced its final text does one row appear. So a conversation in Postgres is always a clean alternating transcript, never a partial one. (Cancelled and failed turns still write a row — a short fixed apology — precisely so that the invariant holds; see §3.4 and §6.3.)

The internal/ convention

An internal/ segment in the path means: the agent calls this, with the shared service token, and no browser ever should. It is a naming convention, not a mechanism — the mechanism is the authenticator class on the view — but having the convention visible in the URL makes an accidental exposure obvious in nginx logs, in route listings and in code review. Note what lives here: the failure closure, the rolling-summary write, and the consulting lifecycle mutations. All of them are things the agent decides on its own behalf, where there is no user request to borrow a credential from.

3.2 The chokepoint: querysets.py

This is the most security-relevant file in the app, and it is thirty lines of filters (:60–104):

def owner_conversation_session_queryset(*, user):
    return ConversationSession.objects.filter(user=user, deleted_at__isnull=True)


def guest_conversation_session_queryset():           # the dormant BFF funnel
    return ConversationSession.objects.filter(
        user__isnull=True, agent_type=AgentType.DIAGNOSIS, deleted_at__isnull=True,
    )


def guest_trial_conversation_session_queryset(*, guest_id):   # P68 anonymous trial
    if guest_id is None:
        return ConversationSession.objects.none()
    return ConversationSession.objects.filter(
        user__isnull=True,
        guest_id=guest_id,
        agent_type=AgentType.DEFAULT,
        deleted_at__isnull=True,
    )

Read those as sentences. A logged-in user reaches sessions they own that are not deleted — full stop; there is no "and also check the owner afterwards". A trial guest reaches sessions that have no owner and carry their own guest_id and are default mode. The service token reaches only ownerless diagnosis rows.

Because these are querysets, a view cannot forget the check: the lookup is the filter. A nonce that belongs to someone else does not produce a 403, it produces a plain 404 — the row simply is not in your queryset. That is deliberate, and it means guessing nonces tells an attacker nothing. OwnedConversationLookupMixin (views.py:113) packages the pattern for the owner-only views.

One decision recorded in the docstrings deserves highlighting: when the anonymous trial was built, the obvious shortcut would have been to widen the existing service-token queryset to cover trial sessions. The code refused, and says why — the service token is one shared secret with no per-caller identity, so widening it would hand a single credential access to every trial conversation on the platform. Instead the trial got its own guest-token-scoped queryset, where the per-browser guest_id does the isolating.

    output_serializer = ConversationHistoryDetailMessageSerializer(message)
    response_status = (
        status.HTTP_201_CREATED
        if getattr(serializer, "created", True)
        else status.HTTP_200_OK
    )
    return Response(output_serializer.data, status=response_status)

201 means "I wrote it"; 200 means "this exact write already existed". The caller gets the message either way, so a retry is invisible to the user — and distinguishable to a developer reading logs. That single line is the entire externally visible surface of idempotency.

The validation is deliberately doubled: validate() re-checks the same rules the model enforces, and for the merged citation layout it literally calls the model's own helper:

# P41.S9: the merged-layout rules (distinct ids, distinct positions,
# every position inside 1..total) live in one place -- the model
# helper the writer itself uses -- so the API and the model can never
# disagree about what a valid citation layout is.

Why validate twice at all? Because the two layers answer different questions. The serializer's job is to give a client a useful 400 with a per-field error; the model's job is to be unbypassable. Sharing the helper keeps them from drifting.

Then create(), which is the real subject. It is a ladder, and the order of the rungs is the design:

with transaction.atomic():
    locked_session = ConversationSession.objects.select_for_update().get(pk=session.pk)

    # 1. idempotency: has this exact key already been written here?
    existing_message = (... filter(session=locked_session,
                                   idempotency_key=validated_data["idempotency_key"]).first())
    if existing_message is not None:
        if self._payload_matches_existing(existing_message, validated_data):
            self.created = False
            return existing_message          # -> 200
        raise ConversationIdempotencyConflict()   # -> 409: same key, different payload

    # 2. security lockdown (P26) -- USER writes only
    if locked_session.is_locked and validated_data["role"] == Role.USER:
        raise ConversationSessionLockedConflict()

    # 3. anonymous trial turn cap (P68) -- USER writes only
    if validated_data["role"] == Role.USER and guest_trial_is_exhausted(locked_session):
        raise ConversationGuestTrialExhausted()

    # 4. alternation
    self._validate_turn_order(session=locked_session, role=validated_data["role"])

    # 5. the write itself
    message = locked_session.append_finalized_message(...)

    # 6. an assistant lockdown message locks the session, same transaction
    if role == ASSISTANT and metadata.get("message_type") == SECURITY_LOCKDOWN_MESSAGE_TYPE:
        locked_session.lock()

    # 7. first assistant reply on an untitled session -> queue title generation
    if self._should_queue_title_generation(...):
        queue_session_title_generation_on_commit(locked_session.pk)

Everything happens under select_for_update() — a row lock on the session — so two concurrent writes to the same conversation serialise rather than interleave. And each rung's position is argued for in the comments:

  • Idempotency is first, so that replaying an already-persisted message returns it even if the session has since been locked or the trial has been spent. A retry of something that already happened must never turn into a refusal.
  • The lockdown and trial guards check USER writes only, so that the lockdown's own assistant message — and the fallback/cancelled writes that close a broken turn — can still land. Guard the input, never the bookkeeping.
  • Alternation is checked last, on the locked row, immediately before the write.

Notice how "same key, different payload" is treated: not as a silent overwrite, and not as a success, but as a 409. Idempotency means "this exact request again", and _payload_matches_existing compares role, content, selected ids, cited document ids, cited content pairs and metadata before agreeing that it is the same request.

3.4 Closing a turn that died: ConversationAssistantFailureClosureView (views.py:370)

Recall the stuck state: a user message was persisted, generation then failed, and the transcript's tail is a lone user row. The owner could repair it with retract-tail — but an anonymous trial guest cannot, because that route is owner-JWT only. The docstring states the consequence plainly:

"""Close a turn whose assistant reply never landed (agent-internal).

Without this a guest turn that died before its assistant row was written
would strand the trial behind the role-alternation guard forever: the guest
cannot retract the tail either (that route is owner-JWT only), so every
later send would 409.
"""

So the agent calls POST /api/conversations/internal/<nonce>/assistant-failure-closure with the service token, and names its target's owner in the body: exactly one of owner_user_id or guest_id. Django then re-scopes the row to that owner (reusing the very same trial queryset from §3.2) so a guest identity can never close a first-party conversation. The transport credential authenticates the agent; the identity in the body is data that Django verifies. That distinction is worth internalising — it is how you safely let a trusted service act on behalf of many users without giving it the power to act as any of them.

Its idempotency key is not sent at all — it is computed on both sides from the turn being closed:

def build_assistant_failure_closure_idempotency_key(*, conversation_nonce,
                                                    user_message_idempotency_key):
    return uuid.uuid5(
        _ASSISTANT_FAILURE_IDEMPOTENCY_NAMESPACE,
        f"{conversation_nonce}:{user_message_idempotency_key}:assistant-fallback",
    )

uuid5 is a deterministic hash-based UUID: same inputs, same UUID, forever, on any machine. Two closure attempts for the same dangling turn therefore collide on the message table's unique constraint by construction. The view answers 201 if it wrote one and 200 if the identical closure already existed.

3.5 Undoing a turn: ConversationMessageRetractTailView (views.py:422)

The owner-facing repair path. When you press "edit" on your last question, or retry a failed answer, the redesigned chat does not mutate anything: it settles the turn, retracts the trailing pair, and streams a fresh one. The front end drives exactly that sequence — see apps/web/src/components/scaffold/session-feedback.ts, which builds the retract target from the transcript and calls the route before opening a new stream.

The request names the pair it expects to delete, by public id:

class ConversationRetractTailSerializer(StrictSerializer):
    user_message_id = serializers.UUIDField()
    assistant_message_id = serializers.UUIDField()

That is the whole safety design. Under a row lock, the view reads the actual last two messages and refuses unless they are exactly that [user, assistant] pair. A replayed request, or a second tab acting on a stale view, finds a different tail and gets a 409 — it can never delete the previous turn. Five distinct refusals, each with its own code, and the front end has a matching union type for them:

CodeMeaning
tail_too_shortfewer than two messages — nothing to retract
assistant_pendingthe tail is a bare user message; the answer has not settled yet
tail_mismatchthe current pair is not the one the client loaded
non_default_turneither message carries a metadata.message_type — a consulting beat, a lockdown notice, a diagnosis report
consulting_round_activea 컨설팅 round owns the tail, even if no marker is on it yet

A locked session is refused with the shared ConversationSessionLockedConflict instead, so the client's existing lock handling fires unchanged. The delete itself is a genuine hard delete — the only one in this app — and the citation rows CASCADE away with it. One consequence the docstring records honestly: retracting the only turn transiently drops the conversation out of the history rail, because the rail filters on "has at least one assistant reply", until the replacement turn completes.

§4 — The life of an anonymous conversation

Explainer #3 covered how a visitor gets a guest credential and what caps it carries. Here is what happens to the conversation that credential creates: it is born ownerless, it may be adopted by a real account, and if it is not, it is eventually deleted.

4.1 Adoption: guest_adoption.py:122

The conversion moment. A visitor chats anonymously, hits the two-turn wall, signs in with Naver — and the conversation they were already having becomes theirs. Same nonce, same transcript, no cap. Because the OAuth exchange happens client-side there is no server-side session hook to hang this on, so adoption is an explicit authenticated call the client makes right after the tokens land: POST /api/conversations/<nonce>/adopt, with the user's new JWT and the old guest token in X-Guest-Token.

The whole mechanism is one conditional UPDATE:

claimed = ConversationSession.objects.filter(
    nonce=nonce,
    user__isnull=True,
    guest_id=guest_id,
    agent_type=AgentType.DEFAULT,
    deleted_at__isnull=True,
).update(user=user, updated_at=timezone.now())

if claimed:
    ...   # adopted
# else: maybe the caller already owns it (idempotent retry), else refuse

Three properties, each earned by a specific part of that filter.

Proof-bound. guest_id=guest_id comes from the guest token in the header, so having a login is not enough: an attacker who somehow learned a nonce still cannot take someone else's trial. The guest token's 12-hour lifetime is what makes "present it again after the OAuth round trip" workable.

One-shot, atomically. user__isnull=True is inside the WHERE, so the database serialises concurrent adopters: exactly one call updates a row, the loser updates zero and falls through. There is no read-then-write window to race. Re-adopting a session you already own is a 200 no-op, because the OAuth return path can legitimately fire twice.

Non-enumerable. Unknown nonce, wrong guest proof, owned by somebody else, consulting mode, soft-deleted — all five answer with one opaque guest_adoption_not_available 404. Only "you presented no usable guest credential" (guest_adoption_proof_invalid, 400) is distinct, because that one is actionable in the UI. Uniform refusals are how you keep an endpoint from becoming an oracle.

Two design notes the module records, both instructive. First, the guest token carries a jti (a token id) that could be burned on adoption — and deliberately is not, because the turn cap is per conversation, so one browser may hold several trials and should be able to adopt all of them with the credential it has. One-shot-ness belongs to the session, not the token. Second, guest_id is kept after adoption rather than cleared: once user is set, every guest surface (which requires user IS NULL) stops matching, so the stamp is inert as a credential and valuable as an audit trail — the only record that this conversation began anonymously, and the join key for "did this guest convert?".

4.2 Retention: guest_retention.py:96

Anonymous rows have no owner to delete them, so a daily Celery beat job at 03:00 hard-deletes them past their window — two families, two windows:

Seven days is generous for something that is at most two turns with a 12-hour credential; the job exists mostly so a visitor who comes back the same day, or logs in on another device, still finds the conversation. The task is conversations.purge_expired_guest_sessions in tasks.py; the beat schedule that drives it belongs to explainer #16.

4.3 Diagnosis snapshots: snapshots.py:13

One paragraph, because the feature is retired. When the changple_web site ran its 무료 AI 진단 funnel, a visitor could submit a 상담신청 off the back of a generated report. resolve_guest_diagnosis_snapshot resolves a guest nonce through the hard-scoped diagnosis queryset and freezes the latest assistant message carrying metadata.message_type == "diagnosis_report" — its text plus a copy of its cited documents — so the consultation record stays readable even after the conversation is purged. §5 — Titles: title_generation.py

A small, complete feature that shows how this codebase does background work — and it starts back in the write serializer:

def _should_queue_title_generation(self, *, session, message) -> bool:
    if message.role != ConversationMessage.Role.ASSISTANT:
        return False
    if session.title:
        return False
    return not ConversationMessage.objects.filter(
        session=session, role=ConversationMessage.Role.ASSISTANT,
    ).exclude(pk=message.pk).exists()

"The first assistant reply in a session that has no title yet." When that is true, the serializer calls queue_session_title_generation_on_commit(session.pk) (dispatcher.py:12), which wraps transaction.on_commit around a send_task("conversations.generate_session_title").

Dispatch-after-commit, in one sentence

The task is queued after the database transaction commits, not during it — because a Celery worker is a different process that will read the database itself, and if it started while the transaction was still open it would look for a row that does not exist yet. Explainer #16 owns this pattern; every place in changple5 that dispatches background work uses it, and this is the first one you have seen.

The task calls generate_and_store_session_title (:212), which is written to be safely re-runnable: missing session → {"status": "missing"}; title already present → skipped; no complete exchange yet → skipped; no API key → skipped; the model failed → failed. It never raises and never retries — a missing title is cosmetic, and the next assistant write will not re-queue it because a conversation only gets one first reply. (An untitled session simply shows its first message as a preview.)

get_first_completed_exchange (:167) fetches the first user message and the first assistant message and does one non-obvious check:

if (first_assistant_message.created_at, first_assistant_message.id) < (
    first_user_message.created_at, first_user_message.id
):
    return None

If the assistant row somehow predates the user row, there is no coherent "first exchange" to summarise, so it declines rather than inventing a title from a scrambled pair. Then strip_visible_citation_markers (:160) removes the [1] [2] markers from the answer — but only when the message actually has cited-document rows, so a bracketed number that is genuinely part of the prose survives.

The model call is GeminiConversationTitleModel (:44): Gemini (gemini-3.1-flash-lite by default, overridable live by the operator console through resolve_role_config(ROLE_CONVERSATION_TITLE, ...) — the live-config pattern from explainer #2), temperature=0.0, and structured output against a one-field Pydantic schema:

class _GeminiConversationTitleSchema(BaseModel):
    title: str = Field(description="30자 이내의 짧은 한국어 채팅 제목.")

Asking for a typed object rather than a string is the reliable way to get a title back instead of "Sure! Here's a title for your conversation:". The prompt (:121) is Korean, sees only the first exchange, and bans quote marks, emoji, and lazily generic titles like 대화 or 질문. Even so, the output is normalised defensively — whitespace collapsed, decorative punctuation stripped, a leading "제목:" removed, then truncated to 30 characters — because a model that has been asked nicely is not a model that has been constrained.

The write is one more conditional UPDATE:

updated_count = ConversationSession.objects.filter(pk=session_id).filter(
    Q(title__isnull=True) | Q(title="")
).update(title=title)

Zero rows updated means somebody else won the race, and the function reports skipped / title_exists. You have now seen this same "put the precondition in the WHERE clause" move four times on this page — lock(), adoption, retract-tail's expected-pair check, and here. It is the house style for concurrency in this codebase, and it is a good one: no locks, no read-modify-write windows, and the database arbitrates.

§6 — The other side of the loop: apps/agent/app/chat/backend.py (1,556 lines)

Everything so far was Django. Now cross the boundary. This one module is the agent's entire view of the conversation store: fifteen typed shapes, a dozen normalisers, and nine network operations. It is worth understanding as a specimen of "how to call another service you also own".

6.1 One HTTP client for the whole process (:83, :91)

_backend_http_client: httpx.AsyncClient | None = None


def get_backend_http_client() -> httpx.AsyncClient:
    """Return the shared, lazily-built backend HTTP client (app-lifetime)."""
    global _backend_http_client
    if _backend_http_client is None:
        _backend_http_client = httpx.AsyncClient()
    return _backend_http_client

This replaced a fresh httpx.AsyncClient per request. The win is the connection pool: TCP handshakes and keep-alive are reused instead of paid on every call, which matters when a single chat turn makes three or four round trips. Explainer #1 noted that the agent's FastAPI lifespan opens six Redis registries eagerly but only closes this client and the retrieval cache — this is that lazily-built client, and aclose_backend_http_client() is what the lifespan finally calls, after draining durable runs (because those persist answers through these same helpers). The comment is emphatic that no request or stream path may ever close it.

Each call site still passes its own timeout= per request (default 10 s), so sharing the client changed pooling and nothing else.

6.2 Two type systems, on purpose (:104–330)

Every payload exists twice. A frozen @dataclass(slots=True) is what the rest of the agent passes around; a private Pydantic BaseModel ending in Payload is what the JSON is validated into first. For example BackendConversationDetail (:187) is mirrored by _BackendConversationDetailPayload (:300):

class _BackendConversationDetailPayload(BaseModel):
    model_config = ConfigDict(extra="ignore")

    nonce: UUID
    messages: list[_BackendConversationMessagePayload]
    agent_type: str = "default"
    consulting_lifecycle: _BackendConsultingLifecyclePayload | None = None
    is_locked: bool = False
    rolling_summary: str | None = None
    summarized_through_message_id: UUID | None = None
    summarized_through_created_at: datetime | None = None

Why validate JSON that came from your own backend? Three reasons, and they generalise to any service-to-service call.

They deploy separately. Django and the agent are different containers, and one can be a version ahead of the other. extra="ignore" plus defaults on every added field is a forward-compatibility contract: a newer Django emitting a field the agent has never heard of is harmless, and an older Django omitting one gives a safe default.

Parsing is where types begin. After model_validate, nonce is a real UUID and created_at is a real datetime — not strings that look like them. Downstream code compares and sorts on them without re-parsing or guessing formats.

A malformed payload becomes one named failure. Anything that does not validate is turned into BackendConversationUnavailableError, which the route already knows how to render as a 503, instead of an AttributeError surfacing from somewhere deep in the chat loop.

There is also a nice paranoid check after validation: if the returned nonce does not equal the one requested, the call fails. Not because Django is expected to be confused — because a mixed-up conversation is exactly the class of bug you want to die loudly.

The dataclass/payload split also lets the boundary be deliberately lossy in one direction: the message builder is called with include_metadata=False on write responses (the agent already knows what it just sent) and with metadata on read, where the lockdown guard needs metadata.message_type.

The page in one paragraph

A conversation is five Postgres tables owned by Django. One method, append_finalized_message, is the only way a message gets in, and it enforces alternation, citation integrity and atomicity for everybody. Access is decided by querysets that encode "yours" as a filter, so an unauthorised nonce is a 404 rather than a leak. The agent keeps no chat state: it reads the transcript with the caller's own credential, writes the user message before generating, writes the assistant message after, and reaches for its service token only on the internal endpoints where there is no user to speak for. Every write carries an idempotency key — the client's for the question, a uuid5 derivation of it for everything else — so retries are free and duplicates are impossible.

Quiz

Five questions. Click an answer to see whether it is right and why.

1. A client sends a user message into a conversation whose last message is already a user message, bypassing the agent's pre-stream check. What status does Django answer with, and what does the browser end up seeing?

append_finalized_message raises a plain ValueError; the serializer's _validate_turn_order converts it into a DRF ValidationError, which DRF renders as 400. The 409 the browser sees is manufactured in the agent by _payload_indicates_turn_conflict (routes/chat.py:448) — a string match on the detail. Any other 400 from that write degrades to 503.

2. On a first-party chat turn, why does the agent forward the user's own bearer JWT to Django instead of using the AGENT_BACKEND_SHARED_TOKEN service token it already holds?

The agent's own comment says it: "the backend — not this route — decides which sessions it may reach." Forwarding the caller's credential means conversation_lookup_queryset is the single authorization chokepoint, so an agent bug cannot reach a conversation the caller could not. (The service token is used both directions — just not here — and tier gates nothing server-side, as explainer #3 measured.)

3. A network blip makes the agent retry the assistant write for the same turn. What stops a duplicate assistant message, and what does the retry receive?

Determinism is the point: uuid5(namespace, "<nonce>:<client key>:assistant") is the same UUID on every attempt, so neither side has to store a key table. The serializer's first rung finds the row, compares the payload field by field, and returns it with created = False → 200. The database constraint is the backstop underneath, not the mechanism. (If the payload had differed, that would be a 409 idempotency_conflict.)

4. Which of these is reachable only with the X-Agent-Service-Token, and why does it need to be?

The internal/ family (failure closure, rolling summary, consulting-round and report mutations) is service-token-only. The failure closure is the clearest case: it fires after the turn collapsed, so it must name its target's owner in the request body — exactly one of owner_user_id or guest_id — which Django then re-scopes through the same querysets. Identity as payload, verified; never as authority. The message route, by contrast, is guest-capable and normally called with the caller's own credential; /adopt requires a user JWT; the shared transcript needs no auth at all.

5. An anonymous visitor's trial conversation is adopted after they sign in with Naver. What actually changes on the row, and what follows from it?

Same row, same nonce, same transcript — one column changes. The user IS NULL predicate inside the WHERE is what makes concurrent adoption race-safe without a lock. Keeping guest_id costs nothing (every guest surface filters on user IS NULL, so it is inert as a credential) and buys the only record that the conversation began as a trial. And because is_guest_trial_session and the retention purge both require user IS NULL, adoption lifts the cap and the expiry with no extra bookkeeping. The jti seam is deliberately not burned — one browser may hold several trials and should be able to adopt them all.
