A chat turn end to end: the LangChain agent, streaming, cancel, and replay

Explainer #5 of the changple5 builder's curriculum, and the centrepiece of Part B. One POST, one answer — and the roughly nine seconds in between, where a LangChain agent runs with three budgeted search tools, its tokens become Server-Sent Events, and the whole run keeps going even if the person who asked closes the tab.

Background

Explainer #4, Conversations as the system of record, ended on a deliberately unsatisfying note. It established where a conversation lives (Django, in the backend schema), who is allowed to write into it (the serializer's create() ladder, under a row lock), and the order in which a turn's two rows land: the user's message is written before the model runs, and the assistant's message is written from inside the streaming generator, once the answer is final. Between those two writes it drew a single arrow labelled “the agent runs”.

This page is that arrow. By the end you should be able to open apps/agent/app/api/routes/chat.py (2,266 lines) and apps/agent/app/chat/agent.py (2,856 lines) and read them top to bottom knowing why every guard, every flag and every finally block is there — because each one is the scar of a specific thing that went wrong in production.

Skip if you know it

Five pieces of vocabulary, defined once so the rest of the page can move fast. If you already know what an agent loop, a tool call, SSE, an async generator and a checkpointer are, jump to the turn itself.

1. An LLM “agent” is a loop, not a model. A plain chat completion is one round trip: you send messages, you get text. An agent is that call placed inside a loop with a list of tools. The model is told “here are functions you may call”; instead of answering it may emit a tool call — a structured request like search_changple_documents(query="치킨집 창업 비용"). The runtime executes that Python function, appends its return value to the conversation as a ToolMessage, and calls the model again with the longer message list. The loop ends when the model finally answers with text instead of a tool call. Everything the model “knows” about your database, it knows because a tool put it into that message list on this turn.

2. LangChain and LangGraph. LangChain is the library that wraps model providers behind one interface (init_chat_model) and turns Python functions into tool schemas (the @tool decorator). LangGraph is its state-machine runtime: it runs the loop above as a graph whose nodes are “call the model” and “run the tools”, and it carries a typed state object between them. changple5 uses create_agent, LangChain's prebuilt version of that graph.

3. A checkpointer is LangGraph's persistence for that state. Give the graph a thread_id and a checkpointer, and after every step it writes the state to storage, so a later run on the same thread resumes from where the last one stopped. changple5 uses AsyncPostgresSaver — the same Postgres, in the agent schema.

4. Server-Sent Events (SSE) is the simplest way for a server to push a sequence of messages down one long-lived HTTP response. The response never “finishes” until the server is done; its body is a plain-text stream of event: / data: pairs separated by blank lines, and the browser's built-in EventSource-style parser fires a callback per frame. It is one-directional (server to client) and rides ordinary HTTP, which is why it beats WebSockets for “stream me an answer”.

5. An async generator is a Python function containing yield inside async def. It produces values lazily: the caller asks for the next one, the function runs until the next yield, and freezes there. FastAPI's StreamingResponse takes one of these and writes each yielded string to the socket. Two properties matter enormously later: a generator that is never asked for another value simply stops running, and when it is thrown away Python raises GeneratorExit inside it — which runs its finally blocks, and only those.

What one turn is, concretely

The browser sends exactly one request per turn:

POST /agent-api/chat/stream
Authorization: Bearer <the user's access JWT>
Content-Type: application/json

{
  "conversation_nonce": "7f3c1e02-9d44-4a1b-b0d2-5c8e6a71f004",
  "message": "치킨집 창업할 때 초기 비용이 대충 얼마나 드나요?",
  "message_idempotency_key": "b41d77aa-2f0e-4d59-9c3f-1e2a55d90c11",
  "selected_content_ids": []
}

and gets back a 200 whose body arrives over the next several seconds as a stream of frames. That single endpoint is the whole live chat surface: it handles a first-party user, an anonymous trial guest, default chat and 컨설팅 mode, a fresh turn and a duplicate of a finished one. All the branching happens inside.

Four facts from the earlier explainers are load-bearing here, and this page cites rather than re-derives them:

  • The endpoint and the frame vocabulary (#1): the agent's entire public surface is 17 routes under /agent-api; the streaming one is POST /agent-api/chat/stream, and a default turn emits message_start, status, keepalive, message_delta, message_end and done, as text/event-stream with Cache-Control: no-cache and X-Accel-Buffering: no.
  • Credential forwarding (#2, #3): for a first-party turn the agent forwards the caller's own bearer JWT to Django rather than a service token, so the backend — not this route — decides which sessions it may reach. A trial guest's X-Guest-Token is forwarded the same way.
  • The per-turn thinking level (#3): chat/user_thinking_level.py does its own SELECT tier, chat_thinking_level FROM "backend"."accounts_user" over the one-way read bridge, per turn, with no cache — because a per-user value inside a process-wide snapshot would leak across users.
  • The write order and the two 409s (#4): user row pre-stream, assistant row inside the generator; assistant idempotency keys are uuid5-derived on both sides; and the browser's 409 for “you sent again before the last answer settled” has two producers — a pre-stream check in this route, and a Django 400 that this route re-classifies by sniffing its detail text.

Scope. This page owns the agent loop, the tool-call budget, and the streaming / cancel / replay machinery. It names the three retrieval tools as surfaces — signature, what the model gets back, what they write into state — and stops at the door: what happens inside them (query planning, embeddings, reranking, eligibility) is explainer #7. The rolling window, compaction and the recall tool are #6. 컨설팅 mode is #10. The injection guard, the session lockdown and the trial caps are #11.

Intuition

Idea 1: a turn is guards, then a generator — and the seam between them is a one-way door

The single most useful thing to understand about chat.py is why it is shaped the way it is, and the answer is a property of HTTP: a status code can only be sent before the body starts. Once the server has written 200 OK and Content-Type: text/event-stream, there is no way to go back and say 409 Conflict. The browser is already reading frames.

So the route splits in two around that door:

This is why the same condition can look completely different to the client. A conversation that is already awaiting an assistant reply is a clean 409 if we notice before the door; a Gemini timeout ten seconds later is a 200 whose final frame says {"status":"error"} — plus a persisted “죄송합니다…” message, so the conversation still alternates user/assistant and the next turn is not blocked.

Idea 2: the answer is a transcript of small frames

Here is a real-shaped transcript of one grounded turn — the toy request from the Background, answered in about nine seconds with one document search. Frame names and payload keys are exactly what the code emits; the prose is abbreviated.

Three things are worth noticing immediately, because each one is a decision:

  • message_end repeats the entire answer, even though the client just received it delta by delta. That is not redundancy: the deltas are what the model produced, while message_end carries what Django actually stored, along with the citation list and the preview card. The client renders the stored version, so a reload shows byte-identical text.
  • status frames are emitted at most once each. A turn that searches four times still shows one searching beat — a set of already-emitted phases guards them.
  • keepalive exists purely so nothing in the middle gives up. Its payload is the empty object, and the comment in sse.py explains why it is not an SSE comment line: a comment-only frame would be silently dropped by the browser's parser and would never reset the client's stall watchdog.

Idea 3: who owns the work — the durability trick

The naive way to build the above is: the HTTP request drives the generator, the generator drives the model. It works, and it has one ugly property. If the user navigates away at second three, the socket closes, Starlette throws the generator away, the model call is abandoned — and the conversation is left with a user message and no assistant message. Django's alternation rule then refuses the next turn too, so a single navigate-away can wedge a conversation.

changple5's answer (the durable_runs.py module, 144 lines) is to invert the ownership. The generation runs as a detached asyncio.Task owned by the server process, pushing its frames into an in-memory queue; the HTTP request merely relays whatever is on that queue. Closing the tab cancels the relay. It does not touch the task.

The trick that makes this work is almost funny in its simplicity. The generator is full of lines like if await request.is_disconnected(): return — the escape hatches from the old design. Rather than delete them, the durable path passes in a fake request:

class AlwaysConnectedRequest:
    async def is_disconnected(self) -> bool:
        return False

Every escape hatch is now unreachable, so the generator always runs to the end, so the real assistant message is always written. The module's own docstring calls this “single writer by construction”: because the abandonment paths cannot fire, the emergency finalizer that used to write a fallback message can never race with the task that writes the real one.

Idea 4: exactly one assistant row, no matter how it ends

A turn can end five ways: it completes, the user presses 멈추기, the model or a dependency fails, the process is shut down mid-answer, or the client vanishes. Every one of those paths ends with exactly one assistant message in the conversation — because all of them write through the same uuid5 keys from explainer #4:

How the turn endedWhat is writtenIdempotency key kind
Normal completionThe model's answer + citationsassistant
Cancelled (멈추기)“답변 생성을 중단했습니다…”assistant-cancelled
Failure mid-turn“죄송합니다… 다시 시도해 주세요.”assistant-fallback
Client vanished, non-durable pathThe same fallback, from the finally blockassistant-fallback
Nothing landed at allThe frontend later calls POST /chat/failures/closeassistant-fallback

Because the key is derived from (conversation_nonce, the client's message key, kind), two racing writers of the same kind collide on the database's unique constraint and the loser simply reads back the winner's row (a 200 instead of a 201). Correctness does not depend on the racers agreeing about who should write — only on them agreeing about the key.

Idea 5: cancel is a flag, replay is a re-read

Two more shapes, both deliberately unglamorous.

Cancel is cooperative. 멈추기 does not kill a task. It is a separate tiny HTTP request, POST /agent-api/chat/runs/{run_id}/cancel, that sets cancel_requested = 1 on a Redis hash, and returns. The generator polls that flag at every natural pause — between agent events, between delta chunks — and when it sees the flag it raises its own ChatRunCancelled, persists the cancellation message and emits a done frame with status: "cancelled". Cancellation is thus a message in the conversation, not an absence of one. This is exactly why it works across the durable split: the cancelling request and the running task share nothing except one Redis key.

Replay is not a re-run. If the browser re-sends a turn it already completed — a flaky network, a double submit — the same message_idempotency_key arrives again. The user write comes back created: false, which tells the route “this exact message already exists”. If the conversation's last message is an assistant reply, the whole turn is already finished, so the route streams the stored answer back out of the database in 80-character chunks, through the same frame vocabulary, and never calls the model at all. Same frames, no tokens spent, no second row.

The four ideas in one line each. Guards before the door, frames after it. The answer is a transcript. The server owns the run, the request only relays it. And every ending writes exactly one row, keyed so that duplicates are free.

Code

Six stops, in the order the turn itself takes them: the route and its guards, the generator and its frames, the agent, durability, cancel and replay, and a closing note on why any of this needs a second Python process at all.

1. The route: apps/agent/app/api/routes/chat.py

The request body: ChatStreamRequest (:204)

A pydantic model with extra="forbid" — an unknown key is a 422, not a silent ignore. Six fields:

conversation_nonce: UUID            # which conversation (the public id from #4)
message: StrictStr | None           # the user's text
message_idempotency_key: UUID       # the client's key for THIS user message
selected_content_ids: list[StrictInt]  # attached 미라클 콘텐츠, first-party only
resume_value: dict | None           # 컨설팅 probe answers (#10)
consulting_action: "start_round" | None

Three validators enforce the rules a type cannot: exactly one of message / resume_value (_validate_message_or_resume), a non-blank message, positive and duplicate-free content ids, and a long normalizer for resume_value. That last one is worth a glance even though 컨설팅 is #10's subject: it does not merely validate, it rebuilds the dict, keeping only answers / finish / note. An unknown key is rejected outright rather than passed through — which is exactly the trap to remember if you ever add a field to the resume payload and wonder why the agent never sees it.

chat_stream (:1852): the guard ladder

This is the “before the door” half of Figure 1, and it reads as one long descent. Each rung either refuses or falls through, and the order of the rungs is argued in the comments, because several of them could technically fire on the same request and the operator cares which reason the user is shown.

0
Resolve the caller. Depends(require_chat_caller_context) yields exactly one of: a user bearer JWT (carries user_id + the token itself), an X-Guest-Token trial guest (carries guest_id), or the dormant changple_web BFF service token. Presenting two is refused by the dependency itself (#3).
1
Fetch the conversation. fetch_conversation_detail (:1877) — the first backend round trip, carrying the caller's own credential. A conversation this caller does not own comes back 404 from Django and is re-raised as 404 here. Everything below reads from the returned detail; there is no second fetch.
2
Retired mode. agent_type == "diagnosis" → unconditional 403. No fall-through to default chat.
3
Ineligible guest. The BFF service-token guest is refused outright: it is one shared secret with no per-caller identity. The trial guest is additionally limited to agent_type == "default" and may not attach selected content.
4
Mode/payload coherence. consulting_action and resume_value are only valid on a 컨설팅 session; selected_content_ids is invalid on one.
5
Session lockdown (#11). If the injection guard has locked this conversation server-side, refuse with 409 before any write or model call, so a locked session cannot be continued to layer a multi-turn attack. Django's write serializer re-checks under the row lock as a race-safe backstop.
6
Trial exhausted (#11). Deliberately after the security guards, so a locked conversation still reports as locked; and deliberately before the rate limiter, so a spent trial always surfaces as the 403 product state (“sign in to continue”) and never as a 429.
7
The pre-stream turn conflict. if not is_resume and conversation_detail.last_message_role == "user" → 409. This is the first of explainer #4's two 409 producers: the previous turn never finished, so its user message is still the tail.
8
Guest rate limits — _enforce_guest_rate_limits (:544), guests only: a daily spend breaker plus per-guest / per-session / per-IP turn caps. A tripped cap is 429 guest_rate_limited; a limiter that cannot decide is 503 guest_limits_unavailable — it fails closed, because with the BFF gone there is no other chokepoint in front of a public LLM surface.
9
Register the run. run_id = uuid4(), then run_registry.register_run(...) writes a Redis hash and the per-(identity, conversation) active-run index. From here on, every failure path must call _cleanup_run_safely — and every one of them does.
10
Resolve attachments. fetch_selected_content_context (:2103), only when selected_content_ids is non-empty.
11
Write the user message (:2128) — the pre-stream write from #4, with the client's idempotency key. Eight except clauses map Django's refusals onto HTTP: 401 / 403-with-code / 404 / 409 / 503. This is where the second 409 producer lives: a Django 400 whose detail matches _payload_indicates_turn_conflict (:448) becomes a 409; any other 400 degrades to 503.
12
Choose the stream. A finished duplicate → iter_replayed_chat_stream. A 컨설팅 turn → iter_consulting_stream (#10). Otherwise assemble the context and hand iter_chat_stream to the durable manager. Return _sse_streaming_response(...) — the door.

The fragile coupling worth carrying with you. Rung 11's 409 is produced by matching prose: _payload_indicates_turn_conflict lowercases Django's error detail and tests "alternate" in detail or "awaiting a finalized assistant reply" in detail. Django gets there because ConversationSession.validate_next_message_role raises a plain ValueError, which DRF renders as a 400. So editing the wording of that ValueError — a copy change, in a different app, in a different repository directory — would silently reclassify every turn conflict as “the service is down”.

The three sibling routes

chat/stream is not alone. Three much smaller routes exist entirely to let a client recover from the fact that a turn outlives a page:

RouteLineWhat it is forWho calls it
POST /chat/runs/{run_id}/cancel:1635 Sets the cancel flag on the run's Redis hash, for its owner only. Answers cancelling or cancelled; 404 for a run this identity does not own (indistinguishable from a nonexistent run, so a guessed run_id leaks nothing); 409 if the run already finished. 2. The generator: iter_chat_stream (:1215)

Its docstring states the two things the rest of the function assumes:

"""Stream one default-chat turn.

P68.S1: the turn is either first-party (`access_token` + `user_id`) or an
anonymous trial (`guest_token`, `user_id is None`). Every backend write below
carries whichever credential opened the turn, so the backend keeps enforcing
the guest's `guest_id` scope on each write, not just on the pre-stream fetch.

P68.F3: `is_guest_trial` is carried explicitly (the caller already computed
it from the verified guest context) so the agent can pin an anonymous turn's
reasoning effort without inferring the posture from a missing `user_id`.
"""

Four local variables carry the whole state machine: emitted_status_phases (a set, so each status phase is emitted once), streamed_any_delta (did the user see any prose? — it decides whether a late failure can still substitute a clean fallback message or must admit the error), completion, and run_terminalized (has this run already been marked complete/cancelled/error? — the finally block reads it).

The body, in order:

  1. message_start — run id, conversation nonce, and the client's idempotency key echoed back, so the client can match the stream to the message it sent.
  2. _advance_run_phase(..., phase="preparing") (:821). This helper does two things at once, and that pairing is the point: it writes the phase into the Redis run record and returns the SSE status frame to emit. The record is what a reconnecting client reads from run-status; the frame is what a connected client sees. One call keeps them from drifting. _maybe_status_frame (:800) returns None if that phase was already emitted.
  3. The compaction wait — if a rolling compaction is in flight for this conversation, emit one compacting beat, wait up to ~10 seconds, re-read the summary, and put the run record back on preparing. The mechanics are explainer #6's; what matters here is why the wait lives inside the generator, which the comment states plainly: the spinner is an SSE frame, and frames only exist here.
  4. The agent run. 
    async for event in run_chat_agent_stream(
        settings=settings, assembled_context=assembled_context,
        run_id=run_id, conversation_nonce=conversation_nonce,
        user_id=user_id, message_idempotency_key=message_idempotency_key,

        return

        ...
    if isinstance(event, ChatAgentStreamDelta):   # -> a message_delta frame

    The agent yields a union of three dataclasses and this loop is the translator: status events become status frames, deltas become message_delta frames, and the single ChatAgentCompletion falls through to the variable. Note the two checks at the top of every iteration — this is where a cancel is noticed, and where a disconnect used to end a turn before durability made that branch unreachable.
  5. Finalize and persist. A finalizing phase, then write_conversation_message(role="assistant", ...) with the derived idempotency key, the citations, and — if the injection guard fired — the {"message_type": "security_lockdown"} metadata that makes Django lock the session in the same transaction.
  6. Schedule compaction, mark the run complete, emit the tail. hydrate_inline_preview_cards runs one small query for a preview card, _format_message_end_frame builds message_end from the persisted message, and done closes the stream.

What happens when it goes wrong — the two except arms

except ChatRunCancelled hands off to _emit_cancelled_generated_stream (:971): persist the cancellation message, mark the run cancelled, emit a cancelled status frame, and — only if nothing had streamed yet — a message_end carrying the cancellation text, so a turn stopped before its first token still renders as a message rather than an empty bubble. Then done with status: "cancelled".

except Exception (:1419) is the interesting one, because it branches on streamed_any_delta:

SituationWhat the user seesRun status
Failed before any prose, fallback message persistedThe fallback text, streamed as a normal answer via _emit_completed_message, then done: completecomplete
Failed before any prose, and even the fallback write failedstatus: error + done: errorerror
Failed after prose had streamedHalf an answer, then status: error + done: error; a fallback row is still persisted so the transcript alternateserror

The first row is the humane case: nothing was shown yet, so the turn can be presented as a complete-but-apologetic answer instead of a red error. The third cannot pretend — the user already saw text.

Both arms also call report_agent_error and consult _degraded_close_detail (:389), which maps the exception type to dependency-specific Korean copy: a Redis registry failure, a backend failure and a Gemini/timeout failure each say something different, behind the enable_degraded_mode_messaging kill-switch. _is_gemini_error (:376) walks the __cause__/__context__ chain looking for a google.* module, because the real error is usually wrapped several layers deep.

SSE plumbing: apps/agent/app/chat/sse.py (232 lines)

format_sse_frame (:115) is three lines and defines the wire format:

def format_sse_frame(event_name: str, payload: dict[str, object]) -> str:
    payload_json = json.dumps(payload, separators=(",", ":"))
    return f"event: {event_name}\ndata: {payload_json}\n\n"

with_sse_keepalive (:50) wraps any frame generator and interleaves a liveness frame during silence. Its loop is a small piece of async craft worth reading closely:

advance = asyncio.ensure_future(_anext_or_done(iterator))
done, _pending = await asyncio.wait({advance}, timeout=interval_seconds)
if not done:
    yield keepalive_frame   # the pending read SURVIVES - re-awaited next loop
    continue

asyncio.wait with a timeout does not cancel the pending task, so the in-flight read of the next real frame is preserved across any number of keepalives — no frame is lost or duplicated. The interval is 15 seconds, chosen to sit below the client's 20-second idle watchdog and well below nginx's 60-second default proxy_read_timeout. And its finally block explicitly aclose()s the wrapped generator, because a wrapper that swallowed GeneratorExit would prevent the inner generator's finally from running — which is where the emergency finalizer lives.

_sse_streaming_response (:319) is the door itself:

return StreamingResponse(
    with_sse_keepalive(source),
    media_type="text/event-stream",
    headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
)

X-Accel-Buffering: no is a request to nginx: do not buffer this response. Without it a proxy may hold frames until its buffer fills, and the user watches a spinner while the answer sits in nginx's memory. Explainer #1 showed the other half of that handshake — proxy_buffering off in the /agent-api/ location block, with proxy_read_timeout 3600s so a long turn is never cut. Both halves must be right; either alone is not enough.

The state: ChatAgentState (:491) and its reducers

LangGraph's state is not a plain dict you overwrite. Each field may declare a reducer: a function (existing, update) -> merged that decides how a node's output combines with what is already there. The default reducer is “last write wins”; the interesting fields here declare their own with Annotated[T, reducer].

Concretely, with toy values. Suppose the model calls search_changple_documents twice. Each call returns a Command(update={...}) containing "retrieval_call_count": 1 — not the new total, just its own contribution:

def _merge_retrieval_call_count(existing, update):        # :444
    if update is not None and update < 0:
        return 0                                          # the reset sentinel
    return int(existing or 0) + int(update or 0)

merge(0, 1)   -> 1     # first search
merge(1, 1)   -> 2     # second search
merge(2, -1)  -> 0     # RETRIEVAL_CALL_COUNT_RESET, at the top of the next turn

So the counter is an accumulator that no tool ever has to read-modify-write, and a single negative value zeroes it. The document map works the same way, keyed by post id:

def _merge_retrieved_documents_by_post_id(existing, update):   # :453
    if update and RETRIEVED_DOCUMENTS_RESET_KEY in update:
        return {k: v for k, v in update.items() if k != RETRIEVED_DOCUMENTS_RESET_KEY}
    merged = dict(existing or {})
    merged.update(update or {})
    return merged

merge({}, {"56007": {...}})                     -> {"56007": ...}
merge({"56007": ...}, {"51993": {...}})         -> {"56007": ..., "51993": ...}
merge({"56007": ...}, {})                       -> {"56007": ...}   # a failed call keeps earlier hits
merge({"56007": ...}, {"__reset_retrieved_documents__": {}})  -> {}

_merge_retrieved_content_by_id (:469) is the identical shape for the parallel published-content channel — a sibling map, deliberately not a widening of the first, because a content_id must never reach anything keyed on post_id.

Why reducers matter for correctness here. These two maps are the turn's ground truth: at the end, a citation is honoured only if its id is a key in one of them (see the finalizer below). Because the reducers merge rather than replace, an error in the fourth search cannot erase the evidence gathered by the first three — and because a reset is a sentinel value rather than an absent key, starting a fresh turn provably clears the previous turn's evidence even if the checkpoint delete was skipped.

The other state fields are per-turn booleans with a single reader each: security_locked (the guard fired — the route rides a lockdown marker on the write), feedback_capture_attempted, session_recall_used, cited_retrieval_used. All three of the latter exist to exempt a turn from a grounding gate, and all three are reset to False on every turn.

The system prompt and the cache prefix rule

build_chat_agent_system_prompt (:934) forwards to build_default_chat_system_prompt in app/prompts.py:37: a long Korean rulebook (범위 / 보안 / 검색 / 인용 / …) with the tool names interpolated in, and two dynamic sections — [Conversation summary] and [Current selected content] — at the very end. The file carries an unusually emphatic comment about that layout:

# P39.S5 (D9 lever 1) - PREFIX STABILITY IS CACHE-LOAD-BEARING. The large
# static rulebook below (scope/security/search/citation/... sections) is the
# prompt PREFIX; only `[Conversation summary]` + `[Current selected content]`
# at the very end are dynamic. Gemini implicit context caching keys on that
# verbatim, turn-stable prefix, so any edit that injects a per-turn/dynamic
# value ABOVE those two trailing sections (or reorders the static block)
# silently defeats the ~75% cached-input discount on every chat turn.

Implicit context caching means the provider recognises that the beginning of your prompt is byte-identical to a recent one and charges a fraction of the price for that prefix. It is worth real money on a chat product, and it is invisible when you break it. This constraint explains a design choice further down that would otherwise look odd — see the budget, next.

The history the model sees is rebuilt from Django on every turn: _build_chat_agent_history_messages (:716) turns backend messages into plain HumanMessage/AIMessage pairs, and _resolve_rolling_window (:730) decides how far back to go. Explainer #6 owns that window. One consequence belongs here, though, because it constrains the tools: the rebuild emits Human and AI messages only — never a ToolMessage. So the model provably cannot see any previous turn's retrieved document bodies or their post ids. A prior turn's citations survive only as an id-free reference like (이전 답변 참고: 창플 카페 "치킨 프랜차이즈 실제 정산표"), built by _format_message_context (:657). Citations are strictly this-turn, by construction rather than by instruction.

The four-call budget — and where it is announced

One constant governs how much searching a turn may do:

MAX_CHAT_RETRIEVAL_CALLS = 4        # agent.py:129

and it is shared by all three retrieval tools. Not four naver searches plus four content searches — four searches, period. Each of the three reads state["retrieval_call_count"] at the top, refuses with a limit_exhausted tool result once it is at 4, and contributes 1 on a successful call.

That last point is the interesting design decision. The remaining budget is not in the system prompt. It is appended to the body of every successful tool result, by _chat_search_budget_guidance (:336):

"Search budget for this turn: 2 of 4 searches used, 2 remaining. Spend the
remaining searches on the aspects of the user's question these documents do not
cover yet; leaving budget unused produces a shallower answer. Stop early only
when the question is genuinely single-aspect and the returned documents already
cover it."

Two reasons, both stated in its docstring. First, timing: the model decides whether to search again immediately after reading a tool result, so that is the moment the number has to be in front of it. Second, and decisively, the cache: a per-turn value in the system prompt would change the prompt prefix on every single turn and defeat Gemini's implicit caching. Tool results are already dynamic, so they cost nothing to vary. A pricing constraint chose the architecture.

The guidance strings (:170–:401) are a whole subsystem in themselves — five or six variants per tool, one per outcome (ok, empty_results, limit_exhausted, unavailable, invalid_query), each written to close a specific failure of model behaviour: do not invent post ids, do not retry a blank query, do not conclude “Changple has nothing on this” from an empty content search, do not mention embeddings or backend errors to the user. This is what prompt engineering looks like once it has been through production: not clever phrasing, but an exhaustive case analysis attached to the exact place the model will read it.

Two tools are deliberately budget-exempt. search_conversation_history (recall inside this conversation) and search_cited_documents (re-fetch what this session already cited) never write retrieval_call_count at all — and, as both files say in a comment, “that omission is the entire budget exemption, and it is pinned by a test.” Neither touches the corpus, so neither costs a search; a follow-up about known material can run beside a fresh search in the same turn. Explainer #6 covers both.

Extracting the answer: extract_chat_agent_completion (:2377)

When the graph finishes, the final state holds a message list. This function turns it into the ChatAgentCompletion the route persists, and most of its work is citation enforcement. The valid id sets are computed straight from state:

What comes out is the final text plus two sibling citation tuples carrying positions from one merged [k] numbering space.

Three grounding gates, and the buffering trick that makes them possible

Retrieval is model-elective — nothing forces the model to search. So three separate failure modes exist, each with its own gate, each replacing the answer with the same fixed refusal (NO_DOCUMENT_DEFAULT_CHAT_RESPONSE, :148) and deleting the checkpoint thread so the bad text is not carried forward:

GateLineFires whenThe hole it closes
_should_use_no_document_default_chat_response:2188 Retrieval ran this turn (count > 0) and returned nothing in either corpus “Searched, found nothing, advised anyway.”
_should_use_ungrounded_memory_fallback:2245 count == 0, no citations, and the answer is at least UNGROUNDED_ANSWER_MIN_CHARS (400) characters “Never searched at all” — a parametric-memory leak. Short greetings fall below the bar; the security refusal, a feedback turn, a recall turn and a cited-arm turn are explicitly exempt.
_should_use_filtered_citation_fallback:2329 At least one marker was filtered and no citation survived The gap between the other two: retrieval ran and returned documents, but the model cited only ids the map does not hold. No length bar — an answer that cites only ids it was never given is ungrounded at any length.

A gate can only replace an answer the user has not already read — which is what _should_buffer_default_chat_delta (:2203) is for. It decides, per delta, whether to stream immediately or hold the text back:

if state is None:                       return True   # nothing known yet - hold
if _has_current_turn_grounding(state):  return False  # grounded - stream live
if not _attempted_current_turn_retrieval(state): return True   # zero-retrieval - hold
return True                                           # searched but empty - hold

So a grounded turn streams token by token, as a chat should; an ungrounded turn is buffered in memory, and if a gate fires the buffer is simply discarded — the user never sees a word of the ungrounded answer. If no gate fires, the buffer is flushed at the end and the reply lands in one lump. That is a real, visible product trade-off (a short zero-retrieval reply appears all at once instead of typing itself out) and the comments record it as accepted deliberately. Note the honest exception, also in a comment: the third gate can fire on a turn whose deltas did stream, so that answer is replaced at finalize after the user already read it.

Checkpoints: sync_chat_agent_checkpoint (:2545) and checkpointing.py

open_chat_checkpointer (all 26 lines of chat/checkpointing.py) opens a LangGraph AsyncPostgresSaver over build_checkpoint_conninfo(settings). That conninfo is the one place in the whole agent that pins a search_path (-c search_path=agent,public) — explainer #2's exception to the “always qualify table names” rule, needed because LangGraph's own SQL is unqualified. The saver's tables are created once at bootstrap (app/db/bootstrap.py:115 calls setup_chat_checkpointer), and they live in the agent schema — a schema Django cannot read at all.

And then the punchline: on a default chat turn, the checkpoint is deleted and rebuilt every single time.

await runtime.checkpointer.adelete_thread(str(conversation_nonce))

    checkpoint_state = await asyncio.to_thread(
        build_chat_agent_checkpoint_state, assembled_context, settings=settings)
    await runtime.agent.aupdate_state(config, checkpoint_state)

The docstring explains why the older, cleverer behaviour was removed: the thread used to be reused whenever a predicted post-turn fingerprint matched the stored one — and a reused thread keeps every prior turn's ToolMessage, i.e. full document bodies with their post ids, in the model's context. Under the operator's strict this-turn citation rule, that context must not exist. So the reuse was deleted and the rebuild made unconditional.

Which leaves a fair question: what is the checkpointer still for? Within a single turn, it is what carries state across the loop's steps — the merged document map, the call counter, the growing message list — and what the reducers write through. Across turns, on the default path, nothing: Django is the memory. chat/fingerprints.py (build_backend_history_fingerprint, :33 — a sorted, normalized sha256 of the history) survives as the shared helper that 컨설팅 still uses to notice backend drift, and the state schema's own comment records the removal: “no backend_history_fingerprint. The chat thread is now rebuilt from backend history on EVERY turn, so there is nothing left to compare against.”

Two stores, two jobs. Django's conversations tables hold the conversation: user and assistant messages, citations, titles, ownership — the durable record the product reads. LangGraph's checkpoint tables hold the run: the message list the model is currently working with, including tool calls and tool results, plus this turn's retrieval state. The first outlives the turn; the second is torn down at the start of the next one.

4. Durability: apps/agent/app/chat/durable_runs.py

144 lines, and the highest ratio of consequence to code in the agent. Read it whole; here is what each of its four pieces does.

AlwaysConnectedRequest — the two-line shim from Idea 3. Its docstring is the design note:

"""Request shim whose ``is_disconnected`` is permanently ``False``.

Driving ``iter_chat_stream`` with this is what makes a durable run durable:
every early ``return`` in that generator (and its emit helpers) is guarded by
``request.is_disconnected()``, so an always-connected request means generation
always runs to completion, the real ``kind="assistant"`` answer is always
persisted, and the abandoned-stream finalizer never fires (single writer by
construction). Structurally satisfies ``chat.DisconnectAwareRequest``.
"""

Note structurally: the generator's parameter is typed as a Protocol (chat.py:196, one method), so a real Starlette Request and this two-line class are interchangeable with no inheritance and no if durable: branching inside the generator. The behaviour switch is a value.

DurableChatRun (:27) — a run's handle: run_id, an asyncio.Queue[str | None] of frames, and the asyncio.Task. A None on the queue is the end-of-stream sentinel.

DurableChatRunManager (:41) — one per process, created in create_app(). start (:61) schedules the work:

queue: asyncio.Queue[str | None] = asyncio.Queue()
task = asyncio.create_task(self._capture(run_id=run_id, source_factory=..., queue=queue))
run = DurableChatRun(run_id=run_id, queue=queue, task=task)
self._runs[run_id] = run
return run

Three details, all deliberate. The manager keeps a strong reference in self._runs — asyncio only holds weak references to tasks, so a fire-and-forget task can be garbage collected mid-flight. asyncio.create_task copies the current contextvars context, so explainer #2's request-id travels into the background task and its error reports stay correlated. And the run removes itself from the dict in _capture's finally (:82), which also puts the None sentinel on the queue so any relaying request is unblocked even if the source blew up.

drain(timeout) (:104) is the shutdown half. Explainer #1 noted that the agent's lifespan teardown is ordered on purpose; this is the first step of it:

durable_manager.drain(timeout=settings.durable_run_shutdown_drain_seconds)   # default 10s
await aclose_backend_http_client()      # the runs need this to persist their answers
await aclose_retrieval_cache()
await chat_run_registry.aclose()        # ... and this to mark themselves complete

Draining before closing the HTTP client and the Redis registry is what keeps a deploy from stranding a user tail: an in-flight run gets up to ten seconds to finish writing its real answer through tools that are still open.

iter_durable_chat_stream (:128) is the relay, and it is five lines:

while True:
    frame = await durable_run.queue.get()
    if frame is None:
        return
    yield frame

It reads the queue. It does not own the task, does not cancel it, and knows nothing about the conversation. If the client disconnects, Starlette cancels this generator; the task keeps going and keeps filling the queue that nobody is draining. When the run ends, the manager drops its reference and the queue is garbage.

What the durable path replaced — and whether the old path is still reachable

chat.py:692–800 still contains the previous design's emergency machinery, and it is worth understanding because it teaches a genuine async trap.

Both stream generators end in the same finally:

finally:
    if not run_terminalized:
        await _run_abandoned_stream_finalizer(
            _finalize_abandoned_generated_stream(...), context="Generated chat stream")

“If we got here without having marked this run finished, the client abandoned us mid-turn: persist a fallback (or a cancellation) message and mark the run terminal, so the conversation is not left broken.” The problem is where that runs. A client disconnect makes Starlette throw the generator away, raising GeneratorExit inside it; the surrounding task is being cancelled. A plain await in that finally is therefore awaiting inside a dying task — the first suspension point raises CancelledError and the backend write never happens. That was a real, shipped bug.

The repair is _run_abandoned_stream_finalizer (:780):

task = asyncio.create_task(finalizer)      # a NEW task - not the dying one
try:
    await asyncio.shield(task)             # cancelling us does not cancel it
except asyncio.CancelledError:
    task.add_done_callback(lambda t: _log_abandoned_stream_task_result(t, context=context))
    raise                                  # we die; the write completes and logs itself

asyncio.shield lets the cancellation propagate to the awaiting coroutine while leaving the shielded task alive. The write finishes on its own, and its result is logged by a callback because by then nobody is left to await it.

So: is that path still live? Two different answers, and the difference is exactly what the durable design bought.

  • For a generated turn — no, it is a fallback. With enable_durable_runs on (its default; config.py:382), the generator is driven by AlwaysConnectedRequest and every early return is unreachable, while the normal and error paths all set run_terminalized = True. So _finalize_abandoned_generated_stream can only fire when the kill-switch is flipped off (chat.py:2237 keeps the in-request path for exactly that) or when the durable task itself is torn down — a drain that times out at shutdown. It is kept, correct and cold.
  • For a replayed turn — yes, live. iter_replayed_chat_stream is handed the real request, never the shim, so a client that disconnects halfway through a replay still lands in _finalize_abandoned_replay_stream (:744), which marks the run complete or cancelled. It has no message to write — the assistant row already exists — so it only tidies the registry. The 컨설팅 stream is driven by the real request too (#10).

5. Cancel and replay

The registry: apps/agent/app/chat/run_registry.py (526 lines)

A run's live state is not in the database and not in process memory — it is a Redis hash on db/0 (explainer #1's map: Celery plus the agent's registries), under agent:chat:run:<run_id>, with a one-hour TTL while active and five minutes once terminal. ChatRunRecord (:57) is what it parses back to:

run_id, user_id | None, guest_id | None, conversation_nonce,
message_idempotency_key, status, cancel_requested, streamed_any_delta

status is one of ten values (:32) — registered, preparing, compacting, searching, finalizing, cancelling, complete, cancelled, error, plus probing / generating_report for 컨설팅. Three of them are terminal, which is all is_terminal means.

Beside the hash, register_run (:134) writes an active-run index: agent:chat:run:active:<scope>:<nonce> → run_id, where the scope is the user id, or guest:<guest_id> for a trial. That is what makes find_active_run (:282) an O(1) lookup for “is something running on this conversation?” — the question the reload path asks. If the index is stale it falls back to _scan_for_active_run (:469), repairs the index, and re-checks ownership against the record itself, so a stale index can never hand a caller someone else's run.

mark_status (:206) writes the status, adjusts the TTL, and refreshes or deletes the index depending on whether the run just went terminal. request_cancel (:239) is the whole cancellation mechanism:

current = await self.get_run(run_id)
if current is None or not _record_matches_owner(current, user_id=..., guest_id=...):
    return None                     # -> the route answers an opaque 404
if current.status in ("cancelled", "complete", "error"):
    return current                  # already over
updated = await self._update_fields(run_id,
    {"cancel_requested": "1", "status": "cancelling"}, ttl_seconds=...)

Two field writes. No signal, no task handle, no cross-process messaging — which is precisely why it survives the durable split, where the cancelling HTTP request and the running task share nothing but Redis.

The polling points are worth memorising, because they define how fast a cancel takes effect: right after the preparing phase, after the compaction wait, once per event from the agent stream, and once more after the loop before the assistant write. A cancel that arrives while a single long model call is in flight is therefore not noticed until that call yields its next chunk — cooperative cancellation, with the latency that implies. In the replay generator the polling is per 80-character chunk.

One consequence that catches people: a cancelled turn spends the turn. The user message is already written, a cancellation assistant message is written, and for a trial guest that counts against the two-turn cap. That is the intended product behaviour, not an oversight.

Replay: iter_replayed_chat_stream (:1072)

The route reaches it through one condition (:2222):

if not user_write_result.created and conversation_detail.messages:
    last_message = conversation_detail.messages[-1]
    if last_message.role == "assistant":
        return _sse_streaming_response(iter_replayed_chat_stream(...))

Read it as two facts joined. created is False means Django recognised this exact message_idempotency_key and returned the existing row (200, not 201) — so this user message was already sent. And the conversation detail fetched before the write ends in an assistant message — so the turn it belonged to already finished. Together: replay the stored answer.

The generator then reproduces the full frame vocabulary from database rows: message_start, preparing, finalizing, then _chunk_text_for_streaming (:347) slices the stored content into 80-character message_delta frames, then _hydrate_replay_inline_previews (:1061) re-fetches the preview card and message_end + done close it. From the client's point of view it is indistinguishable from a live turn — deliberately, so the rendering code has one path. No model is called, no row is written, and the cancel flag is still polled between chunks.

The timing distinction that decides which path a duplicate takes. Re-POST after the turn finished → replay (200, the stored answer). Re-POST while the turn is still running → the conversation's last message is still the user row, so guard rung 7 fires first and the answer is 409. The client is expected to call run-status in that case and re-attach to the state it reports, rather than sending again.

6. Why any of this needs a second Python process

Explainer #1 measured the honest answer, and this page is where it pays off. Django runs under gunicorn config.wsgi:application --workers 3: synchronous workers, one request occupying one worker for its whole lifetime. The agent runs as a single uvicorn process on an asyncio event loop.

Now count what one chat turn needs. It holds an HTTP response open for five to sixty seconds while mostly waiting on a network socket. It keeps a detached background task alive after that response is gone, and an in-memory queue between the two. It runs a bounded wait on another conversation's background compaction. Under gunicorn's sync model, a hundred concurrent chat turns would need a hundred workers, each idle almost all of the time; and the durable task has nowhere to live, because a sync worker is not a place where anything continues to run after the response.

The split is therefore about concurrency model, not language performance. Django does short, transactional, CPU-and-database work where a worker per request is exactly right. The agent does long, IO-bound, streaming work where an event loop is exactly right.

And the file states the limit of its own design honestly. From the manager's docstring:

In-process is sufficient today (single Uvicorn process): cross-process live
re-attach is out of scope, and return-after-finish is covered by the existing
DB-replay duplicate-POST path. A future multi-replica scale-out would swap this
queue for a Redis-backed sidecar.

The queue is in this process's memory. Run two replicas behind a load balancer and a client that reconnects may land on the replica that is not running its turn: the run record is in Redis and visible, but the frames are not. That is why run-status plus the DB replay exist — they are the cross-process story, and they are enough because after the turn finishes, the answer is in Postgres, which every replica can read. Scaling out live re-attach would mean putting the frame queue in Redis too.

Quiz

Five questions on the machinery above. Click an option to see whether it is right and why.

1. A user asks a question, then closes the tab four seconds later while the answer is still being generated. With enable_durable_runs at its default, what ends up in the conversation?

The durable path hands iter_chat_stream an AlwaysConnectedRequest whose is_disconnected() is permanently False, so every disconnect-guarded early return is unreachable and the generator runs to completion inside a task the server owns. The HTTP request was only relaying frames off a queue; cancelling it touches nothing. The finalizer in the finally block is therefore cold on this path — “single writer by construction” — and the first option describes the pre-durability behaviour that this design replaced.

2. Where is the model told how many of its four searches remain, and why there?

_chat_search_budget_guidance writes “Search budget for this turn: 2 of 4 searches used, 2 remaining…” into the ok-path guidance of all three retrieval tools. Its docstring gives both reasons, and the second is a cost constraint shaping an architecture: the static rulebook in app/prompts.py is the cached prompt prefix, so injecting anything per-turn above the two trailing dynamic sections would defeat the discount on every chat turn. (The limit_exhausted result does exist — but it is the wall, not the warning.)

3. The browser re-sends a turn with a message_idempotency_key it already used. What decides between a replay and a 409?

Two facts are joined. created is False from the user write says “this exact message already exists”, and the conversation detail fetched before the write says whether that turn finished. Only when the last message is an assistant row does the route stream iter_replayed_chat_stream — the stored text in 80-character chunks, no model call, no new row. If the turn is still in flight the tail is the user message, so the last_message_role == "user" guard fires earlier in the ladder and answers 409; the client is expected to call run-status and re-attach instead.

4. The user presses 멈추기 during a long answer. Which component actually turns that click into something the conversation records?

Cancellation is cooperative and entirely mediated by two Redis fields. request_cancel sets cancel_requested and status = "cancelling" for the run's owner and returns; the generator checks _is_cancel_requested at each of its polling points (after preparing, after the compaction wait, per agent event, and once before the assistant write) and raises its own exception, which _emit_cancelled_generated_stream turns into a persisted assistant-cancelled message plus the closing frames. Nothing is killed — which is exactly why it works across the durable split, where the cancelling request and the running task share nothing but that key.

5. On a default chat turn, what does the LangGraph Postgres checkpointer hold that Django does not?

Two stores, two jobs. Django holds the conversation — user and assistant messages, citations, ownership — and is the memory across turns. sync_chat_agent_checkpoint unconditionally calls adelete_thread and rebuilds the thread from that history on every turn, precisely because a reused thread keeps prior turns' ToolMessages, i.e. document bodies with their post ids, in the model's context — the supply route for citing documents this turn never retrieved. So the checkpointer carries the run's state within a turn (that is what the reducers write through) and nothing across turns. The thinking level and model id are read fresh per turn, never cached per user.
