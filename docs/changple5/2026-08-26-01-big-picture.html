Big picture: three apps, one Postgres, one Redis, and how a request travels

Explainer 1 of the changple5 builder's curriculum. By the end you should be able to draw this system from memory: which processes exist, where each one lives, what talks to what over which channel, and the exact hops a browser request makes for a page, for an API call, and for a streaming chat turn.

Background

changple5 is the codebase behind 미라클, the product served at miracle.changple.ai: a Korean-language assistant for 창업가 (founders, mostly in 외식업 and services) that answers questions by citing a corpus of real Naver cafe posts and published articles, plus a content library and an operator console that keep that corpus fed.

What makes it a system rather than a program is that it is not one process. It is three application processes, two background processes, and two pieces of shared infrastructure, all started together by Docker Compose. If you built this by vibecoding, this is very likely the layer you never had to look at — and it is the layer every later explainer assumes. So we start here.

Skip if you know this

Five words that will recur constantly. If they are already familiar, jump to the cast.

Container — one process plus its filesystem, isolated from the host. Compose service — one entry in compose.yaml describing how to build and run a container. Compose gives every service a DNS name equal to its service name, so http://django_backend:8000 resolves inside the stack and nowhere else.

Reverse proxy — a server that sits in front of several backends and forwards each incoming request to one of them based on the URL. It is why a browser sees one origin (miracle.changple.ai) even though three different programs answer.

Schema (in PostgreSQL) — a namespace inside a single database, like a folder for tables. Two schemas in one database means one connection string, one backup, one pg_dump, but two disjoint sets of tables.

SSE (Server-Sent Events) — a long-lived HTTP response the server keeps writing to, one small event: / data: frame at a time, until it closes. It is how chat answers appear token by token instead of all at once.

WSGI / ASGI — the two Python web-server calling conventions. WSGI is synchronous (one request per worker at a time); ASGI is asynchronous and can hold thousands of idle connections open. Which one a service uses decides whether it can stream.

The cast: eight containers in dev, seven in production

The local stack (compose.yaml) defines eight services. Production (compose.prod.yml) defines seven — the difference is the front door, and it is the single most misunderstood fact about this system, so it gets its own section below.

Three of those run the same image: django_backend, celery_worker and celery_beat are all built from ./apps/backend. They differ only in the command they run and therefore in what they do. That is worth internalising early — a great many "why did my change not take effect?" incidents in this repo are a deploy that rebuilt the backend but not the two Celery roles.

The front door, and why production is different

In dev, infra/nginx/nginx.conf is a real reverse proxy running as the compose service nginx, publishing host port 80. Everything the operator's browser does goes through it.

In production, changple5 owns no front door at all. compose.prod.yml defines only the seven app/infra services, publishes no host ports (every service is expose:-only), and joins an external Docker network called changple_shared_network. Host ports 80 and 443, TLS termination, and the routing of miracle.changple.ai into these containers all belong to a separate compose project called edge (edge-nginx, living at /home/opc/edge on the production host), with Cloudflare in front of that.

The trap

The repo still contains infra/nginx/nginx.prod.conf. It is not mounted by anything and editing it changes nothing in production — it survives as a route-model and rollback artifact and now carries a banner saying so. This is not trivia: a past phase planned real front-door work as edits to that file, validated with nginx -t, and got a green check on a dead file. When you need to change production routing, gzip, or caching, the work is in the edge project (or in the Cloudflare dashboard), not here.

Source: docs/current/operations.md, sections Nginx — dev is in this repo, production is not and Production Environment.

What this means practically: the dev nginx config is still worth reading closely, because its routing contract is the contract the production edge must also satisfy — in particular the streaming block, which we come to next.

Intuition

One origin, three prefixes

Here is the whole system on one picture. Read it as: a browser only ever talks to one origin; the front door splits traffic by URL prefix; behind that, two Python apps share one database and one Redis.

Three prefixes, decided once, in the front door:

PrefixGoes toRead timeoutBuffering
/agent-api/fastapi_agent:80013600soff (streaming)
/api/django_backend:8000300sdefault
/nextjs_frontend:3000300sdefault
= /healthzanswered inline by nginx——
Why this shape matters

Those two columns on the right are not tuning knobs, they are the reason chat works. A proxy that buffers a response waits for it to finish before forwarding — which for a token-by-token SSE stream means the user sees nothing for thirty seconds and then everything at once. And a 300-second read timeout would cut a long consulting turn mid-answer. So /agent-api/ gets proxy_buffering off and a one-hour read timeout, and every other prefix does not. Whichever machine plays front door in production must satisfy the same contract.

One database, two schemas, one door between them

There is exactly one PostgreSQL database (changple) and exactly one Redis. But each is partitioned, and the partitioning is a security boundary, not a filing convention.

The consequence you will feel constantly in later explainers: the agent can read operator-managed configuration and document metadata straight out of Django's tables, but it can never write there. Anything the agent needs to persist — a conversation message, a rolling summary, a consulting report — it sends back to Django over HTTP, through Django's own validation. That is a deliberate design choice: there is exactly one program that may mutate the system of record, so its invariants (message alternation, entitlement checks, idempotency) cannot be bypassed.

Redis is partitioned the same way, by logical database number:

db/0 — Celery broker + results, and the agent's run / rate-limit / indexing registries db/1 — Django cache (KEY_PREFIX "backend") db/2 — the agent's retrieval and embedding cache (prefix agent:cache:)

The reason is blunt and worth remembering: cache.clear() in Django issues a Redis FLUSHDB. Because the Django cache lives alone on db/1, that command can never wipe the Celery queue or the agent's in-flight run registry. Partitioning by logical db turns a footgun into a no-op.

Trace A — a page load of /

Toy request: the operator opens https://miracle.changple.ai/.

1
browser GET / with cookies. One TLS connection, one origin.
↓
2
front door Path does not start with /api/ or /agent-api/, so the catch-all location / wins → nextjs_frontend:3000.
↓
3
nextjs_frontend Renders the landing page. Its server components may fetch from Django directly — the landing hero reads the operator-saved 첫 화면 문구 server-side so it never flashes default copy. The base URL for that server-side call is WEB_BACKEND_PROXY_TARGET, pinned in compose to http://django-backend:8000.
↓
4
django_backend Answers that server-side fetch from the backend schema; HTML goes back up the chain.
Two real bugs hide in step 3

First, the hostname is the hyphenated alias django-backend, not the underscore service name. Django checks the request's Host header against ALLOWED_HOSTS, which carries django-backend but not django_backend — so the underscore form resolves on the network and then answers 400 DisallowedHost, and the landing silently renders fallback copy while looking perfectly fine.

Second, the value is written literally in compose.prod.yml instead of being interpolated from the environment, because the env file carries a WEB_BACKEND_PROXY_TARGET=http://127.0.0.1:8000 line meant for direct pnpm dev runs — and inside the Next container, 127.0.0.1 is the Next server itself.

Trace B — an API call: GET /api/conversations/<nonce>

Toy request: the browser, holding an access-token JWT, asks for one conversation whose public identifier (a UUID the code calls a nonce) is 9b1f2c34-7e55-4a0d-8c31-2f6b0a91d7e4.

1
browser GET /api/conversations/9b1f2c34-… with Authorization: Bearer <access JWT>. The browser uses a relative base URL — the front-end config defaults backendBaseUrl to the string /api — so the call is same-origin and no CORS is involved.
↓
2
front door Prefix /api/ → django_backend:8000, 300-second read timeout.
↓
3
django_backend config/urls.py matches path("api/", include("conversations.urls")), which routes conversations/<uuid:nonce> to ConversationHistoryDetailView. Authentication turns the JWT into a user; the view scopes the query to that user.
↓
4
postgres_db The connection was opened with options=-c search_path=backend, so the unqualified table names in the ORM resolve inside the backend schema and nowhere else.
↓
5
back up A serializer renders JSON; the same three hops in reverse.

Everything under /api/ is Django, and config/urls.py is the complete map of which prefix belongs to which Django app. It is twenty-four lines long and worth memorising — we quote it in full in the Code section.

Trace C — a streaming chat turn: POST /agent-api/chat/stream

This is the trace that explains why the system has two Python apps at all. Toy request: a logged-in user types "배달 수수료 줄이는 방법 알려줘" into an existing conversation.

1
browser POST /agent-api/chat/stream with the same bearer JWT and a JSON body carrying conversation_nonce and the user's message.
↓
2
front door Prefix /agent-api/ → fastapi_agent:8001, with proxy_buffering off, proxy_request_buffering off, X-Accel-Buffering: no and proxy_read_timeout 3600s. Nothing is held back; frames flow as they are produced.
↓
3
fastapi_agent require_chat_caller_context verifies the JWT locally with JWT_SHARED_SECRET — no call to Django. It accepts exactly one of three credentials: a user bearer JWT, an X-Guest-Token (anonymous trial), or an X-Agent-Service-Token.
↓
4
fastapi_agent → django_backend Over HTTP, fetch_conversation_detail loads the conversation — forwarding the caller's own credential, not a service token. The route's own comment says why: "the backend — not this route — decides which sessions it may reach."
↓
5
fastapi_agent Runs the LangChain agent loop: retrieval tools search the pgvector tables in the agent schema, the model streams tokens back, and each one becomes an SSE frame.
↓
6
fastapi_agent → django_backend When the answer is complete, write_conversation_message POSTs it to /api/conversations/<nonce>/messages with an idempotency_key, so the turn is persisted in the system of record — by Django, through Django's rules.

What the browser actually receives is a single HTTP response of type text/event-stream that stays open for the length of the answer, carrying frames like these (toy data, real frame shapes):

event: message_start
data: {"run_id":"4c0e…","conversation_nonce":"9b1f2c34…","message_idempotency_key":"7a2…"}

event: status
data: {"run_id":"4c0e…","phase":"preparing","message":"…"}

event: status
data: {"run_id":"4c0e…","phase":"searching","message":"…"}

event: keepalive
data: {}

event: message_delta
data: {"delta":"배달 수수료를 "}

event: message_delta
data: {"delta":"줄이는 방법은 "}

event: message_end
data: {"run_id":"4c0e…","content":"배달 수수료를 줄이는 방법은 …","citations":[{"post_id":2418,…}]}

event: done
data: {"run_id":"4c0e…","status":"complete"}
Note the keepalive

Retrieval and a slow first token can leave a multi-second silence in the middle of a stream. An idle SSE connection looks dead to an intermediary proxy and to the client's own stall watchdog, so the agent interleaves event: keepalive frames through with_sse_keepalive. The trailing data: {} is not decoration — a browser SSE parser will not surface an event with no data line.

The two trust boundaries

Two secrets appear everywhere in this repo, and they do different jobs:

SecretShapeWho mints / who checks
JWT_SHARED_SECRET HS256 signing key Django mints user access tokens and guest tokens; the agent verifies them offline with the same key. No network round-trip per request — which is exactly why a rotation must land on both apps at once.
AGENT_BACKEND_SHARED_TOKEN Static shared string, sent as X-Agent-Service-Token Used for service-to-service calls in both directions (backend → agent indexing endpoints; agent → backend internal conversation endpoints). Compared with compare_digest, never ==, to avoid a timing side channel.

Explainer 2 owns these in full — how settings are resolved, how the schemas are pinned, and how operator-editable configuration is read live across the read bridge.

Code

Now the same story, in the actual files. Nothing below is paraphrase — read each quote against the file next to you.

1. compose.yaml — the dev stack

Eight services. The five application services carry profiles: ["stack"], so a bare docker compose up starts only postgres_db and redis (handy when you run Django on the host); --profile stack brings up the whole routed stack. The operator's actual command is make stack-up.

Startup order is not left to luck — every app service declares depends_on … condition: service_healthy against a real healthcheck:

compose.yaml — fastapi_agent

    depends_on:
      postgres_db:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test:
        [
          "CMD",
          "python",
          "-c",
          "import sys, urllib.request; response = urllib.request.urlopen('http://127.0.0.1:8001/agent-api/health', timeout=5); sys.exit(0 if response.status == 200 else 1)",
        ]

Four named volumes carry the state that must outlive a container:

  • pg_data — the PostgreSQL data directory.
  • redis_data — the Redis append-only file.
  • backend_media — uploaded and generated media, mounted into the backend, the worker and beat at /workspace/media/backend.
  • scraper_state — the persisted Naver login session used by the ingestion scraper.

All services join one bridge network, app_network, and address each other by service name through Docker's embedded DNS.

Volume gotcha

backend_media is a Docker volume, not a host bind mount. Copying files into the host's media/backend/ directory does nothing that the containers can see — you must docker cp into the volume.

2. compose.prod.yml — the delta

Same seven app/infra services, minus nginx. The differences worth knowing:

  • Serving mode. The backend runs migrate --noinput && exec gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers ${GUNICORN_WORKERS:-3}. Migrations therefore apply on container start, not as a separate deploy step.
  • No host ports. Every service is expose:-only.
  • Two networks. nextjs_frontend, django_backend and fastapi_agent also join changple_shared_network, declared external: true — it must already exist on the host. This is how the separate edge front door (and the co-hosted changple_web app) reach these containers by service name without going back out through Cloudflare.
  • Required env is enforced. Dev uses ${VAR:-default}; production uses ${VAR:?VAR is required}, so a missing secret fails the deploy loudly instead of silently defaulting.
  • Env is passed by YAML anchors, &backend_env and &agent_env, merged into each service with <<: *backend_env. There is no env_file: at all — which means a variable that is not listed in this file reaches no container, however carefully you set it in .prod.env. That exact gap has bitten this repo repeatedly; the file's comments are a museum of it.
  • celery_worker adds --concurrency=2, because the production box is a shared 4-core VM that also runs another site's SSR.

3. infra/nginx/nginx.conf — the dev front door, in full

This file is short enough to read entirely, and every line earns its place.

infra/nginx/nginx.conf (abridged only where repetitive)

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    location = /healthz {
        access_log off;
        add_header Content-Type text/plain;
        return 200 "ok\n";
    }

    location /agent-api/ {
        proxy_pass $fastapi_agent_upstream;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_cache off;
        chunked_transfer_encoding on;
        proxy_read_timeout 3600s;
        add_header X-Accel-Buffering no;
    }

    location /api/ {
        proxy_pass $django_backend_upstream;
        proxy_http_version 1.1;
        proxy_read_timeout 300s;
    }

    location / {
        proxy_pass $nextjs_frontend_upstream;
        proxy_http_version 1.1;
        proxy_read_timeout 300s;
    }

Two details that look like style but are not:

resolver 127.0.0.11 is Docker's embedded DNS server, and the upstreams are written as set $var variables rather than literal hostnames. When an nginx proxy_pass target contains a variable, nginx resolves it at request time through that resolver instead of once at startup. The practical effect: restarting fastapi_agent (new container, new IP) does not require restarting nginx.

client_max_body_size 500m is global, and it is the ceiling on uploads through the dev front door. Production's ceiling is whatever the edge project and Cloudflare enforce — which is a different number, in a different repo.

4. infra/postgres/init/00-bootstrap.sh — the two schemas and the bridge

This script runs once, on the very first boot of an empty pg_data volume (that is the contract of /docker-entrypoint-initdb.d). It is written as a psql heredoc using SELECT format(…) plus \gexec — a standard trick, because PostgreSQL has no CREATE ROLE IF NOT EXISTS: you build the DDL as a string and execute the result.

It does five things.

(a) Turns on pgvector — CREATE EXTENSION IF NOT EXISTS vector;. This is what makes similarity search possible at all; the agent's index tables use it.

(b) Creates two login roles, asymmetrically:

'CREATE ROLE %I LOGIN CREATEDB PASSWORD %L'   -- django_user
'CREATE ROLE %I LOGIN PASSWORD %L'            -- fastapi_user

Only the Django role gets CREATEDB, and only for one reason: Django's test runner creates and drops a throwaway test database.

(c) Closes the default door — REVOKE CREATE ON SCHEMA public FROM PUBLIC;. Without this, any role could create tables in public, and the whole isolation story would be advisory.

(d) Creates one schema per app, owned by that app's role, and pins each role's default search_path so an unqualified SELECT lands in its own schema:

'CREATE SCHEMA IF NOT EXISTS %I AUTHORIZATION %I'      -- backend / django_user
'CREATE SCHEMA IF NOT EXISTS %I AUTHORIZATION %I'      -- agent   / fastapi_user
'ALTER ROLE %I IN DATABASE %I SET search_path TO %I, public'

(e) Opens the one-way read bridge. These are the exact three statements — there is no mirror-image grant anywhere in the file:

SELECT format(
  'GRANT USAGE ON SCHEMA %I TO %I',
  :'django_schema',
  :'fastapi_user'
);
\gexec

SELECT format(
  'GRANT SELECT ON ALL TABLES IN SCHEMA %I TO %I',
  :'django_schema',
  :'fastapi_user'
);
\gexec

SELECT format(
  'ALTER DEFAULT PRIVILEGES FOR ROLE %I IN SCHEMA %I GRANT SELECT ON TABLES TO %I',
  :'django_user',
  :'django_schema',
  :'fastapi_user'
);
\gexec

The third statement is the subtle one. GRANT SELECT ON ALL TABLES applies only to tables that exist right now; a table created by a later Django migration would be invisible to the agent. ALTER DEFAULT PRIVILEGES makes the grant apply to every future table django_user creates in that schema. Without it, the read bridge would silently rot with each migration.

Where the pinning is enforced in application code

The role default above is a safety net; both apps also pin explicitly.

apps/backend/config/settings.py

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        …
        "OPTIONS": {
            "options": f"-c search_path={DATABASE_SCHEMA}",
        },
    }
}

apps/backend/core/db.py adds ensure_backend_schema, connected to Django's connection_created signal in core/apps.py: on every fresh connection it creates the schema if missing and re-issues SET search_path. On the agent side, apps/agent/app/db/connection.py takes the belt-and-braces route — it schema-qualifies table names explicitly (qualify_table_name), builds an explicit -c search_path=<schema>,public conninfo for the LangGraph checkpointer, and calls register_vector(connection) on every connection, a per-connection side effect without which vector columns do not round-trip. Explainer 2 walks all of this properly.

5. apps/agent/app/main.py — how the agent process comes up

124 lines, and they tell you the shape of the whole service.

create_app() (line 103) builds the FastAPI app with docs_url=None, redoc_url=None, openapi_url=None — the interactive docs are deliberately off, because this service is reachable from the public front door. It attaches RequestIDMiddleware (correlation IDs, explainer 2) and then the one line that defines the service's entire URL space:

apps/agent/app/main.py:120

    app.include_router(api_router, prefix="/agent-api")

That prefix is why the nginx rule works and why the agent's own health endpoint is /agent-api/health rather than /health. The router it mounts is assembled in apps/agent/app/api/routes/__init__.py from eight modules:

chatretrievalindexing chunk_indexingcontent_chunk_indexing content_draftsconsulting_reports health

Eight modules, and only seventeen routes in total. That is the agent's entire public surface — worth appreciating, because nearly all of its ~36,000 lines sit behind those seventeen doors.

The lifespan (line 42) is FastAPI's startup/shutdown hook: everything before yield runs once at boot, everything after runs once at shutdown. On the way up it builds six Redis-backed registries onto app.state — the chat run registry, the guest rate limiter, the retrieval rate limiter, and three indexing run registries (documents, post chunks, content chunks). On the way down, the order is deliberate and commented:

apps/agent/app/main.py:63-80

    try:
        yield
    finally:
        # Let in-flight durable runs finish (and persist their real answers) before
        # the Redis registry they write through is closed, so a graceful deploy
        # does not strand a `user` tail.
        durable_manager = getattr(app.state, "durable_chat_run_manager", None)
        if durable_manager is not None:
            await durable_manager.drain(
                timeout=app.state.settings.durable_run_shutdown_drain_seconds
            )
        # P39.S4: shared backend httpx client -- closed only after the
        # durable-run drain above, since a draining run still calls the
        # `chat/backend.py` helpers to persist its real answer.
        await aclose_backend_http_client()
        # P39.S5: close the lazily-built retrieval/read cache (db/2) if any
        # retrieval touched it during this process's lifetime.
        await aclose_retrieval_cache()

Read that as a small lesson in shutdown ordering. A chat turn that is mid-flight when a deploy starts still needs two things: an HTTP client to POST its answer to Django, and a Redis registry to record that it finished. So the drain happens first, the HTTP client closes second, and the registries close last. Reverse any two of those and a deploy strands a conversation with a user message and no answer.

Note also what is not opened at startup: the HTTP client to Django and the db/2 retrieval cache are both built lazily on first use (see get_backend_http_client in apps/agent/app/chat/backend.py) and merely closed here. And there is no database connection pool — the agent opens short-lived psycopg connections per unit of work. The schema tables themselves are created before uvicorn even starts, by the container command python -m app.db.bootstrap && exec uvicorn app.main:app.

6. apps/agent/app/api/routes/health.py — health vs readiness

A tiny file that teaches a distinction worth having:

@router.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok", "service": "agent"}

/agent-api/health is liveness: it answers "this process is running" and touches nothing else. That is precisely what a container healthcheck should ask — if it depended on Postgres, a database blip would make Docker kill and restart a perfectly healthy agent.

/agent-api/ready is readiness: it pings the Redis chat-run registry and fetches Django's /api/health with a hard 2-second timeout, then answers 200 with {"redis": "ok", "backend": "ok"} or 503 naming the unavailable dependency. The comment states the design rule: "a slow backend should degrade readiness (503) rather than hang the probe."

Django has the mirror pair at /api/health and /api/ready, wired in apps/backend/core/urls.py. Both compose files use the liveness endpoint for their healthchecks.

Twelve Django apps, and the mapping is not always the obvious one — three details to note:

8. asgi.py vs wsgi.py — which one actually serves

Both files exist, both are the Django defaults, and only one is used: compose.prod.yml runs gunicorn config.wsgi:application, and dev runs manage.py runserver. Nothing in the repo references config.asgi at all.

So Django here is synchronous, served by three sync gunicorn workers, each handling exactly one request at a time. That is a perfectly reasonable choice for CRUD over Postgres — and it is also the structural reason the streaming half of the product lives in a separate FastAPI process. Holding hundreds of minute-long SSE connections open on sync workers would consume the whole pool; on uvicorn's async event loop it costs almost nothing. The two-app split is not fashion, it is a concurrency-model split.

Quiz

Five questions. Click an option to see whether it is right and why.

1. A change to the production nginx routing is needed: the streaming timeout must go from one hour to two. Where do you make it?

Production's front door is the standalone edge project (edge-nginx, /home/opc/edge); compose.prod.yml has no nginx service at all. infra/nginx/nginx.conf is the live dev front door, and nginx.prod.conf is an unmounted rollback artifact — editing it and getting a green nginx -t proves nothing about production.

2. The agent has finished generating an answer and must persist it. What does it actually do?

The read bridge is one-way: fastapi_user is granted USAGE + SELECT on the backend schema and nothing more, so an INSERT is impossible by construction. Persistence goes through write_conversation_message in apps/agent/app/chat/backend.py, which POSTs to Django with an idempotency_key — so exactly one program mutates the system of record, enforcing its own invariants.

3. Why does the bootstrap script run ALTER DEFAULT PRIVILEGES FOR ROLE django_user IN SCHEMA backend GRANT SELECT ON TABLES TO fastapi_user in addition to GRANT SELECT ON ALL TABLES?

GRANT … ON ALL TABLES IN SCHEMA is a one-shot expansion over the tables present when it runs. ALTER DEFAULT PRIVILEGES attaches the grant to everything django_user creates in that schema from then on. Without it the read bridge would silently rot: each new Django migration would add a table the agent cannot see.

4. Redis holds the Celery queue, the Django cache and the agent's retrieval cache. Why are they on logical databases 0, 1 and 2 rather than sharing one?

Straight from the policy comment in settings.py: logical databases partition the single Redis instance "so no app can ever flush another's keyspace." cache.clear() issues FLUSHDB against db/1 alone. Logical databases share the instance's memory — they are a namespace boundary, not a resource limit — and Celery is perfectly happy on any db number.

5. Chat streams live in FastAPI while CRUD lives in Django. Which statement best explains the split, given how each is served?

The deciding factor is the concurrency model. compose.prod.yml runs gunicorn config.wsgi:application --workers 3 — sync workers, one request each, so a handful of minute-long streams would block the whole backend. The agent runs uvicorn app.main:app on an async event loop, where an idle open connection costs almost nothing. (Django can stream via ASGI — but config/asgi.py is referenced nowhere in this repo.)
