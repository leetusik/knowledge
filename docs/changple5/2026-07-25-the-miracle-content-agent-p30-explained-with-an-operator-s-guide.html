Changple has years of Naver Cafe posts about opening and running small food-and-service businesses, already indexed and searchable. Background

What "Miracle content" is

Miracle (미라클, at miracle.changple.ai) is Changple's paid-ish content catalogue — long, photo-heavy case studies about opening a real shop. Each article is a row in the Django model content.NotionContent. The article body is not stored in the database: it is a folder of HTML plus images on disk under MEDIA_ROOT/html_content/{id}/, and the row's html_path column doubles as the visibility flag — empty path, invisible article.

How an article got there before P30

Entirely by hand. A human wrote the piece in Notion, exported it as a ZIP, and uploaded it through the operator console. The backend chunked the upload into a ContentUploadSession, queued a ContentImportJob, and a Celery task (content.run_import_job → import_uploaded_zip) unpacked the ZIP, rewrote the relative asset paths, and swapped the finished directory into place. Good machinery — but every word of every article was still written by a person.

Meanwhile, a completely separate part of the system had been quietly accumulating something valuable: an indexed corpus of Naver Cafe posts (thousands of them, with vector embeddings and per-image alt text generated by Gemini), used by the consulting agent to ground its answers. P30's premise is a single observation — that corpus is not just reference material for answering questions, it is raw material for writing new articles.

Three ideas worth having straight before we go on

Retrieval-augmented generation (RAG), in one paragraph. A language model knows nothing about Changple's cafe archive. So instead of asking it to recall, you retrieve: turn a question into a search over your own documents (here: a hybrid of pgvector similarity and a Gemini re-ranking pass), pull back the most relevant posts, paste their text into the prompt, and ask the model to write only from that. The model supplies fluency and structure; your corpus supplies the facts. Grounding is the whole point — an ungrounded draft about 상권 분석 would be plausible, generic, and useless.

"Job-shaped", not "chat-shaped". Changple already has a streaming chat architecture (server-sent events, nonce routing, JWT claims). P30 deliberately did not reuse it. Generating one article takes minutes and involves a dozen model calls; the operator will close the laptop halfway through; the whole thing must survive a page reload, a worker crash, and a deploy. So the unit of work is a row in a database — a ContentDraftJob with a status column — advanced by Celery tasks, and the browser simply polls it every 2.5 seconds. Nothing lives in memory. If the browser vanishes, the job carries on.

Human-in-the-loop (HITL). An agent that autonomously publishes to a live catalogue is a bad idea, and P30 never entertained it. The design instead places explicit human gates where the agent must stop and wait. Which gates, and why those two, is the subject of the next section.

Who can use it

This is an admin-only internal tool. Every endpoint sits behind IsOperatorUser (user_type == "admin"), and the browser never talks to the agent service directly — the Django backend brokers every generation call with a shared service token. It is also PC-web only, by explicit decision: there is no mobile layout and none is planned.

Intuition

The naive version, and why it fails

The obvious design is: operator types a brief → agent searches the corpus → agent writes the article → operator reads it and says yes or no. One shot.

This fails in a specific, expensive way. A 6,000-character illustrated article costs several model calls to produce. If the operator reads it and says "no, this should have been about the build-out timeline, not the menu", every one of those calls is wasted — and the feedback arrives at the point where it is most costly to act on. Worse, a single "write the whole article now" prompt tends to drift: by section 12 the model has forgotten the voice it established in section 2.

The shape P30 actually took

Split the work at its natural seam, and put a human at each one. The agent proposes a 구성안 (an abstract draft: a title, a table of contents, and a plan for which photos go where) and stops. That is cheap to produce and cheap to reject. Only once the operator approves the shape does the expensive writing begin — and even then it happens section by section, each call seeing the approved outline and the sections already written, followed by one integration pass that stitches everything into a single coherent voice.

The mechanic that makes it all work: turn precedence

Here is the part worth understanding properly, because everything else follows from it. There is exactly one generation endpoint on the agent service. It does three completely different jobs, and which one it does is decided by two fields in the payload — nothing else:

latest_version is not None   →  REVISE turn   (research if needed, then edit the existing draft)
approved_outline is not None →  WRITE turn    (skip research entirely, write the approved 구성안)
neither                      →  OUTLINE turn  (research, then propose a 구성안 — never writes a body)

Read it top to bottom: once a version exists, every future turn is a revision, so the agent can never wander back and re-propose an outline. And an approved outline is only sent while no version exists — the write turn happens exactly once.

The elegance is in what the WRITE turn doesn't do. It does not research. When the outline turn finishes, it stores its entire research state — which posts it read, which corpus photos it found, keyed by the same identifiers — inside the outline row. The write turn rehydrates that state deterministically. So approving a 구성안 means "write exactly this, from exactly the material you showed me", not "go off and think again". No second research bill, no drift between what you approved and what gets written.

A worked example

Suppose you brief it with "성수동 5평 테이크아웃 커피 매장 오픈기 — 보증금·권리금 협상과 초기 비용 통제 중심으로".

  • Research turn. A fast model (gemini-3.5-flash) is given two tools, search_cafe_posts and read_posts, and left to drive. It searches 소형 매장 권리금 협상 테이크아웃 커피 초기 비용, gets candidate post IDs back, decides which ones to read in full, maybe searches again. It stops when it stops calling tools, or when it hits a cap: 8 searches, 24 documents, 6 loop iterations.
  • Gate + outline. A stronger model looks at the brief plus everything read and asks: is there enough here? If yes, it emits a title, ~8 sections with key points, and an image plan — slots saying "this section gets 2 photos, and here are the candidates from the corpus". If genuinely not enough, it can pause once and ask you questions instead.
  • You approve. Or you type "section 4 and 5 should be one section, and add something on 인테리어 견적 비교" — which re-runs the outline turn with your feedback and replaces the proposal.
  • Write. 8 model calls, one per section, each seeing the approved outline and the previous sections, each placing image markers for its assigned photos. Then one integration call over the whole body: write the intro, smooth the seams, remove repetition.
  • v1 appears. With photos in it. You revise, or edit the markdown yourself, or approve it.

How photos get in — the marker grammar

The model never handles image bytes or URLs. It places a placeholder, {{img:<uuid>}}, and the position of that placeholder on the line is the layout instruction:

매장을 처음 봤을 때는 이런 상태였습니다.

{{img:8f3a…}}                        ← alone on its line = one full-width figure

철거 후, 배관과 전기 위치를 다시 잡았습니다.

{{img:1c07…}} {{img:b42e…}} {{img:9dd1…}}   ← 2–3 on ONE line = a side-by-side row

Figure 2 — the whole image layout language. Two rules, and they are honoured identically in the workspace preview, the published HTML, and the archive mirror.

The subtle decision behind this: a photo pulled from a cafe post and a photo you uploaded from your desktop become the same kind of thing — an attachment row whose primary key is the marker's uuid. Corpus images are minted a uuid by pipeline code before the model ever sees them, so the model just places markers as usual; afterwards the backend downloads whichever ones survived into local storage. Because the stored text never needs rewriting, the preview renderer, the publisher, and the thumbnail picker required zero changes when corpus images were added. That is the reward for choosing a representation carefully.

Operator's guide

What follows is the real loop, in the order you will actually do it. Everything in monospace or quoted in Korean is a literal label on screen.

Before you start

A full run costs real money — a flash-model research loop plus one strong-model call per section plus an integration pass. A cancelled job still costs whatever it already spent. Editing the draft yourself costs nothing. And on a passing run you will create a live article in the Miracle catalogue; if you are just exploring, delete it afterwards from the operator content console.

  1. Get in

    Go to /operator/content in the operator console and click the 미라클 에이전트 button. That takes you to /operator/miracle-agent, which deliberately looks like nothing else in the console: no header, no nav sidebar, full screen. There is no menu entry for it — the button is the only door.

  2. Read the landing screen

    Two things to notice. The recent-jobs list lets you re-open any past job. And the leftmost item in the composer footer is the 기준 콘텐츠 chip — the standing format reference.

  3. Understand the 기준 콘텐츠 (and change it if you want)

    The agent doesn't invent a house style from nothing. It extracts the structure and tone of one existing Miracle article and adapts them. By default that is content id 19 ("김태용의 섬집 병점점, 골목 상권의 한계를 극복하는…") — a ~6,700-character piece with 54 interleaved photos, 18 numbered chronological process sections, first-person-plural 창플 voice, and concrete numbers throughout.

    Click the chip on the landing to open a small settings popover, type a different content id, and save. Invalid ids are rejected immediately (존재하는 콘텐츠 ID를 입력해 주세요). Note the hint: 변경은 다음 새 작업부터 적용됩니다 — each job snapshots its reference at creation, so changing the setting never rewrites a job already in flight. On the job screen the chip is therefore read-only.

    The reference supplies format and tone only — never substance. Substance comes from your brief plus the cafe corpus. If a draft ever reads like a rigid clone of #19, that is a bug, not the design.

  4. Write the brief

    Type what you want written. Be concrete about the subject and the angle — that text drives both the corpus search and the outline. You may attach photos with captions using the 📎 button, but you do not have to: working with zero operator input is the designed default, and the agent will source its own photos from the corpus.

  5. Watch it research

    After you send, the thread's activity area becomes a live transparency panel — not a spinner. You see the agent's actual search strings as chips, and a running count in the shape 카페 글 N건 검색 · M건 정독 (N surfaced, M read in full). Rows track 카페 자료 수집 → 구성안 제안.

    Red flag

    If you see a generic spinner with no query chips and no counts, the progress channel between the agent and the backend is dead. The work may still complete, but you have lost all visibility into what the agent actually read.

  6. Possibly answer one round of questions

    If the brief plus what it found are genuinely too thin, the agent pauses once with a structured card: numbered questions, plus a 필요한 사진 block with 약 N장 count pills. You have two options, and both work:

    • Answer in the composer, or
    • press 건너뛰기 — which posts a plain "답변 없이 진행해 주세요." message and lets it proceed regardless.

    It is guaranteed never to ask twice in the same job. That guarantee is enforced in two places (the prompt is rebuilt without the ask option, and there is a code-level backstop if the model tries anyway), so you cannot get stuck in a question loop.

    This is the cheapest place in the whole system to change your mind, so spend time here. The canvas shows the proposed title, the numbered table of contents with key points, and the image plan. Each image slot is badged either 코퍼스 있음 (the agent already has candidate photos — and you can see actual thumbnails of them, click to open the source) or 운영자 추가 · 선택 (a spot where an operator photo would help; always optional, never blocking).

    Two moves available:

    • Reshape it — type feedback into the thread. This re-runs the outline turn and replaces the proposal with a new one. Repeat as often as you like.
    • Approve it — press 구성 승인 · 작성 시작. Single click, no confirmation, because nothing irreversible happens.

  8. Watch it build

    The thread panel switches to a per-section build read-out: a row per outline section, a N / M counter as it advances, and a final 통합 · 이미지·인용 정리 row while it stitches everything together. Section count should match the outline you just approved. When it lands, v1 appears in the artifact pane.

  9. Read v1 properly

    The right pane now shows the draft as a document card: real corpus photos placed inline, some full-width, some in 2–3-across rows, with captions from the auto-generated alt text. A version stepper reads v1 / 1.

    You will also see things a reader never will: [n] citation markers in the text, and a collapsible sources panel listing the cafe posts behind the draft. These are review aids. They are stripped at publish time — deliberately, per the project rule that the public copy carries no source markers.

  10. Change it — three different tools

    (a) Ask the agent to revise. Type feedback. Afterwards the artifact header tells you what it actually did: a pill reading 부분 편집 · N곳 (it made N targeted find-and-replace edits, everything else byte-identical) or 전체 재작성, plus v{base} 기반. Press 변경 보기 to swap the card for a word-level diff — additions highlighted, deletions struck through, with a legend. Small requests should produce 부분 편집; if a one-line tweak triggers a full rewrite, be suspicious.

    (b) Revise an older version. Step the version stepper back to, say, v1 while v3 exists, and leave feedback there. The composer placeholder confirms it (v1에 대한 수정 요청을 적어 주세요) and the revision genuinely bases on v1 — this was a real behavioural fix, not just a label.

    (c) Edit it yourself. 초안 직접 수정 opens the raw markdown in a textarea. Save, and you get a new version marked operator-origin. No model call is made — this is free and instant. If you ever see an activity indicator after a manual save, something is wrong.

  11. GATE 2 — approve and publish

    승인 → 정말 승인하시겠어요? → 승인 확정. Two steps, on purpose: this is the only irreversible action in the tool.

    Important

    Approval publishes the version currently on screen, not necessarily the newest one. If you stepped back to compare v2 and v4, check the stepper before you confirm.

    The job then moves 승인됨 → 게시 중 → 게시됨 on its own, without a reload, and a 게시된 콘텐츠 보기 link appears. Open it. This is the moment of truth.

  12. Check the published article

    Read it as a reader would. It must contain none of the following:

    • any [1] / [n] citation numbers,
    • any [post:123] internal markers,
    • any leftover {{img:…}} placeholder text,
    • a sources / 근거 카페 글 list,
    • a bare Post 4821 string (a known leak shape from posts whose titles were backfilled),
    • any cafe.naver.com URL.

    Photos should render with captions, and should be served from your own /media/… — never hotlinked from a Naver host. Any of these appearing publicly is a content-safety failure, not a cosmetic bug.

Rules of thumb

Spend your attention at GATE 1 — restructuring is nearly free there and expensive later. Prefer 초안 직접 수정 for wording nits (free, instant, exact) and save agent revisions for changes that need re-grounding in the corpus. And always open the published article before you walk away.

Code

Three services are involved: Next.js (apps/web) for the workspace, Django (apps/backend) which owns all state and every gate, and a FastAPI agent service (apps/agent) which owns the model calls and owns no state at all. Let's follow one article through.

1. The door and the chrome-free shell

The entry point is a plain link on the existing content page (operator-content-workspace-route.tsx):

<Link href="/operator/miracle-agent" data-testid="operator-content-agent-entry">
  미라클 에이전트
</Link>

Full-screen-ness is achieved without a second auth system. operator-shell.tsx branches on usePathname(): anything under /operator/miracle-agent renders the shared OperatorAdminGate with variant="standalone" — same admin gate, same four non-admin states (loading, login, denied, bootstrap error), but the header/nav wrapper is dropped. Every other operator route is byte-identically unaffected.

2. The data model

apps/backend/content/models.py holds seven models. The ones that carry the design:

  • ContentDraftSettings — a singleton row holding reference_content_id, default 19. Notice it is a PositiveIntegerField, not a foreign key, and the docstring says why: the configured id may not exist in every environment, and resolution must fail soft with a clear job error rather than explode at the FK layer.
  • ContentDraftJob — the unit of work. UUID pk, the twelve-value status enum, a snapshotted reference_content_id, Celery bookkeeping (generation_task_id, generation_attempt_count), a schema-light progress JSON blob for the live panel, and published_content — an FK to NotionContent that acts as the publish idempotency anchor.
  • ContentDraftVersion — immutable, append-only, numbered per job. base_number records which version it was derived from and revision_meta records {mode, edit_count} for an agent revision. Both are plain columns, so lineage is queryable rather than buried in an audit message.
  • ContentDraftAttachment — a UUID pk that is the {{img:uuid}} marker key. A non-empty source_url marks the row as corpus-sourced; empty means an operator upload. No enum, no second table.
  • ContentDraftOutline — the 구성안, with a proposed → superseded | approved status so the reshape history survives.

3. Dispatch: how a message becomes model work

content/draft_dispatch.py is a close clone of the existing consulting-report dispatcher, which is deliberate — it is the house pattern for "backend asks the agent to do something slow". The shape:

  • Queueing happens after commit (transaction.on_commit), so a task can never start against a row that hasn't landed.
  • DRAFT_GENERATION_MAX_ATTEMPTS = 3, with transient vs permanent error classification — a 503 from the agent retries, a missing reference article does not.
  • Two status sets that intentionally differ: QUEUEABLE (which jobs may be dispatched and claimed) includes requested; STALE (which jobs the crash-recovery sweep may re-claim) excludes it.
  • The actual call is plain urllib with an X-Agent-Service-Token header — the browser has no admin claim in its JWT, so brokering through the backend is the authorization boundary.

The payload builder is where turn precedence is decided. This is the part worth reading closely:

# content/draft_dispatch.py — _build_generation_payload

max_number_version = job.versions.order_by("-number").first()
targeted_message = (
    job.messages.filter(
        role=ContentDraftMessage.Role.OPERATOR,
        kind__in=(Kind.FEEDBACK, Kind.ANSWER),
        version_id__isnull=False,
    ).select_related("version").order_by("-created_at", "-id").first()
)
latest_version = (
    targeted_message.version if targeted_message is not None else max_number_version
)

# WRITE turn: a job with an approved 구성안 and no version yet carries the
# stored outline so the agent skips research and writes against it.
approved_outline = None
if latest_version is None:
    outline_row = job.outlines.filter(status=APPROVED).order_by("-number").first()
    if outline_row is not None:
        approved_outline = outline_row.payload

That first block is the fix that makes "step back to v1 and leave feedback" mean something. The revise base is not the highest-numbered version — it is the version your most recent targeted message pointed at. The field name in the payload stayed latest_version; only which row it resolves to changed.

4. The agent pipeline

apps/agent/app/content_drafts/agent.py — one entry point, run_content_draft_pipeline, whose branch mirrors the precedence rule exactly:

is_revision  = latest_version is not None
is_write_turn = (not is_revision) and (approved_outline is not None)

if is_write_turn:
    doc_map = await _rehydrate_doc_map(settings, approved_outline)      # no research
    corpus_candidates = _rebuild_corpus_candidates(approved_outline)    # same keys
else:
    doc_map, research_stats = await _run_research_loop(..., flow=("revise" if is_revision else "outline"))

The research loop is the one genuinely agentic part. A flash model is bound to two tools and left to plan its own reading; the loop dispatches each tool call by hand, accumulates a doc_map of {post_id: {meta, body}}, and stops on a no-tool-call response or at MAX_RESEARCH_ITERATIONS = 6. Caps are enforced inside dispatch rather than by trusting the prompt — past 8 searches the tool simply returns "검색 한도에 도달했습니다. 정리해서 마치세요." Each search and read then emits a progress payload with the real query strings and truthful cumulative counts, which is what you see as chips in the UI.

The gate (_gate_and_outline) decides "enough material?" and either emits asks or an outline. The never-ask-twice guarantee is two-layered: allow_asks=not _has_prior_asks(messages) rebuilds the prompt without the asks option, and if the model returns needs_input anyway the result is coerced to draft mode in Python. Prompt instruction plus deterministic backstop — the guarantee doesn't depend on the model complying.

The write is a per-section call (_write_section, which sees the approved outline, its own section's key points, and the previous sections) followed by _integrate_sections over the whole body. Integration subsumes the older reflection pass — they are never both run. If integration fails, sections are simply concatenated: a degraded article beats no article.

The revise returns (mode, body, note, edit_count). In edits mode the model returns a JSON block of find/replace pairs, and _apply_edits applies each one only if its find string occurs exactly once; otherwise the entire edit set is discarded and it falls back to a full rewrite. That strictness is what makes "untouched text stays byte-identical" a real promise rather than a hope — and edit_count is computed from the applied edits, never self-reported by the model.

5. Corpus images

Selection lives in content_drafts/images.py: build_corpus_image_inventory keeps only images that have generated alt text, excludes URLs already attached to the job, mints a uuid4 per candidate, and round-robins one image per post so a single photo-heavy post can't dominate. Crucially, images are offered only from posts the research loop actually read — relevance follows the agent's own reading choices.

Download happens backend-side at result-apply time (content/draft_images.py), outside the locked transaction, and is guarded: HTTPS only, host must end in *.pstatic.net, content type must be image/*, ~15 MB cap enforced both on the declared length and while streaming. Anything failing those checks is dropped fail-soft — its marker is stripped from the body, one Korean system message notes the drop count, and the version still lands. A photo failing to download never fails the article.

6. Publish — the part that must be right

Approving writes the decision and queues the publish task in the same transaction. Then content/draft_publish.py:

  1. Anchors identity first. _ensure_published_content creates the NotionContent row with an empty html_path before any file work — so it is invisible to readers, and any retry or crash-recovery re-publish reuses the same content id instead of littering the catalogue with duplicates.
  2. Splits blocks with _split_blocks, a line-level mirror of the frontend's splitMiracleAgentArtifactBlocks. Same regex, same buffering rules — which is why the preview and the published page agree about what is a row and what is a full-width figure.
  3. Scrubs every markdown chunk, the title, and the description through publish_scrub.py.
  4. Renders lone markers as <figure> and same-line groups as <div class="column-list">, into a document whose <h1 class="page-title"> comes first — the public reader detects that canonical header and suppresses its own duplicate title.
  5. Swaps the directory atomically, reusing the very same primitives the ZIP importer uses. Only then is html_path filled in and the article becomes visible.

The scrub itself is 56 lines of pure Python with no Django imports, so it is trivially testable in isolation. The order matters and the comments say why:

# content/publish_scrub.py
def scrub_public_text(text: str) -> str:
    without_internal    = _INTERNAL_CITATION_MARKER_RE.sub("", text)   # [post:123]
    without_cafe_url    = _CAFE_URL_RE.sub("", without_internal)       # cafe.naver.com/...
    without_visible     = _strip_visible_citation_markers(without_cafe_url)  # [1]..[50]
    without_post_title  = _BACKFILLED_POST_TITLE_RE.sub("", without_visible) # "Post 4821"
    return _IMAGE_MARKER_RE.sub("", without_post_title)                # {{img:uuid}}

Note the one piece of real judgment in there: visible [n] markers are stripped only for n ≤ 50. Above that the bracketed number is far more likely to be a year or a quantity in the prose than a citation, so it is preserved. And Post \d+ is stripped because of a previously-discovered leak: posts with empty titles get backfilled to the literal string Post {post_id}, which is an internal identifier wearing a title's clothes.

Failure semantics

Any exception during publish returns the job to 검토 대기 — never failed, which stays reserved for generation. It sets an error detail and writes a Korean system message telling the operator to approve again. Because materialization is idempotent and identity was anchored up front, "approve again" is a complete recovery procedure, and the reclaim sweep needs no attempt ceiling.

7. One progress channel, two payload shapes

Live progress could easily have become two half-built systems. It didn't, and the discipline is explicit in the code comments. There is one path:

agent  content_drafts/progress.py :: emit_draft_progress()     # fail-silent, ~5s timeout,
   ↓                                                          # swallows every error
backend POST /api/content/internal/miracle-agent/jobs/<uuid>/progress
   ↓        (X-Agent-Service-Token; 204 no-op unless the job is actively generating)
        ContentDraftJob.progress  (JSONField)
   ↓
web    2.5s poll → getMiracleAgentBuildProgress() → the staged panel

Two payload variants ride it — a writing/integrating build shape and a collecting/outlining/revising/reflecting research shape — discriminated on stage. The endpoint stores whatever envelope arrives, so adding the research variant required zero backend changes.

Two properties make this safe rather than fragile. The emitter is fail-silent: if the backend is unreachable the article still gets written, because cosmetic telemetry must never be able to fail real work. And progress is cleared at claim, at apply, and at failure, so a late callback for a finished job is a cheap 204 and can never resurrect a stale panel.

8. The web side, briefly

operator-miracle-agent-route.tsx is a single large client component. Its state machine is small and readable: getMiracleAgentComposerMode(status) returns "feedback", "answer", or null; the poll runs at 2.5 s for at most 480 attempts (a 20-minute ceiling, comfortably past the 900-second generation timeout) and keeps running through approved/publishing so the published link appears without a reload. Beyond the ceiling it degrades to a stalled notice with a manual refresh rather than pretending to be stuck.

Best practices & next steps

Where P30 matches prevailing practice

Gating the irreversible action, not every step. Anthropic's guidance on agent design notes that agents "can pause for human feedback at checkpoints or when encountering blockers", and that "human review remains crucial for ensuring solutions align with broader system requirements" (Building effective agents — anthropic.com). P30 gates exactly twice, and the second gate sits directly in front of the only action that touches the public site. The research loop, by contrast, runs unsupervised — which is right, because it is cheap and reversible.

Outline-then-write for long grounded articles. This is not a stylistic preference; it is a measured result. Stanford's STORM system generates Wikipedia-length articles by treating research and outlining as a distinct pre-writing stage, and reports roughly a 25-point absolute gain in perceived organization over outline-driven baselines (Assisting in Writing Wikipedia-like Articles From Scratch with Large Language Models — arxiv.org). P30 lands in the same place from a different direction: the outline exists to be approved, and gets structural quality as a side effect.

Durable state so the workflow can genuinely pause. LangGraph frames this as durable execution — persisting state at key points so a run can pause for human review and later "be resumed from its last recorded state" (Durable execution / persistence — docs.langchain.com). P30 needs precisely this property and gets it from a Django row plus Celery rather than a checkpointer, which is a defensible trade when a pause may last days and the "resume trigger" is a human clicking a button in a web app.

Filtering internal context out of user-facing output. OWASP's LLM Top 10 lists Sensitive Information Disclosure as a top risk and recommends output-side sanitization and redaction rather than relying on prompt instructions, noting that system-prompt restrictions "may not always be honored" (LLM02:2025 Sensitive Information Disclosure — genai.owasp.org). publish_scrub.py is exactly that posture: the model is asked to cite properly, but the published copy is mechanically stripped, and the strip is a pure function with its own tests.

Where it deliberately diverges — and why that's defensible

  • No agent framework. No LangGraph, no state graph — plain async functions and a database status column. Given that the "graph" has three nodes, the pauses are measured in hours, and the resume trigger is an HTTP request from a browser, a framework checkpointer would add a second source of truth next to the one Django already owns.
  • Agentic research, deterministic writing. The model plans its own reading, but the write path is a fixed spine: N section calls, one integration, one post-process. Anthropic's framing is that "workflows offer predictability and consistency for well-defined tasks, whereas agents are the better option when flexibility and model-driven decision-making are needed" (anthropic.com, cited above). P30 splits the difference along exactly that line — research is open-ended, writing is not.
  • No fully automatic mode. Scheduled generation was designed and then deliberately deferred to a later phase, and even there it would land drafts in the review queue rather than publish them.

Concrete next steps

  1. Sanitize raw HTML in the materializer. Python-markdown passes raw HTML through by default, and draft_publish.py does not currently strip it — operator review before approve is the only gate. A bleach-based allowlist on the rendered fragments would close it. This is a known, documented deferral, not an oversight; it is the highest-value hardening left.
  2. Add a regression test that asserts the published copy is clean. The scrub is unit-tested, but the end-to-end property operators actually care about — "nothing internal reaches the public HTML" — is currently verified by a human opening the article. A single test that publishes a draft stuffed with every marker shape and greps the materialized HTML would make that guarantee automatic.
  3. Audit for dead environment knobs. Shipping P30's ops slice surfaced that two consulting model variables are set in both env files but referenced by no compose file — they have been silently inert. The content knobs are wired correctly today; a small check that every documented variable actually reaches a container would stop the class of bug rather than the instance.
  4. Decide on a revision cost cap. Manual revisions are currently unbounded, with only a per-attempt retry limit. Since every revise turn is real spend, a soft warning past N revisions — or a visible per-job cost read-out — would make the trade-off legible at the moment the operator is making it.

Quiz

Five questions. Click an answer to see whether it's right and why.

1. A job has an approved 구성안 and three existing versions. The operator leaves feedback. Which turn does the agent run?

Precedence is checked in a fixed order: latest_version first, then approved_outline, then outline. And the backend never even sends approved_outline once a version exists. That ordering is what guarantees a job can't slide backwards into re-proposing structure after it has started producing drafts.

2. Why does the published article strip [3] but keep [2026]?

A published copy has no valid citations at all, so any bracketed number is suspect — but stripping every one of them would mangle prose like "[2026]" or "[300]". The cutoff at 50 is a pragmatic heuristic, written down and commented, rather than a guess buried in a regex.

3. An operator steps the version stepper back to v1 (while v3 exists) and leaves feedback. What was the fix that made this actually work?

Before the fix, the UI honestly told the operator they were revising v1 while the payload builder silently based the revision on v3. The fix is entirely server-side and the payload's field name never changed — only which row it resolves to. Versions stay immutable and are never deleted.

4. Corpus photos are turned into ordinary attachment rows keyed by an agent-minted UUID. What did that buy?

Because a corpus photo and an uploaded photo become the same kind of row, the {{img:uuid}} markers the model writes are already final — nothing downstream has to know where a picture came from. (Images are definitely downloaded, not hotlinked: the published page must never reference an external host.)

5. The agent asks a round of questions, the operator presses 건너뛰기, and the turn re-runs. What stops it from asking again?

The guard reads the thread's own history — has any message of kind asks ever been written? — so it holds no matter how the first round was resolved: skip, a real answer, or a later outline reshape. And it doesn't trust the prompt to be obeyed; the deterministic backstop is what makes "at most once" a guarantee rather than a tendency. The skip itself needs no new mechanism: it is a plain answer message with a fixed body.
