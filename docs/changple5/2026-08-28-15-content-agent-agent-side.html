Background — two agents, one product surface

창플 publishes 미라클 콘텐츠: long Korean articles about real small-business owners, written from the brand's own archive of Naver cafe posts. Two different software systems in this repository know how to write one. They were built two years apart by the same team for the same operator, and they agree on almost nothing else.

The older one — call it v1, the P30 미라클 content-draft agent — is the subject of this page. Its job table is ContentDraftJob. The newer one — v2, the P54 content agent, job table ContentAgentJob — is what explainers #13 and #14 walked, and it is what the operator opens today at /operator/miracle-agent.

What a beginner needs first: what these systems actually do

Skip this subsection if you already know the product. Everything after it assumes only these five sentences.

A 미라클 article is not written from thin air. Somewhere in the corpus — thousands of scraped Naver cafe posts, enriched, embedded and indexed by the pipelines explainers #8 and #9 describe — there are twenty or fifty posts about one particular shop. An operator wants those turned into a single publishable article, in 창플's voice, with photographs, and then put into the content library that explainer #12 taught. Both generations do exactly that. Both take an operator brief, gather source material, propose a plan, write Korean prose, place images, and end by materializing a NotionContent row that readers can open.

Jargon, defined once.

  • Brief — the operator's one-paragraph request that starts a job ("당술샘 사장님 이야기로 미라클 한 편").
  • 구성안 (gu-seong-an, "composition plan") — the article's plan: title, sections, sub-headings, which source posts feed which section, which photos go where. Both generations make one and both make the operator approve it before any prose is written.
  • Marker — a placeholder the model writes into the markdown to say "an image goes here", spelled {{img:<key>}}. It is not HTML; it becomes HTML at publish.
  • doc_map — v1's in-memory dictionary of every corpus post the research loop collected this turn: {post_id: {meta, body, rank, score, queries}}.
  • Post-process — the deterministic pass that runs after every model call: renumber citations, drop unknown image markers, extract the questions block.

Two corrections to the shorthand this page inherited.

(1) "v1 = a brief and a thread, then approve; v2 = approves a 구성안 before prose" is not the difference. Both generations gate on a plan. v1 grew its 구성안 gate in P30.S15 and the operator-editable curation gate in P52 — the job even has a dedicated status, outline_review, and a dedicated table, ContentDraftOutline, with proposed/superseded/approved lineage. The real difference is at the other end: v1 collapses approval and publication into a single operator act, and v2 splits them.

(2) v1's 구성안 is the agent's own proposal, derived from research it chose to do; v2's scaffold is built over posts the operator selected up front. That is a difference of who picks the material, not of whether a plan is approved.

The interesting question: what the old generation still does for the new one

An obituary would stop there. The genuinely interesting fact is that v2 depends on v1 — not historically, but at import time, on every publish.

  • v2 publishes through v1's helpers. The bottom of content/draft_publish.py (lines 707–718) is an explicitly additive block of twelve public aliases — nine functions (extract_title, extract_description, finalize_title, split_blocks, render_markdown_fragment, render_html_document, flatten_inline_markdown, collapse_whitespace, iter_paragraph_blocks) and three regexes (H1_HEADING_LINE_RE, IMAGE_LINE_RE, IMAGE_ID_RE). agent_jobs/publishing.py uses nine of the twelve, importing v1 inside eight different functions (from .. import draft_publish as v1) because v1 imports content.models at module level and a top-level import would be circular.
  • v2 writes into v1's own directory. PUBLISHED_CONTENT_SUBDIRECTORY = "miracle" (draft_publish.py:78) is the sub-folder every published article's HTML and images land in; v2 reuses the constant's value rather than choosing its own.
  • The marker grammar v2 obeys is defined here. The canonical regex is apps/agent/app/content_drafts/agent.py:133 — _IMG_MARKER_RE = re.compile(r"\{\{img:([^}]+)\}\}") — and agent_jobs/build.py:135 keeps a byte-identical local copy that says it is a copy. Grepping {{img: across apps/ hits 23 files in all three applications.

The frame for the whole page: v1 is not dead code, it is a library the new generation stands on. The interesting reading of an old subsystem is rarely "what killed it" — it is "which of its decisions turned out to be load-bearing". For v1 the answer is: its file layout, its markdown-to-HTML semantics, and its five-character image language.

Intuition

1. The hop that defines the generation

Everything that feels different about v1 follows from one architectural choice: the model call happens in the other process. Django never talks to Gemini for a v1 draft. It packs a JSON payload, POSTs it to the FastAPI agent with a shared service token, and waits — for up to 15 minutes.

That single design decision explains a surprising amount. Because the answer must survive one HTTP response, the agent returns one JSON object describing a whole turn — never a stream. Because the call can take ten minutes, the backend needs a claim, an attempt counter, a reclaim sweep, and a 900-second timeout. And because the operator would otherwise stare at a spinner for ten minutes with no idea what is happening, v1 needed a second, one-way channel just for progress pings — which is exactly the module §5 is about.

2. Schema-only tools: the model proposes, the loop disposes

If you have used a tool-calling agent before, you know the normal shape: you write a function, decorate it, hand it to the model, and the framework calls your function when the model asks for it. v1 does something that looks the same and is not. Its two tools are declared with LangChain's @tool decorator — and their bodies raise NotImplementedError.

@tool
def search_cafe_posts(query: str) -> str:
    """인덱싱된 네이버 카페 코퍼스에서 query와 관련된 글을 검색한다. …"""
    # Schema-only: the research loop dispatches this call manually against the
    # live retrieval stack, so this body is never executed.
    raise NotImplementedError

The decorator is used purely to generate a JSON schema for the model — the name, the argument types, the Korean docstring the model reads as documentation. Nothing else. The loop then reads response.tool_calls itself and dispatches each call by hand.

What manual dispatch buys, concretely:

  1. A budget the model cannot spend past. Once search_count reaches MAX_RESEARCH_SEARCHES = 8, the loop does not call retrieval; it hands the model back the string "검색 한도에 도달했습니다. 정리해서 마치세요." ("You have reached the search limit. Wrap up.") — a refusal expressed as a normal tool result, so the model reasons its way to a stop instead of hitting an exception.
  2. One accumulating map instead of N independent results. With framework-run tools you get eight separate tool outputs and whatever the model remembered of them. Here every search's full candidate list is merged into a single doc_map, deduplicated by post_id, keeping the best rerank rank a post earned across all queries — while the model only ever sees a 12-row preview per search. The material the writer eventually gets is assembled by our code, not reconstructed from the model's transcript.

The transferable lesson. "Tool calling" is really two separable things: letting the model choose a call, and letting a framework execute it. Keep the first, take back the second, and you can enforce budgets, deduplicate across calls, and keep the real payload out of the context window. The cost is that you write the loop.

3. Update-vs-rewrite

An operator reads a 5,000-character draft and says: "세 번째 문단만 조금 부드럽게" ("just soften the third paragraph a bit"). The naive implementation asks the model to output the whole article again. That is slow, expensive, and — worst — it silently rewrites the 4,800 characters nobody complained about.

v1's revise turn lets the model answer in either of two shapes. It may return markdown (a full rewrite), or it may return a JSON directive of exact string substitutions:

{"mode": "edits",
 "note": "세 번째 문단의 어투를 부드럽게 조정했습니다.",
 "edits": [{"find": "사장님은 3년을 준비했습니다", "replace": "사장님은 3년을 차근차근 준비했습니다"}]}

_apply_edits then applies them deterministically, with one strict rule: each find must occur exactly once in the body, and if any edit in the set fails that test the whole set is discarded and the original body is returned byte-identical.

Measured, by executing the real function. The three helpers below were source- sliced verbatim out of agent.py and run against a toy Korean draft:

applied: True
untouched tail byte-identical: True
ambiguous find (2 occurrences) applied: False | body unchanged: True
one bad edit in the set  ->  applied: False | body unchanged: True

So a partial application can never happen: the edit set is atomic, and "unique-once" is the integrity check that makes a blind string replace safe.

When the set does not apply, the code does not fail the turn and does not ask the operator anything. It calls the model again with the same feedback plus a Korean suffix that says, in effect, "the local edits could not be applied — rewrite the whole body from scratch, no JSON", and takes the rewrite. Three properties fall out of this: an accepted edit set leaves untouched prose byte-identical; a rewrite is always available as a floor; and the server records only {mode, edit_count, base_version_number} — never the find/replace strings, because post-processing mutates the body afterwards and a stored span could not be guaranteed to still match.

4. A five-character layout language

The model cannot emit HTML — the published copy is scrubbed of everything model-authored except prose. So how does an image get into an article at a place the model chose? With a marker, and two rules about lines:

{{img:a1b2c3}}                      a marker alone on a line  ->  a full-width image
{{img:a1b2}} {{img:c3d4}}           2–3 markers on ONE line   ->  a row of columns (max 3)
문장 안 {{img:x}} 인라인 마커        anything else             ->  not a layout instruction

The key inside the marker is a UUID, and — this is the part worth remembering — that UUID is the primary key of the attachment row the backend creates for the image. There is no mapping table, no rewriting step: the model invents a placement, and the database row is created under the exact name the model used.

Measured. Running the real _strip_unknown_image_markers over a body containing six markers, where only AAA, BBB, EEE and FFF were actually provided:

input                        output
{{img:AAA}}               →  {{img:AAA}}          (kept, full width)
{{img:BBB}} {{img:CCC}}   →  {{img:BBB}}          (row collapses to one image)
{{img:DDD}} {{img:EEE}}   →  {{img:EEE}}          (survivor keeps the line)
문장 안 {{img:FFF}} …     →  문장 안 {{img:FFF}} … (inline marker kept as text)

A marker-only line whose markers all die is deleted entirely, so a hallucinated image leaves no blank hole in the article.

The same measurement exposes a small, real asymmetry. The publisher's block splitter (_split_blocks) matches whole lines only, so the surviving inline marker is never turned into a figure — and the scrubber then deletes it as residue. Verified end to end: scrub_public_text("문장 안 인라인 {{img:FFF}} 마커와 텍스트.") returns "문장 안 인라인 마커와 텍스트.". In v1 an inline marker is silently nothing. That is precisely the failure v2 later engineered away: its _partition_marker_lines lifts an inline marker onto its own line before it can reach the scrubber (explainer #14, §2).

Code

The walk goes in the order a turn actually happens: Django decides to ask (§1), the request crosses the boundary (§2), the agent does the work (§3, §4), it reports progress on a side channel (§5), and Django consumes the answer and eventually publishes it (§6).

§1 The dispatch — how Django asks the agent to write

apps/backend/content/draft_dispatch.py (938 lines). Its own docstring says it was "cloned 1:1" from conversations/consulting_report_dispatch.py — the module explainer #10 walked. So the right way to read it is not as content-agent code but as this repository's standard shape for "a long backend→agent job", instantiated a second time. Why 30 minutes and not 5. A reclaim window shorter than the work it supervises does not recover jobs — it double-dispatches live ones.

The HTTP boundary

request_agent_draft_generation (:257) is the seam. _request_agent_draft_generation (:274) builds the request by hand — plain urllib, not requests or httpx — with two headers and an optional third:

headers = {
    "Content-Type": "application/json",
    AGENT_SERVICE_TOKEN_HEADER: str(settings.AGENT_BACKEND_SHARED_TOKEN),
}
if getattr(settings, "ENABLE_CORRELATION_IDS", False):
    request_id = get_request_id()
    if request_id:
        headers["X-Request-ID"] = request_id

That first credential is the static Django↔agent service token explainer #2 taught: one shared secret, passed unrenamed to both services, compared with hmac.compare_digest on the agent side. There is no user to impersonate here — a draft job belongs to an operator, but the call is machine-to-machine, so the service token is the right credential rather than a forwarded JWT. The correlation header is usually absent in practice, because the dispatch runs under Celery where there is no inbound request to inherit an id from.

A behavioural subtlety with a good name. latest_version does not mean "the highest-numbered version". It resolves to the version targeted by the newest operator feedback/answer message that carries a version foreign key, falling back to the max-number version only when no such message exists. That is what makes "step back to version 2 and leave feedback there" actually revise version 2 instead of version 5. The field name never changed; its meaning did — the kind of thing worth a comment, and it has one.

What comes back: three outcomes

_build_agent_draft_result (:325) validates the response into a frozen AgentDraftResult dataclass, and refuses any outcome outside {"draft", "needs_input", "outline"} as permanent. _apply_agent_draft_result (:687) then forks:

  • outline → _apply_outline_result (:642): supersede any prior proposed outline, insert a new ContentDraftOutline at number + 1, post one short Korean agent NOTE pointing at the canvas, and park the job at outline_review. No version row is written at all.
  • needs_input → write an ASKS message carrying {questions, image_requests} and park at needs_input. This is the outcome that makes v1's whole message thread exist: the agent is allowed to answer "I need more from you", and the operator's reply is just another row in the thread that the next turn sees.
  • draft → download the placed corpus images, then, in one locked transaction, create the attachment rows, the new ContentDraftVersion, an optional NOTE, an optional ASKS, an optional SYSTEM message about dropped images, and park at awaiting_review.

All three start with the same idempotency guard — reload the job under select_for_update and return silently if its status has left the queueable set — so a duplicated task or a late reclaim cannot double-write. And note the ordering in the draft branch: the image downloads happen before the transaction opens, with a comment saying why. Holding a row lock across arbitrary network I/O to Naver's CDN is exactly the kind of thing that turns a slow third party into a database incident.

§2 The door — one route, one contract

apps/agent/app/api/routes/content_drafts.py (172 lines) is one of the agent's 17 public routes and by far the simplest interesting one: POST /agent-api/internal/content/drafts/generate, guarded by require_agent_service_context, which is immediately discarded (del service_context) — the dependency exists for its side effect of rejecting an unauthenticated caller.

Two details are worth copying:

  1. Every request model sets model_config = ConfigDict(extra="forbid"), with a comment saying why: "so a backend↔agent drift 422s loudly instead of silently dropping fields." When two services in one repository share a payload contract, strictness at the boundary converts a silent behavioural bug into a loud deploy-time failure.
  2. Every pipeline exception becomes a 503 with a fixed detail string, after report_agent_error is called with {"source": "content_draft", "job_id", "request_id"}. The backend's transient/permanent classifier reads 503 as transient, so a Gemini hiccup becomes a Celery retry rather than a failed job. Error reporting itself belongs to explainer #16.

§3 The room — content_drafts/agent.py

2,295 lines, and the centre of this page. Its docstring frames the whole thing in one sentence, which the code then honours:

"A hybrid turn: a bounded, model-driven agentic RESEARCH loop (flash driver + two tools over the indexed Naver Cafe corpus) feeds a deterministic write → reflect → post-process spine (pro model). Generation and revision share this module; the backend brokers to it via the internal service-token route — the operator UI never calls it directly."

Two words in that sentence carry the design. Hybrid: the part where creativity helps (deciding what to search for) is model-driven; the part where correctness matters (what the writer sees, what the markers mean, which citations survive) is straight-line Python. Shared: there is no separate revise service — one entry point, run_content_draft_pipeline, handles all three turn kinds.

3.1 Which turn is this? Precedence, not a mode flag

is_revision   = latest_version is not None
is_write_turn = (not is_revision) and (approved_outline is not None)
# else: outline turn

The caller never sends a turn_type. The turn kind is derived from which data is present, in a fixed precedence: a job that has a version is revising, a job that has an approved 구성안 but no version is writing, and everything else is researching toward a proposal. One consequence is stated in a comment on the backend side: once a version exists, the approved outline is not re-sent, because revision precedence would ignore it anyway.

3.2 Decision one: the research loop is hand-rolled and stateless

Six iterations, at most eight searches, no framework:

for _iteration in range(MAX_RESEARCH_ITERATIONS):
    response = await acall_with_retry(lambda: bound.ainvoke(messages), …)
    tool_calls = list(getattr(response, "tool_calls", None) or [])
    if not tool_calls:
        break
    messages.append(response)
    for call in tool_calls:
        …                       # cap checks, manual dispatch, progress ping
        messages.append(ToolMessage(content=result_text, tool_call_id=call_id))

messages is a plain Python list that lives for the duration of one function call. When the turn ends it is garbage. Nothing is persisted, nothing is resumable.

Contrast with the chat agent, deliberately. Explainer #5 walked a loop in the very same codebase that is the opposite in every respect: a LangChain create_agent graph with a Postgres checkpointer, so a turn can be interrupted, resumed and replayed. Same company, same repo, two answers — and the reason is the shape of the work, not fashion. A chat turn is watched by a human who may reload the page mid-stream, so it must survive interruption; a draft turn runs headless inside a Celery task for ten minutes, and if it dies the honest recovery is to run it again from the top. Persistence machinery you do not need is not free: it is schema, migrations, and a whole class of stale-state bugs.

3.3 Decision two: the tools' bodies never run

Covered in the Intuition; here is what the manual dispatch actually does per call.

search_cafe_posts → _run_search (:509). Runs the (blocking) shared retrieval through asyncio.to_thread, catches exactly two exception types (RetrievalEmbeddingError, RetrievalRerankError) and turns them into the Korean string "검색에 실패했습니다." — a failed search is a tool result, not a turn failure. Then it merges every candidate into doc_map: new posts get {meta, body:"", rank, score, queries:[q]}; a repeat hit keeps the better rank ("never first-writer-wins", says the comment). Only the first SEARCH_PREVIEW_LIMIT = 12 rows go back to the model.

read_posts → _run_read (:565). Normalizes the id list defensively (rejecting bool before int, dropping non-positives and duplicates), hydrates bodies through the shared hydrate_document_bodies, stores the full body in doc_map and returns only an 800-character excerpt per post. The model gets enough to decide whether to dig deeper; the writer later gets the whole thing.

After the loop, and only after, the pool is trimmed:

def _trim_candidate_pool(doc_map, *, limit=MAX_CANDIDATE_POOL):
    """… This runs once, after collection ends — never mid-candidate-list, which is
    what made the old `break` truncate a late search arbitrarily. Documents the
    driver actually read (body hydrated) are never evicted: they cost a model
    call already and dropping one would silently lose researched content."""

Measured. Running the real _trim_candidate_pool on a pool of 104 unread posts plus one read post ranked 400th: final size 101, and the rank-400 post survived. The "never evict a hydrated body" rule can legitimately push the pool past its own limit — the cap is a budget on cheap items, not a hard ceiling.

This is the fix for a real, measured bug. Before P52 the same loop capped at 24 documents and enforced the cap with a break in the middle of a candidate list; live on the dev stack, five driver queries plateaued at 6 → 9 → 9 → 9 → 9 documents. The pooled version over the same queries reached 24 → 37 → 69 → 82 → 110, trimmed to 100. The corpus had always been there; the boundary was throwing it away.

3.4 Decision three: the model-call idiom, cloned from the consulting pipeline

Every model call in this package is built the same way (_build_draft_model, :247) and invoked the same way. Four rules, all of them defensive:

RuleCodeWhy

And then the part that is genuinely unusual: JSON comes out by hand.

def _parse_json_from_llm(text):
    if not isinstance(text, str):
        text = "\n".join(…)                 # flatten list-shaped content
    cleaned = text.strip()
    if cleaned.startswith("```"):
        lines = cleaned.split("\n")[1:]     # drop the opening fence
        if lines and lines[-1].strip() == "```":
            lines = lines[:-1]
        cleaned = "\n".join(lines).strip()
    return json.loads(cleaned)

Fourteen lines, no schema, no validation library, and callers that treat a JSONDecodeError as "the model did not choose that shape". Set that next to v2's analysis.GeminiStructuredWorker (explainer #13) and you have two opposite answers to the same question, both of them defensible:

  • Structured output guarantees a shape, and therefore forces you to have a shape. It is a poor fit when the model is choosing between kinds of answer — v1's revise turn returns either a JSON edit directive or plain markdown prose, and "either" is not a schema.
  • Hand parsing costs a class of failures — but those failures are recoverable here by design: an unparseable revise response is simply treated as a rewrite.

3.5 Decision four: the write turn is segmented, and integration replaces reflection

_write_segmented (:1559) writes one section per model call, in order, then makes one whole-body integration call. Three things make it work:

  • Each section sees only its own category's documents. _section_write_post_ids resolves sections[i].category_key to the approved category and passes just those post ids — with a careful fallback: a section that cannot resolve its own category falls back to the whole curated union, never to an empty list, because "the model would invent the section from nothing".
  • Continuity without an unbounded prompt. _previous_sections_block gives the writer everything written so far, and once that exceeds MAX_PREVIOUS_SECTIONS_CONTEXT_CHARS = 8000 it degrades to the immediately previous section verbatim plus the earlier sections' headings.
  • Integration is fail-soft; sections are not. An empty section response raises and fails the attempt (the Celery ladder re-runs the whole idempotent turn); an integration failure logs a warning and falls back to the plain concatenation of the sections. The expensive, already-paid-for work is never thrown away for want of a final polish.

_reflect_draft — a settings-gated self-critique pass (content_draft_reflection_enabled, default True) — therefore runs only on the two paths that have no integration pass: a zero-section outline's one-shot write, and a rewrite-mode revision. Running both would be paying twice for the same review.

3.6 The deterministic tail: _post_process (:1964)

Whatever the model produced, five deterministic steps close every turn:

  1. _extract_asks_block — pull a trailing ```json fence off the body if it is asks-shaped (questions or image_requests). A malformed fence is logged and dropped; a trailing JSON fence that is not asks-shaped is left in the body untouched.
  2. normalize_bare_post_id_markers then render_citation_markers — turn the model's [post:1023] internal markers into visible [1] [2] … numbering, keeping only ids that are actually in doc_map. This is shared chat-citation machinery (explainer #11), reused verbatim.
  3. strip_unmatched_visible_citation_markers — remove any [n] the model invented beyond the real citation count, with a warning log.
  4. _strip_unknown_image_markers — the line-level marker rules measured earlier.
  5. An empty result after all that raises — an empty article is a failed turn, not a publishable one.

Measured. _extract_asks_block on "본문입니다.\n\n```json\n{\"questions\": [{\"id\": \"q1\", …}]}\n```" returns the body '본문입니다.' and the dict {'questions': [{'id': 'q1', 'text': '가격표 사진이 있나요?'}], 'image_requests': []} — note the missing key is normalized to [] rather than left absent, so downstream code never has to test for it.

§4 The supporting modules

4.1 retrieval.py (122 lines) — wide, and only for us

This is the smallest module in the package and the one with the most interesting docstring. Its whole body is one function that calls the shared retrieval entry point with four explicit width arguments:

CONTENT_LEXICAL_CANDIDATE_LIMIT      = 64   # shared default: 32
CONTENT_VECTOR_CANDIDATE_LIMIT       = 64   # shared default: 32
CONTENT_VECTOR_PER_VARIANT_LIMIT     = 24   # shared default: 12
CONTENT_RERANK_CANDIDATE_LIMIT       = 40   # shared default: 16
CONTENT_CHUNK_CANDIDATE_LIMIT        = 24   # + chunk_mode=ChunkMode.SUPPLEMENT

The boast in the docstring is the teachable part: "This module changes nothing for anyone else." No shared module-level default is touched. Chat, 컨설팅 report and probing, author posts and the public POST /agent-api/v1/retrieve all keep calling with defaults. And this is the concrete payoff for the claim explainer #7 made about the retrieval chokepoint: because the shared function takes per-call widths as keyword arguments, a demanding new consumer needs a 122-line call-site wrapper and zero edits inside app/retrieval/. The same is true of the chunk arm added later: this module is the only caller that passes chunk_mode=ChunkMode.SUPPLEMENT, so every other caller executes no chunk SQL at all.

The property that makes it safe: the ranked-result cache key already carries all four widths, the chunk mode and the chunk limit, so a wide content-agent call gets its own cache entry and cannot poison chat's. Widening a shared default would have been one line and would have quietly changed four other products; the boundary makes the reversal one line too (delete two keyword arguments — "it is never a re-index").

4.2 curation.py (400 lines) — ranking is not judgment

This module exists because of one sentence in its docstring:

"P52.S2 widened collection to a ~100-post relevance-ranked pool, but ranking is not judgment: _merge_reranked_post_ids re-appends every candidate the reranker omitted, so a passing mention of the subject survives next to a post that is entirely about it."

Unpack that. The reranker sorts; it never filters — anything the model left out of its ordering is appended back in fusion order (explainer #7 recorded this as the chokepoint's totality guarantee). So after collection you hold 100 posts in a sensible order, of which perhaps 30 are actually about the shop and 70 mention it in passing. Order alone cannot tell you where that line falls. Two flash stages supply the judgment:

  1. filter_relevant_documents — one call over every pooled title + summary, returning the ids with dedicated content about the subject.
  2. categorize_documents — multi-label grouping of the survivors into the sections the article will be written from. Names are invented per subject; there is no house taxonomy.

Two structural rules make these stages safe to run on every outline turn:

Neither stage may fail a turn. Pool ≤ MIN_RELEVANT_DOCUMENTS = 8 → no model call at all. Survivors below that floor → the pool's top 8 by rank. Any exception → the whole pool, with a warning. Categorization failure, or a result that normalizes to zero categories → one 전체 category holding the top 10 by rank. Degraded, but always valid.

Caps are code, never the model. Ids outside the survivor set are dropped, duplicates collapse, MAX_CATEGORIES = 10 × MAX_POSTS_PER_CATEGORY = 10 are applied after the call, categories are ordered by their best member's rank, empty ones vanish, and the stable key is minted here as cat-1 … cat-10 — after ordering — because the operator may rename a category and the key has to survive that.

The one exception to "never with_structured_output". These two stages do use it (with include_raw=True, at temperature 0), and the module docstring argues the case rather than hiding it: both outputs are bare lists of integers, GeminiRetrievalReranker already proves the pattern works in this app, and it removes a whole class of parse failure from a stage that runs on every outline turn. Worth noting as a matter of engineering culture: the exception is documented at the exception, next to the rule it breaks.

4.3 images.py (223 lines) — alt text, or invisible

load_document_images is a deliberate sibling of retrieval/document_bodies.load_document_bodies: a single SELECT post_id, image_urls FROM documents_documentsource WHERE post_id = ANY(%s) over the read bridge, owned by the content-draft package, touching none of the shared retrieval SQL or metadata that consumer chat depends on. hydrate_document_images wraps it fail-soft — an image-load failure means an article with no corpus photographs, never a failed turn.

build_corpus_image_inventory then turns those raw rows into placeable candidates, and its filter is the memorable part:

alt = _normalized_alt(entry)          # entry["generated_alt"], may be None
url = _normalized_url(entry)
if not alt or not url or url in seen_urls:
    continue                          # ← an alt-less image never becomes a candidate

Why an alt-less image is not "an image with no caption" but no image at all. The model choosing where photographs go is a text model. It never sees pixels. Its entire view of an image is one inventory line — {{img:<key>}} — 매장 내부 좌석과 조명 (post 1023) — so an image with an empty generated_alt is literally not describable to it. Excluding it is not a quality filter; it is a type constraint.

This ties both ways. The generated_alt column is filled by ingestion's image_alt.py enrichment (explainer #8) — that is what makes corpus images visible to any writer at all. And v2 hit the same wall from the other side and attacked the other end: its alt_backfill.py service writes generated_alt onto rows that lack it, precisely because writing an alt moves a corpus row into candidacy (explainer #14).

The rest of the module is quiet good behaviour: a fresh uuid4 per candidate (so a corpus image is placed with the same marker grammar as an operator upload), per-post round-robin under MAX_CORPUS_IMAGES_PER_POST = 6 and DEFAULT_CORPUS_IMAGE_INVENTORY_CAP = 40, so one photo-heavy post cannot fill the whole tray, and a seen_urls set seeded with the job's existing attachments so a previously downloaded image is never offered twice.

4.4 prompts.py (584 lines) — where the Korean lives

Nine prompt builders, all Korean-facing, all grounded in exactly three inputs: the operator's brief plus the operator↔agent thread; the reference format profile; and the corpus documents the research loop gathered. The module's structural idea is that the conventions are constants shared across builders — _IMAGE_CONVENTION, _CORPUS_IMAGE_CONVENTION, _CITATION_CONVENTION, _ASKS_CONVENTION, _VOICE_GUIDANCE — so a draft and its revisions state the same rules to the model and therefore render identically downstream. Change the marker grammar in one place and write, revise and reflect all learn it at once.

Two prompt decisions are worth reading as product decisions:

  • Adapt, never copy. _format_reference_profile hands the model a real published article and then narrows what it may take from it: "문체·톤·문장 길이·이미지 배치 리듬만 본보기로 삼고, 문장이나 사실을 그대로 베끼지 않는다" — voice, tone, sentence length and image rhythm only, never sentences or facts. And explicitly: "글의 구조(섹션 수·순서·주제)는 이 참고 형식을 따르지 않는다" — the approved 구성안 owns structure, not the exemplar.
  • The section writer is told what it is not allowed to do. build_section_prompt forbids a # title, forbids inventing a new ## section, forbids numbering the 소제목, and forbids appending an asks fence — because citation renumbering, marker validation and the single asks block are the integration pass's and the post-process's job. Prompts in this codebase are written as contracts with the deterministic code downstream.

§5 The progress channel — and a drift to report

content_drafts/progress.py is 61 lines and does one thing: POST a JSON envelope to the backend and swallow every possible error.

except Exception as exc:  # noqa: BLE001 - progress must never break a turn
    logger.debug("Draft progress emit failed for job %s: %s", job_id, exc)

Five-second timeout, a falsy job_id is a no-op (so the pipeline stays testable without a backend), missing configuration is a no-op, and a network failure is a debug log. The justification is a proportionality argument worth internalizing: a dropped progress ping leaves the operator's panel one poll tick stale; a raised progress ping loses a ten-minute article. Telemetry must never be able to fail the thing it is describing.

One channel, extended twice and never duplicated: the segmented write turn's build stages (writing, integrating) came first, then the research stages (collecting → filtering → categorizing → outlining, plus revising and reflecting) rode the same endpoint, same field, same panel. Each envelope is tagged with a flow ("outline" or "revise") so the UI can pick the right row set. On the backend the envelope lands on ContentDraftJob.progress, a schema-light JSONField whose help_text ends with the instruction "do not add a second channel."

The drift

The module's docstring closes with this paragraph:

"P54.S5 extends the SAME channel to Content Agent v2: the backend endpoint resolves the posted job id against the v1 job table and then against the v2 ContentAgentJob table, so a v2 stage emits through this exact function with its own stage names in the envelope. Still no second channel."

The first half is true and the emphasized clause is not, any more. Verified today:

  • v2 makes no agent-service call at all — agent_jobs/ has zero matches for agent-api, AGENT_BASE_URL or X-Agent-Service-Token.
  • Its five live progress producers are in-process Django/Celery call sites that import record_job_progress directly: build.py:1860, architect.py:718, chat_intake.py:700, revisions.py:306, publishing.py:1216.
  • The HTTP fall-through at content/urls.py:594 → draft_views.py:1022 is real and reachable, but it is a seam, not the live path: it exists so that anything which ever does emit for a v2 job lands on the same field and envelope instead of growing a second channel.

So the sentence is prose lag, not a bug — the guarantee it protects still holds; only the mechanism described is no longer the one in use. It is reported here and routed as a question for the operator (this phase changes no product code, and a docs-only phase fixing comments in passing is how unreviewed edits happen).

A second, smaller precision. It is often said that "both halves share PROGRESS_ACCEPTING_STATES". They do not share the constant — they share the rule. v1's view gates on DRAFT_GENERATION_QUEUEABLE_STATUSES (requested · collecting · drafting · revising); v2's record_job_progress gates on PROGRESS_ACCEPTING_STATES (processing · proposing · writing · integrating · publishing), whose own comment says it is "the v1 rule … carried over to the SAME channel". Both refuse a ping outside an active window with a cheap no-op rather than an error, and v2 deliberately excludes draft_ready so a late envelope cannot paint a progress panel over the editor.

§6 Back on the backend: what v1 does with the answer

6.1 draft_images.py (134 lines) — a hardened downloader

The agent returns corpus_images: the candidates whose markers survived post-process, each {id, url, caption, post_id, image_index}. The backend downloads each one and creates an ordinary ContentDraftAttachment row whose primary key is the agent-minted uuid. That is the whole trick: because the marker key is the attachment pk, every downstream machine — preview, publish, thumbnail selection, revision ordinals — works unchanged on a corpus image and an operator upload alike. (v2 reached the identical idea from a different direction with its asset uuid.)

The module is modelled on remote_images.download_remote_image (explainer #12) but hardened, because these URLs come out of a corpus rather than an operator's hands:

GuardValue
schemehttps only
hostmust end with .pstatic.net (Naver's CDN — dominated by cafeptthumb-phinf; a rare non-pstatic host fails soft and drops)
content typemust start image/
size15 MiB, enforced from Content-Length and by reading one byte past the cap — an undeclared-length stream cannot slip through
timeout20 s
bytesstored as-is; the extension comes from the URL suffix, else the content type, else .img

Every failure raises one exception type, and the caller (_materialize_corpus_images) treats it as "drop this candidate": strip its marker from the body, post one Korean SYSTEM message saying N images could not be loaded, and carry on. There is also a small dedupe fence — a key already used by any job's attachment is dropped rather than colliding on the primary key.

6.2 draft_publish.py (718 lines) — approve is publish

The operator's approval of a version queues content.publish_draft after commit; publish_draft_job (:307) turns markdown into a live article. The pipeline is small and worth knowing in order:

  1. Resolve the approved version from the newest approve decision carrying a version FK.
  2. Title and description: lift the first heading out of the body (_extract_title), truncate (_finalize_title, 200 chars), and derive a 300-character description from the first real paragraph, with inline markdown flattened.
  3. Create the content row early (_ensure_published_content) with an empty html_path. This is the idempotency anchor: a retry or a reclaim reuses the same content id, and a half-published row is invisible to readers because readable() requires a non-empty html_path (explainer #12).
  4. Split into blocks (_split_blocks) — image lines become {"type": "images", "ids": […]}, everything else accumulates as markdown. The docstring says it mirrors the web splitter splitMiracleAgentArtifactBlocks "at exact line-level granularity", which is why the model's line-level marker rules are meaningful at all.
  5. Render: markdown blocks go through scrub_public_text and then markdown.markdown; image blocks become a <figure>, or a <div class="column-list"> of <div class="column"> figures when the line carried 2–3 markers.
  6. Stage, then swap: write index.html plus the images into a temporary tree and _swap_directory it into html_content/<id>/miracle/, so a reader never observes a half-written article.
  7. Update, never save: one queryset .update() writes title, description, paths, thumbnail and the weight fields — with an emphatic comment that content.save() would re-trigger the model's post-save file pipeline.
  8. Flip visibility through the seam: set_content_publish_state(content_id, True) at draft_publish.py:411 — deliberately not folded into the .update() above, so it stays the single publish choke point the chunk-index trigger hangs off. Explainer #12 owns that seam; v1 is one of its five callers.
  9. Then, and only then, queue the non-blocking Notion archive mirror.

The status flow, and the one asymmetry worth remembering. approved → publishing → published. A publish failure is recoverable: the job returns to awaiting_review with a Korean SYSTEM message — "게시에 실패했습니다: … 다시 승인해 주세요." — bound to the approved version, so the operator simply re-approves. failed is reserved for generation, and the reclaim sweep for publications has no attempt ceiling at all, because publish is idempotent and any exception already parks the job somewhere an operator can act on. Contrast v2, where publishing is one of two separate acts (초안 저장 writes a real but invisible row; 발행 makes it visible) — v1 has a single act, and the recoverable failure is what makes a single act safe.

6.3 The operator API and the job domain

draft_views.py (1,049) and draft_serializers.py (796) are the surface an operator client drives: job create/list/detail, the message thread, photo attachments, manual versions, the 구성안 approve and history routes, approve, cancel, and a job-scoped corpus-image proxy. Two details repay attention:

  • The message route is the engine. Posting an operator message re-queues generation — and which turn it re-queues depends on where the job is: at outline_review the status is set back to collecting so the agent re-proposes a 구성안 with the feedback now in the thread digest; anywhere else it becomes revising. One endpoint, two meanings, decided by state rather than by a parameter.
  • The corpus-image proxy exists because of a CDN detail. The serializer never emits a raw .pstatic.net URL to the operator's browser: Naver's CDN 403s the Referer a browser sends for a cross-origin <img> from our origin, so a raw hotlink is dead in the console even though the same URL downloads fine server-side. Every display-facing URL is rewritten to a job-scoped route on our own origin.

The tables live at content/models.py:704–1120 — seven of them:

A small fossil. ContentDraftJob.Mode declares MANUAL and AUTO, and the field is even serialized to the client — but nothing in the backend ever writes AUTO or reads job.mode. The scheduled auto-drafting mode was scoped out ("no auto-mode beat entry was added") and only its enum survived. Harmless, and a good example of the kind of residue a superseded subsystem accumulates.

§7 Part C in one view

Three pages, one product area, told in the order the system was built rather than the order it runs. Explainer #12 taught the library: the NotionContent row, the single publish seam, media derivatives and delivery — the destination every 미라클 article ends up in, whoever wrote it. Explainers #13 and #14 taught the agent that fills it today: KakaoTalk intake, brand-scoped post selection, the architect's scaffold, the unit-by-unit build, the editing surface, and the two publishing acts — all inside Django, all structured passes, all in one 40,000-line package. This page taught the generation that came before: the same product goal answered with an HTTP hop to a separate service, a hand-rolled research loop, hand-parsed JSON, and a five-character image language.

Read together they make one point that no single page could: the hard parts of this product were never the model calls. They were the boundaries — what the writer is allowed to see, what a marker means, who is allowed to change a plan, when a row becomes visible to a reader. v2 replaced almost every mechanism v1 used, and kept, verbatim, v1's answers to those four questions.

Quiz

Five questions. Click an option to see whether it is right and why.

1. v1's two research tools are declared with @tool but their bodies raise NotImplementedError. What does dispatching each tool call manually inside the loop actually buy?

The caps (MAX_RESEARCH_SEARCHES = 8, MAX_CANDIDATE_POOL = 100) are enforced by the loop, which hands back a Korean "limit reached" string instead of running the search; and every search's full candidate list merges into one shared map keyed by post_id, keeping the best rank per post, while the model only ever sees a 12-row preview. The schema is still sent — that is the only thing the decorator is for.

2. curation.py's docstring says "ranking is not judgment". What exactly does _merge_reranked_post_ids re-add that makes a separate relevance filter necessary?

The reranker orders; it never filters. Anything it left out is appended in fusion order, so the pool is invariant and only the order is the model's. Ordering cannot tell you where "dedicated content" ends and "passing mention" begins — that judgment is filter_relevant_documents's job, with an 8-document floor and a fail-soft path in three directions.

3. A corpus image has a perfectly good URL and downloads fine, but its generated_alt is empty. Why can the agent never place it?

A text-only model selects by alt semantics. build_corpus_image_inventory keeps only entries with a non-empty generated_alt and a usable url — the exclusion is a type constraint, not a quality bar. The key is a fresh uuid4, unrelated to the alt. This is the exact problem v2's alt_backfill attacks from the other end.

4. On a revise turn the model returns an edits directive, but one of its three find strings appears twice in the body. What happens?

_apply_edits is atomic: any edit whose find does not occur exactly once aborts the entire set and returns the previous body unchanged (measured). The caller logs a warning and calls _rewrite_fallback, which re-sends the feedback with a Korean suffix instructing a from-scratch rewrite with no JSON block. The turn never fails for this, and edits-mode metadata records mode="rewrite", edit_count=0.

5. A v2 article is published today. Whose code turns its markdown into the stored HTML document?

The bottom of draft_publish.py (lines 707–718) exports twelve public aliases, added purely so v2 could reuse v1's exact title/description/block/markdown/document semantics instead of growing a second copy; v2 uses nine of them. The imports are function-local because v1 imports content.models at module level. That is what "v1 is a library the new generation stands on" means literally.
