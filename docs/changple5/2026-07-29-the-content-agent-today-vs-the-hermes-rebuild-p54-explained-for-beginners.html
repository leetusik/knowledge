Background

A primer, if you need it: workflows, agents, and how an LLM "remembers"

(Skip to the next heading if you already know these terms.)

A large language model has no memory between calls. Every request starts from a blank slate: whatever you want it to "know" must be placed into the prompt, every single time. Systems built around LLMs therefore fall on a spectrum. At one end are workflows — "systems where LLMs and tools are orchestrated through predefined code paths": your Python decides step 1, step 2, step 3, and the model fills in the blanks. At the other end are agents — "systems where LLMs dynamically direct their own processes and tool usage." In a workflow the code is the boss; in an agent the model is.

When people say an agent "learns," they almost never mean the model's weights change. They mean the system around the model accumulates text — notes, preferences, procedures — and injects it into future prompts. The research literature gives this move a name: Reflexion showed that agents which "verbally reflect on task feedback signals" and keep that reflection in an episodic memory buffer improve dramatically without any fine-tuning. Learning, for an agent, is careful bookkeeping of words.

The content agent, and the two defects that started this phase

Changple's content agent is an operator-only tool at /operator/miracle-agent. Changple staff use it to draft 미라클 library articles — long-form Korean case-study content like "평상집 양재점 창업 사례" — grounded in the company's Naver Cafe corpus of ~7,000 posts. P30 built it (job-based drafting, an outline gate, publishing); P52 rebuilt its research half so it collects ~100 candidate posts wide, filters them, sorts them into categories, and lets the operator curate the plan — the 구성안 — before a word of the body is written.

At the 2026-07-27 client meetup, Changple named two defects. First, 학습 능력 부재 — "no ability to learn": "개발자 개입이 없으면 똑같은 지시를 매 콘텐츠마다 삽입해야함" (without developer intervention, the same instructions must be inserted into every piece of content). Second, the agent uses few documents despite the corpus being large. The operator's chosen answer is P54: rebuild the agent's runtime on Hermes Agent, with new input types (KakaoTalk conversation exports, loose photos, content guidelines) and a rule that content is only produced for subjects with a verified total-cost transcript.

What Hermes Agent is (and is not). Hermes Agent is an MIT-licensed, self-hosted agent daemon from Nous Research (github.com/NousResearch/hermes-agent, v0.19.0 at tag v2026.7.20). It is model-agnostic — it calls Gemini, Claude, or ~50 other providers. It is not the "Hermes 3/4" LLM weights from the same company, not Meta's Hermes JavaScript engine, and not any of the SEO clone sites. Its pitch, for our purposes: two curated memory files injected into every session, a SKILL.md skill library, a background "review fork" that decides what is worth remembering, and subagents.

P54.S1 — the document this explainer is based on — was a research slice: read the v1 code first-hand, read the Hermes source first-hand at the pinned tag, and produce a comparison plus an adoption blueprint. Notably, three of the phase's own starting assumptions did not survive that reading; the biggest is that a feared incompatibility (the "P44 effort gap") turned out not to exist at all. Research that corrects its own premises is research working as intended.

Intuition

The amnesiac craftsman

Imagine hiring a genuinely talented writer with total amnesia. Every morning they arrive with no recollection of yesterday. You can leave them one sticky note — that is v1's entire institutional memory, and it is literally one integer: the id of a single exemplar article (ContentDraftSettings.reference_content_id, default 19) whose voice and tone the agent imitates. Everything else you told them yesterday — "keep paragraphs to 3–4 sentences," "use current job titles, 정수과장 not 정수대리," "stop opening with a 브랜드 소개 section" — is gone. So the operator types it again. Every job. That is 학습 능력 부재, and it is not a tuning problem; it is the architecture.

The treasure already in the database

Here is the counterintuitive part: v1 already records the operator's corrections, structurally, and throws none of them away. Every time the operator edits the proposed outline at the 구성안 gate, the backend saves her version as a new row and marks the agent's proposal "superseded." The lineage is append-only:

The proposal's verified punchline: nothing reads this. A grep across the backend shows every ContentDraft* query is scoped to a single job. The corrections are captured and then buried. The learning loop is close, not far — the signal exists; there is simply no reader.

The crux: Hermes learns from conversations, but our operator doesn't chat

Hermes's self-improvement works by replaying conversation transcripts: a background review fork reads the recent exchange and decides whether something in it deserves to become a memory entry or a skill. That is a great fit for a chatty assistant. But our operator does not converse with the drafting agent — she fills a form, edits a JSON outline in a purpose-built UI, and clicks approve. A naive integration hands Hermes a transcript that reads, in its entirety, "user: write about 평상집 양재점" — and there is nothing to learn from that.

The central design insight of P54.S1: installing Hermes does not, by itself, fix 학습 능력 부재. The real work is manufacturing a learning signal out of the diff between what the agent proposed and what the operator approved — the data already sitting in Postgres. The proposal estimates this is 70% of the phase's value; the runtime swap is the other 30%.

What the operator actually feels

Trace two jobs through both worlds. In v1, job 2 costs exactly what job 1 cost: the same re-typed instructions, the same 브랜드 소개 deletion (for the fourth time), the same "문단이 너무 길다" revision round. In v2, job 1's corrections became lessons — so job 2's brief is one sentence, the outline arrives without the unwanted section, and the draft comes back in 3–4 sentence paragraphs. Effort falls with every job that teaches something:

Why memory being tiny is a feature. Hermes's MEMORY.md holds 2,200 characters — maybe a dozen entries — and refuses writes past the limit until the model consolidates. That sounds restrictive, but it forces prioritization: only the always-relevant facts live there ("직원 닉네임은 최신 직급으로"), while long editorial doctrine goes into skills, which are loaded only when relevant. Bounded memory is what keeps every future prompt from silting up.

Code

v1, end to end

The system is three services with one strict seam between each pair:

The heart of it is easy to misread as a state machine. It is not — it is a three-way branch on the shape of the input payload:

# apps/agent/app/content_drafts/agent.py:1997 (paraphrased shape)
if payload.latest_version:      # a version exists → operator left feedback
    REVISE   # exact find→replace edits; falls back to full rewrite
elif payload.approved_outline:  # 구성안 approved → write the body
    WRITE    # rehydrate research_state → one section per category → integrate
else:                           # fresh job → research and propose
    OUTLINE  # bounded tool loop (≤8 searches, ≤6 iterations) → filter
             # → categorize → propose the 구성안

Everything the agent will ever know about a job is assembled by one function — _build_generation_payload (draft_dispatch.py:426): the brief, the reference profile, the thread messages, attachments, the latest version, the approved outline. All of it is loaded from that job's rows. This is where the amnesia lives: run the same function for a new job and every lesson from the last one is out of scope by construction.

Defect one, located: the feedback dead-end

Follow one instruction to its grave. The operator types "문단이 너무 길다. 3~4 문장으로 끊어줘" into the thread. draft_views.py:209 stores it as a ContentDraftMessage(kind=feedback); the payload builder serializes it; the REVISE prompt uses it; the revision lands. The job closes. The next job's job.messages is empty — the instruction is gone. Three facts make this structural:

  • Every ContentDraft*.objects read in the backend is job-scoped (verified by grep — the only cross-job accessors are the settings singleton's).
  • The only cross-job carrier is one integer: reference_content_id (models.py:456-491).
  • The prompts have no seam for operator-authored text: house style is a hardcoded Korean constant, _VOICE_GUIDANCE at prompts.py:58. Changing it is a code change, a build, and a deploy — exactly what the meetup meant by "개발자 개입".

And one absence worth naming: there is no reject action. ContentDraftDecision.Action is approve | cancel | approve_outline (models.py:837-841). 반려 exists only as free-text feedback or a cancel — so the moment the operator is most motivated to explain why, the system offers her no structured way to say it. (Adding one is Decision 5 in the proposal.)

Hermes, verified at the pinned tag

What the S1 slice confirmed by reading the Hermes source (every claim carries a file at commit 3ef6bbd2…):

  • Memory: MEMORY.md (2,200 chars) + USER.md (1,375 chars), injected as a frozen snapshot at session start — a mid-session write takes effect next session, deliberately, to preserve the provider's prompt cache. No auto-compaction: at the limit, writes fail until the model consolidates. Entries are security-scanned before acceptance (tools/memory_tool.py:88).
  • Skills: ~/.hermes/skills/<category>/<name>/SKILL.md with three-level progressive disclosure — a ~3k-token catalog of names and descriptions, then one skill's body on demand, then its reference files. The same convention this repo already uses under .claude/skills/.
  • The review fork's trigger is two different counters, and it matters enormously here: memory review counts user turns (default every 10), skill review counts tool iterations within a turn (default every 10). A content-draft job is one long turn with many tool calls — so out of the box the skill review fires and the memory review never does. How we shape the message array decides whether memory review ever runs. A design lever, found only by reading (agent/turn_context.py:492-502, agent/turn_finalizer.py:576-582).
  • The curator sting: the curator (stale after 30 days, archive after 90) only manages skills the background review fork created. Skills pushed in by our backend are treated as user-directed and are never staled, archived, or consolidated — if we push lessons in explicitly, we own their lifecycle (features/curator.md:141-160).
  • write_approval has no HTTP surface: staged memory/skill writes land as plain JSON under ~/.hermes/pending/, approvable only via slash commands — the API server's route table has no /memory, no /pending (gateway/platforms/api_server.py:1482-1523). Our operator approval gate must read and write those files off the shared volume.
  • API surface: /v1/chat/completions (stateless, SSE, inline images) is the main path; /v1/runs is text-only (it coerces content to str), so the image-carrying draft turn cannot use it. File uploads don't exist — image splitting, OCR, and storage stay on our side.
  • The three corrected premises: the feared "P44 effort gap" does not exist — Hermes exposes reasoning_effort globally, per-model, and on 15 of its 18 auxiliary slots, on the identical eight-level ladder (none…ultra) that P44's operator store already uses (hermes_cli/config.py:1636-1816). So the question shrank from "survive losing effort control" to "keep one store as the source of truth" — project P44's DB rows into Hermes's config.yaml.

The v2 shape

Sidecar, not library. The library path was re-examined and fails harder than assumed: the entry points are synchronous plain defs (run_agent.py:6350, 6407), the docs say "never share an instance across concurrent calls," the import is a 301 KB top-level module, and Hermes's own embedded-use guidance is skip_memory=True — disabling the exact feature this phase exists to adopt. So: a hermes compose service on the internal network (no published ports, mandatory API_SERVER_KEY), a persistent hermes_home volume, and apps/agent calling http://hermes:8642/v1/chat/completions. The backend contract does not change — the backend does not know Hermes exists.

The survival map, compressed. The backend draft path (5,342 lines) survives almost entirely — additive migrations only (a lesson store, optionally a rejection reason and a cost-transcript row). The workspace (10,680 lines) survives and grows at two design-touching points (lesson capture; a learned-knowledge review surface). The agent package is where the work is: the hand-rolled orchestration (~1,400 lines of agent.py) becomes Hermes turns, while ~900 lines of deterministic post-processing survive as helpers, and prompts.py's nine builders become a compact per-job system message plus SKILL.md doctrine. The 구성안 gate stays a backend concept: Hermes's turn ends by returning an outline; Postgres stores it; the operator's 5,058-line curation UI — the "관리자 개입 강화" the meetup asked for — keeps working unchanged.

What a lesson looks like once it graduates to a skill — note the Pitfalls line carrying provenance and a count, which is what makes a rule auditable rather than mystical:

name: changple-content-voice
description: Changple house voice and paragraph rules for 창업 case content
version: 3.0.0
---
# Changple 콘텐츠 어투 · 구성
## When to Use
Any 창업 사례 draft or revision for miracle.changple.ai.
## Procedure
1. 문단은 3~4 문장. 한 문단에 한 가지 주장.
2. 비용 관련 수치는 반드시 출처 게시글을 인용 마커로 붙인다.
## Pitfalls
- "브랜드 소개" 섹션을 앞에 두지 않는다 — 운영자가 6회 연속 삭제함 (jobs #…)
## Verification
각 섹션이 3~4문장 문단으로만 구성되었는지 확인.

The new risk class. Today a poisoned Naver Cafe post can damage one job. With a learning loop, a poisoned post that gets distilled into memory reaches every future job — an injection becomes a persistent implant. The proposal's posture: both write_approval gates ON from day one, every lesson carrying provenance, the dangerous toolsets (terminal, browser, execute_code) disabled, the daemon reachable only on the internal network — and, because Postgres is the system of record, a catastrophic Hermes failure costs a re-projection, not the learning.

Best practices & next steps

Where the proposal aligns with prevailing practice

  • Keep the workflow envelope; add agency only inside it. Anthropic's guidance is to "find the simplest solution possible, and only increas[e] complexity when needed" — workflows offer predictability for well-defined tasks; agents earn their keep where flexibility is needed (Building Effective Agents — anthropic.com). The proposal follows this exactly: the job state machine, the gates, and the retry ladder stay predefined code paths in Django; only the drafting brain inside one dispatch becomes agentic. It resists the tempting rewrite-everything reading of "rebuild on Hermes."
  • Skills with progressive disclosure are the emerging standard for durable procedural knowledge. The SKILL.md pattern — metadata always in context, full instructions on demand, resources last — is documented practice (Equipping agents for the real world with Agent Skills — anthropic.com), Hermes implements the same shape, and this repo already uses it. Putting Changple's editorial doctrine there, rather than in an ever-growing system prompt, is the aligned choice.
  • Learning as curated verbal feedback is a validated mechanism. Reflexion showed agents improving sharply by keeping verbal reflections in an episodic buffer instead of updating weights (Shinn et al., 2023 — arxiv.org). The proposal's lesson distiller is that move — with a stronger footing, because our "reflection" is grounded in a structural diff (proposed vs. approved outline) rather than the model's self-assessment.
  • The memory split matches the cognitive-architecture framing. CoALA organizes agents around modular memory components with a structured action space over them (Sumers et al., 2023 — arxiv.org). Hermes's trio maps cleanly: MEMORY.md/USER.md as semantic memory, SKILL.md as procedural, the SQLite session store as episodic — and v1, notably, has none of the three.

Where it deliberately diverges, and why that is defensible here

  • The agent runtime's own memory is not the system of record. Hermes-native practice would let the daemon own its learned state. The proposal instead makes Postgres authoritative and treats ~/.hermes as an idempotent projection — because the operator UI cannot reach Hermes's pending-approval files over HTTP (there is no such API), because a 2,200-character memory ceiling cannot hold the lesson corpus, and because a container volume is a fragile home for the only durable asset the phase creates. This is a considered divergence, not ignorance of the native path.
  • Human approval where Hermes defaults to autonomy. Hermes ships with write_approval off; the proposal turns it on for both memory and skills from day one. In a single-operator system whose failure mode is a silently wrong rule applied to every future article, the approval gate is the mitigation — everything else is defense in depth.

Next steps (as proposed to the operator)

  1. Read one log line before tuning anything: run a single production job and read the existing pool→kept→categories→curated counts at agent.py:2183 to settle which cap actually causes "few documents used."
  2. Build the capture job first — the deterministic outline-diff recorder. It needs no Hermes, no LLM, and starts accumulating training signal immediately.
  3. Run the two spikes before committing: Korean OCR quality on one real KakaoTalk export, and corpus-as-MCP-tools vs. pre-fetched documents.
  4. Stand up the regression gate with the first deploy, not after: one recorded job replayed end to end, asserting on the config keys, API routes, SSE event names, and pending-file layout that a Hermes upgrade could silently change (the repo is ~2,000 commits/week upstream; the pin is SHA 3ef6bbd2…).

Quiz

Five questions. Click an answer to check it.

1. Why does simply installing Hermes and enabling its memory not fix 학습 능력 부재?

The review fork replays the conversation. Our "conversation" is one synthetic turn ("write about 평상집 양재점") — the real signal is the proposed-vs-approved 구성안 diff in Postgres, which the proposal turns into lessons explicitly. That manufacturing step is estimated at 70% of the phase's value.

2. What is the only cross-job memory the v1 content agent has?

ContentDraftSettings.reference_content_id (default 19) is it. The outline rows do exist — but nothing reads them across jobs; every ContentDraft* query in the backend is job-scoped. House style is a hardcoded constant (_VOICE_GUIDANCE, prompts.py:58), not an editable file.

3. The corpus has ~100 candidates pooled per job, yet a section is written from at most 10 posts. Which cap is the binding one?

Realistically 3–5 categories × ≤10 posts = 30–50 posts reach the gate, and each section draws from ≤10 (curation.py:69). Whether this cap or the read-vs-summary gap is the felt cause is unmeasured — which is why the proposal's first next-step is reading the existing funnel log line at agent.py:2183.

4. A content-draft job is one long turn with many tool calls. Out of the box, which of Hermes's two self-improvement reviews fires?

Memory review triggers on user turns (memory.nudge_interval, default 10); skill review on tool iterations (skills.creation_nudge_interval, default 10). The memory counter hydrates from replayed history, so how v2 shapes the message array decides whether memory review ever runs — a design lever found only by reading the code.

5. Why does the proposal insist both write_approval gates be ON from day one?

The blast radius changes class: an injection becomes a persistent implant. Approval gates + provenance + an unlearn surface are the counterweight that makes the learning loop safe to close. (The curator, incidentally, never touches pushed skills — that is the separate "curator sting.")
