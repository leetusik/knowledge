Background

Skip if you know it This page assumes four things from earlier explainers and re-derives none of them: the repo runs two Python apps over one Postgres — a Django backend owning schema backend, a FastAPI agent owning schema agent — with a one-way read grant so the agent may SELECT Django’s tables and never write them (#1); calls between the two services carry a static X-Agent-Service-Token shared secret (#2); retrieval filters on ds.reference_eligible = TRUE and fuses a lexical arm with a vector arm (#7); and a Naver cafe post becomes a stored, enriched, judged row through the ingestion pipeline (#8).

What an “index” means on this page

In everyday database talk an index is a B-tree that makes WHERE post_id = 42 fast. That is not what this page is about. Here an index is a derived, lossy, re-buildable representation of the corpus that exists so a question phrased in Korean prose can find the posts that answer it. The corpus itself — backend.documents_documentsource, one row per Naver cafe article — is the truth. Everything this page builds lives in the agent schema, is derived from that truth, and could be dropped and rebuilt tonight without losing a single post.

The derived representation is an embedding. An embedding model takes a piece of text and returns a fixed-length list of numbers — here 3,072 floating-point numbers — chosen so that texts about similar things end up pointing in similar directions. Nobody assigns meanings to the individual numbers; what matters is only the angle between two of these vectors.

The angle is measured with cosine distance: 1 − cos(θ), so identical direction is 0, unrelated is around 1. Postgres’s pgvector extension spells this operator <=>. Here is the whole idea in three dimensions instead of 3,072, with the numbers actually computed:

Two practical consequences follow, and both shape the code:

  • Finding the nearest vector is a scan. With no help, Postgres computes the distance from the query to every stored row and sorts. At a few thousand rows that is milliseconds and perfectly fine. At tens of thousands of rows, several times per chat turn, it is not.
  • So there are ANN indexes. ANN = approximate nearest neighbour: a data structure that finds almost always the right neighbours in a fraction of the time. pgvector’s is HNSW (hierarchical navigable small world) — a layered graph of vectors you descend like a skip-list. Approximate is the price; you can miss a true neighbour occasionally.

Why one column here is vector and two are halfvec(3072). pgvector caps an HNSW index on the plain vector type at 2,000 dimensions, and this model returns 3,072. The halfvec type (16-bit floats, half the storage) is indexable up to 4,000, so the two chunk tables use it and get an HNSW index; the older summary table keeps a dimension-less vector column and gets no ANN index at all — which, at one row per post, is a deliberate non-problem. Every one of those facts is load-bearing later on this page.

Intuition

A card catalogue and a page index

Think of the 창플 corpus as a library of roughly 42,000 short documents. There are two useful ways to index a library, and this system builds both.

Pipeline A — the card catalogue (one card per post) During ingestion (#8) a Gemini pass already wrote each post a summary (150–500 characters) and up to 10 keywords. This pipeline embeds the summary into one vector and copies the keywords into a text[]. One row per post. That is what the lexical arm matches against and what the summary vector arm searches.
▼
Pipeline B — the page index (many chunks per post) A card tells you a post is about 치킨집 opening costs. It cannot tell you that the number “보증금 3,000” appears at character 1,700 of that post. So this pipeline cuts each post into overlapping ~900-character chunks, embeds every chunk, and stores the character offsets. Now a citation can quote the exact span.
▼
Pipeline C — the same page index over a different library 미라클 콘텐츠 are the operator’s own long-form published documents. Same chunker contract, different corpus, different eligibility rule, its own table — a deliberate sibling of B rather than a generalization of it.

The one idea that makes all three cheap: a fingerprint

Embedding text costs money and takes about a second per request. A pipeline that re-embedded everything on every run would be unusable. All three runners therefore share one trick: before embedding anything, compute a fingerprint — a SHA-256 over exactly the text that would be embedded — and compare it with the fingerprint stored beside the existing artifact. Same fingerprint and same embedding model? Skip; it is already correct.

# apps/agent/app/indexing/storage.py  (Pipeline A)
def build_source_fingerprint(summary: str, keyword_terms: Sequence[str]) -> str:
    canonical_payload = {
        "keyword_terms": list(normalize_keyword_terms(keyword_terms)),
        "summary": normalize_summary(summary),
    }
    canonical_json = json.dumps(canonical_payload, ensure_ascii=False,
                               separators=(",", ":"), sort_keys=True)
    return hashlib.sha256(canonical_json.encode("utf-8")).hexdigest()

Three details in those eight lines are the whole discipline. The payload is normalized first (whitespace collapsed, keywords case-folded and de-duplicated in order), so cosmetic edits do not trigger a re-embed. The JSON is canonical (sort_keys, no spaces), so the hash is stable across processes and Python versions. And the chunk pipelines put their chunker version inside the hash:

# apps/agent/app/indexing/chunking.py
CHUNKER_VERSION = "1"
...
canonical_payload = {"chunk_texts": [...], "chunker_version": CHUNKER_VERSION}

So bumping CHUNKER_VERSION is how you say “re-chunk and re-embed the entire corpus” — one character in one file — and not bumping it is how a re-run costs one scan and zero provider calls. The comment above it states the rule outright: “Never bump for a pure refactor.”

The overlap rule prefers to snap back to a line start within its 150-character budget; here paragraph 5 is 230 characters long, so no line start falls inside the budget and the code falls to its second branch — snap forward to the nearest space. Deterministic either way.

The hand-off loop, and what ingested means

Pipeline A is the only one of the three that talks back to Django, and the reason is a single boolean column. #8 left the corpus with posts that are eligible — reference_eligible = TRUE, the eligibility engine’s materialized verdict — but not yet ingested. The distinction is exactly:

ColumnOwnerMeans
reference_eligibleThe backend eligibility engine (#8) “This post is allowed to be quoted to a user.”
ingestedThis page’s hand-off loop “A current summary-index artifact exists for this post.”

Retrieval requires both (#7). And the pending work queue is precisely the gap between them: reference_eligible = TRUE AND ingested = FALSE. That is why the agent cannot simply set the flag itself — it has no write grant on the backend schema (#1). It has to ask, over HTTP, with the service token:

The fingerprint travels on that last leg for a reason worth pausing on. Between the agent reading the summary and Django marking the post ingested, an enrichment job may have rewritten that summary. So the agent sends the fingerprint of what it actually embedded, Django recomputes the fingerprint of what the row holds now, and a mismatch is refused with source_changed — the post stays ingested = FALSE and gets picked up again next run. The flag can never claim an artifact that describes an older version of the post.

And now “re-index a post” has a precise meaning: set ingested = FALSE in the backend. That is a backend data operation, not an agent invocation. The next run selects it, sees a fingerprint mismatch (or a model mismatch), re-embeds, upserts, and hands it back.

Code

Everything below lives in two places: apps/agent/app/indexing/ (19 modules, ~5.7k lines — the three pipelines) and a handful of Django clients under apps/backend/ingestion/. 1. Pipeline A — the summary index

The two routes

apps/agent/app/api/routes/indexing.py exposes exactly two endpoints, both behind require_agent_service_context (the shared-secret dependency from #2 and #3 — no user JWT is accepted here):

@router.post("/indexing/runs", status_code=status.HTTP_202_ACCEPTED, ...)   # :98
@router.get("/indexing/runs/{run_id}", ...)                                  # :139

The request model is strict in a way that documents the contract (IndexingRunCreateRequest, extra="forbid"): post_ids must be non-empty and positive (duplicates are dropped, order preserved); trigger must be automatic_schedule or manual_incremental; and a model-level validator enforces that the matching backend run id is present and the other one absent — an automatic run carries backend_automatic_run_id and may not carry backend_manual_incremental_run_id, and vice versa. One more field has a comment worth reading:

# P53.S4: the floor may legitimately be 0 ("no floor"). A `ge=200` bound
# here 422s an entire indexing run the moment the operator drops it.
bot_min_content_length: int = Field(ge=0)

That is the length policy from #8 travelling as data on every request, because the operator owns it and the agent must never out-gate the backend engine.

The POST does three things and returns: register a run record in Redis, hand the actual work to FastAPI’s BackgroundTasks, and answer 202 with the run id. The background task flips the record to running, calls the synchronous runner on a worker thread (anyio.to_thread.run_sync — the runner uses blocking psycopg and must not sit on the event loop), and writes back a terminal status. That status is computed, not guessed:

def _resolve_terminal_status(summary):            # indexing.py:203
    failed, handoff_failed = ...
    if not failed and not handoff_failed:
        return "succeeded"
    successful_work = sum(... "embedded", "reused_current_artifact", "handed_off",
                          "skipped_unchanged", "skipped_ineligible",
                          "skipped_below_floor", "skipped_unprojectable" ...)
    return "partial" if successful_work else "failed"

succeeded / partial / failed — and note that a counted skip is treated as resolved work, never as a failure.

The run registry (Redis)

run_registry.py is a small Redis hash per run under the key prefix agent:indexing:run on db/0 (the registry database from #1), holding trigger, the backend correlation ids, requested_post_count, status, a JSON summary and error_message. Two TTLs: 6 hours while active, 1 hour once terminal. Every Redis failure is converted to IndexingRunRegistryUnavailableError and surfaces as a 503.

The TTL is shorter than a big run. A full-corpus pass takes hours; the registry entry expires after six. So a GET that 404s does not mean “that run failed” — it usually means “the registry forgot” while the work continued. The chunk-run client on the Django side takes this so seriously that it raises a separate exception type for a 404 (AgentChunkRunNotFound, deliberately not a subclass of its generic client error) so a poller can stop polling without declaring the run dead. Real progress lives in the artifact tables, not in Redis.

The projection — what “pending” means, in SQL

projection.py is the read bridge in its purest form: the agent reading Django’s tables, schema-qualified because this connection pins no search_path (#2). The one shared SELECT prefix is the definition of pending work:

SELECT ds.post_id, ds.author, ds.text_with_image_replacement, ds.summary, ds.keywords
FROM "backend"."documents_documentsource" AS ds
INNER JOIN "backend"."documents_documentsourcestatus" AS dss
    ON dss.post_id = ds.post_id
    AND dss.status = %s              -- 'SAVED'
WHERE ds.ingested = FALSE
    AND ds.reference_eligible = TRUE

The comment above it names the history: this used to be an INNER JOIN against an AllowedAuthor table — “the agent’s own private copy of the author rule — exactly the divergence the engine exists to end.” Today eligibility is one materialized column and the agent only reads it.

Rows that come back still have to project, and a row that cannot is counted, never silently dropped. _projection_from_row returns either a DocumentIndexProjection or one of two refusal reasons:

1unprojectable — a data problem: bad post_id, non-string author, empty body, empty summary, keywords not a list, or an empty keyword list after normalization. A junk index entry avoided.
2below_floor — a policy decision: len(content_text) <= min_content_length, where the floor came in on the request. Only checked when the floor is above 0, which it is not in production today.

The tally class carries a comment that is really an incident report: before it existed, “a refusal was a silent continue — S25’s stranded-set re-embed lost 540 sub-floor posts out of a run that reported skipped_ineligible: 0, and the pass had to be repeated with the floor at 0 before anyone could tell where they went.” Hence _report_projection_ refusals in the runner, which prints the drop count and the floor in force even when the run resolved to nothing.

The runner

runner.py’s entry point is run_indexing() (:473), and it has two modes. With post_ids it runs explicit mode (_select_explicit_documents, :145) — the mode the route always uses. Without them it runs pending mode (_select_pending_documents, :88), a keyset walk over the pending query in pages, used by the module’s own CLI (python -m app.indexing.runner --limit N).

Pending mode does something explicit mode cannot: it splits the selection in two. For each candidate it loads the existing artifact (batched, WHERE post_id = ANY(%s)) and asks artifact_requires_reindex:

def artifact_requires_reindex(artifact, *, summary, keyword_terms, embedding_model) -> bool:
    if artifact is None:
        return True
    return (artifact.source_fingerprint != build_source_fingerprint(summary, keyword_terms)
            or artifact.embedding_model != normalize_embedding_model(embedding_model))

“No” does not mean skip. It means the artifact is already correct and the post is merely missing its ingested flag — so it goes straight into the hand-off list as a handoff_candidate with no provider call at all. That is what makes a crashed run cheap to resume: the posts it embedded but never reported are re-selected next pass, find a current artifact, and are simply handed off.

The constants at the top of the module are the run’s whole economics:

ConstantValueWhat it governs
DEFAULT_PENDING_LIMIT100Sweep-mode page size / default cap.
DEFAULT_EMBEDDING_BATCH_SIZE1Not a provider batch — the accumulation and fail-soft group size.
DEFAULT_EMBEDDING_RETRY_ATTEMPTS3Retries for a transport error (not a provider rejection).
DEFAULT_HANDOFF_BATCH_SIZE100Posts per hand-off POST back to Django.

The comment on the second one is the best short explanation of fail-soft batching in the repo:

“1, not 20. Since P53.F4 the summary client issues one provider request per text, so this is only the accumulation / fail-soft group size — and under 429 pressure a group of 20 is an amplifier: one exhausted-retry text discards up to 19 successful embeddings and re-requests them through the split ladder (20 → 10 → 5 → 3 → 2 → 1). At 1 a 429 costs exactly one post and no quota is spent twice.”

That split ladder is real code: _index_projection_batch catches an embedding error and, if the group holds more than one projection, halves it and recurses on both halves; at size 1 it records the failure against that post and moves on. Nothing raises out of a single document’s failure — that is the runner’s documented contract.

Hand-off is decoupled from embedding for a cost reason that only shows up at scale. The comment: reporting once per embedding group “would, at group size 1, open one backend handoff job per post (~12k single-item IngestionJob rows for a full-corpus pass, plus a round trip in the pacing path).” So candidates accumulate and flush at 100, with a final flush before run_indexing returns.

The artifact store and its DDL

storage.py owns agent.document_index_artifacts and the four normalizers every other module imports. Here is the table, verbatim from build_create_table_sql (:131):

CREATE TABLE IF NOT EXISTS "agent"."document_index_artifacts" (
    post_id integer PRIMARY KEY,
    summary_embedding vector NOT NULL,
    keyword_terms text[] NOT NULL,
    source_fingerprint char(64) NOT NULL,
    embedding_model text NOT NULL DEFAULT '',
    indexed_at timestamptz NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()

Look at summary_embedding vector — no dimension. Postgres will accept a 1,536-dimension vector into that column without a murmur. The damage surfaces much later, at query time, when <=> refuses to compare a 1,536-wide row with a 3,072-wide query vector. There is no schema constraint to lean on, which is exactly why the assertion lives in the client (SUMMARY_EMBEDDING_DIMENSIONS = 3072) at “the only place that can still tell the difference between ‘provider returned something odd’ and ‘the corpus is now half-poisoned’.”

keyword_terms is the other half of the story, and it closes a loop from #7. The lexical retrieval arm is not full-text search — no tsvector, no trigram — it is exact set matching (dia.keyword_terms && inputs.lexical_matches). That only works because both sides run through the same normalizer, normalize_keyword_terms, which case-folds, collapses whitespace and de-duplicates in order. Index time and query time agree by construction, not by convention. The same function also feeds build_source_fingerprint — and that function has a byte-identical twin on the Django side (apps/backend/ingestion/fingerprints.py:36), because the hand-off verification recomputes it there.

The write is a plain upsert on the primary key, refreshing every column and updated_at = now(), followed by an explicit commit().

The hand-off client, and the Django side of it

backend_handoff.py is the only place in the agent that writes to the backend, and it does so over HTTP with a single header:

headers = {"X-Agent-Service-Token": self._service_token}        # :223
url = f"{self._backend_base_url}/api/documents/ingestion/index-handoffs"

No user JWT, no correlation splat — there is no user in this flow (contrast the chat path in #4, where the agent forwards the caller’s own bearer token). The client is paranoid about the answer in a way worth copying: it validates every item, refuses duplicate post ids in the request, and then asserts that the set of post ids in the response equals the set requested — anything else raises rather than silently mis-attributing an outcome.

On the Django side ingestion/index_handoff.py::execute_index_handoff materializes the whole thing as an IngestionJob of type INDEX_HANDOFF with one IngestionJobItem per post — so a hand-off is visible in the operator console like any other job — and then walks a five-outcome ladder per item:

1source_missing — no DocumentSource row.
2source_status_missing / source_not_saved — the post is no longer in SAVED.
3source_changed — the recomputed fingerprint differs from the one the agent sent. The current fingerprint is written into the item payload for forensics.
4already_ingested — succeeded, nothing to do (a re-report is harmless).
5marked_ingested — DocumentSource.objects.filter(pk=...).update(ingested=True). The only write in the whole hand-off.

The view behind it (IngestionIndexHandoffView) is authentication_classes = [AgentServiceTokenAuthentication] with permission_classes = [AllowAny] — the idiom from #3: the authenticator is the gate, so “allow any authenticated caller” means “allow the one caller that has the token”.

And who starts all this? From #8: the automatic run’s indexing stage. ingestion/agent_indexing.py::create_agent_indexing_run POSTs over plain urllib with a 30-second timeout, then the stage polls GET /agent-api/indexing/runs/{run_id} every AGENT_INDEXING_POLL_INTERVAL_SECONDS = 30, with a retry ladder of 3 attempts 300 seconds apart. If the candidate list is empty the stage succeeds immediately and never calls the agent at all.

2. Pipeline B — the naver chunk layer

Pipeline B answers a different question: not “which posts are about this?” but “where in this post is the answer?” It shares no code with Pipeline A beyond four normalizers, it never touches a backend column, and it is triggered separately.

The chunker (chunking.py)

Its input is not the stored body text but the SmartEditor segment array the scraper captured, plus the post’s images. Four segment types exist and the distinction between two of them is the sort of thing that is invisible until it is wrong:

SegmentRendered as
{"type": "text", "text": ...}content, appended to the current line buffer
{"type": "image", "placeholder": "IMAGE_n"}[IMAGE_n], or [IMAGE_n:alt] when generated alt text exists
{"type": "break"}a line boundary; consecutive ones collapse
{"type": "blank"}an authored blank line — a paragraph separator, not content

The module docstring says why the last row matters: “A chunker that treats it as text emits empty content and skews every boundary.” Blank lines are what define paragraphs, and paragraphs are what the packer packs.

The rendering rules mirror the scraper’s own renderer line for line — zero-width characters stripped, horizontal whitespace collapsed, the two player-chrome strings {"예약", "재생"} dropped outright, blank-line runs capped at 2, leading and trailing blanks trimmed. Alt text goes through sanitize_alt_text, a deliberate mirror of the backend’s function of the same name (note it rewrites [/] to parentheses, so alt text can never forge a placeholder). All of that exists to support one claim, verified on 2,500 real rows: the chunker’s rendered text is byte-identical to the text_with_image_replacement the backend stored — which is what makes char_start/char_end valid offsets into that stored column.

Then the packer, with three constants and four rules:

CHUNK_TARGET_CHARS  = 900     # greedy pack target
CHUNK_MAX_CHARS     = 1400    # hard ceiling
CHUNK_OVERLAP_CHARS = 150     # carried backwards into the next chunk
1Short post → one chunk. len(rendered_text) <= 1400 emits a single chunk flagged is_whole_post = True. “Chunking these is pure cost — the chunk would equal the post.”
2Units are paragraphs. Maximal runs of non-blank lines. A unit boundary is therefore always a paragraph boundary, “which is what makes the packer prefer paragraph boundaries without any extra scoring.”
3Oversized units split downward: first on their own line boundaries, then — only if a single line still overflows — on whitespace inside that line, with a hard cut as the last resort.
4Pack greedily, then overlap. Keep adding units while the current chunk is under 900 and adding the next stays under 1,400. Then extend each chunk’s start backwards by up to 150 characters, snapped to a content line start when one falls inside the budget, otherwise forward to the nearest space.

Every chunk carries a context header built by build_chunk_header — [title] · board · author · YYYY-MM, skipping absent parts. The header is prefixed to chunk_text (so it is embedded, which is the cheap deterministic form of “contextual retrieval”) but is deliberately outside the span. From the toy run earlier:

chunk_text = "[치킨집 창업 비용] · 창업준비 · 창플지기 · 2026-03\n" + body
body       = rendered_text[char_start:char_end]     # exactly, asserted

What Pipeline B scans (chunk_projection.py)

Same two tables, one crucial difference in the WHERE:

WHERE ds.ingested = TRUE            -- Pipeline A said FALSE
    AND ds.reference_eligible = TRUE

“The chunk index trails the post-level index, so a post that has not been summarized/indexed yet is not chunk material either.” It selects more columns than Pipeline A — title, category (the board name), author, published_at, image_urls, content_segments — because the chunker needs them for the header and the rendering. And filter_still_chunkable() re-uses the identical predicate for the stale sweep, so the sweep can never disagree with the scan.

Three deliberate differences from Pipeline A’s table. The primary key is (post_id, chunk_index), not post_id. The embedding column is halfvec(3072) — pinned, because an ANN index requires a fixed dimension — with an HNSW index using halfvec_cosine_ops. And the fingerprint plus chunker_version are stored on every row of the set.

The halfvec type has a sharp edge the module calls out twice: on the way in you must bind an explicit HalfVector(...) (a bare Python list is sent as float8[] and rejected), and on the way out a HalfVector has no __iter__, so the summary path’s normalize_summary_embedding cannot be reused — hence chunk_embedding_to_list(). This is also why the retrieval arm in #7 must cast its query vector as %s::halfvec(3072): the cast has to name the same type the index was built on, or the planner ignores the HNSW index.

The write path is one method with a one-line justification:

def replace_chunk_set(...):
    """DELETE + INSERT + one commit. A partially-replaced set would carry a
    fingerprint that describes chunks it no longer holds."""

There is also a read helper, list_chunks_for_posts, which never selects embedding: “a halfvec read costs 6 KB per row and the retrieval arm already has its distance from SQL.”

The catch-up run (chunk_runner.py)

run_chunk_indexing() (:237) walks the chunk-eligible corpus by keyset, 200 posts per page. For each post: build the chunk set (_build_pending, :91), compute its fingerprint, compare against the stored ChunkSetState (fingerprint and embedding model and chunk count), and either skip or queue. Queued chunks accumulate until they reach the embedding batch size, then _flush_pending (:120) embeds them and replaces each post’s set in its own transaction.

Its failure posture is per-post and deliberate: if any chunk of a post fails to embed, that whole post is skipped and counted in failed, because a partial set is worse than no set. A persistence failure rolls the connection back and moves on.

The reconciler is the part most people forget to build:

def _sweep_stale_chunk_sets(...):                      # :204
    # keyset-walk the CHUNK table (not the corpus), 1000 post ids at a time
    still_chunkable = document_store.filter_still_chunkable(indexed_post_ids)
    stale_post_ids  = [p for p in indexed_post_ids if p not in still_chunkable]
    chunk_store.delete_chunk_sets(stale_post_ids)

A post that was banned, moved to a de-indexed board, or deleted stops being chunk-eligible — but its chunk rows would otherwise sit in the retrievable index forever. The sweep walks the index itself, asks the corpus which of those posts are still valid, and deletes the complement. It runs only when the run is unscoped: if reconcile_stale and not post_ids and limit is None (:345). A scoped run knows nothing about the rest of the index and must not guess.

Triggering it

Routes: POST /agent-api/indexing/chunk-runs (chunk_indexing.py:56) and GET /agent-api/indexing/chunk-runs/{run_id} (:91), same service-token dependency, same 202-then-background-task shape. Progress is reported during the run: the synchronous runner calls a progress callback which hops back to the event loop with asyncio.run_coroutine_threadsafe, fire-and-forget, because “a progress write must never slow down or fail the run.” The registry key prefix is agent:indexing:chunk-run — its own key space, so “which corpus was that run?” stays answerable from Redis alone.

The Django-side client, ingestion/agent_chunk_indexing.py (create_chunk_run :112), is worth reading for its docstring alone. It deliberately exposes neither limit nor embedding_batch_size, because their only effect from the backend would be to disable the stale sweep or re-tune a knob the agent owns. It refuses an empty post_ids list with a ValueError rather than forwarding it — the agent reads falsy post_ids as “the whole corpus”, so forwarding [] would turn “index these zero posts” into a multi-hour full run. And it states the cost honestly: the initial full build was 26,562 chunks over 7 h 29 m. “Callers must plan for hours, not minutes.”

No conflict guard on this route. Unlike Pipeline C’s, this route registers every run it is asked for — no single-active-run check, no 409. Two overlapping full runs would both walk the corpus and race on the same chunk rows. Mutual exclusion is the caller’s job, and the module says so.

3. Pipeline C — the content chunk layer

The content_chunk_* modules are a deliberate sibling set: same contract, no shared code. The docstring explains the refusal to generalize — chunking.py exists to reproduce the Naver scraper’s renderer byte for byte, “which has no analogue here, and a shared abstraction would put the naver corpus at risk for a refactor it does not benefit from.”

Its input is backend.content_notioncontent.extracted_text — the flattened published document the backend materializes. Its eligibility predicate is written once and reused by the scan, the by-id fetch and the sweep:

# content_chunk_projection.py:49
_CHUNKABLE_CONTENT_WHERE = (
    "c.html_path <> '' AND c.has_body = TRUE AND c.published_at IS NOT NULL"
)

The module is emphatic that this is not the naver gate: “reusing filter_still_chunkable here would delete this whole index on its first run.” Two sibling indexes, two predicates, neither able to delete the other’s rows.

Headings instead of blank lines

The backend extractor emits no blank lines — every line it produces carries content. So chunking.py’s paragraph rule would see the entire document as one unit and fall through to the oversized-unit splitter, losing every real boundary. Here the structure is the markdown heading, and it is treated as structure:

_HEADING_LINE_RE       = re.compile(r"^(#{1,3}) +(.*)$")   # h1/h2/h3 from the extractor
_HEADING_PATH_SEPARATOR = " > "
CONTENT_CORPUS_LABEL    = "미라클 콘텐츠"

A heading always starts a new section and a new chunk; a section carrying a different heading path never merges into its neighbour; and the heading path in force travels into the chunk header. The two differences that are not cosmetic

Everything else about Pipeline C mirrors B — same 900/1400/150, same fingerprint discipline, same halfvec(3072) + HNSW table (content_chunk_artifacts, keyed (content_id, chunk_index), plus one extra column extractor_version), same one-request-per-text embedding client. Two things differ on purpose:

(a) A single-active-run guard. content_chunk_run_registry.py adds one Redis string key, agent:indexing:content-chunk-run:active, taken with SET nx ex and released on the run’s terminal status — but only when the stored run id still matches. A second run gets ContentChunkRunConflictError (:45) and the route answers 409 without registering a run. Why here and not for naver chunks? Because Pipeline C fires per publish (that trigger is #12’s subject), so overlapping runs are the normal case rather than an operator error, and “two runs writing the same content’s chunk set concurrently is not something idempotency alone saves you from.” The route’s comment adds that the 409 is retriable by construction: the run that holds the corpus heals whatever this one was going to do, except for the ids it was never told about — which is why the caller retries rather than drops.

(b) Scoped de-indexing. Pipeline B reconciles only on a full run. Pipeline C reconciles in two shapes, both driven by one flag:

def _de_index_scoped_contents(requested_ids, *, chunkable_ids, ...):   # :216
    stale_ids = [cid for cid in requested_ids if cid not in chunkable_ids]
    chunk_store.delete_chunk_sets(stale_ids)
    progress.deleted_scoped += len(stale_ids)

A requested content that does not come back from the eligibility query was unpublished, emptied or deleted — so its chunk set goes, and the count lands in its own counter, deleted_scoped, distinct from the full sweep’s deleted_stale. That is what makes POST {"content_ids": [id]} a single call shape the backend can fire on publish and on unpublish. Before it existed, an unpublish had to wait for a full catch-up sweep — meaning an unpublished content stayed retrievable in the meantime.

4. The one-embedding posture, and why batch_size = 1

Every embedding client in this repo sends one text per provider request. That looks like a beginner’s mistake — batching is the obvious optimization — and it is instead the single most expensive lesson in the indexing history. The module docstring states it as a measurement, not an opinion:

“ONE SUMMARY PER PROVIDER REQUEST — measured, not assumed. GoogleGenerativeAIEmbeddings.embed_documents accepts a list and packs it into client.models.embed_content(contents=[...]), but through this project’s key that call returns exactly one embedding no matter how many contents are sent (2 sent → 1 back; 5 sent → 1 back; 20 sent → 2 back, langchain having split them into two token-budgeted sub-requests that each returned one). The batched version of this client therefore raised SummaryEmbeddingBatchResultError for essentially every batch — and a client that did not check would have paired the wrong vector with the wrong post.”

Read that last clause twice. The failure that did happen was loud: ~95 % of a full-corpus pass failing, 6,239 errors in 72 minutes. The failure that was avoided would have been silent — post 12,345 wearing post 12,340’s vector, forever, discoverable only as “retrieval feels a bit off”. Every client therefore carries the same guard:

if embeddings is None or len(embeddings) != 1:
    raise ...("returned N embeddings for a single summary")
values = [float(v) for v in embeddings[0]]
if len(values) != SUMMARY_EMBEDDING_DIMENSIONS:      # 3072
    raise ...("returned N dimensions; the summary embedding must have 3072")

The shared shape across the three write-side clients (indexing/embeddings.py, chunk_embeddings.py, content_chunk_embeddings.py) is exactly five things: one request per text; call_with_retry per request (the bounded 429 retry envelope in app/llm_resilience.py, whose internals are #16’s subject); the timeout carried in request_options because GoogleGenerativeAIEmbeddings exposes no timeout kwarg; a 1.0-second monotonic slot gate; and the two guards above.

def _wait_for_request_slot(self) -> None:
    if self._request_interval_seconds <= 0:
        return
    now = time.monotonic()
    if self._last_request_at is not None:
        remaining = self._request_interval_seconds - (now - self._last_request_at)
        if remaining > 0:
            time.sleep(remaining)
    self._last_request_at = time.monotonic()

(The fourth client, the query-side retrieval/embeddings.py from #7, is single-text by construction — it calls embed_query on one string — and shares only call_with_retry and the request_options timeout. It needs no slot gate: one user question is one request.)

“Batch size 20” and “one per request” are both true

The chunk client sets DEFAULT_CHUNK_EMBEDDING_BATCH_SIZE = 20, which looks like a contradiction until you read what the number does. embed_chunks() loops: return [self._embed_one(text) for text in texts]. Twenty texts is twenty requests, one second apart. The batch size is the runner’s accumulation and fail-soft granularity — how many chunks it collects before it writes, and therefore the blast radius of one failure. For the summary runner that number is 1, because a failed group is retried through a halving ladder and a group of 20 would re-request up to 19 successful embeddings.

Three consequences you have to know

1The summary column accepts a wrong-width vector silently. summary_embedding vector has no dimension, so there is no schema constraint. The client-side assertion is the only defence, and the damage would otherwise appear at query time, corpus-wide.
2Switching embedding models is a whole-corpus operation. gemini-embedding-2-preview and GA gemini-embedding-2 are distinct vector spaces of the same width: <=> compares them without complaint and just returns worse neighbours. The only component that notices is the ranked cache, whose key carries the model id (#7). A migration must re-embed the whole corpus in one window, and ds.ingested = FALSE is the gate on every re-embed path.
3Pacing is ours, not the provider’s. Under the preview model a quota ceiling (~8 requests in 4 s) forced group size 1 and a stretched retry envelope. On GA the same corpus indexed at 59.6 posts/min with zero 429s — exactly the client’s own 1.0-second slot. Lowering that interval is an available, untested lever.

The model id itself is settings.gemini_embedding_model (apps/agent/app/config.py:140), currently gemini-embedding-2, GA, 3,072 dimensions. It is env-pinned in compose.yaml (GEMINI_EMBEDDING_MODEL: ${GEMINI_EMBEDDING_MODEL:-gemini-embedding-2}) and deliberately not in the operator’s live LLM-role store (#2), unlike the rerank model — because a live toggle here would silently split the corpus across two vector spaces. The code comment says it plainly: “a missing env var must not silently select a dead model.”

5. Bootstrap — where the three tables come from

The agent owns no migration framework. Its DDL is one idempotent function, apps/agent/app/db/bootstrap.py::bootstrap_agent_db (:60), and it runs on every container start — the Dockerfile’s last line is:

CMD ["sh", "-c", "python -m app.db.bootstrap && exec uvicorn app.main:app --host 0.0.0.0 --port 8001"]

So a failed bootstrap is a container that never serves, which is the intended behaviour. The function checks three preconditions and then does all its DDL under one lock:

1The configured schema exists — otherwise RuntimeError. The agent creates data, not schemas; roles and schemas belong to infra/postgres/init/00-bootstrap.sh (#1).
2The vector extension is installed, and the halfvec type exists (:41) — the probe for pgvector ≥ 0.7.0, “insurance against a database whose extension is older or was never upgraded (ALTER EXTENSION vector UPDATE)”.
3SELECT pg_advisory_xact_lock(key) where the key is derived from "agent:document_index_artifacts". Transaction-scoped, so it releases on commit. The comment is a standing instruction: “One transaction-scoped advisory lock serializes ALL agent DDL here — never derive a second key.” Two agent containers starting at once therefore cannot race.
4Six statements, all IF NOT EXISTS and forward-only: the summary table, its late-added embedding_model column, the naver chunk table + its HNSW index, the content chunk table + its HNSW index. Neither index is CONCURRENTLY — that is forbidden inside a transaction, and the tables are empty at creation, so the build is instant and later inserts extend the graph incrementally.
5Finally, outside the DDL block: asyncio.run(setup_chat_checkpointer(settings)) — the LangGraph checkpointer tables from #5.

Quiz

1. A post has reference_eligible = TRUE and ingested = FALSE. What is true of it?

reference_eligible is the backend engine’s verdict (“may be quoted”); ingested is this pipeline’s receipt (“a current artifact exists”). Retrieval requires both, and the pending queue is exactly the gap between them. Pipeline B additionally requires ingested = TRUE, so no chunk set exists either.

2. Why does agent.document_index_artifacts.summary_embedding have no ANN index while both chunk tables do?

An ANN index needs a fixed dimension, and vector caps out at 2,000 dims for HNSW. halfvec is indexable to 4,000, which is why the two chunk tables use it with USING hnsw (embedding halfvec_cosine_ops). The summary arm still uses <=> — just as an exact scan, one row per post.

3. The chunk embedding client sets DEFAULT_CHUNK_EMBEDDING_BATCH_SIZE = 20 while the summary runner sets DEFAULT_EMBEDDING_BATCH_SIZE = 1. What does that number mean?

Both clients loop [self._embed_one(text) for text in texts]: one request per text, 1.0 s apart. The batch size only sets how much work one failure discards. The summary runner uses 1 because its recovery path halves a failed group (20→10→…→1) and would re-request already-successful embeddings.

4. You switch GEMINI_EMBEDDING_MODEL to a new model of the same width and restart, without re-embedding. What happens?

Two model ids are two vector spaces of the same width; <=> compares them without complaint and returns worse neighbours. It is a silent-degradation risk, not an error. Selection does compare embedding_model — but pending mode only sees posts with ingested = FALSE, so a migration means re-embedding the whole corpus in one window, gated by setting that flag false.

5. Why does the content chunk route answer 409 when a run is already active, while the naver chunk route happily starts a second one?

The guard is one Redis key, agent:indexing:content-chunk-run:active, taken with SET nx ex and released on the terminal status only when the stored id matches; the 409 is raised before any run is registered, and is retriable by construction. The naver route has no such check — two overlapping full runs would race on the same chunk rows, and its docstring says so outright.
