Retrieval: the RAG read path from query plan to ranked citations

Explainer #7 of the changple5 builder’s curriculum, Part B. Explainers #5 and #6 kept calling search_changple_documents a “tool surface” and promised to open it later. This is later. Between the model emitting search_changple_documents("치킨집 창업 비용") and the model receiving a handful of citable 창플 카페 posts, roughly a dozen modules run: a query planner, two SQL arms over a read-only bridge into another app’s database, a materialized eligibility boolean, a live brand policy, rank fusion, a recency boost, a second language model whose only job is reordering, a five-minute Redis cache, and a body fetch deliberately postponed to the very end.

Background

What “RAG” means in this application, concretely

Retrieval-augmented generation (RAG) is the pattern where, instead of hoping a language model already knows something, you look it up first and paste what you found into the model’s prompt for this one request. The model is a very good reader and a very unreliable librarian; RAG makes it read rather than remember. In changple5 the shape is exactly that and nothing more exotic: a 창플 member asks “치킨집 창업 비용이 얼마나 드나요?”, the agent runs a search over the 창플 카페 archive, and the top few posts — title, author, date, summary and full body text — are handed to Gemini inside a tool result. The answer the user reads is written by Gemini from those posts, and every [post:2841] marker in it points at one of them.

That last clause is the product rule the whole pipeline exists to serve, and explainers #5 and #6 already established it: a document is citable only if THIS turn retrieved it. Prior turns’ tool results are deleted from the model’s context, and a citation marker for a document that is not in this turn’s retrieved map is stripped before the user sees the answer. So retrieval is not a convenience layer — it is the only supply of citable material, once per turn, and the quality of an answer is bounded by what this pipeline returns.

Skip if you know it Five facts this page builds on, all from earlier explainers. (1) Two apps share one Postgres over a one-way read bridge: Django owns the backend schema, the FastAPI agent owns agent and holds SELECT-only rights on backend (#1, #2). (2) The agent’s connection pins no search_path, so every cross-schema table name is written out in full (#2). (3) Redis is split by logical database: db/0 registries and rate limits, db/1 the Django cache, db/2 the agent’s retrieval cache (#1). (4) Some config is live: a 30-second snapshot read out of operator-owned tables across the bridge, never a redeploy (#2). (5) A chat turn may call retrieval tools at most MAX_CHAT_RETRIEVAL_CALLS = 4 times, and each call returns at most resolve_chat_max_tool_results(...) documents (#5).

The corpus — or rather, the two corpora

Retrieval here reads two completely different bodies of text, and keeping them apart is a recurring theme of this page.

1. 창플 카페 posts — the naver corpus Scraped Naver cafe articles, owned by Django in the backend schema: documents_documentsource (one row per post, keyed by post_id, carrying title, author, board category, published_at, the body text, an LLM-written summary and keywords), plus documents_documentsourcestatus, documents_author, documents_board, documents_brand and documents_branch. Explainer #8 covers how a post gets scraped, enriched and judged; here it is simply there.
2. The agent’s index over that corpus In the agent schema, written by the indexing pipeline of explainer #9: document_index_artifacts (post_id primary key, one summary_embedding vector, one keyword_terms text[]) and document_chunk_artifacts (per-chunk halfvec(3072) embeddings with an HNSW index). These are derived data: delete them and the posts survive, but nothing is findable.
3. 미라클 콘텐츠 — the published-content corpus backend.content_notioncontent: first-party guides the operator writes and publishes (explainer #12), with their own chunk index agent.content_chunk_artifacts. A different row spine entirely: no post_id, no author, no Naver URL. A content citation links to /content/<id>, not to a cafe post.
4. The session’s own citation ledger Not a corpus but a set of ids the current conversation has already cited (#6). It has its own retrieval arm, because “아까 그 자료 다시” must not depend on the search finding the same post twice.

Two corpora with two id spaces is the single most consequential design fact in this package. A content_id that leaks into a post_id-keyed structure is not a type error — it is a citation pointing at the wrong document, rendered confidently to a paying user. You will see the code go to unusual lengths to make that impossible.

Intuition

Two ways to find a post, and why you want both

Suppose the archive holds 6,900 posts and the question is 치킨집 창업 비용. There are two honest ways to find the relevant ones, and each fails in a way the other does not.

Keyword matching asks: which posts carry these words? It is exact, cheap and explainable — and it is blind to vocabulary. A post that says 프랜차이즈 가맹비 and 인테리어 견적 never mentions 비용, so it does not match, even though it is precisely the answer.

Vector matching asks: which posts mean something close to this? Every post is turned once, at index time, into a list of 3,072 numbers — an embedding — positioned so that texts about similar things land near each other. The question is embedded the same way at query time, and the database returns the nearest posts by cosine distance (0 = same direction, 1 = unrelated, 2 = opposite). Vocabulary stops mattering. What breaks instead is precision on rare literal tokens: ask for a specific brand name or a specific 지점 and semantic nearness will happily hand you the whole genre.

Running both and merging is called hybrid retrieval, and it is what build_hybrid_candidate_result does. The merge is deliberately rank-based rather than score-based: a keyword hit-count and a cosine distance are not comparable numbers, but “#1 in its own arm” and “#3 in its own arm” are. Then, because a rank-merged list is still only a guess about relevance, a small fast language model reads the top sixteen and reorders them.

The funnel: recall first, precision last

The numbers matter as much as the boxes. Each stage is cheap where the set is wide and expensive where it is narrow — which is the whole trick of a retrieval pipeline.

What the model is allowed to see: one boolean and one join

Not every post in the archive may be cited. A post whose author left the cafe, whose board is 출석체크, whose text was never enriched, or which the operator excluded by hand, must not surface. That judgement is genuinely complicated — a dozen reason codes, an operator-editable rank policy, a date floor (explainer #8) — and the crucial design decision is that retrieval does not make it. The backend evaluates everything and writes the answer into one materialized column, documents_documentsource.reference_eligible. Every retrieval statement then reads a single boolean: ds.reference_eligible = TRUE.

There is exactly one exception, and its reason is instructive. The operator can switch a brand (or one 지점 of it) out of retrieval, and that switch has to be instantly reversible — flip it back and the posts return on the next query, with no sweep and no re-index. A materialized column cannot do that, so the brand policy stays a live LEFT JOIN plus a predicate, spliced into every retrieval statement at query time. Two mechanisms, chosen by how fast a change must take effect:

Everything elseBrand / branch toggle
Where it is decidedBackend eligibility engine (#8)The retrieval SQL itself
How retrieval reads itds.reference_eligible = TRUELEFT JOIN + reference_enabled
Cost of a changeA sweep, sometimes a re-indexZero — next query
Effect on the indexMay stop being indexedNever de-indexed; hidden only

Why a cache, and why five minutes

One uncached tool call costs up to three remote embedding calls, three or four SQL round trips and one language-model rerank — on the critical path of a streaming answer the user is watching. Yet the inputs are all corpus-global: the same normalized question, at the same widths, under the same models and the same brand policy, must give every user the same result. So the entire ranked result is stored in Redis db/2 under a hash of exactly those inputs, for 300 seconds. The corpus changes roughly daily; a five-minute window is invisible. Nothing user-specific ever enters that key — which is precisely why the by-id “cited” arm, whose input is session state, is kept out of that namespace entirely.

2. Query planning

query_planning.py is 166 lines of pure text handling — no I/O, no model, no database. It turns one string into a RetrievalQueryPlan:

@dataclass(frozen=True, slots=True)
class RetrievalQueryPlan:
    raw_query: str          # exactly what the caller passed
    normalized_query: str   # whitespace collapsed, trimmed
    lexical_terms: tuple[str, ...]    # deduped casefolded tokens
    lexical_phrases: tuple[str, ...]  # full query, then 3-grams, then 2-grams (max 10)
    query_variants: tuple[str, ...]   # what actually gets embedded (max 3)

Four steps: collapse whitespace and reject a blank query; split on spaces, strip surrounding punctuation (Unicode category P*) from each token and casefold it; build phrases as the normalized query followed by every 3-token then 2-token window, stopping at _MAX_LEXICAL_PHRASES = 10; and build variants as the normalized query plus the shorter phrases, stopping at _MAX_QUERY_VARIANTS = 3. Run on the toy query, that is:

The variants are the recall lever on the vector arm: rather than embedding one long question, the pipeline embeds the whole thing and its two most informative sub-phrases, runs a separate nearest-neighbour query for each, and keeps each post’s best distance. A post that is only “about 창업 비용” and says nothing about 치킨집 can still enter the pool through variant 3.

A real limitation, visible in the plan Tokenization is whitespace-plus-punctuation only — it does not strip Korean particles. Ask “치킨집 창업 비용은 얼마인가요?” and lexical_terms becomes ("치킨집", "창업", "비용은", "얼마인가요"): the term 비용은 will never equal the indexed keyword 비용, so that token contributes nothing to the lexical arm. The vector arm is unaffected (it reads meaning, not tokens), and the phrase windows still produce useful variants, so the failure is a quiet loss of lexical precision rather than an empty result. Note the contrast with apps/agent/app/chat/_author_query.py, which does carry a _KOREAN_NAME_SUFFIXES stripper — because for a person’s name, getting “창수님” to match “창수” is the whole job.

The four gates, restated in every statement

Five statements in this package (three query-driven builders plus two in author_posts.py) carry the identical WHERE spine:

INNER JOIN {DOCUMENT_SOURCE_STATUS_TABLE} AS dss
    ON dss.post_id = ds.post_id AND dss.status = %s      -- 'SAVED'
{brand_policy_join}
WHERE ds.ingested = TRUE
    AND ds.reference_eligible = TRUE
    {brand_policy_clause}
    {author_filter_clause}

Restating it is not duplication-by-accident; the module comment explains why. The chunk table agent.document_chunk_artifacts has no eligibility, date or brand column of its own, so any gate omitted from the chunk statement would make the chunk index a bypass around it — a brand-disabled post’s chunks surfacing where its summary vector cannot. Four gates, four different owners:

  • dss.status = 'SAVED' — the scrape landed and was stored (indexing state).
  • ds.ingested = TRUE — the row has been handed to the indexer (indexing state).
  • ds.reference_eligible = TRUE — the eligibility predicate, materialized by the backend engine. Since P53.S4 it also absorbs what used to be an AllowedAuthor inner join and a per-query retrieval-policy CTE with the operator’s date floor. Retrieval reads one boolean and re-derives nothing.
  • the brand policy — live, below.

The brand policy: SQL as a shared definition

brand_policy.py exports the filter as two strings and a fingerprint:

BRAND_POLICY_JOIN_SQL = (
    "LEFT JOIN backend.documents_brand AS bp_brand  ON bp_brand.id  = ds.brand_id\n"
    "LEFT JOIN backend.documents_branch AS bp_branch ON bp_branch.id = ds.branch_id"
)
BRAND_POLICY_PREDICATE_SQL = (
    "(ds.brand_id IS NULL OR bp_brand.reference_enabled)"
    " AND (ds.branch_id IS NULL OR bp_branch.reference_enabled)"
)

def build_brand_policy_sql(enforce: bool) -> tuple[str, str]:
    if not enforce:
        return ("", "")          # byte-identical to the pre-P53.S8 statement
    return (BRAND_POLICY_JOIN_SQL, f"AND {BRAND_POLICY_PREDICATE_SQL}")

Three details repay attention. The joins are LEFT and the predicate short-circuits on NULL, so unclassified is retrievable by default — an unclassified post can never silently vanish because nobody has labelled it yet. The fragment is parameter-free on purpose: the lexical builder’s positional parameter list is order-sensitive around a conditional author clause, and a predicate carrying a bound value would have to be spliced at exactly the right index. And BRAND_POLICY_PREDICATE_SQL is a plain literal with the aliases inlined rather than an f-string, because a backend test lifts that exact string out of this file with ast and executes it against real Postgres rows — which is how the two apps’ twin definitions get an execution-level proof instead of a shape assertion.

The Django side keeps a matching, deliberately observational reason code. From apps/backend/documents/eligibility.py:

#: Brand/branch reference toggle is off. **Retrieval-side only** -- never indexed
#: away, so a toggle flip is instantly reversible.
BRAND_FILTERED: Final = "brand_filtered"

#: Codes that gate retrieval only and must never gate enrichment or indexing.
RETRIEVAL_ONLY_REASON_CODES: Final[frozenset[str]] = frozenset({BRAND_FILTERED})

Nothing in the agent reads that code — it exists for the operator’s “why is this post not retrievable?” readout — which is exactly why an un-swept row is never wrongly filtered. Contrast MANUAL_EXCLUDED in the same file: the operator excluding one post by hand flips reference_eligible itself, needs no agent-side predicate, and is sticky.

The lexical arm is not full-text search

This is the most commonly mis-assumed part of the pipeline, so read the statement rather than the name. There is no tsvector, no ILIKE, no trigram index. The lexical arm is a set-overlap query against an array column:

WITH retrieval_inputs AS (
    SELECT %s::text[] AS lexical_terms,
           %s::text[] AS lexical_phrases,
           %s::text[] AS lexical_matches
)
SELECT ds.post_id, ds.title, ..., matched.matched_terms, matched.matched_phrases
FROM agent.document_index_artifacts AS dia
CROSS JOIN retrieval_inputs AS inputs
INNER JOIN backend.documents_documentsource AS ds ON ds.post_id = dia.post_id
INNER JOIN backend.documents_documentsourcestatus AS dss
        ON dss.post_id = ds.post_id AND dss.status = %s
{brand_policy_join}
CROSS JOIN LATERAL (
    SELECT ARRAY(SELECT term   FROM unnest(inputs.lexical_terms)   AS term
                 WHERE term   = ANY(dia.keyword_terms)) AS matched_terms,
           ARRAY(SELECT phrase FROM unnest(inputs.lexical_phrases) AS phrase
                 WHERE phrase = ANY(dia.keyword_terms)) AS matched_phrases
) AS matched
WHERE ds.ingested = TRUE
  AND ds.reference_eligible = TRUE
  {brand_policy_clause}
  {author_filter_clause}
  AND dia.keyword_terms && inputs.lexical_matches
  AND (cardinality(matched.matched_terms) > 0
       OR cardinality(matched.matched_phrases) > 0)
ORDER BY (cardinality(matched.matched_phrases) * 3
          + cardinality(matched.matched_terms)) DESC,
         cardinality(matched.matched_phrases) DESC,
         cardinality(matched.matched_terms) DESC,
         ds.published_at DESC NULLS LAST,
         ds.post_id DESC
LIMIT %s

The corpus side of the comparison is dia.keyword_terms, a text[] written at index time by the enrichment model — the handful of terms an LLM decided this post is about (explainer #9). Both sides are normalized identically (normalize_keyword_terms in indexing/storage.py collapses whitespace, casefolds and dedupes; the query planner does the same to the query), so && and = ANY(...) are exact string equality over two small sets. The && overlap in the WHERE is the fast pre-filter; the LATERAL block recomputes which terms and phrases matched so the result can carry them, and the score is:

lexical_score = (phrase_hit_count * 3) + term_hit_count

— computed twice, identically: once in SQL for the ORDER BY, once in Python in _lexical_candidate_from_row for the reported field. Phrases are weighted 3× because a matching two- or three-word phrase is far stronger evidence than the same words scattered. And note what this design buys and costs: it is exact, explainable and index-cheap, and it can only ever find posts whose summarizer chose the same words the user did.

The vector arm, per variant

SELECT ds.post_id, ..., (dia.summary_embedding <=> %s::vector) AS distance
FROM agent.document_index_artifacts AS dia
INNER JOIN backend.documents_documentsource AS ds ON ds.post_id = dia.post_id
INNER JOIN backend.documents_documentsourcestatus AS dss
        ON dss.post_id = ds.post_id AND dss.status = %s
{brand_policy_join}
WHERE ds.ingested = TRUE AND ds.reference_eligible = TRUE
  {brand_policy_clause} {author_filter_clause}
ORDER BY distance ASC, ds.published_at DESC NULLS LAST, ds.post_id DESC
LIMIT %s                                  -- per_variant_limit = 12

<=> is pgvector’s cosine distance operator. The statement runs once per query variant (so at most three times), each with its own embedding and its own LIMIT 12; results are merged in Python by post_id, keeping the minimum distance and unioning the variants that found it (_merge_query_variants), then sorted by _vector_sort_key — distance, then recency, then id descending, a total order so ties are deterministic — and truncated to 32.

Two column types, one embedding The summary column is a dimension-less vector (indexing/storage.py:136) with no ANN index at all — on a corpus of a few thousand rows an exact scan per variant is fine, and the width assertion is client-side because there is no schema constraint to lean on. The two chunk tables are halfvec(3072) with an HNSW index built as USING hnsw (embedding halfvec_cosine_ops), which is why the chunk statements must cast the bind explicitly to %s::halfvec(3072) — a mismatched cast silently loses the index. Both index sides and the query are embedded with the same model, so an extra arm costs an extra ANN query, never an extra embedding call.

Embedding the variants: one client, one request per text

embeddings.py is small and strict. GeminiQueryEmbeddingClient.from_settings resolves settings.gemini_embedding_model, whose default is the GA gemini-embedding-2 at 3,072 dimensions; the request timeout is delivered through request_options because GoogleGenerativeAIEmbeddings accepts no timeout kwarg, and retries are owned by the shared call_with_retry. Every failure becomes one type, RetrievalEmbeddingError.

The architecture record (docs/current/architecture.md, §“One embedding posture across all four clients”) explains why every embedding client in the repo now issues exactly one provider request per text: a multi-text embed_documents call on these models returns one embedding regardless of how many texts were sent, which silently broke a full-corpus indexing pass. The same record carries the warning that matters most for retrieval: a model switch is a silent degradation, not an error. gemini-embedding-2-preview and gemini-embedding-2 are distinct vector spaces of the same width, so <=> compares them without complaint and simply returns worse neighbours. The only component that notices is the ranked cache, because the model id is in its key.

The fan-out in build_hybrid_candidate_result is worth reading for its comment as much as its code:

with ThreadPoolExecutor(max_workers=len(query_variants)) as executor:
    embedding_futures = [
        executor.submit(_embed_query_variant, cache=cache, client=...,
                        variant=query_variant, model=embedding_model)
        for query_variant in query_variants
    ]
    lexical_candidates = store.list_lexical_candidates(...)   # on THIS thread
    variant_embeddings = [future.result() for future in embedding_futures]

The remote embedding calls run on worker threads while the lexical SQL runs on the connection-owning thread, so the two independent latencies overlap and the single psycopg connection is never touched concurrently. The ordering is deliberate and documented: submitting the embeddings, then running lexical before reading any future, keeps a lexical database error ahead of any embedding error; reading futures in index order keeps the first variant’s error first — exactly matching the serial loop this replaced. Behaviour preservation down to which exception surfaces.

Each worker runs _embed_query_variant, which is the embedding cache in three lines: look in db/2 under (variant text, model), embed on a miss, back-fill. A miss that raises still raises at future.result() in index order, so the cache is invisible to error handling.

The chunk arm and the content arm

Two optional arms hang off the same connection and the same variant embeddings.

The chunk arm (list_chunk_vector_candidates) queries per-chunk embeddings instead of one whole-post summary vector, so a long post that only mentions the topic in one section can still be found. It returns chunk-level rows; collapse_chunk_hits_to_posts turns them back into documents — one candidate per post, distance = the minimum over its matched chunks, carrying the best CHUNK_EVIDENCE_LIMIT = 2 chunks as evidence. Then _fuse_chunk_arm merges it into the summary arm, and the SUPPLEMENT semantics are strictly append-only: a post the summary arm already found keeps its own distance, its own variants and its own position and gains only the chunk evidence; a post only the chunk arm found is appended after every summary hit. That is what makes “post-level recall is a strict superset of the OFF behaviour” a property of the code rather than a hope.

The content arm (list_content_chunk_candidates) is a fourth builder, not a fourth mode, because it queries a different corpus: it joins backend.content_notioncontent and its gate is only _READABLE_CONTENT_SQL. The naver gates have no content-side analogue — these are first-party guides, not scraped posts by ranked members. And the gate is restated in the arm for the same structural reason as everywhere else: the chunk table carries none of its own, and the index lags while the query does not. Unpublish a content with the Celery worker stopped and it leaves retrieval instantly, while its chunk rows survive until the queued de-index task runs. author_name is deliberately not even a parameter here (a published content has no author column).

What the content arm must never do is enter the naver channel, and the code says so at the call site:

# P41.S8: ... What it deliberately does NOT do is touch `vector_candidates`:
# these are content ids, and everything downstream of this function -- fusion,
# the recency boost, the reranker, `retrieved_documents_by_post_id`,
# `hydrate_document_bodies`, the citation markers -- is keyed on `post_id`.
# A content id in any of them is a citation pointing at the wrong document.

So content_candidates is a separate field on the result, ordered by raw distance, bypassing fusion, the recency boost and the reranker entirely — not because those would be bad for contents, but because every one of them speaks post_id, and making them work would mean giving a content a post_id. collapse_content_matches is mechanically the mirror of the chunk collapse (best chunk wins, variants merged, up to CONTENT_CHUNK_EVIDENCE_LIMIT = 2 spans as evidence).

4. Fusion, the recency boost, and the reranker

Fusion is reciprocal-rank fusion with k = 0

Read build_fused_retrieval_candidates (ranking.py:304) with _rank_score (:220) and the arithmetic is three lines:

def _rank_score(rank: int | None) -> float:
    if rank is None:
        return 0.0
    return 1.0 / rank

# lexical pass, ranks 1..N:
fused_by_post_id[post_id] = FusedRetrievalCandidate(..., fusion_score=_rank_score(lexical_rank))

# vector pass, ranks 1..M -- a post already seen ADDS its vector contribution:
fusion_score=existing_candidate.fusion_score + _rank_score(vector_rank)

This is reciprocal-rank fusion: score a document by the sum of the reciprocals of its ranks in each arm. The textbook form is 1/(k + rank) with k = 60 to damp the top; here k = 0, so the head is much steeper — rank 1 is worth 1.0, rank 2 is worth 0.5, rank 5 is worth 0.2, rank 32 is worth 0.031. Being first in one arm outranks being third in both (1.0 vs 0.667). Say what the code does, not what the name suggests: this is RRF with an unusually aggressive top weighting, which is defensible when a second-stage reranker is going to re-read the head anyway.

Only the naver arms are fused, and the fusion key is post_id, so a post found by both arms appears exactly once with both ranks recorded.

The recency boost

RECENCY_BOOST_MAX = 0.2
RECENCY_BOOST_HALF_LIFE_DAYS = 30.0

def _calculate_recency_boost(published_at, *, newest_published_at) -> float:
    if published_at is None or newest_published_at is None:
        return 0.0
    age_days = max(0.0, (newest_published_at - published_at).total_seconds()) / 86_400.0
    recency_score = 1.0 / (1.0 + (age_days / RECENCY_BOOST_HALF_LIFE_DAYS))
    return RECENCY_BOOST_MAX * recency_score

_apply_recency_boosts takes the newest published_at in this pool (not “now”) as the zero point, so the boost is relative to the freshest thing the query actually found, and sets ranking_score = fusion_score + recency_boost. Despite the name, “half-life 30 days” is a hyperbolic decay, not an exponential one:

365 d0.0152rank 66 — i.e. nothing

So the boost is a tie-breaker at the tail and a mild nudge in the middle; it can never lift a weak match past a strong one. A missing rank sorts as _MISSING_RANK_SORT_VALUE = 1_000_000.

The reranker: a small model that only reorders

build_reranked_retrieval_candidates takes the top rerank_limit = 16 fused candidates, renders each as a plain text block (format_rerank_candidate_block: post_id, title, category, author, both date fields, summary, keyword_terms — never the body), and asks Gemini for an ordering. The prompt (prompts.py:348) is Korean and short:

당신은 검색 후보 문서를 질문 관련성 기준으로 다시 정렬하는 어시스턴트입니다.
...
규칙:
- 제공된 후보 문서만 사용하세요.
- 가장 관련성 높은 문서부터 낮은 문서 순서로 정렬하세요.
- 질문 관련성이 비슷한 후보끼리는 `published_at`이 더 최신인 문서를 조금 더 우선하세요.
- 최신이라는 이유만으로 질문 관련성이 낮은 문서를 관련성 높은 문서보다 앞세우지 마세요.
- 반드시 후보 문서의 `post_id`만 반환하세요.
- 중복 `post_id`는 반환하지 마세요.
- 질문에 거의 관련이 없는 후보는 생략해도 됩니다.

The output is constrained by structured output — _GeminiRetrievalRerankSchema, a single post_ids: list[int] field — so the response is a list of integers, not prose to be parsed. The model is live-configurable exactly like every other role (#2): resolve_role_model(role=ROLE_RETRIEVAL_RERANK, settings_attr="gemini_retrieval_rerank_model", default="gemini-3.1-flash-lite") plus resolve_role_thinking_level(...), with temperature=0.0 and native retries off (max_retries=1) so the shared call_with_retry owns 429 handling.

Because a language model can drop, duplicate or invent ids, its answer is merged, never trusted:

def _merge_reranked_post_ids(reranked_post_ids, *, candidate_pool):
    allowed_post_ids = {c.metadata.post_id for c in candidate_pool}
    ordered_post_ids = []
    for post_id in reranked_post_ids:                  # 1. model order first
        if isinstance(post_id, bool) or not isinstance(post_id, int):
            continue                                   #    non-ints dropped
        if post_id in seen_post_ids or post_id not in allowed_post_ids:
            continue                                   #    dupes + inventions dropped
        ordered_post_ids.append(post_id)
    if not ordered_post_ids:
        raise RetrievalRerankError("Retrieval reranking returned no valid candidate ids.")
    for candidate in candidate_pool:                   # 2. everything it dropped,
        if candidate.metadata.post_id not in seen_post_ids:
            ordered_post_ids.append(candidate.metadata.post_id)   # in fusion order
    return tuple(ordered_post_ids)

So an invented id vanishes, a duplicate is kept once at its first position, and a candidate the model omitted is appended in fusion order rather than lost — the pool is invariant, only its order is the model’s. Two shortcuts sit above this: an empty pool returns () and a single candidate is returned as rank 1 without any model call at all.

Failure mode — no fallback to fused order Everything that can go wrong in this stage becomes one exception, RetrievalRerankError: the reranker failing to initialize, the API call raising, malformed structured output, or a response containing no valid ids at all. There is no internal fallback to fusion order. build_ranked_retrieval_result does not catch it, so the error propagates to the caller, and each caller degrades in its own way: the public HTTP routes answer 503 “Retrieval is temporarily unavailable”; the chat tool returns status: "unavailable" and — per #5 — burns the whole remaining search budget (retrieval_call_count: MAX_CHAT_RETRIEVAL_CALLS - current_count), so a reranker outage costs the turn all four searches, not one. Worse, because the published-content channel rides on the same result object, an empty rerank response takes the contents with it even when the content arm had the right answer and the naver arms legitimately had nothing. The backend record carries two candidate fixes (treat an empty rerank as “no reordering” and fall back to fusion order; or catch it inside the chokepoint when the content mode is on) and notes that choosing one is an operator decision, because it changes naver-side behaviour.

The stage’s output is RankedRetrievalResult, which deliberately keeps every intermediate list — query_plan, lexical_candidates, vector_candidates, fused_candidates, reranked_candidates, content_candidates, plus an observational cache_hit flag. That is what makes the operator explain endpoint possible without a second run.

5. The cache on Redis db/2

cache.py holds two layers, both keyed only on corpus-global public inputs and never on user data:

RETRIEVAL_CACHE_DB         = 2
RETRIEVAL_CACHE_KEY_PREFIX = "agent:cache:"
_RANKED_KEY_PREFIX         = "agent:cache:retrieval:"
_EMBEDDING_KEY_PREFIX      = "agent:cache:embedding:"
_RANKED_SCHEMA_VERSION     = 3
_DEFAULT_TTL_SECONDS       = 300

The ranked key is a SHA-256 over thirteen components joined by \x1f, and the list is worth memorising because it is the answer to “why did I not get a fresh result?”:

  1. normalized_query — not the raw query, so two callers whose questions differ only in whitespace share an entry;
  2. author_name (or empty);
  3. the four widths: lexical_limit, vector_limit, vector_per_variant_limit, rerank_limit;
  4. embedding_model — env-pinned, never operator-editable;
  5. rerank_model — the resolved one, so an operator model change invalidates the cache for free instead of silently serving results ranked by the old model;
  6. brand_policy_fingerprint;
  7. chunk_mode + chunk_limit, content_mode + content_limit.

The last two pairs are required keyword-only arguments of build_ranked_key, so a caller who forgets one gets a TypeError rather than a silent cross-mode collision, and resolve_chunk_limit/resolve_content_limit zero the width whenever the mode is OFF so a stray limit cannot fragment the key. _RANKED_SCHEMA_VERSION went 2 → 3 when the blob gained the content channel: a v2 blob decoded under v3 would be a result with no contents, so stale blobs simply read as a miss.

The brand fingerprint (resolve_brand_policy_fingerprint) deserves its own note. The predicate is applied at query time, so without the toggle state in the key a flip would be invisible for the whole TTL. But reading the toggle tables per query would add a round trip to the hot path, so the module keeps a process-wide snapshot on the same 30-second TTL as the other live-config readers (#2), digests only the disabled ids (sha256("brands:12,19|branches:7")[:16] — the common case is “none disabled”, a stable digest of an empty list), and fails open to the last known value or the literal sentinel "unknown". A flip changes the fingerprint, old entries go cold, nothing is invalidated by hand.

Two guards decide whether the cache is consulted at all:

cache = (
    resolve_retrieval_cache(current_settings)
    if query_embedding_client is None and reranker is None
    else None
)

An injected embedding client or reranker disables it, because a hit could return a result the caller-supplied model would have computed differently (this pairing occurs only in tests). And resolve_retrieval_cache gates on settings.retrieval_cache_enabled with a getattr default of False, so offline unit tests with a SimpleNamespace settings object never reach for a real Redis client.

Every Redis operation is wrapped: on RedisError, a read is a miss and a write is a no-op. Redis being down never breaks retrieval — it only un-caches it. On a hit the stored blob is restored and only raw_query is patched back (it is the one field that legitimately differs between callers sharing a normalized query), then cache_hit=True is stamped — deliberately not serialized into the blob, since a stored result is by definition a build-path result.

The cache singleton is built lazily (get_retrieval_cache) because the retrieval pipeline runs in synchronous worker threads with no access to app.state, and it is closed in main.py’s lifespan via aclose_retrieval_cache() — third in the shutdown order of explainer #1. Note it is a synchronous redis.Redis, matching the synchronous pipeline, unlike the async registries.

6. After ranking: selection, hydration, consumption

Notice what the pipeline has not done so far: it has never read a post’s body. Every stage — lexical, vector, fusion, rerank — works from title, author, dates, summary and keyword terms. Bodies arrive last, in document_bodies.py:

_BODY_FIELDS = ("text_with_image_replacement", "content", "raw_text")

SELECT post_id, text_with_image_replacement, content, raw_text
FROM backend.documents_documentsource
WHERE post_id = ANY(%s)

— first non-blank field wins, a post with no usable text is logged and dropped, and hydrate_document_bodies wraps the whole thing so a hydration failure degrades to “no bodies” rather than failing the turn. The ordering is a real cost decision: hydrating 32 candidates would mean pulling tens of thousands of characters out of Postgres to throw away 26 of them. The chat tool hydrates after selection, so a default turn reads six bodies:

documents = [_serialize_retrieved_document(candidate)
             for candidate in _select_prefer_uncited(
                 retrieval_result.reranked_candidates,
                 limit=max_tool_results, ...)]        # <= 6
...
contents_by_post_id = _hydrate_chat_document_contents(
    settings=runtime.context.settings,
    post_ids=[document["post_id"] for document in documents],
)

It is also a security ordering, and cited_search.py states the rule outright: gate, then hydrate. hydrate_document_bodies applies no predicate of its own — it is a plain post_id = ANY(...) body read — so hydrating first and filtering afterwards would mean reading bodies the caller may not see.

The per-call width is not a constant: resolve_chat_max_tool_results(settings) is read once per call from the operator singleton (#2), clamped to [1, 16], defaulting to 6. The ceiling of 16 is not arbitrary — it is DEFAULT_RERANK_CANDIDATE_LIMIT, the pool the slice is taken from, so a larger cap could not add a document.

operator_metadata.py is the one other post-ranking read: a post-hoc lookup of board label, brand and branch for the ids the pipeline already returned, run only for the operator bench. It is a separate statement rather than extra SELECT columns for two stated reasons — the brand joins are emitted only when the policy is enforced, and the bench’s comparison mode runs with the policy off; and nothing on the shared hot path changes, so a bug here can only affect the console. It re-uses BRAND_POLICY_JOIN_SQL verbatim rather than writing a second definition, and falls back to the scrape-time ds.category when a post has no linked board row.

7. The three sibling arms

Three more entry points exist beside the chokepoint. All three follow one packaging convention — own module, own frozen result dataclass, own error type, direct HybridCandidateStore calls inside one connect_agent_db scope — rather than becoming another mode on build_ranked_retrieval_result.

Content-only search — content_search.py

Backs the search_changple_contents tool. It runs exactly four steps — plan, embed per variant, list_content_chunk_candidates, collapse_content_matches — and deliberately does not run the lexical arm, the summary-vector arm, the naver chunk arm, fusion, the reranker, the brand policy, any author scope, or the ranked cache. Each of those absences is pinned by an executed-SQL or never-constructed test assertion, because “it happens not to call the reranker today” is exactly the property that decays. Its default width is DEFAULT_CONTENT_SEARCH_RESULT_LIMIT = 5, deliberately wider than the MAX_CHAT_CONTENT_RESULTS = 3 supplement: the supplement rides along uninvited on a naver search, while a call here means the caller asked for contents and nothing else. No result cache, for a reasoned rather than lazy reason: the ranked cache’s advertised saving is mostly the rerank call, which this path never makes — and the embeddings it does make are still db/2 hits, sharing keys with the naver path.

Author posts — author_posts.py + chat/_author_query.py

“창수님이 배달앱에 대해 뭐라고 썼나요?” needs two things the main path cannot do: resolve a fuzzy human name to a real author, and combine relevant with recent.

Resolution starts from the roster: list_active_authors returns every documents_author nickname owning at least one indexed, reference-eligible, brand-permitted document. Deriving the roster from the materialized flag rather than a separate allowlist means the rank vocabulary lives in one place, on the backend — and including the brand policy is load-bearing rather than cosmetic: without it the picker would offer an author every one of whose posts is brand-filtered, and the recent-posts query would then return nothing for them. Then resolve_author tries three strategies in order, on whitespace-stripped casefolded text: exact match; containment (either direction) resolved by _select_unique_containing_author, which picks the candidate whose length is closest to the query and returns None on a tie rather than guessing; and finally _select_confident_fuzzy_author, a difflib.SequenceMatcher ratio that must reach DEFAULT_AUTHOR_FUZZY_MATCH_THRESHOLD = 0.88 and strictly beat the runner-up. Ambiguity resolves to “no author”, never to a wrong one.

Query building is _build_author_related_retrieval_query: the author query plus the topic, plus — only when their Korean person-terms actually overlap — the user’s current message and up to MAX_CHAT_AUTHOR_RELATED_HISTORY_MESSAGES = 2 earlier user turns that mention the same person, deduped and truncated to MAX_CHAT_AUTHOR_RELATED_QUERY_CHARS = 480. That is what lets a follow-up like “그분 다른 글은?” still carry the topic from two turns ago. Its tokenizer strips the Korean particle suffixes listed in _KOREAN_NAME_SUFFIXES (은/는/이/가/님/께서/에게…) and drops role words like 대표/팀장 as stop terms.

The result is build_author_post_retrieval_result: on one connection, resolve the author and fetch their most recent eligible posts; then, if a topic was given, call the chokepoint with author_name= so the full hybrid pipeline runs scoped to that author; then _merge_author_posts lays query-related posts first, recent posts second, deduping and stopping at the limit — and reports which ids came from which list, so the tool can tell the model “these are about your topic, these are just their latest”.

The cited arm — cited_search.py

Backs search_cited_documents, the “아까 그 자료” tool. Its candidate set is not the corpus but the session’s own citation ledger (#6), so it runs list_documents_by_post_ids / list_content_chunks_by_content_ids instead of the query-driven builders. The query is only an ordering signal, which is why it embeds one variant rather than three — and that variant is byte-identical to query_variants[0], so it shares the db/2 embedding key with the fresh arm and costs no round trip on a turn where both run.

Two properties make it more than a convenience. First, eligibility is re-checked, never assumed: list_documents_by_post_ids carries the same four gates as the query-driven builders, so a document retracted, de-ingested or brand-toggled off since it was cited simply does not come back — it lands in missing_post_ids, which the caller must read as “not available to cite this turn”, never as “deleted”. Second, it is budget-exempt, and #6 showed the exemption is structural: the tool returns a Command whose update simply omits retrieval_call_count. The justification is that re-fetching what the session already cited widens nothing — the candidate set is a subset of what earlier turns already paid for — so charging for it would only push the model toward re-searching the whole corpus instead.

The content-side by-id fetch has one structural difference worth stealing: its cap is per content, via ROW_NUMBER() OVER (PARTITION BY content_id ORDER BY distance), not a plain LIMIT. A by-id call promises “the ids you named, if they are still readable”, so one long content whose chunks own the top of the distance order must not push a different requested content out of the result.

The rate limiter — rate_limit.py

RetrievalRateLimiter is fixed-window counting on Redis db/0 (not the db/2 cache), with two windows — retrieval_integration_requests_per_minute = 120 and retrieval_integration_requests_per_hour = 2000. It applies to public integration traffic only: a caller authenticated by X-Agent-Api-Key. First-party user JWT traffic is exempt at the route layer, and the operator bench is exempt too (a single operator behind an admin gate, where a Retry-After banner would only mislead). The scope is a SHA-256 of the integration name, never the key value, so rotating the gpt-actions key keeps the same quota without putting a secret in a Redis key name. A RedisError during the check fails open.

Read it as a set of differences. If a post you expected is missing from every list, it failed a gate — check reference_eligible and the brand toggle, not the ranking. If it is in lexical_candidates but not vector_candidates, the wording matched but the meaning did not (or its summary embedding is stale). And if matched_terms is empty while matched_phrases is not, you are looking at a phrase hit worth 3 points.

The question this page promised to answer “Why did post N not show up?” has exactly six possible answers, in the order to check them: (1) it is not SAVED or not ingested — it never reached the index; (2) reference_eligible = FALSE — the backend engine judged it out (#8 has the reason codes); (3) its brand or branch is toggled off — live, reversible, invisible in the index; (4) it lost the lexical arm (its keyword_terms do not contain your words) and the vector arm (its summary embedding is not among the 12 nearest for any variant); (5) it made the pool but fell below rank 16 after fusion + recency, so the reranker never saw it; (6) it was reranked below the per-call width, which defaults to 6. Only (4)–(6) are ranking questions. The explain endpoint tells you which one you are in.

Quiz

Five questions on the read path. Click an option to check it.

1. At query time, which single thing decides whether a 창플 카페 post is eligible to be retrieved at all — and where is it computed?

P53.S4 folded the author join and the retrieval-policy date CTE into one column. Retrieval reads ds.reference_eligible = TRUE and re-derives nothing; eligibility_reasons is the operator’s readout, and the agent never reads it. The index-artifact join is required too, but it is indexing state, not eligibility.

2. Why does the ranked cache key include a 16-character hash of the disabled brand/branch ids?

The predicate stays live SQL — that is what makes a flip instantly reversible. The fingerprint exists purely so a flip changes the cache key: old entries go cold and nothing needs explicit invalidation. It is read once per 30 s TTL window, not per query, and fails open.

3. The Gemini reranker call raises. What does the pipeline do?

There is no internal fallback. Initialization failure, an API error, malformed structured output, and a response containing no valid ids all become one RetrievalRerankError that propagates. Because the content channel rides on the same result object, it is lost too — a recorded issue with two candidate fixes, unresolved because either changes naver-side behaviour.

4. Why are post bodies loaded only after ranking and selection?

Every ranking stage works from title, author, dates, summary and keyword terms; the rerank prompt block deliberately excludes the body. document_bodies.py is a plain post_id = ANY(...) read with no gates, which is why cited_search.py states the rule as “gate, then hydrate”.

5. A user asks “아까 그 자료 다시 보여줘” and the model calls search_cited_documents. Which statement about that arm is true?

The candidate set is the ledger’s ids, a subset of what earlier turns already paid for, so charging budget would only push the model toward re-searching the corpus. It deliberately stays out of the ranked cache (a session-scoped dimension would destroy the hit rate on the hottest path), embeds exactly one variant — the normalized query, sharing the db/2 embedding key with the fresh arm — and re-applies the four gates, so a document brand-toggled off since it was cited comes back in missing_post_ids.
