Background — from an approved plan to a published article

Explainer #13 left the 미라클 content agent (v2) parked at a state called needs_review. Everything before that point was about deciding what the article is going to be: which cafe posts count as evidence, which KakaoTalk conversations the operator chose, which photos the job may use, and finally a 구성안 — a section-by-section plan, each section carrying a pinned heading, a target length, its own evidence, and an explicit list of the photos and conversation captures allocated to it.

What is left is the second half of the job, and it is the half a reader of the finished article actually sees: write the prose, smooth it into one body, let the operator edit it, and ship it. That is four backend stages —

needs_review --approve_scaffold--> writing --units_done--> integrating
             --integration_done--> draft_ready
             --(begin_adjust)--> adjusting
             --publish--> publishing --publish_succeeded--> published

— plus two things that ride alongside them the whole way: the asset registry (which images exist, which may be used, and what their identity is) and the six-step strip (the one server-computed answer to "where is this job right now").

Jargon, defined once.

  • 구성안 (gu-seong-an) — the approved outline document: title, core message, an opening plan, numbered sections, a closing plan, and a per-unit media allocation.
  • Unit — one writable piece of the article: the 서두 (opening), each 절 (numbered section), and the 맺음 (closing). The build's denominator is units, not sections.
  • Marker — a placeholder the writer puts inline in its prose: {{img:<asset-uuid>}} for a photo, {{cap:<chat_rev>:<from>-<to>}} for a KakaoTalk conversation range. A marker is a position, not a picture.
  • Revision — an immutable row holding a whole 구성안 document. Approving writes a new one; nothing ever edits an old one.
  • Draft — an immutable row holding one integrated body. Every save appends the next draft; nothing ever rewrites one.

If you want the wider orientation before the code, docs/current/backend.md § "Content Agent v2" and its sub-sections "Writing, verification, chat, publishing, revisions", "The v3 machine — the simple job flow (P79)" and "The draft is rendered, saved and adjusted (P81)" are the fastest read. Everything below was verified against the code, and § Drift found while walking lists the three places where that documentation has fallen behind the source.

The one design commitment that makes this interesting

You could build this stage as "hand the LLM the outline and the evidence, ask for an article". This system deliberately does not. The organising rule of everything below is:

The approved plan is immutable input, and every stage downstream is forbidden from quietly changing it. Not "discouraged by the prompt" — forbidden by machine checks that fail the attempt. The heading sequence the operator approved comes back identically or the integration attempt is thrown away. The photos the operator allocated come back marker for marker or the return is repaired deterministically. A unit the machine could not write is removed from the build by an explicit operator answer, and the approved revision is still not touched.

That commitment is what turns a pile of LLM calls into something an operator can trust with a public article, and it is the transferable idea on this page. Everything else — the sequential loop, the asset registry, the derived section list, the single publish choke point — is a consequence of taking it seriously.

Intuition — the plan is frozen, everything downstream obeys it

The gate is a guard over data, not a button

The clearest small example of the system's whole posture sits right at the entrance to this page's territory. "Approving the 구성안" is two separate calls, not one:

  1. services.approve_scaffold_revision(job, …) writes an immutable revision row with kind=APPROVED, a content hash, a timestamp and the approver. That is the record.
  2. services.transition(job, "approve_scaffold") moves the job from needs_review to writing. That is the move, and it is gated on the record existing.

The state machine's edge does not ask "did someone click 승인?". It asks a guard function, and the guard reads the database: is there an approved revision, and does it record that the operator saw the change list? If either is false the transition refuses with a machine-readable blocker. Nothing about the operator's session, intent or click is trusted; only durable data is.

Why the build is a chain and not a fan-out

An article has six units. You have six independent LLM calls to make. The obvious engineering instinct is to run them in parallel — six calls at once, one sixth of the wall-clock time.

This build refuses to, and the reason is not caution. Each unit's prompt packet carries the summaries and continuity notes of every unit already written. Unit 4 is told, in the writer's own earlier words, what units 1–3 already said and what thread they left hanging. That is a genuine data dependency: unit 4's input does not exist until unit 3 has returned.

The reusable lesson. In an LLM pipeline, ask what each call's input depends on before you reach for concurrency. If call n is prompted with the output of call n−1, parallelising them does not make the pipeline faster — it makes it produce a different, worse artifact: six units that repeat each other, contradict each other, and hand off to nothing. Exactly one unit row is in writing at any moment, and that is on purpose.

A machine check standing behind a prompt instruction

After the units are written, one more LLM call — the integration pass — reads the whole assembled body and smooths the seams between units. Its instructions say, in Korean, that it may not add a single fact.

That instruction is worth exactly nothing on its own. A language model asked to "smooth transitions without adding facts" will, on some run, quietly delete a photo marker it found ugly, retitle a section, or invent a sentence of connective tissue containing a claim. So the system does not rely on the sentence. Immediately after the model returns, two deterministic post-checks run against the returned body:

  1. the sequence of ## NN. heading lines must be identical to the approved one, and
  2. the multiset of markers (img:… and cap:…, kind-qualified) must be identical to what went in.

Fail either and the attempt is thrown away and retried under the failure budget. The model is free to rewrite prose; it is structurally incapable of changing what the operator decided.

Measured, not asserted. I extracted check_integration and body_markers from build.py and ran them against a toy draft with two sections, a two-photo row and one conversation capture. Results:

markers extracted        -> ['img:aaaa-1111', 'img:bbbb-2222', 'cap:7:120-134']

integrator reorders the two photos on the line  -> PASSES
integrator drops one photo                      -> BuildError marker_multiset_changed
integrator adds a photo                         -> BuildError marker_multiset_changed
integrator retitles "02. 두 번째 절"              -> BuildError heading_sequence_mismatch
a removed unit's heading is still present       -> BuildError removed_unit_present

Note the first line: the marker check is a sorted multiset, not a sequence. It guarantees which markers survive, deliberately not their order — reflowing is the integrator's job, and reordering photos inside a row is legal.

1. The 승인 gate: two calls, one guard

The edge itself, from the table in states.py:

needs_review --approve_scaffold--> writing

The guard's implementation is nine lines at services.py:115:

def _guard_scaffold_revision_approved(job, context) -> list[str]:
    revision = job.approved_scaffold_revision
    if revision is None:
        return ["scaffold_revision_not_approved"]
    if not revision.change_list_seen:
        # Round 12 §3.6: the gate records that the operator saw the list.
        return ["change_list_not_seen"]

Two blockers, both facts about rows. The second one is the interesting one: re-approving a 구성안 after edits produces a change list ("these three sections will be rewritten, these two are kept"), and the gate refuses to move unless the row itself records that the operator was shown it. "The operator understood the consequences" is stored as data, not assumed from a request reaching the endpoint.

The record is written by services.approve_scaffold_revision (services.py:286) — a plain objects.create(...) of a new ContentAgentScaffoldRevision with kind=APPROVED, a canonical content hash, approved_at and approved_by. Its docstring is explicit: "Writes a new row; a predecessor is never mutated. The approval act is this row — the state move is a separate transition(job, "approve_scaffold") call, gated on it."

The caller that binds them is in scaffold.py:7123, inside one transaction:

승인 IS the freeze. Explainer #13 described freeze_input_revision — the immutable snapshot of the job's inputs — and noted that the intake stays editable right up until approval. This is the moment it stops. From here the 구성안 is history: the build reads it, the draft may diverge from it, and nothing writes back to it.

2. The build — build.py (2,564 lines)

This is the centre of gravity of the whole page, and its module docstring is unusually good. Rather than paraphrase it, here it is, condensed — and then each claim verified against the body of the module:

"""Content Agent v2 — the sequential unit build and the integration pass.

* **Strictly sequential.** Exactly one unit is in `writing` at any moment, and
  each unit's packet carries the *summaries* of every unit already written —
  that is the whole reason the build is sequential and not a fan-out.
* **The approved revision is immutable input.** Unit rows are derived from it;
  the `delete_unit` answer marks a **row** `removed` and never edits the revision.
* **D56 drives every failure** … `unit_retry` (a `writing` self-loop — the same
  unit re-runs in place) while budget remains and `unit_capped` → `needs_answer`.
* **No stop, no cancel.** … Recovery is re-entrancy instead: the task picks the
  first unit that is `queued` **or** `writing` (a crashed attempt).
* **Nothing is auto-rewritten for length.** A ±20% deviation is *reported*.
* **The integrator may not add facts.** … the deterministic post-checks enforce
  what a sentence cannot.
"""

The two models this page owns

Two storage rows, both created by migration 0029:

  • ContentAgentBuildUnit — one row per unit per approved revision, unique on (job, scaffold_revision, unit_id). Its state is queued · writing · done · failed · removed. It carries the pinned heading denormalized from the revision, the target length, the measured chars, the written body with markers inline, and a returns JSON blob holding the worker's structured answer.
  • ContentAgentDraft — append-only, one row per integration pass, unique on (job, number). It holds the integrated body, a units_map saying where each unit landed in it, an integration record, and (since P79.S5) an optional document: the draft's own allocation. None means "inherit the approved revision verbatim", which is why every draft written before that field existed still renders byte-identically.

Unit rows come from the revision, and re-approval is read verbatim

ensure_build_units(job, revision) (build.py:569) is idempotent — "existing rows are law" — and it reads the invalidation block that the approval stored inside the revision's payload:

# scaffold.compute_invalidation, computed per SECTION ID (never per number)
{"first_revision": False,
 "rewrite_ids": ["sec-b", "sec-e"],     # changed or added -> start `queued`
 "keep_ids":    ["sec-a", "sec-c"],     # untouched -> copy the previous
                                        #   build's body forward, state `done`
 "removed_ids": ["sec-d"],              # no row is created at all
 "summary": "다시 집필: 2단위 · 유지: 2단위"}

_carry_forward finds the newest done row for that unit_id from an earlier revision and copies its body, chars and returns onto the new row, stamping carried_from_revision. So editing one section of a six-section 구성안 and re-approving costs one LLM call, not six — and the fact that a unit was carried is recorded rather than re-derived later.

Why removed_ids needs no handling at all. A section the operator deleted from the 구성안 is simply not in the new document, so the loop that walks scaffold_service.units(document) never sees it and creates no row. Deletion needs no delete path. That is a small, repeatable design win: derive the set rather than diff it.

The packet — everything one call may read, and nothing else

build_unit_packet (build.py:1097) assembles a dict that is hashed (services.canonical_hash) and recorded with the attempt, so an attempt is reproducible after the fact. Its keys:

KeyWhat it carries

guide_rulesChapters 3, 5, 6, 7, 8, 13 of the frozen 가이드, sliced verbatim by the standard's own ## n. headings.
section_contractThe unit's pinned heading, body intent, decision, sub-headings, target length, transitions in/out and risks — straight from the approved section.
neighborsneighbor_summaries(rows): for every done unit, its summary (≤300 chars) and continuity_note (≤400). The sequential dependency.

The media block is worth reading closely, because P72.S11 changed the system's whole posture here. The docstring of _allocated_media says it plainly:

"P72.S11 replaced S8's job-wide candidate list with this: the writer is not choosing a photo any more, it is being told which ones this unit carries and in what order. An un-allocated unit carries nothing, so a marker cannot appear where the operator placed none."

The guide slice, measured. build.guide_rules() cuts the six chapters the writer's instruction set quotes. The sequential loop, and what happens when the worker dies

_write_units (build.py:2040) is eleven lines and worth quoting whole, because the comment inside it is the entire crash-recovery story:

while True:
    rows = list(unit_rows(job, revision))
    pending = [
        unit for unit in rows
        if unit.state in (
            ContentAgentBuildUnit.State.QUEUED,
            # A `writing` row means an earlier run crashed on it: re-run it
            # in place on its remaining budget rather than stranding it.
            ContentAgentBuildUnit.State.WRITING,
        )
    ]
    if not pending:
        return None
    outcome = _write_one_unit(job, pending[0], …, neighbors=neighbor_summaries(rows), …)
    if outcome is not None:
        return outcome

There is no cancel edge anywhere in the build — the state machine has exactly one Kind.CANCEL transition in the whole table, and it belongs to the proposal stage (proposing --cancel--> intake). So the build cannot answer "what if this dies halfway" with a rollback. It answers with re-entrancy: the selection predicate includes writing, so a Celery worker that was killed mid-unit leaves a row the next run picks up first. A done unit is never re-written; a half-written one is never stranded.

Two stages, two answers to the same question. Explainer #13's proposal turn does have a cancel edge, and it handles the race by re-checking _still_proposing(job) before every single write — a cancel means the writes must stop landing. The build has no cancel, so it instead makes re-entry safe and idempotent. Both are valid; what matters is that each stage picked one answer deliberately and the code says which. When you design a long-running job, decide up front whether it is interruptible or resumable — trying to be casually both is how half-written state escapes.

The build does still check for interruption, but for a different reason: _write_one_unit re-reads the job's state from the database at the top of each attempt (if _job_state(job) != JobState.WRITING: return {"status": "interrupted", …}), so a job that got capped out from under the loop stops cleanly instead of writing into a state that no longer expects it.

Failure: D56, in place, with a fresh budget per turn

The retry doctrine (internally "D56") is the same one explainer #13 described for the proposal turn, wired to different triggers. services.MAX_STAGE_ATTEMPTS = 2 counts attempts, and services.STAGE_FAILURE_TRIGGERS maps the job's current state to its (retry, capped) pair — for writing that is ("unit_retry", "unit_capped"). In the machine:

writing     --unit_retry-----> writing        system  failure   # self-loop: same unit, in place
writing     --unit_capped----> needs_answer   system  failure
needs_answer--resume_build---> writing        operator recover
integrating --stage_retry----> integrating    system  failure
integrating --stage_capped---> needs_answer   system  failure

At the cap the job parks in needs_answer and the operator is served round 12 §3.7's three options, defined as fixed design copy in build.py:257 (RESUME_OPTIONS):

actionlabelwhat it does to the data
retry근거를 다시 확인하고 이 단위만 다시 씁니다row → queued; neighbours untouched.
delete_unit이 단위를 빼고 계속합니다row → removed. The approved 구성안 is not touched — its own served detail says so: 「승인된 구성안은 그대로 남고…」
keep_empty사진 없이 다시 씁니다row → queued, and this write's packet drops the allocation (_allocated_media(..., keep_empty=True)). The 구성안's placement itself stays.

All three then take resume_build back into writing. And crucially, attempts are keyed (stage, unit_key) where _unit_key appends @turn, and build_turn(job) counts entries into writing from the append-only transition log. So the operator's answer gets a genuinely fresh budget instead of immediately re-hitting the exhausted counter — the docstring is blunt about why: "which would make round 12 §3.7's three options a lie the second time." Nothing is ever deleted; every attempt row survives as the audit trail.

One elegant consequence: when the integration stage caps, no unit is failed, so resume_build is a two-hop — it moves the job to writing, the task finds nothing queued, immediately takes units_done to integrating, and retries the integration. One code path serves both caps.

Length is reported, never fixed

normalize_unit_return computes, when the section has a target:

deviation = {"target": target, "chars": chars, "delta": chars - target,
             "ratio": round(delta / target, 4),
             "within_band": abs(ratio) <= LENGTH_TOLERANCE}   # LENGTH_TOLERANCE = 0.20

and stores it in the unit's returns.length_deviation. No second call is ever made to stretch or trim the prose. The reason is upstream: explainer #13 showed that a section's target_len comes from reference_shape's medians over the operator's chosen reference articles. A median is a shape hint, not a contract, and re-prompting a model to hit a character count reliably damages the prose to satisfy a number nobody promised. The module's comment quotes the design: "Target length is an instruction, not a contract (±20% reported, never auto-rewritten)."

Server-side repair: the return is normalized before it is believed

The writer returns a Pydantic-validated UnitWriteOut (body · quotes[] · continuity_note · summary · unresolved[]). Note what is not in it: an images field. P72.S11 deleted it. The writer no longer reports which photos it used, because the writer no longer chooses; the placement record is computed server-side from the allocation and the body.

normalize_unit_return (build.py:1549) then runs a fixed ladder of deterministic repairs, each of which appends a recorded warning:

  1. heading_rewritten — the heading is pinned, so a body that restates it loses the line (_strip_leading_heading).
  2. image_not_allowed — a {{img:}} key outside media.asset_ids is dropped, line-aware (a line left empty by the drop goes with it).
  3. image_marker_appended — an allocated photo the writer forgot is appended to the end of the unit rather than lost.
  4. the same two rules again for {{cap:}} conversation markers (capture_not_allowed / capture_marker_appended).
  5. marker_lines_repartitioned — _partition_marker_lines rebuilds the marker layout from the allocation's canonical row ordinals: a group's markers share one line (max 3), an ungrouped photo and every capture get their own line, and a marker written inline in a prose sentence is lifted onto its own line below it — because an inline marker publishes as nothing (the publish scrubber eats it), so lifting it is a repair, not a reformat.

The guarantee this buys, stated plainly: the integrated draft carries the operator's allocation, marker for marker, and the integrator may not touch one. Step 2 makes "only allocated photos" true; step 3 makes "all allocated photos" true; the integration post-check (next) makes "and it stays that way" true. Three mechanisms, one promise, none of them a sentence in a prompt.

The integration pass

_integrate (build.py:2079) assembles the pre-integration draft with assemble_draft_body — unit bodies in order, with ## NN. heading lines pinned in for sections only (the 맺음 has no heading, per guide §2.6) — records the expected heading list and marker multiset, and hands the body plus the section transitions to one LLM call. On return:

integrated = check_integration(
    answer.body,
    expected_headings=headings,        # from assemble_draft_body
    expected_markers=markers,          # body_markers(pre-integration body)
    removed_headings=removed_headings, # units the operator removed
)

and check_integration (build.py:1726) — docstring: "Enforce, don't trust. A failed check fails the attempt (D56)." — raises one of four coded BuildErrors: integration_empty, heading_sequence_mismatch, marker_multiset_changed, removed_unit_present. The measured behaviour is in the box back in Intuition.

A passing integration writes the draft row and takes integration_done in one transaction, and then the flow stops. There used to be a chained §11 audit here that produced a machine verdict on the draft; P79.S3 deleted it, and the comment records why: "round 19's draft is the operator's editing surface, not a machine's verdict."

Where the routes are

build_views.py (356 lines) ships two endpoints on the operator's admin segment:

GET  /api/content/admin/miracle-agent/v2/jobs/<uuid>/build
POST /api/content/admin/miracle-agent/v2/jobs/<uuid>/build/resume

with a convention that runs through this whole subsystem and is worth stealing: one response shape for every read and write, and a refused write answers 400 with that same body plus an error{code, detail, …}. The screen never needs an optimistic update or a refetch, because every answer is the whole screen. Everything numeric on it is measured, never estimated — elapsed from the row's timestamps, retries from the current turn's attempt rows — and the ETA is served as null with the label 측정 불가 ("cannot be measured"). The system does not invent a progress estimate.

3. The assets that the writing places

A marker is only useful if the key inside it resolves to real bytes with a caption. That is the asset registry's job, and it runs from intake all the way to publish.

assets.py (744) — one row per usable image, and one candidacy rule

ContentAgentAsset holds one row per image across three provenance families: upload (the operator's 추가 사진), chat_media (images extracted from the KakaoTalk .zip in #13), and corpus (images carried by the selected cafe posts). The single most load-bearing fact about it:

The asset's uuid primary key is the {{img:<key>}} key. Not a mapping, not a lookup table — the marker payload is the row's pk. v1's contract was "the attachment pk IS the marker key", and v2 kept exactly that shape (an opaque uuid) so that every existing parser keeps working and not one consumer site changes. The canonical grammar lives on the agent side at apps/agent/app/content_drafts/agent.py:133:

_IMG_MARKER_RE = re.compile(r"\{\{img:([^}]+)\}\}")

and build.py:135 keeps a byte-identical local copy with a comment saying so. Grepping {{img: across apps/ (tests excluded) finds it in 23 files across all three apps — the backend's dispatch, publish, scrub, extraction and mirror paths, the agent's drafting service, and the operator's Next.js console. That regex is the forward pointer into explainer #15.

The registry exists to fix a specific v1 failure. In v1, a corpus image with no generated_alt was silently dropped and got no key at all (apps/agent/app/content_drafts/images.py:191-195) — invisible and unrecoverable. Here it gets a row anyway, is listed, and becomes usable the moment the operator writes a caption. Two related rules from the docstring: original filenames are provenance and survive verbatim, forever (captured at the view boundary before file assignment, because Django's storage sanitizes the stored name), and the system never writes a caption — inspection_caption is the operator's field and is the only recovery path for an uncaptioned image.

Candidacy — "may this asset be placed?" — is exactly one function, evaluate_candidacy (assets.py:604), and every other module calls it rather than re-deriving. Three job-wide clauses first, then a per-family rule:

deleted_at is not None   -> not a candidate  (recoverable_by="restore")
excluded                 -> not a candidate
duplicate_of is not None -> not a candidate  (byte-sha256 equality, cross-family, no recovery:
                                              the kept copy already IS the recovery)

upload      : candidate iff it has bytes AND an inspection_caption
chat_media  : its conversation must be selected FIRST (deselect the conversation and its photos
              leave the candidate set through THIS rule and no other), then
              matched -> candidate (1.0) · ambiguous -> candidate carrying its 0.70 ·
              unreferenced -> candidate once captioned
corpus      : a genuinely FAILED byte fetch is out whatever its alt says;
              otherwise candidate iff generated_alt OR an operator caption

asset_intake.py (798) — three idempotent arrival paths

  • store_upload — validates the extension, reads the bytes, probes the image with PIL for its real format and dimensions (so the extension is not trusted), hashes it with sha256, stores it in a job-scoped private root, and keeps the client's filename verbatim in a separate field from the sanitized stored name.
  • sync_chat_media_assets — a plain function call at the zip pipeline's success path, not a signal (chat_intake.py:534). Re-attaching a .zip re-syncs; deleting one takes the asset rows with it through the FK cascade. The docstring names the choice explicitly, and it is the right one: a signal here would fire on paths that are not "the archive finished successfully".
  • sync_corpus_assets — one row per image URL on the selected posts, including alt-less ones. Deselecting a post drops its rows unless the operator captioned them or replaced their bytes, in which case the row is kept and reported as orphaned — "both are operator work and the system does not throw operator work away."

A fourth path, materialize_corpus_asset, is the only one that touches the network: it downloads a corpus image's bytes at intake rather than at publish, through the publish path's own downloader (draft_images.download_corpus_image, with its .pstatic.net allow-list and 15 MB cap). The comment is worth internalising: "There is deliberately no second, laxer downloader anywhere."

asset_selection.py (469) — intent versus effect

The sharpest distinction in the asset story, and one that generalises far beyond this codebase:

ContentAgentAsset.selected stores the operator's intent. selected_assets() serves the effect, which is that intent AND evaluate_candidacy. Selection therefore sits on top of candidacy and can never override it — but it is also never destroyed by it. Deselect a KakaoTalk conversation and its photos drop out of the effective set while the operator's earlier picks stay recorded; re-select the conversation and the picks come back.

The other two acts: 교체 (replace) is a swap in place — same row id, same family, same lineage, new bytes, previous name pushed onto replacement_trail. Because the id is the marker key, a replace is invisible to every marker consumer by construction. Chat photos have no replace at all ("the export is the record"), and the API refuses by name. 삭제 (delete) is reversible: it sets deleted_at, and restore puts the row back; the original bytes, the cafe post and the KakaoTalk export are never touched. And "cafe images outweigh chat images" is expressed as group order (카페 → 카카오톡 → 업로드) and nothing else — no score, no badge, no quality field anywhere.

image_pick.py (1,020) — the first v2 stage to send pixels

Explainer #13 taught this module's pass — what it decides. Here is its module — how it is built, because every unusual thing about it follows from "it sends images to a multimodal model":

  • One idempotent scheduler behind four triggers. schedule_image_pass(job) is the only door, knocked on by: the conversation pass landing or failing, the end of corpus materialization, an operator upload (asset_intake.py:238), and a conversation-selection write that moved chat-photo candidacy. At most one run per job is alive, claimed atomically on a shared ContentAgentPass row, so a burst of triggers collapses into one run. A broker outage is logged and swallowed — a read must never fail because a pass could not be queued.
  • Batches of 8 inside one family, families walked in the fixed order above. A batch never crosses a family, because the grid renders per-family judging state.
  • Capped WebP derivatives, never originals: DERIVATIVE_WIDTH = 512, MAX_IMAGE_BYTES = 1,536 KiB per image, MAX_REQUEST_IMAGE_BYTES = 6 MiB per call — and note the difference in how the two ceilings behave: an over-sized image is left unjudged (fail open, per row), while the request ceiling never drops an image, it closes the batch early and the image leads the next call.
  • Judgment is per asset and durable — agent_proposed / agent_reason / agent_off_brand / agent_judged_at live on the asset row, and a re-run judges only rows carrying no judgment and never rewrites an existing reason. That is what makes 나머지 다시 시도 ("retry the rest") mean exactly what it says.
  • Korean prose reasons for the tiles it picked and the tiles it did not. A rejected photo is not silently absent; it says why.
  • The pass never writes a caption — same rule as everywhere else. A caption-required row is judged, gets its reason, and is stored agent_proposed = False.

One late fix is a good cautionary tale about prompt/packet mismatch: the guide had listed "프로젝트와 무관한 사진" (a photo unrelated to the project) as a rejection criterion since v1.3, but the packet carried no subject at all — so the clause was literally undecidable, and a car-wash photo sitting in a tanning-salon job's pool was proposed by a model that was never told what the job was about. build_subject is that missing fact. If a prompt criterion needs a fact, check that the packet actually carries it.

alt_backfill.py (325) — the module in neither slice's file list

This one is in neither #13's nor #14's decomposition file list, and it belongs here. Three of one published article's fourteen figures shipped with alt="": the publish path always writes the attribute, and its caption source is inspection_caption or generated_alt — so an empty attribute simply means the row has neither. Corpus rows arrive with the scraper's alt copied in; chat photos and uploads never had one, because nothing inside content/ had ever generated one.

Six decisions make it a good miniature of the codebase's taste:

  1. A service plus a management command (content/management/commands/backfill_content_agent_alts.py), not a job action and not a new state — "putting an LLM call inside run_publish is deliberately not done here."
  2. The client resolves through the same operator-editable model store as everything else, reusing the image pass's role slug rather than adding a role to the settings UI for a backfill.
  3. It writes generated_alt and only generated_alt; inspection_caption is the operator's field, never machine-written.
  4. Scope defaults to the job's selected live rows with both description fields blank — because writing generated_alt on a corpus row moves it into candidacy, so a wide run would silently grow a reopened job's candidate pool.
  5. A row with no usable bytes is skipped and counted, never captioned. There is no canned placeholder: "An empty alt says 'no description'; a canned sentence says 'described'."
  6. Bytes ride the image pass's existing path — same derivatives, same batches, same ceilings. Ingestion's URL-based alt enricher cannot be reused (an upload has no URL), but its pure sanitize_alt_text is.

asset_views.py (930) is the route table for all of it: list, upload, selection, retry, per-asset delete/replace/restore/fetch, under …/v2/jobs/<uuid>/assets….

4. The draft as an editing surface — draft_editing.py (1,596)

When integration lands, the job is draft_ready and the operator gets one screen. Not an approval screen — an editing screen. The module docstring is again the best summary, and again each claim is checkable.

sections[] is derived, never stored

The draft row holds one integrated body plus a units_map of spans. A "section" on the screen is that body's slice for one written unit, split into the prose the screen edits and the marker lines it does not. split_slice and compose_slice (draft_editing.py:185) are symmetric and deterministic.

Worked example, actually run. I extracted split_slice, compose_slice and revisions._paragraphs and fed them one unit's slice:

## 02. 매장을 고른 이유          <- input slice

첫 문단입니다.

{{img:aaaa}} {{img:bbbb}}

둘째 문단입니다.

{{cap:7:120-134}}

셋째 문단입니다.

split_slice returns:

{"heading": "## 02. 매장을 고른 이유",
 "prose":   "첫 문단입니다.\n\n둘째 문단입니다.\n\n셋째 문단입니다.",
 "markers": [{"line": "{{img:aaaa}} {{img:bbbb}}", "after": 1},
             {"line": "{{cap:7:120-134}}",         "after": 2}]}

The screen edits only prose. Each marker line keeps an anchor — how many prose paragraphs precede it. Editing the second paragraph and recomposing puts everything back where the writer placed it:

첫 문단입니다.

{{img:aaaa}} {{img:bbbb}}

둘째 문단을 짧게 고쳤습니다.      <- the only edited line

{{cap:7:120-134}}

셋째 문단입니다.

And with no edit at all, compose_slice(split_slice(x)) returns the input exactly. The anchor is what makes that true: without it, a conversation capture placed mid-section would drift to the end of the unit on every save. An anchor past the (possibly shorter) new prose falls to the tail; an anchor of 0 leads.

A save is a new rev, never a rewrite

save_edits (draft_editing.py:838) does three things in one transaction, and the docstring insists all three are needed:

  1. the edited prose is spliced back into the body under its pinned heading, with the unit's marker lines put back at their anchors;
  2. the same text is written to the unit row — because the 자유 지시 engine re-assembles from those rows, so "an edit that lived only in the body would be silently overwritten by the next request";
  3. draft rev N+1 is appended via revisions.write_draft.

A stale rev is refused outright (the round has no merge surface), and a refused write answers 409 — well-formed request, the state or the rev said no — so the editor can tell "reload" from "fix your input". One more detail worth stealing: the edits are applied later spans first, because a splice shifts every offset after it, so working backwards keeps the earlier units' precomputed spans valid.

And no edge is taken: a parked 미발행 초안 stays parked and a draft_ready job stays draft_ready. Saving text and 초안 저장 (parking the job) are two different acts.

Media edits change the draft's document, never the approved 구성안

This is the "ruling f" the ContentAgentDraft.document field exists for. The draft screen can remove a photo, bring one in from the 재료 drawer, group or ungroup a row, or trim a conversation range — and all of that changes what publishes without touching the approved revision, which stays the immutable record of what the build ran from. Every draft-stage read of media goes through one accessor, build.draft_document(draft), which returns the draft's own document when it has one and falls back to the revision's when it does not.

The 자유 지시 is atomic — by construction, not by rollback

The screen has one free-text instruction box ("자유 지시" — free instruction): «서두를 두 문장 줄이고, 03절 견적 이야기를 더 구체적으로». It applies to the whole draft. And here is the lovely part — run_free_note (draft_editing.py:1342) rewrites every unit and runs the integration pass entirely in memory:

revision_service._recompose_unit(…, persist=False)      # applies text to the row OBJECT, no save
revision_service._integrate_revision(…, persist=False)  # returns the body, appends no draft
…
return _end(entry, APPLIED, {"result": {"sections": rewritten, …}})

Nothing is written. The request hands the rewritten sections back to the client, which applies them as one undo entry, and the next save persists them. So a failure, an exhausted budget, or the operator hitting 취소 leaves the draft untouched because nothing was ever touched — there is no partial state to undo.

Why this is worth remembering. "Atomic" usually means "we wrote it and can roll it back". This is the cheaper and stronger version: don't write until the whole result exists. It costs one design decision (the worker returns a value instead of mutating rows) and buys you a cancel path, a failure path and an undo entry for free. The cancel check is polled between units (if _cancelled(entry)), and even a cancel arriving at the last moment costs nothing but the compute.

revisions.py (765) — the machinery underneath

Be honest about this module's history: P79.S3 deleted 수정지시 (the structured revision-request subsystem) whole — four scopes, their radio rows, the diff screen, the re-open path. What survives is the primitives the draft editor is built out of: unit_spans / splice_unit (where a unit lives in the body and how to put it back), write_draft (a new draft row per write, never a rewrite), and _recompose_unit / _integrate_revision, which reuse build.py's public names — packet → prompt → client → normalize_unit_return — so nothing about the writer is re-implemented. There is no job state here any more: a rewrite does not move the job.

write_draft also carries two things forward so that "rev N" keeps meaning something: the draft's own document (omitted ⇒ inherit the previous draft's, so a prose-only save never resurrects or drops a media edit), and a per-unit last_edit stamp that rides inside units_map rather than in a new column.

조정 (adjusting) — the fourteenth state

P81 added one more state on operator request. It is reached by begin_adjust from draft_ready, approved_unpublished or failed, and left by back_to_draft, save_draft or publish. The important property: draft_ready --publish--> was left untouched, so 조정 is never a required stop. It joined draft_editing.EDIT_STATES and states.PUBLISH_SOURCES — and publishing.PUBLISH_STATES is now derived from that tuple instead of being a second hand-written copy, so the pre-check and the machine's edges cannot disagree. It is deliberately not in PROGRESS_ACCEPTING_STATES or PAUSE_STATES: 조정 is the operator moving photos around, not the machine running.

The rest of the surface

draft_editing_views.py (257) carries the save, the adjust begin/end, per-unit media ops and the four free-note endpoints. draft_reading_views.py (341) serves GET/PATCH …/v2/jobs/<uuid>/draft. draft_preview.py (100) answers "what will this look like published?" and materializes nothing — no content row, no files, no thumbnail, no state change. It calls the shared renderer publishing.render_document with the console's own asset URLs substituted for the published tree's, which is the single argument the two callers disagree about, so the preview cannot drift from what 발행 actually writes. For how the published document is then delivered to a reader — conditional requests, the render memo, width-capped derivatives — see explainer #12; that is its territory, not this one's.

5. Publish — publishing.py (1,482), and the handoff to #12

Round 19 replaced a two-act gate (승인, then a 발행 게이트 with five rows and a blocker) with the draft editor's end bar. 승인, the gate and the chained 승인→발행 path were all deleted. Two acts remain.

Act one — 초안 저장, and its other half

save_draft is a state transition with a sentence, deliberately not an autosave: the job becomes a 미발행 초안 (approved_unpublished) that the rail can reopen later. Nothing is made public.

materialize_unpublished (publishing.py:1185) is the other half, added by P81: it writes the real NotionContent row — the actual published-content model from explainer #12 — with the HTML and the images on disk, and published_at NULL. So the work appears in the operator's content list with the 비공개 badge while every public surface (NotionContent.objects.readable()) skips it. It is idempotent by construction, keyed on job.published_content_id, so every save refreshes the same content id.

A detail that is pure product thinking. build_published_content(..., touch: bool = False) — the final row update uses a queryset .update(), which bypasses Django's auto_now, so updated_at moves only when the caller asks. 초안 저장 asks (touch=True): the operator rewrote the piece and expects to find it at the top of 최근 변경. 발행 does not: the content screen's own served help promises that 「발행·비공개는 최근 변경 시각을 바꾸지 않습니다」, because a visibility flip is not an edit. The same reasoning appears one layer down in explainer #12's publish seam, which also refuses to bump updated_at. Two layers, one rule, stated in both.

Act two — 발행

request_publish (publishing.py:1257) is 바로 발행 / 다시 발행. P79.S3 widened it and took its guard off: the draft publishes from wherever it sits — draft_ready, approved_unpublished, adjusting or failed. Confirmed by executing the state table: all four publish edges are Kind.GATE with guard = None, and the only guarded edge left in the entire machine is approve_scaffold.

It still validates two things about the 대표 사진 (hero image), and the second is a nice example of a rule that only makes sense if you think about the reader: the hero must be an asset of this job, and it must be one the draft actually places in its 서두 — because "a hero from outside that list would publish a thumbnail the reader never meets on the page." Then, in one transaction, it takes the publish edge, records an immutable decision row carrying the title/hero/category, and queues the worker on_commit.

The worker, and the one line this page ends on

conversation.py (759) — the published conversation, re-rendered every time

When the draft places a {{cap:<chat_rev>:<from>-<to>}} marker, the publish turns that reference — not a copy — into a <blockquote class="chat-view">: a day pill per date change, one group per same-sender run, the authoring side on the right, one <time> per same-minute run, system rows as pills, and a mandatory credit line.

Three properties make this a design decision rather than a renderer:

  • Nothing is stored. It is re-rendered from the archive on every publish and on every 발행 모습 read. No screenshot, no stored copy of the conversation, and no internal identifier (a message id, a chat_rev, an asset uuid) anywhere in the output. Redactions live in their own durable table keyed by message_id, so trimming the range (moving from_id/to_id) can never invalidate one.
  • Photos inside a conversation publish as placeholder bubbles — 사진 N장, 파일 1개, 동영상 1개 — with no bytes ever. And the export's own filler strings (the ones the KakaoTalk parser uses to recognise a media row, including 파일: <원본 이름>) are suppressed, so no original file name reaches a public page.
  • The authoring side is the row's, never the renderer's guess. If no participant is marked, nobody is "me" and every bubble renders left — a visible state the operator fixes in the participant rail, deliberately not a heuristic that is right most of the time.

Every string leaves through content.publish_scrub.scrub_public_text and is HTML-escaped; newlines survive because the reader stylesheet sets white-space: pre-line. This is a privacy-and-provenance decision that happens to be implemented as a renderer.

6. The strip and the progress channel

stage_strip.py (420) — one producer, three servings

Every job screen carries the same six rows directly under the header, and every row in the job rail carries them again as a mini strip. This module is the only producer of all three servings:

STEPS = (("intake","입력"), ("scaffold","구성안"), ("writing","집필"),
         ("draft","초안"),  ("adjust","조정"),     ("publish","발행"))

stage_strip(job)    -> [{index, key, label, state, status, highlight, note}, …]   # the screen
stage_index(job)    -> [{index, status}, …]   # the rail mini — built FROM stage_strip's rows
job_list_value(job) -> the rail's mono word, non-null for every state

Because stage_index is literally a projection of stage_strip's output, a strip and a rail mini can never disagree. And nothing is derived on the client: the label is served, the note is served as a whole sentence, and the visual class is resolved server-side from a single mapping table (RUN_STATES / WAIT_STATES / FAIL_STATES / DONE_STATES) and served pre-resolved as status, so a screen never carries the table at all.

Two readings recorded in the module deserve a look. First, needs_answer is raised at two stages — the proposal turn and the build — so mapping it unconditionally to 집필 would print "writing" for a job that has never written a unit; the step is instead resolved from the transition that produced the pause. Second, MAX_STAGE_ATTEMPTS is never a literal in the served sentence: it prints services.MAX_STAGE_ATTEMPTS + 1, so the number moves with the constant.

There is also a self-aware comment about a real footgun: STATE_STEP.get(state, STEP_INTAKE) fails silently to 입력, so a state missing from the map prints the wrong step rather than raising — "which is why the sixth token is mapped in the same edit that adds it."

progress.py (42) — the v2 half of one channel

This is the smallest module on the page and the clearest statement in the repository of how the two generations relate. Its docstring:

"There is exactly one progress channel in this system and this module does not create a second one. … Same emitter, same endpoint, same field name (progress), same envelope, same fail-soft posture — only the row it lands on differs. Adding a second channel is explicitly forbidden by the agent module's own docstring and by the P54 regression-risk list."

The shared internal route is POST /api/content/internal/miracle-agent/jobs/<id>/progress (content/urls.py:594), service-token gated, and its view draft_views.InternalContentDraftProgressView resolves the id against the v1 job table first and falls through to the v2 row:

def post(self, request, job_id):
    job = ContentDraftJob.objects.filter(pk=job_id).first()     # v1
    if job is None:
        if record_agent_job_progress(job_id, request.data):     # v2 fall-through
            return Response(status=204)
        raise Http404(…)

Resolving the apparent tension. Explainer #13 established (grep-verified) that v2 never calls /agent-api — no AGENT_BASE_URL, no X-Agent-Service-Token, no agent hop anywhere in agent_jobs/. So who writes v2 progress rows, if the route above exists for an agent that never calls it?

Answer, from the code: the v2 pipeline runs entirely inside Django and Celery, so it calls record_job_progress directly, in process. Grepping the whole backend for that function finds exactly five non-test producers, and every one of them is a v2 backend module: build.py:1860 (unit write and integration), architect.py:718 (the proposal turn), chat_intake.py:700 (the KakaoTalk archive pipeline), revisions.py:306 and publishing.py:1216 (the publish). The HTTP fall-through in the view is a seam, not the live producer — it exists so that if anything ever emits progress for a v2 job over the wire, it lands on the same field through the same envelope instead of growing a second channel.

Both halves also share the same guard, and that is the point of the design: a ping outside PROGRESS_ACCEPTING_STATES (processing · proposing · writing · integrating · publishing) is a cheap no-op returning True — the job exists, nothing was stored. A late telemetry envelope must never error the caller or resurrect a stale panel. Note what is deliberately excluded: the draft's free-note request runs while the job sits in draft_ready and reports through its own request row, so a late envelope can never paint a progress panel over the editor.

Quiz

Five questions. Click an option to see whether it is right and why.

1. The unit build writes 서두, each 절 and 맺음 strictly one at a time. What actually breaks if you parallelise the six calls?

It is a real data dependency, not a throttle. neighbor_summaries() feeds every written unit's own summary and continuity note into the next packet — parallel calls would produce six units that repeat each other and hand off to nothing.

2. The integration pass is told, in its prompt, that it may not add a single fact. What does the code actually check when the model returns, and why is the prompt sentence insufficient?

check_integration raises heading_sequence_mismatch or marker_multiset_changed and fails the attempt. Length is reported per unit and never enforced, and there is no verifier model — the checks are deterministic on purpose.

3. A Celery worker is killed while a unit row sits in state writing. What does the next run of the build task do with that row?

The build has no cancel edge at all — the machine's single Kind.CANCEL transition belongs to the proposal stage. The build's answer to a crash is re-entrancy, spelled out in the comment inside _write_units.

4. The 자유 지시 ("free instruction") worker rewrites every unit of a draft and re-runs integration. Why does a failure or a cancel halfway through need no rollback?

"Don't write until the whole result exists" is cheaper and stronger than rolling back. It gives you the cancel path, the failure path and the undo entry for free — and note that a save always appends rev N+1, so no path in this subsystem rewrites a draft.

5. Which single call makes a content-agent article publicly visible, and where does it live?
