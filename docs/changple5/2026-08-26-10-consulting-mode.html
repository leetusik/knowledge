Background — one product, two agents, and a retired sibling

Everything you have read so far in this curriculum describes default chat: the user types, the agent retrieves, the agent answers, the answer is persisted, the turn ends. One request in, one answer out. 컨설팅 mode ("미라클") is the other conversation type the product ships, and it is not a variation of that turn — it is a different shape of interaction laid on top of the same plumbing.

From docs/current/product.md §"Consulting Mode (미라클)", the product promise is three properties:

  • Grounded and cited. Every concrete claim in the report carries a source and is surfaced as an explicit 참고 문서 list; when sources are thin the report is required to admit the limit rather than fabricate.
  • Durable and recoverable. The round's lifecycle state lives in Django (ConsultingRound), not in the browser and not in the agent's memory, so a reload in the middle of the questions — or in the middle of report generation — recovers the exact state.
  • Bounded. A conversation allows 3 reports (report_limit = 3); a probing round the user cancels does not consume one.

The corresponding architecture decision is recorded as docs/current/decisions.md §"D-1 · Consulting v2: backend-owned durable lifecycle": backend is the source of truth for consulting round state; LangGraph checkpoints are agent execution-continuity only, not browser reload recovery. Hold on to that sentence — half of the code on this page exists to honour it.

A deeper background you can skip if you already know it

Three pieces of vocabulary carry the whole page. If they are already familiar, jump to the three new ideas.

Agent. In this codebase an "agent" is a LangGraph state machine built by LangChain's create_agent(...): a model node that calls Gemini, a tools node that runs whichever Python function the model asked for, and an edge that loops back to the model with the tool's result. Explainer #5 walks the default one. 컨설팅 mode builds a second, separate agent with its own tools, its own system prompt, its own state fields and its own checkpoint thread.

Interrupt / resume. A normal function runs to completion. A LangGraph node can call interrupt(value), which suspends the whole graph mid-node, saves everything to the checkpointer, and hands value back to the caller. Later — minutes later, from a different HTTP request, even after a redeploy — you resume the graph with Command(resume=answer), and that interrupt(...) call returns answer as if it had simply been a slow function call. This is how a tool can ask the user a question in the middle of its own execution.

Background worker. Django serves HTTP requests; Celery runs jobs off to the side, picked off a Redis queue by a separate celery_worker container. A job survives the browser closing, can be retried, and can take minutes. Explainer #16 owns Celery in this codebase; this page uses it and points there.

The three new ideas

Everything else on this page is detail hanging off exactly these:

  1. A round is a first-class, backend-owned object. Starting a consultation creates a ConsultingRound row in Postgres that walks probing → generating → complete | cancelled | error. The browser never holds this state; it reads it back on every conversation load.
  2. The clarifying questions are an interrupt inside a tool call. The model calls one tool, start_consulting, and that tool asks up to three rounds of grounded questions by suspending the graph — not by ending the turn and hoping the next message is an answer.
  3. The report is not written by the live stream. The stream's job ends at "a report is now being generated". A Celery task then calls back into the agent over an internal HTTP route, runs a four-stage pipeline, and writes the finished report plus its assistant message into the conversation. The browser finds out by polling.

Intuition — a conversation that pauses, and a report written elsewhere

One turn versus one round

A default chat turn is a straight line. A consulting round is a line with a hole punched in the middle of it, and a second line that runs later, in another process.

What "interrupt" really means, with toy data

The unfamiliar piece is step 3. A tool is a Python function; functions do not normally stop halfway and continue tomorrow. LangGraph's interrupt() makes them do exactly that, by taking a checkpoint of the whole graph and raising out of the node. Here is the shape, stripped to nothing:

# toy version of apps/agent/app/chat/consulting/tools.py
def start_consulting(subject):
    round_id = backend.start_round(subject)          # a real Postgres row

    for turn in (1, 2, 3):
        questions = ask_the_model_for_questions(subject)   # ≤ 3 questions
        backend.save_pending_probe(round_id, questions)    # so a reload can recover them

        answers = interrupt({"questions": questions, "turn": turn})
        #         ^^^^^^^^^ the graph STOPS here. This HTTP request is over.
        #                   Some later request calls Command(resume={"answers": [...]})
        #                   and *this same line* returns that value.

        if answers.get("cancelled"):
            backend.cancel_round(round_id)
            return "취소했어요."
        remember(answers)
        if enough(subject, remembered):
            break

    backend.create_report(round_id, remembered)      # → Celery does the writing
    return "보고서를 작성 중입니다..."

With real toy data, a two-turn consultation looks like this:

#HTTP requestWhat the tool doesWhat the browser gets
1 {"message": "떡볶이집 창업하려는데 조언 좀 해줘"} model streams a one-sentence empathy line, then calls start_consulting(subject="떡볶이집 창업 전략"); the tool creates the round, generates turn-1 questions, interrupt()s deltas of the empathy line, then a consulting_probe card: t1_q1 예산은 어느 정도로 생각하고 계세요? · t1_q2 어느 지역·상권을 보고 계신가요? · t1_q3 외식업 경험이 있으신가요?
2 {"resume_value": {"answers": [{"id":"t1_q1","value":"5천만원"}, …], "note":"배달 위주로 생각 중"}} the graph resumes inside the loop, records turn 1, asks the model whether that is enough (it says no), generates turn-2 questions, interrupt()s again a second consulting_probe card, turn 2 of 3
3 {"resume_value": {"answers": [{"id":"t2_q1","value":"…"}], "finish": true}} records turn 2; finish means "stop asking"; emits consulting_summary + consulting_report_start, asks Django for a report row, returns consulting_report_start {report_id}, then done. The card turns into a "보고서를 작성 중입니다" placeholder and the browser starts polling.

Why an interrupt rather than "just ask in chat". The model could have typed the questions as ordinary text and waited for a reply. Three things break if it does: the questions become free text the code cannot render as a form (the product shows a card with labelled inputs and a skip button); the "are we still probing?" state becomes a guess about the last message instead of a fact; and a reload has nothing to recover. The interrupt keeps the questions structured and the loop's local variables alive across HTTP requests.

The round state machine

Everything user-visible about a consultation is derivable from one row. Five states, and each transition has exactly one owner:

The cancel rule, operator-confirmed. Cancelling the question card produces no assistant reply at all. The card disappears, the round goes cancelled, and nothing is written to the transcript. That is deliberate, not a missing feature — the code for it is named skip_cancel_write and we walk it below.

Why the report left the live stream

Generating a consulting report means: one model call to plan an outline, up to eight retrieval queries (each with its own embedding call and reranker call), one model call to write several thousand Korean characters against two dozen full post bodies. That is minutes, not seconds. If it ran inside the SSE response, three things would go wrong:

FailureOn the live streamWith Celery (what actually ships)
The user closes the tabThe work is cancelled; nothing is written; the round is stuckThe task is already queued and finishes anyway; the report lands in the conversation
Gemini rate-limits us (429)The turn dies with an error frame The task raises a transient error and is retried, 30 s later, up to 3 attempts total
The worker is killed mid-reportNothing to reclaim — the request is gone The row is still generating; the reclaim pass requeues it

The price is a handover: the live stream must tell the browser "a report with this id is coming" and then get out of the way, and the browser must find out about completion some other way. Both halves are visible in the sequence below.

The single most load-bearing line in the three models is a database constraint:

# ConsultingRound.Meta.constraints
models.UniqueConstraint(
    fields=("session",),
    condition=models.Q(status__in=("probing", "generating")),
    name="consultrnd_one_active_session",

A partial unique index: at most one row per session whose status is probing or generating, with terminal rounds unconstrained. "One consultation at a time" is therefore enforced by Postgres, not by careful Python. Everything else in the lifecycle code is there to give a good error message before the database has to say no.

It rides on the ordinary conversation-detail GET: explainer #4 noted that ConversationHistoryDetailSerializer carries consulting_lifecycle as a SerializerMethodField. So a browser that reloads mid-round, and an agent turn that is about to start, both learn the state from the same request they were making anyway — no extra round trip, and no possibility of the two disagreeing.

Metadata only, on purpose. completed_report_ids carries ids, never bodies (see the comment at :70-73): the conversation-detail payload is fetched on every load, and embedding two or three multi-thousand-character reports in it would make every page load pay for them. The agent fetches a body on demand instead — that is what the grounding helper in §5 does.

The write side: consulting_mutations.py

apps/backend/conversations/consulting_mutations.py (597 lines) holds every state change, and each one follows the same four-step discipline:

with transaction.atomic():

Two locks, always in the same order (session, then round), so two concurrent requests on the same conversation can never deadlock against each other. Every refusal is a ConsultingLifecycleConflict (:26) — a DRF APIException with status_code = 409 whose body is {"code": …, "detail": …}, so clients branch on a machine-readable code and never on prose. Four functions do the work.

start_consulting_round (:159) creates the round — or, crucially, returns the existing one:

if active_round is not None:
    # LangGraph re-executes an interrupted node top-to-bottom on every
    # resume, so the agent's `start_consulting` tool re-fires this
    # round-start after the round it created is already active (still
    # PROBING). Treat that as a replay and return the existing round …
    if active_round.status == ConsultingRound.Status.PROBING:
        return active_round
    raise _conflict("active_round_exists", …)

The single most surprising fact about interrupts. Resuming does not continue from the interrupt() line — LangGraph re-runs the whole node from the top and replays each interrupt() call from the checkpoint until it reaches the one that is still pending. So every line before the interrupt runs again, on every resume. That is why round-start is idempotent here, why the tool re-reads persisted questions instead of regenerating them, and why the cancel path re-cancels the round it just "created". Any side effect you put in an interrupting node must be idempotent, full stop.

persist_pending_probe (:205) stores the question set the user has not answered yet, so a reload can re-render the card.

accept_probe_answers (:319) is the busiest function. It validates that the submitted ids are exactly the pending ids (set(answer_by_id) != set(question_ids) → stale_probe_answers), appends a turn entry to probing_context["turns"], clears pending_probe — and then writes the user's answers into the transcript as a real message (_persist_probe_answers_message, :259):

Q. 창업 예산은 어느 정도로 생각하고 계세요?
A. 5천만원

Q. 어느 지역·상권을 보고 계신가요?
A. 아직 정하지 못했어요

with metadata = {"message_type": "consulting_probe_answers", "qa_pairs": […], "turn": 1, "round_id": …}. Two details are worth copying into your own designs:

  • Its own idempotency namespace. build_consulting_probe_answers_idempotency_key (:240) is a uuid5 over "{nonce}:{round_id}:{turn}:consulting_probe_answers" under a namespace constant that belongs to this message kind alone (:235). The same turn therefore always derives the same key, and explainer #4's UniqueConstraint(session, idempotency_key) makes the write replay-safe for free.
  • It refuses rather than breaks alternation. Before writing, it checks that the newest message is an assistant one; if a preceding acknowledgment failed to persist, the bubble is simply skipped (the answers still live in probing_context). A user→user pair would be rejected by append_finalized_message and would block the submission entirely — so a cosmetic bubble is never allowed to cost the user their answer.

cancel_probing_round (:402) flips the round to cancelled, clears pending_probe, stamps terminal_at — and is idempotent: a round already cancelled is returned as-is.

A fifth function, create_or_link_consulting_report (:433), is where probing becomes generating: it creates the ConsultingReport row, moves the round to generating, stamps report_started_at, and calls queue_consulting_report_generation_on_commit(report). Note what report_started_at means: count_started_consulting_reports counts rounds where it is set, so the 3-report cap counts started reports, not successful ones — a report that errors still consumes one — while a cancelled probing round never sets it and therefore costs nothing.

The consulting agent cannot retrieve. Default chat registers up to seven tools — three retrieval tools, session search, cited-document search, the security check, and the feedback tool. 미라클 registers two: start_consulting and security_check. Retrieval still happens, but only inside the consulting code paths (probing-question grounding and the report pipeline), never as something the conversational model can decide to do. That is the mechanical expression of the product rule "all substantive analysis comes from the report": with no retrieval tool, an ungrounded claim has no source to come from, and the system prompt's [제한] section forbids inventing one.

The state schema, and why consulting kept the fingerprint

ConsultingAgentState (:120) extends LangChain's AgentState with the whole lifecycle mirror:

Explainer #5 recorded that default chat deleted its backend_history_fingerprint: sync_chat_agent_checkpoint unconditionally deletes the thread and rebuilds it from backend history every turn, so a fingerprint would have had nothing to decide. Consulting cannot do that, and this is the reason:

# agent.py:350  sync_consulting_agent_checkpoint
if snapshot_values and stored_fingerprint == backend_history_fingerprint:
    return config                     # history unchanged → keep the thread as-is
if is_resume and snapshot_values:
    return config                     # ← a RESUME must never rebuild the thread

preserved_consulting_state = {…}      # :375  keep the 11 consulting_* fields
if snapshot_values:
    await runtime.checkpointer.adelete_thread(f"consult:{conversation_nonce}")
… rebuild from verbatim_messages, then re-merge preserved_consulting_state …

Deleting the thread would destroy the pending interrupt. The suspended start_consulting call — its loop counter, its accumulated probing_context, its place in the interrupt() sequence — is the checkpoint. So the resume path returns early, and the non-resume path preserves the eleven consulting_* fields across a rebuild. The fingerprint (a hash of the backend message history, chat/fingerprints.py) is what lets it skip the rebuild entirely when nothing changed. That module survives in the codebase for consulting alone.

Three details in the replay logic

  • Questions are recovered, not regenerated (_recover_questions, :99). On resume the node re-runs from the top; without recovery every replayed turn would burn another question-generation call and the wording could drift under the user's eyes. The persisted round carries the answered turns and the pending set, so the replay reads them back. interrupt() is still called once per turn regardless — LangGraph matches resume values to interrupts by call index, so skipping one would misalign the whole sequence.
  • The acknowledgment is skipped on replay (:283-294). The reasoning in the comment is a small proof: only the turn that genuinely suspends reaches stream.py as the interrupt value, and a non-resume stream on an active probing round is refused with a 409, so the suspending turn is always a new turn — therefore the ack computed on a replayed turn is provably never consumed. One saved ainvoke per replayed turn per resume.
  • The ack never touches the database via the round. It rides only the in-memory interrupt payload; the three keys type, round_id, ack are stripped from what is persisted (:318-322) so consulting_lifecycle.pending_probe stays a pure question set.

A known trap, worth knowing before you add a field. Each answer must be exactly {"id", "value"} — no more keys, no fewer — and the returned dict is assembled from scratch. (Empty value strings are allowed on purpose: that is the "skip this question" button.)

The silent cancel, in code

Three mechanisms cooperate to produce "the card just disappears":

  1. Suppress the model's deltas. On a cancel resume the node still runs the model once more after the tool returns, and that regenerated reply "tends to apologize with a system-fault tone or append an unsolicited report" (:50-56).   2. Replace the content with the deterministic _CONSULTING_CANCEL_MESSAGE (:57) — "컨설팅 질문을 취소했어요. 다른 도움이 필요하시면 언제든 편하게 말씀해 주세요."
  3. Then usually do not write it at all. So skip_cancel_write takes the elif branch at :637: mark the agent state cancelled, refresh the fingerprint, terminalize the run, emit done — and write nothing.

The user-visible result — card gone, round cancelled, no bubble — is operator-confirmed intended behaviour, not an oversight. The durable cancelled status is what the frontend renders the terminal state from. If you "fix" it by writing a cancel reply, you break alternation and re-introduce the bug this code was written to remove.

Stage 2 — queries. _build_retrieval_queries (:683) assembles, in order: the subject; one query per probing turn built from that turn's first two answers; then every retrieval_queries string the outline asked for. Case-insensitive dedupe, then [:8]. With the toy data:

["떡볶이집 창업 전략",
 "떡볶이집 창업 전략 5천만원 아직 정하지 못했어요",
 "떡볶이집 상권 분석",
 "분식 프랜차이즈 창업 비용",
 …]                        # ≤ 8

Stage 3 — retrieval. Every query goes through explainer #7's single chokepoint, build_ranked_retrieval_result, and they run concurrently:

# :761  each query is independent: sync function, own DB connection, own embedding/rerank clients
results = await asyncio.gather(*(_retrieve_one(query) for query in queries))

The comment is careful about what parallelism did and did not change: results are still accumulated in the original query order, so the deduped, capped output is byte-identical to the old serial loop — the only difference is that a query past the cap now runs and is discarded, instead of being skipped. Two budgets accumulate independently: naver posts up to MAX_CONSULTING_DOCUMENTS = 24 (6 per query) and 미라클 콘텐츠 up to MAX_CONSULTING_CONTENTS = 6 (3 per query). The report path opts the content channel on (content_mode=ContentMode.ON) while probing deliberately leaves it off. Failures are per-query: a RetrievalEmbeddingError or RetrievalRerankError logs and returns None for that query only. Finally the bodies of the selected posts are hydrated in one batch — gate first, hydrate after, explainer #7's security rule.

Stage 4 — generate_report. The prompt (prompts.py:446) hands the model the subject, the Q&A, the outline, a [참고 문서] block of [문서 post_id=42] 제목\n본문 entries, and a separate [참고 콘텐츠] block of excerpt-based [콘텐츠 content_id=19] entries. The rules are explicit about the two id spaces ([post:N] vs [content:N], never mixed, never bundled as [post:42,43], never a bare number), about admitting thin sources ("참고 문서가 없거나 부족하면 … 솔직히 밝히고 추측으로 빈자리를 채우지 마세요"), and about not writing its own 참고 문서 list — the app renders that from the structured citations. Empty output raises rather than returning "": an empty report is a failure, and the Django side agrees (_build_agent_report_generation_result rejects blank content as permanent).

Citation rendering (:986-1013) then does three passes: normalize_bare_post_id_markers rewrites a bare [42] into [post:42] when 42 is a retrieved post id (never for content ids — a bare [19] is indistinguishable from a display number); render_citation_markers turns the internal markers into the visible, sequential [k] and records the merged, ordered cited_references; and strip_unmatched_visible_citation_markers deletes any leftover [k] with no citation behind it. The route then projects that one ordered list into the response's three fields — citations (each with index, type, and either post_id + source_url or content_id), cited_document_post_ids, and cited_content — and every id must resolve or the whole thing raises.

6.5 Finalization (Django) — consulting_report_finalization.py

complete_consulting_report(nonce=…, report_id=…, owner_user_id=…, content=…,
                           citations=…, cited_document_post_ids=…, cited_content=…)   # :33

Inside one transaction.atomic(), with the session and report locked and the linked round locked too:

  1. Already COMPLETE? Re-run the round transition (idempotent) and return.
  2. Not GENERATING? Refuse — 409 round_not_generating if a round is linked, otherwise a validation error.
  3. Derive the message key: uuid5(ns, f"{nonce}:{report_id}:consulting_report") (:22) — again a content-derived key under its own namespace, so a retried task cannot double-post.
  4. If a message with that key already exists, adopt it; otherwise session.append_finalized_message(role=ASSISTANT, content=…, cited_document_post_ids=…, cited_content=…, metadata={"message_type": "consulting_report", "report_id": …, "subject": …, "per_turn_persisted": True}).
  5. Save the report as COMPLETE with its content, citations and message FK, then transition_linked_round_to_complete.

fail_consulting_report (:141) is the mirror image: same key, an apology message "죄송합니다. 보고서 생성 중 오류가 발생했습니다. 다시 시도해 주세요." with message_type: "consulting_report_error", the report to ERROR with its error_detail, and the round to error. Either way the round always leaves the active states, so the conversation is never left frozen by a report that failed. (_extract_qa_pairs_from_probing_context at :271 is the legacy helper that flattened turns into qa_pairs for the report card; new reports set per_turn_persisted: True and the frontend renders the per-turn bubbles instead — consulting-report-message.tsx:43 gates on exactly that flag, so old reports keep their inline summary.)

6.6 How the browser finds out

No SSE frame carries the finished report — the stream is long over. The browser polls:

// apps/web/src/lib/consulting.ts:195
export async function pollConsultingReport(getReport, options) {
  const intervalMs  = options.intervalMs  ?? 3000;
  const maxAttempts = options.maxAttempts ?? 60;
  for (let attempt = 0; attempt < maxAttempts; attempt += 1) {
    const report = await getReport(options.conversationNonce, options.reportId);
    if (report.status === "complete") return { status: "complete", report };
    if (report.status === "error")    return { status: "error", report };
    await sleep(intervalMs);
  }
  return { status: "timeout" };
}

3 s × 60 = 3 minutes — the same order as the 180 s the agent gets for one attempt. The endpoint is the owner-JWT GET /api/conversations/<nonce>/reports/<report_id>, and on a terminal status the hook reloads the whole conversation detail so the report renders from the persisted assistant message, not from the poll response.

Why this survives a reload. The poll is not started by the SSE frame. It is started by an effect keyed on generatingReportId, which comes from getActiveGeneratingState(detail) — that is, consulting_lifecycle.active_round.status === "generating" && consulting_lifecycle.active_report_id (apps/web/src/lib/consulting-lifecycle.ts:70). A browser that loads the page fresh, hours later, sees the same lifecycle object and starts polling as if it had been there all along. This is decision D-1 paying for itself: the browser recovers from durable backend state, never from stream history.

6.7 Recovery when the worker itself dies

Retries cover a failing call. They do not cover a worker that is killed between "claim the attempt" and "finish", which would leave a row generating forever — and, because the round is generating too, the whole conversation refuses new turns with a 409. That is what reclaim_stale_consulting_report_generations (:150) is for: every report still GENERATING whose generation_last_attempt_at (or, if never attempted, updated_at) is older than CONSULTING_REPORT_RECLAIM_AFTER_MINUTES (default 15) is either requeued or, at the attempt ceiling, terminally failed.

Read the trigger carefully. The reclaim task is not on the beat schedule. apps/backend/config/celery.py's beat_schedule (:15-43) lists five entries and this is not one of them; the task is dispatched from @worker_ready.connect dispatch_startup_recovery (:59-72), i.e. only when a Celery worker starts. So the 15-minute window is not "checked every 15 minutes" — it is "checked at the next worker restart, and only reclaims rows older than 15 minutes at that moment". In a long-lived deployment a report stranded by a hard worker kill stays stranded, with its conversation frozen, until the next restart. docs/current/backend.md describes this correctly as startup recovery; recorded as an operator question, not changed here.

Quiz

Five questions. Click an option to see whether it is right and why.

1. A user answers the last probing question. Which process writes the finished consulting report into the conversation, and why that one?

The live stream's job ends at "a report with this id is coming" (consulting_report_start). queue_consulting_report_generation_on_commit queues conversations.generate_consulting_report; the worker POSTs to /agent-api/internal/consulting/reports/generate (180 s), then writes the report row and the assistant message itself. That buys durability, 3 attempts with 30 s backoff, and reclaim after a crash.

2. What is resume_value, and who is the last component that gets to decide what it contains?

It is either {"cancelled": true} or {"answers": [{"id","value"}, …]} plus optional finish / note. chat.py:250 rejects anything else and normalises away what it does not recognise, so adding a field to the resume value requires an edit there — otherwise the tool never sees it.

3. A conversation has already started three reports (one of which errored). The user asks for a fourth. What happens?

count_started_consulting_reports counts report_started_at__isnull=False, which is stamped when the round enters generating — outcome irrelevant. Only a cancelled probing round costs nothing, because it never reaches that stamp. The user is told to start a new conversation.

4. The user cancels the probing card in the middle of turn 2. What is written to the conversation transcript?

Three cooperating pieces: suppress_deltas, _resolve_consulting_final_content, and skip_cancel_write (true when it is a probe cancel and the tail is an assistant message). Writing a second assistant message would break the user→assistant alternation rule. Operator-confirmed as intended: the card just disappears.

5. A legacy conversation with agent_type = "diagnosis" is opened and a message is sent today. What does the user get?

P35 deleted the agent package and added the 403 tombstone; P36.S1 removed ENABLE_DIAGNOSIS_MODE entirely and made creation refuse unconditionally. No migration was needed because agent_type is a plain CharField, so historic rows still read back — they just cannot be continued. (product.md's "reversibly flag-gated" paragraph is stale.)
