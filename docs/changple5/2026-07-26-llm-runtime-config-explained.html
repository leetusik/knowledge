Moving LLM configuration out of environment variables and into the database

How changple5 gave its operator a web page for choosing which Gemini model each part of the product uses — and how much thinking each one does — without a redeploy, a restart, or a single outage. Phase P44, shipped 2026-07-26.

Background

The very beginning: what "configuration" even means

If you already know what an environment variable is and why config lives outside code, skip to "Eleven places, one product" below.

Every program has values that are not really part of the program. A database password. A port number. The name of an AI model to call. These are configuration: things the same code should be able to run with different values, depending on where it is running.

The industry's standard answer for the last decade or so is the twelve-factor rule: keep configuration in environment variables — key/value pairs the operating system hands to a process when it starts. The twelve-factor manifesto (12factor.net) puts it plainly: "the twelve-factor app stores config in environment variables," because they can be changed between deploys without touching code, are unlikely to be committed to version control by accident, and work in every language.

changple5 follows this. A file called .dev.env holds the developer's values, a file called .prod.env holds production's, Docker Compose passes them into each container, and the code reads them at startup.

The catch that this whole story is about

Environment variables are read once, when the process starts. To change one, you must edit a file on the server and restart the container. That is completely fine for a database password. It is not fine for a value a non-engineer wants to change on a Tuesday afternoon.

Eleven places, one product

changple5 is an AI product for Korean small-business owners. Under the hood it does not call "the AI" once — it calls a large language model (LLM) in eleven different roles, each doing a different job:

ServiceRolesWhat they do
apps/agent
(FastAPI, 8 roles)		 chat, chat_context_token_estimation, chat_history_compaction, retrieval_rerank, consulting_chat, consulting_report, content_draft, content_research Answering the user, re-ranking search results, summarising long histories, running the consulting flow, drafting marketing content
apps/backend
(Django, 3 roles)		 conversation_title, image_alt, text_enrichment Naming a conversation, writing alt-text for images, enriching scraped documents

Each role had its own environment variable naming a Gemini model. Cheap-and-fast models (gemini-3.1-flash-lite) for mechanical jobs, expensive-and-smart ones (gemini-3.1-pro-preview) for writing. Choosing well is a real business decision: it trades money against answer quality, and the person best placed to make it is the operator running the product — not an engineer with SSH access.

The two complaints that started the phase

The operator asked for something short: "make llm configurable in webui (out of env). with their effort level. every model." Behind it were two concrete frustrations.

First: "the content agent LLM is hardcoded." This turned out to be true, and for a sneaky reason. The agent's settings loader is configured with env_ignore_empty=True, meaning an empty environment variable is treated as if it were absent, so the code default applies. Compose passed the content-model variables through as ${VAR:-} — empty when unset — and .dev.env had no line for them at all. So the variables existed, were passed, were empty, and were ignored. The model was effectively hardcoded, exactly as reported. Worse, a related pair (GEMINI_CONSULTING_CHAT_MODEL, GEMINI_CONSULTING_AGENT_MODEL) was set in both env files but named in no Compose block at all — so those values never reached a container in any environment, ever.

Second: there was no way to control reasoning effort per role. Modern Gemini models can be told how hard to think before answering — a thinking_level of minimal, low, medium or high. A previous phase had wired this for the main chat role only, through an environment variable. The other ten roles had no control at all.

So the phase's job: build the store, make both services read it live, build the web page, fix the env plumbing underneath it, and prove the whole thing works on a real running stack.

Intuition

The shape of the change, in one picture

Why this is harder than "just read from the database"

The naive version — look up the model in the database every time you need it — has three problems, and the interesting design work is all in dodging them.

Problem 1: the settings object is frozen. The agent's get_settings() function is decorated with @lru_cache, a Python decorator meaning "call this once, then hand out the same object forever." That is a deliberate performance choice, but it means anything read through settings is frozen for the life of the process. A database-backed value therefore has to be read outside the cached settings object entirely — a separate code path that nobody has cached.

Problem 2: one query per LLM call is too many. A single chat turn constructs several models. Querying the database each time adds latency to the hottest path in the product. The standard fix is a TTL cache — "time to live." Read the table once, keep the answer in memory, and only re-read when the answer is older than N seconds. Here N is 30. So the cost is one query per process per 30 seconds no matter how much traffic flows, and the operator's edit shows up within 30 seconds. That is the trade: a tiny, bounded staleness in exchange for effectively free reads.

Toy example of the TTL

t = 0s    process reads the table       snapshot = {chat: "flash", ...}, expires at t=30
t = 5s    operator saves "pro" via the web page   (database now says "pro")
t = 6s    a chat turn asks for the model → snapshot is still fresh → "flash"
t = 31s   a chat turn asks for the model → snapshot expired → re-read → "pro"

The read at t = 6s returning the old value is not a bug — it is the proof that the cache is real. When the P44 team verified this on a live stack, that unchanged read was the load-bearing piece of evidence: without it, a later change could just have been an accidental fresh read rather than the TTL doing its job.

Problem 3: a config read must never break the product. This is the one that shapes everything else. The database holding the configuration is the same database everything else uses, but the failure modes are not the same. If the conversation table is unreachable the product is down anyway. If the config table is unreachable — a bad migration, a typo, a network blip — the product should carry on happily with whatever it used yesterday.

The three-step ladder

So every role resolves its model through a ladder, and each rung is a fallback for the one above:

The environment variables were deliberately not deleted. That sounds like it undercuts "get config out of env," but it does the opposite: it is what makes moving to the database safe. Rung 2 exists so a brand-new container that has never reached the database still starts with sensible values.

The trick that made this a one-step, zero-risk migration

Before writing any code, the team checked every one of the eleven roles across .dev.env, .prod.env.example and both Compose files, and found that every value actually in use already equalled its code default. So the database migration seeds each row with the code default, and on the day it lands nothing changes anywhere. Dev behaves identically. Production behaves identically. That is what makes the rule "the database wins" safe to ship in one go instead of behind a flag. It was later verified on the live stack, not just argued: ALL SEEDED VALUES == REGISTRY CODE DEFAULTS: True.

The two shapes a config table can have

There was a real design fork here. changple5 already had an operator-editable config table, DocumentRetrievalPolicy, built as a singleton: exactly one row, one column per setting. Copying that shape would have meant a table with 22 columns (a model id and a thinking level for each of the eleven roles).

The deciding evidence was in the repo's own history: another table, LandingPageCopy, had started as a singleton and been migrated away from it in an earlier phase. The team had already paid for that lesson once. Crucially, the role column has no choices= constraint, so the database does not need to know the list of valid roles — that list lives in code, and adding to it never requires touching the schema.

What "no value" has to mean

One subtle but load-bearing decision: thinking_level is nullable, and NULL means "send no thinking parameter at all" — not "send zero," not "use some default we picked." Ten of the eleven roles seed as NULL, which preserves the provider's own behaviour exactly. Only chat seeds a real value (high), preserving what the previous phase had already shipped.

This is why the web UI has a 기본값 (미설정) ("default / unset") option that sends an explicit JSON null — which is meaningfully different from omitting the field. Omitting means "leave it alone"; null means "clear it." Confusing the two would make it impossible to ever turn a thinking level back off.

Guarding against a typo

Free text in a box that feeds a paid API call is a little scary. If the operator types gemini-3.1-fash-lite, what happens?

The tempting answer is "detect it at call time and quietly substitute a known-good model." The team rejected that, and the reasoning is worth internalising: silently substituting masks the misconfiguration, so the operator sees a working product and never learns their setting is wrong, while the bill quietly reflects a model they did not choose. Later, behaviour becomes unexplainable — the config says one thing, reality does another.

Instead, validation happens on write, at the moment the operator can actually do something about it:

1. Shape check A conservative regex on the id, ≤ 200 characters.
2. Embedding guard Reject known embedding-model ids for any generation role.
3. Live probe Actually call the provider with the submitted id and see if it exists.

The probe is the interesting one. Before saving, the server builds a throwaway client with the submitted id and asks it to count the tokens in the word "ping" — the cheapest real call available. If Google says "no such model," the save fails and the operator sees Google's own words. If the probe fails for some other reason — a quota error, a timeout, a missing API key — the save is allowed. That asymmetry is the whole craft of it: a provider outage must never lock an operator out of their own settings page.

And because a genuinely brand-new model might not answer a token-count call yet, there is a deliberate escape hatch: a ?probe=false flag, surfaced in the UI as a 검증 없이 저장 ("save without verification") button that appears only after a probe rejection. The alternative — a hardcoded list of allowed models — would go stale within weeks and block the operator from adopting a new Gemini model, which is the entire point of the feature.

Why embeddings are deliberately excluded

The operator said "every model." Eleven roles are configurable; one model is not, and that exclusion is enforced in code. An embedding model is the thing that turns documents into vectors for semantic search. changple5 has thousands of documents already converted using one specific embedding model. Swapping it at runtime would not produce worse search — it would produce nonsense, because new vectors would live in a different mathematical space than the stored ones. The whole index would need rebuilding. So the embedding model stays pinned to an environment variable, is absent from the table, the API and the UI, and the write path actively rejects known embedding ids for any generation role.

A nice detail in that guard

The rejection matches embedding ids exactly, after lower-casing and stripping a models/ prefix — deliberately not by substring. If it matched substrings, a future generation model whose name happened to contain the word "embedding" would be permanently unselectable, and the operator would be locked out by a guard meant to protect them.

Code

The change landed as six commits. Rather than walk them chronologically, it is clearer to walk the data flow: where the value is stored, how each service reads it, how the operator writes it, and what had to be fixed underneath.

1. The store (apps/backend/operators/)

A Django model with a unique role slug, plus a migration that both creates the table and seeds all eleven rows. The seed is a frozen inline snapshot of the registry — a copy of the values as they were the day the migration was written, deliberately not an import, because a migration that imports live code stops being reproducible the moment that code changes.

Alongside it, operators/llm_roles.py is the canonical registry: a tuple of frozen LLMRoleSpec records carrying each role's slug, which app owns it, a Korean UI label, whether it supports a thinking level, and its defaults.

2. The agent-side reader (apps/agent/app/llm_config.py)

This is where the @lru_cache problem is solved. The module keeps a snapshot in a module-level variable guarded by a lock, refreshed by a plain SQL query:

_lock = threading.Lock()
_snapshot: dict[str, tuple[str | None, str | None]] | None = None
_snapshot_expires_at: float = 0.0

def refresh_llm_config(settings=None, *, force=False) -> None:
    """Refresh the snapshot when it is stale (or force). Never raises."""
    global _snapshot, _snapshot_expires_at, _failure_logged_at
    now = time.monotonic()
    with _lock:
        if not force and _snapshot_expires_at > now:
            return
        ttl = _cache_ttl_seconds(settings)
        try:
            rows = _fetch_llm_config_rows(settings)
        except Exception as exc:      # broad on purpose — see below
            _snapshot_expires_at = now + ttl
            ...  # log at most once per failure window
            return                     # keep the OLD snapshot
        _snapshot = rows
        _snapshot_expires_at = now + ttl

Three things in those twenty lines carry most of the design:

  • The except catches bare Exception, not a database error. That is normally a code smell. Here it is deliberate and documented: a stubbed or partial settings object raises AttributeError while building the connection string, long before any database library is reached, and that path must degrade exactly like a dead network would.
  • On failure the old snapshot is kept. "Last known good" beats falling back to environment variables. A process that has read the store once keeps serving the operator's real choices straight through an outage.
  • The failure is cached too (_snapshot_expires_at = now + ttl). Without that line, an outage would mean a fresh connection attempt on every resolution — turning a database problem into a latency problem. The warning log is separately throttled to one line per window, so a broken table cannot flood the logs during a stream.

The query itself has to be schema-qualified, because Django's tables live in a backend schema while the agent's own search path points at agent:

SELECT role, model_id, thinking_level FROM "backend"."operators_llmroleconfig"

Call sites then resolve through small helpers. Here is the chat role's thinking level, inside the streaming hot path:

# P44.S2: store -> GEMINI_CHAT_THINKING_LEVEL -> unset. Still conditional:
# the kwarg is omitted entirely when nothing resolves, which is also what keeps
# the stubbed-settings tests from seeing an unexpected kwarg.
thinking_level = resolve_role_thinking_level(
    settings,
    role=ROLE_CHAT,
    settings_attr="gemini_chat_thinking_level",
)
if thinking_level:
    extra_model_kwargs["thinking_level"] = thinking_level

That if is not defensive padding. It is the difference between "unset" and "explicitly none": passing thinking_level=None to the model constructor is a different thing from not passing the argument at all, and only the latter preserves the provider's own default. It also keeps the existing test suite green — the tests build fake model constructors with strict signatures that reject unexpected keyword arguments, so an unconditional pass-through would have broken hundreds of tests.

The test-isolation trap this uncovered

Postgres publishes port 5432 to the host, and the agent's default database host is 127.0.0.1. So a test suite run on a developer's laptop can reach the real development database. Without a guard, the moment the table existed, roughly 700 unit tests would silently start resolving whatever the operator last saved instead of their stubbed values — tests that pass or fail depending on a web form. The fix is an autouse fixture in conftest.py that patches the connection factory to raise and resets the snapshot around every test, forcing the store "offline" for the whole suite.

3. The backend-side reader (apps/backend/operators/llm_runtime.py)

The Django side has no cache at all — one function, one query, no TTL:

def resolve_role_config(role, *, settings_attr, default_model, default_thinking=None):
    try:
        row = (LLMRoleConfig.objects.filter(role=role)
               .values_list("model_id", "thinking_level").first())
    except DatabaseError:
        logger.warning("LLM runtime config read failed for role %r; "
                       "falling back to env/default.", role, exc_info=True)
        row = None
    stored_model_id, stored_thinking_level = row if row is not None else (None, None)
    model_id = (stored_model_id
                or getattr(settings, settings_attr, default_model)
                or default_model)
    thinking_level = stored_thinking_level
    if thinking_level not in THINKING_LEVELS:
        thinking_level = default_thinking
    return model_id, thinking_level

Why no cache, when the agent needed one? Because of where these three roles run. Each is invoked from a builder function that is called once per background job, not once per item. A job might process hundreds of images, but it asks for the model exactly once. So a single query per job already gives per-job freshness for free; a cache would add staleness without saving any queries. The measured effect is ~20 ms from a save to the next job seeing the new value.

Note also if thinking_level not in THINKING_LEVELS. A junk value stored through the Django admin back door would otherwise reach a strict enum field and raise at model construction — i.e. it would break generation, which the whole design forbids. The agent has the identical guard.

4. The batch path

Two of the backend roles have a second consumer: a Gemini batch API, which sends requests as lines of JSON rather than as client calls. A thinking level cannot ride on a client there — it has to go inside the request body:

def _batch_generation_config(base, *, thinking_level):
    config = dict(base)
    if thinking_level:
        config["thinking_config"] = {"thinking_level": thinking_level}
    return config

The team verified against the installed SDK's type definitions — rather than guessing — that the snake_case dictionary this repo already builds corresponds to types.GenerationConfig (the class backing a raw request's generation_config, not the higher-level wrapper the SDK's convenience method uses), that it declares a thinking_config field, and that the nested enum's values match this repo's lowercase vocabulary. Both batch roles currently seed NULL, so the key is omitted in practice today; the wiring exists for the first time an operator sets one.

5. The write API and the UI

One endpoint, two methods. GET /api/admin/llm-config returns all eleven roles merged with their code defaults — including thinking_levels, the vocabulary itself, so the web form never hardcodes the options. PATCH takes a partial map keyed by role slug and applies it in one transaction:

{"chat": {"model_id": "gemini-3-flash-preview", "thinking_level": "medium"},
 "image_alt": {"thinking_level": null}}

The probes run before the transaction opens — a small but important detail, so no database row lock is ever held across a network call to Google. The web panel computes a diff against the last-loaded state and sends only what changed, which is also what keeps it clear of the API's "reject an empty payload" rule.

A gotcha for anyone touching that panel again

The shared operator error helper flattens only one level of {field: [messages]}. This endpoint's errors are two levels deep — {role_slug: {field: [messages]}} — because they are keyed by role. Using the shared helper unmodified silently swallowed Google's actual message and showed a generic "(HTTP 400)" instead, defeating the entire point of the live probe. The fix was a small local flattener in the panel, deliberately leaving the shared helper untouched so no other operator screen was affected.

6. Fixing the plumbing underneath

With the store landed, the phase went back and repaired the environment layer it now sits on top of: the two consulting variables were finally added to both Compose files (they had never reached a container), and the two content variables were added to .dev.env (they had never existed). Because the database wins, these changes alter no behaviour today — they complete the fallback chain so that an outage degrades to something sensible.

7. The proof — and the thing that nearly shipped broken

The last slice wrote no product code at all. Its whole job was to prove the feature on a real running stack: switch a value through the real HTTP API, watch a real process pick it up, and point a container at an unroutable database to confirm it degrades instead of dying. All of it passed — 8 roles resolved from fallbacks, 0 exceptions, exactly 1 warning.

But it also caught the single most dangerous thing in the phase.

The deploy trap: the Celery workers are the real backend runtime

The rollout plan named three services: the Django backend, the FastAPI agent, and the Next.js frontend. But the three backend roles do not run in the Django container at all — they run inside celery_worker, the background job process. When the team checked, that container was running a 14-hour-old image with the new resolver module missing entirely.

The failure mode is the nastiest kind: completely silent. The operator saves a new model. The web page confirms it. The database has it. The agent honours it. And title generation and image enrichment go on using the old model forever, with no error anywhere. The verification only caught it because someone asked "but where does this code actually execute?" and re-ran the proof inside the worker.

Two corollaries were recorded with it: this is an image rebuild, not a restart (Compose builds images, it does not mount source — restarting a stale container changes nothing), and the same audit found the FastAPI agent was stale too.

That finding is now the first thing in the operations documentation, ahead of any "how to change a model" instructions — because a runbook that teaches the happy path before the deploy prerequisite teaches people to ship the feature dead.

Best practices & next steps

Runtime configuration that a human changes without a deploy is a well-trodden problem — it is essentially the same problem as a feature-flag system, and the same patterns apply.

Where this implementation aligns with prevailing practice

A local cache with a configurable TTL is the standard answer, not a shortcut. Unleash's guidance for feature-flag SDKs is that the client should "query the local cache, and ask the central service for updates in the background," with the cache holding a configurable time-to-live (Unleash feature-flag best practices — getunleash.io). AWS's dynamic-configuration guidance is the same shape: store the configuration in a local cache with a configurable TTL to cut API calls and cost, exposed as a single max-age knob (AWS Lambda Handler Cookbook, dynamic configuration — ran-isenberg.github.io). P44's LLM_CONFIG_CACHE_TTL_SECONDS is exactly that knob; its 30-second default is on the aggressive-freshness end of the usual range, which is a reasonable trade when the table is eleven rows and a human is waiting to see their change take effect.

Falling back to last-known-good rather than hard-failing is the recommended posture. AWS's Well-Architected reliability pillar frames it as turning hard dependencies into soft ones: components "should continue to perform their core function even if dependencies become unavailable," possibly serving "slightly stale data." It names "a parameter store is unavailable" as a worked example, prescribing soft-dependency caching or sane defaults baked into the image — and, pointedly, lists as an anti-pattern "invalidating or emptying local state as a result of a failed refresh" (AWS Well-Architected, REL05-BP01 — docs.aws.amazon.com). P44 does precisely this: a failed refresh keeps the previous snapshot, and the compiled-in DEFAULT_* constants are the "sane defaults included in the image" rung. Unleash makes the same argument from the product side — graceful degradation means falling back to cached data so that infrastructure degradation never becomes total application failure (Unleash on graceful degradation — getunleash.io).

Validating configuration on write is standard too. The AWS cookbook validates fetched configuration against a Pydantic schema before use, so a malformed value is caught rather than propagated (ran-isenberg.github.io, above). P44 pushes that validation one step earlier — to the moment of writing, where a human is present to fix it — and adds a live provider probe on top, which is stronger than schema validation alone because it catches a *well-shaped but nonexistent* model id that no schema could reject.

Where it deliberately diverges

It keeps environment variables rather than eliminating them. Strict twelve-factor says config belongs in the environment (12factor.net, Config). P44 demotes env to a fallback rung instead of deleting it, which is a considered divergence: twelve-factor's concern is deploy-time configuration, and it has little to say about values a non-engineer must change at runtime. Keeping env as the bootstrap and degradation path is what makes rung 3 of the ladder meaningful and what let the migration land in one step with zero behaviour change.

It uses no dedicated feature-flag or config service. No LaunchDarkly, no Unleash, no AWS AppConfig — just a table in the database the application already uses. For eleven rows read by two services in one deployment, an external service would add a network dependency, an SLA and a bill in exchange for capabilities (targeting rules, gradual rollouts, audit UIs) that nothing here needs. The trade shows up honestly in what P44 had to hand-build: the TTL cache, the degradation path, and the "log once per failure window" throttle are all things a mature SDK would have provided.

It refuses a generation-time fallback. Fail-open is the usual advice for flags, and P44 is fail-open about reading config. But it is deliberately fail-loud about a bad value: no silent substitution of a known-good model. That matches the Amazon Builders' Library caution that fallback paths in distributed systems are themselves a risk — they run rarely, so they are the least-tested code you own (Amazon Builders' Library, avoiding fallback — aws.amazon.com). Here the reasoning was more product-shaped: substituting a model would hide the misconfiguration and quietly change the bill.

Concrete next steps

  1. Show the operator the resolved value, not just the stored one. Today the panel shows what is in the table plus the code default. It cannot show what a given service is actually using right now — which, thanks to last-known-good caching, can legitimately differ during an outage. A small read-only echo endpoint on each service would close the loop and make the Celery-staleness class of bug visible in the UI instead of invisible. This was explicitly parked as out of scope; it is the most valuable follow-up.
  2. Make the deploy prerequisite mechanical rather than documentary. The "rebuild the Celery services too" rule currently lives in a runbook, which means it holds exactly as long as people read runbooks. A startup assertion — each service logging its resolver module version, or a health check that fails when the config module is missing — would turn a silent failure into a loud one.
  3. Add the rerank thinking level to the retrieval cache key. The ranked-result cache is keyed on the resolved rerank model, so a model change invalidates it for free; an effort-only change does not, so identical queries can be served at the old effort for up to five more minutes. Bounded and harmless today, but it is the one place where "the change took effect" is not quite true.
  4. Exercise the batch thinking-config path for real. It is unit-tested against the SDK's type definitions and is a no-op while both batch roles hold NULL. The first time an operator sets an effort on image_alt or text_enrichment it becomes live code that has never met the real API — worth a deliberate batch run at that moment.

Quiz

1. Why did the agent need a separate module to read the config instead of just adding a field to its settings object?

The @lru_cache decorator means the settings object is built once and reused forever. A value the operator must change without a restart has to be read outside that cached object entirely — which is exactly what app/llm_config.py exists to do.

2. During the live verification, a model id was changed through the API and the very next read in the same process returned the old value. Why was that treated as evidence of success rather than a bug?

Without that unchanged read, a value that differs 35 seconds later proves nothing — it could have come from a process that simply re-read the table for unrelated reasons. The unchanged read establishes that the cache was genuinely holding a stale value, so the later change can only have come from the TTL expiring.

3. The live probe rejects a save when the provider returns a 400 or 404, but allows the save when the probe fails with a timeout, a quota error, or a missing API key. What is the reasoning?

The distinction is between "the provider told us this id is bad" and "we could not ask." A 403 is deliberately on the allow side too: a key-scoping problem says nothing about whether the model id is valid.

4. Why does a NULL thinking_level mean "send no thinking parameter at all" rather than "send the lowest level"?

"Unset" and "explicitly lowest" are different instructions to the provider. Only "unset" is behaviour-neutral, which is what let all eleven rows be seeded at once without changing anything — and it also sidesteps models that reject a thinking level entirely.

5. A deploy refreshes the Django backend, the FastAPI agent and the frontend, but not the Celery services. What does the operator observe?

This is exactly why the deploy note leads the operations runbook. The three backend roles execute inside celery_worker, so a stale worker simply never runs the new resolver — no error, no warning, just the old models forever, while every visible surface reports success.
