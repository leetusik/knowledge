Chat context: rolling windows, compaction, budgets, and recall

Explainer #6 of the changple5 builder’s curriculum, Part B. A conversation can run for hours; a language model is handed a fixed slab of text and charged by the character. This is the machinery that decides, on every single turn, which slice of a long 미라클 chat the model reads verbatim, which part it reads only as a paragraph of Korean prose — and how the model can still go find the rest when the user says “아까 그거”.

Background

Explainer #5, A chat turn end to end, followed one POST /agent-api/chat/stream from the guard ladder through the LangChain agent, the Server-Sent Events, cancellation and replay. It walked past one door without opening it. Every turn rebuilds the model’s thread from the conversation Django stores — and the page said only “#6 explains which messages actually go in”. This is that page.

The question sounds trivial and is not. A 미라클 session is a normal chat: the user asks about 평상집 창업, the assistant answers with citations from the 창플 카페 corpus, they go back and forth about 임대료 and 인건비, and forty minutes later they are on message ninety. What exactly does the model see on message ninety?

Tokens, and why “just send everything” stops working

A token is the unit a language model reads and bills in — roughly a short word or a word-piece in English, and roughly one character in Korean. Every turn is a fresh, stateless call: the model remembers nothing between requests, so whatever it needs to know must be re-sent in that request. This is worth saying plainly because it is the root of everything below: a chat model has no memory. The application re-sends the conversation on every turn, and “memory” is a name for whatever the application chooses to re-send.

Re-sending everything has two costs, and only one of them is money.

  • Price and latency grow with the transcript. Ninety messages of Korean prose is on the order of tens of thousands of tokens, paid on every turn, plus the time to transmit and process them before the first word of the answer comes back.
  • Attention degrades. A model given a very long context reliably attends to its beginning and its end and gets vaguer about the middle. A transcript that keeps growing does not just get more expensive; past a point it gets worse at the thing it was supposed to help with.

So every serious chat application eventually needs a policy for what to drop. changple5’s policy has a name in the code — the rolling window — and this page is about how it is computed, where it is stored, who moves it, and what escape hatches exist when the model needs something the window has dropped.

What changple5 did before, and why it was replaced

The pre-P61 posture was the obvious first thing to build, and it is worth understanding because its three weaknesses shaped the design that replaced it:

  1. Load the whole conversation, every turn. The route fetched the full history from Django and handed it all to the agent.
  2. Summarize only when a token budget tripped. A 200,000-token estimate was computed per turn; if the context blew past it, an LLM call summarized the older part of the history right there, on the user’s turn, and the newest six messages were kept verbatim.
  3. Persist nothing. The summary was a local variable. The next turn threw it away and, if the budget tripped again, paid for the same summary again.

Three things are wrong with that. The trigger is a token estimate, which is invisible to the product and impossible to reason about (“how many turns until this gets summarized?” has no answer). The summarization runs on the critical path, so the unlucky turn that crosses the line pays an extra blocking model call before its answer starts. And because nothing is persisted, that cost recurs, and every recomputation is a fresh chance for the summary to come out different from the one the previous turn used.

P61 replaced it with the scheme this page teaches: a message-count window (predictable), compacted by a background task after the turn (off the critical path), whose result is persisted on the session row (paid once, stable across turns). The token budget survives underneath it as a second-line safety valve, because a message count cannot see a single pathological 40,000-character message.

Skip if you know it Facts from earlier explainers this page builds on. Each is established, not re-derived here:

  • #5 — the checkpointer holds the run, Django holds the conversation. Every turn deletes the LangGraph thread and rebuilds it from backend history, emitting Human/AI messages only. A prior turn’s documents therefore survive as an id-free annotation, never as a tool result.
  • #5 — the system prompt is a cached prefix. The static Korean rulebook sits at the front so Gemini can cache it; only two slots at the tail change per turn. One of those slots is the rolling summary, which is why it lands where it lands.
  • #5 — two chat tools are budget-exempt (search_conversation_history and search_cited_documents) while the three retrieval tools share a 4-call budget; and a turn that arrives while a compaction is running emits a compacting status frame.

Intuition

A pane that slides, and a bookmark that never moves backwards

Picture the conversation as a strip of message cards laid left to right, oldest first. The scheme has exactly two moving parts:

  • a bookmark — the code calls it the watermark — that marks the last message already folded into prose;
  • one paragraph of Korean prose — the rolling summary — covering everything to the left of the bookmark.

What the model is handed each turn is: the summary, then every message to the right of the bookmark, verbatim. That is the whole read rule. Everything else in this page is about how the bookmark moves.

It moves in fixed steps, on a fixed trigger. The two numbers are ROLLING_WINDOW_MESSAGE_LIMIT = 20 and ROLLING_EVICTION_BATCH_SIZE = 10: when the number of messages to the right of the bookmark reaches 20, the oldest 10 of them are folded into the summary and the bookmark jumps forward over them. The window is therefore never wider than 19 verbatim messages in steady state, and never narrower than 10.

Odd-numbered messages are the user’s, even-numbered ones the assistant’s — the backend enforces strict user/assistant alternation (#4). That is why the bookmark landing on message 10 is a happy accident worth noticing: the seam falls between a completed turn and the next one, never through the middle of a question-and-answer pair.

Why the bookmark is an identity and not a count

The lazy implementation stores “the first 10 messages are summarized” — a number. It is wrong here, and the code says so in a comment. changple5 has retract-tail (#4): the owner of a conversation can delete the last [user, assistant] pair to redo a bad turn. Deleting two rows from the end silently shifts every count-based boundary. The stored watermark is therefore a message identity: the pair (created_at, id) of the last summarized message, compared as a tuple. Since it is compared rather than dereferenced, it keeps working even if that very message is later retracted — a deleted row still has a position in the ordering.

The idea in one line. Store where you got to, not how many you did. A position expressed as a count is invalidated by any edit before it; a position expressed as an identity is not.

Merge, never re-summarize

When the bookmark moves a second time, the system does not re-read messages 1–20 and write a fresh summary. It hands the model the previous summary plus the 10 newly evicted messages and asks for one merged summary. This matters for three reasons:

  • Cost is constant per boundary. Summarizing message 1 again on every boundary would make a long conversation quadratically expensive.
  • The old text is already gone. After the first merge, messages 1–10 exist in the database but nothing re-reads them; the summary is the only representation the model will ever see of them again.
  • It degrades gracefully. With no previous summary the same prompt is a plain “summarize these messages”, so the first boundary and the tenth run the same code path.

The trade is honest and worth stating: a merged summary is a summary of a summary of a summary. Detail decays with distance, deliberately. The recall tool below exists precisely because sometimes the user wants a detail that decayed.

Reading the window at any moment

Given the two numbers, you can predict the state of any session. The only input is how many messages sit to the right of the bookmark:

Session stateRaws after the watermarkWhat the model getsCompaction due?
12 messages, never compacted12no summary + 12 verbatimno (12 < 20)
20 messages, never compacted20no summary + 20 verbatimyes → evict 1–10
23 messages, watermark on #1013 (#11–#23)summary of 1–10 + 13 verbatimno (13 < 20)
30 messages, watermark on #1020 (#11–#30)summary of 1–10 + 20 verbatimyes → evict 11–20, bookmark to #20

Two rows deserve a note. The third row’s odd message count is not a typo: a turn writes the user’s message before the model runs (#4), so a session sitting mid-turn genuinely has an odd number of stored rows. And the last row is the one that makes this design cheap to operate: an over-wide window is legal. Nothing is broken while 31 raws are in flight; the next compaction simply evicts two batches instead of one and catches up in a single pass.

Three layers, not one mechanism

It is easy to conflate the three things this page covers. They answer different questions and fire at different times:

The design point to hold on to. The window and the recall tool disagree about visibility on purpose. The window decides what the model reads by default, and it is aggressive because most turns do not need message 3. The tool exists so that the rare turn that does need message 3 can go get it — on demand, scrubbed and capped, instead of paying for the whole prefix on every turn just in case.

Code

Six stops, in the order the machinery engages on a real turn: the arithmetic, where the summary lives, the task that writes it, the token budget beneath it, the recall tool beside it, and finally what all of this does to citations.

1. The arithmetic — apps/agent/app/chat/rolling_window.py

195 lines, zero I/O, no settings, no LLM, no database. Everything in it is a function of “the ordered messages” plus “the watermark”. It is its own module because two callers need the same answer and must never disagree: the read half that builds the model’s context, and the write half that decides what to compact. Its docstring defines the vocabulary the rest of the codebase uses:

*watermark* — the last message covered by the persisted rolling summary,
identified by ``(created_at, id)`` (never a count: retract-tail deletes trailing
message pairs, so any count desyncs — P61 F1). Comparisons are on the tuple, so
a watermark whose row has since been deleted still orders correctly.

*post-watermark raws* — the messages the model still sees verbatim.

The two constants, and the frozen dataclass that carries the bookmark:

ROLLING_WINDOW_MESSAGE_LIMIT = 20     # rolling_window.py:40
ROLLING_EVICTION_BATCH_SIZE  = 10     # :44

@dataclass(frozen=True, slots=True)   # :47
class RollingSummaryWatermark:
    message_id: UUID | None = None
    created_at: datetime | None = None

The read half: select_post_watermark_messages (:88)

Given the full history and a watermark, return everything strictly after it. The comparison is on a tuple, built by _order_key (:79), which pairs the timestamp with the id as a string so two messages written in the same millisecond still have a total order:

watermark_key = _order_key(watermark.created_at, watermark.message_id)
return tuple(
    message
    for message in ordered_messages
    if _order_key(message.created_at, message.id) > watermark_key
)

Two fallbacks keep the function total — it has no failure mode that raises. A watermark with no timestamp (or a history whose rows predate the identity widening) is located by id instead; a watermark that cannot be resolved at all returns every message. That last choice is the interesting one, and it is the safe direction: an unresolvable bookmark means the model gets too much history, never too little. Silently dropping messages the model has no summary for would be the real bug.

Never split a turn: _snap_to_turn_boundary (:126)

while (
    evict_count > 0
    and post_watermark_messages[evict_count - 1].role != "assistant"
):
    evict_count -= 1

The seam between “summarized” and “verbatim” must not fall between a user question and its answer — that would leave the model an orphan answer whose question exists only as a clause in a summary. Because the backend alternation is user-first, the 10th, 20th and 30th message are always assistant halves, so in a well-formed history this loop is a no-op. It is asserted rather than trusted, and the snap goes backwards (evict 9 instead of 10): snapping forwards could leave fewer than 10 raws in the window.

The write half: plan_rolling_compaction (:147)

This is the whole decision, and it is eight lines of arithmetic:

post_watermark_messages = select_post_watermark_messages(messages, watermark=watermark)
if len(post_watermark_messages) < window_limit:
    return None                       # nothing due

evict_count = 0
remaining = len(post_watermark_messages)
while remaining >= window_limit:      # catch-up: expand by whole batches
    evict_count += eviction_batch_size
    remaining   -= eviction_batch_size

evict_count = _snap_to_turn_boundary(post_watermark_messages, evict_count)
if evict_count < 1:
    return None

Trace it on the two interesting inputs:

Post-watermark rawsLoopEvictedRetainedNew watermark
20 (the normal boundary)20 ≥ 20 → evict 10, remaining 10; 10 < 20 stop1010the 10th raw
31 (a job was lost)31 ≥ 20 → evict 10, remaining 21; 21 ≥ 20 → evict 20, remaining 11; stop2011the 20th raw

The loop is the entire recovery story for a lost background job. There is no retry queue anywhere in this subsystem; instead, the eviction slice expands until the remainder is back under the window, so one task run clears every missed boundary at the cost of one model call rather than one per boundary.

The returned RollingCompactionPlan carries the evicted slice, the retained slice, and the new watermark — which is always the last evicted message’s identity. If that message has no id, the plan is None: nothing persistable, so leave the bookmark where it is and let the next turn re-trigger. That refusal-to-guess appears at every layer of this subsystem.

2. Where the summary lives, and how a turn reads it

Three columns on the session row

apps/backend/conversations/models.py:188–213 adds exactly three nullable fields to ConversationSession — and the help_text on the middle one is the design decision written into the schema:

rolling_summary                 = models.TextField(null=True, blank=True)
summarized_through_message_id   = models.UUIDField(null=True, blank=True)
    # "public_id of the last message folded into `rolling_summary`.
    #  A message identity, NOT a foreign key -- the row may later be
    #  retracted, and the watermark must survive that."
summarized_through_created_at   = models.DateTimeField(null=True, blank=True)

A ForeignKey would have been the reflexive choice and would have been actively wrong: a foreign key with on_delete either forbids the retraction or nulls the watermark out. A bare UUID plus its timestamp is a coordinate, and coordinates survive deletions.

The write, and a subtle product bug it avoids

ConversationSession.record_rolling_summary (models.py:264) writes through a queryset .update() instead of .save(), and the docstring explains why:

`QuerySet.update()` rather than `.save()` is deliberate: `updated_at` is
`auto_now` and the owner's history rail orders by `-updated_at`, so a
`.save()` here would float the session to the top of the rail for a
background compaction job the user never triggered.

This is the kind of detail that only shows up in production: a correct-looking write that would have made old conversations mysteriously jump to the top of the sidebar minutes after the user closed them. Compare with append_finalized_message, which touches updated_at on purpose — there the float is the desired behaviour.

The internal endpoint: rolling_summary.py

The agent cannot write Django’s tables (#1: the bridge grants SELECT only), so the summary lands through an HTTP endpoint reserved for the agent:

POST /api/conversations/internal/<uuid:nonce>/rolling-summary   # urls.py:71
     authentication_classes = [AgentServiceTokenAuthentication]   # views.py:868
     body: {owner_user_id, summary, summarized_through_message_id}

All the logic is in apps/backend/conversations/rolling_summary.py (apply_rolling_summary, :38), inside one transaction holding select_for_update() on the session. It refuses three things and accepts everything else:

AA session that is not the owner’s, or is soft-deleted → 404. The scope is the lookup (#4).
BA non-default session → 409 not_default_session. 컨설팅 owns its own lifecycle and is out of scope by construction.
CA watermark message that does not belong to this conversation → 409 unknown_watermark_message. This is the retract-tail race: the tail was deleted while the summarizer was thinking, so the summary describes text that no longer exists. Refuse it.
DA watermark that does not strictly advance the stored one → 200 with applied: false. Not an error: a late or duplicate job, whose work is simply redundant.
EOtherwise → record_rolling_summary inside the same transaction.

Rung C is also why the payload deliberately does not carry summarized_through_created_at. The backend looks it up from the message row itself:

The watermark's ``created_at`` is resolved server-side from the message row
rather than taken from the payload: the backend owns message ordering, and
requiring the row to still exist means a compaction whose tail was retracted
mid-flight is refused instead of persisting a summary of retracted text.

Rung D is the concurrency rule in one comparison, rolling_summary.py:87:

applied = (
    session.summarized_through_created_at is None
    or watermark.created_at > session.summarized_through_created_at
)

Two racing compaction jobs cannot corrupt each other, because the row lock plus this strict advance means a summary can only ever be stored together with a watermark that is further along than the one it replaces. The loser is told applied: false and simply stops. The agent-side caller mirrors that in its own result type, backend.py’s BackendRollingSummaryWriteResult: “applied=False is a success … The caller logs it and moves on — never a retry.”

The read half, and the surprising shape the summary takes

On the agent side the three fields ride through AssembledChatContext (chat/context.py:29), copied straight off the conversation detail. Then _resolve_rolling_window (chat/agent.py:730) turns them into the pair the rest of the code wants:

persisted_summary = (assembled_context.rolling_summary or "").strip() or None
if persisted_summary is None:
    return None, assembled_context.verbatim_messages      # nothing compacted yet

watermark = RollingSummaryWatermark(
    message_id=assembled_context.summarized_through_message_id,
    created_at=assembled_context.summarized_through_created_at,
)
return persisted_summary, select_post_watermark_messages(
    assembled_context.verbatim_messages, watermark=watermark
)

Note what does not happen: the summary is never recomputed. It is injected exactly as persisted — “that is the whole point of persisting it”, says the docstring.

Now the part worth pausing on. The summary does not become a message. Follow it through build_chat_agent_checkpoint_state (agent.py:883): it is written to a LangGraph state channel called conversation_summary, and the only thing that ever reads that channel is the system-prompt builder, build_chat_agent_system_prompt (:934), which drops it into a named slot at the very end of the prompt (prompts.py:288):

[Conversation summary]
{conversation_summary}

[Current selected content]
{selected_content_block}

So the model’s context for a compacted session is: one system message ending in the summary, then Human/AI messages for the raws, then this turn’s question. The summary is framed as instruction-side background, not as something anyone said. Two consequences fall out:

  • Because the middleware rebuilds the system prompt from state on every model step (#5), a summary refreshed mid-turn is picked up without touching the message list.
  • Those two slots sit at the tail of the prompt because everything before them is the static Korean rulebook that Gemini caches as a prefix. Putting a per-turn value earlier would invalidate that cache on every chat turn — the constraint #5 flagged, and this is the code that lives inside it.

When the messages are absent entirely (a compacted session whose raws are all gone), the function short-circuits and returns summary-only. Otherwise the windowed messages go through _build_chat_agent_history_messages (:716), which emits HumanMessage / AIMessage and nothing else — the P51 guarantee from #5 that a prior turn can carry no tool output, no document body and no post id.

3. The compaction task — apps/agent/app/chat/rolling_compaction.py

460 lines that never appear on a user’s critical path except for one Redis GET. Its docstring names three disciplines, and every function in the file is one of them applied somewhere:

1Nothing on the critical path. The pre-check is arithmetic over data the turn already has in memory. A turn that does not cross a boundary pays a list comprehension.
2Genuinely detached. A client stop cancels the request task, and anything awaited in a stream generator’s finally dies with it. The compaction task is created on the loop and held by a module-level strong reference, never awaited by the stream.
3Never raises, never retries. Transport, LLM, Redis, a refused write — every failure family is caught and logged. A lost job leaves the watermark where it was and the next turn re-triggers. No queue, no retry bookkeeping, no dead letter.

The trigger, and where it sits

There is exactly one call site, in the default-chat stream generator, after the assistant message is durably persisted (api/routes/chat.py:1541). Its comment is worth reading as a specification:

# P61.S3: the turn's assistant message is durably persisted at this
# point, so the post-turn message count is final. This is the ONLY
# compaction trigger ... it never raises, never awaits backend work here,
# and deliberately does NOT fire on the failure/fallback paths above --
# a failed turn simply leaves the watermark for the next one.
if user_id is not None:
    schedule_rolling_compaction(...)

The user_id is not None guard skips anonymous trial turns (a guest is capped at two assistant turns, orders of magnitude below the boundary, and compaction is owner-scoped by its endpoint contract). schedule_rolling_compaction (:427) then does the cheap check and, if it passes, spawns the task:

task = loop.create_task(run_rolling_compaction(...))
_BACKGROUND_COMPACTION_TASKS.add(task)                 # module-level strong ref
task.add_done_callback(_BACKGROUND_COMPACTION_TASKS.discard)

That two-line strong-reference dance is not decoration. asyncio keeps only a weak reference to a task; a bare create_task(...) whose result nobody stores can be garbage collected before it ever runs. The error_reporting module established the pattern in this codebase — explainer #16 teaches background work in general.

The pre-check itself, is_rolling_compaction_due (:232), has one subtlety encoded in a constant:

_CURRENT_TURN_MESSAGE_COUNT = 2   # :75

return (len(post_watermark_messages) + _CURRENT_TURN_MESSAGE_COUNT) >= window_limit

The context was assembled from a detail fetched before this turn’s user message was written, so the post-turn count is “what we fetched, plus our own pair”. And the check is deliberately optimistic: it decides only whether the task is worth starting. The authoritative decision is made again inside the task against freshly fetched data.

Re-fetch, don’t reconstruct

run_rolling_compaction (:341) begins by fetching the conversation detail again. The docstring argues the alternative down explicitly: reconstructing the post-turn history by appending two ids to the stale in-memory list would be free, but it would “silently compact retracted or already-summarized text whenever it guessed wrong”. The re-fetch costs the user nothing (it is off the critical path) and is authoritative — it sees a watermark another worker just advanced and a tail another request just retracted.

One credential detail lives here, and it is a nice example of a boundary being narrower than it looks: the task re-fetches with the turn’s own bearer JWT, not the service token, because the backend hard-scopes service-token conversation reads to guest sessions. It then writes with the service token, because the internal endpoint takes no user identity beyond the owner_user_id field. One task, two different credentials, each the minimum for its call.

One boundary at a time: _compact_once (:292)

plan = plan_rolling_compaction(messages, watermark=watermark)
if plan is None:
    return None

# The merge is a BLOCKING sync Gemini call; running it inline would freeze
# every other stream on this worker.
summary = await asyncio.to_thread(
    build_rolling_merged_history_summary,
    previous_summary=previous_summary,
    evicted_messages=plan.evicted_messages,
    settings=settings,
)
result = await write_rolling_summary(...)

The asyncio.to_thread is mandatory, not stylistic. The agent is a single async process serving every concurrent chat (#1); a synchronous network call made directly on the event loop freezes all of them for its duration. The loop around _compact_once is capped at MAX_ROLLING_COMPACTION_PASSES = 3 — and normally runs exactly once, because the planner’s expanding slice already cleared every missed boundary. The cap only bounds a pathological re-plan, where each extra pass would cost another model call.

The summarizer — chat/compaction.py

GeminiChatHistoryCompactor (:64) is a small, ordinary structured-output client, and the ordinariness is the point:

  • Structured output. with_structured_output(_GeminiChatHistoryCompactionSchema, include_raw=True) — a one-field pydantic model whose Field(description=...) is Korean and tells the model what a good summary preserves: goals, constraints, decisions already made, open questions, relevant selected content and cited documents.
  • Live-configurable model and thinking level. from_settings resolves resolve_role_model(..., role=ROLE_CHAT_HISTORY_COMPACTION, default="gemini-3.1-flash-lite") and resolve_role_thinking_level(...) — the operator-editable rows from #2. The role is registered as chat_history_compaction / 채팅 히스토리 압축 in operators/llm_roles.py:122, so the model behind compaction can be changed in the console with no redeploy.
  • Retries are owned elsewhere. max_retries=1 on the client, with call_with_retry as the single 429 authority.

What gets sent is built by serialize_older_history_messages (:187) — a flat [Message n] / role / content rendering, with selected-content titles and cited documents appended per message, and visible citation markers stripped from any message that carried citations. And the merge itself, build_rolling_merged_history_summary (:253), is a two-branch prompt in prompts.py:295. With a previous summary the Korean rule is explicit:

- 아래에는 지금까지의 대화를 정리한 `이전 요약`과, 그 이후에 오간
  `추가 대화 기록`이 함께 주어집니다.
- 둘을 하나의 요약으로 합치세요. 이전 요약에만 있는 내용도 여전히
  유효하면 빠뜨리지 말고, 추가 기록이 그 내용을 바꿨으면 최신 내용을
  따르세요.

— merge the two into one, keep what is still true, prefer the newer where they conflict. Without a previous summary the same function degrades to a plain “summarize this older history”. One code path, two boundaries.

The Redis flag, and the turn that arrives mid-compaction

Compaction takes a model call — a second or two, sometimes more. A user who fires the next question immediately would otherwise be answered from a context that is about to be replaced. The fix is one key:

COMPACTION_IN_FLIGHT_KEY_PREFIX = "agent:chat:compaction"   # run_registry.py:22
COMPACTION_IN_FLIGHT_TTL_SECONDS = 180                      # :30
    # a crash ceiling, not a deadline: the task clears the key in a `finally`,
    # so this only matters when the worker dies mid-compaction.

A separate prefix from agent:chat:run:*, deliberately: the registry’s active-run scan walks that namespace and must never trip over a compaction marker. The task sets the key when it starts (_mark_in_flight, :258) and clears it in its finally (_clear_in_flight, :275) — and both of those helpers swallow every Redis error, because a marker is an optimization and must never fail a turn.

The read side is the mirror image, and it is the only part of this subsystem that runs while a user waits. is_rolling_compaction_in_flight (:131) answers no on any failure whatsoever — Redis down, no reader wired, anything — because a false “no” merely means the turn proceeds on a slightly stale context, which is a state the system already tolerates. Then wait_for_rolling_compaction (:157) polls:

COMPACTION_WAIT_CEILING_SECONDS       = 10.0   # a latency bound, not a correctness one
COMPACTION_WAIT_POLL_INTERVAL_SECONDS = 0.25   # ~40 GETs on one key, worst case

It returns True only if the marker was observed cleared within the ceiling — the one case where re-reading is worth a round trip. Timeout, Redis failure, no reader: all False, all meaning “carry on with what you have”. The one exception it re-raises is asyncio.CancelledError: a client stop is not this function’s to absorb.

The wait lives inside the stream generator, after the preparing phase and before the agent runs (chat.py:1283) — because SSE frames only exist there, and because the pre-stream status beat only renders while the answer body is still empty. Three details in that block repay attention:

  • After the wait the run record is put back to preparing with no second frame: status frames are emit-once, and a client reconnecting mid-answer must not read a stale compacting.
  • The wait is the one place a turn can sit idle for seconds, so the disconnect and cancel signals are re-checked immediately afterwards, before spending a model call.
  • The re-read, _refresh_rolling_summary_state (chat.py:836), is a full detail fetch but grafts on only the three rolling fields. The fresh message list is discarded on purpose: it now contains this turn’s user message, which the agent already receives separately, and re-assembling from it would hand the model the same question twice.

The posture, stated once. Every branch in this subsystem — marker write, marker read, wait, merge, persist, re-read — degrades to “proceed with the previous summary and the extra raws”. That state is explicitly legal (the 21–29 raw over-window case), which is what lets every failure path be a one-liner instead of a recovery protocol. Design the tolerated degraded state first, and the error handling writes itself.

4. The token budget — apps/agent/app/chat/budget.py

A message count cannot see size. Twenty short messages and twenty pasted 사업계획서 are the same number. So the pre-P61 budget survives beneath the window as a second-line valve:

DEFAULT_CHAT_CONTEXT_BUDGET_TOKENS = 200_000     # budget.py:19

Two estimators, and why the cheap one won

GeminiChatContextTokenEstimator (:29) is exact — it calls Gemini’s token counting endpoint. It is also a network round trip on every turn, so it is no longer the default; it is kept injectable for calibration work. LocalHeuristicChatContextTokenEstimator (:116) is what actually runs:

_HEURISTIC_CJK_TOKENS_PER_CHAR   = 1.0     # Hangul / Kana / CJK: ~1 token per char
_HEURISTIC_OTHER_TOKENS_PER_CHAR = 0.25    # everything else: ~4 chars per token

The naive “characters ÷ 4” heuristic every tutorial teaches would under-count Korean by roughly a factor of four, which for this product is the whole corpus. _is_cjk_char (:100) enumerates the actual Unicode ranges — Hangul syllables, four Jamo blocks, Hiragana and Katakana, two CJK ideograph blocks, and the halfwidth/fullwidth forms — and the class is otherwise a single loop with no dependencies and no I/O. The estimate is deliberately conservative rather than exact: it guards a 200k threshold, not a bill.

(The corresponding operator role, chat_context_token_estimation, is labelled 채팅 컨텍스트 토큰 추정 (현재 미사용) in operators/llm_roles.py:114 — the console is honest about the fact that the remote estimator is not on the hot path any more.)

What gets measured is render_chat_context_preview (:216): a flat text rendering of the current user message, the verbatim messages, the selected content and the retrieval results. Not the real prompt — a faithful stand-in for it, cheap to build.

Where it trips: the tail of _build_checkpointed_chat_history

The estimate is taken on the windowed context, never the fetched one. The code even rebuilds a temporary context to make that true, and says why:

windowed_context = (
    assembled_context
    if verbatim_messages == assembled_context.verbatim_messages
    else replace(assembled_context, verbatim_messages=verbatim_messages)
)
# the route keeps history_message_limit=None, so pre-watermark messages are
# still in assembled_context and would otherwise be counted TWICE --
# once as raws, once inside the summary.

Then four branches, in order (agent.py:795–843):

ConditionWhat the model gets
the estimator itself raisedpersisted summary + the newest DEFAULT_CHAT_HISTORY_MESSAGE_LIMIT = 6 messages — the conservative fallback
estimated_tokens ≤ 200_000 (the overwhelmingly common case)persisted summary + the whole window. No LLM call at all.

over budget with more than 6 rawsbuild_rolling_merged_history_summary(previous_summary=persisted_summary, evicted_messages=window[:-6]) → summary + the newest 6

Two things to notice about that last branch. First, it rolls the persisted summary forward rather than recomputing from scratch — the same merge function the background task uses, so the valve can never throw away work the task already paid for. Second, and easy to miss: the inline merge is not persisted. Nothing in _build_checkpointed_chat_history writes to Django; only the background task does. So the valve is a per-turn repair that runs again on the next turn if the pathological message is still inside the window — correct, and honest about which component owns the write. If the merge itself fails, the code falls back to the persisted summary, because dropping it would hand the model strictly less context than it already had.

5. Recall — apps/agent/app/chat/session_search_tool.py

First, why the route fetches everything

build_assembled_chat_context (chat/context.py:53) takes a history_message_limit and slices the tail off the history when it is set. The default is 6. The chat route passes None (chat.py:463), i.e. give me the whole conversation.

That looks like a contradiction — why fetch 90 messages to send 13? It is the enabling decision for everything in this section. The windowing happens later, at checkpoint build, so between the fetch and the model call there is a moment where the full session sits in memory, already parsed, already carrying every message’s citations. Two features are built entirely out of that fact, and neither needs a new endpoint, a query or a round trip: the recall tool here, and the cited ledger below.

(DEFAULT_CHAT_RETRIEVAL_LIMIT = 4 in the same module is a different kind of constant — its own comment marks it “NOT the live per-call retrieval cap … quarantined, not deleted”, kept only because two test suites depend on it. The real cap is operator-tunable at runtime. Reading a constant is not the same as reading the behaviour.)

The tool

search_conversation_history (:351) is a LangChain tool bound on every default-chat turn. Its docstring is its API — the model reads exactly this Korean text when deciding whether to call it:

지금 이 대화에서 앞서 오간 사용자·어시스턴트 메시지를 검색합니다.

오래된 대화는 대화 요약에만 남아 있을 수 있습니다.
사용자가 앞선 대화를 가리키면(예: "내가 아까 말했잖아", "아까 그거",
"전에 얘기한 그 브랜드") 기억으로 답하지 말고 이 도구로 원문을 찾으세요.

Mechanically it is the least clever component on this page, and that is the design: a substring scan over a list already in memory. No embeddings, no database, no model call, no network.

1_resolve_keywords (:173) lowercases the query and splits it on whitespace, capped at MAX_SESSION_SEARCH_KEYWORDS = 6. Substring matching, not tokenization — because Korean particles mean the user’s earlier wording is rarely an exact token match (“카페” vs “카페를”), and a substring absorbs the particle.
2_scrub_message_content (:145) cleans each message before searching it (see below).
3_collect_matches (:211) records, per matching message, how many distinct keywords hit, its position, and messages_ago — counted so that the newest stored message is 1.
4_build_excerpt (:196) cuts a SESSION_SEARCH_EXCERPT_CHARS = 300 window centred on the earliest hit, with ellipses.
5_select_matches (:256) keeps the strongest MAX_SESSION_SEARCH_MATCHES = 5, then emits them oldest-first.

Three of those steps encode a ruling that is worth more than the mechanism.

Scrub before searching, not before emitting. Past message text can carry visible [3] citation markers, internal [post:51927] markers, and (in old conversations) a prior-turn annotation. All of it is stripped up front, so “an excerpt window can never be cut around a marker that is about to disappear — and no unscrubbed byte has a path to the output at all”. The tool echoes conversation text back into the model’s context; if a post id survived that trip, the P51 this-turn citation guarantee would have a hole in it. The guidance string sent alongside the results says the same thing to the model in Korean: 창플 문서가 아니므로 인용 마커는 붙이지 마세요 — this is not a document, do not cite it.

Bounded output. Five matches × 300 characters, with SESSION_SEARCH_MAX_TOTAL_EXCERPT_CHARS asserted by a test. Otherwise a deliberately broad query (“아”) would drag the whole compacted prefix back into the context and undo exactly the saving compaction just made.

Ties break to the OLDEST. This one was flipped after live testing. The newest 10–19 messages are always raw in the model’s window, so the tool exists for the older, compacted-away specifics. On a one-word query every match ties on keyword count, and the tie-break alone decided the five slots — handing back five recent mentions, including the user’s own question, and pushing out the original one “아까” actually meant. Preferring the oldest also subsumes a “prefer pre-watermark matches” rule, since every compacted-away message is by definition older than every retained one — which is why this tool never reads the watermark at all.

The return type is a Command, and that is the budget exemption

The tool returns a LangGraph Command (:311) whose update carries exactly two keys:

update = {"messages": [ToolMessage(content=json.dumps(payload, ensure_ascii=False), ...)]}
if status == "ok":
    update[CHAT_AGENT_SESSION_RECALL_STATE_KEY] = True   # "session_recall_used"
# NOTE: no `retrieval_call_count` key, EVER.
# That omission is the entire budget exemption, and it is pinned by a test.

Recall #5: the 4-call search budget is enforced by each retrieval tool incrementing retrieval_call_count in the shared state. A tool that never writes that channel is exempt — not by a flag or an if, but by the shape of what it returns.

The session_recall_used marker exists for a subtler reason. A recall answer is grounded in the conversation but cites no documents, so the ungrounded-memory gate from #5 (“you answered from memory with no sources — refuse”) used to swallow perfectly good recall answers and replace them with a canned refusal — observed twice on the live stack. The marker is the one bit the gate reads to know better. Two details in how it is written are the actual lesson: it is set only on status: "ok" (a blank query, an empty result and an unavailable context all deliver no grounding, so those turns stay under the gate), and it is written True and never False, so a second, empty-handed call cannot un-mark a turn that already recalled something.

Finally, four status values, each with its own Korean guidance line, because the difference matters to the model: ok, empty_results (“the phrase is not in this conversation — ask, do not invent”), invalid_query, and unavailable (“I could not check”, which is not the same claim as “it never happened”). And the whole body is wrapped in a bare except Exception that degrades to unavailable: the tool-call middleware turns any tool exception into a failed turn, and a memory lookup must never be able to do that.

6. Citations across turns — the ledger and the markers

One thing survives compaction that is not text: the record of which documents this session has already cited. Two modules own it.

cited_ledger.py — what this session has cited

Built from the same in-memory full history, with the same zero-I/O posture, build_session_cited_ledger_from_messages (:292) walks every message’s cited_documents / cited_content rows — the citation side-tables from #4 — and accumulates a SessionCitedLedger (:131): one entry per id, in first-cited order, carrying the title, the first citation’s [k] slot, how many messages cited it, and how many messages ago it was last cited. Three rulings inside it are the interesting part:

  • Posts and contents are separate namespaces. A 창플 카페 post id and a published 미라클 content id are never the same kind of thing, so an id collision across the two is not a collision at all.
  • Titles take the most recent non-empty value; positions keep the first. A title backfilled later is a better label, but a later blank must never erase a good earlier one.
  • Metadata only. No bodies, and no guarantee the document is still eligible; a caller that wants either must re-fetch by id.

And the property that ties it to this page: the ledger is unaffected by the window. Because compaction happens later, at checkpoint build, the ledger still sees citations from turns the rolling window has already summarized away. The session’s citation history outlives the session’s visible history. Its consumer is the cited retrieval arm, cited_retrieval_tool.search_cited_documents — a tool that re-materializes an already-cited document so it becomes citable again this turn. That arm is explainer #7’s subject; here it is a surface with one relevant property, the same one as recall: it writes no retrieval_call_count, so it too is budget-exempt.

citations.py — two marker vocabularies

There are two kinds of citation marker in this system and confusing them is the source of a whole family of bugs:

InternalVisible
form[post:51927], [content:19], and the grouped/shorthand variants [post:5, post:13] / [post:5,13][1], [2] …

who sees itnobody — it is rewritten before the user or the database ever sees itthe user; the number is also the citation’s position in the ordered list the web renders

render_citation_markers assigns sequential numbers in first-mention order across one numbering space shared by both corpora, so [content:19][post:51927] renders [1][2]. Ids that are not in the turn’s valid set are dropped, and when a whole group is dropped the whitespace that introduced it is dropped too — otherwise the answer ships an orphan “ .”.

Doing this while streaming is the interesting engineering. Tokens arrive in arbitrary chunks, so [post: can end one chunk and 51927] begin the next. CitationMarkerStreamParser (:535) holds back an unterminated marker in a pending buffer and emits everything before it; _consume_internal_citation_marker (:231) is a small hand-written parser returning complete / partial / invalid, and the two prefixes were chosen to differ in their first character so a partial match is never ambiguous. Trailing spaces get their own second buffer, so that a marker arriving on the next chunk can still consume the space that introduced it. InternalCitationStripper (:499) is the same chunk-boundary machinery with the opposite job — used where citations are not allowed at all, such as the 컨설팅 follow-up stream.

What a prior turn’s citation looks like to the model

The last piece closes the loop with #5. When the window keeps a message that carried citations, _format_message_context (agent.py:657) rewrites it: the visible markers are stripped, and the documents come back as an annotation with a source label and a title — and no id:

(이전 턴 참고 자료, 인용 불가: 창플 카페 "평상집 임대료 계약 전에 확인할 것들")

The label constant is PRIOR_TURN_REFERENCE_ANNOTATION_PREFIX (citations.py:45), defined next to the stripper that removes it so the two can never drift. The comment records what the previous form cost: it carried post:<id>="<title>" pairs, which was “both the standing invitation to cite out-of-map ids and, copied verbatim into an answer, the visible leak the operator reported”. The rule it enforces is P51’s: citation is a this-turn property. A document is citable only if this turn’s retrieval put it in this turn’s document map. A compacted-away citation, a citation from message 4, a citation the model remembers — none of them are citable. The only routes back are retrieving the document again, or asking the cited arm to re-materialize it. The gate that enforces the rule at answer time belongs to explainer #11.

Putting it together: what the model sees on message ninety

The question the Background opened with now has a mechanical answer. On a session with 90 stored messages and a watermark on message 80:

  • system prompt — the cached Korean rulebook, then [Conversation summary] with the merged prose covering messages 1–80, then [Current selected content].
  • messages — HumanMessage/AIMessage for messages 81–90, verbatim except that any citations they carried are now id-free annotations, then this turn’s question.
  • available on request — search_conversation_history over all 90, capped and scrubbed, free; search_cited_documents over every document the session ever cited, also free; and up to 4 fresh retrieval calls into the corpus.
  • afterwards — if this turn pushed the raw count to 20, a detached task merges messages 81–90 into the summary and moves the bookmark to 90, and the next turn starts from a window of one.

And what the user sees is unchanged throughout: a reload renders every one of the 90 messages, because Django stored all of them (#4). Compaction only ever narrows what the model reads — never what the product remembers.

Quiz

Five questions on the machinery above. Click an answer to see whether it is right and why.

1. A session has 41 stored messages and a watermark on message 10 — 31 post-watermark raws, because an earlier compaction job was lost. The next turn finishes and a new compaction runs. How many messages does plan_rolling_compaction evict?

The catch-up loop runs while remaining ≥ window_limit: 31 ≥ 20 evicts 10 (remaining 21), 21 ≥ 20 evicts 20 (remaining 11), and 11 < 20 stops. One task run, one model call, every missed boundary cleared — which is why a lost job needs no retry queue.

2. The watermark is stored as (summarized_through_message_id, summarized_through_created_at) rather than as a count of summarized messages. What breaks if you store the count instead?

An owner can delete the last turn to redo it (#4). With a count, “the first 10 are summarized” starts pointing at different messages after any deletion. An identity compared as (created_at, id) keeps ordering correctly even when its own row is gone — which is also why it is a bare UUID and not a foreign key.

3. A user sends the next question while a compaction for that session is still running. What does the turn do?

The wait is bounded (COMPACTION_WAIT_CEILING_SECONDS = 10.0, 0.25s poll) and never blocking in the strong sense: a timeout, a Redis failure or a failed re-read all fall back to the pre-wait context, which is the legal over-window state. The task is detached — nothing awaits it, and the turn only ever observes a Redis key.

4. search_conversation_history can find a phrase from message 4 of a 90-message session, even though the model’s context only holds the summary plus messages 81–90. How, given that the tool does zero I/O?

Fetch everything, send a slice. The full session sits in AssembledChatContext.verbatim_messages the whole time, so the tool is a substring scan over a list already in hand — and so is the cited ledger. That is also why the tool costs nothing against the 4-call search budget: it returns a Command that never writes retrieval_call_count.

5. Message 85 of a session cited a 창플 카페 post, and message 85 is still inside the verbatim window. What does the model see of that citation this turn?

Citation is a this-turn property. The rebuilt thread carries Human/AI messages only, so no prior tool result, body or post id survives, and _format_message_context rewrites a cited message into a source label plus a title marked 인용 불가. The routes back to citability are retrieving the document again this turn, or asking the cited arm to re-materialize it.
