Background

Every AI feature in Changple Miracle — 일반 대화, the 컨설팅 에이전트, the public GPTs retrieve API, and the content agent — answers by citing posts from one Naver Cafe (cafe.naver.com/cjdckddus). The ingestion pipeline is the machinery that turns that cafe into a citable corpus: it scrapes posts, stores them, enriches them with AI-generated summaries and image descriptions, indexes them as vectors, and finally serves them to retrieval. If ingestion starves, every agent downstream starves with it.

Terms used throughout (skip if familiar):
  • Scraping — fetching a post. Today this means driving a real Chromium browser (Playwright) to load the cafe page and read the rendered HTML (the DOM). The alternative is calling Naver's own JSON article API directly — one small HTTP request instead of a page load.
  • Enrichment — paid Gemini calls that produce, per post, a summary + keywords (text enrichment) and a description of each image (image-alt). This is where the money goes.
  • Indexing — embedding text into a vector so semantically similar queries can find it. Today each post is represented by one vector over its summary.
  • Eligibility — the rules deciding whether a stored post may be cited at all (who wrote it, how long it is, when it was published…).

What the 2026-07-27 meetup diagnosed

The content agent was starving, and the meetup named the cause 자료의 부족 — not model quality, but supply: pre-2024 material was never collected, short-but-important posts are excluded by a length floor, and the hand-maintained 허용 저자 (allowed-author) list is too narrow. The P53.S1 forensics then quantified it against the live cafe:

  • The cafe holds 42,023 live posts (latest id 56,256). The database holds 6,942, of which only 2,657 are indexed — retrieval sees about 6 % of the cafe.
  • Collection starts at post id 46,360 (BACKFILL_START_POST_ID), so roughly 35,000 live posts below that id have never been fetched. Post density is a uniform 70–85 % across 2018→2026 — the old range is just as full as the new.
  • 1,160+ posts that are already collected, already enriched, and already paid for are invisible for exactly one reason: their author's nickname string is not on the 20-name allowlist. 227 of those belong to three staff members who are on the list — under their previous nickname (정수대리 → 정수과장 and friends).
  • Nearly half the stored corpus (3,380 of 6,942 rows, 48.7 %) has no summary and no keywords at all — unenriched, therefore unindexable.

P53 is the response: not a rule patch but a reconstruction of the ingestion subsystem. Its product requirements, after the operator's 2026-07-29 rulings: collect every post from #1; drop the length floor; exclude the 출석체크 and 가입인사 boards (together 56 % of the cafe and worthless as reference); replace the allowlist with a rank rule — authors holding one of five cafe ranks (카페매니저, 카페스탭, 대표회원, 파트너회원, 코어회원) are citable — plus a 금지저자 (banned-author) denylist that overrides rank; auto-classify documents by brand/branch with per-brand on/off; and gate the expensive full run behind a measured cost/time approval.

Intuition — the two pipelines, side by side

Strip away the detail and the change is three ideas:

  1. From "filter early and silently" to "collect everything, decide late, and explain every decision." Today a post that fails a rule simply never appears — nothing records why. Tomorrow every fetched post is stored, and a materialized eligibility state with machine-readable reason codes (rank_ineligible, board_blocked, unenriched…) says exactly why any post is or isn't citable.
  2. From string matching to entities. Today the author is a nickname string compared byte-for-byte against a hand-typed list, and the board is a name string nothing reads. Tomorrow authors are rows keyed on Naver's stable memberKey (proven identical across nickname changes) carrying a live rank and a banned flag; boards are rows keyed on menuId with collect/index toggles.
  3. From one blind walk to a known id list. Today the scraper walks post ids one by one and guesses what a 404 means. Tomorrow it first reads the cafe's own board listings — which enumerate every live id along with its author, rank, board, and date — and only then fetches, skipping excluded boards and dead ids before spending anything.

A true story, told twice: post 48755

당술샘 — a cafe member who runs a 한식주점 built with Changple — wrote post 48755 in the 창플 후기 board: 2,326 characters, nine images, fully enriched with a summary and keywords. Today that post is invisible to every agent. Not because it is short, not because it failed anything technical — but because the string 당술샘 does not appear in the AllowedAuthor table. No log says so; the post is simply never a candidate. This is D55, and 7 of its 8 missing rows fail for exactly this reason.

Under P53, the same post is stored with an Author entity (memberKey …COHxOZ5Cc-style, current rank 코어회원). The eligibility engine evaluates it against the five-rank rule — 코어회원 qualifies, per the operator's ruling — and stamps it eligible. It gets indexed in the next sweep. And if the operator ever banned this author, the engine would stamp author_banned, the sweep would de-index it, and the operator UI would show that reason instead of silence.

The rename story is the same lesson from another angle: when 박대리 became 박과장, the old 112 posts kept displaying "박대리" forever (Naver never rewrites history), so the allowlist — which lists 박과장 — silently lost all of them. The S1 probe proved both nicknames share one memberKey; key on that, and a rename costs nothing.

Code — where each behavior actually lives

Today: the scatter, in five excerpts

1. The extractor captures a nickname and nothing else about the author (apps/backend/ingestion/scraper.py:365-370). This is why the rank rule needs a re-scrape — rank was never stored:

author: getFirstText([
  ".nickname",
  ".article_writer .nickname",
  ".WriterInfo .nickname"
]),
date: getFirstText([".date", ".article_info .date", ".WriterInfo .date"]),

2. The enrichment gate silently drops short posts (apps/backend/ingestion/execution.py:433-449). A skipped post gets no summary and no keywords, which later disqualifies it from indexing — a two-step invisibility no single line admits to:

min_content_length = get_bot_min_content_length()
if len(input_text) <= min_content_length:
    _finish_item(item_id, ItemExecutionResult(
        item_status=str(IngestionJobItem.Status.SKIPPED),
        payload={"result": "skipped", "reason": "content_too_short", ...},
    ))
    return

A second, undocumented floor sits next to it (apps/backend/ingestion/image_alt.py:26-27) — posts under 500 raw characters get no image descriptions at all, which is exactly wrong for short posts whose substance is a kakaotalk screenshot (636 such posts in the current corpus):

RAW_TEXT_ALT_THRESHOLD = 500
MAX_ALT_IMAGES_PER_POST = 10

3. The backend's index-candidate predicate (apps/backend/ingestion/index_candidates.py:47-79) — note the exact-name author join and the five stacked conditions:

active_author_exists = AllowedAuthor.objects.filter(
    name=OuterRef("author"), is_active=True,
)
...
.filter(
    has_active_author=True,
    has_saved_status=True,
    normalized_text_length__gt=min_content_length,
)
.exclude(summary="")
.exclude(keywords__isnull=True)
.exclude(keywords=[])

4. The agent re-implements the same rules in raw SQL — once for indexing (apps/agent/app/indexing/projection.py:37-52) and again inside every retrieval query (apps/agent/app/retrieval/candidates.py:347-374, shown; the vector variant repeats it):

INNER JOIN {DOCUMENT_SOURCE_STATUS_TABLE} AS dss
    ON dss.post_id = ds.post_id AND dss.status = %s
INNER JOIN {ALLOWED_AUTHOR_TABLE} AS aa
    ON aa.name = ds.author AND aa.is_active = TRUE
...
WHERE ds.ingested = TRUE
    AND ds.published_at IS NOT NULL
    AND ds.published_at >= (inputs.published_on_or_after ...)

5. And the constants disagree with each other. The model default and validator floor say 200 (documents/models.py), the agent's fallback says 500 (projection.py:32), and the live policy row in the database says 450 — matching none of them. When a rule lives in six places, drift is not a risk, it is a schedule.

The measured consequence (P53.S1, dev DB): 21 corpus rows mention 당술샘; 8 are un-indexed; 7 of those 8 fail only the author name-match. Corpus-wide, 1,160+ enriched posts are invisible the same way, and 40 posts sit as valid "reprocess me" candidates that no trigger has ever fired.

P53: the same behaviors, relocated — slice by slice

The phase builds the new pipeline in ten slices (works/phases/active/P53/phase.md holds the full decomposition). The map from diagram to code-to-be:

  • S2 — the collection domain. Author (PK memberKey, current rank, banned flag, rename history), Board (PK menuId, toggles), FKs from DocumentSource, and the materialized eligibility fields (flag + reason-code set). Backfilled from the 6,942 stored rows. S1 proved the keys: three rename pairs (박대리→박과장, 나라대리→나라과장, 정수대리→정수과장) each share one memberKey, and 2 of 46 stored board names have already drifted from the live board list — name joins would orphan 301 rows on day one.
  • S3 — the scraper. Transport swap to cafe-articleapi/v3/cafes/29268355/articles/{id} (S1 measured 0.22–0.32 s/post and byte-identical extraction: the API's contentHtml fed to the unchanged EXTRACT_ARTICLE_SCRIPT reproduced stored text at similarity 1.00 on every post tested). Plus pacing/jitter knobs, a consecutive-failure circuit breaker wired to the existing alert mailer, rank + memberKey capture, and epoch-based dates. The error map is already known: 200 = readable, 401/0004 = member-only, 404/4003 = deleted or never existed — indistinguishable, which is why the listing pre-scan matters.
  • S4 — the eligibility engine. One predicate: author's current rank ∈ {카페매니저, 카페스탭, 대표회원, 파트너회원, 코어회원} ∧ not banned ∧ board index-enabled ∧ per-policy floor/date — materialized with reason codes, plus the re-evaluation sweep. Then the consolidation: every one of the ≈13 enforcement sites in both apps rewired to consume it, the AllowedAuthor readers retired (table dropped later, post-prod-verification), and the length-floor constants unified.
  • S5 — run machinery. The from-#1 preset, the listing-driven id enumeration with the two boards pre-skipped, and batch-vs-direct enrichment as a per-run flag (the backfill currently hardcodes direct mode, forfeiting the ~50% batch discount).
  • S6 — the measurement gate. Sample runs on the real machinery → per-stage ₩, wall-clock under 2–3 pacing options, ban-risk, chunk pricing. The full run does not start until the operator approves the numbers.
  • S7 — the dev full run (snapshot first; ends with the run healthy and runbooks written, including the dev→prod restore recipe). S8 adds brand/branch classification with a new LLM role and retrieval-parameter filtering; S9 + DECOMP2 design and then build the operator surfaces.

One number to keep in mind while reading S6's output later: the corpus today indexes 2,657 posts; the run should take that to roughly the high-teens of thousands. The S1 chunk proposal (works/phases/active/P53/chunk-proposal.md) deliberately recommends sequencing — grow the corpus first, re-measure retrieval, and only then decide whether chunk-level vectors are still needed — because today's one-vector-per-post compresses a p90 post of 3,380 characters into a 316-character summary, and nobody yet knows how much of the "적은 양의 자료만 사용" complaint survives a 7× corpus growth.

Best practices & next steps

Where P53 aligns with prevailing practice

  • Load raw, decide late — the ELT shape. Modern data pipelines load everything first and transform inside the store, precisely so teams can "re-transform historical data without re-extracting it from source systems" when rules change (Databricks: What is ELT? — databricks.com). P53's "collect everything, filter at index/retrieval" plus the re-evaluation sweep is this exact shape: a rank change becomes a sweep, never a re-scrape. Today's pipeline is the anti-pattern — the filter runs at the most expensive, least reversible stage.
  • Polite, adaptive crawling. Scrapy's AutoThrottle exists to "be nicer to sites" by adapting delay to observed latency, and it hard-codes one safety rule P53 should copy verbatim: latencies of non-200 responses are never allowed to decrease the delay — a struggling server must not be hit faster (Scrapy AutoThrottle docs — docs.scrapy.org). S3's pacing/jitter knobs and S6's measured pacing options are the same philosophy, tuned for a single authenticated account rather than throughput.
  • Circuit breaking on consecutive failures. The breaker pattern trips after a failure threshold so doomed calls stop consuming resources and the failure becomes visible to operators (Fowler, CircuitBreaker — martinfowler.com). Today a captcha would surface as content_root_not_found on every remaining post and burn 3 retries × thousands of ids; S3's breaker + alert is the textbook fix.
  • Chunking, approached with measurement rather than faith. The RAG literature is clear both that chunks lose context without care and that smaller corpora often don't need the complexity at all — Anthropic's contextual-retrieval write-up quantifies chunk-context fixes (49–67% retrieval-failure reduction) while explicitly noting that sufficiently small knowledge bases should skip RAG-style chunking entirely (Anthropic: Introducing Contextual Retrieval — anthropic.com). The S1 proposal's "sequence, don't skip" and its per-consumer opt-in design sit squarely inside that guidance.

Where it deliberately diverges, and why that's legitimate here

  • Single-account, session-authenticated scraping. Crawl-politeness literature assumes anonymous crawlers optimizing throughput. Here ~65% of articles are member-only, so every request is attributable to one account — politeness is not just etiquette, it is account survival. That justifies being more conservative than AutoThrottle's adaptive optimum: fixed jittered pacing, no concurrency, and a stop-immediately rule S1 already practiced.
  • One vector per post stays the default. Chunking orthodoxy would split everything, but the operator's constraint is all-agents no-regression across four very different consumers. Keeping the post-level vector as the universal default and making chunks an opt-in layer trades some retrieval ceiling for guaranteed stability — a reasonable trade until S6 prices the alternative with real numbers.

Next steps

  1. Re-measure with the session before trusting any total. 42,023 live posts is an anonymous-visible count — a lower bound. S6 must re-run the count, the per-board numbers, and the latency curve logged in, and produce the ₩/wall-clock/ban-risk table the full run is approved on.
  2. Take the batch discount decision with data. The flag ships in S5; at ~18,400 posts the ≈50% Gemini Batch saving is the single biggest cost lever — S6 should price both modes and let the number decide.
  3. Re-measure retrieval after the corpus grows, then judge chunking. Run the 당술샘-style queries once indexed posts go from 2,657 to ~18k; only span-level citation is something corpus growth cannot deliver, so let P54's actual needs pull chunking in, not push it.
  4. Sequence the prod restore correctly. Deploy P53 code to prod before restoring the dev-built corpus — the old prod SQL still inner-joins allowedauthor and would filter the new corpus into invisibility.

Quiz

Five questions. Click an answer to check it.

1. Post 48755 (당술샘's 후기, 2,326 chars, fully enriched with summary and keywords) is invisible to every agent today. Why?

The S1 gate table showed it passes every check — length, SAVED status, summary, keywords, date — except the exact-name author join. (No board denylist even exists today.) Under P53's five-rank rule, 코어회원 qualifies, so it becomes eligible.

2. Why does P53 key the Author entity on memberKey instead of the nickname?

S1 verified three real rename pairs (박대리→박과장, 나라대리→나라과장, 정수대리→정수과장): old posts display the old nickname forever, and both eras share one memberKey. Exactly this split cost the allowlist 227 posts by people who ARE on it.

3. Why does brand/branch filtering live at retrieval time in P53, while board and author rules gate enrichment and indexing?

Everything that gates enrichment/indexing requires a re-index to undo; a retrieval parameter flips back instantly. That's also why the ranked-result cache key must carry the toggle version — otherwise a flip serves stale cached results for up to 5 minutes.

4. Under the current pipeline, what happens when the operator adds a new allowed author (or a rule changes)?

The daily run only moves the frontier forward over NEW ids. Retrieval does re-check the author join per query — but only over already-indexed posts, and indexing is what never re-fires. Hence 40 valid reprocess candidates sitting orphaned in dev, and P53's re-evaluation sweep as the structural fix.

5. Why does P53 enumerate post ids from board listings instead of walking ids 1→latest?

~370 listing requests replace ~14,000 fetches of ids that never existed, pre-skip the two excluded boards (56% of the cafe), and give the eligibility engine its inputs before a single article fetch is spent. The 404 signature alone (404/4003) cannot distinguish deleted from never-existed.
