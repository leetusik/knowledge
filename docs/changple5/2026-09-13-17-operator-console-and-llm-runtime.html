Background — what "the console" is on the backend

Two halves with one name

"The operator console" names two different things that meet over HTTP. The half you look at is a set of Next.js pages under /operator/… in apps/web — not this page's subject. The half this page teaches is the JSON API those pages call, and it lives almost entirely in one small Django app: apps/backend/operators/, about 2,900 lines across a dozen modules.

Django's URL root shows where it hangs (apps/backend/config/urls.py):

path("api/admin", RedirectView.as_view(pattern_name="api-admin-overview", permanent=False)),
path("api/admin/", include("operators.urls")),
path("api/documents", DocumentSourceListView.as_view(), …),
path("api/documents/ingestion/", include("ingestion.urls")),
path("api/documents/", include("documents.urls")),
path("api/django-admin/", admin.site.urls),

Three things are worth noticing already.

First, the console's API is not all under one prefix. The dedicated operator app mounts at /api/admin/, but plenty of operator-only endpoints live under the prefix of the app that owns the data — the corpus coverage tab is served from /api/documents/collection/coverage, the ingestion job controls from /api/documents/ingestion/…, the content library's operator writes from /api/content/admin/…. There is no single "admin router". What holds these scattered surfaces together is not a URL prefix; it is a permission class.

Second, api/admin without a trailing slash is a redirect to the overview endpoint. A small courtesy, and a hint that this API is browsed by humans with session cookies as well as by the SPA.

Third, api/django-admin/ is Django's own built-in admin site. It is the break-glass path: the resolver module's docstring literally calls it "the django-admin break-glass path". Nobody uses it day to day — it exists so that when the console is broken, or a value needs setting that no panel exposes, someone with a superuser account can still edit a row by hand. You will see the code defend against exactly that below: several readers re-validate values "because django admin can write anything".

One permission class for the whole backend

Here is apps/backend/operators/permissions.py in its entirety — all 28 lines, including the docstring, because its size is part of the point:

"""Operator authorization: the ``is_operator_user`` predicate and DRF permission.

``IsOperatorUser`` is the single operator permission class across the backend
(documents/ingestion consolidated onto it in P34.S7); it grants access only to
authenticated users whose ``user_type == "admin"``.
"""

from __future__ import annotations

from rest_framework.permissions import BasePermission


def is_operator_user(user) -> bool:
    return bool(
        user
        and getattr(user, "is_authenticated", False)
        and getattr(user, "user_type", "") == "admin"
    )


class IsOperatorUser(BasePermission):
    """Allow operator (admin) users only; 403 with a generic message otherwise."""

    message = "You do not have permission to perform this action."

    def has_permission(self, request, view) -> bool:
        return is_operator_user(request.user)

That is the whole authorization story for every operator surface in the product. Two conditions: the request is authenticated, and the user row's user_type column reads "admin". Note what is not here — no roles, no scopes, no per-object rules, no superuser requirement. (How a user gets user_type == "admin" in the first place, and how the JWT that proves authentication is minted and verified, is explainer 3's subject. This page starts one step later, at the permission check.)

Measured reach, grepped today rather than assumed: eight non-test modules import IsOperatorUser, spread across eight app directories — accounts/operator_views.py, consultations/admin_views.py, content/views.py, conversations/admin_views.py, documents/views.py, feedback/admin_views.py, ingestion/views.py, and operators/views.py itself. Those eight declare ten permission_classes = [IsAuthenticated, IsOperatorUser] lines directly, and then fan the pair out through mixins: content/views.py's OperatorContentViewMixin / OperatorJsonContentViewMixin / OperatorContentLookupMixin are inherited by sixteen content modules, most of them the content agent v2 stage views from explainers 13–14.

Pattern worth naming

The permission is centralized; the mixin is not. Each app writes its own tiny base class that pairs IsOperatorUser with whatever authentication and parsers it needs — operators.OperatorAdminViewMixin, documents.AdminDocumentViewMixin, content.OperatorContentViewMixin, accounts.OperatorUserAdminViewMixin. Duplicating four three-line classes buys the thing that actually matters: the operators app depends on no domain app, and no domain app has to import another one just to be gated. operators/serializers.py does the same with its StrictSerializer and says so in a comment — "third copy of the same tiny class … duplicated rather than cross-imported so the operators app keeps no dependency on a domain app".

The authentication half is equally short. The shared mixin in operators/views.py reads:

class OperatorAdminViewMixin:
    """Shared authentication/authorization for operator-console JSON endpoints.

    Accepts either a bearer JWT (the Next.js ``/operator/*`` SPA) or a Django
    session (django-admin login), and requires the caller to be an operator
    (``user_type == "admin"``). Endpoints inheriting this mixin answer 401 for
    anonymous callers and 403 for authenticated non-operators.
    """

    authentication_classes = [JWTAuthentication, SessionAuthentication]
    permission_classes = [IsAuthenticated, IsOperatorUser]

Two ways in, one gate: the SPA carries a bearer JWT, and a human logged into django-admin carries a session cookie. 401 means "I do not know who you are"; 403 means "I know, and you are not an operator".

Intuition — a setting that is alive

The console is two kinds of endpoint

Once you look past the routing, every endpoint in the console is one of exactly two shapes:

  • Read models. The overview dashboard, the system-log list, the Cloudflare analytics panel, the corpus coverage and per-post diagnostic screens. These run bounded aggregate queries and return a payload. They write nothing.
  • Config panels. LLM runtime config, ingestion alert recipients, the chat retrieval width, the Notion export credentials. These read and write a handful of rows that the rest of the product then obeys.

The read models are honest, careful, and not very surprising — we will walk them, because the carefulness is instructive. The config panels are where the interesting engineering is, and they all turn on one question.

The question: how do you change a setting on a running system?

Start from the obvious answer and watch it fail. Suppose the chat model should move from gemini-3-flash-preview to something newer. The traditional answer is an environment variable: edit .prod.env, redeploy, done. But a redeploy of this product means rebuilding and restarting the Django backend, the FastAPI agent, and the Celery worker and beat containers. It takes minutes, it interrupts in-flight chat streams, and — the fatal part — it means the person who should be tuning the model (the operator) needs the person who can deploy (the builder). A knob you can only turn by shipping is not a knob.

So the value has to live in the database, where an HTTP request can change it and every process can see it. That gives the shape the whole rest of this page elaborates:

The dashed box is the piece people usually forget. If the operator types gemini-3.7-flesh, a database-backed setting will happily store the typo and every generation call in the product will start failing minutes later, in the background, where nobody is watching. So the write path makes one cheap real call to Gemini with the submitted id before it saves. We will look at exactly which failures block the save and which do not, because that asymmetry is the most thoughtful thing in the module.

The part that is genuinely counter-intuitive: two readers, two policies

Both services read the same row. Neither caches it the way you would guess.

The agent — the FastAPI service that serves chat — caches it for 30 seconds in process memory. The Django backend — which runs the Celery jobs — does not cache it at all: it re-reads the row every single time. If you have absorbed the usual instinct that caching is an optimization and "no cache" is the lazy option, this looks backwards. It is not. Look at how often each side actually asks:

The agent builds a model client on nearly every step of a streaming chat turn — per model call, per retrieval rerank, per compaction. Without a cache, a single conversation would mean dozens of round-trips to Postgres for a value that changes maybe twice a month. The Django backend's builders, by contrast, are called once per Celery job: a title-generation task, an image-alt task, a content-agent stage. One ORM read per job already gives per-job liveness, for free. Adding a 30-second cache there would save a fraction of a query per job and would mean a job could start with a stale model id the operator had just changed.

The idea to keep

Same store, two read policies, each justified by call frequency rather than by taste. Say it as a rule: cache a config read when the read is in a hot loop; skip the cache when the read already happens exactly as often as the work it configures. Both sides here wrote the reasoning into their module docstrings, which is why the decision survived three years of later edits.

One consequence of the 30-second snapshot is worth internalizing as an operator: after you press 저장, the agent may keep using the previous model for up to about half a minute. That is not a bug and not a deploy problem — it is the snapshot window expiring. The backend, on the other hand, picks it up on the very next job.

The end-date handling is a small correctness detail with a long tail of bugs behind it in other codebases: the filter is < (end_date + 1 day), not <= end_date, so "through 9 September" includes events at 23:59 on the 9th. The same convention appears in operators/date_ranges.py, which every other operator date-windowed endpoint shares.

The overview snapshot

operators/overview.py (247 lines) is the dashboard. Five builders, each returning a frozen dataclass, composed into one OperatorOverviewSnapshot: accounts, content, documents, ingestion, conversations. Model imports are function-local, deliberately, "to avoid cross-app import cycles at module load" — the same independence rule the duplicated mixins bought.

Here is one builder in full. Read it for its shape rather than its fields:

def build_ingestion_overview_summary() -> IngestionOverviewSummary:
    from ingestion.models import IngestionJob

    # One pass over ingestion_ingestionjob: total + the seven per-status counts
    # + the two Max bounds, all conditional (was 9 separate queries).
    status = IngestionJob.Status
    aggregates = IngestionJob.objects.aggregate(
        total_jobs=Count("id"),
        pending_jobs=Count("id", filter=Q(status=status.PENDING)),
        queued_jobs=Count("id", filter=Q(status=status.QUEUED)),
        running_jobs=Count("id", filter=Q(status=status.RUNNING)),
        succeeded_jobs=Count("id", filter=Q(status=status.SUCCEEDED)),
        failed_jobs=Count("id", filter=Q(status=status.FAILED)),
        partial_jobs=Count("id", filter=Q(status=status.PARTIAL)),
        cancelled_jobs=Count("id", filter=Q(status=status.CANCELLED)),
        latest_job_created_at=Max("created_at"),
        latest_job_finished_at=Max("finished_at"),
    )
    …

Conditional aggregation — Count("id", filter=Q(…)) — is the technique here, and it is the difference between one SELECT and nine. In SQL it compiles to COUNT(id) FILTER (WHERE status = 'queued') repeated per tile, all in a single pass over the table. Every builder in the file carries a comment recording how many queries it replaced; the documents builder additionally swaps a post_id__in subquery for a correlated Exists(), and the conversations builder replaces a join + distinct with the same. The dashboard as a whole is, in the view's own words, "the ~10-query conditional-aggregation collapse".

The last helper in the file is three lines and quietly the most maintainable thing in it:

def _build_status_breakdown(*, queryset, field_name: str, choices: list[str]) -> dict[str, int]:
    raw_counts = {
        row[field_name]: row["count"]
        for row in queryset.values(field_name).annotate(count=Count("id"))
    }
    return {choice: raw_counts.get(choice, 0) for choice in choices}

It takes the choices from the model's own TextChoices class and fills in a zero for any value the data does not currently contain. Two properties follow. First, a status with no rows shows as 0 rather than vanishing from the payload — the console's tiles never silently change shape. Second, when a new status is added to the domain, the console picks it up for free. That is not hypothetical: P98 added RANK_RESTRICTED to DocumentSourceStatus.Status (a post the scraper account's cafe rank cannot read), and I verified today that the only change needed on the operators side was the test file's expected dictionary — _build_status_breakdown is called with choices=DocumentSourceStatus.Status.values, so the new key appeared in the payload with no console code touched at all.

The whole snapshot is cached for 20 seconds on the shared Redis cache (OPERATOR_OVERVIEW_CACHE_KEY = "operators:overview-snapshot"), under a convention settings.py spells out: poll-class TTLs of roughly 15–30 s for polled operator snapshots, read-class TTLs of roughly 5 minutes for content read caches. One key serves every operator because the payload is permission-invariant and takes no query parameters, and generated_at is stored inside the cached payload so it truthfully says when the data was gathered rather than when it was re-served. Setting the TTL to 0 disables the cache entirely, which is how tests assert the uncached query shape.

Cloudflare Web Analytics, in one breath

operators/cloudflare_analytics.py (290 lines) is the console's only outbound third-party read. One HTTP round-trip to Cloudflare's GraphQL Analytics API with four aliased selections on the same rumPageloadEventsAdaptiveGroups dataset (totals, daily, referrers, hosts), normalized into a flat payload, cached for 300 seconds per resolved date window. Two error classes map to two statuses and nothing else can escape: CloudflareAnalyticsBadGatewayError → 502 ("Cloudflare rejected the query" or returned a malformed body — the normalizer catches KeyError/IndexError/ TypeError and converts them), and CloudflareAnalyticsUnavailableError → 503 (unreachable, timed out at 10 s, or — importantly — not configured, which is checked before any network call is made). Errors are never cached.

Read the numbers correctly

The module's docstring records three quirks that matter more than the code: Cloudflare's adaptive sampling means every pageview/visit figure is extrapolated, not exact; a referrer legitimately showing visits: 0 is a real measurement, not a gap; and an empty referrer host ("") means direct traffic. A dashboard that presents estimates as counts is a dashboard that will eventually be used to make a wrong decision.

The centrepiece: live LLM runtime config

Now the main event. The feature, in one sentence: an operator edits a model id and a reasoning effort per LLM role at /operator/settings, and both services start using it within seconds, with no redeploy. It is built from five small modules, and the cleanest way to understand it is to follow one save all the way through.

1. The registry — what a "role" is

operators/llm_roles.py (393 lines) is the source of truth for which roles exist. A role is one place in the product that calls an LLM: generating a chat reply, writing a conversation title, reranking retrieval candidates, drafting one section of a 미라클 article. Each is one frozen dataclass:

@dataclass(frozen=True, slots=True)
class LLMRoleSpec:
    """One configurable LLM role.

    ``slug`` is simultaneously the DB key, the API field key and the UI label
    key — freeze it. ``label`` is operator-facing and therefore Korean.
    """

    slug: str
    app: str
    label: str
    supports_thinking: bool
    default_model_id: str
    default_thinking_level: str | None = None
    requires_explicit_thinking: bool = False

"slug is simultaneously the DB key, the API field key and the UI label key — freeze it" is the sort of comment worth copying into your own code. One string is the primary key of a table row, a JSON field name in a public API, and the key a React component looks up its label by. Renaming it is a three-system migration; the comment is there so nobody tries.

I counted the registry by parsing the module rather than trusting its comments: 25 roles, tagged app=agent for 20 and app=backend for 5. A sample across the range:

Three details in that table repay attention.

supports_thinking=False is a real distinction. chat_context_token_estimation calls get_num_tokens — a counting endpoint, not a generation one — so a reasoning level is meaningless for it, and the API refuses one ("This role does not support a reasoning level"). Modelling "this knob does not apply" beats letting the UI show a control that silently does nothing.

NULL is a value, not an absence. A NULL thinking_level means "send no thinking kwarg at all" — take the provider's own default. Every role except chat seeds NULL, which is precisely what made turning the store on behavior-neutral on the day it shipped.

The chat role can never be cleared. That is the requires_explicit_thinking flag, and it is the one non-obvious rule in the module. The chat role's stored level is not merely an internal default — it is the service default a user sees on the composer's 생각 깊이 control. If it were NULL, the control would have nothing to show. So the serializer refuses an explicit clear, in Korean, because the message is rendered verbatim in the console:

        and "thinking_level" in attrs and attrs["thinking_level"] is None):
    raise serializers.ValidationError({"thinking_level": [
        f"{spec.label} 역할의 추론 강도는 비울 수 없습니다. "

Note the precision of the condition: only an explicit null is refused. Omitting the key — a model-only update — stays legal and leaves the stored level alone.

Prose lag — trust the code

The app column is a UI grouping label, and it has drifted from reality. Eleven roles tagged agent — content_architect, content_section_writer, content_chat_pick, scaffold_section_note and their siblings — are in fact called from the Django backend, in content/agent_jobs/, through the shared factory analysis.build_client(). The registry's own section comments still read --- apps/agent (9) --- and --- apps/backend (4) ---, counts that predate the content agent v2 block and the cost_table_normalize role. The same stale-count family reaches the docs and apps/agent/app/llm_config.py:132 ("12 rows") and is already recorded as an open operator question for this curriculum phase. Nothing is broken by it — the query is a SELECT-all and each reader ignores the slugs it does not own — but count the registry, do not read the comment.

The module also owns the model-id vocabulary. MODEL_ID_PATTERN is ^(models/)?[a-zA-Z0-9]+([.\-][a-zA-Z0-9]+)*$ and is deliberately permissive: an allow-list of known model ids "would go stale within weeks and block the operator from adopting a new Gemini model — which is the entire point of the phase". Embedding models, by contrast, are rejected outright for any generation role, because swapping the embedding model at runtime would silently invalidate the entire vector index (so gemini_embedding_model is not in the registry at all and stays env-pinned). I executed the three helpers against stubs to see exactly where the lines fall:

A subtlety the measurement exposes: normalize_model_id is a comparison helper, not a write-path normalizer. The serializer's validate_model_id only calls .strip() before storing, so an operator who types models/Gemini-3.7-Flash gets exactly that stored (Gemini accepts both forms). Normalization exists so the embedding check cannot be dodged by case or by the models/ prefix — matched exactly against a known list rather than by substring, "so a future generation model that happens to carry the word never locks the operator out".

2. The probe — one cheap real call

operators/llm_probe.py (127 lines) answers "does this model id actually exist?" by asking the provider. One throwaway client, one get_num_tokens("ping"). Then the classification that makes the module worth studying:

#: Provider status codes that mean "this model id is wrong" rather than "the
#: probe could not run". 401/403 (auth/permission), 429 (quota) and 5xx are
#: deliberately treated as infrastructure failures.
REJECTION_STATUS_CODES = frozenset({400, 404})
def probe_model_id(model_id: str) -> None:
    api_key = resolve_probe_api_key()
    if not api_key:
        logger.warning("Skipping LLM model probe for %r: no Gemini API key is configured "
                       "on this service; allowing the save.", model_id)
        return
    try:
        build_probe_client(model_id, api_key).get_num_tokens(PROBE_TEXT)
    except Exception as exc:
        rejection = _provider_rejection_message(exc)
        if rejection is not None:
            raise ModelProbeRejected(rejection) from exc
        logger.warning("LLM model probe for %r could not run (%s: %s); allowing the save.", …)

Two failures, two opposite reactions. A 400 or 404 means the provider looked at the id and said no — that is a typo, and the save is refused with the provider's own message carried back to the panel. Anything else — no API key on this container, a timeout, a network error, a 429 quota wall, a 5xx at Google — means the probe could not run, and the save is allowed with a warning in the log.

Why the asymmetry is right

Imagine the opposite policy. Gemini has an outage; the operator wants to switch to a different model to work around it; the probe cannot reach Gemini; the save is blocked. The configuration system would fail exactly when configuring is most needed. A validator that cannot run must not become a lock. The same reasoning gives the endpoint a ?probe=false escape hatch: a brand-new model might reject count_tokens while being perfectly usable for generation, and the operator must never be locked out of adopting one.

The rejection walk is also careful: _provider_rejection_message traverses the __cause__ chain, because LangChain wraps provider errors, and it truncates the message to 500 characters before it becomes a validation error.

3. The write — one atomic round trip

PATCH /api/admin/llm-config takes a partial map keyed by role slug — {"chat": {"model_id": "…", "thinking_level": "medium"}, …} — because the panel has one save button and firing twenty-five requests behind it would be absurd. The view (operators/views.py) does four things in order:

serializer = LLMRoleConfigBulkUpdateSerializer(data=request.data)
serializer.is_valid(raise_exception=True)
changes = serializer.validated_data

existing = {row.role: row for row in LLMRoleConfig.objects.filter(role__in=list(changes))}

if self._probe_enabled(request):
    self._probe_changed_model_ids(changes, existing)

with transaction.atomic():
    locked = {row.role: row for row in
              LLMRoleConfig.objects.select_for_update().filter(role__in=list(changes))}
    for slug, fields in changes.items():
        row = locked.get(slug)
        if row is None:
            # The seed migration creates every row, but a hand-deleted
            # (or newly registered) role must still be writable: start
            # from the registry default and apply the submitted fields.
            spec = LLM_ROLES_BY_SLUG[slug]
            row = LLMRoleConfig(role=slug, model_id=spec.default_model_id,
                                thinking_level=spec.default_thinking_level)
        for field, value in fields.items():
            setattr(row, field, value)
        row.updated_by = request.user
        row.save()

return Response(build_llm_role_config_payload())

Validate → probe → write under select_for_update() → return exactly the payload GET would have returned. That last move is a convention every config panel in this app follows: the write response is the fresh read, so the UI never needs a second request and can never render a value the server did not confirm.

The probe step is narrower than it first looks. _probe_changed_model_ids compares each submitted id against the current one (the stored row, or the registry default when no row exists) and probes only the ids that actually changed — deduplicated, so two roles moving to the same model cost one provider call. Re-saving an unchanged panel costs zero. Rejections are collected per slug and raised together, so the operator sees every bad field at once rather than one per attempt.

And validation is strict. StrictSerializer rejects any payload key that is not a declared field, an unknown slug is an error rather than a silent no-op, and the entry serializer refuses an empty object. The store is small enough and consequential enough that silently ignoring input would be the wrong kindness.

4. The backend read seam — no cache, on purpose

operators/llm_runtime.py is 95 lines, and roughly half of them are the docstring explaining why it does not do things. The whole resolver:

def resolve_role_config(role: str, *, settings_attr: str, default_model: str,
                        default_thinking: str | None = None) -> tuple[str, str | None]:
    try:
        row = (LLMRoleConfig.objects.filter(role=role)
               .values_list("model_id", "thinking_level").first())
    except DatabaseError:
        logger.warning("LLM runtime config read failed for role %r; falling back to env/default.",
                       role, exc_info=True)
        row = None

    stored_model_id, stored_thinking_level = row if row is not None else (None, None)

    model_id = (stored_model_id
                or getattr(settings, settings_attr, default_model)
                or default_model)

    thinking_level = stored_thinking_level
    if thinking_level not in THINKING_LEVELS:
        thinking_level = default_thinking

    return model_id, thinking_level

The fallback chain is three rungs for the model (stored → the role's Django setting → the co-located default constant) and two for the thinking level (stored, if it is one of the four known levels → the caller's default). There is no environment layer for the thinking level at all, by an explicit decision: no per-role thinking env var was ever added, so an unset or out-of-vocabulary stored value goes straight to the default. That vocabulary check is what defends against the break-glass path — the API rejects a bad level on write, but django-admin, or a hand-run UPDATE, can put anything in the column, and passing it through would raise at model construction.

I ran the function against a stub settings object and a fake queryset to confirm every rung rather than read it off:

The last two rows are the invariant that matters most: a config read must never fail a Celery task. ProgrammingError — which is what an unapplied migration looks like, when the table does not exist yet — is a DatabaseError subclass, so the deploy window in which the code is new and the migration has not run yet degrades to "use the env value and log a warning" instead of crashing every background job. The content-agent factory states the consequence plainly: "resolve_role_config cannot raise: the chain is total and a DatabaseError is treated as an absent row … That invariant is why no content-agent call, pass or stage can stop on a missing model any more."

Five backend role constants live in this module — ROLE_CONVERSATION_TITLE, ROLE_IMAGE_ALT, ROLE_TEXT_ENRICHMENT, ROLE_BRAND_CLASSIFICATION, ROLE_COST_TABLE_NORMALIZE — "copied verbatim from llm_roles.py". But the resolver's reach is much wider than five: grepping today finds nine direct call sites (conversations/title_generation.py, ingestion/text_enrichment.py, ingestion/image_alt.py, ingestion/batch_execution.py ×2, documents/brand_verification.py, content/cost_table_normalize.py, content/agent_jobs/analysis.py, content/agent_jobs/depth.py) plus the shared factory analysis.build_client(), which eleven more content-agent stage modules call. A representative consumer, the conversation-title builder:

model_name, thinking_level = resolve_role_config(
    ROLE_CONVERSATION_TITLE,
    settings_attr="GEMINI_CONVERSATION_TITLE_MODEL",
    default_model=DEFAULT_CONVERSATION_TITLE_MODEL,
)
model = GeminiConversationTitleModel(model_name=model_name, google_api_key=google_api_key,
                                     thinking_level=thinking_level)

The env attribute name and the DEFAULT_* constant stay at the call site rather than moving into the resolver. That is deliberate: every consumer kept the exact shape it had before the store existed, so adopting live config was a two-line change per call site instead of a refactor.

5. The agent read seam — a snapshot across the schema boundary

The agent's copy of this problem is a different problem, for two reasons. First, it cannot use the ORM at all: it is a separate FastAPI service with its own database role, and it reaches the Django tables through the one-way read bridge that explainer 2 teaches — a SELECT grant on the backend schema and nothing else. Second, its settings object is @lru_cached, so anything derived from the environment is frozen for the life of the process. A value the operator must be able to change without a redeploy has to be read outside that cached object. apps/agent/app/llm_config.py (271 lines) is that reader:

LLM_ROLE_CONFIG_TABLE = qualify_table_name(BACKEND_SCHEMA_NAME, "operators_llmroleconfig")

def _fetch_llm_config_rows(settings) -> dict[str, tuple[str | None, str | None]]:
    """Read every stored role row. 12 rows — cheaper than a filtered query."""
    rows = {}
    with connect_agent_db(settings) as connection:
        with connection.cursor() as cursor:
            cursor.execute(f"SELECT role, model_id, thinking_level FROM {LLM_ROLE_CONFIG_TABLE}")
            for record in cursor.fetchall():
                slug = _normalize(record[0])
                if slug is None:
                    continue
                rows[slug] = (_normalize(record[1]), _normalize(record[2]))
    return rows

(That "12 rows" in the docstring is the prose lag flagged above — there are 25 today. The query is a SELECT-all, so the number is descriptive, not load-bearing; the module then serves the nine slugs it owns and ignores the rest.)

Around that read sits the snapshot. Four module-level globals under a threading.Lock — _snapshot, _snapshot_expires_at, _failure_logged_at — with time.monotonic() for the clock (never wall time, which can jump). The failure path is the interesting half:

try:
    rows = _fetch_llm_config_rows(settings)
except Exception as exc:
    # Broad on purpose: a stubbed/partial settings object raises
    # AttributeError inside build_conninfo long before psycopg is
    # reached, and that path must degrade exactly like a dead network.
    _snapshot_expires_at = now + ttl
    if _failure_logged_at is None or (now - _failure_logged_at) >= max(ttl, _FAILURE_LOG_MIN_INTERVAL_SECONDS):
        _failure_logged_at = now
        logger.warning("LLM runtime config read failed; falling back to %s (%s: %s)",
                       "the last known snapshot" if _snapshot else "env defaults", …)
    return
_snapshot = rows
_snapshot_expires_at = now + ttl
_failure_logged_at = None

Three decisions in nine lines. The failure sets the expiry too, so a database outage costs one attempt per 30-second window rather than one attempt per LLM call — without that line, an outage during a busy hour would mean thousands of failing connections. The last known-good snapshot is kept and preferred over env, so an outage degrades to slightly stale config rather than to code defaults. And the log is throttled to at most once per max(ttl, 30 s), because a broken config table must not flood the logs during a stream. (Exactly the same skeleton appears in the agent's two sibling live-config readers — chat/retrieval_config.py and retrieval/brand_policy.py — all three sharing the single llm_config_cache_ttl_seconds knob rather than growing three.)

The public surface is four functions: ensure_llm_config_fresh (async; awaited at the entry points before model construction, and a genuine no-op — not even a thread hop — while the snapshot is warm, otherwise the blocking read goes through asyncio.to_thread), resolve_role_model, resolve_role_thinking_level (where returning None means omit the kwarg), and resolve_model_provider.

The three other config panels — same shape, smaller

Once you have the LLM panel, the rest of /operator/settings is variations on one skeleton, and the variations are the lesson:

The shared shape. A singleton-ish config row (singleton_key = "default", the DocumentRetrievalPolicy idiom); a dumb model with no save() or clean() override, so validation lives in field validators for django-admin and is re-declared in the serializer for the API (DRF does not run model validators for a plain Serializer — ChatRetrievalConfigUpdateSerializer has a comment saying exactly that, "without these two kwargs a PATCH of 0 or 99 would reach save() and land"); a get_or_create under select_for_update() inside a transaction; an updated_by foreign key; and a payload that returns the effective value plus is_stored — the flag that separates "the operator decided this" from "this is just the fallback".

Ingestion alert recipients — a write-through cache, because the reader may not use the ORM

This one has a constraint none of the others do. The alert path (ingestion/alerts.py) is deliberately ORM-free: during the 2026-07 outage a poisoned Celery prefork child made every ORM call raise SynchronousOnlyOperation for days, and except DatabaseError does not catch that. Making the recipient list operator-editable therefore could not put a model read in the alert path. The resolution is a write-through cache, and operators/alert_recipients.py (85 lines) deliberately imports no models at all so that the ORM stays out of that import graph:

ALERT_RECIPIENTS_CACHE_KEY = "ingestion:alert-recipients"
MAX_ALERT_RECIPIENTS = 5

def read_cached_alert_recipients() -> list[str] | None:
    try:
        payload = cache.get(ALERT_RECIPIENTS_CACHE_KEY)
    except Exception:   # the alert path must survive a dead Redis
        logger.warning("Alert recipient cache read failed.", exc_info=True)
        return None
    if not isinstance(payload, dict) or not payload.get("stored"):
        return None
    …

The {"stored": True, "recipients": [...]} envelope — rather than storing the bare list — is what makes a saved empty list meaningful. An empty list with stored: True means "deliberately nobody, send no alerts"; a cache miss means nothing was ever saved and the env fallback settings.INGESTION_ALERT_RECIPIENTS applies. Without the marker the two would be indistinguishable. The cache is written with timeout=None (no expiry) because it is a transport, not a cache in the performance sense — and if Redis is flushed, the degraded window closes the next time anyone reads the settings panel, because build_alert_recipients_payload re-warms it:

row = _alert_recipient_row()
is_stored = row is not None
stored = stored_alert_recipients(row)
cached = read_cached_alert_recipients()
if is_stored and cached is None:
    cached = stored if write_cached_alert_recipients(stored) else None

The panel therefore reports three separate facts — is_stored (the operator decided), is_cached (the alert path can actually see it), and email_backend (whether mail really leaves the box or is printed to the console). The 테스트 메일 button sends through the real alert path with throttle_seconds=0 and its own key, re-warming the cache first, and distinguishes two outcomes that are genuinely separate: "the addresses are saved" (200 with the stored list intact) and "the mail went out" (502 send_failed if it did not).

Chat retrieval width — the row is the transport

One integer: how many naver-cafe documents a single search_changple call hands to the chat model. Default 6, ceiling 16 — and the ceiling is not arbitrary: 16 is the agent's DEFAULT_RERANK_CANDIDATE_LIMIT, the size of the pool the reranker actually orders, so a higher cap could only pad the list with the rerank tail. It is explicitly not the per-turn call budget (MAX_CHAT_RETRIEVAL_CALLS = 4 stays a source constant) and not the published content supplement width.

No Redis write-through here, and the docstring says why: "the row is the transport", read cross-schema by the agent on the same ~30 s TTL snapshot. And the bound is enforced three times — model validator (for django-admin), serializer field (for the API), and a _clamp() on the agent side — so even a hand-written SQL value can never widen the cap past the ceiling. Belt, braces, and a third belt, for a value that multiplies prompt size by up to four.

Notion export — the one with a secret in it

Token plus target database id, for the content export. Two deliberate differences from its siblings: there is no seed row and no env fallback (a fresh environment reads as unconfigured until an operator saves), and the token is never stored or returned in plaintext — only a Fernet ciphertext whose key is derived from SECRET_KEY (urlsafe_b64encode(sha256(SECRET_KEY).digest())), with the API returning a mask. A blank or omitted token on PATCH keeps the stored ciphertext, because the panel only ever holds the mask and so cannot resubmit the real value.

The nicest consequence is a security property that falls out of the encryption for free. A production database dump restored into another environment has a different SECRET_KEY, so the ciphertext will not decrypt — and notion_export_config_state() reports that as unconfigured_reason: "token_unreadable" rather than pretending. A restored dump therefore cannot export into the production Notion workspace by accident.

The observability read models — why they live in documents/

Two of the console's most-used screens are not served by the operators app at all. documents/observability.py (633 lines) backs the corpus coverage tab (GET /api/documents/collection/coverage), the authors tab (collection/authors, …/summary, …/export) and the per-post 진단 readout (/api/documents/<int:post_id>/diagnostic) — all gated by MixedAuthAdminDocumentViewMixin, which is documents' own local copy of the same JWT-or-session + IsOperatorUser pair.

They live in documents/ for a reason worth generalizing: the module reads materialized state, it does not re-derive policy. Its opening line is "Everything here reads the materialized eligibility state written by eligibility_engine; nothing re-derives the predicate (that scatter is what P53.S4 removed) and nothing writes." A "verdict" here — is this author citable, is this post retrievable — is the answer the retrieval rules already computed; the console displays it. annotate_author_verdict makes the point in code:

return queryset.annotate(
    is_citable=Exists(citable_author_queryset().filter(pk=OuterRef("pk"))),
).annotate(
    verdict=Case(
        When(is_banned=True,   then=Value(AUTHOR_VERDICT_BANNED)),
        When(is_citable=True,  then=Value(AUTHOR_VERDICT_CITABLE)),
        When(current_rank="",  then=Value(AUTHOR_VERDICT_UNKNOWN)),
        default=Value(AUTHOR_VERDICT_INELIGIBLE),
        output_field=CharField(),
    ),
)

is_citable is citable_author_queryset() — the single SQL expression of the author gate, not a reimplementation. The verdict annotation only sub-classifies the not-citable case for display, "which is presentation, not policy". The rules themselves belong to explainers 7 and 8. Had the console re-derived them, the corpus screen and the chatbot would eventually have disagreed — which is exactly the class of bug this arrangement was built to end. The same discipline gives the list view and the CSV export one shared queryset builder, "so a download can never disagree with the table it was taken from".

The module's other rule is epistemic, and my favourite line in the console:

A zero is a measurement; an unmeasured code is null

_reason_count_is_observed decides whether the reason histogram may print 0 for a code. A code nothing in the pipeline can stamp today is never "observed" — its true count is unknown, not zero. And for every other code, the count is trustworthy only when the eligibility engine has covered the whole corpus: "One unswept row is enough to make 'zero documents carry this code' a claim we cannot make." A dashboard that renders unknown as zero is lying to the person who trusts it most.

A related honesty, worth a sentence: the coverage tab's brand tiles and the diagnostic's brand gate read the live toggle tables — exactly what retrieval reads — while the histogram's brand_filtered row reports the last sweep's stamp. The two can legitimately disagree for one sweep interval, and the module states that "that disagreement is information, not a bug".

The per-post diagnostic (build_document_diagnostic) returns facts plus a nine-gate state list, computed server-side on purpose — which gate is na rather than pass is a domain question, and shipping raw reason codes for the UI to interpret is precisely the thirteen-site re-derivation that was removed. Its one live-evaluation branch is a nice touch: if the sweep has not reached this row yet, it evaluates that one document read-only, because "a row the sweep has not reached would otherwise read as 'blocked by nothing'". Nothing is written back — the sweep owns materialization.

Finally, documents/retrieval_bench.py (142 lines): the operator's retrieval bench runs the production retrieval path, which lives in the agent, and the agent has no operator concept — its JWT contract carries no user_type. So the chain is web → Django (operator gate) → agent (X-Agent-Service-Token): one synchronous urllib POST to /agent-api/retrieval/operator/explain with a 20-second default timeout. Unreachable, timed out or malformed → 503; the agent's own 5xx → 503 with the upstream detail preserved; the agent's 4xx → passed through with its status, "so a contract mistake shows up as a contract mistake rather than an outage".

Users administration

Four views in accounts/operator_views.py, mounted under /api/admin/users… — an operator can list and search accounts, create an admin, patch one account, reset an admin's password, and activate/deactivate in bulk. The interesting parts are the two guards, which I verified exist and are broader than "you cannot deactivate yourself":

if (instance.pk == request.user.pk
        and (not next_is_active
             or next_user_type != "admin"
             or (instance.is_staff and not next_is_staff)
             or (instance.is_superuser and not next_is_superuser))):
    raise serializers.ValidationError({"non_field_errors": [
        "The current operator cannot deactivate or demote their own account."]})

You cannot deactivate yourself, or demote yourself out of admin, or strip your own staff/superuser bits. The second guard is the system-level one: "At least one active admin account must remain" — the last active admin cannot be deactivated or demoted by anybody, including another admin.

The bulk endpoint is shaped around those guards rather than in spite of them. It is deliberately not the all-or-nothing batch shape used elsewhere in the product: because per-user rejection is a designed outcome, every id gets its own {id, ok, error?} row and the successes commit regardless of the failures. The guards run sequentially in the caller's (deduplicated) id order, each seeing the changes the earlier ids already made — "so deactivating every admin in one batch deactivates all but the last one, and the last one fails with last_active_admin deterministically". The serializer still owns the decision; a small classifier turns its rejection into a stable machine code (self_deactivate, last_active_admin, invalid) so the UI never parses an English sentence.

Closing: a thin layer over rows, and two seams worth copying

Stand back and the operator console backend is unglamorous, which is the compliment it deserves. It is a thin DRF layer over five small tables and a handful of read models, gated by a 28-line permission class, with one convention repeated everywhere — the write returns exactly what the read would, and every payload reports whether the value it just gave you was decided by an operator or fell out of a default.

The engineering that is actually hard lives in the read seams: how a value that lives in a row reaches code that is running right now. This repo has two of them for the same store, and they look nothing alike — an uncached ORM read on the backend because the caller is a once-per-job builder, and a 30-second cross-schema snapshot in the agent because the caller is a hot loop behind an lru_cached settings object. Neither is the "right" way to read config. Each is the right way to read that config from that caller, and both modules wrote the reasoning down where the next person would find it. When you next add an operator-editable setting here, that is the question to answer first: not "where do I store it?" but "how often will the code that obeys it ask, and what does it do on the day the answer does not come back?"

Quiz

Five questions. Click an option to see whether it is right and why.

1. The Django backend's resolve_role_config has no cache at all, while the agent's llm_config.py keeps a ~30-second snapshot. What actually justifies the difference?

The deciding factor is call frequency, stated in both module docstrings. One read per job costs nothing and can never be stale; dozens of reads per chat turn would be wasteful, so the agent pays 30 seconds of staleness to avoid them. (The agent does read raw SQL cross-schema, but that is a consequence of the service boundary, not the reason for the cache.)

2. An operator saves a new model id. The live probe call fails because the Gemini API key is not configured on the backend container. What happens?

REJECTION_STATUS_CODES = frozenset({400, 404}). Everything else — missing key, timeout, network error, 429 quota, 5xx — is an infrastructure failure and must not lock the operator out. Otherwise a provider outage would block exactly the configuration change that works around it.

3. Why can the chat role's thinking_level never be cleared to NULL, when every other role's can?

NULL is otherwise a perfectly good value meaning "send no thinking kwarg". The chat row is special because it is user-visible: the composer's control has to display something. Note the precision — only an explicit null is refused; a model-only update that omits the key is still legal.

4. The ingestion-alert cache holds {"stored": true, "recipients": []}. What does the alert path do with it?

That marker is the whole reason the cache stores an envelope rather than a bare list. Cache hit ⇒ the operator decided, empty included; cache miss ⇒ nothing was ever saved, so env applies. And the alert path may not touch the ORM at all — that is why operators/alert_recipients.py imports no models.

5. Which statement about IsOperatorUser is correct?

Two conditions, no superuser requirement, no roles or scopes. Operator-only endpoints are scattered across /api/admin/, /api/documents/… and /api/content/admin/…, and what unifies them is this class — each app pairs it with its own small authentication mixin so no app has to import another. And enforcement always re-reads the database: the JWT's tier claim gates nothing server-side.
