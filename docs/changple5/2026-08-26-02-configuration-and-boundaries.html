Configuration and boundaries: settings, schema pinning, shared secrets, and live operator config

Explainer #2 of the changple5 builder’s curriculum. How each process learns who it is, what it is allowed to touch, and which knobs it can change without a redeploy.

Background

The previous explainer, Big picture: three apps, one Postgres, one Redis, and how a request travels, drew the shape of the system: a Next.js front end, a Django backend behind /api/, a FastAPI agent behind /agent-api/, one Postgres database split into two schemas, and one Redis split into three logical databases. It stopped at the edge of four questions and promised them to this page:

  • Where does a process get its configuration — database host, API keys, timeouts, feature flags — and when is it allowed to change?
  • How does each app pin itself to its own schema, and how does one of them read across into the other’s?
  • What exactly do the two shared secrets guard, and which arrow carries which?
  • How can the operator change a model id in a web form and have a running Python process pick it up thirty seconds later, with no deploy?

Those four are really one question asked four ways: what does a process know about itself, where did it learn it, and how stale is it allowed to be?

Skip this box if you already know it

Environment variables are a set of NAME=value pairs the operating system hands to a program when it starts. They are the standard way to give a program a secret or an address without writing it into the source code: the code says “read DATABASE_PASSWORD from the environment”, and the password lives outside the repository. A dotenv file (here .dev.env for development, .prod.env on the server) is just a text file of those pairs that some tool loads for you. The critical property, which this page comes back to twice: the environment is handed over once, at process start. Nothing in the operating system pushes an update to a running process when you edit the file.

Skip this box if you already know it

A PostgreSQL schema is a namespace inside one database — a folder for tables. Two schemas can each hold a table called documents without colliding, because their full names are backend.documents and agent.documents. When SQL mentions a bare table name, Postgres resolves it through the connection’s search_path, an ordered list of schemas to look in — the same idea as PATH for shell commands. A role is a Postgres login (a user). Roles are given grants: permission to see a schema, to SELECT from a table, to write to it. changple5 uses these three ideas together to build a wall down the middle of one database.

Skip this box if you already know it

A JWT (JSON Web Token) is a small blob of JSON — here things like user_id, exp, token_type — plus a signature. With the HS256 algorithm the signature is an HMAC computed with a shared secret: whoever holds the secret can both mint tokens and verify them. That is why a JWT lets one service trust another service’s claim about who the caller is without a database lookup or a network round trip — and why the secret is the whole boundary. This page covers only which secret guards which arrow; explainer #3 covers login, minting and entitlements.

What this page does not cover. Login flows, token minting and entitlements belong to explainer #3. The prompt-injection guard, session lockdown and the trial caps belong to #11. The operator console’s writer side — the forms, serializers and permissions behind /operator/settings — belongs to #17. Here we stay on the reading side and on the boundaries themselves.

Intuition

One file, two readers, one habit

Both Python apps start the same way: find a shared env file, read it, and freeze what they found into an object. They do it with different libraries — Django’s django-environ on one side, pydantic-settings on the other — but the resolution rule is written twice, deliberately identically: the file named by CHANGPLE_ENV_FILE, or .dev.env, at the workspace root; plus an optional per-app .env.

That right-hand edge is the load-bearing part. In the agent it is explicit: get_settings() is wrapped in @lru_cache, so the Settings object is built exactly once per process and every later call gets the same instance. In Django it is implicit but identical: settings.py is a module, its env(...) calls run at import time, and a module is imported once. Editing .dev.env while the stack is up changes nothing anywhere until the process restarts.

That is not a defect — it is what you want for a database password. It becomes a problem the moment a human wants to change something while the system is serving traffic: which Gemini model the chat agent uses, how many documents a search hands the model, whether a particular brand’s posts are quoted. Those knobs cannot live in the frozen object. changple5’s answer is the pattern this page builds up to.

Three kinds of knob

Sorting every setting in the repo into three buckets makes the rest of the page easy to read:

KindLives inChanges whenExample
Structuralenv file → process envthe process restarts DATABASE_PASSWORD, JWT_SHARED_SECRET
Operator-live (snapshot)a Django-owned table, read by the agent on a TTL snapshotwithin ~30 s of the operator saving the form a role’s model id, max_tool_results
Operator-live (predicate)a Django-owned table, joined straight into the queryon the very next query brand / branch reference_enabled

The third row is the interesting one. It is not cached at all: the toggle state is a LEFT JOIN inside the retrieval SQL, so flipping a brand off takes effect immediately and is instantly reversible. But that creates a second-order problem — the ranked results of a search are cached in Redis, and a cached result computed under the old toggle state would keep being served. The fix is a small hash of the disabled-id set mixed into the cache key. We will walk it in the Code section; it is the neatest idea on this page.

The wall down the middle of the database

One Postgres database, two schemas, two roles, and a deliberately asymmetric set of grants. Django owns backend and may do anything in it. The agent owns agent (its LangGraph checkpoints and its pgvector chunk tables) and may do anything there — plus SELECT, and only SELECT, on Django’s schema.

Everything the agent knows about users, conversations, documents and operator settings arrives through that dashed arrow — as a plain SELECT. Everything the agent wants to write to Django’s world (a new assistant message, a rolling summary, an indexing result) has to go the long way round: over HTTP, through a Django view, with a credential. That asymmetry is the reason the next diagram exists.

Four arrows, two secrets

Notice the asymmetry in arrow ④. When the agent finishes generating an answer and needs to persist it, it could authenticate to Django as “the agent service” and write wherever it liked. It deliberately does not: for a first-party user it forwards that user’s bearer token, so Django — not the agent’s routing code — decides which conversation may be touched. The privilege boundary is enforced at the far end, by the service that owns the data.

The centrepiece: a knob the operator can turn on a running system

Now put the two halves together. The operator opens /operator/settings and changes the chat model from one Gemini id to another. That is an HTTP request to Django, which writes a row in the backend schema. The agent is a different process, on a different container, holding a frozen Settings object — but it can SELECT across the bridge. So it does, on a timer:

Three modules in the agent implement exactly this shape for three different values. Reading one of them closely, then recognising the other two as the same skeleton, is the fastest way to understand how configuration actually moves through this system.

Code

1. One env file, two readers

The backend resolves the file in apps/backend/config/settings.py, line 13, and reads it immediately below:

# apps/backend/config/settings.py:13

    *,

        shared_env_file or os.getenv("CHANGPLE_ENV_FILE") or ".dev.env"

env = environ.Env(DEBUG=(bool, True))

The agent resolves it in apps/agent/app/config.py, line 15, with a function whose body is the same three lines — and then hands the result to pydantic instead of looping over it:

def get_settings() -> Settings:
    return Settings()

Two style differences are worth naming. First, the agent declares typed fields with defaults and AliasChoices — database_port accepts either DATABASE_PORT or POSTGRES_PORT, and a bad value fails validation at start-up rather than at the first use. Django reaches the same end with per-call converters (env.int, env.float, env.bool, env.list) and explicit default= arguments. Second, and more importantly: in both libraries an already-present process environment variable wins over the file. django-environ’s read_env takes overwrite=False by default, and pydantic-settings ranks environment variables above dotenv files. The file is a source of defaults for local runs, not an override.

The consequence to remember

get_settings() is @lru_cached. One Settings instance per process, built the first time anything asks. app/main.py line 111 pins it onto app.state.settings so every request handler sees the same object. Nothing re-reads the environment, ever. An env-only knob requires a restart — which is exactly why sections 4 and 5 of this page exist.

2. From a file on your laptop to a variable in a container

If you only read the two functions above you would conclude that the containers read .dev.env. They do not — the file is never copied into an image (apps/backend/Dockerfile sets WORKDIR /workspace/apps/backend and copies only that app), so inside a container env_file.exists() is simply false and the loop does nothing. Everything arrives as a real process environment variable, put there by Docker Compose. The Makefile shows the seam:

# Makefile:1
CHANGPLE_ENV_FILE ?= .dev.env
DOCKER_COMPOSE := COMPOSE_BAKE=false docker compose --env-file $(CHANGPLE_ENV_FILE)

--env-file does not pass those variables into the containers. It populates the variables Compose itself interpolates while parsing compose.yaml, and each service block then declares, explicitly, which variables its process gets:

# compose.yaml, django_backend                # compose.yaml, fastapi_agent
environment:                                    environment:
  DATABASE_USER:   ${DJANGO_DB_USER:-django_user}   DATABASE_USER:   ${FASTAPI_DB_USER:-fastapi_user}
  DATABASE_SCHEMA: ${DJANGO_DB_SCHEMA:-backend}     DATABASE_SCHEMA: ${FASTAPI_DB_SCHEMA:-agent}
  JWT_SHARED_SECRET: ${JWT_SHARED_SECRET:-...}      JWT_SHARED_SECRET: ${JWT_SHARED_SECRET:-...}
  AGENT_BACKEND_SHARED_TOKEN: ${AGENT_...:-...}     AGENT_BACKEND_SHARED_TOKEN: ${AGENT_...:-...}

This is how one file gives two processes two different identities through the same variable names. Both apps read a variable called DATABASE_SCHEMA; the backend’s copy is filled from DJANGO_DB_SCHEMA and the agent’s from FASTAPI_DB_SCHEMA. Meanwhile the two secrets are passed through unrenamed to both — because a shared secret is only shared if both sides genuinely receive the same string.

So any value has three rungs to fall through:

  • 1. .dev.env / .prod.env read by Compose at parse time; the operator’s real setting
  • 2. the Compose default in ${VAR:-default} what the service gets when the key is absent from the env file
  • 3. the code default in settings.py / config.py what the process gets when the variable is not in the environment at all
The exact trap — quoted from the architecture doc

“The same class of bug bit three times (an env key present in .dev.env/.prod.env but absent from the per-service compose block, so the code ran its default). P53.S29 measured it end to end — 148 keys × 4 services — and fixed 11 real gaps. The durable invariant to re-check after any compose edit is prod ⊇ dev on every service. The trap that makes a naive fix fatal: django-environ resolves value = None if default is None and value == '', so ${VAR:-} is safe on the backend only when the code default is None — otherwise env.int/env.float raise ValueError and settings import dies. The agent is uniformly empty-safe via pydantic env_ignore_empty.” (docs/current/architecture.md §5)

Read that twice. “Unset” and “set to the empty string” are the same thing to Compose (an unset variable soft-passes as ""), and settings.py leans on it on purpose — DJANGO_CACHE_URL = env("DJANGO_CACHE_URL", default="") or build_redis_url(...) (line 680) treats the empty string as “fall back to the computed URL”. The same idiom applied to an env.int with a numeric default would kill the process at import.

4. Schema pinning, in three places

Explainer #1 sketched the two schemas; here is how each process actually gets pinned to its own. There are three mechanisms, and the two apps use them differently.

a. Django pins its connection with a libpq option

# apps/backend/config/settings.py:146
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        ...
        "OPTIONS": {
            "options": f"-c search_path={DATABASE_SCHEMA}",
        },
    }
}

Every connection Django opens starts with search_path set to backend. Every unqualified table name in every ORM query resolves there, and — note what is missing — public is not in the list, so nothing leaks in from the default schema.

b. A signal handler makes the schema exist and re-asserts the path

# apps/backend/core/db.py:4
def ensure_backend_schema(sender, connection, **kwargs) -> None:
    """Create the configured backend schema when Django opens a fresh DB."""

    if connection.alias != "default" or connection.vendor != "postgresql":
        return
    schema_name = getattr(settings, "DATABASE_SCHEMA", "")
    if not schema_name or schema_name == "public":
        return
    quoted_schema_name = connection.ops.quote_name(schema_name)
    with connection.cursor() as cursor:
        cursor.execute(
            "SELECT 1 FROM information_schema.schemata WHERE schema_name = %s",
            [schema_name],
        )
        if cursor.fetchone() is None:
            cursor.execute(
                f"CREATE SCHEMA {quoted_schema_name} AUTHORIZATION CURRENT_USER"
            )
        cursor.execute(f"SET search_path TO {quoted_schema_name}, public")

It is wired to Django’s connection_created signal in apps/backend/core/apps.py, with a dispatch_uid so a re-import cannot register it twice:

# apps/backend/core/apps.py:9
def ready(self) -> None:
    from .db import ensure_backend_schema

    connection_created.connect(
        ensure_backend_schema,
        dispatch_uid="core.ensure_backend_schema",
    )

This is what makes a fresh database work: the test runner creates an empty database, Django opens the first connection, and the schema springs into existence before the first migration runs. Note the difference from (a): this SET appends , public, so a connection that has been through the signal can also see extension objects living in public — the vector type among them.

c. The agent pins nothing per connection — on purpose

# apps/agent/app/db/connection.py:22
def build_conninfo(settings: Settings) -> str:
    """Build a libpq conninfo string for the shared agent/backend database."""
    return make_conninfo(
        host=settings.database_host,
        port=settings.database_port,
        dbname=settings.database_name,
        user=settings.database_user,
        password=settings.database_password,
    )

No options=, no search_path. The agent relies on the role default the database bootstrap installed once, at cluster init:

# infra/postgres/init/00-bootstrap.sh:112,120  (built with format(...) + \gexec)
ALTER ROLE %I IN DATABASE %I SET search_path TO %I, public

… applied to both roles. So fastapi_user logs in already pointed at agent, public. And when the agent wants a Django-owned table it never relies on the path at all — it qualifies the name explicitly, with a helper that escapes the identifier:

# apps/agent/app/db/connection.py:13
def quote_identifier(identifier: str) -> str:
    return '"' + identifier.replace('"', '""') + '"'


def qualify_table_name(schema_name: str, table_name: str) -> str:
    """Return a schema-qualified, double-quote-escaped SQL identifier."""
    return f"{quote_identifier(schema_name)}.{quote_identifier(table_name)}"

Which is why every cross-schema reader in the agent begins the same way:

# apps/agent/app/llm_config.py:84
BACKEND_SCHEMA_NAME = "backend"
LLM_ROLE_CONFIG_TABLE = qualify_table_name(
    BACKEND_SCHEMA_NAME,
    "operators_llmroleconfig",
)
# -> "backend"."operators_llmroleconfig"

There is exactly one exception in the agent, and it proves the rule. LangGraph’s Postgres checkpointer creates and manages its own tables, and it does that with unqualified SQL that we do not control — so that one connection gets an explicit pin:

# apps/agent/app/db/connection.py:33
def build_checkpoint_conninfo(settings: Settings) -> str:
    """Build a conninfo string for the LangGraph checkpointer connection,
    pinning `search_path` to the agent schema (falling back to `public`)."""
    search_path = f"{settings.database_schema},public"
    return make_conninfo(..., options=f"-c search_path={search_path}")
A non-obvious per-connection side effect

connect_agent_db calls register_vector(connection) before yielding. Without it, pgvector’s vector columns do not round-trip through psycopg — you get strings where you expected arrays. It is easy to miss because it is not part of the connection string; it is a Python-side type registration that must be redone on every new connection. The agent opens short-lived connections per unit of work (there is no pool), so this runs constantly.

d. The grants that make (c) safe

Pinning is about convenience; the grants are about permission. From infra/postgres/init/00-bootstrap.sh, quoted in explainer #1 and worth re-reading with the diagram in mind:

GRANT USAGE ON SCHEMA <django_schema> TO <fastapi_user>
GRANT SELECT ON ALL TABLES IN SCHEMA <django_schema> TO <fastapi_user>
ALTER DEFAULT PRIVILEGES FOR ROLE <django_user> IN SCHEMA <django_schema>
    GRANT SELECT ON TABLES TO <fastapi_user>

The third statement is the load-bearing one: without it, every table a future Django migration creates would be invisible to the agent, and the failure would show up months later as a mysterious permission error on a brand-new feature. And there is no mirror: django_user is granted nothing whatsoever on the agent schema. The wall has a window, and the window only opens one way.

5. The trust boundaries

Two secrets, four arrows. Both secrets are plain strings in the environment, passed unrenamed to every service that needs them, and both comparisons use compare_digest — a constant-time string comparison, so an attacker cannot learn the secret one character at a time by measuring how long a rejection takes.

a. JWT_SHARED_SECRET — minted in Django, verified in the agent

Django is the only minter. Its SimpleJWT policy names the secret directly:

# apps/backend/config/settings.py:577
SIMPLE_JWT: dict[str, object] = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=30),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=30),
    "ALGORITHM": "HS256",
    "AUTH_HEADER_TYPES": ("Bearer",),
    "BLACKLIST_AFTER_ROTATION": True,
    "ROTATE_REFRESH_TOKENS": True,
    "SIGNING_KEY": JWT_SHARED_SECRET,
}

The agent never mints, only verifies — in apps/agent/app/api/dependencies.py, which is where every authenticated route gets its caller:

# apps/agent/app/api/dependencies.py:124  (_build_user_context)
claims = jwt.decode(
    credentials.credentials,
    request.app.state.settings.jwt_shared_secret,
    algorithms=["HS256"],
    options={"require": REQUIRED_ACCESS_TOKEN_CLAIMS},   # ("exp","token_type","user_id")
)
if claims.get("token_type") != "access":
    raise unauthorized("Invalid authentication credentials.")

Two guards there are easy to skim past and both matter. algorithms=["HS256"] pins the algorithm, so a token that claims "alg": "none" is rejected rather than trusted. options={"require": ...} makes the claim set mandatory, so a token without an expiry cannot slip through as “never expires”.

The same secret also signs the anonymous trial credential (the browser-held guest token), and the two token families are kept apart structurally rather than by convention:

# apps/agent/app/api/dependencies.py:306  (_build_guest_trial_context)
claims = jwt.decode(
    provided_token,
    request.app.state.settings.jwt_shared_secret,
    algorithms=["HS256"],
    options={"require": REQUIRED_GUEST_TOKEN_CLAIMS},    # ("exp","token_type","guest_id")
)
if claims.get("token_type") != GUEST_TOKEN_TYPE:         # "guest"
    raise _guest_unauthorized("Invalid authentication credentials.")

# A guest credential must never carry a user principal along with it.
if "user_id" in claims:
    raise _guest_unauthorized("Invalid authentication credentials.")

A guest token requires guest_id and forbids user_id; a user token requires user_id and must say token_type: "access". Neither verifier can be satisfied by the other family’s token, even though one secret signs both. The guest token also travels in its own header, X-Guest-Token, never in Authorization — the comment in apps/agent/app/chat/backend.py gives the reason: Django’s SimpleJWT authenticator raises on a non-access bearer token instead of falling through to the next authenticator, so reusing the header would break the request rather than degrade it.

b. AGENT_BACKEND_SHARED_TOKEN — one static string, used in both directions

This one is not a token in the JWT sense at all; it is a fixed password that says “I am the other half of this system”. It rides in the header X-Agent-Service-Token, and both apps implement the same check. On the agent side:

# apps/agent/app/api/dependencies.py:244
def require_agent_service_context(request, service_token=Depends(service_token_header)):
    configured_token = str(
        getattr(request.app.state.settings, "agent_backend_shared_token", "") or ""
    ).strip()
    if not configured_token:
        raise _unauthorized("Agent service token is not configured.", ...)
    provided_token = str(service_token or "").strip()
    if not provided_token:
        raise _unauthorized("Authentication credentials were not provided.", ...)
    if not compare_digest(provided_token, configured_token):
        raise _unauthorized("Invalid authentication credentials.", ...)
    return AgentServiceContext(service_name="backend-ingestion")

And on the Django side, as a DRF authentication class:

# apps/backend/ingestion/authentication.py:25
class AgentServiceTokenAuthentication(BaseAuthentication):
    def authenticate(self, request) -> tuple[AgentServicePrincipal, None]:
        configured_token = str(settings.AGENT_BACKEND_SHARED_TOKEN or "")
        if not configured_token:
            raise AuthenticationFailed("Agent service token is not configured.")
        provided_token = str(request.META.get(_HEADER_META_KEY, "") or "")
        if not provided_token:
            raise AuthenticationFailed("Authentication credentials were not provided.")
        if not hmac.compare_digest(provided_token, configured_token):
            raise AuthenticationFailed("Invalid authentication credentials.")
        return AgentServicePrincipal(), None

Note that an empty configured token is a hard failure on both sides, not an open door. Mis-deploying the variable makes the boundary refuse everything, which is the safe direction.

The header-picking code makes the intent explicit:

# apps/agent/app/chat/backend.py:540  (_conversation_request_headers)
"""Pick the caller credential for a conversation detail/message call.

* first-party turn -> the user access token (bearer);
* P68 anonymous trial turn -> the caller's own guest token, FORWARDED as-is.
  The agent does not substitute the service token here on purpose: the
  backend then scopes the lookup to that token's `guest_id`, so cross-guest
  isolation is enforced at the backend chokepoint rather than trusted to the
  agent;
* dormant changple_web BFF guest turn -> the service token.
"""

Compare that with the other agent→Django call, the indexing hand-off, which has no human caller to impersonate and therefore does use the service token:

# apps/agent/app/indexing/backend_handoff.py:223
headers = {"X-Agent-Service-Token": self._service_token}

One system, two answers, chosen by whether a user identity exists to carry.

Read the defaults

Both secrets have committed development defaults ("changple-shared-dev-jwt-secret-key-2026", "changple-agent-backend-service-token-2026"), in the code and in compose.yaml’s ${VAR:-default}. That is a deliberate convenience so a fresh clone runs — and a deployment that forgets to set them is catastrophically insecure while looking perfectly healthy, because a well-known signing key means anyone can mint a valid token for any user_id. Nothing in the code can detect this for you: a real secret and the default secret are both just strings.

6. Live operator config across the read bridge — the pattern

Now the centrepiece. The problem statement is in the module docstring, and it is the same argument Figure 1 ended on:

# apps/agent/app/llm_config.py:8
Why a module-level snapshot rather than a settings field: ``get_settings()`` is
``@lru_cache``d (``app/config.py``), so anything derived from the environment is
frozen for the life of the process. A value the operator must be able to change

Three modules do this today, for three different values. Walk the first one fully; the other two are the same skeleton with a different SELECT.

a. app/llm_config.py — which model each role runs

Django’s operators app owns a table with one row per LLM role — a named job like chat, retrieval_rerank, consulting_report, content_architect. Each row holds a model id and an optional thinking level. The operator edits them at /operator/settings. The agent reads them, whole table at a time:

# apps/agent/app/llm_config.py:129
def _fetch_llm_config_rows(settings) -> dict[str, tuple[str | None, str | None]]:
    """Read every stored role row. 12 rows — cheaper than a filtered query."""
    rows: dict[str, tuple[str | None, str | None]] = {}
    with connect_agent_db(settings) as connection:
        with connection.cursor() as cursor:
            cursor.execute(
                f"SELECT role, model_id, thinking_level FROM {LLM_ROLE_CONFIG_TABLE}"
            )
            for record in cursor.fetchall():
                role, model_id, thinking_level = record[0], record[1], record[2]
                slug = _normalize(role)
                if slug is None:
                    continue
                rows[slug] = (_normalize(model_id), _normalize(thinking_level))
    return rows

The state is three module-level globals behind a lock — the snapshot, when it expires, and when the last failure was logged:

# apps/agent/app/llm_config.py:103
_lock = threading.Lock()
_snapshot: dict[str, tuple[str | None, str | None]] | None = None
_snapshot_expires_at: float = 0.0

And the refresh is where all the interesting decisions live:

# apps/agent/app/llm_config.py:148
def refresh_llm_config(settings=None, *, force: bool = False) -> None:
    """Refresh the snapshot when it is stale (or ``force``). Never raises."""
    global _snapshot, _snapshot_expires_at, _failure_logged_at

    now = time.monotonic()
    with _lock:
        if not force and _snapshot_expires_at > now:
            return
        ttl = _cache_ttl_seconds(settings)
        try:
            rows = _fetch_llm_config_rows(settings)
        except Exception as exc:               # broad on purpose
            _snapshot_expires_at = now + ttl   # remember the FAILURE for a window too
            if _failure_logged_at is None or (now - _failure_logged_at) >= max(
                ttl, _FAILURE_LOG_MIN_INTERVAL_SECONDS
            ):
                _failure_logged_at = now
                logger.warning(
                    "LLM runtime config read failed; falling back to %s (%s: %s)",
                    "the last known snapshot" if _snapshot else "env defaults",
                    type(exc).__name__, exc,
                )
            return
        _snapshot = rows
        _snapshot_expires_at = now + ttl
        _failure_logged_at = None
  • time.monotonic(), not time.time(). A clock adjustment (NTP, daylight saving) must not make a snapshot look fresh for an hour or expire instantly.
  • The failure sets the expiry too. A dead database costs one attempt per window, not one per LLM call — and the old snapshot is deliberately not cleared, so the agent keeps serving the last known-good configuration.
  • Log throttling with its own floor. max(ttl, 30 s) means even a TTL of zero (refresh on every call) cannot turn an outage into a log flood during a stream.
  • except Exception is justified in a comment, not left to guesswork: a partially-stubbed settings object raises AttributeError inside build_conninfo long before psycopg is reached, and that path must degrade exactly like a dead network.

There are two freshness helpers, because the agent has both synchronous and asynchronous call paths:

# apps/agent/app/llm_config.py:180
def ensure_llm_config_snapshot(settings=None) -> None:
    """Sync freshness check. Refreshes inline when stale (sync call paths)."""
    if _snapshot_expires_at > time.monotonic():
        return
    refresh_llm_config(settings)


async def ensure_llm_config_fresh(settings=None) -> None:      # :187
    """Async pre-warm for hot paths, so the sync resolvers do no I/O."""
    if _snapshot_expires_at > time.monotonic():
        return
    await asyncio.to_thread(refresh_llm_config, settings)

The async one is awaited at the entry points that precede model construction, so the blocking database read happens in a worker thread instead of stalling the event loop that is streaming tokens to a browser. When the snapshot is warm it does not even hop threads — it is a float comparison.

Finally, the resolvers — the only functions the rest of the app calls:

# apps/agent/app/llm_config.py:207
def resolve_role_model(settings, *, role: str, settings_attr: str, default: str) -> str:
    """Resolve a role's model id: store -> ``settings_attr`` -> ``default``."""
    stored_model, _ = _stored_role_config(settings, role)
    if stored_model:
        return stored_model
    return getattr(settings, settings_attr, default)

That is the DB → env → DEFAULT_* ladder in five lines, and it is why settings.py keeps saying “this is only the middle rung”. resolve_role_thinking_level (line 226) adds one wrinkle worth knowing: it can return None, and None means omit the keyword argument entirely rather than pass a null — because the model builder rejects a null level. It also refuses a stored value outside ("minimal", "low", "medium", "high"), guarding the Django-admin break-glass path where nobody validated the write.

The code is the authority — and it drifts

That docstring says “12 rows”, and docs/current/architecture.md says 13. Counting the registry today (apps/backend/operators/llm_roles.py) gives 25 roles: successive content-agent phases kept adding them. Nothing is broken — the query is SELECT-all-rows and the agent simply ignores the 16 slugs it does not own (they belong to backend-side jobs like conversation_title, image_alt, brand_classification, cost_table_normalize) — but it is a useful reminder for the whole curriculum: comments and docs are orientation, the code is the authority.

b. app/chat/retrieval_config.py — the same shape, one integer

How many documents one chat search hands to the model. Same globals, same lock, same TTL, same fail-open logging. Three differences:

# apps/agent/app/chat/retrieval_config.py:121
cursor.execute(
    f"SELECT max_tool_results FROM {CHAT_RETRIEVAL_CONFIG_TABLE} "
    "WHERE singleton_key = %s",
    (CHAT_RETRIEVAL_SINGLETON_KEY,),          # "default"

  1. The row is a singleton — one row keyed "default", the project’s idiom for “a settings object that happens to live in a table”.
  2. Every rung is clamped to [1, 16] (_clamp, line 85), including the value read from the database. 16 is the size of the reranked candidate pool, so a hand-written SQL value cannot widen the cap past the pool it slices from.
  3. It reuses llm_config_cache_ttl_seconds rather than adding a second TTL field — one TTL for every agent-side operator-config snapshot. The docstring says so explicitly, which is how a pattern stays a pattern.

Note also what the module says it is not: not the per-turn call budget (MAX_CHAT_RETRIEVAL_CALLS = 4), not the published-content supplement width (MAX_CHAT_CONTENT_RESULTS = 3). Retrieval widths are explainer #7’s subject; here it is only an instance of the pattern.

c. app/retrieval/brand_policy.py — the counter-example, and a fingerprint

The operator can switch a brand — or one branch of a brand — out of retrieval. Unlike the two above, this state is not read into Python and cached. It is compiled into the SQL of every retrieval query as a join plus a predicate:

# apps/agent/app/retrieval/brand_policy.py:55
BRAND_POLICY_JOIN_SQL = (
    f"LEFT JOIN {BRAND_TABLE} AS bp_brand\n"
    f"    ON bp_brand.id = ds.brand_id\n"
    f"LEFT JOIN {BRANCH_TABLE} AS bp_branch\n"
    f"    ON bp_branch.id = ds.branch_id"
)

BRAND_POLICY_PREDICATE_SQL = (                                        # :68
    "(ds.brand_id IS NULL OR bp_brand.reference_enabled)"
    " AND (ds.branch_id IS NULL OR bp_branch.reference_enabled)"
)

Read the predicate as English: a document with no brand is never blocked (unclassified is retrievable by default, enforced structurally by the nullable foreign key); a document with no branch is never blocked; and because both clauses must hold, switching the brand off overrides a branch that is still on. LEFT JOIN, not JOIN, is what keeps the un-branded rows in the result at all. The fragment is deliberately parameter-free — the surrounding query builder maintains an order-sensitive positional parameter list, and a predicate needing a bound value would have to be spliced in at exactly the right index. Pure joins sidestep that whole class of bug.

Because it is live SQL, a toggle flip takes effect on the very next query and is instantly reversible. Which creates the second-order problem promised in the Intuition section: ranked retrieval results are cached. A result computed while a brand was enabled would keep being served after it was switched off. The fix is small and elegant — put a fingerprint of the disabled set into the cache key:

# apps/agent/app/retrieval/brand_policy.py:172
def _fetch_fingerprint(settings) -> str:
    """Digest the *disabled* ids only -- the common case is "none disabled"."""
    with connect_agent_db(settings) as connection:
        with connection.cursor() as cursor:
            cursor.execute(f"SELECT id FROM {BRAND_TABLE} WHERE reference_enabled = FALSE")
            brand_ids = sorted(int(row[0]) for row in cursor.fetchall())
            cursor.execute(f"SELECT id FROM {BRANCH_TABLE} WHERE reference_enabled = FALSE")
            branch_ids = sorted(int(row[0]) for row in cursor.fetchall())

    material = (
        f"brands:{','.join(str(value) for value in brand_ids)}"
        f"|branches:{','.join(str(value) for value in branch_ids)}"
    )
    return sha256(material.encode("utf-8")).hexdigest()[:16]

And that read — the fingerprint, not the predicate — is cached on exactly the same TTL snapshot as the other two modules. So the module is both the counter-example and the third instance of the pattern, at the same time.

Toy example. Suppose brands 7 and 12 are disabled and no branches are. The material string is brands:7,12|branches:, whose digest might be 4f2b9a10c7e35d88, and the Redis key for a ranked search becomes something like agent:cache:rank:<query-hash>:4f2b9a10c7e35d88. Re-enable brand 7 and the material becomes brands:12|branches: — a different digest, a different key. The old entries are not deleted; they simply go cold and expire on their own TTL. No invalidation logic, no sweep, no chance of a missed key. The two sentinels matter too: "off" when the caller opted out of the policy entirely, and "unknown" when the toggle tables could not be read — a stable string, so a database blip does not shatter the cache into unique keys.

d. The three constraints that define the pattern

docs/current/architecture.md states them, and all three fall out of what we just read:

  1. It must be read outside get_settings(), which is @lru_cached — otherwise the value is frozen for the process’s life.
  2. The table identifier must be schema-qualified with qualify_table_name(...), because the agent’s own search_path points at agent while these tables live in backend.
  3. A read failure must degrade, never raise. The bridge is read-only and the agent has no write-back path for configuration, so an unreachable table falls through to env and then to a code default, logging once.

And the direction is absolute: writes never cross the bridge. The operator console writes through Django over HTTP; the agent only ever SELECTs.

7. Two small cross-cutting boundaries

a. ApiNoStoreMiddleware — the browser cache is a boundary too

Thirty lines in apps/backend/config/middleware.py, and its docstring is a bug story worth reading in full:

# apps/backend/config/middleware.py:9
class ApiNoStoreMiddleware:
    """Send ``Cache-Control: no-store`` on every ``/api/`` response.

    API payloads are identity-scoped: the user-side and the operator-side
    session providers fetch the SAME url (``/api/auth/me`` above all) with
    different ``Authorization`` headers. Nothing here sends
    ``Vary: Authorization``, so without a caching directive the browser keeps
    one disk-cache entry per url for both identities and, on a history
    navigation, reuses it without revalidating -- which answered the operator
    provider's ``/auth/me`` with the *user's* body and silently swapped the
    session on a back navigation (P67.F5). ``no-store`` closes the whole class,
    not just that endpoint: no ``/api/`` response is meant to be HTTP-cached.
    """

The implementation is four lines, and the guard in it is load-bearing:

    def __call__(self, request):
        response = self.get_response(request)
        if request.path.startswith(API_PATH_PREFIX) and not response.has_header(
            "Cache-Control"
        ):
            response["Cache-Control"] = API_CACHE_CONTROL
        return response

A response that already set its own Cache-Control is left alone — the content delivery views set public, max-age=3600 on media derivatives and no-cache on content HTML, and Django admin’s never_cache sets one too. Blanket-overwriting would have made every image uncacheable. Its position in MIDDLEWARE (second, line 92) is also deliberate and commented: it does no request-phase work, and sitting near the top means its response pass runs last and therefore sees the final headers.

# apps/agent/app/chat/backend.py:505
def _correlation_headers() -> dict[str, str]:
    # FORWARD is gated by the flag; the X-Request-ID itself is always generated
    # by the request middleware (read here from the request-scoped contextvar).
    if not get_settings().enable_correlation_ids:
        return {}
    request_id = get_request_id()
    if not request_id:
        return {}
    return {REQUEST_ID_HEADER: request_id}

Every outbound header builder in that module — bearer, service token, guest token — splats **_correlation_headers() into its dictionary, so a single chat turn carries one id from the browser through the agent into Django and back out into both services’ logs.

Quiz

Five questions. Click an option to see whether it is right and why.

1. An operator edits .prod.env to change GEMINI_CHAT_AGENT_MODEL, and separately changes the chat role’s model on /operator/settings. The agent container is not restarted. What happens?

get_settings() is @lru_cached, so the env-derived Settings object is built once per process — and the file is not even present inside the container. The console edit lands in backend.operators_llmroleconfig, which llm_config.py re-reads across the bridge once its snapshot expires. The ladder is DB → env → DEFAULT_*, so the stored value also outranks the env value when both are set.

2. connect_agent_db never sets search_path, yet the agent successfully reads Django’s operators_llmroleconfig table. Why?

The bootstrap runs ALTER ROLE ... IN DATABASE ... SET search_path TO <schema>, public for both roles, so fastapi_user arrives pointed at its own schema. Every cross-schema reader then builds its table name with qualify_table_name("backend", ...), which does not depend on the path at all. The one connection that does pin explicitly is the LangGraph checkpointer’s, because that library emits unqualified SQL we do not control.

3. The agent has finished generating an answer for a signed-in user and needs Django to persist it. Which credential does it send, and why that one?

Forwarding the user’s own token keeps authorization at the service that owns the data. The same reasoning applies to an anonymous trial turn: the guest token is forwarded so the backend scopes the lookup to that token’s guest_id. The service token is used for the calls with no human caller to carry, such as the indexing hand-off. And the bridge is SELECT-only — there is no SQL write path at all.

4. The brand/branch filter is a live SQL predicate rather than a cached value. What, then, is the fingerprint in brand_policy.py protecting against?

The predicate itself is always current, so live queries are correct. But ranked results are cached, and a cached entry has no idea the policy moved. Mixing a digest of the disabled-id set into the cache key means a flip produces different keys, so stale entries simply go cold instead of needing an explicit invalidation sweep.

5. A compose block is edited so a service gets SCRAPER_REQUEST_DELAY_SECONDS: ${SCRAPER_REQUEST_DELAY_SECONDS:-} and the key is not present in the env file. What is the result?

Compose soft-passes an unset variable as "", and django-environ resolves an empty value to None only when the declared default is None; otherwise the typed converter gets "" and raises. The last option is the trap: the agent is uniformly empty-safe via pydantic’s env_ignore_empty=True, but the backend is not, so the same edit is harmless on one service and fatal on the other.
