Knowledge System Internals: The Content Plane, the Write Path, and the Contracts

This part is the engine room: where a document actually lives, exactly what happens when one is written, and which contracts you may extend but must not break. Background

Physically, this is a small system. One FastAPI process, one SQLite file, one Postgres database, a git repository, and — in production — two more containers for the web app and the MCP service. What makes it interesting is not its size but one decision made early and honored everywhere since. Everything below is downstream of it.

The two planes

The FastAPI process runs two planes at once, and knowing which one you are looking at is the first skill to acquire:

The accounts plane is lazy and dormant: with DATABASE_URL unset the async engine is never created, and /api/* behaves byte-for-byte like the pre-multi-tenant single-token deployment. That dormancy is not a nicety — it is what makes the open-core self-host story work at all. A person who scaffolds their own copy gets a single-tenant knowledge base out of the same code that runs the multi-tenant service, because one environment variable is unset.

Two deployments, one codebase

There is no hosted fork and no "prod mode". The entire difference between what runs on your laptop and what runs at knowledge.hi2vi.com is two flags, both defaulting off:

Local / plugin (default)Hosted
Reads and searchopenbearer required (KB_REQUIRE_READ_AUTH=true)
After the scoped commitnever pushesfetch → rebase → non-force push (KB_GIT_PUSH=true)
Repo it writes toyour working tree (bind mount)its own clone on the box

Read that table as a compatibility contract rather than a configuration list. Every existing local user gets the old behavior by doing nothing, and a hosted-only capability can never leak into a local install by accident. It also means the hosted write path is a publish path: a single POST /api/documents carries a document from JSON all the way to a publicly readable page — file, landing page, index bullet, database row, commit, embedding, push — with no cron, no queue service, and no operator action.

Intuition

The one idea: disk is canonical, the database is a projection

Here is the decision everything hangs from. The files under docs/ are the truth. SQLite is a cache you are allowed to delete.

That sounds like a slogan until you try it. Do this on a running system and nothing is lost:

To make that true, every column in the documents table must be recoverable from the file alone. Follow one document through the rebuild and you can see how each field is re-derived:

ColumnWhere reindex gets it back
title, date, tags, relatedthe file's frontmatter block
rel_path, project, slugthe file's path — <project>/<date>-<slug>.<ext>
format, raw_htmlthe file's extension and its bytes
tenant_idthe content root the file sits in: docs/ → tenant #1, tenants/<uuid>/ → that uuid
versionthe version: frontmatter line — absent means 1

Notice the fourth row. Tenant isolation is encoded in the file path, not only in the database. That is not redundancy; it is a requirement. A tenant_id that lived only in SQLite would be wiped on the next boot, and cross-tenant isolation would quietly evaporate along with it. The multi-tenancy survives a full database rebuild because the filesystem layout carries it.

Three consequences you will meet constantly

Once "the DB is disposable" is real, a chain of otherwise-puzzling decisions becomes obvious:

  1. documents.id is not a durable identity. It is a rowid that a rebuild may reassign. That is precisely why /documents/25 was a poor permanent share link, and why an org's public slug had to be added to Postgres. A public URL is now composed only of parts that survive a reindex: the org slug (durable plane) plus the project name and doc slug (which are already the content plane's durable identity, rel_path).
  2. Version history had to live on disk too. Superseded bodies are archived as files under .versions/; the document_versions table is a projection of them. The invariant is stated bluntly in the backend doc: a version-history feature that stored bodies only in SQLite would be silently erased by the next boot reindex — never build one.
  3. reindex is a repair tool, not a migration. Manual edits, a git reset, an offline fallback write — anything that changes files behind the API's back is fixed by re-deriving. This is why a failed git commit never rolls back the file or the row: the files are canonical, and reconciliation is always available.

The second idea: exactly one writer

The content plane is guarded by a single in-process lock, and the API must run one uvicorn worker. Never scale workers — the lock is in-process, so a second worker would not see it. SQLite's WAL mode gives you concurrent readers for free, which is the half of concurrency this workload actually needs.

Two rules fall out of that, and both are contracts every client must honor. First, push_pending: true with pushed: false is the normal success — never an error, never a reason to retry. Second, and more subtly: a lost or timed-out write response is not evidence of failure. The correct reaction is to read the document back once and find out what actually happened, then at most one retry. Blind retrying is how you create a duplicate — or, now that versioning exists, an unwanted v2.

One rule makes HTML a document type

Adding interactive HTML explainers could have meant a parallel pipeline. It did not, because of a single rule applied identically in two places — the write path and reindex:

body = the on-disk content minus its frontmatter block

md    →  markdown = body                      raw_html = NULL   format = 'md'
html  →  markdown = extract_html_text(body)   raw_html = body   format = 'html'

Because both call sites apply the same rule to the same normalized string, a fresh-database reindex reproduces the write path's row byte for byte. And because the markdown column always holds readable text, FTS5, snippet(), and the embedding input all keep working unchanged — the search machinery never learns that HTML exists.

extract_html_text is a stdlib html.parser subclass that drops script, style, template, and noscript content — no new dependency, and no chance of indexing an explainer's CSS. The raw bytes live in raw_html, which is dropped from every JSON projection: it is served only by the dedicated raw route, never leaked into an ordinary document read.

The write lock, and what may not happen inside it

There is exactly one WRITE_LOCK object in the process, defined only in server/main.py. It is a plain threading.Lock, which means it is not reentrant — and that single fact generates several rules that look arbitrary until you know it:

  • The web app's member-delete route reaches the shared delete helper through a function-level import rather than an extraction, specifically so there is still one lock object, and it must not wrap its own lookup in the lock — the helper takes it.
  • A publish task re-takes the same lock (a rebase mutates the working tree), so tasks are always submitted from outside the critical section. Submitting while holding it would self-deadlock the moment the worker ran.
  • The async accounts plane never touches the lock at all. When a write needs Postgres — to get-or-create the project row, or to resolve the org slug for the response URL — that work runs in an async FastAPI dependency in front of the synchronous handler. That seam is how a Postgres write can precede a SQLite critical section in a handler that cannot await.

The publish worker: a queue, deliberately

server/publish.py is about 120 lines and its docstring is the design document. The worker is one daemon thread started lazily on first submit, and submit does exactly one thing:

def submit(name: str, task: Callable[[], None]) -> None:
    """Queue ``task`` to run after the response. Returns immediately.

    Never raises: enqueuing is the only work done on the request thread.
    """
    global _PENDING
    _ensure_worker()
    with _COND:
        _PENDING += 1
    _QUEUE.put((name, task))

The loop catches BaseException so the worker can never die, logs the failure, and keeps going. Note what is absent: any way for a failure to reach the caller. The response is long gone by then, so a failed push is logged to the container log — which is the operator's surface — and the document republishes on the next successful push.

The docstring also records why this is not Starlette's BackgroundTasks:

Starlette BackgroundTasks would also run after the handler, but ordering against the BaseHTTPMiddleware metering in the stack is subtle — a queue makes "the response never waits" a property of the code, not of the ASGI stack.

That is a good instinct to internalize: when you are fixing a bug caused by a subtle ordering guarantee, do not fix it with a different subtle ordering guarantee.

Bounded git is what makes the lock-holding worker safe

gitops.py is small and strict. add stages only the touched paths and never -A. push is fetch → rebase → non-force push, aborting any in-progress rebase on failure so the local commit is always preserved. Fetch-and-rebase-before-push is both the safety mechanism and the freshness mechanism: the box lands on top of the latest remote at every write, so it can neither clobber operator work nor drift stale.

Every subprocess runs with timeout=config.git_timeout_s() (KB_GIT_TIMEOUT_S, default 60s; an unparseable or non-positive value falls back to 60, so the cap cannot be switched off). Without it a hanging SSH connection would hold the process's only write lock forever — which would be worse than the timeout bug the worker was introduced to fix.

Search: three signals, two fusions

search.py re-ranks the full match set in Python rather than in SQL. The pipeline:

RRF_K = 60
HALF_LIFE_DAYS = 90
RECENCY_WEIGHT = 0.5
# bm25 column weights (title, tags_text, markdown) = 8.0 / 4.0 / 1.0

keyword score = bm25 + RECENCY_WEIGHT * exp(-age_days * ln2 / HALF_LIFE_DAYS)
final         = RRF over [keyword ordering, vector cosine ordering]

Two details worth carrying. First, CJK searchability is achieved at the query layer: build_match_query prefix-expands Hangul/CJK/Kana tokens to "tok"*, so the FTS5 tokenizer never had to change — and changing it would mean rebuilding the index. Second, the degradation path is real: with no Gemini key, or when the query fails to embed, mode is "bm25" and behavior is exactly the pre-vector implementation. Semantic search is an enhancement, never a dependency.

Versioning: the archive is the truth

A re-publish archives the body it is about to replace, then writes the new one at the same rel_path:

ARCHIVE_DIR = ".versions"

docs/knowledge/2026-08-08-example.html                    ← current body, version: 3
docs/.versions/knowledge/2026-08-08-example/v0001.html    ← superseded
docs/.versions/knowledge/2026-08-08-example/v0002.html    ← superseded

Three choices here are worth understanding rather than rediscovering:

  • set_frontmatter_version edits the version: line in place rather than re-serializing the file, so an archived body is a faithful copy — unknown frontmatter fields and the exact bytes survive.
  • The version: line is emitted only for version ≥ 2. A v1 file is therefore byte-identical to a pre-versioning file, which is what makes "no version: means v1" a real no-migration story rather than a backfill job.
  • document_versions is keyed UNIQUE(tenant_id, rel_path, version) and has no foreign key to documents. A rebuild reassigns documents.id, and a legacy drop-and-recreate path would cascade the history away. Keying on the same identity the documents table is unique on makes the archive index survive both — at the cost that any id-keyed route must resolve the document to its rel_path first.

Identity is immutable across a chain: a resolved target whose project or format differs from the request is a 422, never a silent coercion — the rel_path encodes both the project directory and the extension. Conversely a miss is not an error: if the target cannot be resolved, the write falls through to an ordinary v1 create, so an agent that guessed wrong still publishes.

Contracts you may extend but must not break

Three surfaces are pinned, for different reasons:

  • /api/* is frozen. External consumers code against it. Additive fields are fine; changing a status, a key, or a shape is not.
  • The MCP tool contract is v1 and additive-only. The service is a thin proxy that forwards the caller's bearer verbatim upstream, so it inherits corpus scoping with no auth code of its own — and it changed no server/ code to exist.
  • The knowledge-kb config file has two independent implementations — the CLI's config.py and the inline resolver inside the explain skill — which cannot be merged (the skill must work with the CLI uninstalled, and vice versa). Drift is the standing risk. Change one, change the other.

The newest addition shows the house style for adding a field safely. The pretty canonical_path is emitted at the two detail call sites and deliberately not inside the shared list projector — injecting it there would add a Postgres lookup per row on every list page. It carries a round-trip guard: the pretty path is handed out only when resolving it lands back on this row. And the composer checks the org slug first on purpose, so a deployment with no slug claimed short-circuits before touching SQLite at all. One assembly site, one place the rule can be violated, one place to guard it.

The self-reference, paid off. This document travelled the exact path above. The explain skill POSTed it to knowledge.hi2vi.com; the hosted API wrote docs/knowledge/2026-08-08-knowledge-system-internals.html into its own clone of this repository, indexed it, committed it, answered 201, and then pushed to origin/main on the publish worker. The practical consequence for anyone doing this kind of work here: while a phase writes explainers about the repo, the hosted service is committing to that same repo's main from another machine — so local work must git pull --rebase between saves, or the two histories diverge. The system documents itself, and the documentation is a write against the system.

Best practices & next steps

Three of the decisions above have well-established external counterparts, and it is worth knowing which way each one leans.

Where it aligns with prevailing practice

The single-writer rule is SQLite's own guarantee, not a self-imposed limit. The official documentation is explicit that WAL mode permits exactly one writer while readers proceed concurrently: "since there is only one WAL file, there can only be one writer at a time", and "writers and readers can run at the same time" (SQLite WAL documentation — sqlite.org). So the in-process lock is not fighting the database; it is making the database's real constraint explicit at the application layer, where it can be reasoned about — and it is what buys the read concurrency this read-heavy corpus actually needs.

The RRF constant is the standard default, used as intended. Reciprocal Rank Fusion combines several ranked lists without tuning weights, scoring each document as Σ 1/(k + rank) with a default rank constant of 60 — exactly the RRF_K = 60 in search.py (Elasticsearch reciprocal rank fusion reference — elastic.co), which traces the method to Cormack et al.'s 2009 SIGIR paper. Fusing rank positions rather than raw scores is the whole point: BM25 scores and cosine similarities are not on comparable scales, and RRF sidesteps that without a normalization step to get wrong.

Where it deliberately diverges

An in-process queue instead of a task queue. FastAPI's own guidance draws the line by process boundary: use BackgroundTasks when "you need to access variables and objects from the same FastAPI app, or you need to perform small background tasks", and reach for something like Celery when you "need to perform heavy background computation and you don't necessarily need it to be run by the same process… they tend to require more complex configurations, a message/job queue manager, like RabbitMQ or Redis" (FastAPI background tasks documentation — fastapi.tiangolo.com).

This system lands on the same side of that line but takes a third option — a hand-rolled thread and queue.Queue rather than BackgroundTasks — because the work must stay in-process (it takes the process's write lock and mutates the process's working tree), and because it wanted "the response never waits" to be a property of the code rather than of the ASGI middleware stack. That is a defensible divergence, and the cost is stated honestly in the code: the queue is in-memory, so a crash before it drains loses the push — never the save — and the next successful push republishes everything accumulated.

Concrete next steps

  1. Bound the Gemini embed the way git is bounded. Every git subprocess has a timeout precisely because the worker holds the write lock; the worker-side embed has no client timeout, so a stalled embed blocks the single FIFO worker and every push queued behind it until restart. This is already recorded as a deferred job — it is the clearest remaining gap in the P24 design, and the fix mirrors an existing pattern rather than inventing one.
  2. Reconcile the publish queue at boot. Today an unpushed commit waits for the next write to carry it. A startup check for "local main ahead of origin/main → submit a push" would close the crash window without adding a broker, and it fits the existing self-healing philosophy that already gives reindex its startup run.
  3. Consume the sqlite-vec seam when the corpus outgrows the Python cosine loop. Every vector is keyed by doc_id specifically so this stays a local change to two modules; the fusion, the signals, and the mode logic are untouched by it. Do it when a search gets slow, not before — the current loop is honest about being a loop.
  4. Populate the citation url field. Every MCP search hit currently returns url: "" because no document carries a public origin, and consumers are told to treat that as "no citation link". Now that pretty share URLs exist and resolve, the ingredients for a real public origin are present — and populating an existing optional field is additive, so the v1 contract holds.

Quiz

1. You are adding a feature that records who last read each document. Storing it as a new column on the SQLite documents table is a bad idea. Why?

Reindex rebuilds every row from the files on disk, so a column with no file-derived source is silently wiped on the next boot. This is the same trap the version-history design had to avoid: bodies live in .versions/ files and the table is derived from them. Durable-but-not-file-derived data belongs in the Postgres accounts plane instead.

2. A publish task must be submitted from outside the write lock. What goes wrong if you submit while holding it?

The push task takes WRITE_LOCK itself because a rebase mutates the working tree, and threading.Lock is not reentrant. Submitting is only a queue append and never blocks — the deadlock happens later, on the worker thread, which is what makes it an easy mistake to ship.

3. An agent re-publishes a markdown document as HTML, passing the existing document's rel_path as the version target. What does the API do?

Identity is immutable across a version chain, and the 422 says so explicitly ("publish it as a new document instead"). The reason is structural: rel_path encodes both the project directory and the file extension, and the archive directory sits beside it — so a format change is not the same document by any definition the storage layer recognizes.

4. Why is canonical_path emitted at the two detail read sites rather than inside the shared projector both the detail and list routes use?

Cost. The projector is shared with the list route, so putting the emitter there would mean an accounts-plane round trip per row. The related optimization is in the composer itself: it checks the org slug first, so a deployment that has claimed no slug short-circuits without even the SQLite round-trip guard.

5. An operator sets DATABASE_URL to nothing and restarts. What happens?

The accounts plane is a lazy singleton: unset DATABASE_URL means no engine is ever created and the content plane behaves byte-for-byte like the pre-multi-tenant deployment, gated by a legacy regression suite. This dormancy is what makes the open-core scaffold possible — a self-hoster runs the same code as the SaaS with one variable unset.
