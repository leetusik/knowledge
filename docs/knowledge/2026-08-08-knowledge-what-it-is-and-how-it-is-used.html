Knowledge: What It Is and How It Is Used

Part 1 of a five-part series for someone taking over the knowledge project. This part is the product: what it is, who it serves, and how people actually use it. Part 2 is the internals (how a document is written and stored), part 3 the read surfaces (the two front ends), part 4 shipping and running it, part 5 why it is built this way and how to change it. Read them in order — each assumes the one before.

Background

Start with the problem, because everything else in this system is downstream of it. The project's own product doc states it in one line:

Knowledge is scattered across conversations and repos, with no durable, browsable, searchable home.

That sentence is worth unpacking, because the word conversations is doing real work. When you solve something hard with a coding agent — why two nginx configs were fighting each other, why a cache only earned its keep after being measured, how a prompt-injection defense actually works — the understanding exists for about an hour. It lives in a chat transcript that nobody will ever scroll back through, and in a diff whose commit message says fix: nginx routing. The code survives. The explanation evaporates.

Knowledge is the machine that catches those explanations before they evaporate. The pitch is small and specific: when you finish something non-trivial, you type one command, a coding agent reads the real code (not its memory of it) and writes a beginner-friendly explainer, and that explainer is filed somewhere durable, browsable, and searchable. The library grows as a side effect of working.

What a "document" is here

A knowledge document is not a wiki page and not a README. Since P16 it is a self-contained interactive HTML explainer: one HTML file with its CSS and JavaScript inlined, containing a fixed set of sections — Background, Intuition, Code, an optional cited "Best practices & next steps", and a five-question multiple-choice quiz that actually works when you click it. As of P17 that is the only output format; the older markdown house style was retired. The page you are reading right now is one of these documents.

Jargon, defined once. Phase and slice appear throughout this series. This repo is developed with an agentic workspace harness: a phase is a grouped unit of work (P1, P2, … P26), and a slice is one concrete unit inside it. "P19 added public projects" means "the nineteenth phase of work delivered that". Part 5 explains the harness itself; until then, read Pn as a timestamp with a story attached.

How it grew — and why that matters to you

A new maintainer needs to know that this system was not designed all at once. It started as one person's docs/ tree browsed through a MkDocs site, and each phase widened it. The shape you inherit is the accumulated result:

Two facts about the current state that you should hold onto, because they shape every decision in parts 2–5. First, it is live: https://knowledge.hi2vi.com runs the multi-tenant version in production. Second, every web-UI feature is free and nothing is plan-gated — the one intended monetizable surface was always agent retrieval, and billing for it still is not built. When you read the code and wonder where the paywall is, there isn't one.

Intuition

One corpus, four doors

The single most useful mental model for this product is this: there is one body of documents, and there are four different doors into it, each built for a different kind of visitor. Newcomers usually assume the four surfaces are four features. They are not. They are four roles, and knowing which role you are looking at explains most of the design decisions you will meet later.

Take them one at a time:

  • The plugin (P7) is the write door, and the odd one out. It ships two skills: /knowledge:explain, which researches and files an explainer, and /knowledge:setup, which wires you to a knowledge base. Setup has two modes — Connect (the zero-infra default: sign up on the hosted service, paste one key, done) and Scaffold (stand up your own self-hosted copy: site, API, graph, publishing workflow). That second mode is why the plugin is not merely a client: it hands out a working copy of the backend. Part 4 covers the machinery that keeps that copy honest.
  • The CLI (P13) is for someone who lives in a terminal — and, more importantly, for the coding agent driving that terminal. It is deliberately agent-first: a one-shot knowledge init runs signup → project → key → config → verify unattended, passwords never pass through argv, and every command takes --json with a documented exit-code contract. It adds no backend capability; it is a pure client of surfaces that already existed.
  • The web app (P12, deployed P14) is the primary human surface: sign in, a dashboard, project pages, browse/search/read documents, an in-app knowledge graph. All free.
  • The MCP service (P15) is the newest idea and the one people miss. It exposes retrieval to any AI agent as two tools — search and fetch_document — over the standard Model Context Protocol. Its first consumer is real: hi2vi's customer-service bot grounds its answers on hi2vi's knowledge through it. That is the "search as a service" surface, and it is the thing that was always meant to be paid for.

The load-bearing consequence. Three of the four doors are clients of one HTTP API, so a change to that API is a change to three products at once. The API is deliberately frozen for exactly this reason (part 2), and the MCP tool contract is independently pinned at v1 with additive-only evolution, because an external consumer pins to it.

Who owns what: user → org → project → document

The second model you need is ownership, restructured at P18 into a plain four-level chain. Concretely, follow one imaginary user:

Three properties of that chain do most of the work, and each one removes a step a user would otherwise have to perform:

  1. Signup auto-provisions a default org and a default project. There is no empty state where you must create something before you can save.
  2. Projects are get-or-create by name. Saving to a project that does not exist creates it. No client flow — web, CLI, or skill — has a "create a project" step. When an agent runs /knowledge:explain inside a repo, the project name is simply the repo's directory name, so your corpus partitions itself along the repos you actually work in.
  3. One org-level key serves every repo. A vk_ key is mintable at org level and grants the whole org. This was mostly an act of honesty: enforcement had always been org-wide, and a key's project binding only ever drove usage attribution.

A naming trap you will hit within an hour of reading the code. The product says "org" everywhere — chrome, CLI output, skills. Internally, the database table is still called tenants, and the code says tenant_id. The tenant row is the org. The rename was deliberately not done: it would be a large diff with zero behavior change. Read tenant as org and you will never be confused again.

Private by default, public on purpose

Until P19 there was no visibility concept at all. Now every project carries a flag, and private is the default — including for projects that were implicitly get-or-created, which is the case that would otherwise leak. Flipping a project to public opens both its documents and its slice of the knowledge graph to anonymous visitors.

The rule that governs every miss is worth memorizing, because you will see it enforced in the code of parts 2 and 4: 404-never-403. Private, nonexistent, and malformed all answer the same "not found". A private document never reveals that it exists. The graph follows the same discipline — to an outsider, private nodes are absent, not dimmed.

What a shared link looks like

P19 made sharing possible. P25 made the resulting link presentable — and this is a good example of how this project reasons, so it is worth walking through.

The old share link was the document's row id from the content-plane SQLite database:

https://knowledge.hi2vi.com/documents/25

Two things are wrong with that, and only one of them is cosmetic. The cosmetic problem is that it tells a reader nothing. The structural problem is that the number is a rowid in a database the system considers disposable — a full reindex re-derives every row from the files on disk, and there is no promise the number survives. Building a permanent public link out of a disposable identifier is a bug waiting for a maintenance window.

So P25 gave each org a durable, globally unique slug — stored in the accounts plane, which is not disposable — and built readable URLs on it:

https://knowledge.hi2vi.com/@hi2vi/payments-api/why-our-retries-were-doubling-charges
https://knowledge.hi2vi.com/@hi2vi/graph

Notice what is not in that URL: a date. The pretty path is deliberately dateless and means "the newest document under this title" — the natural reading of a shared link. If you need to address one exact row, or one exact past version, the id URL is still there and always resolves. Old links never break; an anonymous visitor on an id URL is temporarily forwarded to the pretty one, while a signed-in member stays put because the id page carries member-only controls.

The subtlety that makes the promise real. A document advertises a pretty URL only when that URL resolves back to it. If a later document reuses the same project and title-slug, the older one quietly stops advertising and keeps its id link — because the alternative is forwarding a reader who followed an old link to different content. "No link breaks" is being applied to what the link shows, not just to its HTTP status.

Explaining the same thing twice

The last product idea is versioning (P23), and it exists because of a specific bug. A document's path encodes the date it was created, and the explain skill derives that date from today. So re-explaining a subject a month later silently produced a second, unrelated post rather than an update.

The skill now looks for the document before it writes: it lists the target project, matches on subject, and reads what the current version said so the new explanation builds on the old one instead of starting cold. Two design choices keep this quiet rather than noisy: only the current version is searchable, embedded, and on the graph — history is deliberately invisible to search — and there is no rollback and no editing. You can read history; you cannot rewrite it.

Code

Everything above is visible in real files. This section walks the artifacts a user actually touches — the two skills, the CLI, the MCP contract — treating them as the product surface. The internals behind them (the write path, the storage model, the schema) are part 2's job.

The write door: plugin/skills/explain/SKILL.md

The explain skill is a ~640-line markdown file that instructs a coding agent, step by step. It is worth understanding as a product spec, because it is the closest thing the project has to one. Its eight steps: resolve the topic and mode, resolve the KB config, research read-only, write the document, save it via the API, handle transport failure, optionally copy into the project, and report.

Two of those steps carry most of the product meaning. Mode resolution is where the skill decides whether you asked about a topic ("explain the retry logic") or a change ("explain what we just shipped"):

- **Change mode** — the arguments name or point at a code change: a diff, a branch,
  a PR, a commit or commit range, a phase, or a phrase like "what we just changed".
- **Topic mode** — anything else: the arguments name a concept, tool, subsystem, or
  file to explain.

Both modes produce the **same document**, with the same four content sections.
Only the lens differs.

That is a real product decision, not an implementation detail: one output format everywhere means a reader never has to learn two document shapes.

The second is the research gate. The "Best practices & next steps" section is default-on, and every claim in it must carry a source link plus the bare domain as plain text:

<p>Request-scoped connection pooling is standard practice for this
(<a href="https://www.postgresql.org/docs/current/runtime-config-connection.html">PostgreSQL
docs</a> — postgresql.org).</p>

Why repeat the domain in text when it is already in the href? Because the search index and the MCP surface store the document's extracted text, and an attribute is not text. A bare "source" link would lose its provenance the moment an agent fetched the document. This is the first of many places where you will find a decision shaped by the fact that documents are read by machines as often as by people.

Where the section goes when research is skipped. If the subject is purely internal — a private repo's own architecture, say — the gate skips web research, and then the section and its table-of-contents entry are simply absent. The document carries no "skipped" note; the chat report explains instead. That is why this explainer has four sections, not five.

The setup door: Connect vs Scaffold

/knowledge:setup is the fork in the road for a new user, and the plugin's README states the two modes plainly:

**Connect** (the zero-infra default): sign up at the hosted KB, mint one ingest key,
paste it, and your explainers post to your own tenant — no server to run, one key
serves every repo.

**Scaffold** (full control): stand up your own self-hosted KB from scratch — a MkDocs
Material site, a FastAPI + SQLite document API, an interactive knowledge graph, and a
GitHub Pages publishing workflow.

Connect mode is what made public multi-user ingestion real at P17: a stranger installs the plugin, signs up in a browser, pastes one key, and their explainers land in their tenant. Note the security shape — email and password never reach the agent; only the minted key does.

Both modes converge on one file, and it is the seam the whole client story hangs from:

~/.config/knowledge-kb/config.json     # mode 0600
{
  "kb_root": "/path/to/a/local/checkout",     # optional — absent in a remote-only config
  "api":  { "base_url": "https://knowledge.hi2vi.com", "token": "vk_…" },
  "site": { "base_url": "https://knowledge.hi2vi.com" }
}

The CLI's knowledge init writes exactly this file, and the explain skill reads it. That is the entire integration between the two: run init once and the plugin starts posting to the hosted service with zero plugin change. Environment variables (KB_API_BASE_URL, KB_API_TOKEN) override it per key, which is the path the landing page recommends for coding agents generally.

The terminal door: the CLI's agent contract

The CLI's own README states the two-token model and the agent protocol compactly:

`init` is idempotent — re-run it any time; it logs in, reuses your project, and keeps
your key. Passwords never go through `argv`: use `--password-stdin`,
`$KNOWLEDGE_PASSWORD`, or an interactive prompt. Your `vk_` API key is show-once and
the CLI stores it for you — it is never printed. Everything except `usage` keeps
working after the 30-day session expires; only `usage` needs `knowledge login`.

Two tokens, two lifetimes: a 30-day session for account operations, and a non-expiring vk_ API key for content operations. Log out and save/search/list/read keep working while usage reports the session expired. That asymmetry is visible from the terminal on purpose — it teaches the model rather than hiding it.

For agents, the contract is deliberately blunt:

Every command also takes `--json` to print the server's payload verbatim; errors go to
stderr with a non-zero exit, never as JSON, so an agent branches on the exit code.

Errors are never a JSON envelope. That means stdout is always "valid JSON or nothing", which is a far easier promise for a program to consume than "JSON, but sometimes it's an error object with a different shape". And knowledge guide prints the whole machine-readable lifecycle contract — bundled in the wheel, so it works offline and is versioned with the code.

The agent door: mcp-server/CONTRACT.md

The MCP service is the only surface with a frozen, versioned, externally-pinned contract, because a consumer outside this repo depends on it. Its own document says so in the first paragraph:

External agents (the first consumer is hi2vi's OpenClaw CS bot) **pin to this
document**: the transport, endpoint, auth header, tool names, and input/output schemas
below are the contract. Changes are **additive-only** within v1.

The two tools are exactly what an agent needs and nothing more — search(query, project?, limit=5) returning ranked hits, and fetch_document(id | rel_path) returning one document's text. Three details in that contract are the product decisions worth carrying forward:

  • The bearer is forwarded verbatim upstream. "No auth logic lives in this service." The MCP server is a thin proxy; the existing tenant resolver does the scoping. One less place for an authorization bug to live.
  • A key sees the whole org's corpus, not one project. The optional project parameter narrows; it does not define the scope. This is the same org-wide enforcement the P18 key change made honest.
  • An HTML explainer is served to agents as extracted text. For a format: "html" document, the markdown field carries the readable text, not the raw HTML — so an agent consuming the corpus never has to parse a page. Consumers are told to tolerate a missing format field and treat it as "md", which is what additive-only evolution looks like in practice.

One honest wart, recorded rather than hidden: every hit's url field is currently "", because no document carries a public citation origin yet. The contract explicitly tells consumers to treat an empty url as "no citation link, not an error", and points at the deferred job that will populate it. Populating a field is additive, so the contract stays v1.

What a save actually returns

Finally, the moment where all four doors meet: publishing. A successful write answers 201 with the document's id, its version, and a URL you can share — and, since P24, with two flags whose meaning trips up everyone the first time:

"pushed": false, "push_pending": true     ← this is the NORMAL success

It reads like a failure and is not. The API deliberately answers before doing any network work: the document is already written, indexed, and committed when you get the reply, and the push to the remote runs in the background just after. Reporting that as "not saved", or retrying because of it, is the single most likely mistake a client can make here — which is why the skill spells out the correct sentence to say ("saved and committed; publishing in the background") and forbids the retry.

The same phase fixed the mirror-image mistake. If the reply never arrives at all, a client used to assume the write failed — but the write is durable before the response is sent, so a timeout proves nothing. Both clients now follow one rule: ask the API what is at the target path, once, before saying anything. Verify, then at most one retry, then stop. Never loop.

This document is its own example. The explainer you are reading was written by /knowledge:explain and published through that exact write path, into project knowledge — which is to say, into the repository that implements the system it describes. Part 2 walks that path line by line and says what that self-reference costs.

Quiz

1. A user runs /knowledge:explain inside a repo called payments-api, but has never created a project by that name. What happens?

Projects are get-or-create by name (P18) — no client flow has a "create a project" step. The skill sends the repo's directory name as the project, and a project that does not exist is created. It is private by default (P19), including when implicitly created — that default is exactly what stops an implicit project from leaking.

2. Why was the org slug stored in the accounts plane rather than alongside the documents?

The content-plane rows — including document ids — are a disposable projection that a full reindex re-derives from the files on disk. That is precisely why /documents/25 was a poor permanent share link, and why the org's public identity had to live in the durable accounts plane.

3. An agent saves a document and gets back 201 with "pushed": false, "push_pending": true. What is the correct response?

This is the normal 201. Since P24 the API answers before doing off-box network work, so the document is already written, indexed, and committed when the reply arrives; the remote push follows in the background. Retrying is the specific mistake that produces a duplicate document or an unwanted extra version.

4. A document that could be reached at /@acme/api/rate-limiting instead keeps advertising only its /documents/{id} link. What is the most likely reason?

The pretty path is dateless and means "the newest document under this title". A document only advertises a pretty URL when that URL resolves back to it; otherwise a reader following the link would land on different content. So the superseded document quietly keeps its permanent id link. (A private project is a decent guess, but then there would be nothing public to share at all.)

5. Which statement about the four surfaces is true?

The MCP service is explicitly "a thin proxy over the frozen search and single-document reads; it reimplements no retrieval" and forwards the bearer upstream, where the existing tenant resolver scopes the corpus. The plugin is the exception to "just a client": its Scaffold mode stands up an entire self-hosted KB. And the CLI and plugin deliberately share one config file, so knowledge init onboards both at once.
