Why Knowledge Is This Way, and How to Change It

Part 5 of five — the last in a series for a new maintainer of the knowledge project. Parts 1–4 described a system: the product, the internals, the read surfaces, and how it ships and runs. This part explains the reasoning that produced all of it, and hands you the machinery for making the next change.

Background

This part has two halves, and the second explains why the first exists.

The first half is the decision record: 1,230 lines in docs/current/decisions.md, spanning twenty-five phases of work, each entry naming what was chosen, what was rejected, and what the choice cost. The second half is the agentic workspace — the phase/slice machinery this repository is developed with.

The connection is the interesting part, and it is easy to miss. A decision log usually decays, because writing one is a separate act of discipline that competes with shipping. Here it does not decay, because durable documentation is versioned once per phase, at the phase review — a required step, not a good intention. Individual slices never write a doc version; they leave a one-line "doc impact" note, and the review consolidates those notes into new versions. So decisions.md is not a file someone remembered to update. It is an artifact the process forces into existence.

That is worth stating plainly, because it changes how you should read every other document in this series: the durable docs are trustworthy not because someone was diligent, but because there is no clean way to finish a phase without producing them.

Intuition

A decision log's value is in the road not taken

The naive reading of a decision record is "here is what we do". That information is already in the code. What the code cannot tell you is what we considered and rejected, and what this choice cost us — and those are exactly the two things a maintainer needs before changing anything, because a change usually amounts to re-litigating an old rejection.

So read these entries backwards: alternatives first, consequences second, decision last. Here are five that still shape daily work, in that shape:

Disk is canonical; the database is disposable Rejected: treating SQLite as the store of record. Cost: every durable fact must be recoverable from a file. Version history had to become an on-disk archive; tenant identity had to be encoded in the path; a public share URL could not be built from a row id.
Mirror the server into the open-core template; do not narrow what ships Rejected: excluding the multi-tenant modules from the scaffold, which would have made the parity guard pass immediately. Cost: a scaffolded knowledge base boots an unused Postgres container, and every future change under server/ re-opens parity and must be mirrored again. Bought: one server, not two — and a self-hoster who can opt into multi-tenancy by setting one variable.
No package registry — install the CLI from a git URL Rejected: publishing to PyPI, npm, or brew. Cost: no registry discoverability and no version-pinned upgrades; upgrading is a re-run of the installer. Bought: zero release ceremony and no account to maintain. The entry is explicit that PyPI "stays a later, separate call" — a deferral, not a rejection on the merits.
One pinned, un-revokable master bearer Rejected: migrating the existing consumer to a normal key (a client change the intent forbade), and making the master a real revokable database credential. Cost: a documented exception that cannot be revoked from the accounts store. Bought: a frozen public contract kept working through the entire multi-tenant migration with zero consumer changes. It fails closed — unresolvable, never silently accepted — when misconfigured.
The agent does not design; it integrates Rejected: keeping the perfectly serviceable design system the agent had already written. Cost: a full-surface stylesheet rebuild, and a hard dependency on the operator's design work landing. Bought: the visual language is operator-owned rather than agent taste — which is why part 3 found a stylesheet section marked never hand-tune it.

Two decisions the earlier parts deliberately deferred to here

Part 2 named a seam it would not justify: the knowledge-kb config file has two independent implementations — one in the CLI, one inlined into the explain skill — which cannot be merged, because each must work with the other uninstalled. The skill is the open-core self-host path; the CLI is the hosted path. Neither may depend on the other's presence.

So two implementations of one contract is the correct answer, and the cost is paid honestly: drift is a permanent standing risk, mitigated only by a test that pins the documented behavior — validated against the skill's actual resolver across a twenty-scenario matrix. The rule that follows is the kind a maintainer needs on a card: anyone editing either side must edit both.

Part 3 named the other: a design round's record is read-only provenance. When the app needed three treatments the design handback had no specimen for, each went into its own header-flagged file rather than being appended to the file that mirrors the canvas. Editing that file would forge a decision the design round never made. The quarantine is not tidiness; it is a truthfulness constraint about who decided what.

Code

The "code" of this part is the machinery. Everything runs through one script:

python3 scripts/workflow.py <command>

The unit of work

A phase is a grouped unit of work; a slice is one concrete unit inside it. A new phase begins with exactly two slices and grows a middle:

Each phase folder holds an intent.md carrying the operator's request verbatim alongside the confirmed, refined interpretation and any clarifying questions that were resolved. The verbatim text is immutable. When a later slice is unsure what was actually asked, that file — not anyone's memory of the conversation — is the source of truth.

Orchestrator and executor

Work is split between two roles. The orchestrator plans each slice, moves the workflow state, commits, and talks to the operator. A dispatched executor does the slice's job in its own context, writes the result, and returns a verdict — but never commits and never changes a status. The point is context economy: the orchestrator stays lean because it never loads the details of the work it delegates.

The tier is chosen by the slice's risk, which makes risk the phase's main cost lever. There is a deliberate exception worth knowing, because this very series depended on it: a slice whose work needs a user-level tool the executors do not have must be run inline by the orchestrator instead. That is why writing these explainers could not be delegated.

Two states people misread

active/ does not mean in flight. A passing review marks a phase done but leaves it in works/phases/active/. Archiving is a separate, manual step. Five phases are sitting there right now, all finished. If you infer "active means in progress" you will badly misjudge the state of the project.

pending is not blocked. pending means "waiting on the operator" — a validation only a human can do, or an action only they can perform. It halts selection entirely: nothing may start, finish, or advance past it. blocked means an impediment the agent cannot resolve. Conflating them either strands work that a person could unstick in a minute, or silently rolls past a gate that existed for a reason.

How to change something

The practical close. Say you want to add rate limiting to the anonymous read surface — the outstanding item from part 4:

1. Capture intent.   Refine the request, ask about anything ambiguous, confirm it,
                     then create the phase — its intent.md holds the verbatim ask.

2. Decompose.        The DECOMP slice surveys the ground and cuts the middle slices,
                     setting each one's risk deliberately.

3. Work the slices.  One at a time: plan → execute → result → commit. A slice that
                     changes durable truth leaves a one-line doc-impact note.

4. Review.           Validate every slice together, judge against the intent, and
                     consolidate the doc-impact notes:

                     doc-new-version --doc security --summary "..." --source P27.REVIEW
                     rebuild-docs

5. Archive later.    A passing review does not archive. Do that deliberately, when the
                     phase is genuinely finished with.

Never patch a file under docs/versions/, and never hand-edit docs/current/*.md — the latter is generated from the former. Both rules exist so that the history of a claim is recoverable, which is the same instinct that produced the on-disk document version archive in part 2. This project keeps its history in the same shape everywhere.

Closing the loop. Part 2 noted that these explainers travel the write path into the repository they describe. There is one more turn: the series you are finishing was itself a phase in the workspace just described — cut into five slices by a decomposition slice, each with a plan written before and a result after, with an intent.md recording what the operator actually asked for. The process documented here is the process that produced the documentation. If you want to know whether it works, you are holding the evidence.

Best practices & next steps

Where it aligns with prevailing practice

The decision log is a decision log in the established sense. An architectural decision record "captures a single AD and its rationale … along with its trade-offs and consequences", and "the collection of ADRs created and maintained in a project constitute its decision log" (Architectural Decision Records — adr.github.io). The widely-used Michael Nygard template, per the same site's template catalogue (ADR templates — adr.github.io), carries five components: Title, Status, Context, Decision, Consequences.

Every entry in decisions.md carries all five — and adds two more that are worth keeping:

  • Alternatives considered. Nygard's Context holds the forces; naming the rejected options as their own field makes the road not taken retrievable rather than inferred. This is the field that makes the log useful to someone contemplating a change.
  • Source. A pointer back to the slice and result file that produced the decision. This is traceability the workspace gives away for free — every decision can be walked back to the work that occasioned it, and the phase intent behind that.

Where it deliberately diverges

Standard ADR practice puts one decision per immutable file, numbered, with superseded records left in place and marked. This project instead keeps one appended log inside a versioned document, with the version history living beside it under docs/versions/decisions/.

The trade is real in both directions. Given up: a stable per-decision URL, and the ability to see one decision's own revision history at a glance. Gained: decisions version in lockstep with the ten other documentation tracks they constrain, so a phase's consequences land across architecture, security, and decisions in one consolidated act rather than three that can drift apart. Since the review is what forces all of them, a per-file scheme would have needed its own separate discipline — which is precisely the discipline that decays.

Concrete next steps

  1. Archive the finished phases. Five completed phases sit in active/ awaiting a rotate, which makes the directory listing a misleading first impression for exactly the audience this series is written for. It is one command, and it is the cheapest accuracy improvement available.
  2. Sweep the deferred triggers periodically, not just opportunistically. Sixteen open jobs each carry a written condition for revisiting them, and at least two have plausibly already fired (the anonymous-read limiter's "before promoting public links to real traffic", and the embed bound's "when touching the publish worker next"). A scheduled read of the trigger column turns a backlog into a queue.
  3. Retire the stale executor-tier file. The agent definitions still include a third tier the contract no longer describes — harmless drift, but the workspace's whole claim is that its written state is trustworthy, and a maintainer reading three tiers where two exist is exactly the failure that claim is supposed to prevent.
  4. Give the two-implementation config seam a shared conformance fixture. The standing drift risk between the CLI resolver and the skill's inline resolver is currently guarded by one side's tests. A checked-in table of input scenarios and expected resolutions — read by the CLI test and executable against the skill's heredoc — would make the twenty-scenario validation repeatable rather than a one-time verification recorded in prose.

Quiz

1. Why does docs/current/*.md stay accurate rather than decaying like most project documentation?

The discipline is structural, not aspirational. Individual slices never run the versioning command — they leave a one-line doc-impact note — and the review consolidates those notes into new versions. There is no clean way to finish a phase without producing them, which is what makes the durable docs trustworthy.

2. You find a phase marked done sitting in works/phases/active/. What does that tell you?

active/ means "not yet archived", not "in flight". Five finished phases are sitting there right now. Reading the directory as a list of in-progress work would badly misrepresent the state of the project — which is why it is worth archiving them.

3. The config resolver has two independent implementations that cannot be merged. Why is that the correct design rather than duplication to be cleaned up?

The skill must resolve config for someone who never installs the CLI, and the CLI must work for someone who never installs the plugin. Two implementations of one contract is the right answer; the cost — permanent drift risk — is paid honestly with a pinned test and the rule that editing either side means editing both.

4. A slice reaches a point where only the operator can verify something. What status should it take?

pending means "waiting on the operator" and is deliberately distinct from blocked, which means an impediment the agent cannot resolve on its own. A pending item stops the loop entirely — nothing may start, finish, or advance past it — and clears only when the operator says so.

5. Compared with the standard Nygard ADR template, what do this project's decision entries add?

The Nygard template carries Title, Status, Context, Decision, and Consequences; every entry here has all five plus those two. "Alternatives considered" makes the road not taken retrievable instead of inferred — the single most useful field for anyone contemplating a change — and "Source" gives traceability back to the work that occasioned the decision.
