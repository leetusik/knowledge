Background

The first surprise waiting for a new maintainer is that this project has two front ends, built years and philosophies apart — and that the older one was retired from production but is still very much in the repository, doing a different job now.

This matters practically. If you open docs/javascripts/graph.js — 1,100 lines of zero-dependency canvas force simulation — and assume it is dead code, you will be wrong twice: it is the renderer the Next app's GraphCanvas was ported from, and it is shipped verbatim to every person who runs /knowledge:setup in scaffold mode. The MkDocs stack is not legacy. It is the open-core product.

The visual language is not the agent's

One provenance fact, stated early because it changes how you should treat these files. The "calm editorial library" design system — warm ivory paper, a single deep-teal accent, Fraunces serif display over Source Sans 3 — came from the operator's Claude Design project, and was integrated rather than invented. Section 1 of extra.css carries an explicit instruction:

§1 Color tokens (Target 1, LOCKED — verbatim) … This section is locked — never hand-tune it.

The same discipline holds in the app: kb-console.css is copied verbatim from the design canvas, and the three places where the app needed something the handback had no specimen for — a prose reader block, a graph token layer, a rail-fold treatment — each live in their own header-flagged, co-located file rather than being appended to it. The reasoning is worth internalizing: the canvas is *the record of a design round*, so editing it would forge a decision that round never made.

Intuition

The public site never calls the API — and that is load-bearing

Your instinct on meeting a documentation site next to a search API is that one calls the other. Here it never does. The MkDocs site's search is lunr running in the browser over a static index, and its knowledge graph is a static graph.json emitted at build time. It has no backend at all.

That is not laziness; it is what buys a specific architectural property. Because the viewer never calls the API, the two services can cohabit one domain behind simple path routing with no CORS and no runtime coupling between them. The moment the site fetched from /api/, the API would need a browser client story — CORS, preflights, and a token in the page. The decoupling is what keeps that door shut.

The sealed-cookie BFF: the browser never holds a token

So how does the authenticated app read the API without becoming that browser client? By not being one. The browser talks only to the Next.js origin; the Next server talks to the backend, server-to-server, with a bearer:

The pattern has a name — a backend-for-frontend — and the payoff here is that a pre-existing invariant ("the API has no browser client by design") survived the arrival of a browser app completely intact.

The central trick: rendering untrusted HTML that still runs

Now the hardest problem this front end solves, and the reason S3 deserves its own document.

A knowledge document can be a self-contained interactive HTML explainer — with a quiz that has to actually work when you click it. So the app must render untrusted HTML with live JavaScript, inside a page that holds a signed-in session. The obvious move is to sanitize the HTML and inline it. That was considered and rejected, because sanitizing strips the <script> and the quiz dies — the feature is gone.

The solution is to run the script but take away everything it could abuse:

The key insight is that sandbox is a subtractive attribute: an empty sandbox denies everything, and each token adds one capability back. Adding allow-scripts alone gives the document script execution and nothing else. Its origin is a special value that fails every same-origin check — which is exactly the property being bought.

The one combination that would undo it all. Adding allow-same-origin beside allow-scripts, for a same-origin document, lets the framed page reach up and remove the sandbox attribute from itself — leaving you no safer than having no sandbox at all. That is why the pin is written as an absolute in this codebase: never allow-same-origin. See the citation in the next section.

The consequence nobody anticipates: you cannot measure it

Opacity cuts both ways. Because the parent cannot touch the framed document's DOM, it cannot ask how tall the content is — so an iframe would either scroll internally (two nested scrollbars, an unpleasant read) or be a fixed guess. The frame has to volunteer its height:

The third message exists because of a race worth studying, since the same shape will bite anywhere a client island listens for a message an already-loaded resource may have sent. The frame's src is in the server-rendered HTML, so the child can load and post its height before the parent island hydrates and attaches its listener. And because the child dedupes — re-posting only on a real change — that missed first message was never repeated. The frame kept its fallback height forever, until some unrelated window resize happened to un-wedge it.

The debugging lesson recorded in the repo is better than the fix. The bug looked branch-specific: the signed-in view broke, the anonymous view seemed fine. It was not — the member branch just loses the race more often, because it hydrates five client islands while the public shell hydrates zero. It only became deterministic under CPU throttling. The note left behind reads: never conclude a client-island bug is branch-specific without re-testing under throttle.

Code

Four route groups

The app's shape is legible from its directory listing:

web/src/app/
  (auth)/{login,signup}            dark "quiet threshold" gate
  (app)/{dashboard,documents,projects/[projectId],graph}
                                   the light console — session required
  (marketing)/page.tsx             the public landing at /
  (public)/                        optional identity: same URL, two branches
    documents/[id]                 · member: app shell + delete + copy-link
                                   · anonymous: lighter public shell
    documents/[id]/versions/[v]    read-only past version
    [org]/[project]/[slug]         /@{org}/{project}/{doc-slug}
    [org]/graph                    /@{org}/graph
  api/{auth,documents}             the BFF route handlers

The (public) group is the interesting one: those pages take an optional identity and render two different branches from one URL. The same link must work for the person who wrote the document and for the stranger they sent it to.

The raw relay: five headers, pinned three times

The iframe's src points at a same-origin BFF route rather than at the backend, and that route is the app's first non-auth route handler — so it self-guards, because the (app) layout guard does not cover /api/*. It validates the id before touching a session, reads the sealed cookie, relays the upstream bytes, and sets five headers explicitly — never copied from upstream:

Content-Type:             text/html; charset=utf-8
Content-Security-Policy:  sandbox allow-scripts; frame-ancestors 'self'
X-Frame-Options:          SAMEORIGIN
X-Content-Type-Options:   nosniff
Cache-Control:            no-store

The CSP sandbox directive is defense in depth: it applies to the top-level document too, so someone who navigates directly to the raw bytes is privilege-stripped exactly like the framed copy. And since the app's global header is X-Frame-Options: DENY, this one path is exempted to SAMEORIGIN — with the identical values asserted at three layers (the backend route, the BFF relay, and the Next config), so no header-precedence rule can resolve to a wrong value.

The height handshake, both sides

The child-side reporter is source text in lib/explainer-height.ts, and the detail that makes it maintainable is where it gets injected: by the BFF raw routes at serve time, not authored into the explainer template. That single choice fixes every explainer already saved and leaves the three byte-parity-guarded copies of the skill file untouched.

The safeguards on the parent side are worth reading literally, because two of them look wrong until you know why:

  • targetOrigin: "*" is mandatory, not laziness. An opaque origin can never be named by a concrete origin string, so there is no value to put there. Nothing leaks: the request message carries no data and is delivered to one specific frame's window.
  • Identity is checked with event.source, never event.origin — for an opaque origin, event.origin is the literal string "null", which is useless as an identity. Comparing event.source === frame.contentWindow is the check that actually means something.
  • The height is clamped to [120, 40000] and shape-checked, and the re-send request is the only trigger that bypasses the child's dedupe — it resets the "last height" but never the budget, so a runaway document stays latched and a parent→child→parent feedback loop is impossible.
  • The child measures body's box, never documentElement.scrollHeight (which is floored by the frame's own height and would ratchet upward forever), and debounces with setTimeout — never requestAnimationFrame, which Chrome does not run in an opaque-origin frame at all.

The /@{org} namespace, and one guard that is load-bearing

P25's pretty URLs are two new routes under a root-level dynamic [org] segment. Next compiles full-path regexes and sorts static before dynamic, so nothing existing is shadowed — verified against the built route manifest and by a live probe. But the consequence is sharp, and recorded:

the pretty doc route is the catch-all for every unmatched 3-segment URL.

Which is precisely why both pages reject an org segment that does not start with @ — before resolving identity and before any upstream call. Without that guard, every junk three-segment URL on the internet would fire a backend request. The @ is a web-plane convention only: it is stripped before calling the backend, which takes the bare slug.

The other rule to absorb here is one line long: pretty URLs are consumed, never composed. The detail shapes carry canonical_path; the web plane reads it and never re-derives a pretty path in TypeScript. There is exactly one deliberate exception — the dashboard panel composes /@{slug}/graph for display, because that page loads no payload carrying one.

A field-placement detail that will confuse you once. canonical_path lives on the /app plane's detail reads and on the graph response — and nowhere else. It is absent from list projections (adding it there would mean an accounts-plane lookup per row) and absent from the /api plane entirely, because that contract is frozen and P25 was additive to /app only. So a document read back through /api/documents/by-path/… shows no canonical_path even while its pretty URL resolves perfectly. Nothing is broken; you are looking at the wrong plane.

Two small things that teach the house style

The graph went quiet. Both maps share one canvas component, but since P22 the in-app map's labels are selection-driven: titleless at rest, one title for the selected node, one for the node under the pointer, and zoom no longer affects labels at all. The public MkDocs map still uses the older zoom-ladder behavior. The operator's report was blunt — a wall of titles — and the fix deliberately changed titles only, leaving the neighborhood-dimming on hover untouched even though that leaves a visible asymmetry.

The rail folds without a flash. The collapsed/expanded preference is a plain cookie read server-side, so the first paint already has the right grid — no localStorage, no post-hydration jump. The cookie is the state, read through useSyncExternalStore rather than mirrored into useState, because a client navigation across route groups remounts the frame from a server render that could predate the last toggle. And the rail is hidden with display: none specifically so its links leave the tab order and the accessibility tree — the one thing a width or visibility trick gets wrong.

Best practices & next steps

Where it aligns with prevailing practice

The sandbox pin matches the platform's own guidance exactly. MDN warns, for a same-origin embedded document, that it is "strongly discouraged to use both allow-scripts and allow-same-origin, as that lets the embedded document remove the sandbox attribute — making it no more secure than not using the sandbox attribute at all", and that without allow-same-origin "the resource is treated as being from a special origin that always fails the same-origin policy" (MDN <iframe> reference — developer.mozilla.org). The repo's absolute — never allow-same-origin — is that warning turned into a rule, and the CSP sandbox directive on the raw response extends the same protection to a direct visit.

Where it deliberately diverges — and why the divergence is right

postMessage with targetOrigin: "*". MDN is emphatic about this: "Always specify an exact target origin, not *, when you use postMessage to dispatch data to other windows. A malicious site can change the location of the window without your knowledge, and therefore it can intercept the data sent using postMessage" (MDN Window.postMessage() — developer.mozilla.org).

This code uses "*" anyway, and is right to. The advice assumes the recipient has a nameable origin; an opaque origin has none, so there is no exact value to supply. The two conditions that make the warning bite are both absent: the message carries no data (it is the four-character request "re-send your height"), and it is delivered into one specific frame's contentWindow, not broadcast. The same MDN page's other instruction — "always verify the sender's identity using the origin and possibly source properties" — is honored, and honored in the only way available here: by source, since origin is the useless literal string "null". That is the shape of a good divergence: the rule's purpose is satisfied, by a different mechanism, because the rule's assumption does not hold.

Concrete next steps

  1. Add a backend ownership field for the share surfaces. The unclaimed-slug hint on the document page needs to know whether the viewer owns the document, and today it infers that from "this document advertises no pretty path" — a proxy that is right in the misleading cases and wrong on another org's name-less document. The repo already states the conclusion: if a future slice needs exact ownership on a share surface, add a backend field — do not infer it in TypeScript. That is a small, contained addition.
  2. Close the loop on the browser-QA residuals. Several items are honestly recorded as owed to the operator's eyes rather than machine-verified: that the quiz actually runs in a real browser, the graph's feel in both color schemes, and whether the hovered-node title should exist at all. There is no browser or jsdom tooling in the repo, which is why these accumulate. A single headless-browser check in CI — the codebase already demonstrates the technique with a CPU-throttled probe — would convert a growing list of residuals into assertions.
  3. Decide the MkDocs viewer's future explicitly. It is retired from production but shipped to every self-hoster, which means its design system and graph renderer are simultaneously dead code and product. Naming that status in one place — rather than leaving a reader to infer it from a P14 note — would prevent the likeliest maintenance mistake, which is "cleaning up" files that a plugin user depends on.
  4. Give the reader and graph blocks a design round when one is due. Three on-token extensions (the prose reader, the graph token layer, the rail fold) exist because the design handback had no specimen for them, and each is quarantined in its own file precisely so a future design pass can formalize and retire them. That deferral is deliberate and correctly structured; it is worth doing rather than letting the quarantine become permanent.

Quiz

1. Why does the explainer iframe use sandbox="allow-scripts" without allow-same-origin, rather than sanitizing the HTML before inlining it?

The feature is the interactivity — an explainer's quiz has to work — so sanitize-and-inline was explicitly ruled out. The sandbox keeps script execution while the missing allow-same-origin gives the document an origin that fails every same-origin check, so it cannot reach cookies, storage, or the parent.

2. The parent island verifies incoming height messages with event.source === frame.contentWindow rather than checking event.origin. Why?

The sandboxed document has no nameable origin, so event.origin arrives as "null" — every such frame reports the same thing. The window identity check is the only one that distinguishes this frame. It is also why the outbound targetOrigin must be "*": there is no concrete origin to name.

3. A document read back through GET /api/documents/by-path/… shows canonical_path: null, yet its pretty /@org/project/slug URL resolves fine. What is going on?

canonical_path is emitted only at the /app plane's detail reads and on the graph response. The /api surface is frozen for external consumers, so P25 added nothing to it. The round-trip guard and the list-projection omission are both real, but neither explains a working pretty URL — you are simply reading the wrong plane.

4. You want to add a page at /settings/billing/history. What must you know first?

Next sorts static routes before dynamic ones, so a fully static path is safe — but the recorded consequence is that /[org]/[project]/[slug] sorts last and catches every otherwise-unmatched three-segment URL. A second all-dynamic three-segment route would race it. No middleware or config change was needed for P25, and none should be needed now.

5. A client-island bug reproduces on the signed-in document view but appears fine on the anonymous one. What does this codebase's experience suggest?

This is exactly the P25.F4 story. The height-handshake race existed on every article view; the member branch hydrates five client islands against the public shell's zero, so it simply lost the race more often. It only became deterministic under Emulation.setCPUThrottlingRate ≥ 4 — hence the recorded lesson.
