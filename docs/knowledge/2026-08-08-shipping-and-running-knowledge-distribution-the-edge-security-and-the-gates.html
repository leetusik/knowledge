Background

This project ships in an unusual way: it does not just run a service, it hands out a copy of itself. That single fact organizes everything in this document — the distribution machinery exists to make the copy trustworthy, and the production machinery exists to make the running service trustworthy, and they are different problems.

Four channels, one repository

ChannelWhat actually ships
The pluginA marketplace manifest plus an isolated payload: two skills and a complete, renderable copy of the server
The CLIA separate package installed straight from git — no PyPI, no npm, no brew — wrapped by a served curl … | bash installer
The hosted serviceThree containers behind a shared nginx edge, deployed by a manual-dispatch GitHub Action

How the threat model actually grew

Security here is not a fixed posture; it is a record of a threat model widening step by step, and reading it that way is how you know which rules are load-bearing:

At first: a personal knowledge base. Modest threat model — no customer data. The concern was hygiene: nothing on the public site should leak the author's local filesystem paths.
Then it became installable. Two new boundaries appeared at once: a payload-isolation rule (nothing personal may ship) and a config model that keeps a hosted version possible.
Then it went on the public internet, holding a write-capable git credential. The corpus was already public, so the exposure is about abuse and write authority, not content secrecy.
Then it grew accounts. The largest shift: real multi-tenant data, emails, and passwords. Everything about hashing, token storage, and cross-tenant isolation dates from here.
Then a document could contain executable untrusted code — an HTML explainer with live JS — which part 3 covered as a mechanism and this part treats as a posture.
Then reads went anonymous. The first unauthenticated read path, built fail-closed at every layer.

Intuition

Distribution: one line of configuration doing all the work

A Claude Code plugin's source directory is copied whole into every installer's cache. That is the entire security model of plugin distribution, and it makes one line the most consequential configuration in the repository:

// .claude-plugin/marketplace.json
{ "name": "knowledge", "source": "./plugin" }

Had that read "./", every person who installed the plugin would receive the operator's docs/ corpus, the works/ workflow state, the data/ database, the .env, and the tokens in it. Pointing at plugin/ ships only the templated knowledge base and the two user-facing skills. Nothing else about the packaging matters as much as this.

The scaffold is a snapshot, and the snapshot is guarded

Now the harder question: how do you hand someone a copy of a server that keeps evolving, without the copy quietly becoming a fork?

The answer is a byte-parity snapshot. The shipped tree under plugin/templates/kb/ mirrors the repo path-for-path, declared by one manifest in three file classes:

That shared renderer is the whole trick. The setup skill uses it to scaffold a user's KB; the CI parity guard uses it to re-render the templates with the operator's real parameters and byte-compare the result against the live repo. If a file drifts on either side, CI fails. There is no second source of truth, and no human is asked to remember to sync anything.

Mirror, don't narrow. When the server grew a multi-tenant accounts plane, the scaffold could have shipped a trimmed-down single-tenant variant. That would have meant two code paths forever. Instead the template ships the whole server, and single-tenant behavior is achieved by one render token: the operator's render supplies a real database URL (so parity matches byte-for-byte), while a scaffold render supplies an empty one → the variable is unset in the container → the accounts plane never wakes up. A configuration value, not a code branch — which is exactly why part 2's "dormant accounts plane" mattered.

The production shape, and the one thing that is not container state

Production is three containers — the API, Postgres, and the Next app — with no published host ports, reachable only by an nginx edge over a shared Docker network. The API works from its own clone of the repository rather than a mounted working tree, because it commits and pushes and therefore needs a real remote and a credential.

The piece worth slowing down for is the edge. Its config files are read-only bind mounts from the host, which makes them declarative host state rather than container state. Changing the routing is a host file drop plus a reload — gated on nginx -t inside the running container, then a graceful reload, never a recreate (a recreate would drop the network attachment).

That property solved a long-standing fragility: because the vhost is a host file on a read-only mount, a co-tenant's deploy on the same box can no longer wipe this site's routing. An older explainer in this very knowledge base describes the previous regime — and the operations doc says plainly to read it as history, not as an operating manual. Documentation ages; that is a maintenance fact, not a failure.

404-never-403: one rule, everywhere

The single most repeated security rule in this codebase is that a resource you may not see is indistinguishable from one that does not exist. Private, cross-org, malformed, and genuinely-missing all answer the same 404. There is no 403 anywhere on these surfaces.

The reason is that a 403 is an affirmative statement that something exists. On a public share surface that is a real leak: an attacker enumerating slugs learns which orgs and projects are real. Notice how far the discipline extends — the slug lookup helper normalizes its input and returns "not found" for anything malformed or reserved with no database round trip at all, so the uniform 404 falls out for free rather than being remembered at each call site.

Code

Three parity gates, and why there are three

scripts/plugin_parity.py   → the shipped scaffold vs. the repo (whole tree)
scripts/skills_parity.py   → the explain-skill copies vs. the canonical one
scripts/site_smoke.py      → the built site's load-bearing invariants

The second exists because the first does not cover it: the template guard checks plugin/templates/kb/ and never looks at plugin/skills/. So a second guard byte-compares the skill copies — including the one served on the landing page at /SKILL.md, which is checked as a full-file identical copy, frontmatter included. That copy is what the landing's "Copy" button fetches, so a fork would be simultaneously a CI failure and a live content divergence.

site_smoke.py is a different kind of gate. It asserts a fixed list of named invariants rather than running mkdocs build --strict, and the reasoning is worth adopting elsewhere: --strict turns any build warning into a hard failure, which would block a future zero-config page add on warning-level noise. Named invariants fail on the things that actually matter and stay quiet about the rest.

The edge's footguns, in order of how badly they bite

1. Setting one proxy_set_header in a location drops the entire inherited set. This is documented nginx behavior, not a quirk (see the citation below). The vhost therefore hoists its shared proxy headers to server level so both locations inherit them — and the moment someone adds a single header inside a location, every other header silently disappears from that location.

2. A duplicate limit_req_zone name breaks the whole edge. The conf.d/ tree is tested and reloaded as a unit and zone names are global across it, so a duplicate is a hard nginx -t failure that blocks the reload for every site on the box. This vhost declares none — and it is why the auth rate limit was implemented in the application rather than at the edge.

3. Never add an IPv6 listen [::]. No sibling config listens on v6, so adding one would silently make this vhost the default server for all v6 traffic on the box. Same family of hazard as default_server, which the catch-all config owns.

Routing itself is ordinary until it is not. Both upstreams are referenced through set $var names with Docker-DNS re-resolution, so the proxy survives either container being recreated. And one route is a regex specifically to beat prefix matching — the raw-HTML explainer path must reach the Next BFF rather than the API, and a plain prefix would lose to /api/.

Deploy ordering is not arbitrary

build  →  migrate  →  recreate + gate the api  →  then web and mcp

Migrations run inside the container — alembic upgrade head — because Postgres publishes no host port, so there is no way to reach it from the host at all. And the API is recreated and health-gated before the web and MCP services come up, because both are its clients: bringing them up against a not-yet-migrated backend would produce a window of confusing 5xx.

Secrets: two credentials that must never be conflated

Push deploy keyDeploy runner key
Directioncontainer → GitHubGitHub Actions → the box
Lives inthe box, and only the boxa GitHub Actions secret
Blast radiuspush to one reposhell on the box

They are deliberately separate ed25519 keys so either can be revoked without touching the other. The house rule is that secrets are box-born and never transit, and the runner key is the one acknowledged exception — its private half must reach GitHub — so it is minted in a umask 077 temporary directory, piped once into the secret store, and shredded. Naming the exception is what keeps the rule meaningful.

The deploy Action is workflow_dispatch-only and branch-guarded, which matters more than it first appears: the API pushes to main on every write, so an automatic push-triggered deploy would let publishing a document redeploy production.

What no gate covers is recorded rather than glossed. There is no browser or jsdom tooling in the repo, so a handful of items are explicitly owed to the operator's eyes: that the quiz actually runs in a real browser, that a direct visit to a raw explainer URL is sandbox-stripped, and how the graph feels in both color schemes. Calling these operator residuals rather than pretending they are covered is the honest move — but the list grows.

The most instructive failure class in the whole repo: silent publishing. Everything the push path needs — the ssh binary, the deploy key, the remote URL, network egress — fails without a loud signal. Writes keep answering 201 while nothing publishes. There is no unit test that can see it; the only guards are an end-to-end assertion and a bring-up capability check. Since the publish moved behind the response, this got quieter still: a failed push appears only as one line in the container log. When you are looking for the riskiest thing in a system, look for the failure that produces a success.

Two more fragilities deserve memorizing because both have already caused real drift. The parity gates are CI-only — a slice that skips them locally ships drift, and that happened twice in one phase. And the config resolver has two independent implementations — one in the CLI, one inline in the explain skill — which cannot be merged, because each must work without the other installed. Anyone editing either side must edit both.

Best practices & next steps

Where it aligns with prevailing practice

Password hashing is the current first-choice recommendation. OWASP's guidance is to "use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism", noting that Argon2id won the 2015 Password Hashing Competition and "provides a balanced approach to resisting both side-channel and GPU-based attacks" (OWASP Password Storage Cheat Sheet — cheatsheetseries.owasp.org). This codebase uses argon2id, stores session and API tokens only as sha256 digests with the raw value returned exactly once, and keeps login responses byte-identical for unknown-email and wrong-password. Verifying the configured memory and iteration parameters against those minimums is a worthwhile five-minute audit.

The header-inheritance footgun is documented behavior, and the vhost is built around it. The nginx documentation states the rule exactly: these directives "are inherited from the previous configuration level if and only if there are no proxy_set_header directives defined on the current level" (nginx ngx_http_proxy_module reference — nginx.org). Hoisting the shared headers to server level is the correct response, and the repo's warning is the official semantics restated as an operational rule. That is what good operational documentation looks like: not a discovery, but a platform behavior written down where the person who will trip over it is standing.

Where it deliberately diverges

No package registry. The CLI installs from a git URL rather than PyPI, with a served shell installer as the friendly path. This gives up discoverability and version pinning through a registry in exchange for zero release ceremony and no account to maintain — a reasonable trade for a solo-operated project, and it is recorded as a deliberate decision rather than an oversight. The mitigation already exists (the installer bootstraps the package manager, so the one-liner works on a clean machine); the residual cost is that upgrades are a re-run rather than a version bump.

Concrete next steps

  1. Rate-limit the anonymous read surface. This is the one unchecked box on the project's own security checklist. The pre-existing rationale for having no throttle ("every call is bearer-gated, one known consumer") stopped being true when anonymous document, raw, and graph reads shipped. They leak nothing — the 404-never-403 discipline and the fail-closed visibility bridge hold — but they are open to volume. Reuse the in-process per-IP limiter already built for the auth grant rather than an edge zone, since a duplicate zone name would break the whole edge.
  2. Run the parity gates before the commit, not after the push. Both guards are CI-only, and drift has shipped twice because of it. A pre-commit hook or a single make check that runs both takes minutes to add and removes an entire recurring failure mode — and the repo already has a Makefile to hang it on.
  3. Give the silent-publish class a loud signal. A failed background push is one line in a container log that nobody reads. Since a failed push means the off-box backup is falling behind, a periodic check comparing the local head against the remote — surfaced anywhere a human looks — would convert a silent failure into a visible one. This pairs naturally with the boot-time push reconciliation suggested in part 2.
  4. Add one headless-browser check to CI. The operator-residual list is growing because there is no browser tooling, yet the repo has already demonstrated the technique — a CPU-throttled devtools-protocol probe caught a hydration race that no unit test could see. One smoke-level check that loads a real explainer and asserts the quiz is interactive would retire several residuals permanently.

Quiz

1. Why is the plugin's payload kept in a plugin/ subdirectory rather than shipping from the repository root?

Payload isolation is the load-bearing boundary of the whole distribution story. The source: "./plugin" line is what keeps docs/, works/, data/, and .env out of every installer's cache. It is arguably the single most consequential line of configuration in the repo.

2. The shipped scaffold contains the full multi-tenant server, yet a scaffolded KB runs single-tenant. How?

Mirror, don't narrow. Shipping a trimmed variant would mean two code paths forever, so the template carries the whole server and dormancy comes from a configuration value: an empty rendered database URL leaves the variable unset, and the lazily-created accounts engine is never created. The scaffold does still start an unused Postgres container — a benign, recorded consequence.

3. You add proxy_set_header X-Request-Id $request_id; inside one location block of the vhost. What happens?

This is documented nginx behavior: the directives are inherited from the previous level if and only if there are no proxy_set_header directives on the current level. Defining one replaces the whole inherited set rather than adding to it — which is exactly why this vhost hoists its shared headers to server level and warns about it.

4. Why is the production deploy restricted to manual dispatch rather than running on every push to main?

Publish-on-write means the running service is itself a committer to main. With a push trigger, every saved explainer would kick off a production deploy — an unbounded feedback loop between the content path and the deployment path. The dispatch-only guard is what keeps those two worlds separate.

5. A document saves successfully and returns 201, but nothing appears in the GitHub repository for days. Which characteristic of this failure makes it the most dangerous class in the system?

Everything the push path depends on — the ssh binary, the deploy key, the remote URL, network egress — fails without a loud signal, and since the publish moved behind the response it is not even visible to the client. The save itself is genuinely durable, so nothing is lost; what is lost is the off-box backup, quietly. A failure that produces a success is always worth more attention than one that produces an error.
