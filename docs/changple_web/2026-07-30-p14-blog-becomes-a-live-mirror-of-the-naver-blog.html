P14: /blog Becomes a Live Mirror of the Naver Blog

How a hardcoded six-post page turned into a paginated, cached, 428-post archive fetched from an undocumented API — with no database, no worker, and no cron job.

Background

창플 (Changple) is a Korean restaurant-startup consultancy, and changple_web is its marketing site — a Next.js 16 app. The company's real publishing happens somewhere else entirely: a Naver blog (blog.naver.com/changple__), where the team has written over 400 columns (칼럼) about opening restaurants — budgets, locations, branding. Naver is Korea's dominant portal, and for a Korean small business the Naver blog is the content platform; the website is a storefront that points at it.

If you have never touched this repo: the site has a /blog page meant to show those columns. Before this change (phase P14 in the repo's workflow), the page was a placeholder wearing real clothes: it rendered six hardcoded posts from a static file, src/content/columns.ts. The cards had no images (a decorative 📝 emoji block instead), and — more tellingly — no links. Clicking a card did nothing. There was also a /blog/[slug] detail route that rendered only a "준비 중" (coming soon) placeholder, marked noindex so search engines would ignore it.

The decision that shaped everything

The operator's request was: show the real posts (title + thumbnail) on /blog, and make each card link out to the actual Naver post. Two architectural paths were on the table:

  1. Ingest: run a worker/cron that periodically scrapes Naver into the site's own Postgres database, then render from the database.
  2. Mirror: fetch from Naver at request time, cache the responses, and own no data at all.

The operator chose to try the mirror first ("not using dedicated worker approach"), with ingestion held back as a fallback. That single decision is why the finished phase contains no database table, no queue, no scheduled job — just one fetch module and one page.

Key concept — own vs. mirror
A page can either own its content (store it, edit it, back it up) or mirror someone else's (fetch, cache, link back). Mirroring is dramatically less machinery — but it means your page's fate is tied to an upstream you do not control, so resilience (caching, graceful failure) becomes the core engineering problem instead of storage.

What the phase had to discover first

Naver has no public, documented API for reading a blog. The phase's decomposition step probed the options and found:

  • RSS was a dead end. rss.blog.naver.com/changple__.xml caps at 50 items and carries zero thumbnails. It cannot serve a 428-post archive with images.
  • The mobile site's internal JSON API works. The Naver mobile web app (m.blog.naver.com) fetches its post list from /api/blogs/<id>/post-list?categoryNo=0&itemCount=30&page=N. It is undocumented, but it returns clean JSON: titles, thumbnails, dates, categories.

Everything in the implementation flows from the quirks of that undocumented endpoint, which the team verified by hand (with curl) before writing any code. That verify-first habit matters: with an unofficial API, every assumption you don't test is a production incident waiting to happen.

Intuition

The shape of the system

Here is the whole architecture on one line: the page asks a fetch layer for "page N"; the fetch layer asks Naver, but only at most once per hour per page, and never lets a failure escape.

The cache is Next.js's built-in data cache: when a server-side fetch() passes next: { revalidate: 3600 }, Next stores the response on disk, keyed by the request URL, and serves it for up to 3600 seconds before fetching again. Because the page number is part of the URL (...&page=2), each page of the archive gets its own independent cache entry — page 1 being popular doesn't keep page 7 fresh, and page 7 being requested doesn't cost page 1 anything. This was the repo's first use of the pattern, which is why the phase documented it so heavily.

Toy walkthrough

Imagine the archive has 68 posts and the API serves 30 per page. Three requests arrive:

RequestUpstream returnshasMore?UI renders

Notice what is absent: the UI never computes "3 pages total". That is deliberate, and it comes from the single strangest fact about this API.

The API lies about its own metadata
The response has a totalCount field — it is always 0. It has a page field — it always echoes 1, whatever page you asked for (verified live: requesting page 15 returns page-15 content with page: 1 in the envelope). So the only trustworthy pagination signal is the shape of the data itself: a full page (30 items) probably has a successor; a short or empty page is the end. hasMore = items.length === 30, and nothing else.

The thumbnail trap

The second discovery was subtler. The API hands you a thumbnail URL per post — and if you request that URL exactly as given, the CDN returns 404. Adding a size parameter makes it work:

Request to mblogthumb-phinf.pstatic.netResult
…/KakaoTalk_Photo_….jpeg (as the API gives it)404
…jpeg + a Referer headerstill 404
…jpeg?type=w773200 (156 KB)
…jpeg?type=w80_blur200 (2 KB blurred preview)

The CDN apparently only serves pre-generated size variants, never the raw original. So the fetch layer's normalizer appends ?type=w773 to every photo thumbnail before the UI ever sees it — the URL that leaves the data layer is render-ready, and the one rule downstream code must obey is: never strip the query string. (A second CDN host, phinf.pstatic.net, serves video-post thumbnails and behaves the opposite way: bare URLs work fine. Two hosts, two behaviors, one normalizer that knows both.)

What the user sees

One more piece of intuition: failure is a first-class state, and it comes in two flavors. "Naver is down / changed its response shape" and "you paged past the end of the archive" both produce zero posts, but they mean different things to a visitor. The fetch layer therefore returns an ok boolean alongside the posts, and the UI words the two cases differently — a retry-later message versus a friendly "nothing here, go back to page 1". A public marketing page must never show a 500 because a third party had a bad minute.

Code

The phase landed as three commits, each one slice of the plan. In diff terms: src/server/naver-blog/posts.ts (+165 lines, new), src/app/blog/page.tsx (rewritten), next.config.ts (+8), and then −163 lines of deletions. Let's walk them in order.

Slice 1 — the fetch layer (src/server/naver-blog/posts.ts)

This module is the only thing in the repo that knows Naver exists. It starts with import "server-only" — a guard package that makes the build fail if any client component ever imports this file, keeping the fetch (and its cache) strictly on the server. The heart of it:

const response = await fetch(postListUrl(pageNo), {
  headers: { Referer: `${MOBILE_ORIGIN}/${NAVER_BLOG_ID}` },
  next: { revalidate: REVALIDATE_SECONDS },   // 3600 — the per-page 1h cache
});

Two things to notice. The Referer header is the API's only "authentication" — without it, Naver answers isSuccess: false. And the next.revalidate option is the entire caching strategy: no cache library, no Redis, just the framework's data cache keyed by URL. The phase review later verified this empirically — after visiting three pages, .next/cache/fetch-cache contained exactly three entries, one per page URL, each tagged "revalidate":3600.

The response is parsed with zod schemas that validate only the five fields the site consumes (logNo, title, date, thumbnail, category) and ignore everything else — so Naver adding fields can never break the page. A malformed item is skipped (and logged) rather than blanking the whole page. And the whole function is wrapped so it never throws:

} catch (error) {
  captureError(error, { route: "/blog", op: "fetchNaverBlogPage", page: pageNo });
  return { posts: [], hasMore: false, ok: false };
}

That return shape — { posts, hasMore, ok } — is the module's entire public contract with the UI. The normalizer also builds the render-ready thumbnail URL:

export function toRenderableThumbnailUrl(raw: string | null | undefined): string | null {
  const url = raw?.trim();
  if (!url) return null;
  if (url.includes("?")) return url;          // already sized upstream — leave it alone
  const host = hostnameOf(url);
  if (host === null || host === VIDEO_THUMBNAIL_HOST) return url;  // video host serves bare
  return `${url}?type=${PHOTO_THUMBNAIL_TYPE}`; // photo host 404s without ?type=w773
}

Small supporting change: the blog's handle moved into src/lib/site.ts as NAVER_BLOG_ID / NAVER_BLOG_URL, because the same string is now a link in the footer, a URL path segment in the API call, and the Referer value — one constant, three consumers, zero drift.

Slice 2 — the page (src/app/blog/page.tsx) and the image config

The page is an async server component with no client-side JavaScript at all — pagination is plain links. Next.js 16 delivers query parameters as a Promise, and awaiting it has a useful side effect:

export default async function BlogPage({
  searchParams,
}: {
  searchParams: Promise<{ page?: string }>;
}) {
  const { page: pageParam } = await searchParams;
  const { posts, hasMore, ok } = await fetchNaverBlogPage(Number(pageParam));
Key concept — dynamic route, cached data
Awaiting searchParams is a "request-time API", which opts the route out of static prerendering — so next build never calls Naver (builds work offline, in CI, anywhere). The page renders on every request, but its data still comes from the 1-hour cache in the fetch layer. Rendering freshness and data freshness are two separate dials, and this phase sets them independently: dynamic render, cached data. The page deliberately adds no export const revalidate — that would duplicate the TTL in a second place — and no force-dynamic — awaiting the params already does the job.

Each card is one big anchor — the whole card is clickable and leaves the site honestly:

<a key={post.logNo} href={post.url}
   target="_blank" rel="noopener noreferrer" className="…card styles…">
  {post.thumbnailUrl ? (
    <Image src={post.thumbnailUrl} alt={post.title} fill
           sizes="(max-width: 768px) 100vw, (max-width: 1024px) 50vw, 33vw" … />
  ) : (
    <div className="…gradient…"><span aria-hidden="true">📝</span></div>
  )}

Using next/image against an external host requires allow-listing it. This was the repo's first remote image host, so next.config.ts gained its first images block:

images: {
  // Both Naver CDN hosts (photo + video thumbnails). No `search` constraint:
  // omitting it is what lets the mandatory ?type= sizing query through.
  remotePatterns: [{ protocol: "https", hostname: "**.pstatic.net" }],
},

The comment is load-bearing. remotePatterns has an optional search field; if you set it, the query string must match exactly, and if you omit it, any query is allowed. Since every photo thumbnail carries ?type=w773, omitting search is not laziness — it is the requirement. This was also the phase's one genuinely unverified risk going in: would the Next image optimizer's own server-side fetch to Naver succeed? The slice proved it against a running production build — curl to /_next/image?url=… returned 200 image/jpeg for both CDN hosts — before the phase declared the approach sound. The documented fallbacks (a plain <img>, then mirroring images locally) were never needed.

Pagination closes the loop on the "API lies" story — 다음 (next) exists only because the current page came back full:

Slice 3 — deleting what the mirror replaced

Only after the new page rendered real data did the phase delete the old world — ordering that matters, because deleting first would have broken the build. Gone: src/app/blog/[slug]/page.tsx (the "coming soon" detail stub — posts open on Naver now, so a local detail route has no reason to exist), src/content/columns.ts (the six hardcoded posts, 90 lines), its line in the content barrel file, and the unit test that pinned the deleted route's metadata. A stale comment in sitemap.ts was updated to match. Net: the site now contains no authored column content at all — /blog is honestly a viewport onto Naver.

Testing stayed deliberately small, per the repo's conventions: the fetch layer's tests cover only the pure functions (the normalizer and URL builders — no network in unit tests), and the page's new test file is four cases with the fetch layer mocked: links carry the right attributes and keep the ?type= query, the placeholder branch, the two empty-state wordings, and the hasMore-driven pager. The heavier verification (accessibility sweep, live behavioral checks, screenshot captures) ran against a real server in each slice's gate and again — independently — at the phase review.

Best practices & next steps

Where this aligns with prevailing practice

Time-based revalidation for third-party data is the textbook pattern. The Next.js fetch reference documents next: { revalidate: n } as exactly this: "specify the resource should have a cache lifetime of at most n seconds," with the data cache keyed per request URL — which is what turns "cache the API" into "cache each page independently" for free (Next.js fetch API reference — nextjs.org). The same page also warns that conflicting options (a revalidate plus no-store, or a second, lower segment-level TTL) silently change behavior — which is precisely why the phase keeps the TTL in one place, the fetch layer, and forbids the route from declaring its own.

Allow-listing image hosts with remotePatterns is the recommended posture. The Image component reference is explicit that patterns exist "to allow images from specific external paths and block all others," supports the **.example.com subdomain wildcard used here, and defines the search semantics the config relies on: an exact-match constraint when present, any query string when omitted (Next.js Image component reference — nextjs.org).

Where it deliberately diverges

The pattern is broader than the two observed hosts. **.pstatic.net admits every subdomain of Naver's CDN domain, not just the two the API currently returns. The docs' spirit is "be as specific as possible"; the phase chose resilience instead, reasoning that Naver shuffling thumbnail traffic to a sibling subdomain should not 400 every card. That is a defensible trade on a single-operator marketing site with no user-generated content — the classic risk of wide patterns is hostile image sources, and every *.pstatic.net host is still Naver. Worth knowing: the same reference notes that redirects from an allowed host are followed without re-checking remotePatterns (tunable via maximumRedirects) — one more reason to keep patterns scoped to a trusted operator rather than truly open (Next.js Image component reference — nextjs.org).

Pagination SEO currently diverges from Google's guidance — knowingly. Google's pagination documentation says: "Don't use the first page of a paginated sequence as the canonical page. Instead, give each page its own canonical URL," and recommends unique ?page=n URLs with plain sequential links (Google Search Central: pagination best practices — developers.google.com). This implementation has the unique URLs and the plain links, but every page canonicalizes to bare /blog. The phase flagged this to the operator rather than fixing it, on the theory that the posts' real, indexed home is Naver — the mirror may not want its deep pages indexed. That is a legitimate product decision, but it is a decision, and it is currently open.

Next steps

  1. Decide the deep-page indexing question. If the archive should be crawlable, give each ?page=N a self-referential canonical (per the Google doc above); if not, an explicit noindex on pages > 1 would make the current implicit stance intentional.
  2. Use the free blur placeholders. The CDN's ?type=w80_blur variant (2 KB, verified working) is a ready-made blurDataURL source for next/image — cards could fade in instead of popping.
  3. Add a "새 창" (new window) cue to cards. Every card opens a new tab with no visual or screen-reader hint; the accessibility sweep passes, but it is a polish gap the review noted.
  4. Watch the upstream. The API is unofficial; its contract can change without notice. The captureError calls already make a silent shape-change visible in logs — periodically checking those logs (or alerting on them) is the cheap insurance policy for this architecture.

Quiz

Five questions. Click an answer to check it.

1. The Naver API response includes a totalCount field. Why does the fetch layer ignore it and compute hasMore = items.length === 30 instead?

Live probing showed totalCount: 0 and page: 1 regardless of the request — the metadata lies, so a full page (30 items) is the only end-of-archive signal available.

2. A future refactor "cleans up" thumbnail URLs by stripping their query strings before rendering. What happens to the photo thumbnails on /blog?

The bare URL 404s even with a Referer header; only ?type=wNNN variants return 200. That's why the normalizer emits render-ready URLs and downstream code must never strip the query.

3. Why does blog/page.tsx deliberately not declare export const revalidate = 3600, even though the data should refresh hourly?

Caching is owned by the fetch layer (next: { revalidate: 3600 }, keyed per page URL). The route is dynamic (it awaits searchParams), and its data freshness is a separate, already-set dial.

4. During next build, how many requests does the build make to the Naver API, and why?

The build output lists /blog as ƒ (dynamic). That keeps builds working offline and in CI; the first real visitor triggers the first upstream fetch, which then serves from cache for an hour.

5. A visitor loads /blog?page=7 while Naver is briefly down. What do they see?

The layer never throws: failures become { posts: [], hasMore: false, ok: false } after a captureError. The UI distinguishes ok: false (retry-later wording) from a genuinely empty page (ok: true), which gets the "coming soon" wording instead.
