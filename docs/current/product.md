# Product

## Status

The knowledge base is built and live across P2–P6 (DB-backed document API, public GitHub Pages site, hybrid search, operator-designed visual system, interactive knowledge graph). As of **P7** the feature also **ships as an installable Claude Code plugin** hosted in this repo — any Claude Code user can install it and scaffold their own knowledge base, not just the operator. The architecture is kept **SaaS-open** (a hosted multi-user version stays possible; nothing hosted is built). As of **P10–P12** that hosted multi-user version is real: the deployment is a multi-tenant SaaS with an **authenticated web app** as the primary user surface — a tenant dashboard, project detail pages, per-tenant document browse/search/read, and an in-app knowledge graph. **All web-UI features are free** — nothing in the web UI is plan-gated; the one planned monetizable feature — a retriever endpoint for AI-agent use — is **not** a web-UI feature, and as of **P15** its *surface* now exists as an **agent-facing MCP retrieval service** ("search as a service"; plan-gating/billing still future). As of **P13** there is a **third distribution surface**: a standalone installable `knowledge` **CLI** — explicitly not a plugin feature — that lets a user working *inside* Claude Code or Codex sign up, log in, configure credentials, and use the knowledge features end to end **without ever visiting the website**, shipped with **bundled agent-readable guide docs** so a coding agent can drive the whole flow. See *CLI + agent-first onboarding (P13)* below. As of **P15** there is a **fourth surface**, and the first *agent-to-agent* one: an **MCP-over-HTTP retrieval service** any AI agent consumes as tools (`search` + `fetch_document`), backed by the frozen retrieval API — the reusable "search as a service" product surface, whose first consumer is hi2vi's OpenClaw CS bot. See *Agent-facing retrieval product surface (P15)* below. As of **P16** the knowledge base holds a **new first-class document type: the standalone, self-contained interactive HTML explainer** — end-to-end across ingest, safe interactive render (the quiz runs), full-text search, and the MCP read path, alongside markdown docs. This is the rendering pipeline for all future explainers (the P17 `/explain` skill upgrade emits this HTML). See *HTML explainer documents as a first-class doc type (P16)* below. As of **P17** the `/explain` skill is upgraded to **always emit that interactive HTML explainer** for **both** topic and code-change modes (the markdown house style is retired — one output format everywhere), adding a default-on, citation-backed **"Best practices & next steps"** web-research section; and **public multi-user ingestion is live** — any plugin user onboards to the hosted KB (`https://knowledge.hi2vi.com`) from `/knowledge:setup` **Connect mode** and posts explainers to **their own tenant with their own `vk_` key**, one key serving every repo. Delivering this executed the long-pending P10–P13 accounts-plane production cutover (now verified live end to end). See *Explain v2 + public multi-user ingestion (P17)* below. As of **P18** the accounts plane is restructured to an explicit **user → org → project** model: signup auto-provisions a **default org + default project**, API keys become mintable at **org level** (one `vk_` grants the whole org — making today's already-tenant-wide enforcement honest), and projects are **get-or-create by name** (no explicit create step in any client flow). Product-facing naming becomes **org** across the web app, CLI, and skills. Org **creation** + member **invites** stay out of scope (deferred **D14**). See *Accounts v2: user → org → project (P18)* below. As of **P19** projects gain **per-project public/private visibility** (private by default, including implicitly get-or-created projects): a public project's docs **and** graph become readable by **anonymous visitors and other users** — the product's **first anonymous read path** — with the graph exposing only public-project nodes to outsiders; and **every save now returns a working direct doc URL** (replacing the retired mkdocs link), shareable once the project is public. Org **creation**/invites, org-slug vanity graph URLs, and anonymous-read rate limiting remain deferred. See *Public projects & direct doc links (P19)* below. As of **P20** the landing hero's onboarding journey is made **real, honest, and the easiest on-ramp** for humans and coding agents: the broken hero install line becomes a **live curl installer** (`curl -fsSL …/install.sh | bash`, which bootstraps `uv` then runs the canonical `git+` install — **not** a PyPI publish, D-P13-1 stands), the depicted `init`/password step becomes honest (a shown password prompt plus a `knowledge init` web-login line — the CLI and web share one accounts plane; no password generator), the **env-var REST path** (`KB_API_BASE_URL`/`KB_API_TOKEN`) is promoted on the landing as the recommended **agent** setup (with its real blockers surfaced), and the canonical **explain skill is published on the landing** — copyable + downloadable at `/SKILL.md` under the parity gate — with agent-first guidance. See *Frictionless onboarding: real hero, env-var quickstart, published skill (P20)* below. As of **P23** a knowledge document has a **version history**: re-explaining a subject publishes **v2/v3 of the same document** instead of a second post, previous bodies stay readable by both agents and the web app, and the old destructive `overwrite` becomes non-destructive. See *Versioned documents (P23)* below.

## Summary

A personal knowledge base. Its content is a `docs/` tree of educational explainer documents written by the `/explain` skill and browsed through a MkDocs Material viewer run via Docker. The same content is served through two consumption tracks: a public static site and a database-backed read/write/search API. As of P7 the whole feature is **packaged as a Claude Code plugin** (`/plugin marketplace add leetusik/knowledge` → `/plugin install knowledge@knowledge`): it ships **`/knowledge:explain`** (write an explainer into your KB) and **`/knowledge:setup`** (scaffold your own KB — API server + MkDocs site + Pages workflow — from scratch), so the feature is usable by anyone, independent of the operator's workspace system.

## Target Users

- The operator (owner and primary reader of the knowledge base).
- Coding agents writing knowledge via the `/explain` skill.
- **Any Claude Code user** who installs the `knowledge` plugin and runs `/knowledge:setup` to stand up their own KB (added P7).
- **A user working inside Claude Code or Codex** who installs the standalone `knowledge` CLI (added P13) to onboard to the hosted SaaS and use the knowledge features from the terminal — driven by their coding agent via the bundled guide — never touching the website.
- **Any AI agent** (added P15) that consumes knowledge retrieval as an MCP tool over HTTP — the first is hi2vi's OpenClaw customer-service bot, which grounds its answers on hi2vi's knowledge; external paying agents later. The agent connects with a project (`vk_`) key, calls `search`/`fetch_document`, and cites the results.

## Problem

- Knowledge is scattered across conversations and repos, with no durable, browsable, searchable home.

## Goals

- Publish the `docs/` tree publicly via GitHub Pages (Track 1).
- Provide a DB-backed read/write/search API to power a future personal web UI with hybrid search (Track 2).

## Non-Goals for Now

- ~~The personal web UI itself.~~ **Delivered in P12** — see *Authenticated web app + free web UI (P12)* below (production deploy + public landing page land in P14).
- An embeddings pipeline (Track 2 leaves a `sqlite-vec` extension point, but no embeddings this cycle) — *resolved P4* (hybrid semantic search is live).
- Editing the `bootstrap_agentic_workspace` repo (the `/explain` update is handled there separately).

## Product Direction

Keep durable product truth here. Update by creating a new version under `docs/versions/product/`, not by patching old versions.

**Distribution & SaaS-open (P7).** The feature is now distributed as a Claude Code plugin (marketplace + isolated payload), so its reach is no longer limited to the operator's machine. Per operator direction, knowledge may eventually become a **SaaS-like** hosted, multi-user product — not today's work, but the plugin's config model (per-user config file, bearer auth, local-vs-remote resolution) is deliberately kept from precluding a hosted version. Building the hosted service is out of scope for now.

**Authenticated web app + free web UI (P12).** The primary user surface is now an authenticated web app (Next.js, in `web/`): sign up / sign in, a tenant dashboard, project detail pages (with show-once `vk_` credentials), per-tenant document browse/search/read, and an in-app knowledge graph. **Every web-UI feature is free** — the knowledge graph and the Claude Code-facing surfaces included; nothing in the web UI is plan-gated. The one planned monetizable feature is a retriever endpoint for AI-agent use, which is **not** a web-UI feature — its *surface* is **delivered in P15** as the agent-facing MCP retrieval service (billing/plan-gating still future); see *Agent-facing retrieval product surface (P15)* below. This resolves the earlier "the personal web UI itself" non-goal: it is built (production deploy + a public landing page land in P14).

**CLI + agent-first onboarding (P13).** P13 adds a **third distribution surface** beside the plugin and the web app: a standalone installable `knowledge` CLI (its own package, `uv tool install`, console script `knowledge`) so a user who lives inside Claude Code or Codex can run the entire lifecycle from the terminal — sign up, log in, set up credentials against the hosted SaaS, then `save`/`search`/`list`/`read`/`projects`/`usage` — **without visiting the website**. This directly delivers the operator's "let's say you are my user" intent. Two product properties define it:

- **Agent-first, non-interactive.** The CLI is designed to be driven by a coding agent, not typed by a human: a one-shot `knowledge init` runs the whole signup→project→credential→config→verify sequence unattended, passwords never come from interactive flags, and every command has a machine-readable `--json`/exit-code contract. The CLI *writes the config seam* that `/knowledge:explain` already reads — so a single `init` lights up the plugin against the hosted SaaS with zero plugin change.
- **A second deliverable: bundled agent-readable guide docs.** A `knowledge guide` command emits the full machine-readable lifecycle contract (every non-guessable constraint included), **bundled in the CLI package** so it works offline and is versioned with the code — the intent's explicit "proper guide docs so a user doesn't even need the website" deliverable. Discovery is install-instruction tails aimed at agents (READMEs + the `--help` epilog), not a served API doc.

The existing `/knowledge:explain` + `/knowledge:setup` plugin **stays untouched** as the self-host, open-core path; the CLI is the hosted-SaaS onboarding path. Knowledge saving and the Claude Code connection remain **free-tier** — the CLI adds no paid gating. (One honest caveat: the hosted flow is code-complete and edge-routed, but end-to-end on prod awaits a one-time operator cutover of the P10–P12 accounts plane — see operations.)

**Agent-facing retrieval product surface (P15).** P15 delivers the reusable **"search as a service"** surface the operator intended from the start: a **knowledge-owned MCP server over HTTP** that exposes retrieval to *any* AI agent as tools — `search` (ranked, corpus-scoped, citable hits) and `fetch_document` (full markdown for deeper grounding) — over the standard Streamable-HTTP transport, authed by a project (`vk_`) key. This is the product move behind the operator's decision to let **knowledge own retrieval for other services** rather than bolt a one-off shim into each consumer. It **realizes/subsumes the long-deferred D6** ("paid-plan retriever endpoint for external AI agents"), and its **first consumer is real dogfooding**: hi2vi's own customer-service chatbot (OpenClaw) grounds its answers on hi2vi's knowledge through this surface, and the identical interface serves external paying agents later. Two product notes: (1) the surface is **dual-reachable** — a co-tenant agent reaches it internally with no public hop, and off-box agents reach it at `https://knowledge.hi2vi.com/mcp` — and the tool contract is **stable + versioned** (v1) so consumers pin to it; (2) P15 builds the retrieval *surface* (free / internal dogfooding first) — **billing and plan-gating are not built**, so the monetization D6 imagined is a future step and every web-UI feature stays free. See **api** for the tool contract, **architecture** for how it wraps the frozen retrieval API, and **operations** for the deploy.

**HTML explainer documents as a first-class doc type (P16).** Until P16 a knowledge document was markdown. P16 makes a **standalone, self-contained interactive HTML explainer** (a single HTML file with inline CSS+JS — Background / Intuition / Code / Quiz sections, an interactive multiple-choice quiz, HTML diagrams, responsive) a **first-class KB document type end-to-end**: the document API accepts it (additive `format` field), it is stored under `docs/<project>/` alongside markdown, the web app **renders it with its interactivity intact** (the quiz JS runs) while preserving the "XSS-safe by construction" stance via a sandboxed opaque-origin iframe, full-text search indexes its extracted readable text, and the MCP read path returns it sanely. Existing markdown documents are **unaffected — byte-for-byte**. This is item 4 of the operator's request, and it lands the **rendering pipeline first** so emitted explainer HTML is renderable the moment the P17 `/explain` skill upgrade ships (P17 = the skill upgrade + public ingestion; the cross-repo order is bootstrap P7 → knowledge P16 → knowledge P17 → bootstrap P8). No new services, deploy topology, or monetization change — the surface is free like the rest of the web UI. See **api** (the additive contract), **architecture** (the doc-type + opaque-origin render), **backend**/**data** (storage + extraction), and **frontend**/**experience** (the render).

**Explain v2 + public multi-user ingestion (P17).** P17 completes the operator's explain-skill request (items 1 + 3 + the follow-up). Two product moves:

- **The explainer is now always the interactive HTML page.** `/knowledge:explain` emits a single self-contained interactive HTML explainer — Background → Intuition → Code → **Best practices & next steps** → a 5-question interactive quiz — for **both** modes (explaining a topic and explaining a code change/diff/phase). The old markdown house style is fully removed; there is one output format everywhere. The **"Best practices & next steps"** section is **default-on**: web research compares the implementation to prevailing external practice and proposes 2–4 concrete next steps, **every claim carrying a visible-domain source link** ("no citation, no claim"). A judgment gate skips it for purely-internal subjects and trivial fixes, and it **degrades gracefully offline** (this skill runs unattended at automated phase reviews, so the offline path must never hang or fail the save). Trailing `research` / `no-research` flags force it on/off.
- **Public multi-user ingestion.** Plugin users no longer need to self-host: `/knowledge:setup` **Connect mode** signs a user up on the hosted KB, mints one `vk_` key, and writes the config the explain skill reads — so `/explain` posts explainers to **that user's own tenant with their own key**. **One key serves every repo** (the skill sends the repo dirname as each doc's `project`; the key's bound project is usage attribution only), and email/password never cross the agent — only the minted key does. The self-host **Scaffold mode** is preserved. This shipped by executing the P10–P13 accounts-plane production cutover (verified live: signup → project → `vk_` → HTML ingest → sandboxed render → tenant search → MCP `vk_` read). No monetization change — this surface is free like the rest.

**Accounts v2: user → org → project (P18).** P18 restructures the accounts plane from today's user / tenant-named-"X's workspace" / project shape into an explicit **user → org → project** model, without renaming anything internally (the tenant row *is* the org; the rename would be a large, zero-behavior-change diff — see decisions/architecture). Four product moves:

- **Signup auto-provisions a default workspace.** Every new user gets a `"default"` org and a `"default"` project created atomically at signup (replacing the old `"<localpart>'s workspace"` tenant naming). A user never has to create a project before saving.
- **Org-level API keys.** A `vk_` key is now mintable at **org level** — one key grants the whole org, serving every project/repo. This makes honest what was already true: enforcement was always tenant-wide (a `vk_` resolved to the tenant and the write path never checked the doc's `project` against the key); the key's project binding only ever drove usage attribution. Existing per-project keys keep working unchanged.
- **Projects are get-or-create by name.** Saving to a project that does not exist creates it — no explicit project-creation step anywhere in the flow (web, CLI, or skill).
- **Org naming across every client.** The web app, CLI, and the explain/setup skills read **"org"** where they used to read "workspace"; the CLI's outside-a-repo save fallback is now `"default"`, and `knowledge init` mints an org-level key.

Org **creation** (additional orgs) + member **invites**/roles are explicitly deferred (**D14**), and monetization is unchanged — everything here stays free. See **architecture**/**backend**/**data** for the model + schema, **api** for the additive endpoints, and **frontend**/**experience** for the surfaces.

**Public projects & direct doc links (P19).** P19 delivers the two paired sharing capabilities the operator asked for (intent points 5 + 6). Until now there was **no visibility concept anywhere** and, on prod, **no anonymous read path at all** — every `/app/*` read required a session. Two product moves, both free:

- **Per-project public/private visibility (default private).** Each project carries a visibility flag, toggled from the web app (and honest for implicitly get-or-created projects, which default private). Making a project **public** opens its docs and its knowledge graph to **anonymous visitors and other users**; the visibility takes effect **instantly** (no re-index). The **graph rule**: to anyone who is not a member of the owning org, the public graph exposes **only public-project nodes/edges** — private-project nodes are absent, not dimmed. Everything private or nonexistent answers a **404** that is indistinguishable from "does not exist" (404-never-403), so a private doc/graph never leaks its existence anonymously or cross-org.
- **Every save returns a working direct doc URL.** The `POST /api/documents` 201 `url` — previously the retired mkdocs link (`{project}/{date}-{slug}/`, broken for every non-#1 tenant, so the CLI hid it) — is now **mode-aware**: in tenant mode it points straight at the doc's direct page (`{app origin}/documents/{id}`, live-verified), while the dormant single-tenant/legacy template stack keeps the mkdocs shape. The CLI now surfaces this URL on `save`, and both `SKILL.md` copies say it is shareable when the project is public. The two capabilities pair deliberately: the direct link is what gets shared once a project is public.

No new visual design (every public surface composes 1:1 from already-designed pieces), no new services, and no monetization change. Anonymous-read rate limiting, login `returnTo` for anonymous doc misses, and org-**slug** vanity graph URLs (UUID suffices for the MVP) are recorded as deferred follow-ups. See **api**/**backend**/**security** for the anonymous read surface + the mode-aware URL, **frontend**/**experience** for the web surfaces, **data** for the `0004` schema, and **operations** for the executed prod cutover.

**Frictionless onboarding: real hero, env-var quickstart, published skill (P20).** P20 makes the landing hero's depicted journey **real and honest end to end** and turns the landing into the easiest on-ramp for both humans and coding agents (intent points 1, 3, 4, 7). Four moves, all free — **no new services, no schema/API change**:

- **The broken install line is fixed with a live curl installer.** The hero's live-broken `uv tool install knowledge-cli` (the package was never published to PyPI — D-P13-1) is replaced by `curl -fsSL https://knowledge.hi2vi.com/install.sh | bash`. The served script (`web/public/install.sh`, live at `/install.sh` with zero infra) bootstraps `uv` if missing then runs the canonical `uv tool install git+…#subdirectory=cli`. **PyPI stays out of scope** — the fix is the installer, not a package publish.
- **The init/password step is made honest.** The hero terminal now depicts the real password prompt, and `knowledge init` prints a `web login: {base_url}/login (same email + password)` line — the CLI and the web app share one accounts plane, so the same credentials log into the web UI. No password generator, no signup-flow change.
- **The env-var REST path is promoted as the recommended agent setup.** A landing **agent quickstart** section presents the two exports (`KB_API_BASE_URL` + `KB_API_TOKEN`, an org-level key) → any coding agent on the machine saves via plain REST, with the real blockers surfaced honestly (a repo `.env` is never auto-loaded → put them in `~/.zshenv`; Codex's workspace-write sandbox needs `network_access = true`; the edge is not a barrier).
- **The explain skill is published on the landing — copyable + downloadable — agent-first.** The canonical `plugin/skills/explain/SKILL.md` is served at `/SKILL.md` (`web/public/SKILL.md`, joined to `scripts/skills_parity.py` as a third, **full-file** byte-identical copy — it can never fork) with Download + Copy controls and an expandable in-page reader. The steer is explicit: the REST API is fully usable by hand, but the recommended path is a coding agent driving this skill.

Also settles deferred **D16** (an `init --project other` now **reuses** the org key across projects — org keys are project-agnostic since P18) and **D10** (the two mid-feature ledes, resolved through design round 02). Windows `install.ps1` is a POSIX-only follow-up (deferred **D20**). Shipped and verified live on `https://knowledge.hi2vi.com`. See **frontend**/**experience** for the landing surfaces + hero, **decisions** for the ADRs, and **operations** for the ship.

**Versioned documents (P23).** Until P23 a knowledge document had exactly one body and no version concept. Re-explaining the same subject on a later day silently produced a **second post** (a document's identity includes its date, and the `/explain` skill derives that from *today*), and the only way to replace a body was a destructive `overwrite` whose previous content was recoverable — at best — from git, and only for the operator's own tenant. P23 makes a re-publish **additive**, delivering the operator's ask ("the coding agent can see the previous document, and add v2 and v3 of it, not a new post") across three surfaces:

- **Agents publish the next version of the same document.** The write API accepts "this is a new version of *that* document": the previous body is archived, the new one is written **in place**, and the document keeps its id, its URL, its graph edges and inbound links, and its original date and slug. Targeting is forgiving by design — name the document explicitly or just let the server match the newest document with the same project + slug; if nothing matches, it is an ordinary new document, never an error. The one hard rule is that a version chain cannot change a document's **project or format**; that is a new document, and the API says so.
- **Agents (and people) can read what a previous version said.** A document's history is readable on both planes — the agent API and the web app — and an agent can fetch an older body in full before writing the next one, so a re-explanation builds on what came before instead of starting cold. Only the **current** version is searchable, embedded and on the graph: history is deliberately quiet, so search results and the knowledge map look exactly as they did before.
- **The web app shows the history.** A document page gains a version-history panel — visible **only** when there is history — and a read-only page for each superseded body (a past HTML explainer still renders interactively). There is no rollback and no editing: you can read history, not rewrite it. It is free and unmetered like every other web-UI feature.
- **`overwrite` stops losing data.** The legacy destructive path now archives the body it replaces and shares the same version chain. Its response shape is unchanged, so the CLI and every existing consumer keep working untouched.
- **`/explain` is the first real consumer.** The skill resolves an existing document in the target project *before* authoring, reads the current (and, if useful, older) body, and publishes as the next version — which is precisely the duplicate-post bug this phase set out to fix. The change is mirrored across all four copies of the skill (canonical, portable, the landing-served copy, and the installed one).

Version **diffing**, **rollback** ("make v2 current again"), **pruning** of old versions, and a CLI `--new-version` flag are deliberately out of scope; a **known gap** is that the skill's API-unreachable offline fallback still cannot version (it says so, and tells the agent to re-publish once the API is back). No new services, no schema migration on the accounts plane, and no monetization change. See **api** for the contract, **backend**/**data** for the on-disk archive, **frontend**/**experience** for the surfaces, and **decisions** for the "disk is canonical, the DB is disposable" ADR that shapes it.
