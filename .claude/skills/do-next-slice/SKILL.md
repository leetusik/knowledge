# do-next-slice

Run `python3 scripts/workflow.py next` — it prints the current pointer, so there is no need to re-read `works/state.json` or `works/backlog.md` — then read `CLAUDE.md`, the selected slice folder, and the phase's `phase.md`: the **bounded phase notebook** (`## Slices` generated from `slice.json`, `## Decisions`, `## Doc impact`, `## Operator Questions`, `## Notes for later slices`, `## Now`) that carries the phase's state and is your handoff from the last slice. Read `docs/current/` **sections** just in time, only where this slice's work touches them — never the whole doc set up front, and not `docs/index.json` (version history, not truth). If you are ever unsure of the operator's intent, consult the phase's `intent.md` (linked from `phase.md`) — the confirmed record of what was asked. `next` reports **the current stream's** active phase: on the default stream it skips phases running in their own worktrees (printing `parallel_phases_elsewhere=<P>:<branch>` when any exist), and inside a phase worktree it sees only that phase (printing a `stream=` line). Run `python3 scripts/workflow.py parallel-status` when you need the picture across every stream.

You are the ORCHESTRATOR (main thread): you plan each slice, verify, commit, move workflow state, and talk to the operator. The execution of every slice — decomposition, `research`, implementation, `fix`, and the phase **review** — is delegated to a `slice-executor` tier subagent (`slice-executor-mid` or `slice-executor-high`; you do not do that slice's work yourself). **One exception: a `co-work` (design) slice runs inline, with dispatched spans (inline → dispatched → inline).** The round's lifecycle and the operator's words stay inline — `design-open`, the handoffs, the read-back, every publish to a job's canvas, `feedback.md`, `SIGNOFF.md`, `design-close` and every commit stay on the main thread — but the **drafting is dispatched to `design-drafter`** (the design subagent, not a slice executor) every round, the **critique to `design-critic`** when a job's critique level asks for it, and the **mockup build is the one span dispatched to a slice executor** (`slice-executor-high`, built from the round's `build-prompt.md` and its record on disk), only when the operator asked for a mockup. See the `design-cowork` skill. One slice, then stop.

If `next` prints `WAITING ON OPERATOR` (the current slice or phase is `pending`, shown `[~]`), STOP: the work is waiting on operator co-work. Report what is needed and do not start, finish, or advance it. Resume only after the operator approves and clears the `pending` status back to `in_progress`. When the phase is pending because its **operator acceptance gate** is open (`next` also prints `acceptance_gate=open` and the walkthrough), relay that walkthrough to the operator as-is: it clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]`, not with `set-phase-status`. (In a phase worktree a `pending` slice or phase halts only its own stream.) **A `co-work` design slice stops `pending` once per wave — twice when a mockup was requested, and once more for each superseding round — and the engine cannot tell its windows apart** — every stop is `status: pending` on the same slice and prints the same line — so the difference lives entirely in what you report; say which one this is, and what the operator's words on return will do (step 3).

**After a context compaction** (the `SessionStart` hook has printed `compaction=done source=compact`, the pointer and a resume line): re-read this `SKILL.md` from disk — only its first 5,000 tokens were re-injected — then the active slice folder (`plan.md`, `result.md`) and `phase.md`'s `## Now`. An executor dispatched before the compaction is still running and the harness lists it: wait for its completion notification, never re-dispatch; the mode word and any open operator gate are among the summary's kept facts.

Work exactly one slice:

1. If the selected slice is `todo` or `ready`, run `python3 scripts/workflow.py start-slice <slice_id>`. (In `plan only` mode, skip this — the slice is readied, not started; see step 2.)
2. Plan the slice, then persist the plan to this slice's own `plan.md`.
   - **Skip planning for an existing `ready` (`[r]`) slice.** Its `plan.md` was operator-approved by an earlier `plan only` pass, so re-read that plan and `phase.md`, then dispatch directly (step 3). Re-plan only when concrete visible workspace drift makes the approved plan unsafe or stale.
   - **Default is `auto`.** With no mode word, do not enter plan mode: plan inline, `Write` the complete free-form plan to `plan.md`, and dispatch immediately. Pull context from `phase.md`, incorporate any operator note without duplicating `intent.md`, and never pre-fill another slice's plan. This waives only the approval gate; every safety halt still applies. **One carve-out (v40): a decomposition slice (`kind: decomposition` — `DECOMP`, `DECOMP2`, `DECOMP3`, …) is gated by default.** Under the bare default, plan it through the `gate` path below (plan mode → operator approval → copy the harness plan file) — the decomposition fixes the shape, risk ratings, and cost of every slice after it, so its plan gets operator eyes even when everything else runs `auto`. **A second carve-out (v59): a slice that spends money (vendor LLM or model API calls, paid third-party APIs, per-use billed cloud resources; the workspace's own executor dispatches do not count) is gated by default too.** When planning shows the work will spend money, plan it through the `gate` path, and name in the plan what it calls and a rough volume or cost estimate, so the operator approves the spend with the plan. An **explicit** `auto` (or "run unattended") is the opt-out for both: it plans the whole run, decompositions and spending slices included, inline with no pause.
   - **`gate` is the operator-approved path.** When invoked with `gate`, call `EnterPlanMode`, do read-only research and surface clarifications, then call `ExitPlanMode` to present the readied plan. After approval, copy the exact harness plan file named for this planning session to the slice's `plan.md`; never glob `~/.claude/plans/` or choose by mtime. First confirm its opening lines match the plan just approved, then copy immediately before another `EnterPlanMode` can overwrite it. Append slice-local additions after the copied body, never by rewriting it. If Claude Code names no harness plan file, fall back to writing the approved plan verbatim and in full.
   - **`plan only` readies one plan without executing it.** Run the same gated planning path even if `auto` also appears. If the selected slice is already `ready`, target the next ordered slice that is neither `done` nor `ready`. **Stop before anything whose plan depends on something that has not landed yet** — `REVIEW` (it depends on the implementation results), `P<N>.DECOMP2` (it depends on findings or a design that do not exist yet: a **research** slice's findings, or a design round that has not come back), and a `paired` phase's **apply slice** (its `plan.md` is written at its turn, from the round that just landed) — and stop when there is nothing left to ready. After approval, copy the harness plan file (with the same guarded fallback), set the slice to `ready`, validate, commit, report what was readied, and STOP without `start-slice`, executor dispatch, or `finish-slice`.
3. Dispatch the executor to implement the slice. Always launch it through the Agent tool **as a background task** (the default — never pass `run_in_background: false`) and wait for its completion notification; never run the executor synchronously inline in the main session. This applies to decomposition, `research`, implementation, `fix`, and review. **`kind: co-work` is the exception, and only in part** — its round runs inline with dispatched spans; *When the selected slice is a design slice* below carries it. **Dispatch through the engine's route table — the decision is the engine's, never yours:** kind first (decomposition, `research` and review always route to the high row, by **kind**, whatever their `risk` says; a `co-work` mockup span too), then `risk` (exactly `low` → the mid row, `slice-executor-mid`, the default tier — real code and multi-file work included, as long as `plan.md` pins the approach — and `docs` / `qa` rated `low` → the cheap row on that same file; anything else → the high row, `slice-executor-high`), then attempt (every second attempt → high). (1) **Resolve:** once `plan.md` is written (and after `start-slice`), run `python3 scripts/workflow.py executor-route <slice_id>` — add `--retry` on a second attempt — and `python3 scripts/workflow.py executor-route --explore`. **Bump up, never down:** when the plan you write hits a named trigger (open design, a core invariant, an unlocated root cause, a wide blast radius) on a slice rated `low`, set `risk` to `high` in its `slice.json` (that one field; `python3 scripts/workflow.py rebuild` regenerates the table), say why in `plan.md`, and resolve again; never lower a rating. (2) **Pin:** append a final `## Dispatch` section to the slice's `plan.md` holding the slice form's lines verbatim (`route=` … `attribution=`) plus the `--explore` form's `model=` / `effort=` renamed `explore_model=` / `explore_effort=` — the executor copies its `model` / `effort` into its verdict block from there and takes its `Explore` lookup model from it; on a retry the new lines go under the `## Escalation: mid → high` section instead. (3) **Dispatch:** the Agent tool, as a background task, `subagent_type` = the `subagent_type=` line; pass `model` (the `model=` line, an Agent-tool alias) only when `pass_model=yes`, and `effort` (the `effort=` line) only when `pass_effort=yes`. A `fallback=` line is informational (`model=` already carries the fallen-back model); relay every `warning=` line to the operator in your report — it means the per-dispatch value will not take effect on this machine. The prompt stays the slice id, its folder and the repo root. (4) **Record:** after the completion notification — before `finish-slice`, so the record rides in the slice's commit — run `python3 scripts/workflow.py record-dispatch <slice_id> --route <route=> --tier <tier=> --model <model=> --effort "<effort=>" --verdict <done|escalate|needs_operator|blocked|failed> --attempt <attempt=> --agent <subagent_type=> --duration-ms <duration_ms> --tokens <subagent_tokens> --tool-uses <tool_uses>`: the flags copied from the pinned lines, never recomputed, and the three numbers from the notification's `<usage>` block; a failed or empty return is `--verdict failed`. Every return is recorded, whatever its verdict: each design span with its own `executor-route --drafter`, `--critic` or `--judge` lines (`--route design|critic|judge --tier -`, `--agent` its `subagent_type=` line), the mockup span like any slice. (5) **Explore for lookups:** your planning research uses the project `Explore` agent (`subagent_type: Explore`) at the `--explore` form's `model` / `effort` (haiku @ high; `sonnet` under a loopback proxy), upgraded per call — `model: sonnet` or `model: opus` — for a lookup that needs judgment (why, a trade-off, an audit); it locates and summarizes, never decides, and its brief is advisory input to your plan, never a plan (`Plan`-type agents and inline reads stay available). `/executor-route` shows the resolved table and `python3 scripts/workflow.py dispatch-summary` the recorded runs; `executors.toml`'s per-row `[claude.<row>]` overrides are the operator's knob — there are no presets. Give the executor the slice id and folder path; it reads the plan and context, implements, validates, writes `result.md` (verdict block first), edits the phase notebook under its budget — consuming the notes written for it, recording decisions and doc impact — and returns the structured verdict. Do not implement the slice yourself.
4. Trust the verdict; do not re-run the slice's work. Read the returned verdict and the **head** of `result.md` — its verdict block is that return's durable copy, so reading further is only worth it on a verdict other than `done` (or when you want the detail) — then run `python3 scripts/workflow.py validate` (state integrity only — do **not** re-run the slice's tests; the phase review validates all slices together later). Then act on `status`:
   - `done` → continue to step 5.
   - `needs_operator` → set the slice `pending` (`python3 scripts/workflow.py set-slice-status <slice_id> pending`), report the `operator_need`, and STOP without finishing.
   - `blocked` → record the blocker in `result.md`, report it, and STOP.
   - `escalate` (returned only by `slice-executor-mid`) → escalate instead of stopping: append an `## Escalation: mid → high` section to this slice's `plan.md` carrying the executor's `escalation` findings and what to do differently, then resolve with `executor-route <slice_id> --retry`, pin its lines under that section, re-dispatch the slice to **`slice-executor-high`**, and record the second attempt. In `gate` mode, present the revised plan for the operator's approval first (plan mode, as in step 2); in the default (`auto`) re-dispatch straight away. At most 1 escalation per slice; the slice stays `in_progress` throughout.
   - failed or empty return → from `slice-executor-mid`, treat it as an `escalate` with no findings (record it `--verdict failed`, note the failed attempt in the escalation section and re-dispatch to `slice-executor-high` through the same `--retry` path); from `slice-executor-high`, treat the slice as not done: do not finish, do not commit; report and STOP.
5. Mark the slice done with `python3 scripts/workflow.py finish-slice <slice_id> --outcome "<one line>"` only when complete and verified. The outcome is one line, taken from the executor's verdict `summary`; it fills that slice's row in the notebook's generated `## Slices` table, which is how a later slice sees at a glance what this one did. Omitting it warns and never errors, but leaves the row's Outcome cell empty.
6. Run `python3 scripts/workflow.py validate`.
7. Commit by default: group the slice's pending changes into focused `type(scope): summary` commit(s) following the Commit Convention. Committing is the orchestrator's job — the executor never commits. **Attribute the slice commit to the model that did the work:** its trailer is `Co-Authored-By: <attribution> <noreply@anthropic.com>`, `<attribution>` being the `attribution=` line of the dispatch that produced the work — equivalently the name for the `model:` its verdict block records; a slice done in two attempts goes to the model that completed it. Commits carrying only your own work (phase creation, a gate declaration alone, a verdict record) are attributed to the session's model as before; never carry over another session's trailer. Do not branch unless the operator asks; never push. A phase the operator asked into a worktree already has its branch — that branch *is* the worktree they asked for, so its slice commits land on `phase/P<N>-<slug>` without asking again; every other phase's land on the current branch. Pushing is separate and still needs asking: the `parallel-phase` integration merges locally by default, and its push → PR variant runs only when the operator asks (each push still goes through the permission prompt).

When the selected slice is a design slice (`kind: co-work`), step 3 runs it like this, per the `design-cowork` skill: the round's lifecycle and the operator's words stay inline; the **drafting is dispatched to `design-drafter`**, the **critique to `design-critic`** (its judge mode too) when a job's critique level is `critic` or `critic+judge`, and the **mockup build is the one span dispatched to a slice executor** (`slice-executor-high`, like any code slice) — **when the operator asked for one, and only then**. A phase whose `intent.md` still says `Design tool: claude-design` is a legacy one: at its first design slice set the slice `pending` and ask the operator to re-confirm it on `drafter`, per `design-cowork`'s legacy rule. **Inline:** for each job of the slice's wave (one, or about 3–4, as `DECOMP` recorded them), `python3 scripts/workflow.py design-open --slug <slug> --slice <slice_id> --critique <level>` (`--new-job` for each further job; `design-init` first on a product's first job), create the job's canvas on its first round, do the preview prep, and write `handoff.md` — the screens × states with a check each, the data, the system inventory, the constraints, the collected taste, the `## The operator's bar` section (the operator's own standing rules from `bar.md`, or none beyond the shipped bar), a `new visual direction: yes` or `no` line (the operator's call: the licence for a new look, built as one direction), the `critique:` line and the three paths. **Dispatched:** one drafter per job **at once** — the one carve-out from one executor at a time: disjoint job folders, design spans only — on the `executor-route --drafter` lines, each prompt the round **address** `<job>/<round>` and the slice id; then, per job whose critique is on, one critic pass and, with any must-fix open, one drafter answer pass; under `critic+judge` the judge rules once beside that answer pass on the items the critic escalated, and its upheld items get one more short drafter pass. There is no second critic pass. A drafter's `needs_operator` or `blocked` holds only its job, and the stop reports it. **Inline again:** read each job back — run `design-check <job>` yourself, never resting on the drafter's own line, read `result.md` and `build-prompt.md`, and run the concreteness check (**a failure the drafter can fix goes back to it once, on the same open round; otherwise report exactly those points at the stop and sign nothing**) — publish it (`design-publish-plan <job>` → the `Artifact` publish → `design-canvas <job> --version <id>`), commit the drafted wave and stop at **PENDING #1**, once for the whole wave. On the **resume** the operator has returned with their words, which decide each job separately; first read their in-app edits and the comments they sent to Claude back into `feedback.md`, verbatim. **Literal approval, no mockup requested** (`Mockup: on request` and the operator did not ask): write `SIGNOFF.md` with their words and run `design-close <job>/<round> --words "<their literal words>"`. **Anything else is feedback:** write their words verbatim into `feedback.md`, run `design-close <job>/<round> --superseded`, then `design-open --slug <s> --slice <slice_id> --job <job> --critique <level>` — the new round edits the job's canvas in place — and **write its handoff**: what the feedback asks for, pointing at the superseded round's `feedback.md`, the boards the operator edited locked as edited, and its `new visual direction` line. Re-draft, read back and republish (a new canvas version) exactly as above, commit (the superseded round's `feedback.md` and close ride in the same commit), and stop at PENDING #1 again — **one more commit, stop and invocation per superseding wave**. When every job is signed, or dropped by the operator, continue at step 5: **a wave signed at the first return takes two commits, one `pending` stop and two `/do-next-slice` invocations**. **Mockup requested** (`Mockup: requested` in `intent.md`, or asked for in their own words before the round closed): their go-ahead dispatches the mockup executor (step 4's verdict handling applies to it unchanged — `needs_operator` covers a record too thin, wrong or inconsistent to build from), commit, and stop at **PENDING #2**, the mockup gate; on the **second resume** take the operator's literal approval of the running mockup, write `SIGNOFF.md`, run `design-close <job>/<round> --words "<their literal words>"`, then continue at step 5 — **three commits, two stops, three invocations**. **PENDING #2 exists only when a mockup was requested.** **Report each window for what it is:** at PENDING #1 give, per job, the canvas link, the scorecard when critique was on (open items, the bar line by line, Holds, Not seen), the taste notes, open wave choices, what the answer pass left open (rebuttals, with both sides), unsure items under `critic` and low-confidence items when the judge was skipped, the drafter's departures and `open_questions` as decisions to take, and what their words will do — literal approval signs that job (no mockup) or starts its mockup build (mockup requested), anything else is feedback and a superseding round re-drafts it; at PENDING #2 say that you are **asking for approval** — give the run command, the mockup route's URL, the viewports, what is real and what is stubbed, and that only their literal words close the round.

**The phase runs on this checkout unless the operator asked for a worktree (v43).** Do nothing about worktrees by default: run the slice here, on the current branch. Three things change that, and all three are the operator's word, never your judgment. (a) **They asked in this invocation** — `worktree` (or `in a worktree`, `in parallel`, `on its own branch`) alongside the command, on a phase that is still `planned`: run `python3 scripts/workflow.py parallel-start <P>` (it commits the stamp — only the phase folder plus the regenerated `works/` files, whatever else is dirty or staged; your other uncommitted edits stay behind on this checkout, and the worktree starts from that commit), call `EnterWorktree` with the `worktree=` path it printed, re-run `python3 scripts/workflow.py next` there (it now prints `stream=phase/P<N>-<slug>`), and continue at step 1 in that worktree, in this same session — background executors you dispatch from there run in the worktree. **In a nested install** run `parallel-start <P> --host-branch <name>` instead, after you propose the name from the host's recorded custom (`nested-convention`) and the operator confirms it; `EnterWorktree` goes to the printed **host** worktree path, and integration follows `parallel-phase` §5's nested form. (b) **They already ran `parallel-start <P>` themselves** — the phase carries an `execution` block with `mode: "parallel"`, `next` on the default stream skips it and prints `parallel_phases_elsewhere=<P>:<branch>`, so enter that worktree the same way and work there. (c) **You are already in the worktree** — `next` prints `stream=phase/…`; just continue. A `hint:` line about a phase waiting behind a live one is a **suggestion to relay, not an instruction to act on**: report it and keep going on this stream. Never run `parallel-start` on your own initiative, and never ask for one on a docs phase (`doc-new-version` only works on the default stream). The `parallel-phase` skill has the rules and the lifecycle.

When the selected slice is a decomposition (`kind: decomposition`), it runs the **same path** as any slice — you plan it (**at the gate by default** — see step 2; only an explicit `auto` plans it inline), the `slice-executor` does its job. That job is to create the phase's middle slices: in step 3 the executor runs `python3 scripts/workflow.py new-slice --phase <P> --slice <P>.S<n> --name "..."` (with `--kind`, `--risk`, `--order`, `--depends-on` as the plan specifies) to create them as **bare folders** — never pre-filling their `plan.md`; each fills its own when it runs — and records the slice breakdown (what each slice covers and why) plus findings in the phase's `phase.md`, so later slices share that context. Set each middle slice's `--risk` deliberately — `risk` selects the executor route (`low` → `slice-executor-mid` on the mid row, or the cheap row for `docs` / `qa`; anything else → `slice-executor-high`), so it is the phase's main cost lever, and an unrated slice lands on the top tier. **Mid is the default (v46):** rate `implementation`, `fix`, `docs` and `qa` slices `low` — real code and more than one file included — and rate one `high` only for a named trigger, written beside it in the breakdown: **open design** (the plan cannot pin the approach: a new abstraction, an architecture choice, an algorithm to invent), a **core invariant** (logic the product cannot afford to break — persisted state or a schema migration, state transitions, auth, money, deletion, concurrency), an **unlocated root cause** (a bug whose cause is already known and located is `low`), or a **wide blast radius** (a shared interface whose callers are spread across the code). **When the phase cannot be cut past a point without learning something first, that is what the `research` kind is for:** the executor cuts a `research` slice (`--kind research --risk high` — findings-only, no product code, findings landed in `phase.md`) and a `<P>.DECOMP2` ordered after it, instead of guessing at the slices beyond it; `DECOMP2` then re-cuts the rest from what was learned. That is `DECOMP2`'s second origin and it is as ordinary as the design one below — usually, not always: a research slice whose findings change nothing about the remaining breakdown needs no re-cut, and a phase genuinely needing a third pass numbers it `DECOMP3`. Plan the decomposition accordingly; you still verify, `finish-slice`, and commit as for any slice. **When the phase touches product visual design, its shape follows the operator-confirmed style** — `build-after`, `design-only` or `paired`, recorded in the phase's `intent.md` under `## Design Style` — the style, and on its second line whether the operator wants an in-product mockup in addition to the working canvas, `Mockup: requested` / `Mockup: on request` (read the `design-cowork` skill). In **every** style this `DECOMP` creates the design slice(s) (`--kind co-work --risk high` — each holds one job per surface, or a wave of about 3–4 jobs, and **how many slices and jobs there are is decided here**, foundations first) and records in `phase.md` the **build inventory** — what to build, not how — and each slice's jobs with their critique level (`off | critic | critic+judge`, unset = off). What else it creates is what the style decides: **`build-after`** — the groundwork slices plus a second decomposition slice `<P>.DECOMP2` after the last design slice, and **no build slices** (`DECOMP2` cuts them once the design has landed, backend first and the design implementation after); **`design-only`** — a single pass, `DECOMP` → design slice(s) → `REVIEW`, the apply phase being a separate phase created at `/create-phase`; **`paired`** — the design/apply pairs as **bare folders**, one apply slice per design slice and **no `DECOMP2`** (a bare folder is not pre-planning; each apply plan is written at its turn). If `intent.md` carries no `## Design Style` because the phase was created before its visual nature was clear, **ask the operator at this slice**: suggest a style with a reason, ask the mockup question with it, set the slice `pending`, and stop — noting that `design-only` cannot be chosen from inside `DECOMP`, since its apply phase needs `new-phase` and the executor may not run it, so that answer goes back to the main thread and `/create-phase`.

**Declare the phase's operator acceptance gate at the `DECOMP` boundary.** Right after `finish-slice <P>.DECOMP`, and in the same commit, decide from `intent.md` and the decomposition whether this phase changes anything the operator can see, then run `python3 scripts/workflow.py accept-gate <P> --require` (it does — the operator will walk the running product before the review can pass) or `python3 scripts/workflow.py accept-gate <P> --waive --note "why nothing operator-visible changes"`. **A design phase's gate follows its mockup, with no judgment call left in it:** a phase that ships one (`Mockup: requested`, or asked for in the operator's words) takes `--require` — the operator opens a running route, an operator-visible surface by definition — and a `design-only` phase that ships none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`, the fixed note; `build-after` and `paired` phases take `--require` for their build/apply slices as always. A mockup requested after this declaration re-declares it: run `python3 scripts/workflow.py accept-gate <P> --require` in the mockup commit. And when `DECOMP` had to ask the design style (above), **that answer must land before you declare the gate**, because the declaration depends on it. There is no default and no declaring by omission: `review-phase --verdict pass` refuses an undeclared phase and names both flags. Phases created before workspace v32 carry no `acceptance` block at all and need no declaration.

When the selected slice is a phase review (`kind: review`), step 3 resolves it with `executor-route <P>.REVIEW` (the high row) like any slice and delegates the review to `slice-executor-high` — you do not review it yourself. Plan it so the executor: validates all of the phase's slices together (each slice's validation commands from its `plan.md` / `result.md`, plus `python3 scripts/workflow.py validate`), reviews the phase against its objective, `intent.md`, and the docs, and — **on a passing review** — **verifies** that the running "Doc impact" list in `phase.md` covers every durable-truth change (an incomplete list is a finding) and returns `doc_versions: none — deferred to a docs phase`. It consolidates nothing: the only doc versions a review may create are its two named gate sections (`## Regression Checklist` in the qa doc, `## Operator Runtime` in the operations doc), and **in a phase worktree** (the phase carries an `execution` block with `mode: "parallel"`, because the operator asked for one) not even those — it records them as `## Doc impact` notes tagged `(gate section — written at merge)`, and the post-merge step on the default stream writes exactly those; see the `parallel-phase` skill. A **non-passing verdict stops the executor** before those pass-only steps and hands the phase back to you: it completes validation and judgment first (so you receive the whole picture in one cycle, not one finding per cycle), then returns the verdict with numbered findings and proposed fix slices instead of doing any pass-only work. The review does **not** produce a phase explainer — explaining is a separate operation the operator runs, and the executor just reports the fixed pointer `explain: not written — run /explain for this phase`. On a review slice the executor writes only docs, never source code. **When the phase's gate is `required: true`**, plan the review to run the gate stages as well: the executor opens the running product itself in the `## Operator Runtime` manifest runtime and spot-checks the phase's headline claims (never passing on other slices' reports alone), walks the surfaces the phase changed with fresh eyes as a first-time user, re-runs the `## Regression Checklist` lines inside the phase's boundary (`python3 scripts/workflow.py phase-scope <P>` — its own surfaces plus every earlier line a changed file feeds, never the whole list) and appends this phase's headline checks, and routes every `## Operator Questions` entry into the walkthrough or into a deferred job for you to file — returning a **`walkthrough`** beside the verdict (see the `review-phase` skill). Put `phase-scope <P>`'s output (or the command) in the review's `plan.md`, and never plan the review to re-run the whole list — a plan that says "N lines, read it whole, re-run all of it" is exactly what the boundary rule retires; whatever the review notices outside the boundary comes back as deferred-job candidates for you to file, never as findings. It returns a `review_verdict`; you record it and act on it instead of running steps 5–7:

- **On `pass` with a required acceptance gate, do not record the verdict yet.** Run `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough the executor returned>"` — the phase goes `pending` — file any deferred jobs the review listed (`defer-job ...`), run `validate`, commit, report the walkthrough to the operator, and STOP. When the operator accepts, the gate clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` and the phase returns to `in_progress`; on that resume the `REVIEW` slice is still `in_progress` with its `result.md` carrying `review_verdict: pass` and the gate showing `cleared_at`, so record the pass **without re-dispatching the review**. If the operator reports failures instead, record `python3 scripts/workflow.py review-phase <P> --verdict changes_requested --note "operator-reported: ..."` (never refused — it resets the gate), create `fix` slices from their report, complete them, and re-review from the top. A waived phase, and a legacy phase with no `acceptance` block, record the verdict straight away as before.
- Record the verdict: `python3 scripts/workflow.py review-phase <P> --verdict pass|changes_requested|blocked --reviewer slice-executor-high --note "..."`, then `python3 scripts/workflow.py validate` (state integrity — also catches a stale `docs/current`).
- On `pass`: `review-phase` has already marked the phase `done` **and closed the `REVIEW` slice** — no separate `finish-slice` is needed. The phase **stays in `active/`** — archiving is a separate, manual step, so do **not** archive now. Archiving is never this loop's job: it is `/rotate-backlog`'s, which pays the doc debt and archives after the docs phase it runs, or the operator's `archive-all` (once every active phase is done) or `archive-phase <P>` for one phase. A phase that left "Doc impact" notes is now stamped `consolidation: pending` and stays out of archiving until a docs phase pays it (`doc-new-version` per note, then `docs-consolidated <P>`) — report that debt to the operator, do not create the docs phase on your own initiative. **If the operator asked this phase into its own worktree**, a `pass` is also what opens its integration: run the `parallel-phase` sequence — `parallel-gate <P>` → `ExitWorktree` (`keep`) → `git pull --ff-only` only if `main` tracks a remote → STOP and ask if anything is staged or a file the merge touches is uncommitted — typically the generated `works/` files after a phase was created here since the stamp, which is workflow state you commit first (git refuses both; never unstage or discard the operator's work) → `git merge --no-ff phase/P<N>-<slug> -m "merge(P<N>): <name>"` → `parallel-merge-finish` → `doc-new-version` + `rebuild-docs` for the `## Doc impact` notes tagged `(gate section — written at merge)` → commit → `parallel-teardown <P>` → commit — stopping and reporting if the gate is closed. The rest of the doc debt waits for the operator's docs phase, which records `parallel-consolidated <P>`. Push → PR → CI → `gh pr merge` is the remote variant, only when the operator asks.
- On `changes_requested`: `review-phase` returns the phase to `in_progress` and sets the `REVIEW` slice to `changes_requested` (kept open for re-review). Create the executor's proposed fix slices (`python3 scripts/workflow.py new-slice --phase <P> --slice <P>.F<n> --name "..." --kind fix --risk <low|high>`, the rating the review proposed: `high` for a fix to a defect in mid-tier work — its `result.md` verdict block reads `tier: mid` — because work the mid tier got wrong never goes back to it), complete them, then re-review; do not finish or archive.
- On `blocked`: record the blocker; do not finish or archive.

Durable-doc versioning happens **in a docs phase the operator creates** — no slice of this phase runs `doc-new-version` (the review's two named gate sections excepted). Every slice that changes durable truth appends a one-line "Doc impact" note to `phase.md`; the passing review verifies that list; the engine then stamps `consolidation: pending`, which keeps the phase out of archiving until `docs-consolidated <P>`. `docs/current/*.md` is therefore expected to trail the code between docs phases — `docs-debt` names what is owed at any time, and `/create-phase`'s docs-phase route turns it into the phase that pays it. Never patch `docs/current/*.md` or old versions.

Stop after one slice. Do not advance to the next slice in the same turn.
