# do-next-slice — a decomposition slice and the acceptance gate

When the selected slice is a decomposition (`kind: decomposition`), it runs the **same path** as any slice — you plan it (**at the gate by default** — see step 2; only an explicit `auto` plans it inline), the `slice-executor` does its job. That job is to create the phase's middle slices: in step 3 the executor runs `python3 scripts/workflow.py new-slice --phase <P> --slice <P>.S<n> --name "..."` (with `--kind`, `--risk`, `--order`, `--depends-on` as the plan specifies) to create them as **bare folders** — never pre-filling their `plan.md`; each fills its own when it runs — and writes the slice breakdown (what each slice covers and why) to the phase's `topics/breakdown.md`, its findings into `phase.md` as gist lines, so later slices share that context. **The breakdown lives in `topics/breakdown.md`, never in `phase.md`:** the executor writes it whole, with `## Passes` (one line per pass), `## Estimate`, `## Join-rebuilt artifact` when the phase has one, `## Build inventory` in a design phase, and one `## <slice id>` block per slice (goal, set, risk and trigger, `spends money:`, depends on); each later pass (`DECOMP2`, `DECOMP3`) rewrites it in place, a done slice keeping a one-line block, and `## Decisions` keeps one `Breakdown (<pass>): …` gist line per pass linking it, earlier passes' lines kept. Set each middle slice's `--risk` deliberately — `risk` selects the executor route (`low` → the mid row, `docs` and `qa` included; anything else → the high row), so it is the phase's main cost lever, and an unrated slice lands on the high row. **A DECOMP estimates time from the meter:** the phase's time comes from `python3 scripts/workflow.py dispatch-summary`'s `means` block — the metered minutes per span by route and span-minutes per slice by kind, the main thread included — applied to the slices it cuts; never a session-$ figure (the workspace's own dispatches are not spend) and never a recorded `tokens` figure (a span's final context, not its volume). **Each cut slice carries one line beside it in the breakdown: `spends money: no` or `spends money: yes, ~$X via <service>`** (vendor LLM or model API calls, paid third-party APIs, per-use billed cloud); a `yes` slice plans at the gate (the spend carve-out in `reference/modes.md`). **Slice size stays as is, with one rule:** a slice whose work is a bulk sweep (many screens, large API or sheet dumps) splits by surface, because an executor that compacts recovers from what is on disk, and a sweep's findings live only in its context until written. **Mid is the default (v46):** rate `implementation`, `fix`, `docs` and `qa` slices `low` — real code and more than one file included — and rate one `high` only for a named trigger, written beside it in the breakdown: **open design** (the plan cannot pin the approach: a new abstraction, an architecture choice, an algorithm to invent), a **core invariant** (logic the product cannot afford to break — persisted state or a schema migration, state transitions, auth, money, deletion, concurrency), an **unlocated root cause** (a bug whose cause is already known and located is `low`), or a **wide blast radius** (a shared interface whose callers are spread across the code). **When the phase cannot be cut past a point without learning something first, that is what the `research` kind is for:** the executor cuts a `research` slice (`--kind research --risk high` — findings-only, no product code, findings landed in `phase.md` as gist lines, long detail in a topic) and a `<P>.DECOMP2` ordered after it, instead of guessing at the slices beyond it; `DECOMP2` then re-cuts the rest from what was learned. That is `DECOMP2`'s second origin and it is as ordinary as the design one below — usually, not always: a research slice whose findings change nothing about the remaining breakdown needs no re-cut, and a phase genuinely needing a third pass numbers it `DECOMP3`. Plan the decomposition accordingly; you still verify, `finish-slice`, and commit as for any slice. **When the phase touches product visual design, its shape follows the operator-confirmed style** — `build-after`, `design-only` or `paired`, recorded in the phase's `intent.md` under `## Design Style` — the style, and on its second line whether the operator wants an in-product mockup in addition to the working canvas, `Mockup: requested` / `Mockup: on request` (read the `design-cowork` skill). In **every** style this `DECOMP` creates the design slice(s) (`--kind co-work --risk high` — each holds one job per surface, or a wave of about 3–4 jobs, and **how many slices and jobs there are is decided here**, foundations first) and records in `topics/breakdown.md`'s `## Build inventory` the **build inventory** — what to build, not how — and each slice's jobs with their critique level (`off | critic | critic+judge`, unset = off). What else it creates is what the style decides: **`build-after`** — the groundwork slices plus a second decomposition slice `<P>.DECOMP2` after the last design slice, and **no build slices** (`DECOMP2` cuts them once the design has landed, backend first and the design implementation after); **`design-only`** — a single pass, `DECOMP` → design slice(s) → `REVIEW`, the apply phase being a separate phase created at `/create-phase`; **`paired`** — the design/apply pairs as **bare folders**, one apply slice per design slice and **no `DECOMP2`** (a bare folder is not pre-planning; each apply plan is written at its turn). If `intent.md` carries no `## Design Style` because the phase was created before its visual nature was clear, **ask the operator at this slice**: suggest a style with a reason, ask the mockup question with it, set the slice `pending` (`--stop-kind decision --on-words "<their answer records the style and DECOMP cuts the slices>"`; the question follows the stop rules in the contract's `pending` rule), and stop — noting that `design-only` cannot be chosen from inside `DECOMP`, since its apply phase needs `new-phase` and the executor may not run it, so that answer goes back to the main thread and `/create-phase`.

**Every middle slice the decomposition leaves open is declared (v77).** `finish-slice <P>.DECOMP` refuses, writing nothing, while a non-barrier middle slice is undeclared (`python3 scripts/workflow.py set-slice-deps <slice> --depends-on …` declares one already cut), and prints the engine's `parallel_plan=` and `parallel_rounds=` lines. The executor returns the same rounds as `parallel:` (for a chain, why, and what would unlock parallelism): relay it in your report in a line or two. It adds no stop; `/do-whole-phase` runs those rounds as waves.

**Declare the phase's operator acceptance gate at the `DECOMP` boundary.** Right after `finish-slice <P>.DECOMP`, and in the same commit, decide from `intent.md` and the decomposition whether this phase changes anything the operator can see, then run `python3 scripts/workflow.py accept-gate <P> --require` (it does — the operator will walk the running product before the review can pass) or `python3 scripts/workflow.py accept-gate <P> --waive --note "why nothing operator-visible changes"`. **A design phase's gate follows its mockup, with no judgment call left in it:** a phase that ships one (`Mockup: requested`, or asked for in the operator's words) takes `--require` — the operator opens a running route, an operator-visible surface by definition — and a `design-only` phase that ships none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`, the fixed note; `build-after` and `paired` phases take `--require` for their build/apply slices as always. A mockup requested after this declaration re-declares it: run `python3 scripts/workflow.py accept-gate <P> --require` in the mockup commit. And when `DECOMP` had to ask the design style (above), **that answer must land before you declare the gate**, because the declaration depends on it. There is no default and no declaring by omission: `review-phase --verdict pass` refuses an undeclared phase and names both flags. Phases created before workspace v32 carry no `acceptance` block at all and need no declaration. **An explain phase** (`## Explain` in `intent.md`) declares by its unit, which `next` prints as `explain_unit=`: a **book** takes `--require` (the operator reads the book), and its first chapter slice then stops `pending` at the outline gate; a **document** takes `--waive --note "standalone explain document: published private; a v2 is cheap"` and a **chapter** `--waive --note "explain chapter: published private; a v2 is cheap"`. The rest: `reference/explain-decomposition.md`.
