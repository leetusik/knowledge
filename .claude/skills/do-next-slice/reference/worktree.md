# do-next-slice — a phase in its own worktree

**The phase runs on this checkout unless the operator asked for a worktree (v43).** Do nothing about worktrees by default: run the slice here, on the current branch. Three things change that, and all three are the operator's word, never your judgment. (a) **They asked in this invocation** — `worktree` (or `in a worktree`, `in parallel`, `on its own branch`) alongside the command, on a phase that is still `planned`: run `python3 scripts/workflow.py parallel-start <P>` (it commits the stamp — only the phase folder plus the regenerated `works/` files, whatever else is dirty or staged; your other uncommitted edits stay behind on this checkout, and the worktree starts from that commit), call `EnterWorktree` with the `worktree=` path it printed, re-run `python3 scripts/workflow.py next` there (it now prints `stream=phase/P<N>-<slug>`), and continue at step 1 in that worktree, in this same session — background executors you dispatch from there run in the worktree. **In a nested install** run `parallel-start <P> --host-branch <name>` instead, after you propose the name from the host's recorded custom (`nested-convention`) and the operator confirms it; `EnterWorktree` goes to the printed **host** worktree path, and integration follows `parallel-phase` §5's nested form. (b) **They already ran `parallel-start <P>` themselves** — the phase carries an `execution` block with `mode: "parallel"`, `next` on the default stream skips it and prints `parallel_phases_elsewhere=<P>:<branch>`, so enter that worktree the same way and work there. (c) **You are already in the worktree** — `next` prints `stream=phase/…`; just continue. (d) **An explain phase** (v86) is the one exception to asking: `create-phase`'s explain route starts it in its own worktree (unless `worktree: no`), its one confirmation being the operator's word — in a nested install with no `--host-branch`, a **detached** host worktree at the host base with nothing to integrate on the host — and runs it with `do-whole-phase` in `auto`, which also merges it back by itself after its `pass` (`do-whole-phase/reference/worktree.md`). A `hint:` line about a phase waiting behind a live one is a **suggestion to relay, not an instruction to act on**: report it and keep going on this stream. Never run `parallel-start` on your own initiative, and never ask for one on a docs phase (`doc-new-version` only works on the default stream). The `parallel-phase` skill has the rules and the lifecycle.

**`merge_ready=<P>:<branch>` on the default stream** means a stamped phase is `done` with a `pass` on its branch and not merged here (typically an explain run whose automatic merge could not run). At this slice boundary — nothing staged, the last slice committed — integrate it before starting the next slice, by `parallel-phase` §5 (`parallel-gate <P>` first: `exemption=phase-folder-only (<n> paths)` opens it past a busy default stream; a closed gate leaves it for later, never merged past). Never unstage or discard anyone's work to make it fit.
