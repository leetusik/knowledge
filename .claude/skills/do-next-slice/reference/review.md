# do-next-slice — the phase review, its verdict and the doc debt

When the selected slice is a phase review (`kind: review`), step 3 resolves it with `executor-route <P>.REVIEW` (the high row) like any slice and delegates the review to `slice-executor` — you do not review it yourself. Plan it so the executor: validates all of the phase's slices together (each slice's validation commands from its `plan.md` / `result.md`, plus `python3 scripts/workflow.py validate`), reviews the phase against its objective, `intent.md`, and the docs, and — **on a passing review** — **verifies** that the running "Doc impact" list in `phase.md` covers every durable-truth change (appending any missing line itself and reporting it as `doc_impact_added:`; a gap is never a finding on its own) and returns `doc_versions: none — deferred to a docs phase`. It consolidates nothing: the only doc versions a review may create are its two named gate sections (`## Regression Checklist` in the qa doc, `## Operator Runtime` in the operations doc), and **in a phase worktree** (the phase carries an `execution` block with `mode: "parallel"`, because the operator asked for one) not even those — it records them as `## Doc impact` notes tagged `(gate section — written at merge)`, and the post-merge step on the default stream writes exactly those; see the `parallel-phase` skill. A **non-passing verdict stops the executor** before those pass-only steps and hands the phase back to you: it completes validation and judgment first (so you receive the whole picture in one cycle, not one finding per cycle), then returns the verdict with numbered findings and proposed fix slices instead of doing any pass-only work. The review does **not** produce a phase explainer — explaining is a separate operation the operator runs, and the executor just reports the fixed pointer `explain: not written — run /knowledge:explain P<N> for one chapter, or create an explain phase for a book`. An explain phase's review (`## Explain` in `intent.md`) is planned from `reference/explain-review.md` instead: it publishes the book private and reads it in the reader. On a review slice the executor writes only docs, never source code. **When the phase's gate is `required: true`**, plan the review to run the gate stages as well: the executor opens the running product itself in the `## Operator Runtime` manifest runtime and spot-checks the phase's headline claims (never passing on other slices' reports alone), walks the surfaces the phase changed with fresh eyes as a first-time user, re-runs the `## Regression Checklist` lines inside the phase's boundary (`python3 scripts/workflow.py phase-scope <P>` — its own surfaces plus every earlier line a changed file feeds, never the whole list) and appends this phase's headline checks, and routes every `## Operator Questions` entry into the walkthrough or into a deferred job for you to file (a collapsed `(resolved → <ref>)` entry counts as routed) — returning a **`walkthrough`** beside the verdict (see the `review-phase` skill). Put `phase-scope <P>`'s output (or the command) in the review's `plan.md`, and never plan the review to re-run the whole list — a plan that says "N lines, read it whole, re-run all of it" is exactly what the boundary rule retires; whatever the review notices outside the boundary comes back as deferred-job candidates for you to file, never as findings. **In a nested install** plan the **team-rules check** too: a read-only pass (`git log`, `gh pr view`; it never creates or edits a pull request) over each repo the phase touched, per `phase-scope <P>` (the host in a single-repo install; skipped at-root), against that repo's recorded conventions and rules files, written into `result.md` as `team-rules check:` (`n/a (0 product files)` when the phase touched none). A failed item is a finding with a fix slice, and a history rewrite waits for the operator's word; the `review-phase` skill has the list. It returns a `review_verdict`; you record it and act on it instead of running steps 5–7:

- **On `pass` with a required acceptance gate, do not record the verdict yet.** Run `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough the executor returned>"` — the phase goes `pending` — file any deferred jobs the review listed (`defer-job ...`), run `validate`, commit, report the walkthrough to the operator (by the stop rules in the contract's `pending` rule), and STOP. When the operator accepts, the gate clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` and the phase returns to `in_progress`; on that resume the `REVIEW` slice is still `in_progress` with its `result.md` carrying `review_verdict: pass` and the gate showing `cleared_at`, so record the pass **without re-dispatching the review**. If the operator reports failures instead, record `python3 scripts/workflow.py review-phase <P> --verdict changes_requested --note "operator-reported: ..."` (never refused — it resets the gate), create `fix` slices from their report, complete them, and re-review as a bounded round, gate stages included. A waived phase, and a legacy phase with no `acceptance` block, record the verdict straight away as before.
- Record the verdict: `python3 scripts/workflow.py review-phase <P> --verdict pass|changes_requested|blocked --reviewer slice-executor --note "..."`, then `python3 scripts/workflow.py validate` (state integrity — also catches a stale `docs/current`).
- On `pass`: `review-phase` has already marked the phase `done` **and closed the `REVIEW` slice** — no separate `finish-slice` is needed. The phase **stays in `active/`** — archiving is a separate, manual step, so do **not** archive now. Archiving is never this loop's job: it is `/rotate-backlog`'s, which pays the doc debt and archives after the docs phase it runs, or the operator's `archive-all` (once every active phase is done) or `archive-phase <P>` for one phase. A phase that left "Doc impact" notes is now stamped `consolidation: pending` and stays out of archiving until a docs phase pays it (`doc-new-version` per note, then `docs-consolidated <P>`) — report that debt to the operator, do not create the docs phase on your own initiative. **If the operator asked this phase into its own worktree**, a `pass` is also what opens its integration: run the `parallel-phase` sequence — `parallel-gate <P>` → `ExitWorktree` (`keep`) → `git pull --ff-only` only if `main` tracks a remote → STOP and ask if anything is staged or a file the merge touches is uncommitted — typically the generated `works/` files, which a phase worktree refreshes here as it runs (v67) and a phase created here since the stamp rewrites, which is workflow state you commit first (git refuses both; never unstage or discard the operator's work) → `git merge --no-ff phase/P<N>-<slug> -m "merge(P<N>): <name>"` → `parallel-merge-finish` → `doc-new-version` + `rebuild-docs` for the `## Doc impact` notes tagged `(gate section — written at merge)` → commit → `parallel-teardown <P>` → commit — stopping and reporting if the gate is closed. The rest of the doc debt waits for the operator's docs phase, which records `parallel-consolidated <P>`. Push → PR → CI → `gh pr merge` is the remote variant, only when the operator asks.
- On `changes_requested`: `review-phase` returns the phase to `in_progress` and sets the `REVIEW` slice to `changes_requested` (kept open for re-review). Create the executor's proposed fix slices (`python3 scripts/workflow.py new-slice --phase <P> --slice <P>.F<n> --name "..." --kind fix --risk <low|high>`, the rating the review proposed: `high` for a fix to a defect in mid-row work — its `result.md` verdict block reads `route: mid` (or a pre-v83 `route: cheap`) — because work the mid row got wrong never goes back to it), complete them, then re-review; do not finish or archive. The review proposes one fix per problem class (the `review-phase` skill's *Findings, fix slices and re-review rounds*): copy each class's case list into its fix slice's `plan.md` as the acceptance matrix the executor proves case by case, and plan the next round as a bounded one (its number; each fix against its case list and any slice added since in full, each fix's blast radius, the validation suite; earlier results reused for what no fix touched).
- **Stop instead of another round.** When a re-review fails a problem class that already had a fix slice (the same rules failing a second time; the review marks it `repeat of round <n> finding <k>`), cut no further fix. Record the verdict, then set the `REVIEW` slice `pending --stop-kind decision --on-words "<what each answer does>"`, ask the operator by the stop rules, and STOP. The answers: one more fix with a simpler rule (set the `REVIEW` slice back to `changes_requested` and cut it as above); accept and defer the rest as a job (`defer-job`, then clear the stop to `in_progress` for one more round with that class out of scope); or cut scope (record it in `intent.md`, then clear the stop to `in_progress` for one more round against what is left).
- On `blocked`: record the blocker; do not finish or archive.

Durable-doc versioning happens **in a docs phase the operator creates** — no slice of this phase runs `doc-new-version` (the review's two named gate sections excepted). Every slice that changes durable truth appends a one-line "Doc impact" note to `phase.md`; the passing review verifies that list; the engine then stamps `consolidation: pending`, which keeps the phase out of archiving until `docs-consolidated <P>`. `docs/current/*.md` is therefore expected to trail the code between docs phases — `docs-debt` names what is owed at any time, and `/create-phase`'s docs-phase route turns it into the phase that pays it. Never patch `docs/current/*.md` or old versions.
