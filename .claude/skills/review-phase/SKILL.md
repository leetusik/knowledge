# review-phase

The phase review is executed by `slice-executor` on the high row — reviews never run on a lower row — dispatched by the orchestrator at the `REVIEW` slice; this is its checklist. It is where the phase's slices are **validated together** — the orchestrator trusted each executor's `done` and did not re-run per-slice validation, so re-run it here across the whole phase — and where the phase's durable-doc changes are **verified, not consolidated**: you check that the "Doc impact" notes in `phase.md` cover everything the phase changed, and a docs phase the operator creates later turns them into versions. You write exactly two doc sections yourself (the carve-out below), never source code, and you do not implement fixes — those are done by fix slices.

**In a phase worktree — one the operator asked for — the carve-out is recorded, not written.** If the phase's `phase.json` carries an `execution` block with `mode: "parallel"` (the review then runs in that phase's worktree), a passing review creates **no** doc versions at all — a doc version copies the doc's whole body and writes the one shared `docs/index.json`, so two branches versioning at once fork it. Instead it appends the two sections it would have written to `phase.md`'s `## Doc impact` as notes tagged `(gate section — written at merge)`: the stage-4 checklist lines verbatim, and any `## Operator Runtime` change as the exact text; the post-merge step on the default stream writes exactly those. Everything else — validating all slices together, judging the phase, recording the verdict — is unchanged. A phase with no `execution` block — which is every phase nobody asked into a worktree — reviews on the default stream and writes the sections itself, as does one carrying v42's legacy `mode: "default"` pin. See the `parallel-phase` skill.

**The operator acceptance gate: on a gated phase you are not the last word.** Read the phase's `phase.json`. `acceptance.required` is `true` (the phase changes operator-visible surfaces — declared by the orchestrator at the `DECOMP` boundary), `false` (waived, with the reason in `note`), or `null` (undeclared — the engine refuses a `pass` until the orchestrator declares it; report that as a finding rather than guessing). A phase carrying **no `acceptance` block at all** is legacy (created before workspace v32) and reviews exactly as it always did. Only when `required` is `true` do the gate stages below apply, and only then do you return a `walkthrough` — the concrete script the operator runs against the running product. You never run `accept-gate` yourself: you return the walkthrough, the orchestrator opens the gate, and the operator has the last word. In a phase worktree the gate composes unchanged — the review runs on the branch, and the gate opens and is cleared there against the branch's running product before `pass` is recorded, so `parallel-gate`'s "branch phase `done` + review `pass`" already implies the operator accepted it; only the doc versions are created later, on the default stream.

## The boundary — the review reviews the phase, not the whole system

The **boundary** of a phase is what it changed: the product files in its commit range — `python3 scripts/workflow.py phase-scope <P>` prints the creation commit, the range and the files (measured from the merge-base in parallel mode; read-only, and advisory where git cannot answer) — plus the surfaces those files feed and the claims the phase made about them (`intent.md`, `## Decisions`, each slice's `result.md`). Everything you check is inside it: the slices' validation, the headline claims, the fresh-eyes walk, the regression lines. A file many surfaces share — global styles, chrome or layout, a shared library, a dependency manifest or build config — **widens** the boundary to every surface it feeds, and a checklist line you cannot place is **inside** (when in doubt, re-run). What you notice **outside** the boundary is an **observation**: list it as a deferred-job candidate (title · reason · trigger) for the orchestrator to file, never a finding, and do not re-verify it further — the verdict is about the phase. The product-wide sweep is no review's duty: the operator runs it as a **QA phase** (the `create-phase` skill's *QA-sweep route*). A plan that says "N lines, read it whole, re-run all of it" is exactly what this section retires.

Read:

- `CLAUDE.md`
- the `docs/current/` **sections** the phase actually touched (per its `## Doc impact` list) — not the whole doc set, and not `docs/index.json`: that is version history, and `validate` checks currency for you. Reading a section to judge the phase is fine; **rewriting one is not** — that is the docs phase's job, and the whole-doc rewrite is what this review no longer pays for
- `python3 scripts/workflow.py next` for the pointer (no per-slice re-read of `works/backlog.md` — it is generated from the same state)
- the phase folder under `works/phases/active/<P>/`: `phase.md` — the **bounded notebook**, rewritten as the phase ran, read only through `phase-section` (`phase-section <P>` for the index, `<P> <name>` for a section, `--list` / `--entry K` / `--page N`, `--topic <slug>` to follow a gist line's pointer), never with `Read` or `cat`, and its `topics/*.md` beside it — and each completed slice's `slice.json` + `result.md`, read **head-first** (each `result.md` opens with that slice's verdict block: status, validation commands, deviations), whole wherever the detail matters
- the phase's `## Operator Questions` list in `phase.md` — every entry has to be routed before this review can pass
- `python3 scripts/workflow.py phase-scope <P>` — the phase's boundary: its creation commit, commit range and the product files it changed (see *The boundary* above)
- on a gated phase: `## Operator Runtime` in `docs/current/operations.md` (how the operator runs and views the product) and `## Regression Checklist` in `docs/current/qa.md` (the cumulative product smoke list — read whole so you can classify every line, re-run only inside the boundary)

Check:

- Did the phase objective actually ship?
- Did each slice meet its brief and plan? Are deviations explained in `result.md`?
- **Validate all slices together** (the orchestrator no longer re-runs per-slice validation): re-run each slice's validation commands — they are in the verdict block at the head of its `result.md`, with its `plan.md` as the fallback — plus `python3 scripts/workflow.py validate`. Do they pass across the finished phase?
- Does the `## Doc impact` list in `phase.md` **cover every durable-truth change the phase made** (product, architecture, API, …)? That list is the sole input to the later consolidation, so a missing note would never reach a doc version: **append it yourself** (`phase-section <P> "Doc impact" --append`) and report it under `doc_impact_added:`. A gap in the list is not a finding on its own: a fix slice and a re-review round would only paste the text you already drafted.
- Do `docs/current/*.md` match the latest versions in `docs/index.json`? (`python3 scripts/workflow.py validate` checks this.) They are expected to be **behind the code** until a docs phase runs — that is the deferral, not a defect.
- **Cross-check the notebook against the logs.** `phase.md` is bounded state that each slice *rewrote*, so what a slice knew survives only if it was written into `## Decisions` (or consumed and dropped on purpose). Read the notebook **and** every `result.md`: a decision or constraint a `result.md` records that no longer appears anywhere in `phase.md` is a **finding**. **A decision counts as present when its gist line is in `## Decisions` and its detail is in the linked topic** (`topics/<slug>.md`, `topics/breakdown.md` for a breakdown): the topics are part of the notebook. A dangling-pointer warning from `validate` (a gist line whose topic or heading is gone) is a lost decision, so a **finding**; a `## Doc impact` line missing for a durable-truth change a slice's log describes is one you append (above). (The notebook being *shorter* is not a finding — that is the point; the pre-edit text is in git.)
- Is every entry on `phase.md`'s `## Operator Questions` list **routed** — folded into the walkthrough as a decision for the operator, or listed for the orchestrator to file with `defer-job`? An entry already collapsed to `(resolved → <ref>)` counts as routed. An unrouted entry is a finding, and the review may not pass with one.
- On a gated phase: did you open the running product **yourself**, or are you about to pass on other slices' reports?
- Did you stay inside the boundary — `phase-scope <P>` read, every checklist line classified inside/outside, and what you noticed outside listed as deferred-job candidates rather than findings?
- Did a design round ship a **throwaway in-product mockup route**? (One exists only when the operator asked for a mockup in addition to the job's working canvas — `Mockup: requested` in `intent.md`, or asked for during the round; a job reviewed on its canvas alone leaves no route to check here.) Then no **orphaned design route** may remain: whichever slice implemented the surface for real deletes it (under `design-only` the route deliberately survives into the apply phase and is deleted there). A leftover route is a finding.
- Did the phase build a signed design job? Its Design canvas Artifact is now history: list each **implemented** job's canvas (`job.json` status `implemented`, its `canvas.url`) in the walkthrough as a decision (on a waived phase, in your return for the orchestrator to raise) — "delete canvas <link>: its design is built and signed in the repo". You cannot delete it (you have no `Artifact` tool), and the orchestrator deletes one only on the operator's yes. A signed job not yet marked `implemented` whose build landed in this phase is a finding.
- **Nested install:** did the team-rules check (next section) run for every repo the phase touched, and is it recorded in `result.md` as `team-rules check:`?
- Are any issues serious enough to require fix slices?

## Team-rules check — nested installs

A nested install's product commits, branches and pull requests land in the team's own repos, under rules the team set: a commit convention, an author and trailer policy, a branch pattern, a pull-request shape, rules files. Nothing else reads the finished work against them, so this review does, in one read-only pass inside the boundary. It reads through `git log` and `gh pr view` only; it never creates or edits a commit, a branch or a pull request.

Where it runs:

- **Multi-repo host** (`python3 scripts/workflow.py nested-repos` lists repos): once per repo whose `phase-scope <P>` block shows commits or files. A repo printed as `(untouched)` or as not in this worktree set was not changed by the phase: skip it.
- **Single-repo nested install:** the host is the one repo. Items 1-5 and 7, plus item 6 against the host's own CONTRIBUTING, AGENTS.md or CLAUDE.md when it has one.
- **At-root install:** skipped. There is no host/nested split, and the contract's Commit Convention is the only one.

For each repo, take the `base=` and `head=` of its `phase-scope` block and read the range with `git -C <repo> log --format='%H%n%an <%ae>%n%B%x00' <base>..<head>` (the host: the same without `-C`; in a worktree set `<repo>` is the repo's worktree at `<host worktree>/<repo>/`, which `phase-scope` reads too). Check, one line per item, `ok` or the offending commits:

1. Subjects follow that repo's commit convention (`python3 scripts/workflow.py nested-convention [--repo <name>]`).
2. Authorship and trailers: the author is who the convention says; `Co-Authored-By` or any AI attribution appears only where it says `allowed`.
3. No phase, slice or deferred IDs (`P<N>`, `P<N>.S<n>`, `D<N>`: `P46-k2`, `P12` and `P-7kq2` alike) and no workspace paths (`workflow/`, `CLAUDE.local.md`, `.claude/settings.local.json`) in subjects, bodies or branch names.
4. The branch follows that repo's branch pattern, with no IDs in it.
5. A pull request, when one exists: `gh pr view <branch> --json title,body,commits,baseRefName`, run in the repo. Its title, body and base follow the repo's PR rules, with no IDs, workspace paths or workspace files. No pull request yet, or no `gh` here, is `n/a`, not a failure.
6. The repo's own rules files (`nested-repos` lists each repo's `rules`) were held for what the phase changed, e.g. the checks or guards they require before a merge.
7. No workspace file is tracked in the repo: `git -C <repo> ls-files -- workflow CLAUDE.local.md .claude/settings.local.json` prints nothing.

Record it in `result.md` as `team-rules check:` with one row per repo and item (one row per item in a single-repo install). A failed item is a **finding** with a fix slice. Rewording or amending commits that already exist is history rewriting: the fix slice names it, and nothing is rewritten without the operator's word. When the phase touched no product file, write `team-rules check: n/a (0 product files)`.

## Gate stages — only when `acceptance.required` is `true`

Run these after validating all the slices together and before rendering the verdict. On a waived (`false`) or legacy phase, skip the whole section.

1. **Find the manifest.** `## Operator Runtime` in `docs/current/operations.md` gives the run command(s), the mode (dev vs production build), the origin/host the operator browses, the devices/viewports/browsers, and the production build command + origin when they differ. If that section is **absent, or still carries its `UNFILLED` marker**, stop and return `needs_operator` asking the operator to fill it — never substitute your own most convenient runtime.
2. **Independent spot-check (you open the product).** Open the running product in that runtime and access path and verify the phase's headline claims yourself — a handful of key flows, end to end. Never pass a phase purely on the fidelity slice's or any other slice's report. When the manifest's runtime differs from the production build, check both: whole bug classes (dev-only double effects, reload semantics, origin and viewport differences) live in exactly that gap. **Drive it with Claude in Chrome** — the workspace's prescribed instrument for real-browser work, its `mcp__claude-in-chrome__*` tools, you picking each next action — **in place of a pre-written assertion suite**, which can only assert the selectors someone already thought of; the same instrument serves stages 3 and 4. On the agent's own Chrome profile only: **before any other browser tool**, `list_connected_browsers`, then `select_browser` on the entry whose `deviceId` is `## Operator Runtime`'s `Agent's Chrome deviceId:` (never a `name`, a moving position label); no Chrome tools, no recorded id, or no match means `needs_operator` (the third halt), never borrowing the operator's browser. The fallback is the manifest's choice, never yours mid-run: where it names another real browser, run the identical checks in the identical runtime there — the doctrine's demands bind, the instrument does not. Setup, the halt and the fallback in full: `design-cowork`'s `reference/build.md`. Say in `result.md` which instrument you used, and never report a walk you did not make.
3. **Fresh-eyes walkthrough, inside the boundary.** Reach the surfaces the phase changed the way a first-time user would — from the entry point, along the path a reader actually takes — and use them; report everything dead, confusing, or annoying on those surfaces and on that path, **explicitly not judged against the design record**. Something the record drew is still a finding if it is bad in the flesh; something the record never drew (focus treatment, typeahead, empty and loading states) is still a finding even though no check exists for it. These findings go into the walkthrough for the operator to decide on — never into silent fixes, and never into overriding an approved design on your own authority. Surfaces the phase did not touch are not walked; what you happen to notice on the way there is an observation (see *The boundary*), not a finding. **One qualifier, for a phase whose operator-visible surface is a design mockup — a phase in which the operator asked for one:** a mockup is stubbed by design and **exempt from the functional sweep**, so its non-functional controls are not defects — name them in the walkthrough as deliberately unwired instead, and keep judging what it *is* for (does it run, does every designed element and state render, does it match the record). A phase shipping real wiring gets the unqualified stage above. A `design-only` phase that shipped no mockup has no running surface — its gate was waived at `DECOMP` with the fixed note, so this section does not run for it.
4. **Re-run the checklist lines inside the boundary.** Take the file list from `phase-scope <P>` and classify every existing line of `## Regression Checklist` — the qa doc's cumulative product smoke list — by its `<surface>`: **inside** when a changed file feeds that surface (a shared file widens the boundary; a line you cannot place is inside), **outside** otherwise. Re-run every inside line in the manifest runtime and with the same instrument as stage 2. Record the classification in `result.md` as a table — block, lines, inside/outside, result — naming every inside line that is not a clean pass and giving the outside count with the diff as its proof, never a quiet green. Outside lines are not re-run: that is the boundary, not a skipped step — a later phase touching a shared surface is still caught, because the shared file is in its diff. Then append this phase's headline checks in the shipped shape `- [ ] <surface>: <one observable behaviour> (P<N>)`. That append is one of the review's two named doc writes below — the smoke list may not wait for the operator's next docs phase. The whole list is re-run by an operator-created QA phase, never by a review.
5. **Route every operator question.** Each entry on `phase.md`'s `## Operator Questions` list is either folded into the walkthrough as a decision for the operator to take, **or** filed as a deferred job (an entry already collapsed to `(resolved → <ref>)` counts as routed). You may not run `defer-job`: list the jobs to file — title, reason, trigger — in `result.md` and in your return, and the orchestrator files them. An unrouted entry is a finding.
6. **Return the walkthrough.** Beside `review_verdict`, return a **`walkthrough`** field: the concrete script the operator runs — URLs to open, actions to try, in the manifest runtime and access path — plus the routed questions as decisions to take. It follows the stop rules (the contract's `pending` rule): at most ~5 decisions, only those that change a contract, contradict the operator's own words, or are costly to reverse after the build; the rest in one "decided as drawn" list; about 2k chars plus links. Keep it short enough that an operator will actually run it.

## Findings, fix slices and re-review rounds

**A finding is a problem class, not an instance.** A failing case is one symptom of a rule that usually fails in more places, and a round that reports one case buys one fix and then one more round for the next case. *Form the verdict* below keeps you from stopping at the first failing check; this keeps you from stopping at the first failing case. Before you write a finding:

1. Name the rule or invariant that failed.
2. Enumerate every case it governs, across every file that implements or describes it: its states, paths and modes (nested and single-repo installs, alone and beside others, before and after a compaction, …).
3. Test each case you can, live where the runtime allows.
4. Report **one finding per class**, listing its failing cases and the cases you checked that pass.

Propose **one fix slice per class**, never one per case. It names every file of the rule's family, not only the failing line; it carries the class's case list as its **acceptance matrix**, which the orchestrator copies into the fix's `plan.md` and the fix executor proves case by case; and it prefers the simplest rule that makes the whole class impossible over a patch to the failing case.

**Form the verdict from the complete picture, then branch on it.** Finish the validation and the judgment across every slice *first* — never abort at the first failing check, or the orchestrator learns one finding per review cycle instead of all of them at once. Only once the verdict is settled does the review split:

- On a **passing** review, before recording `pass`, do the two doc duties and no more. **(a) Verify and complete the list**: does `phase.md`'s `## Doc impact` cover every durable-truth change? Append any missing line yourself (`doc_impact_added:`). Report `doc_versions: none — deferred to a docs phase`. When `review-phase --verdict pass` is recorded, the engine stamps the phase's `consolidation` debt from that list and holds the phase out of archiving until a docs phase pays it with `doc-new-version` per note and `docs-consolidated <P>` (the operator starts one from `docs-debt`, through the `create-phase` skill's *docs-phase route*). **(b) Write the two named sections** — `## Regression Checklist` in the qa doc (stage 4's append) and `## Operator Runtime` in the operations doc, only when this phase changed them: `python3 scripts/workflow.py doc-new-version --doc <qa|operations> --summary "..." --source <P>.REVIEW`, edit **only that section** in the returned `edit_path`, then `python3 scripts/workflow.py rebuild-docs`. Nothing else in those docs, and no other doc at all. If the phase's only durable change was a section you just wrote, say so and the orchestrator records `docs-consolidated <P>` straight away — the debt is a mechanical read of the notes list, not a judgment. **In a phase worktree, (b) becomes notes**: no `doc-new-version` and no `rebuild-docs` on the branch — append each section you would have written to `## Doc impact` as `- qa.md: ## Regression Checklist append: <the lines> (P<N>.REVIEW) (gate section — written at merge)` / `- operations.md: ## Operator Runtime: <the change> (P<N>.REVIEW) (gate section — written at merge)`, and report `doc_versions: none — deferred to post-merge consolidation (parallel mode)`.
- On **`changes_requested` or `blocked`, stop here and hand back.** The two doc duties are pass-only work: do not run them, and do no other pass-only step either. Return to the orchestrator the verdict, the numbered findings, and the proposed fix slices (`<P>.F<n>`, one line of scope and a `risk` each — `high` when it repairs a defect in a slice whose verdict block reads `route: mid` (or a pre-v83 `route: cheap`), otherwise rated on the usual triggers); it decides what happens next — create the fix slices, or take the decision to the operator. This is a full stop, not a skipped step you carry on past: the review ends there. Every slice's verdict block records `model:` and `effort:` beside `route:`, and the rating rule is unchanged: it reads `route:` alone (`route: mid`, or a pre-v83 `route: cheap`, → a `high` fix, since work the mid row got wrong never goes back to it).

**Re-review rounds are bounded.** A round after a `changes_requested` states its number (`round <n>`, in `result.md`'s title and verdict) and checks three things: each fix against its full case list (and any other slice added since the last round, in full); each fix's blast radius, the files it touched and what reads them; and the validation suite (every slice's commands plus `validate`). For whatever no fix touched, it reuses the earlier rounds' results by reference instead of walking them again. A new problem in a fix's own surface is a finding. A new problem elsewhere in the boundary is a finding only when the earlier rounds could not have seen it, and the finding says why; otherwise it is a deferred-job candidate, so the rounds converge. When a class fails again after its fix slice ran, say so in the finding (`repeat of round <n> finding <k>`): the orchestrator then stops for the operator instead of cutting another fix.

## After a passing review — what the orchestrator does with it

On a phase whose gate is `required: true`, your `pass` does not end the phase:

1. The orchestrator runs `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough you returned>"` — the phase goes `pending` — files any deferred jobs you listed, commits, reports the walkthrough to the operator, and STOPS. `next` then prints `WAITING ON OPERATOR` with the walkthrough and the clear command.
2. The operator walks the running product. If they accept (one word clears it: "accept", "moveon"), the gate clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` (the operator's command, or the orchestrator's on their word) and the phase returns to `in_progress`.
3. On the resume the `REVIEW` slice is still `in_progress`, your `result.md` still carries `review_verdict: pass`, and the gate now shows `cleared_at`: the orchestrator records `review-phase <P> --verdict pass` **without re-dispatching the review**, validates, and commits.
4. If the operator reports failures instead, the orchestrator records `review-phase <P> --verdict changes_requested --note "operator-reported: ..."` — never refused, and it resets `walkthrough` / `requested_at` / `cleared_at` — creates `fix` slices from the report, runs them, and the review runs again as a bounded round (above), gate stages included.

Waived and legacy phases skip all of that: the verdict is recorded straight away, as it always was.

**Two commands you never run on a review slice:** `accept-gate` (a phase-state command — you return the walkthrough, the orchestrator opens the gate) and `defer-job` (you list the jobs, the orchestrator files them). A third you never run: `docs-consolidated` (the operator's, once a docs phase has landed the versions). Your workflow commands stay `doc-new-version` / `rebuild-docs` for the two named sections on a pass, plus `validate`.

**The review does not write the phase explainer.** Explaining is a separate operation the operator runs when they want one (`/knowledge:explain`, from the knowledge plugin); it left the review's default behaviour, so the review locates no explain skill, runs no KB probe, and has no offline fallback or commit of any kind. Its whole obligation is one pointer line, reported in `result.md` and in the structured return, identical on every verdict: `explain: not written — run /knowledge:explain P<N> for a document, or ask it for a book`. **An explain phase is the exception** (`## Explain` in `intent.md`): the unit (a document, a chapter or a book) is the phase's own work, and its review reads it, publishes it private and reads it in the reader, per `do-whole-phase`'s `reference/explain-review.md`.

The orchestrator records exactly one verdict (the executor returns it; the executor never runs `review-phase` itself):

```sh
python3 scripts/workflow.py review-phase <P> --verdict pass --reviewer slice-executor --note "short justification"
# or
python3 scripts/workflow.py review-phase <P> --verdict changes_requested --reviewer slice-executor --note "numbered issues + proposed fix slices like <P>.F1"
# or
python3 scripts/workflow.py review-phase <P> --verdict blocked --reviewer slice-executor --note "the blocker and needed input"
```

On a gated phase the engine refuses `--verdict pass` until `accept-gate <P> --clear` has stamped `cleared_at`, so the pass above is recorded on the resume after the operator's walkthrough, not in the same turn as the review. `pass` also marks the phase `done` **and closes the `REVIEW` slice** — the phase stays in `active/`; archiving is a separate step, never the review's (`/rotate-backlog`, which pays the doc debt first, `archive-all`, or `archive-phase`). `changes_requested` returns the phase to `in_progress` and sets the `REVIEW` slice to `changes_requested` (reopened for re-review). `blocked` sets **both the phase and the `REVIEW` slice** `blocked`. A recorded `pass` on a phase with "Doc impact" notes stamps its `consolidation` debt, and archiving stays blocked until `docs-consolidated <P>`. For a parallel-mode phase the same `pass` also opens the integration sequence the orchestrator then runs (`parallel-gate <P>` → `ExitWorktree` → local `git merge --no-ff` → `parallel-merge-finish` → the tagged gate-section notes → `parallel-teardown <P>`; push → PR is the remote variant, on request).
