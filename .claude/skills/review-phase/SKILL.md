# review-phase

The phase review is executed by `slice-executor-high` — the top executor tier; reviews never run on a lower tier — dispatched by the orchestrator at the `REVIEW` slice; this is its checklist. It is where the phase's slices are **validated together** — the orchestrator trusted each executor's `done` and did not re-run per-slice validation, so re-run it here across the whole phase — and where the phase's durable-doc changes are **verified, not consolidated**: you check that the "Doc impact" notes in `phase.md` cover everything the phase changed, and a docs phase the operator creates later turns them into versions. You write exactly two doc sections yourself (the carve-out below), never source code, and you do not implement fixes — those are done by fix slices.

**In a phase worktree — one the operator asked for — the carve-out is recorded, not written.** If the phase's `phase.json` carries an `execution` block with `mode: "parallel"` (the review then runs in that phase's worktree), a passing review creates **no** doc versions at all — doc versions are allocated from one shared `docs/index.json`, so two branches writing at once collide. Instead it appends the two sections it would have written to `phase.md`'s `## Doc impact` as notes tagged `(gate section — written at merge)`: the stage-4 checklist lines verbatim, and any `## Operator Runtime` change as the exact text; the post-merge step on the default stream writes exactly those. Everything else — validating all slices together, judging the phase, recording the verdict — is unchanged. A phase with no `execution` block — which is every phase nobody asked into a worktree — reviews on the default stream and writes the sections itself, as does one carrying v42's legacy `mode: "default"` pin. See the `parallel-phase` skill.

**The operator acceptance gate: on a gated phase you are not the last word.** Read the phase's `phase.json`. `acceptance.required` is `true` (the phase changes operator-visible surfaces — declared by the orchestrator at the `DECOMP` boundary), `false` (waived, with the reason in `note`), or `null` (undeclared — the engine refuses a `pass` until the orchestrator declares it; report that as a finding rather than guessing). A phase carrying **no `acceptance` block at all** is legacy (created before workspace v32) and reviews exactly as it always did. Only when `required` is `true` do the gate stages below apply, and only then do you return a `walkthrough` — the concrete script the operator runs against the running product. You never run `accept-gate` yourself: you return the walkthrough, the orchestrator opens the gate, and the operator has the last word. In a phase worktree the gate composes unchanged — the review runs on the branch, and the gate opens and is cleared there against the branch's running product before `pass` is recorded, so `parallel-gate`'s "branch phase `done` + review `pass`" already implies the operator accepted it; only the doc versions are created later, on the default stream.

## The boundary — the review reviews the phase, not the whole system

The **boundary** of a phase is what it changed: the product files in its commit range — `python3 scripts/workflow.py phase-scope <P>` prints the creation commit, the range and the files (measured from the merge-base in parallel mode; read-only, and advisory where git cannot answer) — plus the surfaces those files feed and the claims the phase made about them (`intent.md`, `## Decisions`, each slice's `result.md`). Everything you check is inside it: the slices' validation, the headline claims, the fresh-eyes walk, the regression lines. A file many surfaces share — global styles, chrome or layout, a shared library, a dependency manifest or build config — **widens** the boundary to every surface it feeds, and a checklist line you cannot place is **inside** (when in doubt, re-run). What you notice **outside** the boundary is an **observation**: list it as a deferred-job candidate (title · reason · trigger) for the orchestrator to file, never a finding, and do not re-verify it further — the verdict is about the phase. The product-wide sweep is no review's duty: the operator runs it as a **QA phase** (the `create-phase` skill's *QA-sweep route*). A plan that says "N lines, read it whole, re-run all of it" is exactly what this section retires.

Read:

- `CLAUDE.md`
- the `docs/current/` **sections** the phase actually touched (per its `## Doc impact` list) — not the whole doc set, and not `docs/index.json`: that is version history, and `validate` checks currency for you. Reading a section to judge the phase is fine; **rewriting one is not** — that is the docs phase's job, and the whole-doc rewrite is what this review no longer pays for
- `python3 scripts/workflow.py next` for the pointer (no per-slice re-read of `works/backlog.md` — it is generated from the same state)
- the phase folder under `works/phases/active/<P>/`: `phase.md` — the **bounded notebook**, rewritten as the phase ran — and each completed slice's `slice.json` + `result.md`, read **head-first** (each `result.md` opens with that slice's verdict block: status, validation commands, deviations), whole wherever the detail matters
- the phase's `## Operator Questions` list in `phase.md` — every entry has to be routed before this review can pass
- `python3 scripts/workflow.py phase-scope <P>` — the phase's boundary: its creation commit, commit range and the product files it changed (see *The boundary* above)
- on a gated phase: `## Operator Runtime` in `docs/current/operations.md` (how the operator runs and views the product) and `## Regression Checklist` in `docs/current/qa.md` (the cumulative product smoke list — read whole so you can classify every line, re-run only inside the boundary)

Check:

- Did the phase objective actually ship?
- Did each slice meet its brief and plan? Are deviations explained in `result.md`?
- **Validate all slices together** (the orchestrator no longer re-runs per-slice validation): re-run each slice's validation commands — they are in the verdict block at the head of its `result.md`, with its `plan.md` as the fallback — plus `python3 scripts/workflow.py validate`. Do they pass across the finished phase?
- Does the `## Doc impact` list in `phase.md` **cover every durable-truth change the phase made** (product, architecture, API, …)? That list is the sole input to the later consolidation, so a missing note is a review finding, not a detail — the change would otherwise never reach a doc version.
- Do `docs/current/*.md` match the latest versions in `docs/index.json`? (`python3 scripts/workflow.py validate` checks this.) They are expected to be **behind the code** until a docs phase runs — that is the deferral, not a defect.
- **Cross-check the notebook against the logs.** `phase.md` is bounded state that each slice *rewrote*, so what a slice knew survives only if it was written into `## Decisions` (or consumed and dropped on purpose). Read the notebook **and** every `result.md`: a decision or constraint a `result.md` records that no longer appears anywhere in `phase.md` is a **finding**, and so is a `## Doc impact` line missing for a durable-truth change a slice's log describes. (The notebook being *shorter* is not a finding — that is the point; the pre-edit text is in git.)
- Is every entry on `phase.md`'s `## Operator Questions` list **routed** — folded into the walkthrough as a decision for the operator, or listed for the orchestrator to file with `defer-job`? An unrouted entry is a finding, and the review may not pass with one.
- On a gated phase: did you open the running product **yourself**, or are you about to pass on other slices' reports?
- Did you stay inside the boundary — `phase-scope <P>` read, every checklist line classified inside/outside, and what you noticed outside listed as deferred-job candidates rather than findings?
- Did a design round ship a **throwaway mockup route**? (One exists only when the operator asked for a mockup — `Mockup: requested` in `intent.md`, or asked for during the round; a round that shipped none leaves nothing to check here.) Then no **orphaned design route** may remain: whichever slice implemented the surface for real deletes it (under `design-only` the route deliberately survives into the apply phase and is deleted there). A leftover route is a finding.
- Are any issues serious enough to require fix slices?

## Gate stages — only when `acceptance.required` is `true`

Run these after validating all the slices together and before rendering the verdict. On a waived (`false`) or legacy phase, skip the whole section.

1. **Find the manifest.** `## Operator Runtime` in `docs/current/operations.md` gives the run command(s), the mode (dev vs production build), the origin/host the operator browses, the devices/viewports/browsers, and the production build command + origin when they differ. If that section is **absent, or still carries its `UNFILLED` marker**, stop and return `needs_operator` asking the operator to fill it — never substitute your own most convenient runtime.
2. **Independent spot-check (you open the product).** Open the running product in that runtime and access path and verify the phase's headline claims yourself — a handful of key flows, end to end. Never pass a phase purely on the fidelity slice's or any other slice's report. When the manifest's runtime differs from the production build, check both: whole bug classes (dev-only double effects, reload semantics, origin and viewport differences) live in exactly that gap. **Drive it with Aside** — the workspace's prescribed instrument for real-browser work: the `repl` surface over Bash, `aside repl "<js>"` (one tool — `page`, `snapshot()`, locators, page JS, screenshots — and you pick each next action; the re-attach preamble is in `design-cowork`), and **never a standing `aside mcp` registration**, whose identical tool definition is paid in every session, and always on the agent's own Aside profile (`aside repl --account <id> "<js>"`, the id from the manifest — never the operator's signed-in one; a manifest naming Aside with no agent account id, or only a personal profile on the machine, means `needs_operator`) — **in place of a pre-written assertion suite**, which can only assert the selectors someone already thought of; the same instrument serves stages 3 and 4. Aside is macOS-only and needs an account, so where it cannot be installed run the identical checks in the identical runtime through whatever real browser the workspace has — the doctrine's demands bind, the instrument does not. Say in `result.md` which instrument you used, and never report a walk you did not make.
3. **Fresh-eyes walkthrough, inside the boundary.** Reach the surfaces the phase changed the way a first-time user would — from the entry point, along the path a reader actually takes — and use them; report everything dead, confusing, or annoying on those surfaces and on that path, **explicitly not judged against the design record**. Something the record drew is still a finding if it is bad in the flesh; something the record never drew (focus treatment, typeahead, empty and loading states) is still a finding even though no check exists for it. These findings go into the walkthrough for the operator to decide on — never into silent fixes, and never into overriding an approved design on your own authority. Surfaces the phase did not touch are not walked; what you happen to notice on the way there is an observation (see *The boundary*), not a finding. **One qualifier, for a phase whose operator-visible surface is a design mockup — a phase in which the operator asked for one:** a mockup is stubbed by design and **exempt from the functional sweep**, so its non-functional controls are not defects — name them in the walkthrough as deliberately unwired instead, and keep judging what it *is* for (does it run, does every designed element and state render, does it match the record). A phase shipping real wiring gets the unqualified stage above. A `design-only` phase that shipped no mockup has no running surface — its gate was waived at `DECOMP` with the fixed note, so this section does not run for it.
4. **Re-run the checklist lines inside the boundary.** Take the file list from `phase-scope <P>` and classify every existing line of `## Regression Checklist` — the qa doc's cumulative product smoke list — by its `<surface>`: **inside** when a changed file feeds that surface (a shared file widens the boundary; a line you cannot place is inside), **outside** otherwise. Re-run every inside line in the manifest runtime and with the same instrument as stage 2. Record the classification in `result.md` as a table — block, lines, inside/outside, result — naming every inside line that is not a clean pass and giving the outside count with the diff as its proof, never a quiet green. Outside lines are not re-run: that is the boundary, not a skipped step — a later phase touching a shared surface is still caught, because the shared file is in its diff. Then append this phase's headline checks in the shipped shape `- [ ] <surface>: <one observable behaviour> (P<N>)`. That append is one of the review's two named doc writes below — the smoke list may not wait for the operator's next docs phase. The whole list is re-run by an operator-created QA phase, never by a review.
5. **Route every operator question.** Each entry on `phase.md`'s `## Operator Questions` list is either folded into the walkthrough as a decision for the operator to take, **or** filed as a deferred job. You may not run `defer-job`: list the jobs to file — title, reason, trigger — in `result.md` and in your return, and the orchestrator files them. An unrouted entry is a finding.
6. **Return the walkthrough.** Beside `review_verdict`, return a **`walkthrough`** field: the concrete script the operator runs — URLs to open, actions to try, in the manifest runtime and access path — plus the routed questions as decisions to take. Keep it short enough that an operator will actually run it.

**Form the verdict from the complete picture, then branch on it.** Finish the validation and the judgment across every slice *first* — never abort at the first failing check, or the orchestrator learns one finding per review cycle instead of all of them at once. Only once the verdict is settled does the review split:

- On a **passing** review, before recording `pass`, do the two doc duties and no more. **(a) Verify the list**: does `phase.md`'s `## Doc impact` cover every durable-truth change? Report `doc_versions: none — deferred to a docs phase`. When `review-phase --verdict pass` is recorded, the engine stamps the phase's `consolidation` debt from that list and holds the phase out of archiving until a docs phase pays it with `doc-new-version` per note and `docs-consolidated <P>` (the operator starts one from `docs-debt`, through the `create-phase` skill's *docs-phase route*). **(b) Write the two named sections** — `## Regression Checklist` in the qa doc (stage 4's append) and `## Operator Runtime` in the operations doc, only when this phase changed them: `python3 scripts/workflow.py doc-new-version --doc <qa|operations> --summary "..." --source <P>.REVIEW`, edit **only that section** in the returned `edit_path`, then `python3 scripts/workflow.py rebuild-docs`. Nothing else in those docs, and no other doc at all. If the phase's only durable change was a section you just wrote, say so and the orchestrator records `docs-consolidated <P>` straight away — the debt is a mechanical read of the notes list, not a judgment. **In a phase worktree, (b) becomes notes**: no `doc-new-version` and no `rebuild-docs` on the branch — append each section you would have written to `## Doc impact` as `- qa.md: ## Regression Checklist append: <the lines> (P<N>.REVIEW) (gate section — written at merge)` / `- operations.md: ## Operator Runtime: <the change> (P<N>.REVIEW) (gate section — written at merge)`, and report `doc_versions: none — deferred to post-merge consolidation (parallel mode)`.
- On **`changes_requested` or `blocked`, stop here and hand back.** The two doc duties are pass-only work: do not run them, and do no other pass-only step either. Return to the orchestrator the verdict, the numbered findings, and the proposed fix slices (`<P>.F<n>`, one line of scope each); it decides what happens next — create the fix slices, or take the decision to the operator. This is a full stop, not a skipped step you carry on past: the review ends there.

## After a passing review — what the orchestrator does with it

On a phase whose gate is `required: true`, your `pass` does not end the phase:

1. The orchestrator runs `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough you returned>"` — the phase goes `pending` — files any deferred jobs you listed, commits, reports the walkthrough to the operator, and STOPS. `next` then prints `WAITING ON OPERATOR` with the walkthrough and the clear command.
2. The operator walks the running product. If they accept, the gate clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` (the operator's command, or the orchestrator's on their explicit say-so) and the phase returns to `in_progress`.
3. On the resume the `REVIEW` slice is still `in_progress`, your `result.md` still carries `review_verdict: pass`, and the gate now shows `cleared_at`: the orchestrator records `review-phase <P> --verdict pass` **without re-dispatching the review**, validates, and commits.
4. If the operator reports failures instead, the orchestrator records `review-phase <P> --verdict changes_requested --note "operator-reported: ..."` — never refused, and it resets `walkthrough` / `requested_at` / `cleared_at` — creates `fix` slices from the report, runs them, and the review starts again from the top, gate stages included.

Waived and legacy phases skip all of that: the verdict is recorded straight away, as it always was.

**Two commands you never run on a review slice:** `accept-gate` (a phase-state command — you return the walkthrough, the orchestrator opens the gate) and `defer-job` (you list the jobs, the orchestrator files them). A third you never run: `docs-consolidated` (the operator's, once a docs phase has landed the versions). Your workflow commands stay `doc-new-version` / `rebuild-docs` for the two named sections on a pass, plus `validate`.

**The review does not write the phase explainer.** Explaining is a separate operation the operator runs when they want one (`/explain`); it left the review's default behaviour, so the review locates no explain skill, runs no KB probe, and has no offline fallback or commit of any kind. Its whole obligation is one pointer line, reported in `result.md` and in the structured return, identical on every verdict: `explain: not written — run /explain for this phase`.

The orchestrator records exactly one verdict (the executor returns it; the executor never runs `review-phase` itself):

```sh
python3 scripts/workflow.py review-phase <P> --verdict pass --reviewer slice-executor-high --note "short justification"
# or
python3 scripts/workflow.py review-phase <P> --verdict changes_requested --reviewer slice-executor-high --note "numbered issues + proposed fix slices like P1.F1"
# or
python3 scripts/workflow.py review-phase <P> --verdict blocked --reviewer slice-executor-high --note "the blocker and needed input"
```

On a gated phase the engine refuses `--verdict pass` until `accept-gate <P> --clear` has stamped `cleared_at`, so the pass above is recorded on the resume after the operator's walkthrough, not in the same turn as the review. `pass` also marks the phase `done` **and closes the `REVIEW` slice** — the phase stays in `active/`; archiving is a separate, manual step (`archive-all`, `rotate-backlog`, or `archive-phase`). `changes_requested` returns the phase to `in_progress` and sets the `REVIEW` slice to `changes_requested` (reopened for re-review). `blocked` sets **both the phase and the `REVIEW` slice** `blocked`. A recorded `pass` on a phase with "Doc impact" notes stamps its `consolidation` debt, and archiving stays blocked until `docs-consolidated <P>`. For a parallel-mode phase the same `pass` also opens the integration sequence the orchestrator then runs (`parallel-gate <P>` → `ExitWorktree` → local `git merge --no-ff` → `parallel-merge-finish` → the tagged gate-section notes → `parallel-teardown <P>`; push → PR is the remote variant, on request).
