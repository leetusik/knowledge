# do-whole-phase — a phase in its own worktree

**The phase runs on this checkout unless the operator asked for a worktree (v43).** By default do nothing about worktrees — run the whole loop here, on the current branch. Move only on the operator's word: when they asked in this invocation (`worktree`, `in a worktree`, `in parallel`, `on its own branch`) and the phase is still `planned`, run `python3 scripts/workflow.py parallel-start <P>` (the stamp commit holds only the phase folder plus the regenerated `works/` files, a dirty tree is allowed, and your other uncommitted edits stay behind here), call `EnterWorktree` with the printed `worktree=` path, re-run `next` there (`stream=phase/P<N>-<slug>`), and run the whole loop in that worktree in this same session — background executors dispatched from there run in the worktree. **In a nested install** the same word runs `parallel-start <P> --host-branch <name>` after you propose the name from the host's recorded custom (`nested-convention`) and the operator confirms it, and `EnterWorktree` goes to the printed **host** worktree path. Do the same when they ran `parallel-start <P>` themselves and the phase already carries a `mode: "parallel"` execution block. Never run `parallel-start` on your own initiative — a `hint:` about a phase queued behind a live one is a suggestion to relay, not an instruction — and never ask for a worktree on a docs phase, since `doc-new-version` runs only on the default stream (see the `parallel-phase` skill).

- **If the operator asked this phase into its own worktree, a `pass` is what opens its integration:** run the `parallel-phase` sequence — `parallel-gate <P>` from the worktree → `ExitWorktree` (`keep`) → `git pull --ff-only` only if `main` tracks a remote → STOP and ask if anything is staged or a file the merge touches is uncommitted — typically the generated `works/` files after a phase was created here since the stamp, which is workflow state you commit first (git refuses both; never unstage or discard the operator's work) → `git merge --no-ff phase/P<N>-<slug> -m "merge(P<N>): <name>"` → `parallel-merge-finish` → `doc-new-version` + `rebuild-docs` for the `## Doc impact` notes tagged `(gate section — written at merge)` → commit → `parallel-teardown <P>` → commit. A closed gate means STOP and report — never merge past it. **In a nested install** integrate by `parallel-phase` §5's nested form instead: the merge, `parallel-merge-finish` and the commits run as `git -C workflow …`, the host side follows the recorded custom, and nothing is pushed, opened or merged without the operator's word. The rest of the doc debt waits for the operator's docs phase, which records `parallel-consolidated <P>`; push → PR → CI → `gh pr merge` is the remote variant, only when the operator asks. A phase that ran on this stream has nothing to integrate: report its `consolidation: pending` debt to the operator and stop there.
