# do-whole-phase — a phase in its own worktree

**The phase runs on this checkout unless the operator asked for a worktree (v43).** By default do nothing about worktrees — run the whole loop here, on the current branch. Move only on the operator's word: when they asked in this invocation (`worktree`, `in a worktree`, `in parallel`, `on its own branch`) and the phase is still `planned`, run `python3 scripts/workflow.py parallel-start <P>` (the stamp commit holds only the phase folder plus the regenerated `works/` files, a dirty tree is allowed, and your other uncommitted edits stay behind here), call `EnterWorktree` with the printed `worktree=` path, re-run `next` there (`stream=phase/P<N>-<slug>`), and run the whole loop in that worktree in this same session — background executors dispatched from there run in the worktree. **In a nested install** the same word runs `parallel-start <P> --host-branch <name>` after you propose the name from the host's recorded custom (`nested-convention`) and the operator confirms it, and `EnterWorktree` goes to the printed **host** worktree path. Do the same when they ran `parallel-start <P>` themselves and the phase already carries a `mode: "parallel"` execution block. Never run `parallel-start` on your own initiative — a `hint:` about a phase queued behind a live one is a suggestion to relay, not an instruction — and never ask for a worktree on a docs phase, since `doc-new-version` runs only on the default stream (see the `parallel-phase` skill).

**One exception: an explain phase (v86).** `create-phase`'s explain route starts it in its own worktree unless its `## Explain` says `worktree: no`: the route's one confirmation is the operator's word, so you never ask again. Right after the intake commit it runs `parallel-start <P>` — **in a nested install with no `--host-branch`**, which cuts a **detached** host worktree at the host base (no branch to name, nothing to integrate on the host; `--repo` still needs one) — then `EnterWorktree` (nested: the printed host path) and `next` (`stream=…`, `explain_unit=<document|book|chapter>`), and runs this skill there in `auto`. A long full run is best started in a session of its own: one session drives one checkout at a time, and an explain's `pending` stops halt only its own stream. Manual-mode research permissions live in the untracked `.claude/settings.local.json`; Claude Code (v2.1.211 and later) reads and writes the **main checkout's** copy from a worktree session, so the preflight's rules apply there too (on Windows, or where Claude Code does not use the repository root, put them in user settings, or run in auto mode, which needs none).

- **If the operator asked this phase into its own worktree, a `pass` is what opens its integration:** run the `parallel-phase` sequence — `parallel-gate <P>` from the worktree → `ExitWorktree` (`keep`) → `git pull --ff-only` only if `main` tracks a remote → STOP and ask if anything is staged or a file the merge touches is uncommitted — typically the generated `works/` files, which a phase worktree refreshes here as it runs (v67) and a phase created here since the stamp rewrites, which is workflow state you commit first (git refuses both; never unstage or discard the operator's work) → `git merge --no-ff phase/P<N>-<slug> -m "merge(P<N>): <name>"` → `parallel-merge-finish` → `doc-new-version` + `rebuild-docs` for the `## Doc impact` notes tagged `(gate section — written at merge)` → commit → `parallel-teardown <P>` → commit. A closed gate means STOP and report — never merge past it. **In a nested install** integrate by `parallel-phase` §5's nested form instead: the merge, `parallel-merge-finish` and the commits run as `git -C workflow …`, the host side follows the recorded custom, and nothing is pushed, opened or merged without the operator's word. The rest of the doc debt waits for the operator's docs phase, which records `parallel-consolidated <P>`; push → PR → CI → `gh pr merge` is the remote variant, only when the operator asks. A phase that ran on this stream has nothing to integrate: report its `consolidation: pending` debt to the operator and stop there.
- **An explain phase merges back by itself, with no stop.** Its branch touches only its phase folder (notebook, slices, dossier, draft), the five `works/` files and added deferred jobs: it writes no doc version, no `## Doc impact` note, no `## Regression Checklist` line, no product file. So right after its `pass` (a document or chapter: the gate was waived; a book: the operator's `accept-gate <P> --clear` came before the pass) run the integration above without asking. `parallel-gate <P>` does not close on a busy default stream when it prints `exemption=phase-folder-only (<n> paths)` — the engine checked the branch's diff since its merge-base — while `exemption=none: <path> (<status>)` means the branch touched more and the busy reasons stand. The passing review with no `## Doc impact` note already settled the phase's consolidation to `done`: no doc debt to report, and it is archivable after teardown. Tear down with `parallel-teardown <P> --discard-ignored` in a nested install (it deletes the ignored `pages/` cache, whose passages the committed findings quote); at root plain `parallel-teardown <P>` (git drops ignored files itself, and the flag is refused). A detached host worktree has no branch to keep and skips `parallel-phase` §5's nested step 7 (the host side).
- **When the automatic merge cannot run** — the gate closed for any other reason, something staged, an uncommitted file the merge touches, a conflict outside the generated files — leave the branch `done` and unmerged, never unstage or discard anyone's work, and say so in the closing report. `next` on the default stream then prints `merge_ready=<P>:<branch>`, and whoever drives that stream merges it at its next slice boundary.
- **The closing report** of an explain run comes last: after the teardown and its commit, from the default checkout — or, when the merge could not run, from the worktree with the unmerged note above.
- **`merge_ready=` on the default stream** (any phase, any run): a stamped phase is `done` with a `pass` on its branch and not merged here. At a slice boundary (nothing staged, the last slice committed), before the next slice, integrate it from this checkout by the sequence above, `parallel-gate <P>` first; a closed gate leaves it for later, never merged past.
