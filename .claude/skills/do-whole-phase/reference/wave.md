# do-whole-phase — a wave: several slices at once

Read this when the phase's `DECOMP` **declared** its slices (`--depends-on <id>` or `--depends-on none`; `next` then prints `ready_slices=`). Its *Resume* runs at every session start, after every compaction and before every start or commit, with one ready slice or a barrier next too: it reads only the disk, and does nothing when nothing waits. The rest applies when `ready_slices=` lists more than one id, or a slice becomes ready while others still run; otherwise (one ready slice, a barrier) the loop in `SKILL.md` is unchanged. `/do-next-slice` never runs a wave: in a declared phase it stops while one is unfinished (its `reference/verdicts.md`). An explain phase declares nothing, so it stays sequential.

## What the engine prints

A declared phase's `next` (and `run-phases`) adds, after `next_slice=` and in its WAITING branch, the lines below. While a barrier runs alone it adds none and the card has no `wave:` line: the phase then reads as an undeclared one.

- `ready_slices=<ids|none>`: the slices that may start now, by order. A declared slice is ready when it is `todo` or `ready` and every slice it depends on is `done`. A **barrier** (`DECOMP`, `DECOMP2`, `REVIEW`, a `co-work` slice, and every undeclared slice) is ready only alone: first open slice, nothing in progress. It also ends the walk, so nothing behind a barrier starts before it is done.
- `running_slices=<ids|none>`: the wave's slices `in_progress`, never a barrier.
- With a stop on disk (a `pending` or `blocked` slice anywhere): `ready_slices=none -- stopped by <id> (<status>)…: nothing new starts while a stop is on disk`, and if slices run, `running_slices=<ids> -- already running beside the stop: wait for each, then finish and commit it`.
- `current_slice=` / `target_slice=` stay the plain pointer (the first open slice). In a wave they name the first open slice, which may already be running: the work is the whole `ready_slices=` list.
- The resume card adds `wave: running=<ids>; returned=<ids>; ready=<ids>; stops=<ids> -- …`, and a `stop: slice <id> …` line for a sibling's stop the pointer does not show. `returned` are the running slices whose `result.md` exists.
- `start-slice` warns, never refuses: it prints one `warning:` line, and still starts the slice, for a start the ready set would not make (a declared slice whose dependency is not `done`, or a barrier beside a running slice).

## Declaration and independence

`DECOMP` declares every non-barrier slice and writes each slice's **set** in its `## <slice id>` block of `topics/breakdown.md` (`reference/decomposition.md`); read the sets there (`phase-section <P> "<slice id>" --topic breakdown`), and copy each into its slice's `## Wave` set line. What you rely on: any two slices with no dependency path between them (neither depends on the other, even transitively) have **disjoint sets**. A set is a slice's files; the generated files its edits regenerate; any numbered sequence it extends (migrations, doc versions); any shared runtime resource it mutates or holds (a local database, a fixed port, the agent's Aside profile).

**The join-rebuilt artifact is the one exception.** A build output regenerated from many slices' sources (a bundled single file, a compiled asset) is not counted as overlap: `DECOMP` names it in `topics/breakdown.md`'s `## Join-rebuilt artifact`, with its sources and the command that rebuilds it. A wave executor never rebuilds it; you rebuild it once at the join (*At each return*), so two slices that edit different sources of it may run together.

If two ready slices' sets overlap anyway, that is a defect in `DECOMP`: start only the lower-ordered one, say so in `## Now`, and start the other when it is done.

## Planning and dispatching a wave

- **Every ready slice starts: there is no cap.** Plan each one, then dispatch them together.
  - `auto` (the default): plan each inline and `Write` its `plan.md`. A slice that spends money still plans at the gate (`reference/modes.md`), so its approval comes before the wave's dispatch.
  - `gate`: approve each plan in turn (`EnterPlanMode` → `ExitPlanMode`), copying each approved plan to its slice's `plan.md` at once, as `reference/modes.md` says; then dispatch them together.
  - `plan only` is unchanged: plans are readied one at a time and nothing runs. A `ready` (`[r]`) slice dispatches from its approved plan, with its `## Wave` section added first.
- **Each wave slice's `plan.md` carries a `## Wave` section, placed before `## Dispatch`:** its declared set, plus any path an answer added to it (*At each return* step 1); the slices running or starting beside it, with their sets; each `done` slice whose commit still waits (*At each return* step 4), with its set; the join-rebuilt artifact (the executor never rebuilds it) or `none`; and the checks scoped to its own set. That section is what puts the executor under the wave rules in `slice-executor.md`. Write it afresh at every dispatch, a re-dispatch after a stop or an escalation included. A slice dispatched while no other slice is running, starting or stopped and no commit waits gets none: it runs alone, and its commit takes all its pending changes (`reference/verdicts.md`). Nothing can join it, because a slice becomes ready only when a running one finishes. Any other dispatch gets one, a stopped slice's re-dispatch beside a held commit or another stop included.
- Then, for each slice: `executor-route <slice>` and pin its `## Dispatch`; `start-slice <slice>`; and dispatch all of them in **one message**, as background tasks, each prompt starting `slice: <id>`, with its own `model` and `effort`.
- **Rolling starts.** After each return, recompute (`next`) and start every newly ready slice while the others still run. A slice whose dependencies are done never waits for the rest of the wave; it starts as a wave slice, its `## Wave` naming what runs beside it. **A shared file waits for its commit:** a slice whose set overlaps the set of a `done` slice whose commit still waits (its `slice.json` uncommitted, *At each return* step 4; a directory or glob covers every path under it) starts only once that commit is in (at the join, after the drain), because that commit takes every dirty path of its set. `next` cannot see commits, so this check is yours; the join-rebuilt artifact is in no set and never counts. **A stopped slice's re-dispatch, after the operator's word, is not a start:** no held commit or other stop holds it, only a running set or waiting commit that overlaps its set (*The executor in a wave*). Unless it runs alone it carries `## Wave` (above), so it edits only its set and no other commit can take its edits.
- **While executors run you write only what this protocol gives you:** the state commands of wave slices (`start-slice`, `finish-slice`, `record-dispatch`, a stop's `set-slice-status`), the `plan.md` of a slice about to start, an answered set change (*At each return* step 1), and the notebook entries and commit of a slice that has returned. You never edit a running slice's files, bar that set line.

## The executor in a wave

When its `plan.md` carries `## Wave`, the executor (`slice-executor.md`):

- writes **no `phase.md`**: it returns its entries in a `notebook` field of its verdict (so its `result.md` verdict block holds them too), by section (Decisions, Notes for later slices, Doc impact, Operator Questions, Now). Each entry is gist-sized; long material goes in a new `topics/<slug>.md` of its own, behind a gist line linking it;
- runs **no engine command that writes**; `validate` and `phase-section` reads are fine;
- edits **only its declared set**. Any other file it needs, whether in a sibling's set, in a waiting commit's set or in no set at all, means the declaration was wrong, and a stronger row would hit the same wall, so on either row it returns `needs_operator` naming the file and the slice whose set or commit holds it, if any (a stop like any other, below). Once the operator has answered, re-dispatch it (the file added to its set, if that is the answer) as soon as no running slice's set and no waiting commit's set holds the file. No out-of-set edit is allowed: its commit takes its set from the tree (*At each return* step 4), so an edit outside it would land in another slice's commit or in none;
- regenerates only the generated files in its own set, and **never a join-rebuilt artifact**;
- runs only the checks scoped to its own set, and lists every whole-tree check it left out (a full suite, a whole-project typecheck or build, a check the repo's rules say must run alone) as `deferred: whole-tree` in its `validation`. The review runs those with every other slice's commands. A failure that traces to a file outside its set is a sibling's work in flight: it reports it and never fixes it.

## At each return

Handle returns one at a time, in the order they come in.

1. `record-dispatch`. On `done` from a slice with `## Wave`, first **check its edits against the sets**. Every product path its `files_changed` lists must be in its set. Every dirty product path in the tree (`git status --porcelain --untracked-files=all`, both sides of an `R` line; the workflow state and the join-rebuilt artifact aside) must be in the set of a slice in flight (its own, a running or stopped sibling's, or a waiting commit's) or named by a check stop already on disk, and an `R` line's two sides in the same one. A path that fails, a rename across its set's edge included, is an edit no commit can file: handle the return as a **check stop** naming every such path (*Stops and retries*), so nothing of the slice is finished or committed. **That stop is the hold, and it is on disk:** while it stands, the commit of any slice whose set holds a path it names waits for the answer, in this session or any later one (*Resume*). When the operator answers, apply the answer first: revert the path, or write it into the `## Wave` set line of the slice it joins (and out of the one it leaves), because a commit stages its set from that line in any session. Then clear the stop and go on from `finish-slice` in one command (`set-slice-status <id> in_progress && finish-slice <id> --outcome "…"`), so no boundary falls between them and the check never runs again on a stale `files_changed`: the work is done, so nothing is re-dispatched. A boundary before that command leaves the stop on disk, and the operator's repeated answer finds its first half already applied. Otherwise, `finish-slice <id> --outcome "<its summary>"`.
2. Write its `notebook` entries one entry at a time, through `phase-section` only (never `Read`, `Edit` or `Write` `phase.md`): Doc impact and Operator Questions are **appended** (`--append`); number each question `OQ<n>` yourself, in finish order, because the executor cannot see its siblings' numbers. Decisions and Notes are merged entry by entry: a new line is `--append`ed, a superseded one is swapped with `--entry K --replace` (`--list` gives K), and a note this slice consumed goes with `--entry K --remove`. Rewrite `## Now` **for the whole wave** (section `--replace`): what landed, what is running, what is next. **If `next` printed `notebook_over_budget=` with `notebook_move=` lines, run them here**, beside these writes and before the next start (`reference/verdicts.md`).
3. `validate`.
4. **The slice's commit, one per slice: its host paths first, then its workflow state**, at the time step 5 gives, attributed to its dispatch's model. **Its host paths are every dirty path of its declared set (its `## Wave` set line), read from the tree, not from `files_changed`:** `git status --porcelain --untracked-files=all -- <set>` lists them, modified, new, deleted, mode-changed and both sides of a rename, listed or not (step 1 stopped anything outside the set). Never the join-rebuilt artifact, even under a directory in the set (it rides only with the last, step 5). An empty set stages nothing: never run that command without a path, which lists the whole tree. A slice that ran alone (no `## Wave`) takes every dirty product path instead, as `reference/verdicts.md` does, because nothing else was in flight. The workflow state is its slice folder and its `topics/` file: in a single-repo install they ride in that same commit; in a nested pair they go to the nested repo right after it. A rolling commit, or the last of several that waited (held, or at the join), also carries `phase.md` and the generated state, which hold every entry so far. **Commit exactly those paths:** `git add --` only the new ones (`??`; a path `git rm` already removed makes `git add` fail), then `git commit -- <paths>`, which takes every other kind from the tree and leaves anything staged by another hand (an executor's `git mv` or `git rm`, a held commit's `git add`) out; never `git add -A`, never `--no-verify`. **So a `done` slice whose `slice.json` is still uncommitted is exactly a commit that waits:** `finish-slice` writes that file and only the slice's own commit takes it in. No other record is kept, and the start rules and *Resume* read this one.
5. **When it commits** depends on the join-rebuilt artifact:
   - **Rolling (the default).** When no running or finished-uncommitted slice touches the artifact's sources (or the phase has none), commit at once, alone. A hook failure or a busy index lock while siblings run **holds** that commit, every later commit and every new start until the running set drains; then commit the held ones in finish order. A worktree-wide hook can trip on a sibling's half-done edit, and a drained tree is the honest test; a commit that still fails there is fixed like any slice's failed commit, and nothing starts until it is in. When a stopped sibling's half-done edit is what trips the hook, that sibling's re-dispatch, which is no start (*Rolling starts*), is the fix.
   - **At the join.** When a running or finished-uncommitted slice touches the artifact's sources, **every commit waits until the running set drains.** Then rebuild the artifact once, and commit each slice in finish order, **the rebuilt artifact with the last host commit** (that slice's workflow state also carries `phase.md` and the generated state, step 4). The earlier commits carry their sources without the rebuilt artifact, an exception to a same-commit rebuild rule that holds for a wave's commits only (the `DECOMP` gate approved the artifact's naming); the pre-commit hook still passes, because it reads the worktree, which is rebuilt by then. A commit a check stop holds (step 1) keeps the artifact: the others commit without it, and once the answer is in you rebuild again and it rides with that commit, as with a stopped source (*Stops and retries*).
6. Recompute the ready set (`next`; `run-phases` in a run) and start what it lists, unless a stop is on disk or a held commit (*Rolling*) holds starts. A listed slice whose set overlaps a waiting commit's set starts once that commit is in (*Rolling starts*), and a barrier (`REVIEW` included) only once no commit waits.

## Stops and retries

- **Every stop goes to disk the moment it returns**, so the ready set empties and no compaction or later session can restart work:
  - `needs_operator` → `set-slice-status <id> pending --stop-kind decision|operator-action --on-words "<its operator_need>"`;
  - a check stop (*At each return* step 1) → `set-slice-status <id> pending --stop-kind decision --on-words "check stop on <path>, <path>: revert each, or add it to a slice's set"`, naming every path that failed;
  - `blocked` → `set-slice-status <id> blocked`;
  - a failed or empty high-row return → `set-slice-status <id> pending --stop-kind other --on-words "re-dispatch <id> on the high row"`.
- The running siblings then **finish and are committed** as above (bar a commit a check stop holds), nothing new starts, and the run STOPS with every stop reported. If the stopped slice touches the artifact's sources, its half-done edits are in the tree: rebuild anyway so the hook passes, commit the siblings, and leave the artifact uncommitted for that slice's re-run, saying so in the report.
- A mid `escalate` (or a failed or empty mid-row return) re-dispatches on the high row at once, even while the run is stopping: it is that slice's own second attempt, not a new start, and the limit stays one per slice (`reference/verdicts.md`).

## Resume

In a declared phase this runs first at every session start (a fresh `/do-whole-phase` or `/do-whole-phases`), after every compaction and before every start or commit, with one ready slice or a barrier next too (`SKILL.md` and `do-whole-phases` give the same trigger). Everything it needs is on disk, so it never depends on knowing that a compaction happened, and when nothing waits and nothing is in flight it does nothing.

1. **First, the commits that still wait.** The card shows no waiting commit, and once the running set drains it points at the barrier. So run `git status --porcelain --untracked-files=all` on the phase's `slices/` folder, in the repo that holds the workflow state (the nested repo in a nested pair), and read only its `slice.json` lines. **A `done` slice whose `slice.json` is uncommitted has a commit that waits** (*At each return* step 4), held, at the join, failed, or cut off by a compaction or a session's end, unless its committed `slice.json` already says `done` (a second `finish-slice` rewrote it after its commit). A slice whose `slice.json` is committed never waits, even while a later slice edits its files or its `result.md` is edited by hand. Then read the stops: each `pending` slice's `on_words`, in its `slice.json`. Nothing else is read: not `phase.md` or the generated state, no ownership, no clock. Take each waiting slice in finish order (`completed_at`) and finish *At each return* where it stopped: write the `notebook` entries `phase.md` still lacks (its `result.md` verdict block holds them), `validate`, then commit it by step 4 when step 5 says, **unless a check stop names a path in its set: that commit keeps waiting for the answer**, and at the join the artifact waits with it (step 5). Its set is its `## Wave` set line, answered changes included. Its set's dirty paths are its own, bar a path a check stop names (every dirty product path, for a slice that ran alone): while its commit waits no other slice may edit them (a wave slice edits only its set, *Rolling starts* keeps an overlapping set out, and a lone slice had nothing beside it). When none is dirty, its host commit is already in and only its workflow state is left. Step 6's holds stand until they are in: no barrier, no slice whose set overlaps a waiting one's, and nothing at all beside a waiting slice that ran alone. While a barrier runs alone this finds nothing, because a barrier starts only once no commit waits.
2. **Then each slice `in_progress`:** **wait for every running span and never re-dispatch one** (after a compaction, the contract's kept running executors and the card's running spans). A span never outlives the session that dispatched it, so at a fresh session's start none is running. A slice whose `result.md` verdict head says `done` has returned: finish it by *At each return*, step 1's check first (an answered check stop's slice is already `done`, step 1). Re-dispatch any other from disk (a dead span's, an answered stop's, an escalation's on the high row), which is no start (*Rolling starts*). Start `ready=` only while no stop is on disk, by step 6's holds.

## The idle window

While a wave runs, prepare only the **next frontier**: slices whose every open dependency is running now, never further ahead. The rest of `reference/prep.md` holds: read-only, never block, discard on any verdict other than `done`.

## Unchanged

`reference/dispatch.md`, the explain references, the `plan only` and spend gates, a design wave's spans inside one `co-work` slice, and `/do-next-slice`, bar its stop while a wave is unfinished. The phase stays the unit of *worktree* parallelism (`reference/worktree.md`).
