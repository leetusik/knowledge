# do-whole-phase — a decomposition slice and the acceptance gate

- When the slice is a decomposition (`kind: decomposition`), it runs the same path as any slice: you plan it — **at the gate by default** (the v40 carve-out above; only an explicit `auto` plans it inline) — then dispatch `slice-executor` on the high row, whose job is to create the phase's middle slices with `new-slice` (bare folders — never pre-filling their `plan.md`) and write the breakdown to `topics/breakdown.md`, its findings and notes into `phase.md` as gist lines. **The breakdown lives in `topics/breakdown.md`, never in `phase.md`:** the executor writes it whole, with `## Passes` (one line per pass), `## Estimate`, `## Join-rebuilt artifact` when the phase has one, `## Build inventory` in a design phase, and one `## <slice id>` block per slice (goal, set, risk and trigger, `spends money:`, depends on); each later pass (`DECOMP2`, `DECOMP3`) rewrites it in place, a done slice keeping a one-line block, and `## Decisions` keeps one `Breakdown (<pass>): …` gist line per pass linking it, earlier passes' lines kept. Set each slice's `--risk` deliberately — it selects the executor route (`low` → the mid row, `docs` and `qa` included; anything else → the high row), so it is the phase's main cost lever, and an unrated slice lands on the high row. **A DECOMP estimates time from the meter:** the phase's time comes from `python3 scripts/workflow.py dispatch-summary`'s `means` block — the metered minutes per span by route and span-minutes per slice by kind, the main thread included — applied to the slices it cuts; never a session-$ figure (the workspace's own dispatches are not spend) and never a recorded `tokens` figure (a span's final context, not its volume). **Each cut slice carries one line beside it in the breakdown: `spends money: no` or `spends money: yes, ~$X via <service>`** (vendor LLM or model API calls, paid third-party APIs, per-use billed cloud); a `yes` slice plans at the gate (the spend carve-out in `reference/modes.md`). **Slice size stays as is, with one rule:** a slice whose work is a bulk sweep (many screens, large API or sheet dumps) splits by surface, because an executor that compacts recovers from what is on disk, and a sweep's findings live only in its context until written. **Mid is the default (v46):** rate `implementation`, `fix`, `docs` and `qa` slices `low` — real code and more than one file included — and rate one `high` only for a named trigger, written beside it in the breakdown: **open design** (the plan cannot pin the approach: a new abstraction, an architecture choice, an algorithm to invent), a **core invariant** (logic the product cannot afford to break — persisted state or a schema migration, state transitions, auth, money, deletion, concurrency), an **unlocated root cause** (a bug whose cause is already known and located is `low`), or a **wide blast radius** (a shared interface whose callers are spread across the code). **When the phase cannot be cut past a point without learning something first, that is what the `research` kind is for:** the executor cuts a `research` slice (`--kind research --risk high` — findings-only, no product code, findings landed in `phase.md` as gist lines, long detail in a topic) plus a `<P>.DECOMP2` ordered after it, instead of guessing at the slices beyond; `DECOMP2` re-cuts the rest from what was learned. That is `DECOMP2`'s second origin, as ordinary as the design one — usually, not always: findings that change nothing about the remaining breakdown need no re-cut, and a third pass, if one is genuinely needed, is `DECOMP3`. **When the phase touches product visual design, its shape follows the operator-confirmed style** — `build-after`, `design-only` or `paired`, recorded in the phase's `intent.md` under `## Design Style` — the style, and on its second line whether the operator wants an in-product mockup in addition to the working canvas, `Mockup: requested` / `Mockup: on request` (read the `design-cowork` skill). In **every** style this `DECOMP` creates the design slice(s) (`--kind co-work --risk high` — each holds one job per surface, or a wave of about 3–4 jobs, and how many slices and jobs there are is decided here, foundations first) and records in `topics/breakdown.md`'s `## Build inventory` the **build inventory** — what to build, not how — and each slice's jobs with their critique level (`off | critic | critic+judge`, unset = off). The rest follows the style: **`build-after`** — the groundwork slices plus a second decomposition slice `<P>.DECOMP2` after the last design slice and **no build slices** (`DECOMP2` cuts them once the design has landed, backend first and the design implementation after); **`design-only`** — a single pass, `DECOMP` → design slice(s) → `REVIEW`, the apply phase being a separate phase created at `/create-phase`; **`paired`** — the design/apply pairs as **bare folders**, one apply slice per design slice and **no `DECOMP2`**. If `intent.md` carries no `## Design Style`, ask the operator here: suggest a style with a reason, ask the mockup question with it, set the slice `pending` (`--stop-kind decision --on-words "<their answer records the style and DECOMP cuts the slices>"`; the question follows the stop rules in the contract's `pending` rule), and stop — `design-only` cannot be chosen from inside `DECOMP` (its apply phase needs `new-phase`, which the executor may not run), so that answer goes back to the main thread and `/create-phase`. The loop will stop at each design slice's `pending` windows; that is expected, not a failure. **Declare the phase's operator acceptance gate at this boundary:** right after `finish-slice <P>.DECOMP`, in the same commit, run `python3 scripts/workflow.py accept-gate <P> --require` when the phase changes anything the operator can see, or `python3 scripts/workflow.py accept-gate <P> --waive --note "why nothing operator-visible changes"` when it does not — decided from `intent.md` and the decomposition. **A design phase's gate follows its mockup, with no judgment call left in it:** a phase that ships one (`Mockup: requested`, or asked for in the operator's words) takes `--require` — the operator opens a running route, an operator-visible surface by definition — and a `design-only` phase that ships none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`, the fixed note; `build-after` and `paired` phases take `--require` for their build/apply slices as always. A mockup requested after this declaration re-declares it: run `python3 scripts/workflow.py accept-gate <P> --require` in the mockup commit; and when `DECOMP` had to ask the design style, that answer must land **before** you declare the gate, because the declaration depends on it. Never by omission: `review-phase --verdict pass` refuses an undeclared phase and names both flags. Phases created before workspace v32 carry no `acceptance` block and need no declaration. **An explain phase** (`## Explain` in `intent.md`) declares by its unit, which `next` prints as `explain_unit=`: a **book** takes `--require` (the operator reads the book), and its first chapter slice then stops `pending` at the outline gate; a **document** takes `--waive --note "standalone explain document: published private; a v2 is cheap"` and a **chapter** `--waive --note "explain chapter: published private; a v2 is cheap"`. The rest: `reference/explain-decomposition.md`.

- **Declare the slices you cut: the declaration is what lets the loop run several at once (`reference/wave.md`).** Pass each non-barrier middle slice `--depends-on <id>` once per real dependency (repeatable; the id names a slice of this phase **ordered strictly before** it, so give each slice an `--order` after everything it depends on, or `new-slice` refuses), or `--depends-on none` when it needs nothing before it. A dependency is real whenever one slice reads another's output, a `phase.md` note, or the code it changes. **Never declare `DECOMP2`, `REVIEW` or a `co-work` slice:** they are barriers that run alone, and a declaration on them only draws a warning. **Every middle slice a decomposition leaves open is declared (v77):** `finish-slice <P>.DECOMP` refuses, writing nothing, while one is undeclared, and `python3 scripts/workflow.py set-slice-deps <slice> --depends-on …` declares one already cut; chaining a slice on the one before is always safe. A fix slice cut after a review and an explain phase's chapters stay undeclared and run alone.
  - **Relay the parallel proposal, then run as drawn.** The executor returns `parallel:` (the rounds `python3 scripts/workflow.py parallel-plan <P>` prints; `finish-slice` prints the same `parallel_plan=` and `parallel_rounds=` lines) and, for a chain, why and what would unlock parallelism. Put it in your next report in a line or two and run the phase as drawn: it adds no stop.
  - **Independence means disjoint sets.** Record each slice's **set** in its `## <slice id>` block of `topics/breakdown.md`: its files; the generated files its edits regenerate; any numbered sequence it extends (migrations, doc versions: two slices that run `doc-new-version` share `docs/index.json`); any shared runtime resource it mutates or holds (a local database, a fixed dev-server port, the agent's Chrome profile). Mark two slices independent only when no dependency path joins them and their sets are disjoint; when in doubt, chain them with `--depends-on`, which is always safe. A wave executor edits nothing outside its set (any other file stops it with `needs_operator`), and each slice's commit stages its set's dirty paths, so list every file a slice may touch: its tests and the changelog, the files it deletes, and both paths of a rename. A directory or glob covers every path under it.
  - **The join-rebuilt artifact.** A build output regenerated from many slices' sources (a bundled single file, a compiled asset, a lockfile the repo's rules rebuild with every change) is not counted as overlap: if the phase has one, name it in the breakdown's `## Join-rebuilt artifact` with its sources and the command that rebuilds it (the repo's `CLAUDE.md` says). Wave executors never rebuild it; the orchestrator rebuilds it once when the wave drains and commits it with the last of the wave's commits, so two slices that edit different sources of it may still be independent.
