# do-whole-phase — a decomposition slice and the acceptance gate

- When the slice is a decomposition (`kind: decomposition`), it runs the same path as any slice: you plan it — **at the gate by default** (the v40 carve-out above; only an explicit `auto` plans it inline) — then dispatch `slice-executor-high`, whose job is to create the phase's middle slices with `new-slice` (bare folders — never pre-filling their `plan.md`) and record the breakdown, findings, and notes in `phase.md`. Set each slice's `--risk` deliberately — it selects the executor tier (`low` → `slice-executor-mid`, else → `slice-executor-high`), so it is the phase's main cost lever, and an unrated slice lands on the top tier. **A DECOMP estimates from the meter:** the phase's cost and time come from `python3 scripts/workflow.py dispatch-summary`'s `means` block — the metered mean minutes and $ per span by route and per slice by kind, the main thread included — applied to the slices it cuts; never from a recorded `tokens` figure (a span's final context, not its volume). **Mid is the default (v46):** rate `implementation`, `fix`, `docs` and `qa` slices `low` — real code and more than one file included — and rate one `high` only for a named trigger, written beside it in the breakdown: **open design** (the plan cannot pin the approach: a new abstraction, an architecture choice, an algorithm to invent), a **core invariant** (logic the product cannot afford to break — persisted state or a schema migration, state transitions, auth, money, deletion, concurrency), an **unlocated root cause** (a bug whose cause is already known and located is `low`), or a **wide blast radius** (a shared interface whose callers are spread across the code). **When the phase cannot be cut past a point without learning something first, that is what the `research` kind is for:** the executor cuts a `research` slice (`--kind research --risk high` — findings-only, no product code, findings landed in `phase.md`) plus a `<P>.DECOMP2` ordered after it, instead of guessing at the slices beyond; `DECOMP2` re-cuts the rest from what was learned. That is `DECOMP2`'s second origin, as ordinary as the design one — usually, not always: findings that change nothing about the remaining breakdown need no re-cut, and a third pass, if one is genuinely needed, is `DECOMP3`. **When the phase touches product visual design, its shape follows the operator-confirmed style** — `build-after`, `design-only` or `paired`, recorded in the phase's `intent.md` under `## Design Style` — the style, and on its second line whether the operator wants an in-product mockup in addition to the working canvas, `Mockup: requested` / `Mockup: on request` (read the `design-cowork` skill). In **every** style this `DECOMP` creates the design slice(s) (`--kind co-work --risk high` — each holds one job per surface, or a wave of about 3–4 jobs, and how many slices and jobs there are is decided here, foundations first) and records in `phase.md` the **build inventory** — what to build, not how — and each slice's jobs with their critique level (`off | critic | critic+judge`, unset = off). The rest follows the style: **`build-after`** — the groundwork slices plus a second decomposition slice `<P>.DECOMP2` after the last design slice and **no build slices** (`DECOMP2` cuts them once the design has landed, backend first and the design implementation after); **`design-only`** — a single pass, `DECOMP` → design slice(s) → `REVIEW`, the apply phase being a separate phase created at `/create-phase`; **`paired`** — the design/apply pairs as **bare folders**, one apply slice per design slice and **no `DECOMP2`**. If `intent.md` carries no `## Design Style`, ask the operator here: suggest a style with a reason, ask the mockup question with it, set the slice `pending` (`--stop-kind decision --on-words "<their answer records the style and DECOMP cuts the slices>"`; the question follows the stop rules in the contract's `pending` rule), and stop — `design-only` cannot be chosen from inside `DECOMP` (its apply phase needs `new-phase`, which the executor may not run), so that answer goes back to the main thread and `/create-phase`. The loop will stop at each design slice's `pending` windows; that is expected, not a failure. **Declare the phase's operator acceptance gate at this boundary:** right after `finish-slice <P>.DECOMP`, in the same commit, run `python3 scripts/workflow.py accept-gate <P> --require` when the phase changes anything the operator can see, or `python3 scripts/workflow.py accept-gate <P> --waive --note "why nothing operator-visible changes"` when it does not — decided from `intent.md` and the decomposition. **A design phase's gate follows its mockup, with no judgment call left in it:** a phase that ships one (`Mockup: requested`, or asked for in the operator's words) takes `--require` — the operator opens a running route, an operator-visible surface by definition — and a `design-only` phase that ships none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`, the fixed note; `build-after` and `paired` phases take `--require` for their build/apply slices as always. A mockup requested after this declaration re-declares it: run `python3 scripts/workflow.py accept-gate <P> --require` in the mockup commit; and when `DECOMP` had to ask the design style, that answer must land **before** you declare the gate, because the declaration depends on it. Never by omission: `review-phase --verdict pass` refuses an undeclared phase and names both flags. Phases created before workspace v32 carry no `acceptance` block and need no declaration.
