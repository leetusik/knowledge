# do-whole-phase — the phase review, its verdict and the doc debt

- Durable-doc versioning happens **in a docs phase the operator creates**, not in this phase: no slice runs `doc-new-version` (the review's two named gate sections excepted) — when a slice changes durable truth it appends a one-line "Doc impact" note to `phase.md`, the review verifies that list, and the engine stamps `consolidation: pending` until a docs phase pays it (`docs-debt` for the worklist, `/create-phase`'s docs-phase route to start it, `docs-consolidated <P>` to record it). **In a phase worktree even the gate sections wait**: the branch review records them as `## Doc impact` notes tagged `(gate section — written at merge)`, and the post-merge step on the default stream writes exactly those (`parallel-merge-finish` → `doc-new-version` for the tagged notes → `rebuild-docs`); the rest of the list waits for the docs phase, which records `parallel-consolidated <P>`. Doc versions come from one shared index.
- When you reach the phase review slice, resolve it with `executor-route <P>.REVIEW` (the high row) like any slice and delegate it to `slice-executor-high`. Plan it so the executor validates all of the phase's slices together (each slice's validation commands plus `python3 scripts/workflow.py validate`), reviews against the objective / `intent.md` / docs, and — **on a passing review** — verifies that the phase's "Doc impact" list is complete, returning `doc_versions: none — deferred to a docs phase` (writing only its two named gate sections, never source). **In a phase worktree** (the phase carries an `execution` block with `mode: "parallel"`, because the operator asked for one) it writes no doc versions at all, records the two gate sections as `## Doc impact` notes tagged `(gate section — written at merge)`, and returns `doc_versions: none — deferred to post-merge consolidation (parallel mode)`. A **non-passing verdict stops the executor** before those pass-only steps and hands the phase back to you: it completes validation and judgment first (so you receive the whole picture in one cycle, not one finding per cycle), then returns the verdict with numbered findings and proposed fix slices rather than doing any pass-only work. The review does **not** produce a phase explainer — explaining is a separate operation the operator runs. **When the phase's gate is `required: true`**, plan the review to run the gate stages too: the executor opens the running product itself in the `## Operator Runtime` manifest runtime and spot-checks the phase's headline claims (never passing on other slices' reports alone), walks the surfaces the phase changed with fresh eyes as a first-time user, re-runs the `## Regression Checklist` lines inside the phase's boundary (`python3 scripts/workflow.py phase-scope <P>` — its own surfaces plus every earlier line a changed file feeds, never the whole list) and appends this phase's headline checks, and routes every `## Operator Questions` entry into the walkthrough or into a deferred job for you to file (a collapsed `(resolved → <ref>)` entry counts as routed) (see the `review-phase` skill). Put `phase-scope <P>`'s output (or the command) in the review's `plan.md`, and never plan the review to re-run the whole list — a plan that says "N lines, read it whole, re-run all of it" is exactly what the boundary rule retires; whatever the review notices outside the boundary comes back as deferred-job candidates for you to file, never as findings. It returns a `review_verdict`, the fixed `explain: not written — run /explain for this phase` pointer, and — on a gated phase — a **`walkthrough`**.
- **On `pass` with a required acceptance gate, the loop ends before the verdict is recorded.** Run `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough the executor returned>"` — the phase goes `pending` — file any deferred jobs the review listed, `validate`, commit, report the walkthrough to the operator (by the stop rules in the contract's `pending` rule), and STOP the loop, exactly as any `pending` item stops it. The operator walks the running product; accepting clears the gate (`python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` — theirs to run, or yours on their explicit say-so) and returns the phase to `in_progress`. On the resume run the `REVIEW` slice is still `in_progress` with its `result.md` carrying `review_verdict: pass` and the gate showing `cleared_at`: record the pass **without re-dispatching the review**. Operator-reported failures are recorded instead as `python3 scripts/workflow.py review-phase <P> --verdict changes_requested --note "operator-reported: ..."` (never refused; it resets the gate) and become `fix` slices the loop completes before re-reviewing. A waived phase, and a legacy phase with no `acceptance` block, record the verdict straight away as before.
- Record the verdict: `python3 scripts/workflow.py review-phase <P> --verdict pass|changes_requested|blocked --reviewer slice-executor-high --note "..."`, then `python3 scripts/workflow.py validate`.
- If the verdict is `changes_requested`, create the executor's proposed fix slices with `python3 scripts/workflow.py new-slice --phase <P> --slice <P.Fn> --name "..." --kind fix --risk <low|high>`, the rating the review proposed: `high` for a fix to a defect in mid-tier work — its `result.md` verdict block reads `tier: mid` — because work the mid tier got wrong never goes back to it, complete them (via the executor), then re-review.
- Only a `pass` verdict marks the phase `done` **and closes the `REVIEW` slice** — `review-phase` does both for you, so do **not** run a separate `finish-slice` for the review slice (the general "run `finish-slice` when a slice finishes" rule above does not apply to the review slice).
- A passing review leaves the phase `done` in `active/`; do **not** archive it here. Archiving is never this loop's job: it is `/rotate-backlog`'s, which pays the doc debt and archives after the docs phase it runs, or the operator's `archive-all` (once every active phase is done) or `archive-phase <P>` for one phase.
