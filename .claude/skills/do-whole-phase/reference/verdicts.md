# do-whole-phase — delegating a slice, its verdict and the commit

- Delegated slices (decomposition, `research`, implementation, `fix`, review — every kind except `co-work`, whose round lifecycle stays inline but whose **drafting span (`design-drafter`), critique spans (`design-critic`, when a job's critique level asks for them) and mockup span (`slice-executor` on the high row, when the operator asked for one) dispatch exactly like these**): dispatch the executor via the Agent tool **as a background task** (the default — never pass `run_in_background: false`) and wait for its completion notification, doing nothing else in the meantime **except the optional read-only preparation for slice N+1 — the next slice only — described in the next bullet** — never run it synchronously inline in the main session, never write to the repo or move workflow state while it runs, and one **executor** at a time for an undeclared or barrier slice: wait for it to return before dispatching the next (read-only research is not an executor and does not count against that limit). Declared, independent slices run together instead, and the state commands, notebook writes and commits of a wave are the ones `reference/wave.md` gives you. **A `co-work` slice's spans are the one carve-out:** inside the one `co-work` slice, its page drafters are dispatched at once, then its page critics (each as its page drafter returns), after its frame pass and before its join; the join, the cross-page critic, the judge and every answer pass run in turn (`design-cowork/reference/drafting.md`). The slice itself still runs alone (the design-wave carve-out of one drafter per job at once stays retired).

The route table (resolve, pin, dispatch, record, Explore) is in `reference/dispatch.md`.

The executor does the slice's job against `plan.md`; it writes `result.md` (verdict block first), edits the phase notebook under its budget, and returns a structured verdict. Then trust the verdict: read it and the **head** of `result.md` (its verdict block is that return's durable copy — read further only on a verdict other than `done`, or when you want the detail), and run `python3 scripts/workflow.py validate` (state integrity only — do **not** re-run the slice's tests; the phase review validates all slices together). On `needs_operator`, set the slice `pending`, report, and STOP; on `blocked`, record the blocker and STOP; on `escalate` — or a failed/empty return from a mid-row dispatch (an escalation with no findings) — append an `## Escalation: mid → high` section to the slice's `plan.md` with the executor's `escalation` findings, resolve with `executor-route <slice_id> --retry`, pin its lines under that section, re-dispatch the slice on the high row, and record the second attempt (present the revised plan for approval only in `gate` mode — in the default re-dispatch straight away; max 1 escalation per slice); on a failed or empty return from a high-row dispatch, treat the slice as not done and STOP. A `done` verdict proceeds.

**An over-budget notebook is moved before the next dispatch.** When `next`, `run-phases` (for the run's target phase) or the resume card prints `notebook_over_budget=<P> (<bytes> of 40960 B) -- required before the next dispatch: …`, run each `notebook_move=` line under it, prefixed `python3 scripts/workflow.py` (`phase-section <P> "<Section>" --to-topic <slug> --entry <ranges>`: the entries move verbatim to `topics/<slug>.md` and a gist line stays, so nothing is lost), then re-run `next` and carry the moved files in the next workflow-state commit. Do it on the main thread between dispatches, before the next `start-slice` (whose `warning: notebook <P> is over budget` line still starts the slice); in a wave, at a return, beside that return's notebook writes (`reference/wave.md`); never while a non-wave executor runs, since it writes the notebook itself. Past 3 moves the line says `(+N more moves …)`: re-run `next` for the rest. The **advisory** form (`-- advisory: nothing left to move (…)`, no `notebook_move=` line) asks only for the remedy it names, such as `--resolve` on answered questions. It never blocks a write, a stop or a finish. Executors never act on it.

- Commit at every clean slice boundary by default, following the Commit Convention (do not branch unless the operator asks; never push. A phase the operator asked into a worktree already has its branch — that branch *is* the worktree they asked for, so its slice commits land on `phase/P<N>-<slug>` without asking again; every other phase's land on the current branch. Pushing still needs asking: the `parallel-phase` integration merges locally by default, and its push → PR variant runs only when the operator asks, each push still passing the permission prompt). Commits are the orchestrator's job — the executor never commits (in a wave each slice's commit stages the dirty paths of its declared set, read from the tree, rolling or at the join: `reference/wave.md`; a slice that runs alone, lone or undeclared, commits all its pending changes). In a nested pair commit the host paths first and the workflow state right after, so a `done` slice whose `slice.json` is still uncommitted always marks a commit that waits (`reference/wave.md`, *At each return* step 4). **Attribute the slice commit to the model that did the work:** its trailer is `Co-Authored-By: <attribution> <noreply@anthropic.com>`, `<attribution>` being the `attribution=` line of the dispatch that produced the work — equivalently the name for the `model:` its verdict block records; a slice done in two attempts goes to the model that completed it. Commits carrying only your own work (phase creation, a gate declaration alone, a verdict record) are attributed to the session's model as before; never carry over another session's trailer.
