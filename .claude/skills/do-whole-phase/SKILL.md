# do-whole-phase

Read `CLAUDE.md` and the phase's `phase.md` — the **bounded phase notebook** (`## Slices` generated from `slice.json`, `## Decisions`, `## Doc impact`, `## Operator Questions`, `## Notes for later slices`, `## Now`) — run `python3 scripts/workflow.py next` for the pointer, then finish every remaining slice in the current phase only. Read `docs/current/` **sections** just in time, as the slices reach them, never the whole doc set up front. If you are ever unsure of the operator's intent, consult `intent.md` — the confirmed record of what was asked. `next` reports **the current stream's** active phase: on the default stream it skips phases running in their own worktrees (printing `parallel_phases_elsewhere=<P>:<branch>`), and inside a phase worktree it sees only that phase (printing a `stream=` line); `python3 scripts/workflow.py parallel-status` shows every stream. **The phase runs on this checkout unless the operator asked for a worktree (v43).** By default do nothing about worktrees — run the whole loop here, on the current branch. Move only on the operator's word: when they asked in this invocation (`worktree`, `in a worktree`, `in parallel`, `on its own branch`) and the phase is still `planned`, run `python3 scripts/workflow.py parallel-start <P>` (the stamp commit holds only the phase folder plus the regenerated `works/` files, a dirty tree is allowed, and your other uncommitted edits stay behind here), call `EnterWorktree` with the printed `worktree=` path, re-run `next` there (`stream=phase/P<N>-<slug>`), and run the whole loop in that worktree in this same session — background executors dispatched from there run in the worktree. **In a nested install** the same word runs `parallel-start <P> --host-branch <name>` after you propose the name from the host's recorded custom (`nested-convention`) and the operator confirms it, and `EnterWorktree` goes to the printed **host** worktree path. Do the same when they ran `parallel-start <P>` themselves and the phase already carries a `mode: "parallel"` execution block. Never run `parallel-start` on your own initiative — a `hint:` about a phase queued behind a live one is a suggestion to relay, not an instruction — and never ask for a worktree on a docs phase, since `doc-new-version` runs only on the default stream (see the `parallel-phase` skill).

You are the ORCHESTRATOR (main thread): you plan each slice, verify, commit, move workflow state, and talk to the operator. Every slice — decomposition, `research`, implementation, `fix`, and the phase **review** — is delegated to a `slice-executor` tier subagent (`slice-executor-mid` or `slice-executor-high`), one at a time and sequentially. **One exception: a `co-work` (design) slice runs inline, with dispatched spans (inline → dispatched → inline).** The round's lifecycle and the operator's words stay inline — `design-open`, the handoffs, the read-back, every publish to a job's canvas, `feedback.md`, `SIGNOFF.md`, `design-close` and every commit stay on the main thread — but the **drafting is dispatched to `design-drafter`** (the design subagent, not a slice executor) every round, the **critique to `design-critic`** when a job's critique level asks for it, and the **mockup build is the one span dispatched to a slice executor** (`slice-executor-high`, built from the round's `build-prompt.md` and its record on disk), only when the operator asked for a mockup. See the `design-cowork` skill; the slice ends the run at a `pending` stop. Same contract as `do-next-slice`, looped over the phase.

Rules:

- If a slice or the phase is `pending` (shown `[~]`; `next` prints `WAITING ON OPERATOR`), STOP the loop: it needs operator co-work (validation or an operator-run action). Report what you need and do not start, finish, or advance past it. Resume only after the operator clears `pending` back to `in_progress`. When the phase is pending because its **operator acceptance gate** is open (`next` also prints `acceptance_gate=open` and the walkthrough), relay that walkthrough as-is: it clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]`, not with `set-phase-status`. If you hit such a point mid-slice, set it `pending` with `set-slice-status <slice_id> pending` and STOP. **A `co-work` design slice stops `pending` once per wave — twice when a mockup was requested, and once more for each superseding round — and the engine cannot tell its windows apart** — every stop is `status: pending` on the same slice and prints the same line — so the difference lives entirely in what you report; say which one this is, and what the operator's words on return will do (the `co-work` rule below). (In a phase worktree a `pending` item halts only its own stream.)
- After each slice, re-read the phase's `phase.md` and the executor's returned verdict — that pair is the handoff, and the notebook was **rewritten**, not appended to, so the previous read is stale. Drop the per-slice re-read of `works/backlog.md` (and `works/state.json`): `next` prints the pointer, and the dashboards are generated from the same state.
- **After a context compaction** (the `SessionStart` hook has printed `compaction=done source=compact`, the pointer and a resume line): re-read this `SKILL.md` from disk — only its first 5,000 tokens were re-injected — then the active slice folder (`plan.md`, `result.md`) and `phase.md`'s `## Now`. An executor dispatched before the compaction is still running and the harness lists it: wait for its completion notification, never re-dispatch. The mode word (`auto`, `gate`, `plan only`) and any open operator gate are among the summary's kept facts; when in doubt, `intent.md` and `next` are the record.
- Delegated slices (decomposition, `research`, implementation, `fix`, review — every kind except `co-work`, whose round lifecycle stays inline but whose **drafting span (`design-drafter`), critique spans (`design-critic`, when a job's critique level asks for them) and mockup span (`slice-executor-high`, when the operator asked for one) dispatch exactly like these**): dispatch the executor via the Agent tool **as a background task** (the default — never pass `run_in_background: false`) and wait for its completion notification, doing nothing else in the meantime **except the optional read-only preparation for slice N+1 — the next slice only — described in the next bullet** — never run it synchronously inline in the main session, never write to the repo or move workflow state while it runs, and one **executor** at a time: wait for it to return before dispatching the next (read-only research is not an executor and does not count against that limit). **The one carve-out from one executor at a time is a design wave's spans:** one drafter per job at once, and a judge beside its job's next drafter pass — disjoint job folders, design spans only, all inside the one `co-work` slice. **Dispatch through the engine's route table — the decision is the engine's, never yours:** kind first (decomposition, `research` and review always route to the high row, by **kind**, whatever their `risk` says; a `co-work` mockup span too), then `risk` (exactly `low` → the mid row, `slice-executor-mid`, the default tier — real code and multi-file work included, as long as `plan.md` pins the approach — and `docs` / `qa` rated `low` → the cheap row on that same file; anything else → the high row, `slice-executor-high`), then attempt (every second attempt → high). (1) **Resolve:** once `plan.md` is written (and after `start-slice`), run `python3 scripts/workflow.py executor-route <slice_id>` — add `--retry` on a second attempt — and `python3 scripts/workflow.py executor-route --explore`. **Bump up, never down:** when the plan you write hits a named trigger (open design, a core invariant, an unlocated root cause, a wide blast radius) on a slice rated `low`, set `risk` to `high` in its `slice.json` (that one field; `python3 scripts/workflow.py rebuild` regenerates the table), say why in `plan.md`, and resolve again; never lower a rating. (2) **Pin:** append a final `## Dispatch` section to the slice's `plan.md` holding the slice form's lines verbatim (`route=` … `attribution=`) plus the `--explore` form's `model=` / `effort=` renamed `explore_model=` / `explore_effort=` — the executor copies its `model` / `effort` into its verdict block from there and takes its `Explore` lookup model from it; on a retry the new lines go under the `## Escalation: mid → high` section instead. (3) **Dispatch:** the Agent tool, as a background task, `subagent_type` = the `subagent_type=` line; pass `model` (the `model=` line, an Agent-tool alias) only when `pass_model=yes`, and `effort` (the `effort=` line) only when `pass_effort=yes`. A `fallback=` line is informational (`model=` already carries the fallen-back model); relay every `warning=` line to the operator in your report — it means the per-dispatch value will not take effect on this machine. The prompt stays the slice id, its folder and the repo root. (4) **Record:** after the completion notification — before `finish-slice`, so the record rides in the slice's commit — run `python3 scripts/workflow.py record-dispatch <slice_id> --route <route=> --tier <tier=> --model <model=> --effort "<effort=>" --verdict <done|escalate|needs_operator|blocked|failed> --attempt <attempt=> --agent <subagent_type=> --duration-ms <duration_ms> --tokens <subagent_tokens> --tool-uses <tool_uses>`: the flags copied from the pinned lines, never recomputed, and the three numbers from the notification's `<usage>` block; a failed or empty return is `--verdict failed`. Every return is recorded, whatever its verdict: each design span with its own `executor-route --drafter`, `--critic` or `--judge` lines (`--route design|critic|judge --tier -`, `--agent` its `subagent_type=` line), the mockup span like any slice. (5) **Explore for lookups:** your planning research uses the project `Explore` agent (`subagent_type: Explore`) at the `--explore` form's `model` / `effort` (haiku @ high; `sonnet` under a loopback proxy), upgraded per call — `model: sonnet` or `model: opus` — for a lookup that needs judgment (why, a trade-off, an audit); it locates and summarizes, never decides, and its brief is advisory input to your plan, never a plan (`Plan`-type agents and inline reads stay available). `/executor-route` shows the resolved table and `python3 scripts/workflow.py dispatch-summary` the recorded runs; `executors.toml`'s per-row `[claude.<row>]` overrides are the operator's knob — there are no presets. The executor does the slice's job against `plan.md`; it writes `result.md` (verdict block first), edits the phase notebook under its budget, and returns a structured verdict. Then trust the verdict: read it and the **head** of `result.md` (its verdict block is that return's durable copy — read further only on a verdict other than `done`, or when you want the detail), and run `python3 scripts/workflow.py validate` (state integrity only — do **not** re-run the slice's tests; the phase review validates all slices together). On `needs_operator`, set the slice `pending`, report, and STOP; on `blocked`, record the blocker and STOP; on `escalate` — or a failed/empty return from `slice-executor-mid` (an escalation with no findings) — append an `## Escalation: mid → high` section to the slice's `plan.md` with the executor's `escalation` findings, resolve with `executor-route <slice_id> --retry`, pin its lines under that section, re-dispatch the slice to `slice-executor-high`, and record the second attempt (present the revised plan for approval only in `gate` mode — in the default re-dispatch straight away; max 1 escalation per slice); on a failed or empty return from `slice-executor-high`, treat the slice as not done and STOP. A `done` verdict proceeds.
- When a slice finishes (its `result.md` written and the notebook edited by the executor), run `finish-slice <slice_id> --outcome "<one line>"` — the outcome comes from the executor's verdict `summary` and fills that slice's row in the notebook's generated `## Slices` table; omitting it warns, never errors — then `python3 scripts/workflow.py validate`.
- Commit at every clean slice boundary by default, following the Commit Convention (do not branch unless the operator asks; never push. A phase the operator asked into a worktree already has its branch — that branch *is* the worktree they asked for, so its slice commits land on `phase/P<N>-<slug>` without asking again; every other phase's land on the current branch. Pushing still needs asking: the `parallel-phase` integration merges locally by default, and its push → PR variant runs only when the operator asks, each push still passing the permission prompt). Commits are the orchestrator's job — the executor never commits. **Attribute the slice commit to the model that did the work:** its trailer is `Co-Authored-By: <attribution> <noreply@anthropic.com>`, `<attribution>` being the `attribution=` line of the dispatch that produced the work — equivalently the name for the `model:` its verdict block records; a slice done in two attempts goes to the model that completed it. Commits carrying only your own work (phase creation, a gate declaration alone, a verdict record) are attributed to the session's model as before; never carry over another session's trailer.
- **Default is `auto` — plan inline → executor, straight through, no approval pause.** With no mode word, do **not** enter plan mode (no `EnterPlanMode` / `ExitPlanMode`): for each slice, plan inline → **`Write` `plan.md` verbatim and in full** (no harness plan file exists to copy, since plan mode is never entered — the default persistence path is `Write`, not `cp`) → dispatch the executor → validate (state integrity) → finish → commit → next, to the end of the phase. Free-form, no template; pull context from `phase.md`, let the plan incorporate any operator note, and never pre-fill another slice's `plan.md` (the operator's verbatim intent lives in the phase's `intent.md`, not duplicated per slice). The default waives only the plan-approval pause — the safety halts still apply: a `pending` slice/phase, any `needs_operator` / `blocked` return, or a failed/empty `slice-executor-high` return, STOPS the loop. An `escalate` (or a failed/empty return from `slice-executor-mid`) does not stop the loop: revise the plan and re-dispatch the slice to `slice-executor-high` without a pause. For a slice already `ready` (`[r]`), skip the inline planning too — its operator-approved `plan.md` already exists; dispatch from it directly. **One carve-out (v40): decomposition slices (`kind: decomposition` — `DECOMP`, `DECOMP2`, `DECOMP3`, …) are gated by default.** When the bare-default loop reaches one, plan that slice exactly as `gate` mode does below — `EnterPlanMode` → read-only research → `ExitPlanMode` for the operator's approval → copy the harness plan file to the slice's `plan.md` (same confirm-then-copy rule) — then dispatch and return to the straight-through loop for the slices after it. The decomposition fixes the shape, risk ratings, and cost of everything downstream, so its plan pauses for operator eyes even in an otherwise unattended run. **A second carve-out (v59): a slice that spends money (vendor LLM or model API calls, paid third-party APIs, per-use billed cloud resources; the workspace's own executor dispatches do not count) is gated by default too.** When the loop's planning shows a slice will spend money, plan it through the same gate, naming in the plan what it calls and a rough volume or cost estimate, so the operator approves the spend with the plan; then return to the straight-through loop. An **explicit** `auto` (or "run unattended") is the opt-out and runs the whole phase, decompositions and spending slices included, without the pause.
- **`gate` (operator opt-in) restores manual-approval mode — plan → operator approves the readied plan → executor, repeated.** Use it only when the operator invokes the skill with `gate` (e.g. `/do-whole-phase gate`); then the operator must approve each slice's readied plan before its executor runs. The orchestrator advances on its own only *between* slices: after each slice it **automatically enters plan mode to plan the next** — it never stops to ask permission to start planning. For each slice: in Claude Code, **call the `EnterPlanMode` tool** to enter plan mode, do read-only research (surface any clarifying questions), then **call `ExitPlanMode` to present the readied plan** for the operator's approval. The only pause is approving the finished plan — never a pause before planning begins. After approval (the harness exits plan mode), persist the plan by **copying the harness plan file** — the exact path the harness named for this planning session; never glob `~/.claude/plans/` and never pick by modification time — to that slice's **own** `plan.md`, after **confirming its opening lines match the plan just approved** (the harness reuses one plan file per session, so a skipped step can leave an earlier slice's plan sitting there); copy **immediately after approval, before the next `EnterPlanMode`**, which overwrites the file. Free-form, no template; pull context from `phase.md`, let the plan incorporate any operator note, and append any slice-local addition (an `## Escalation` section, for example) **after** the copy, never a rewrite of the copied body; then dispatch the executor; then re-read state and head straight into planning the next slice (`EnterPlanMode` again). Never pre-fill another slice's `plan.md`. The operator's verbatim intent lives in the phase's `intent.md`, not duplicated per slice. When the loop reaches a slice already `ready` (`[r]`) — its `plan.md` was operator-approved in an earlier `plan only` pass — skip plan mode for it: re-read its `plan.md` and `phase.md` and dispatch the executor directly, re-planning through the gate only if the workspace state has visibly drifted from the plan.
- **`plan only` (operator opt-in) readies every plan without executing.** If the operator invokes the skill with `plan only` (e.g. `/do-whole-phase plan only`), ready the phase's plans instead of finishing the phase. If the `DECOMP` slice is not `done`, run it first exactly as `gate` mode does (plan at the gate → operator approves → dispatch `slice-executor-high` → verdict → `finish-slice` → `validate` → commit) — the middle slices must exist before they can be planned. Then for each remaining middle slice in `order` (skip `done` and already-`ready` slices): plan it at the gate as in `gate` mode (`EnterPlanMode` → read-only research → `ExitPlanMode` for approval), after approval persist the plan by **copying the harness plan file** to that slice's own `plan.md` — the same confirm-then-copy rule as `gate` mode above — mark it `python3 scripts/workflow.py set-slice-status <slice_id> ready` (shown `[r]` — plan approved, awaiting execution), commit, and head straight into planning the next. No executor dispatch and no `start-slice`/`finish-slice` for these slices. **Stop before anything whose plan depends on something that has not landed yet.** That is one rule with four faces: the `REVIEW` slice (its plan depends on the implementation results), a `P<N>.DECOMP2` following a **research** slice (its plan depends on findings nobody has produced yet), a `P<N>.DECOMP2` following the design round(s) under `build-after` (its plan depends on the landed design), and — under the **`paired`** style, which has no `DECOMP2` — each **apply slice**, whose bare folder already exists but whose `plan.md` is written at its turn from the round that just came back. So `plan only` readies a research slice but stops before its `DECOMP2`, and in a design-bearing phase readies the slices up to and including the **first** design slice whose round has not landed, and stops there; when only such slices remain unreadied, run `python3 scripts/workflow.py validate`, report which slices were readied, and STOP. `plan only` is **always gated** — it exists to produce operator-approved plans, so it runs the approval gate even though the default mode is `auto`; if `auto` also appears, ignore it and keep the gate. The safety halts (`pending`, `blocked`) still stop the loop.
- **`kind: co-work` (a design slice) runs inline, with dispatched drafting spans every round, critique spans when a job's level asks for them, and a dispatched mockup span only when the operator asked for one — and stops the loop once per wave, twice with a mockup.** The round's lifecycle and the operator's words stay inline (no executor runs them); the **drafting is dispatched to `design-drafter`**, the **critique to `design-critic`**, and the **mockup build is the one span dispatched to a slice executor** (`slice-executor-high`, like any code slice), when one was requested. Per the `design-cowork` skill, and with `python3 scripts/workflow.py set-slice-status <slice_id> pending` at each stop. Steps 1–4 are the loop. A phase whose `intent.md` still says `Design tool: claude-design` is a legacy one: at its first design slice set the slice `pending` and ask the operator to re-confirm it on `drafter`, per `design-cowork`'s legacy rule.
  1. **Inline** — for each job of the slice's wave (one, or about 3–4, as `DECOMP` recorded them): `python3 scripts/workflow.py design-open --slug <slug> --slice <slice_id> --critique <level>` (`--new-job` for each further job; `design-init` first on a product's first job), the job's canvas on its first round, the preview prep, then `handoff.md`: the screens × states with a check each, the data, the system inventory, the constraints, the collected taste, the `## The operator's bar` section (the operator's own standing rules from `bar.md`, or none beyond the shipped bar), a `new visual direction: yes` or `no` line (the operator's call: the licence for a new look, built as one direction), the `critique:` line and the three paths.
  2. **Dispatched — one `design-drafter` per job, at once** (the one carve-out from one executor at a time), as background tasks (never pass `run_in_background: false`); each prompt is the round **address** `<job>/<round>` and the slice id, its `model` / `effort` the `executor-route --drafter` lines, and every return recorded. Then, per job whose critique is `critic` or `critic+judge`, one critic pass on the `--critic` lines and, with any must-fix open, one drafter answer pass; under `critic+judge` the judge (`--judge`) rules once beside that answer pass on the items the critic escalated, and its upheld items get one more short drafter pass. There is no second critic pass. A drafter's `needs_operator` or `blocked` holds only its job; the stop reports it.
  3. **Inline read-back and publish** — per job, run `design-check <job>` yourself, never resting on the drafter's own line; read `result.md` and `build-prompt.md`; then the concreteness check. **A failure the drafter can fix goes back to it once, on the same open round; otherwise report exactly those points at the stop, nothing signed.** Publish each job (`design-publish-plan <job>` → the `Artifact` publish → `design-canvas <job> --version <id>`), commit the drafted wave and STOP the loop at **PENDING #1**, once for the whole wave.
  4. **The operator's words, inline** — read their in-app edits and the comments they sent to Claude back into `feedback.md` verbatim, then their words decide each job:
     - **Literal approval, no mockup requested:** write `SIGNOFF.md` with their literal words and run `design-close <job>/<round> --words "<their literal words>"`.
     - **Anything else is feedback:** write their words verbatim into `feedback.md`, run `design-close <job>/<round> --superseded`, then `design-open --slug <s> --slice <slice_id> --job <job> --critique <level>` — the new round edits the job's canvas in place — and **write its handoff**: what the feedback asks for, pointing at the superseded round's `feedback.md`, the boards the operator edited locked as edited, and its `new visual direction` line. Re-draft (step 2), read back and republish as in step 3 (a new canvas version), commit (the superseded round's `feedback.md` and close ride in the same commit), and STOP at PENDING #1 again — **one more commit and one more stop per superseding wave**.
     - **Mockup requested** (`Mockup: requested` in `intent.md`, or the operator asked in their own words before the round closed): their go-ahead at PENDING #1 dispatches the mockup build to `slice-executor-high` (built from `build-prompt.md` and the job's record on disk, stubbed data, verified in the `## Operator Runtime`); handle its verdict exactly as any delegated slice below — `needs_operator` also covers a record too thin, wrong or inconsistent to build from, and you raise it rather than filling the gap — then commit and STOP the loop at **PENDING #2**, the mockup gate. **PENDING #2 exists only when a mockup was requested.** On the operator's **literal** approval of the running mockup, write `SIGNOFF.md` and run `design-close <job>/<round> --words "<their literal words>"`.

     When every job is signed, or dropped by the operator, `finish-slice`, commit, and continue the loop: **a wave signed at the first return is two commits and one stop; with a mockup, three commits and two loop stops**.

  **Report each `pending` window for what it is:** at PENDING #1 give, per job, the canvas link, the scorecard when critique was on (open items, the bar line by line, Holds, Not seen), the taste notes, open wave choices, what the answer pass left open (rebuttals, with both sides), unsure items under `critic` and low-confidence items when the judge was skipped, the drafter's departures and `open_questions` as decisions to take, and what their words will do — literal approval signs that job (no mockup) or starts its mockup build (mockup requested), anything else is feedback and a superseding round re-drafts it; at PENDING #2 say that you are **asking for approval** — the run command, the mockup route's URL, the viewports, what is real and what is stubbed, and that only their literal words close the round.
- **While executor N runs you are idle on the main thread — you *may* use that window to prepare for slice N+1 — **and only N+1**, never N+2 or any slice after it (`do-whole-phase` only; `do-next-slice` never prefetches).** Once N is dispatched as a background task you are simply waiting, and the wait is yours to spend on whatever will make plan N+1 better: dispatch a read-only research subagent (the project **`Explore`** agent is the natural fit, at the `executor-route --explore` model / effort, upgraded per call to `model: sonnet` or `model: opus` for a lookup that needs judgment), read files inline yourself, think the slice through, or just wait. None of it is required and no mechanism is prescribed — choose per slice, and prefer waiting when there is nothing useful to learn yet. The goal is efficient, high-quality work, not a procedure to follow.
  - **Limits on whatever you choose** (they constrain the *how*, never the *whether*): **one slice ahead, never two** — prepare slice N+1 alone, never N+2 or any later slice, even when a later slice looks independent of N and N+1: plan N+1 reconciles against what N actually changed, and N+2's plan must in turn reconcile against what N+1 changes, which has not happened yet — preparing two ahead compounds that staleness and spends the window on work the next return can void; stay strictly **read-only** — no repo writes, no `workflow.py` state commands, no commits, and never any part of slice N+1's actual work; dispatch **no second executor** (read-only research is not an executor and does not count against the one-at-a-time rule); **never block** — executor N's completion notification always wins, so anything not ready by then is dropped rather than waited for, `finish-slice` / `validate` / the commit are never delayed for it, and nothing is carried on into the slice after next; **discard** whatever you gathered on any verdict other than `done` (`escalate`, `blocked`, `needs_operator`, a failed or empty return) — the world it assumed did not happen, so plan (or re-plan for `slice-executor-high`) from the current tree; keep notes in the **session scratchpad**, never in a slice folder (a slice owns exactly two context files, and a stale draft must never be readable as an approved plan). What you gather is advisory input to *your* plan, never an approved plan: in `gate` mode **the operator's approval gate does not move** — they still approve plan N+1 after seeing slice N's `result.md`, verdict, and updated `phase.md`.
  - **Judgment, not a checklist.** Preparing ahead tends to pay off when slice N+1's subject is separate from what N is touching, when it is decision-dense and you want your own view before the gate, or when it lands in a large area you do not know well. It usually does not when the current slice is `DECOMP` (the middle slices do not exist yet) or `research` (its findings are what decides the work after it), when the current slice is `co-work` (its drafter, critic and judge spans and a requested mockup span are dispatched windows, but they run between inline steps you must take as each returns, with the loop stopping at PENDING #1 or #2 right after them — so there is rarely a next slice worth preparing), when the next slice is `REVIEW` (never pre-planned), `P<N>.DECOMP2` or a `paired` apply slice (never pre-planned — their plans come from what has not landed yet: a research slice's findings, or the landed design) or already `ready` (`[r]` — an operator-approved `plan.md` exists), when the phase or any slice is `pending` (the loop stops there anyway), or when the next slice's files sit inside what N is rewriting (anything read there may be stale by the time N returns). Weigh these; do not tick them off.
  - **If you delegate, keep the ask small.** The agent cannot see your session, so hand it everything by path — slice N+1's id and folder, the phase folder (`phase.md`, `intent.md`), and the paths N is mutating right now as explicit exclusions. Ask a few sharp questions rather than "research this slice", and ask for a **compact advisory brief**: relevant files with one line each on why they matter, patterns and utilities to reuse, constraints and risks, open questions, and an explicit "not read / possibly stale" list. Never a plan, never a file dump. A shallow brief that arrives in time beats an exhaustive one that does not.
  - **After N returns**, `finish-slice` / `validate` / commit are unchanged; then plan N+1, **reconciling** whatever you gathered against what N actually changed (its `files_changed`, the verdict block at the head of its `result.md`, and the rewritten `phase.md`) instead of re-reading everything. Do a full research pass when you prepared nothing, dropped what you had, or the state visibly drifted from what it assumed.
  - **Modes:** this applies in the default (`auto`) loop **and** in `gate` (in the default the reconciliation feeds the inline plan; in `gate` it feeds the plan-mode pass). `plan only` runs no executor, so there is no idle window to use.
- When the slice is a decomposition (`kind: decomposition`), it runs the same path as any slice: you plan it — **at the gate by default** (the v40 carve-out above; only an explicit `auto` plans it inline) — then dispatch `slice-executor-high`, whose job is to create the phase's middle slices with `new-slice` (bare folders — never pre-filling their `plan.md`) and record the breakdown, findings, and notes in `phase.md`. Set each slice's `--risk` deliberately — it selects the executor tier (`low` → `slice-executor-mid`, else → `slice-executor-high`), so it is the phase's main cost lever, and an unrated slice lands on the top tier. **Mid is the default (v46):** rate `implementation`, `fix`, `docs` and `qa` slices `low` — real code and more than one file included — and rate one `high` only for a named trigger, written beside it in the breakdown: **open design** (the plan cannot pin the approach: a new abstraction, an architecture choice, an algorithm to invent), a **core invariant** (logic the product cannot afford to break — persisted state or a schema migration, state transitions, auth, money, deletion, concurrency), an **unlocated root cause** (a bug whose cause is already known and located is `low`), or a **wide blast radius** (a shared interface whose callers are spread across the code). **When the phase cannot be cut past a point without learning something first, that is what the `research` kind is for:** the executor cuts a `research` slice (`--kind research --risk high` — findings-only, no product code, findings landed in `phase.md`) plus a `<P>.DECOMP2` ordered after it, instead of guessing at the slices beyond; `DECOMP2` re-cuts the rest from what was learned. That is `DECOMP2`'s second origin, as ordinary as the design one — usually, not always: findings that change nothing about the remaining breakdown need no re-cut, and a third pass, if one is genuinely needed, is `DECOMP3`. **When the phase touches product visual design, its shape follows the operator-confirmed style** — `build-after`, `design-only` or `paired`, recorded in the phase's `intent.md` under `## Design Style` — the style, and on its second line whether the operator wants an in-product mockup in addition to the working canvas, `Mockup: requested` / `Mockup: on request` (read the `design-cowork` skill). In **every** style this `DECOMP` creates the design slice(s) (`--kind co-work --risk high` — each holds one job per surface, or a wave of about 3–4 jobs, and how many slices and jobs there are is decided here, foundations first) and records in `phase.md` the **build inventory** — what to build, not how — and each slice's jobs with their critique level (`off | critic | critic+judge`, unset = off). The rest follows the style: **`build-after`** — the groundwork slices plus a second decomposition slice `<P>.DECOMP2` after the last design slice and **no build slices** (`DECOMP2` cuts them once the design has landed, backend first and the design implementation after); **`design-only`** — a single pass, `DECOMP` → design slice(s) → `REVIEW`, the apply phase being a separate phase created at `/create-phase`; **`paired`** — the design/apply pairs as **bare folders**, one apply slice per design slice and **no `DECOMP2`**. If `intent.md` carries no `## Design Style`, ask the operator here: suggest a style with a reason, ask the mockup question with it, set the slice `pending`, and stop — `design-only` cannot be chosen from inside `DECOMP` (its apply phase needs `new-phase`, which the executor may not run), so that answer goes back to the main thread and `/create-phase`. The loop will stop at each design slice's `pending` windows; that is expected, not a failure. **Declare the phase's operator acceptance gate at this boundary:** right after `finish-slice <P>.DECOMP`, in the same commit, run `python3 scripts/workflow.py accept-gate <P> --require` when the phase changes anything the operator can see, or `python3 scripts/workflow.py accept-gate <P> --waive --note "why nothing operator-visible changes"` when it does not — decided from `intent.md` and the decomposition. **A design phase's gate follows its mockup, with no judgment call left in it:** a phase that ships one (`Mockup: requested`, or asked for in the operator's words) takes `--require` — the operator opens a running route, an operator-visible surface by definition — and a `design-only` phase that ships none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`, the fixed note; `build-after` and `paired` phases take `--require` for their build/apply slices as always. A mockup requested after this declaration re-declares it: run `python3 scripts/workflow.py accept-gate <P> --require` in the mockup commit; and when `DECOMP` had to ask the design style, that answer must land **before** you declare the gate, because the declaration depends on it. Never by omission: `review-phase --verdict pass` refuses an undeclared phase and names both flags. Phases created before workspace v32 carry no `acceptance` block and need no declaration.
- Durable-doc versioning happens **in a docs phase the operator creates**, not in this phase: no slice runs `doc-new-version` (the review's two named gate sections excepted) — when a slice changes durable truth it appends a one-line "Doc impact" note to `phase.md`, the review verifies that list, and the engine stamps `consolidation: pending` until a docs phase pays it (`docs-debt` for the worklist, `/create-phase`'s docs-phase route to start it, `docs-consolidated <P>` to record it). **In a phase worktree even the gate sections wait**: the branch review records them as `## Doc impact` notes tagged `(gate section — written at merge)`, and the post-merge step on the default stream writes exactly those (`parallel-merge-finish` → `doc-new-version` for the tagged notes → `rebuild-docs`); the rest of the list waits for the docs phase, which records `parallel-consolidated <P>`. Doc versions come from one shared index.
- When you reach the phase review slice, resolve it with `executor-route <P>.REVIEW` (the high row) like any slice and delegate it to `slice-executor-high`. Plan it so the executor validates all of the phase's slices together (each slice's validation commands plus `python3 scripts/workflow.py validate`), reviews against the objective / `intent.md` / docs, and — **on a passing review** — verifies that the phase's "Doc impact" list is complete, returning `doc_versions: none — deferred to a docs phase` (writing only its two named gate sections, never source). **In a phase worktree** (the phase carries an `execution` block with `mode: "parallel"`, because the operator asked for one) it writes no doc versions at all, records the two gate sections as `## Doc impact` notes tagged `(gate section — written at merge)`, and returns `doc_versions: none — deferred to post-merge consolidation (parallel mode)`. A **non-passing verdict stops the executor** before those pass-only steps and hands the phase back to you: it completes validation and judgment first (so you receive the whole picture in one cycle, not one finding per cycle), then returns the verdict with numbered findings and proposed fix slices rather than doing any pass-only work. The review does **not** produce a phase explainer — explaining is a separate operation the operator runs. **When the phase's gate is `required: true`**, plan the review to run the gate stages too: the executor opens the running product itself in the `## Operator Runtime` manifest runtime and spot-checks the phase's headline claims (never passing on other slices' reports alone), walks the surfaces the phase changed with fresh eyes as a first-time user, re-runs the `## Regression Checklist` lines inside the phase's boundary (`python3 scripts/workflow.py phase-scope <P>` — its own surfaces plus every earlier line a changed file feeds, never the whole list) and appends this phase's headline checks, and routes every `## Operator Questions` entry into the walkthrough or into a deferred job for you to file (see the `review-phase` skill). Put `phase-scope <P>`'s output (or the command) in the review's `plan.md`, and never plan the review to re-run the whole list — a plan that says "N lines, read it whole, re-run all of it" is exactly what the boundary rule retires; whatever the review notices outside the boundary comes back as deferred-job candidates for you to file, never as findings. It returns a `review_verdict`, the fixed `explain: not written — run /explain for this phase` pointer, and — on a gated phase — a **`walkthrough`**.
- **On `pass` with a required acceptance gate, the loop ends before the verdict is recorded.** Run `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough the executor returned>"` — the phase goes `pending` — file any deferred jobs the review listed, `validate`, commit, report the walkthrough to the operator, and STOP the loop, exactly as any `pending` item stops it. The operator walks the running product; accepting clears the gate (`python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` — theirs to run, or yours on their explicit say-so) and returns the phase to `in_progress`. On the resume run the `REVIEW` slice is still `in_progress` with its `result.md` carrying `review_verdict: pass` and the gate showing `cleared_at`: record the pass **without re-dispatching the review**. Operator-reported failures are recorded instead as `python3 scripts/workflow.py review-phase <P> --verdict changes_requested --note "operator-reported: ..."` (never refused; it resets the gate) and become `fix` slices the loop completes before re-reviewing. A waived phase, and a legacy phase with no `acceptance` block, record the verdict straight away as before.
- Record the verdict: `python3 scripts/workflow.py review-phase <P> --verdict pass|changes_requested|blocked --reviewer slice-executor-high --note "..."`, then `python3 scripts/workflow.py validate`.
- If the verdict is `changes_requested`, create the executor's proposed fix slices with `python3 scripts/workflow.py new-slice --phase <P> --slice <P.Fn> --name "..." --kind fix --risk <low|high>`, the rating the review proposed: `high` for a fix to a defect in mid-tier work — its `result.md` verdict block reads `tier: mid` — because work the mid tier got wrong never goes back to it, complete them (via the executor), then re-review.
- Only a `pass` verdict marks the phase `done` **and closes the `REVIEW` slice** — `review-phase` does both for you, so do **not** run a separate `finish-slice` for the review slice (the general "run `finish-slice` when a slice finishes" rule above does not apply to the review slice).
- **If the operator asked this phase into its own worktree, a `pass` is what opens its integration:** run the `parallel-phase` sequence — `parallel-gate <P>` from the worktree → `ExitWorktree` (`keep`) → `git pull --ff-only` only if `main` tracks a remote → STOP and ask if anything is staged or a file the merge touches is uncommitted — typically the generated `works/` files after a phase was created here since the stamp, which is workflow state you commit first (git refuses both; never unstage or discard the operator's work) → `git merge --no-ff phase/P<N>-<slug> -m "merge(P<N>): <name>"` → `parallel-merge-finish` → `doc-new-version` + `rebuild-docs` for the `## Doc impact` notes tagged `(gate section — written at merge)` → commit → `parallel-teardown <P>` → commit. A closed gate means STOP and report — never merge past it. **In a nested install** integrate by `parallel-phase` §5's nested form instead: the merge, `parallel-merge-finish` and the commits run as `git -C workflow …`, the host side follows the recorded custom, and nothing is pushed, opened or merged without the operator's word. The rest of the doc debt waits for the operator's docs phase, which records `parallel-consolidated <P>`; push → PR → CI → `gh pr merge` is the remote variant, only when the operator asks. A phase that ran on this stream has nothing to integrate: report its `consolidation: pending` debt to the operator and stop there.
- A passing review leaves the phase `done` in `active/`; do **not** archive it here. Archiving is never this loop's job: it is `/rotate-backlog`'s, which pays the doc debt and archives after the docs phase it runs, or the operator's `archive-all` (once every active phase is done) or `archive-phase <P>` for one phase.
- Do not continue into the next phase.
