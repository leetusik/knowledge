# do-whole-phase

Read `CLAUDE.md` and the phase's `phase.md` — the **bounded phase notebook**, read and written only through `phase-section` (`phase-section <P>` lists its sections, `<P> <name>` prints one), never with `Read`, `Edit` or `Write`; long material sits in `topics/` — run `python3 scripts/workflow.py next` for the pointer, then finish every remaining slice in the current phase only. Read `docs/current/` **sections** just in time, never the whole doc set up front. When unsure of the operator's intent, `intent.md` is the confirmed record of what was asked. `next` reports **the current stream's** active phase: on the default stream it skips phases running in their own worktrees (printing `parallel_phases_elsewhere=<P>:<branch>`), and inside a phase worktree it sees only that phase (printing a `stream=` line); `python3 scripts/workflow.py parallel-status` shows every stream.

You are the ORCHESTRATOR (main thread): you plan each slice, verify, commit, move workflow state, and talk to the operator. Every slice — decomposition, `research`, implementation, `fix`, and the phase **review** — is delegated to the `slice-executor` subagent (mid or high row), one at a time unless a wave runs (below). **One exception: a `co-work` (design) slice runs inline, with dispatched spans (inline → dispatched → inline).** The round's lifecycle and the operator's words stay inline — `design-open`, the handoffs, the read-back, every publish to a job's canvas, `feedback.md`, `SIGNOFF.md`, `design-close` and every commit stay on the main thread — but the **drafting is dispatched to `design-drafter`** (the design subagent, not a slice executor) every round, the **critique to `design-critic`** when a job's critique level asks for it, and the **mockup build is the one span dispatched to a slice executor** (`slice-executor` on the high row, built from the round's record on disk), only when the operator asked for a mockup. See the `design-cowork` skill; the slice ends the run at a `pending` stop. Same contract as `do-next-slice`, looped over the phase.

Rules:

- If a slice or the phase is `pending` (shown `[~]`; `next` prints `WAITING ON OPERATOR`), STOP the loop: it needs operator co-work. Report what you need and do not start, finish, or advance past it. Resume only after the operator clears `pending` back to `in_progress`. When the phase is pending because its **operator acceptance gate** is open (`next` also prints `acceptance_gate=open` and the walkthrough), relay that walkthrough as-is: it clears with `python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]`, not with `set-phase-status`. If you hit such a point mid-slice, set it `pending` with `set-slice-status <slice_id> pending --stop-kind <kind> --on-words "<what the operator's words will do>"` and STOP; the kinds are `wave`, `mockup`, `decision` (a question only the operator answers, a `needs_operator`), `operator-action`, `limit` and `other`, and `next` and the resume card print the kind and the words. **A `co-work` design slice stops `pending` once per wave — twice when a mockup was requested, and once more for each superseding round** — `--stop-kind wave` or `mockup`; in your report say which one this is, and what the operator's words on return will do (the `co-work` rule below). (In a phase worktree a `pending` item halts only its own stream.)
- After each slice, read the executor's returned verdict and `python3 scripts/workflow.py phase-section <P> Now` — that pair is the handoff — plus only the sections the next plan needs (`phase-section <P>` lists them), never the whole notebook. When `next` prints `notebook_over_budget=`, run its `notebook_move=` lines before the next dispatch (`reference/verdicts.md`). Never re-read `works/backlog.md` or `works/state.json` per slice: `next` prints the pointer.
- **After a context compaction** (the `SessionStart` hook has printed `compaction=done source=compact` and the resume card; `next --card` prints it on demand): continue from the card's next action, and read a reference only when that action needs it. An executor dispatched before the compaction is still running (the card lists it under running spans, a wave's `wave:` line every one): wait for its completion notification, never re-dispatch. The mode word (`auto`, `gate`, `plan only`) and any open operator gate are among the summary's kept facts; when in doubt, `intent.md` and `next` are the record.
- **The loop, slice by slice** (each step's procedure is in the reference it names):
  1. **Plan the slice.** The default is `auto`: plan inline, `Write` the full `plan.md`, no approval pause — except a decomposition slice and a slice that spends money, which plan at the gate unless the operator said `auto` explicitly. `gate` (the operator's word) waits for approval of every plan; `plan only` readies plans and runs nothing; a `ready` (`[r]`) slice is dispatched from its approved `plan.md`. **Before you plan the first slice of this run, read `reference/modes.md`.**
  2. **Dispatch one executor**, as a background task, on the engine's route table, and record its return. One executor at a time; while it runs, never write to the repo or move workflow state (a wave: below). Executors never commit, and move no workflow state beyond their own carve-outs. **Before the first dispatch of this run, read `reference/dispatch.md` (resolve → pin → dispatch → record → Explore) and `reference/verdicts.md` (the delegation rules, the verdicts, escalation and the commit).**
  3. **While executor N runs**, you may prepare slice N+1 (only N+1, read-only): read `reference/prep.md` first.
  4. **Act on the verdict:** `done` proceeds; `needs_operator` → set the slice `pending` (`--stop-kind decision` or `operator-action`, `--on-words` from its `operator_need`) and STOP; `blocked` → STOP; `escalate`, or a failed or empty return from a mid-row dispatch → one re-dispatch on the high row; a failed or empty return from a high-row dispatch → STOP (`reference/verdicts.md`).
- **A wave.** A phase whose `DECOMP` declared its slices prints `ready_slices=` and `running_slices=` in `next` (none while a barrier runs alone); there `reference/wave.md`'s *Resume* runs first at every session start, after every compaction and before every start or commit. When `ready_slices=` lists more than one id, or a slice becomes ready while others run, plan, dispatch, finish, commit and stop by `reference/wave.md` in place of steps 1-4 and the one-executor rule above; with one id, or nothing declared, the loop is unchanged.
- When a slice finishes (the executor wrote `result.md`), run `finish-slice <slice_id> --outcome "<one line>"` — the outcome comes from the executor's verdict `summary` and fills the slice's row in the generated `## Slices` table — then `python3 scripts/workflow.py validate`.
- **Before you plan a special slice, read its reference:** a design slice (`kind: co-work`) → `reference/co-work.md`, with the `design-cowork` skill; a decomposition (`kind: decomposition`) → `reference/decomposition.md`, which also declares the phase's acceptance gate; the phase review → `reference/review.md` (the review, the acceptance gate, recording the verdict, fix slices, the doc debt, archiving). An explain phase (`## Explain` in `intent.md`): its decomposition → `reference/explain-decomposition.md`, each chapter slice → `reference/explain-chapter.md`, its review → `reference/explain-review.md`.
- **Worktrees:** the phase runs on this checkout unless the operator asked for a worktree (an explain: its confirmation asked). When they asked, the phase already runs in one, or `next` prints `merge_ready=`, read `reference/worktree.md` before the first slice; it also carries the integration after a `pass`.
- Do not continue into the next phase. (`/do-whole-phases` runs several: `.claude/skills/do-whole-phases/SKILL.md`.)
