# update-workspace

Update the CURRENT repo's agentic-workspace machinery to the latest upstream cornerstone, preserving your own work. Explicit-invocation only. Run this when the cornerstone has changed since you adopted or last synced and you want this repo to match the current version. (For first-time adoption use `/retrofit` instead.)

What it changes: it OVERWRITES machinery (`scripts/workflow.py`, the `.claude/agents/` subagents, every skill under `.claude/skills/`, `works/templates/*`), additively MERGES `.claude/settings.json` (removing only hooks the workspace itself retired, such as v60's `compact-gate`, and moving an `autoCompactWindow` still at a value it shipped; each listed on a `removed:` / `changed:` line), and refreshes the `CLAUDE.md` contract. It PRESERVES everything under `works/` except templates (your state, phases, slices, deferred jobs) and all of `docs/` (your versioned docs). It commits the refresh as its last step and never pushes.

**Nested personal install.** If `workflow/.agentic-nested.json` exists under the current directory, this is a private (nested) install, the default layout since v50: the engine and state live in the nested git repo `workflow/`, and the skills and agents sit untracked in the host's `.claude/`. Run this skill from the host root (never from inside `workflow/`). Every step below applies, and the steps marked **(nested)** differ. Instead of merging `.claude/settings.json` and refreshing `CLAUDE.md`, a nested update merges `.claude/settings.local.json`, refreshes `workflow/CLAUDE.workspace.md` and the managed block in `CLAUDE.local.md`, and never touches a tracked file. **The installer detects the layout itself**, so steps 5 and 7 run the same plain `--update` command for a nested and an at-root install, with no `--nested` or `--at-root`; it refuses, writing nothing, when it finds both layouts at once or when a flag contradicts the one it found. (A downstream still carrying the v49 text of this skill can keep running `--update --nested`: it matches a nested install and works.) A **multi-repo host** (one workspace over several product repos) and the `--to-multi-repo` conversion are covered in the last section.

Preflight (read-only):

1. Confirm a git repo: `git rev-parse --is-inside-work-tree`. If the working tree is dirty (`git status --porcelain` is non-empty), tell the operator and recommend committing or stashing first, so the update lands as a clean, reviewable diff. **(nested)** The update writes only inside `workflow/` and to untracked host files, so check `git -C workflow status --porcelain` instead, and leave the host's own branch and changes alone.
2. Confirm this repo already has the workspace: `works/state.json` (or any `works/phases/active/*/phase.json`) AND `scripts/workflow.py` must exist (**nested:** and `workflow/.agentic-nested.json`). If not, STOP — this repo has not adopted the workspace; use `/retrofit` instead.
3. If `works/.workspace-version.json` exists, read it and report the last-synced commit and time so the operator knows the starting point. Also read its `workspace_version` — the integer version this repo is on (call it **N**). If that key is absent, this repo is **pre-versioning** (adopted before workspace versions existed); note that and treat N as "pre-versioning" in the preview below.

Fetch upstream:

4. Shallow-clone the cornerstone to a temp dir and capture its HEAD commit:

   ```sh
   tmp="$(mktemp -d)"
   git clone --depth 1 https://github.com/leetusik/bootstrap_agentic_workspace.sh.git "$tmp"
   ref="$(git -C "$tmp" rev-parse HEAD)"
   ```

   The clone is a full checkout, so read the upstream version straight from it: the top `## v<M>` heading in `$tmp/CHANGELOG.md` is the **upstream version M**, and the entries under each `## v` describe what that version brings.

Preview the diff (this is the "check what is different" step):

5. First report the version gap, then show the file change-list.

   **Version gap** — compare your local version **N** (from step 3) with the upstream version **M** (the top `## v<M>` in `$tmp/CHANGELOG.md`):
   - N < M: report "workspace vN → upstream vM" and print every `## v` entry in `$tmp/CHANGELOG.md` newer than N (vN+1 … vM) — that is exactly what this sync brings, including any **Migration notes**.
   - Pre-versioning (no local `workspace_version`): say the repo is pre-versioning, then show the upstream `## v` entries and point the operator to `$tmp/CHANGELOG.md` for the full file.
   - N == M: say "already on vM; any file diff below is unreleased upstream drift".

   **File change-list** — run the freshly-cloned installer in dry-run update mode from the repo root; it writes nothing and prints the change-list:

   ```sh
   sh "$tmp/bootstrap_agentic_workspace.sh" . --update --dry-run
   ```

   **(nested)** The same command, run from the host root, detects the nested install (its banner says `(nested, detected)`); it also lists the untracked host files it would change and the clash renames it keeps.

   Show the operator the change-list: machinery files that would be updated (with +added/-removed counts) or added, settings merged, how many files are preserved and unchanged, and the update report below it, every line of it: the `removed:` / `changed:` settings lines, the files listed `stale (ours, unchanged — remove these files)`, the files listed `yours, kept`, and any `intents naming a retired mechanism`.

6. STOP and let the operator review and approve. Do not apply without approval.

Apply (after the operator approves):

7. Run the same installer in update mode, recording the upstream commit so provenance is tracked (this also stamps the upstream `workspace_version` M into `works/.workspace-version.json`):

   ```sh
   SYNCED_COMMIT="$ref" sh "$tmp/bootstrap_agentic_workspace.sh" . --update
   ```

   **(nested)** The same command, run from the host root; the installer detects the layout.

Verify:

8. The installer's update already ran `validate` / `rebuild` (or `next` for a repo without the docs subsystem) and printed the result. It preserves the repo-root `executors.toml` but refreshes the generated `slice-executor` agent file from upstream, so **always** run `python3 scripts/workflow.py sync-agents` after an update to re-apply the preserved per-row overrides. Then run `python3 scripts/workflow.py next` to confirm the current state under the refreshed engine. **Then the route overrides:** run `python3 scripts/workflow.py executor-route` and show the operator every `override=` line. Each is a row the repo's `executors.toml` sets, beside the engine default, or `same as the default` (which stops that row following later defaults). Ask whether to drop each; on a yes, delete that `[claude.<row>]` table and re-run `sync-agents`. Never drop one unasked: the file is the operator's. **Coming from a pre-v23 workspace:** the `low` tier is retired (routing is two-tier now — `risk: low` goes to `slice-executor-mid`, everything else to `slice-executor-high`). The update lists `.claude/agents/slice-executor-low.md` as stale when it still holds what v22 shipped, or as yours, kept when it differs (a `sync-agents` model line counts), and never deletes it; drop any `[claude.low]` block from `executors.toml` — `sync-agents` now rejects that section. **Coming from a pre-v31 workspace:** this workspace ships Claude Code only. The update checks every file under `.agents/` and `.codex/`, `AGENTS.md` and `AGENTS.workspace.md` by content: what v30 shipped there, unchanged, is listed stale; anything else (your own skills in `.agents/skills/`, an `AGENTS.md` your project maintains for other tools) is listed yours, kept, and nothing here writes those paths any more. A leftover `[codex.*]` table in `executors.toml` is a hard error: `executors.toml line <n>: Codex support was removed in workspace v31 — this workspace ships Claude Code only, so drop this section`. **Coming from a pre-v32 workspace:** phases you already have carry no `acceptance` block, so they stay legacy and pass exactly as before; opt a **live** phase into the new operator acceptance gate with `python3 scripts/workflow.py accept-gate <P> --require` (never a `done` one — `validate` would then report it as done with an uncleared gate). `--update` never touches `docs/`, so the seeded `## Operator Runtime` manifest and the rewritten `## Regression Checklist` (the product's cumulative smoke list, re-run by every later phase inside its own boundary — `phase-scope <P>` names the changed files — and whole only by an operator-created QA phase, since v41) reach fresh installs only: add both to your own operations/qa docs with `doc-new-version` — copying the seed text from `installer/payloads/doc_bodies/` in the upstream clone — and fill the manifest in, or the first slice claiming real-browser verification will stop `pending` asking you for it. **Coming from a pre-v42 workspace:** a phase runs on the current checkout, exactly as it always did; the per-phase git worktree (`.claude/worktrees/P<N>-<slug>`, branch `phase/P<N>-<slug>`) is opt-in, reached by asking for it — `worktree` on `/do-next-slice` / `/do-whole-phase`, or `python3 scripts/workflow.py parallel-start <P>` by hand. `.git/info/exclude` gains `.claude/worktrees/` on the first `parallel-start` — nothing to do by hand, and `.gitignore` is untouched. Integration merges locally by default (`git merge --no-ff` after `parallel-gate`); push → PR → CI is the remote variant, and the seeded CI `parallel-gate` job still runs on `phase/*` PRs if you use it. Nothing else to run. **Coming from a v42 workspace:** the default reversed — v42 put every phase in its own worktree at first execution, v43 puts it back on the current checkout unless you ask. Two commands retired into no-ops that write nothing: `parallel-skip <P>` and `new-phase --on-main` (there is nothing left to pin, so a docs phase needs neither). Phases already stamped `execution: {"mode": "parallel"}` keep running in their worktrees and integrate unchanged; phases carrying v42's `execution: {"mode": "default"}` pin keep it and still validate — `parallel-start` refuses them rather than override a deliberate pin, so delete that block from `phase.json` by hand if you later want one in a worktree. Nothing else to run. **Coming from a v65 workspace:** one `slice-executor` replaces the mid/high pair. The update lists `.claude/agents/slice-executor-mid.md` and `.claude/agents/slice-executor-high.md` as stale (by content, their `model:` / `effort:` lines aside); delete both, then run `python3 scripts/workflow.py sync-agents`. A `[claude.high]` full model id is now refused, so use an alias; `[claude.mid]` still takes a full id. The verdict's `tier:` field and `executor-route`'s `tier=` line are now `route:` and `route=`. **Coming from a workspace that ships `.claude/agents/explain-critic.md` (v65 up to v80):** an explain phase's critic is now the knowledge plugin's `knowledge:explain-critic`, and a book needs the plugin at 0.6.0 or later (update it from the `/plugin` panel). The update lists `.claude/agents/explain-critic.md` as stale (by content; a nested host's copy too, renamed or not), and step 9 deletes it; a copy you edited is listed yours, kept. An explain phase already past its outline gate has no `book/research/` for its next chapter to top up: re-run its `DECOMP` (as outline feedback does) before that chapter. **Coming from a workspace whose `executors.toml` sets `[claude.cheap]`:** v83 retired the cheap row (Haiku for docs and qa rated low); `executor-route` and `sync-agents` refuse the table, naming its line, until you delete it, and those slices run on the mid row.

Report and clean up:

9. Act on the update report, then summarize. Remove **only the files listed as stale**, each by its path, never a directory wholesale; remove a directory (`rmdir`) only once its listed files are gone and it is empty. Files listed `yours, kept` stay. Each `intents naming a retired mechanism` line goes to the operator to re-confirm that phase's intent; never edit an `intent.md` yourself. Then list back to the operator every file you removed and every `removed:` / `changed:` settings line, summarize what was updated / added / merged / preserved, and show `git status`. **(nested)** Show `git -C workflow status`, and `git status --porcelain` in the host, which the update must leave as it was.

10. Commit the refresh, without being asked. When step 1 found the tree clean, stage everything the update, `sync-agents` and your removals changed (`git add -A`); when it was dirty and the operator went ahead, stage only the paths the update report and your removals name. Commit on the current branch as `chore: update agentic workspace to v<M>`, in the contract's Commit Convention, and never push. **(nested)** Commit in the nested repo, `git -C workflow add -A && git -C workflow commit -m "chore: update agentic workspace to v<M> (nested)"` (the same clean-tree rule); the host gets no commit. Show the commit, then remove the temp clone: `rm -rf "$tmp"`.

## A multi-repo host

A host that tracks nothing and holds several product repos at depth 1 (`python3 scripts/workflow.py nested-repos` lists them, with each repo's rules files) is updated exactly as above, from the host folder, and `--update` never writes inside a repo. What its preview and report add, to show the operator and not to act on alone:

- **Registry seeding.** On a host that tracks no file and holds at least one depth-1 repo but whose marker has no `repos` yet (a layout made by hand), the first `--update` seeds the registry and switches the `CLAUDE.local.md` block to the multi-repo one. Under a confirmed host-level convention every repo inherits it; otherwise each repo's is inferred from its own history and stays UNCONFIRMED until the operator confirms it (`nested-convention --confirm --repo <name> --text "<conventions>" --trailers allowed|forbidden`).
- **Drift lines.** Once `repos` exists, `--update` never re-detects. For a depth-1 repo the registry lacks it prints one line with the command that takes it in, `nested-repos --add <path>` (plus `--name <name>` for a folder name the registry cannot take). The registry is the operator's to change.
- **A `--map-anchors` note.** When phases hold `host_anchors` shas that are no commit of the host but are commits of exactly one registered repo (repos that moved under the host), it prints `nested-repos --map-anchors <repo>`. Read it, and run it only if it names the right repo: it moves those phases' anchors to `repo_anchors.<repo>`, active and archived phases alike, skips a phase in flight on its own branch, writes `phase.json` files only, and a re-run writes nothing. Commit the result in the nested repo.
- **The AGENTS.md hint.** Claude Code reads no `AGENTS.md` while a `CLAUDE.local.md` sits at the working directory, which every nested install writes. When a registered repo (or a single-repo host) tracks one, the report says to set **Project instructions** to `claude-md-and-agents-md` in `~/.claude/settings.json` (`/config` shows it; Claude Code 2.1.277 or later). The update writes nothing into any repo; pass the line on, and leave the operator's user settings to them.
- **The unstamped-worktree warning.** `validate`, which the update runs, warns when a live host worktree holds git worktrees the phase's stamp does not name (made by hand): `... holds git worktrees it did not stamp ...`. The update still exits 0 and never touches `.claude/worktrees/`. A live set keeps running its own branch's engine, so `parallel-add-repo` exists there only once the phase branch has taken this release (merge the nested repo's default branch into it). Then clear the warning from inside the set with `parallel-add-repo <P> --repo <name>=<branch> --adopt` and merge the phase branch again, or by hand after integrating the branch: `git -C <repo> worktree remove <path>`.
- **Never run `parallel-teardown` on a host whose engine predates the set teardown.** With `--discard-ignored` it silently deletes a hand-made repo worktree inside the host worktree, uncommitted work included. Check that the engine that will run it lists `parallel-add-repo` in `python3 scripts/workflow.py --help`; inside a live set that is the phase branch's copy, not the default checkout's.

### Converting a per-repo nested install: `--to-multi-repo`

A per-repo nested install (the repo is the host, with `<repo>/workflow/`) becomes a multi-repo host at the repo's parent folder. It converts a per-repo nested install only, never an at-root workspace and never a host that is already multi-repo, and only on the operator's word. Use the installer from the upstream clone (`$tmp`, step 4). It takes the repo and no target, and does not combine with `--update`, `--at-root`, `--into-existing`, `--nested`, `--force-empty-ok`, `--name` or `--summary`.

1. Bring the install to the installer's version and commit it first: `--update <repo>`, then the nested commit (steps 7-10), `sync-agents` and `validate`.
2. Preview: `sh "$tmp/bootstrap_agentic_workspace.sh" --to-multi-repo <repo> --dry-run`. It prints every step it would take, or every refusal in one run, and writes nothing. Show it to the operator and STOP for approval. The refusals, all before any write, each naming its fix:
   - no per-repo nested install, an at-root workspace, a marker that already holds `repos`, or a convention that is not the four keys;
   - an install not at the installer's version, or a marker without `installed`;
   - an in-flight worktree pair (`parallel-teardown` it first), or linked worktrees of the nested repo;
   - a dirty nested repo, or an install whose `validate` fails;
   - a parent folder that sits inside a work tree, tracks files, has an unusable `.git` or exclude, holds a `workflow/`, a managed `CLAUDE.local.md` block or a non-repo entry, or whose ignore rules would make a host file visible to git;
   - a repo name the registry cannot take, or a repo that tracks a workspace file.
3. Run the same command without `--dry-run`. In order, it: (1) runs `git init` in the parent and makes the empty commit `chore: start the host history` (a parent that is already a repo tracking nothing keeps its history and gets no commit; with no git identity the init is kept and the closing block prints the commands); (2) moves `<repo>/workflow` to `<parent>/workflow`, the nested repo with its history and branches; (3) runs the plain `--update` at the parent, which seeds the registry: the old repo keeps its convention verbatim, every other repo is inferred and UNCONFIRMED, and the host-level convention (the rules for every repo) starts UNCONFIRMED with nothing inferred; (4) records `converted_from`; (5) runs `nested-repos --map-anchors <repo>`, so every phase's `host_anchors` become `repo_anchors.<repo>` and `phase-scope` gives the same range; (6) cleans the old repo, deleting only workspace files byte-identical to what the installer writes, keeping and listing any you edited, removing only the workspace's entries from `.claude/settings.local.json` and only the managed block from `CLAUDE.local.md`, then shrinking its exclude block to what hides what is left; (7) lists the old repo's leftover worktrees, never deleting one.
4. The closing block says what is left, in order: the nested commit to make (`git -C <parent>/workflow add -A && git -C <parent>/workflow commit -m "chore(works): convert to a multi-repo host"`), the conventions to confirm (`nested-convention --confirm [--repo <name>] --text "<conventions>" --trailers allowed|forbidden`, the host-level one and each UNCONFIRMED repo's), `sync-agents`, and the rollback. Start Claude Code at the parent folder from then on. Lines of the operator's own that stayed in `<repo>/CLAUDE.local.md` are theirs to move to the parent's file.

**Rollback** (the closing block prints it with real paths; the nested repo's history is the backup, and the installer deletes none of the host's files): revert the nested commit (before it is made: `git -C <parent>/workflow reset -q --hard && git -C <parent>/workflow clean -qf`); `mv <parent>/workflow <repo>/workflow`; `sh "$tmp/bootstrap_agentic_workspace.sh" --update <repo>`, which rewrites that repo's installed skills and agents as every `--update` does, so **copy aside the ones the conversion listed as yours first**; then remove the host's own files: its `.claude/skills` and `.claude/agents` copies, `.claude/settings.local.json`, `CLAUDE.local.md`, and the `.git` this run made.

**If it halts** after the move and before the cleanup, it prints `--to-multi-repo stopped after the move, before the old repo was cleaned` with a shorter rollback (`reset --hard` and `clean -qf` in the moved nested repo, then `mv` it back; nothing in the old repo was deleted). Fix what it says and re-run `--to-multi-repo`. Never finish with a plain `--update` at the parent: its registry rule is not the conversion's.
