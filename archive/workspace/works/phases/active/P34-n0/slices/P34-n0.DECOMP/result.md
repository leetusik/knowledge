## Findings that changed the cut

1. **The deploy itself would leak and refuse.** The server's `docs/index.md` is dirty today, so `deploy.sh` would refuse, and it prints `git status --short` (untracked paths included) into the public Actions log when it does. The remote helper uploads `git status --short --branch` as a run artifact on every deploy. An untracked private file that is not excluded therefore reaches GitHub through the deploy. Result: S3's server pre-steps (restore the index, exclude the stray project), and the exclude block as a standing duty for S1 and S2. `info/exclude` keeps every later deploy's status clean.
2. **History rewrite versus the server's rebase loops.** `gitops.push` (on every write) and `deploy.sh` (on every deploy) both rebase local commits onto `origin/main`. After a force-push of rewritten history, the server's old-history commits would be replayed on top and pushed back. Result: S5 resets the server checkout before any write or deploy, and the write pause holds through that reset.
3. **Commit messages leak on their own.** `docs(<project>): add <slug>`. S1 makes sure a private project never reaches `gitops.commit`. S2's unpublish commit names no project. S5 rewords any surviving historical message.
4. **The registry default is `private`.** After S4, every tenant #1 project the operator never toggled public is unpublished, and S5 then purges it. Result: S4 dry-runs first and stops for the operator to confirm the private list. OQ1 asks whether new projects should keep starting private.
5. **The footprint is wider than `docs/<project>/`.** The `.versions` and `.books` trees carry superseded bodies and manifests per project. Every gate, guard, reconcile and purge must cover them (recorded in Decisions as **Footprint**).
6. **Not everything in `docs/` is a project.** Site assets and workspace docs live there too. The reconcile and the purge are driven only by the registry's private set, never by "everything not public".
