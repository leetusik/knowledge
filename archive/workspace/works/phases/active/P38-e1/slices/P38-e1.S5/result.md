## The design

Every rule went inside existing sections. There are no new headings, `§` numbers or Part B markers, no new `## Explain` field and no new `run:` value. The delta is how `full` runs when `prior:` names a version and its dossier is found.

**Where it lives:**
- the card: a `D1d` table row, a sentence on `full`, and one sentence under "Never skip or shorten a stage";
- §1 step 5 (the dossier lookup) and step 7's prose (the offer and the decline word);
- §3.1: the brief's `[ · delta: declined]`, the D0 read of the decline, and the delta block with D1d's five steps and the recheck prompt;
- §3.3: the `D1d` log line and the resume rule;
- §3.4: the delta's `size:` header form, the `angle: carried` question form, step 1 scouting, step 2's carried/open split, step 4's changed-share sizing with a worked example, and step 5's owner;
- §3.5: leads in `known already`;
- §3.6: D3 keeps the carried lines and maps their questions, and D3s keeps their statuses;
- §3.8: D5p counts carried claims; D5 skips them; the swap pool includes them; the records rule;
- §4: the writer reads a carried entry in `prior/`, and the writer gap may pick a carried claim;
- §8: the delta line;
- B9: the `prior/` table row, *A carried id*, the carried ledger line and the library mark.

**1. Finding the prior's dossier (D1d step 1).** Read-only, in this order; the first place that has it wins.
- **The explain phase that published it.** Grep every slice `result.md` under the workspace's `phases/active/*` and `phases/archived/*` for `PRIOR_REL_PATH`. A hit counts when its `## Published` table (or report line) records that `rel_path` at `PRIOR_VERSION`, in a phase whose `intent.md` has `## Explain`. The dossier is that phase's `doc/`; for a chapter a book phase wrote, it is `book/research/` with that chapter's overlays.
- **A legacy dossier.** An earlier skill version kept runs in `<KB_EXPLAIN_STATE>/<run-id>/`. Grep its `*/response.json` for `PRIOR_REL_PATH` and take the one whose `"version"` is `PRIOR_VERSION`.
- **Not found.** That covers none found, two different dossiers in one place, or one with no `ledger.md`/`verify/`. The run logs `D1d: delta: none (no dossier)` and runs as a plain `full` run. It is never a stop.

The key is `rel_path` plus `version`, not `subject`. That pair is what §3.1's prior lookup returns for both a document and a chapter, and what every review's `## Published` records. Subjects drift in wording.

**2. Copy, not link (D1d step 2).** One `python3 -c` command copies `brief.md plan.md run.md library.md ledger.md findings verify prior` into `<DOSSIER>/prior/`, with `pages/` and the drafts never copied. A book chapter adds its overlays.
- I tested it in the scratchpad on the v1 legacy dossier: it copied 792 K, and it is idempotent (`dirs_exist_ok`), so a redo is safe.
- Why copy rather than link: links into another phase's folder break when that phase is archived (the folder moves) or pruned. A legacy dossier is machine-local. The critic and the review read only this phase's committed dossier, and `Read(/<UNIT>/**)` already covers `prior/`.
- Chained versions work by nesting. A v3 copies v2's dossier, including v2's own `prior/`.

**3. The content check (D1d step 3). It checks sources, never claims.** The claims in play are the prior's verified ones:
- `supported`;
- `partial` with its narrower claim;
- `contested` with its `D-` entry, both sides counted.

Each must link a `verified` record.
- **Code.** One `git diff --name-only <source commit> HEAD -- <cited paths>`.
  - A range in an unlisted file is unchanged, with no hashing.
  - A range in a listed file is hashed at HEAD at the same lines by B9's form. The same 16 hex digits mean unchanged.
  - A `@WORKTREE` range is hashed from the file. A WORKTREE citation with no range is changed.
  - A claim about what the code never, only or always does is changed whenever its file changed.
  - A commit git does not know makes every range of that source changed.
  - Why diff first: in the P50-4b hand-run, 3 of v1's 139 recorded hashes do not match their own commit (researcher slips). Diff-first carries them correctly because their files did not change.
- **Web.** One fresh fetch per source, and the saved passage re-found verbatim with `pagetext.py --check`. The reference is the passage text in the prior's findings or verify file, because `pages/` were never committed. A `quote-match: approximate` source cannot be re-found verbatim, so it is changed and not fetched.
- **Who fetches: the recheck.** It is a general subagent on a cheap model (`haiku` on Claude Code, like D0b's probes), with one agent per 20 sources at most, sent in one message as a wave is. Its prompt is given in full: one curl and one convert per source, one `--check` per file, no search and no WebFetch. On the sequential path, the lead runs these calls itself. A recheck that fails twice leaves its sources changed; it is never a stop. The lead's context stays free of ~70 fetch calls.
- A source that fails its check, or cannot be fetched, is **changed**. The claims resting on it become **leads**: their questions stay open, and the owning researcher gets them in `known already`, to find again, never to cite.

**4. Reuse and ids (D1d step 4, B9).**
- **The id form.** A carried id puts `p<N>-` after its letter, where `<N>` is the prior's version:
  - `C-p1-r1-code-04` for a claim, `S-p1-…` for a source, `S-p1-…/P2` for a passage;
  - `C-p1-v2-01` for a counter-claim, `D-p1-03` for a disagreement.
- **Why `p` and not `v`.** `C-v<n>-<seq>` is already the verifier's counter-claim form, and `C-v2-…` would be ambiguous. `p<N>-` cannot collide with `r<n>-`, `ch<k>-r<n>-`, `v<n>-` or `G-r<n>-`.
- **Chains.** An id that already carries a `p<k>-` keeps it, so a v3 keeps v1-origin claims as `C-p1-…`. The entry stays in `prior/` under its id without the prefix, in the file its line names.
- **The ledger line** carries:
  - the claim's status (a `partial` with its narrower claim);
  - its record (`verified prior/verify/…#V-<prior id>-<n>`);
  - its counter-evidence;
  - `reused-from: <prior run-id>/<id there> (<file in prior/>)`.
- **The library line** adds `unchanged: code at <HEAD sha>` or `unchanged: re-found <date>`.
- **Order and questions.** D1d writes these lines first, and every merge keeps them. Their question field is `p<N>-Q<k>` until D3 maps it to the new plan's questions.
- **Scope.** A carried code claim holds at HEAD at its lines, which the check proved.

**5. What is researched (§3.4).**
- **Scouting.** `git diff --stat <prior commit>..HEAD` over the subject's paths; `git log --since=<prior date>` over them and the records; the signed sections marked `new`/`renamed`; the must-cover items `prior/brief.md` lacks; and D1d's leads.
- **Questions.** A question whose prior question (in `prior/plan.md`) was `answered` or `contested`, by claims D1d carried, takes `angle: carried (p<N>-Q<k>, …)` and no researcher. Every other question is open.
- **Size.** `W_Δ = W × open ÷ all questions`, rounded to the nearest 100, on S3's ladder plus two lower rungs (none, then 1). Code researchers take the changed code and the records since; web researchers take the rest; there are none on a side with no open question.
- **Claims.** Shares sum to `W_Δ ÷ 25`. The pick's cap stays `C`.
- **No open question.** D2 sends nothing, D3 merges the carried lines alone, and the gap review still runs.
- **The header line.** `size: W <n> words · delta v<N>: <o> of <q> questions open → W_Δ <d> → <r> researchers (<c> code · <w> web) · new claims ≤ <d ÷ 25> · claims ≤ <C> · carried <k> · ceiling 8 · …`.

**6. With S4 (§3.8).**
- Carried claims are picked like any other and count toward `C`.
- D5 batches only used claims with no record, and a carried claim has its prior's. The one exception is a used main claim with no counter search (deviation 3).
- The swap pool is the unpicked candidates plus the unpicked carried claims. Only swaps with no record join the extra batch. In a v1 every swap is a `candidate` with no record, so this is unchanged.
- The records rule adds "a carried claim its prior's, under `prior/verify/`". The critic can read those, since they are inside the committed dossier.
- The D5p, D5, D5s order, D5g and S4's resume walk are untouched.

**7. The decline word: `from scratch`.**
- §1 step 7's prose says a v2's cost line offers the delta when step 5 found the dossier, names the word, and otherwise says `delta: none (no dossier)`. No `Cost:` line was written; that is S7's.
- At D0 the lead reads it from the request or reply under *Original Input*. It never counts the confirmation's own text, which names the word. The brief's `prior:` line then says `· delta: declined`.
- In D1d, a declined delta only logs `D1d: delta: none (declined)`, and the run is a plain `full` run with the prior read as one source, as today.

**8. §8 report.** `delta: reused <n> claims from v<N> · re-researched <m> questions`, or `delta: none (no dossier | declined)`.

**9. Resume.** D1d writes its `## Log` line last:

    D1d: prior v<N> (<run-id>) at <dossier> · sources: unchanged …, changed … (id: why) · claims carried <k> of <m> | delta: none (…)

A `full` v2 with no `D1d` line runs D1d again, whole. The copy is idempotent, the fetches run again, and the carried lines are rewritten, which is safe because nothing else has written the indexes yet. With the line present, D1d never runs again (§3.3 step 3). Names were added, never renamed: D0–D9 and D5p keep theirs.

**The card's rule.** One sentence: "A delta's carried claims skip no stage: each was verified by its own run, and D1d re-checks its sources by content before carrying it (§3.1)." It is repeated in §3.1's opening.
